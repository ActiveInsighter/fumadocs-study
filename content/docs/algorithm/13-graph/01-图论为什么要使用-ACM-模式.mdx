# 图论为什么要使用 ACM 模式

在很多算法平台上，我们习惯的是“核心代码模式”：题目已经帮你构造好参数，你只需要实现某个函数并返回结果。

图论不太一样。**图的输入本身就是算法的一部分**：顶点如何编号、边如何读入、用邻接表还是邻接矩阵、无向边是否需要存两次、带权边怎样表示，这些都会直接影响后续 DFS、BFS、最短路、最小生成树等算法的写法。

因此，从图论开始，建议统一使用 **ACM / 标准输入输出模式** 训练：自己读取输入、自己构造图、自己调用算法、自己按题目要求输出答案。

<Callout type="info" title="这一篇真正要掌握什么">

不是背一套 `cin` / `scanf` 模板，而是建立一条完整链路：

**题目输入 → 图的存储 → 算法处理 → 结果组织 → 标准输出**。

后面的 DFS、BFS、并查集、最短路、拓扑排序，本质上都会复用这条链路。

</Callout>

## 1. 核心代码模式和 ACM 模式差在哪里

<Cards>
  <Card title="核心代码模式">
    平台通常已经把输入转换成数组、二维数组或对象，你只负责实现核心函数。
  </Card>
  <Card title="ACM 模式">
    你需要从标准输入读取顶点和边，亲自构造图，执行算法，并严格按照格式输出结果。
  </Card>
</Cards>

例如，同样是“从节点 `1` 出发，寻找所有能到达节点 `n` 的路径”，核心代码模式可能直接给你：

```cpp
vector<vector<int>> graph;
```

而 ACM 模式更接近真实笔试：

```text
5 5
1 2
1 3
2 4
4 5
3 5
```

第一行表示有 `5` 个顶点、`5` 条边，后面每一行表示一条有向边。

此时你首先要解决的并不是 DFS，而是：

1. 顶点编号从 `0` 还是从 `1` 开始？
2. 这是有向图还是无向图？
3. 图应该存成邻接表还是邻接矩阵？
4. 如果是带权图，权值存在哪里？
5. 输入规模允许你申请多大的空间？

这些问题如果处理错了，后面的搜索算法即使完全正确，也得不到正确答案。

## 2. 为什么图论尤其需要训练输入

对于数组题，输入通常只是把若干数字放进数组；而对于图论题，输入决定了**图的结构**。

假设有 $n$ 个顶点、$m$ 条边。

### 邻接矩阵

可以申请一个 $n \times n$ 的二维结构：

```cpp
vector<vector<int>> graph(n + 1, vector<int>(n + 1, 0));
```

若存在边 $u \to v$：

```cpp
graph[u][v] = 1;
```

它的优点是判断两点之间是否存在边非常直接，查询通常是 $O(1)$；但空间复杂度为 $O(n^2)$。

当 $n$ 很大而 $m$ 很小时，这会造成明显的空间浪费。

### 邻接表

更常见的写法是：

```cpp
vector<vector<int>> graph(n + 1);
```

读到一条边 $u \to v$ 时：

```cpp
graph[u].push_back(v);
```

空间复杂度通常可以记为 $O(n+m)$，特别适合稀疏图，也是 DFS、BFS、拓扑排序、Dijkstra 等算法中最常见的存储方式。

<Callout type="warn" title="无向图最容易写漏的一行">

如果输入的一条边表示无向边 $u-v$，邻接表通常必须同时加入两个方向：

```cpp
graph[u].push_back(v);
graph[v].push_back(u);
```

只存一个方向，会把无向图错误地变成有向图。

</Callout>

这就是为什么只在 LeetCode 一类平台上做“已经构造好 `graph` 参数”的题目，并不能完全训练图论基本功。

## 3. “会算法”不等于“会写完整图论程序”

以 [LeetCode 797：所有可能的路径](https://leetcode.cn/problems/all-paths-from-source-to-target/description/) 为例，如果题目直接给出邻接表，那么核心工作确实主要是 DFS + 回溯。

但在标准输入输出模式下，还需要自己完成：

```text
输入边
  ↓
构造邻接表 / 邻接矩阵
  ↓
设计 visited、path、result 等状态
  ↓
执行 DFS / BFS
  ↓
把答案转换成题目要求的输出格式
```

因此，图论题建议形成固定检查顺序：

| 检查项 | 需要确认的问题 |
| --- | --- |
| 顶点 | 一共有多少个？编号范围是什么？ |
| 边 | 有向还是无向？是否带权？是否可能有重边、自环？ |
| 存储 | 邻接表还是邻接矩阵？空间是否可接受？ |
| 遍历 | DFS、BFS，还是其他图算法？ |
| 状态 | 是否需要 `visited`？路径是否允许重复经过节点？ |
| 输出 | 输出一个值、一条路径、所有路径，还是多行答案？ |

<Callout title="一个很实用的习惯">

拿到图论题后，**不要第一时间写 DFS / BFS**。

先把“输入是什么、图怎么存、从哪里出发、答案长什么样”写清楚，很多图论错误其实发生在搜索开始之前。

</Callout>

## 4. 输出为什么也值得单独练习

假设从节点 `1` 到节点 `5` 有两条路径：

```text
1 2 4 5
1 3 5
```

如果算法内部保存的是：

```cpp
vector<vector<int>> result;
```

那么核心代码模式往往直接：

```cpp
return result;
```

ACM 模式则要求把二维结果逐行打印出来。

### 不推荐：每个元素后都直接打印空格

```cpp
for (int x : path) {
    cout << x << ' ';
}
cout << '\n';
```

这会产生类似：

```text
1 2 4 5
```

末尾多了一个空格。

多数现代 OJ 使用按 token 比较时不会因此判错，但**不能假设所有判题器都会忽略格式差异**。更稳妥的习惯是从一开始就输出标准格式。

### 推荐：只在元素之间输出分隔符

```cpp
for (int i = 0; i < path.size(); ++i) {
    if (i > 0) cout << ' ';
    cout << path[i];
}
cout << '\n';
```

这种写法有三个优点：

- 不会产生行尾多余空格；
- 不需要单独处理“最后一个元素”；
- 即使 `path` 为空，也不会访问越界。

<Callout type="warn" title="不要写成 size() - 1 的危险循环">

下面这种写法在非空数组时可以工作：

```cpp
for (int i = 0; i < path.size() - 1; ++i) { ... }
```

但 `size()` 通常是无符号类型。当容器为空时，`size() - 1` 可能发生无符号下溢。

算法模板最好优先选择天然覆盖空容器的写法。

</Callout>

## 5. 图论 ACM 模式的标准解题框架

以后遇到图论题，可以先按下面这套骨架组织程序：

```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n, m;
    cin >> n >> m;

    // 1. 构造图
    vector<vector<int>> graph(n + 1);

    for (int i = 0; i < m; ++i) {
        int u, v;
        cin >> u >> v;
        graph[u].push_back(v);
    }

    // 2. 初始化算法状态
    // vector<bool> visited(n + 1, false);
    // vector<int> path;
    // ...

    // 3. 执行 DFS / BFS / 最短路 / 并查集等算法

    // 4. 输出结果

    return 0;
}
```

这段模板最重要的不是代码本身，而是它把程序划分成了四层：

```text
读入 → 建图 → 算法 → 输出
```

后续学习图论时，尽量保持这四层清晰分离。这样当答案错误时，你可以快速定位：

- 是输入读错了；
- 是建图方向错了；
- 是算法状态错了；
- 还是输出格式错了。

## 6. 常见输入形式一览

### 无权有向图

输入：

```text
u v
```

表示：

$$
u \to v
$$

邻接表：

```cpp
graph[u].push_back(v);
```

### 无权无向图

输入：

```text
u v
```

表示：

$$
u \leftrightarrow v
$$

邻接表：

```cpp
graph[u].push_back(v);
graph[v].push_back(u);
```

### 带权有向图

输入：

```text
u v w
```

表示从 $u$ 到 $v$ 有一条权值为 $w$ 的边：

$$
u \xrightarrow{w} v
$$

可以存成：

```cpp
vector<vector<pair<int, int>>> graph(n + 1);
graph[u].push_back({v, w});
```

### 带权无向图

```cpp
graph[u].push_back({v, w});
graph[v].push_back({u, w});
```

<Callout type="info" title="后续算法和存储结构的关系">

- DFS / BFS：常用无权邻接表或邻接矩阵；
- Dijkstra：常用 `邻接表 + (终点, 权值)`；
- Kruskal：常常直接保存边集合 `(u, v, w)`；
- Floyd：通常更适合邻接矩阵；
- 拓扑排序：除了邻接表，还经常维护每个节点的入度。

所以“图怎么存”不是固定答案，而是算法设计的一部分。

</Callout>

## 7. 做图论题前的 30 秒自检

在真正开始写算法前，可以快速检查：

- [ ] 顶点编号是 `0 ~ n-1` 还是 `1 ~ n`？
- [ ] 一共有 $m$ 条边，是否恰好读了 $m$ 次？
- [ ] 有向图还是无向图？
- [ ] 无向边是否存了两个方向？
- [ ] 是否带权？权值类型用 `int` 还是 `long long`？
- [ ] 是否可能出现重边、自环？
- [ ] 邻接矩阵的 $O(n^2)$ 空间能否接受？
- [ ] 输出是否要求固定顺序？
- [ ] 多组答案之间如何换行、空格分隔？

只要这张清单形成习惯，后面很多“算法看懂了但代码就是过不了”的问题会大幅减少。

## 8. 一份可直接复用的多语言建图模板

下面统一以 **$n$ 个顶点、$m$ 条无权有向边、顶点编号从 `1` 开始** 为例。若题目是无向图，只需要再加入反向边。

```cpp tab="C++" tab-group="graph-acm-template"
#include <bits/stdc++.h>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n, m;
    cin >> n >> m;

    vector<vector<int>> graph(n + 1);

    for (int i = 0; i < m; ++i) {
        int u, v;
        cin >> u >> v;
        graph[u].push_back(v);

        // 无向图时再加入：
        // graph[v].push_back(u);
    }

    // 示例：按邻接表内容输出，便于检查建图是否正确
    for (int u = 1; u <= n; ++u) {
        cout << u << ':';
        for (int v : graph[u]) {
            cout << ' ' << v;
        }
        cout << '\n';
    }

    return 0;
}
```

```java tab="Java"
import java.io.*;
import java.util.*;

public class Main {
    public static void main(String[] args) throws Exception {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        StringTokenizer st = new StringTokenizer(br.readLine());

        int n = Integer.parseInt(st.nextToken());
        int m = Integer.parseInt(st.nextToken());

        List<List<Integer>> graph = new ArrayList<>(n + 1);
        for (int i = 0; i <= n; ++i) {
            graph.add(new ArrayList<>());
        }

        for (int i = 0; i < m; ++i) {
            st = new StringTokenizer(br.readLine());
            int u = Integer.parseInt(st.nextToken());
            int v = Integer.parseInt(st.nextToken());
            graph.get(u).add(v);

            // 无向图时再加入：
            // graph.get(v).add(u);
        }

        StringBuilder out = new StringBuilder();
        for (int u = 1; u <= n; ++u) {
            out.append(u).append(':');
            for (int v : graph.get(u)) {
                out.append(' ').append(v);
            }
            out.append('\n');
        }

        System.out.print(out);
    }
}
```

```go tab="Go"
package main

import (
    "bufio"
    "fmt"
    "os"

func main() {
    in := bufio.NewReader(os.Stdin)
    out := bufio.NewWriter(os.Stdout)
    defer out.Flush()

    var n, m int
    fmt.Fscan(in, &n, &m)

    graph := make([][]int, n+1)

    for i := 0; i < m; i++ {
        var u, v int
        fmt.Fscan(in, &u, &v)

        // 无向图时再加入：

    for u := 1; u <= n; u++ {
        fmt.Fprintf(out, "%d:", u)
        for _, v := range graph[u] {
            fmt.Fprintf(out, " %d", v)
        }
        fmt.Fprintln(out)
    }
}
```

## 总结

图论统一训练 ACM 模式的核心原因只有一句话：

> **图的“构造”本身就是图论能力的一部分。**

真正完整的图论能力，不只是会写 DFS、BFS 或最短路，而是能够独立完成：

$$
\text{输入解析}
\rightarrow
\text{图的建模与存储}
\rightarrow
\text{算法求解}
\rightarrow
\text{规范输出}
$$

从下一篇开始，再系统学习图的基本概念、邻接矩阵、邻接表以及图的遍历方式时，这套输入输出框架会成为整个图论模块的基础。
