# 动态规划理论基础

动态规划（Dynamic Programming，简称 **DP**）不是“背公式”的算法，而是一种**把大问题拆成相互重叠的子问题，并系统保存子问题答案**的思考方式。

如果只能记住一句话，可以记住：

> **动态规划的核心，是先定义“状态表示什么”，再说明“这个状态怎样由已经算出的状态转移而来”。**

![](https://file1.kamacoder.com/i/algo/动态规划-总结大纲1.jpg)

<Callout type="info" title="学习目标">
学完这一节，你应当能独立回答五个问题：`dp` 数组表示什么、状态如何转移、初始状态是什么、按什么顺序计算、怎样验证自己的状态设计是否正确。
</Callout>

## 1. 什么是动态规划

### 1.1 从递归到动态规划

许多动态规划问题，都可以先写成一个递归问题。

以斐波那契数列为例：

$$
F(n)=F(n-1)+F(n-2)
$$

如果直接递归计算 `F(n)`，`F(n-2)`、`F(n-3)` 等子问题会被反复求解。动态规划做的事情就是：

1. 把已经得到的子问题结果保存下来；
2. 后续再次需要时直接使用；
3. 按照依赖关系，从较小状态逐步推出较大状态。

因此，动态规划通常特别适合存在**重叠子问题**的问题。

### 1.2 三个最重要的特征

可以用下面三个概念判断一道题是否具有明显的动态规划特征。

| 特征 | 含义 | 观察方式 |
| --- | --- | --- |
| 重叠子问题 | 不同决策会反复遇到同一个子问题 | 递归树中出现相同参数 |
| 状态可递推 | 当前答案能够由规模更小的状态得到 | 可以写出状态转移关系 |
| 最优子结构 | 原问题最优解可以建立在子问题最优解之上 | 常见于最值问题 |

需要注意：**不是所有动态规划问题都要求“求最优值”**。计数问题、可行性问题同样可以使用 DP，例如“有多少种方案”“是否能够到达”。

### 1.3 动态规划与贪心的区别

动态规划和贪心经常都用于最优化问题，但两者的决策方式不同。

假设有 $N$ 件物品，第 $i$ 件物品重量为 $weight[i]$，价值为 $value[i]$，背包容量为 $W$，每件物品最多选择一次。

01 背包的一维状态转移可以写成：

$$
dp[j]=\max\bigl(dp[j],\ dp[j-weight[i]]+value[i]\bigr)
$$

这里当前状态 `dp[j]` 明确依赖之前已经计算出的状态 `dp[j-weight[i]]`。

而贪心通常是在当前步骤根据某个局部规则直接做选择，例如“优先选择价值最大”“优先选择重量最小”或“优先选择单位价值最高”。局部最优选择并不天然保证整体最优，因此 01 背包不能直接用普通贪心解决。

<Callout type="warning" title="不要用一句话机械区分 DP 与贪心">
“DP 看过去状态，贪心只看当前”只是直觉描述。真正做题时，更重要的是分析：当前局部最优选择是否具有可证明的贪心性质；如果没有，就要考虑枚举状态并通过递推得到全局答案。
</Callout>

## 2. 动态规划到底在“规划”什么

动态规划最关键的对象是**状态**。

所谓状态，就是：

> 用尽可能少的信息，完整描述一个子问题。

例如：

- `dp[i]`：到达第 `i` 级台阶的方法数；
- `dp[i][j]`：考虑前 `i` 个物品、背包容量为 `j` 时的最大价值；
- `dp[i][j]`：字符串 `s[0..i-1]` 和 `t[0..j-1]` 的最长公共子序列长度；
- `dp[i][0/1]`：第 `i` 天处于“不持股 / 持股”状态时的最大现金。

一个好的状态定义应该满足两点：

1. **信息足够**：能够支持后续状态转移；
2. **信息不过量**：不会把无关历史全部塞进状态，导致维度爆炸。

### 2.1 状态设计的本质：保留“未来仍然需要的信息”

例如股票问题中，未来决策通常只关心“当前是否持股”和“当前最大收益”，并不需要保留此前每一次买卖的完整历史。

这就是状态压缩背后的本质：

> **历史发生了什么不重要，重要的是历史对未来还留下了哪些影响。**

## 3. 动态规划五步法

动态规划最稳定的做题方式，可以固定为下面五步。

### 第一步：确定 `dp` 数组及下标含义

这是最重要的一步。

不要一看到题目就先写递推公式，而应该先完整说出：

> `dp[...]` 到底表示什么？

例如爬楼梯：

$$
dp[i]=\text{到达第 }i\text{ 级台阶的方法数}
$$

例如最长递增子序列：

$$
dp[i]=\text{以 }nums[i]\text{ 结尾的最长严格递增子序列长度}
$$

注意“以 `nums[i]` 结尾”这一限定极其重要。如果只写“前 `i` 个数的最长递增子序列”，状态转移就会完全不同。

<Callout type="tip" title="检查状态定义的方法">
把代码中的 `dp[i]` 替换成你写出的中文定义，看看状态转移式是否仍然通顺。如果读不通，通常意味着状态定义不够准确。
</Callout>

### 第二步：推导状态转移方程

状态转移回答的是：

> **当前状态有哪些来源？**

例如爬楼梯，每次可以爬 1 级或 2 级，那么到达第 `i` 级只能来自：

- 从 `i-1` 级再走 1 步；
- 从 `i-2` 级再走 2 步。

因此：

$$
dp[i]=dp[i-1]+dp[i-2]
$$

如果是最值问题，则常见形式是：

$$
dp[i]=\max(\text{若干个前驱状态})
$$

如果是计数问题，则常见形式是：

$$
dp[i]=\sum \text{所有可行前驱状态}
$$

如果是可行性问题，则常见形式是：

$$
dp[i]=\bigvee \text{所有可行前驱状态}
$$

这里的 `max / sum / or`，往往对应了题目的三大类型：**最值、计数、是否可行**。

### 第三步：确定初始化

初始化不是随便把数组填成 `0`。

初始化应当来自状态定义和转移方程。

例如：

$$
dp[0]=1
$$

有时并不是说“第 0 级台阶真的有一种爬法”，而是为了让后续递推具有统一形式。

在最小值问题中，未知状态常常需要初始化为一个足够大的值：

$$
dp[i]=+\infty
$$

在最大值问题中，某些不可能状态可能需要初始化为：

$$
dp[i]=-\infty
$$

<Callout type="warning" title="初始化必须区分“真实的 0”与“尚未到达”">
如果 `0` 本身就是合法答案，那么用 `0` 同时表示“未计算 / 不可达”就会引起歧义。此时应使用 `INF`、`-INF`、`false` 或额外标记。
</Callout>

### 第四步：确定遍历顺序

遍历顺序取决于状态依赖。

核心原则只有一句：

> **计算某个状态时，它依赖的状态必须已经被计算出来。**

例如：

$$
dp[i]=dp[i-1]+dp[i-2]
$$

显然应从小到大遍历 `i`。

二维 DP 中，如果：

$$
dp[i][j]\leftarrow dp[i-1][j],\ dp[i][j-1]
$$

那么通常需要从左上向右下计算。

背包问题的一维滚动数组尤其需要注意遍历方向：

- **01 背包**：容量通常从大到小遍历，避免一个物品被重复使用；
- **完全背包**：容量通常从小到大遍历，允许同一物品重复使用。

因此，遍历顺序不是模板习惯，而是**状态依赖关系的直接结果**。

### 第五步：手工推导小规模 `dp` 表

写代码前，至少选择一个很小的样例，手工列出完整状态。

例如爬楼梯：

| `i` | 0 | 1 | 2 | 3 | 4 | 5 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `dp[i]` | 1 | 1 | 2 | 3 | 5 | 8 |

然后检查：

1. 初始化是否正确；
2. 每一步是否符合状态转移；
3. 最终答案是否位于你认为的位置。

这一步看似慢，实际上可以大幅减少调试时间。

## 4. 一个完整例子：斐波那契数

以 LeetCode 509 为例：

$$
F(0)=0,\qquad F(1)=1
$$

且：

$$
F(n)=F(n-1)+F(n-2),\qquad n\ge 2
$$

### 4.1 五步分析

### 状态

定义：

$$
dp[i]=F(i)
$$

即 `dp[i]` 表示第 `i` 个斐波那契数。

### 转移

由题意：

$$
dp[i]=dp[i-1]+dp[i-2]
$$

### 初始化

$$
dp[0]=0,\qquad dp[1]=1
$$

### 顺序

因为 `dp[i]` 依赖 `dp[i-1]` 和 `dp[i-2]`，所以 `i` 必须从小到大遍历。

### 结果

最终答案为：

$$
dp[n]
$$

### 4.2 从二维思维到空间优化

如果一个状态只依赖前两个状态，就没有必要保存完整数组。

原始空间复杂度：

$$
O(n)
$$

只保留两个前驱状态后：

$$
O(1)
$$

这就是滚动数组或状态压缩的基本思想。

<Callout type="info" title="状态压缩的前提">
只有当旧状态未来不再需要时，才能安全覆盖。不要为了追求 $O(1)$ 空间而在还没弄清状态依赖时过早压缩。
</Callout>

## 5. 自顶向下与自底向上

动态规划通常有两种实现方式。

### 5.1 记忆化搜索：自顶向下

先从原问题开始递归，需要哪个子问题就计算哪个，并把结果缓存起来。

优点：

- 写法接近原始递归思路；
- 只计算真正访问到的状态。

缺点：

- 有递归调用开销；
- 可能受到递归深度限制；
- 状态依赖不够直观时，调试较困难。

### 5.2 递推 DP：自底向上

从最小状态开始，按照依赖顺序逐步计算到目标状态。

优点：

- 计算顺序明确；
- 容易分析时间与空间复杂度；
- 更便于做滚动数组优化。

多数基础 DP 题更推荐优先掌握自底向上的写法。

## 6. 动态规划与普通递归的复杂度差异

斐波那契的朴素递归会构造大量重复分支，时间复杂度呈指数增长，通常记作：

$$
O(2^n)
$$

使用动态规划后，每个状态只计算一次：

$$
O(n)
$$

如果一共有 $S$ 个状态，每个状态需要枚举 $T$ 种转移，那么很多 DP 的时间复杂度都可以用统一框架分析：

$$
O(S\times T)
$$

例如二维背包有大约 $N\times W$ 个状态，每个状态做常数次转移，因此时间复杂度通常为：

$$
O(NW)
$$

这种“**状态数 × 每个状态的转移代价**”的分析方法非常通用。

## 7. 动态规划的常见题型

可以先建立下面这张知识地图。

| 类型 | 典型状态 | 常见目标 |
| --- | --- | --- |
| 线性 DP | `dp[i]` | 爬楼梯、打家劫舍、LIS |
| 网格 DP | `dp[i][j]` | 不同路径、最小路径和 |
| 背包 DP | `dp[i][j]` / `dp[j]` | 最大价值、方案数、能否装满 |
| 区间 DP | `dp[l][r]` | 回文、区间合并 |
| 序列 DP | `dp[i][j]` | LCS、编辑距离 |
| 状态机 DP | `dp[i][state]` | 股票买卖 |
| 树形 DP | `dp[u][state]` | 树上选择、不相邻节点 |

后续学习时，不要把它们看成彼此独立的几十种模板。它们本质上仍然围绕：

> **状态定义 → 转移来源 → 初始状态 → 计算顺序。**

## 8. 动态规划如何调试

DP 出错时，最有效的方法不是不断修改代码，而是**把状态表打印出来，与手工推导结果比较**。

推荐按下面顺序排查。

### 8.1 第一层：状态定义是否正确

先问自己：

- `dp[i]` 或 `dp[i][j]` 到底是什么？
- 最终答案真的在 `dp[n]` / `dp[n][m]` 吗？
- 是否遗漏了必须记录的状态信息？

### 8.2 第二层：转移方程是否漏情况

对于每个当前状态，检查所有来源：

- 选择 / 不选择；
- 买 / 卖 / 不操作；
- 左边 / 上边 / 斜上方；
- 最后一步来自哪里。

很多错误本质上是少枚举了一种合法来源。

### 8.3 第三层：初始化是否与语义一致

重点检查：

- `dp[0]` 的含义；
- 空字符串、空集合、容量 0 等边界；
- 不可达状态是否误初始化为 0。

### 8.4 第四层：遍历顺序是否破坏依赖

尤其是一维背包、区间 DP、状态压缩题，顺序错误会直接导致“读取了本轮刚刚修改过的状态”。

### 8.5 第五层：打印 `dp` 表

可以打印：

- 每一轮外层循环后的数组；
- 二维表每一行；
- 关键状态的转移来源。

如果程序打印出的状态与手工推导不同，说明是实现问题；如果二者一致但答案仍错，说明你的**状态设计或递推逻辑本身有问题**。

<Callout type="tip" title="DP 调试三问">
1. 我是否手工推导过一个小样例？
2. 我是否打印过关键 `dp` 状态？
3. 程序得到的状态是否与手算完全一致？
</Callout>

## 9. 常见误区

### 误区一：只背状态转移公式

同一个公式放在不同状态定义下，含义可能完全不同。公式不是 DP 的起点，**状态定义才是**。

### 误区二：认为所有数组都初始化为 0

初始化必须符合语义。特别是最小值、不可达状态和状态机 DP，错误初始化很容易让非法路径参与转移。

### 误区三：认为循环顺序只是代码风格

错误。循环顺序是状态依赖的一部分。01 背包和完全背包最典型。

### 误区四：一上来就空间压缩

先写正确的二维或完整一维状态，再分析依赖范围，最后压缩。学习阶段不要为了少几个变量而牺牲可读性。

### 误区五：看到“最优”就用 DP

最优化问题还可能使用贪心、图最短路、二分答案、搜索等方法。是否使用 DP，要看问题能否设计出合理状态并形成可复用的子问题。

## 10. 一套可以直接套用的分析模板

遇到一道新的 DP 题，可以先在草稿上写下面六行：

```text
1. 状态：dp[...] 表示什么？
2. 答案：题目最终要求哪个状态？
3. 转移：当前状态来自哪些前驱状态？
4. 初始化：最小规模问题的答案是什么？
5. 顺序：怎样保证前驱状态先被算出？
6. 复杂度：状态数 × 单状态转移代价是多少？
```

如果这六个问题能够完整回答，代码实现通常只是最后一步。

## 11. 示例代码：斐波那契数

### C++

```cpp
class Solution {
public:
    int fib(int n) {
        if (n <= 1) return n;

        int prev2 = 0;
        int prev1 = 1;

        for (int i = 2; i <= n; ++i) {
            int cur = prev1 + prev2;
            prev2 = prev1;
            prev1 = cur;
        }

        return prev1;
    }
};
```

### Java

```java
class Solution {
    public int fib(int n) {
        if (n <= 1) return n;

        int prev2 = 0;
        int prev1 = 1;

        for (int i = 2; i <= n; i++) {
            int cur = prev1 + prev2;
            prev2 = prev1;
            prev1 = cur;
        }

        return prev1;
    }
}
```

### Python

```python
class Solution:
    def fib(self, n: int) -> int:
        if n <= 1:
            return n

        prev2, prev1 = 0, 1

        for _ in range(2, n + 1):
            prev2, prev1 = prev1, prev1 + prev2

        return prev1
```

### JavaScript

```javascript
var fib = function(n) {
  if (n <= 1) return n;

  let prev2 = 0;
  let prev1 = 1;

  for (let i = 2; i <= n; i++) {
    const cur = prev1 + prev2;
    prev2 = prev1;
    prev1 = cur;
  }

  return prev1;
};
```

## 12. 本节总结

动态规划学习最容易陷入“看懂题解、记住公式、下次仍然不会”的循环。解决办法不是背更多模板，而是坚持把每一道题拆成稳定的分析流程。

<Cards>
  <Card title="先定义状态" icon="Braces">
    明确 `dp` 数组每个维度和下标的含义，这是所有递推的基础。
  </Card>
  <Card title="再找状态来源" icon="GitBranch">
    从“最后一步从哪里来”或“当前有哪些选择”推导状态转移。
  </Card>
  <Card title="初始化服从语义" icon="CircleDot">
    初始值必须与状态定义一致，而不是习惯性全部填 0。
  </Card>
  <Card title="顺序服从依赖" icon="ArrowRight">
    保证每个状态计算时，依赖的前驱状态已经准备好。
  </Card>
</Cards>

最终可以把动态规划浓缩成一句更完整的话：

> **定义最小充分状态，枚举所有合法转移，按照依赖顺序计算，并保存可复用的子问题结果。**

下一阶段再进入具体题型时，无论是基础线性 DP、背包、股票、子序列还是编辑距离，都可以不断回到这套框架中检查自己的思路。
