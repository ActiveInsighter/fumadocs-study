## 应用层概览与网络应用模型

**本章整体框架与考情分析**

**应用层究竟研究什么？** 应用层是 TCP/IP 协议体系中直接向网络应用程序提供服务的最高层。 学习应用层，不应仅仅记忆协议名称，而应理解：

1. 一个网络应用由哪些进程构成？
2. 客户端和服务器如何交换信息？
3. 使用 TCP 还是 UDP？
4. 使用什么端口号？
5. 需要建立多少条连接？
6. 不同请求之间是否存在先后依赖？
7. 发送请求到接收结果需要多少时间？

例如，在浏览器输入 `http://www.example.com/index.html` 后，可能依次发生：

```text
用户输入 URL
      ↓
检查域名解析缓存
      ↓
DNS 解析域名
      ↓
得到 Web 服务器 IP
      ↓
查询本机路由表
      ↓
必要时通过 ARP 获取下一跳 MAC
      ↓
TCP 三次握手
      ↓
发送 HTTP GET
      ↓
服务器返回 HTML
      ↓
浏览器解析 HTML
      ↓
请求图片、CSS、JavaScript 等资源
      ↓
页面加载完成
```

这一个过程可能综合考查：应用层：DNS、HTTP；传输层：TCP、UDP、端口、拥塞控制；网络层：IP、路由、NAT；数据链路层：ARP、以太网、交换机自学习。 因此，应用层既有基础概念选择题，也很适合出跨层综合大题。

### 6.1 网络应用模型

**什么是网络应用？** 网络应用的本质，是不同主机上的应用进程通过网络交换数据。 例如：

```text
用户电脑上的浏览器
          ↓
         网络
          ↓
服务器上的 Web 服务进程
```

应用进程通过传输层提供的服务进行通信。 在经典 TCP/IP 模型中：

```text
应用层：HTTP、FTP、DNS、SMTP
          ↓
传输层：TCP、UDP
          ↓
网络层：IP
          ↓
链路层：以太网等
```

特别注意：应用层协议定义应用进程如何交换消息，但不负责实现 TCP 的可靠传输、拥塞控制等机制。

**客户/服务器模型 C/S** C/S 即 Client/Server。 基本结构：

```text
客户端 A ──请求──┐
                 │
客户端 B ──请求──┼──服务器
                 │
客户端 C ──请求──┘
```

**客户端特点**

1. 主动发起服务请求；
2. 通常不需要长期运行；
3. 通常需要知道服务器地址；
4. 可以使用临时端口；
5. 同一个客户端可以访问多个服务器。

**服务器特点**

1. 通常长期运行；
2. 监听特定服务端口；
3. 提供服务和资源；
4. 地址相对稳定；
5. 可能同时为大量客户端服务。

例如：

```text
浏览器：客户端
Web 服务器：服务器

浏览器主动建立 TCP 连接
          ↓
Web 服务器接收连接
          ↓
浏览器发送 HTTP 请求
          ↓
服务器返回 HTTP 响应
```

**高频易错点一：服务器是否必须知道客户端地址？** 不需要预先知道。 服务器只需监听指定端口。 当客户端发来请求时，服务器可以从收到的 IP 分组、TCP 连接信息中获知客户端的地址和端口。 所以： “客户端和服务器必须事先知道彼此的 IP 地址。” 错误。

**高频易错点二：服务器能不能主动发送数据？** 可以。 客户端主动建立连接，不意味着连接建立后只有客户端能发送。 TCP 是全双工通信。 例如：

```text
客户端发送 HTTP GET
          ↓
服务器返回 HTML
```

服务器显然可以发送响应数据。 需要区分：

- 谁主动建立连接；
- 谁发送应用数据。

这是两个不同概念。

**高频易错点三：客户端之间能不能通信？** 在典型的 C/S 应用组织方式中，客户端之间的业务交互通常经由服务器。 但是不能扩大理解为： “两个运行客户端程序的主机在任何情况下都不能直接通信。” 如果它们另外建立直接连接，就可以直接通信。 考试应按题目讨论的应用模型判断。

**C/S 模型优缺点** 优点：管理集中；资源容易统一管理；权限控制方便；服务质量容易统一维护。 缺点：服务器可能成为瓶颈；中心服务器可能存在单点故障；服务器需要承担大量上传和处理任务。 例如：一个服务器给 1000 个用户发送相同文件。 如果所有文件都由服务器上传，那么服务器的上传能力可能成为限制因素。

**P2P 模型** P2P 即 Peer-to-Peer，对等网络。 基本结构：

```text
节点 A ←────→ 节点 B
   ↑             ↑
   │             │
   ↓             ↓
节点 C ←────→ 节点 D
```

每个节点都可以：下载资源；上传资源；请求服务；提供服务。 因此：一个节点既可能充当客户端，也可能充当服务器。 典型例子： BitTorrent 文件共享。

**P2P 的核心特点** 资源由多个节点共同提供。 例如：

```text
节点 A 下载文件块 1
节点 B 下载文件块 2
节点 C 下载文件块 3
```

三个节点可以互相交换已获得的文件块。 节点越多，总上传能力可能越强。

**重要提醒** P2P 不意味着完全不存在中心服务器。 P2P 系统可能使用：

- 登录服务器；
- 目录服务器；
- 追踪器；
- 节点发现服务。

只要主要资源能够由对等节点之间直接交换，就可以具有 P2P 特征。

**C/S 与 P2P 对比**

| 比较项目 | C/S | P2P |
|---|---|---|
| 角色 | 客户和服务器相对明确 | 节点角色对等 |
| 服务提供 | 主要由服务器承担 | 节点共同承担 |
| 资源分布 | 相对集中 | 相对分散 |
| 管理 | 集中 | 分散 |
| 扩展性 | 受服务器资源影响 | 新节点可贡献资源 |
| 典型应用 | Web、FTP | P2P 文件共享 |
| 是否必然更安全 | 否 | 否 |
| 是否可能有中心组件 | 是 | 是 |

**文件分发时间模型** 这是理解 P2P 扩展性的重要方法。 假设：文件大小为 $F$ bit；有 $N$ 个客户端下载；服务器上传速率为 $u_s$；第 $i$ 个客户端上传速率为 $u_i$；第 $i$ 个客户端下载速率为 $d_i$；最小下载速率为 $d_{\min}$。

**C/S 文件分发** 服务器必须上传总共 $NF$ bit。 因此： $D_{CS}\geq\frac{NF}{u_s}$ 最慢客户端需要至少： $D_{CS}\geq\frac{F}{d_{\min}}$ 所以理想模型中的分发时间下界为：

$$
\boxed{
D_{CS}\geq
\max\left\{
\frac{NF}{u_s},
\frac{F}{d_{\min}}
\right\}
}
$$

**P2P 文件分发** 服务器至少需要上传一份文件： $D_{P2P}\geq\frac{F}{u_s}$ 最慢客户端下载一份文件需要： $D_{P2P}\geq\frac{F}{d_{\min}}$ 系统总共要传输 $NF$ bit。 总上传能力为： $u_s+\sum_{i=1}^{N}u_i$ 因此：

$$
\boxed{
D_{P2P}\geq
\max\left\{
\frac{F}{u_s},
\frac{F}{d_{\min}},
\frac{NF}{u_s+\sum_{i=1}^{N}u_i}
\right\}
}
$$

结论： C/S 中，服务器上传总量随客户端数量线性增长。 P2P 中，新节点可能同时增加下载需求和上传能力。 这解释了为什么 P2P 在大规模文件分发中通常更有扩展性。

**真题：2019 年网络应用模型** 题目问：下列关于网络应用模型的叙述，错误的是哪项？ A. P2P 模型中节点之间具有对等关系 B. C/S 模型中客户与客户之间可以直接通信 C. C/S 模型中客户端主动发起通信 D. P2P 文件分发通常具有更好的扩展能力

**答案**

**B**

**解析** A 正确： P2P 节点在逻辑上处于对等地位。 B 错误：在题目所讨论的典型 C/S 应用模型中，业务通信主要通过服务器进行。 C 正确：客户端主动请求，服务器通常被动等待初始连接。 D 正确： P2P 节点可以同时下载与上传资源。

**本题总结** 遇到 C/S、P2P 题，主要检查：

1. 角色是否固定；
2. 谁主动请求；
3. 谁提供资源；
4. 扩展能力是否依赖中心服务器；
5. 是否出现“必然、更安全、完全没有服务器”等绝对表述。

## DNS：域名解析、查询与时延

### 6.2 域名系统 DNS

这一节是应用层的重要考点。 核心问题：

**知道域名，怎样得到 IP 地址？**

**DNS 的作用** DNS 全称： Domain Name System。 即域名系统。 例如：

```text
www.example.com
        ↓
      DNS
        ↓
服务器对应的 IP 地址
```

因为人类更容易记忆域名，而 IP 分组转发主要依赖 IP 地址。 DNS 可以完成名称解析。

**DNS 是否是 IP 通信的必要条件？** 不是。 如果已经知道目标 IP 地址，可以直接通信。 例如： `ftp 202.38.70.25` 不一定需要先解析域名。 因此： “没有 DNS，IP 网络就不能传输数据。” 错误。 DNS 解决名称解析问题，不直接负责 IP 分组转发。

**DNS 使用 TCP 还是 UDP？** DNS 属于应用层协议。 通常使用：

**UDP 53 端口** 但也可以使用：

**TCP 53 端口**

**UDP 常见场景** 普通域名查询；较小的 DNS 响应；经典 408 域名解析题。

**TCP 常见场景** DNS 区域传送；UDP 响应截断后重新查询；其他需要 TCP 的 DNS 通信场景。 因此： “DNS 只能使用 UDP。” 错误。 “DNS 一定使用 TCP 保证可靠性。” 也错误。

**记忆**

```text
DNS
 │
 ├── 普通查询：常用 UDP
 │
 └── 特定情况：可以 TCP

服务器端口：53
```

**域名空间的层次结构** 例如： `www.example.com` 从右往左看：

```text
根域 .
   ↓
顶级域 com
   ↓
example
   ↓
www
```

更完整地可以写为： `www.example.com.` 最后的点表示根域。

**DNS 为什么采用层次结构？** 如果全球所有域名都由一台服务器管理：数据量巨大；查询压力集中；单点故障严重；维护困难。 所以 DNS 采用分布式、层次化管理。

**域与区的区别** 这是容易被忽略的细节。

**域（Domain）**：域名空间中的一个子树。

**区（Zone）**：由某组权威 DNS 服务器实际管理的 DNS 数据范围。 一个域可以包含委派出去的子域。 因此：域名中每多一个标签，并不意味着现实查询过程中一定要多访问一台 DNS 服务器。 考试中若给出了具体层次，应按题设计算。

**DNS 资源记录** DNS 不是简单的域名和 IP 地址对应表。 常见资源记录：

| 记录类型 | 功能 |
|---|---|
| A | 域名对应 IPv4 地址 |
| AAAA | 域名对应 IPv6 地址 |
| NS | 指定权威域名服务器 |
| CNAME | 指定规范名称 |
| MX | 指定邮件交换服务器 |

**A 记录** 例如：

```text
www.example.com
        ↓
    192.0.2.10
```

**AAAA 记录** 用于 IPv6 地址。

**CNAME** 表示别名。 例如：

```text
www.example.com
       ↓
server.example.net
```

之后还可能需要解析规范名称对应的地址记录。

**MX** 邮件交换记录。 例如：

```text
example.com
     ↓
mail.example.com
```

发送方邮件服务器需要知道接收方域名对应的邮件服务器。 因此可能查询 MX 记录。

**高频考点** 如果题目问： “电子邮件服务器通过 DNS 查询什么记录？” 通常重点考虑：

**MX 记录**

**DNS 域名服务器的分类** 408 常见四类：

1. 根域名服务器；
2. 顶级域名服务器；
3. 权威域名服务器；
4. 本地域名服务器。

**第一类：根域名服务器** 根域名服务器位于 DNS 权威层次的顶端。 例如查询： `www.example.com` 根服务器通常不直接告诉你最终 Web 服务器 IP。 而是返回： `.com 顶级域名服务器信息`

注意：传统 DNS 根服务器有 13 个逻辑标识 A～M。 这不意味着全世界只有 13 台物理根服务器。 实际存在大量 Anycast 部署实例。

**第二类：顶级域名服务器** 例如：

```text
.com
.cn
.org
.net
```

查询： `www.example.com` .com 顶级域名服务器通常返回： `example.com 对应的权威 DNS 服务器信息`

**第三类：权威域名服务器** 保存其负责区域的权威 DNS 资源记录。 可以返回对应的 A、AAAA、MX 等记录。

**第四类：本地域名服务器** 也称本地 DNS 解析器或递归解析器。 主要职责：接收主机查询；检查缓存；必要时向其他 DNS 服务器查询；返回最终结果；缓存查询结果。

**非常重要** 本地域名服务器不是根域、顶级域、权威域之间固定的一层。 它主要是面向客户端的解析服务。 典型结构：

```text
用户主机
   │
   ▼
本地 DNS
   │
   ├── 根域名服务器
   │
   ├── 顶级域名服务器
   │
   └── 权威域名服务器
```

### DNS 递归查询与迭代查询

这是 DNS 最核心的考试内容。

**递归查询** 核心思想：

**被查询的 DNS 服务器负责继续查找，并返回最终结果。** 例如： `主机 → 本地 DNS` 主机告诉本地 DNS： “请帮我查出最终 IP。” 主机通常不需要自己再去询问根服务器、顶级域名服务器。

**递归查询的关键** 查询者把继续查找的责任交给被查询服务器。

注意：递归查询不意味着整个过程中只产生一条 DNS 报文。 它意味着当前查询者通常只向下一台服务器提出一次递归请求。 后续可能由其他服务器继续执行查询。

**迭代查询** 核心思想：

**被查询服务器可以告诉查询者下一步应该去问谁。** 例如：

```text
本地 DNS → 根服务器
               ↓
          返回 TLD 信息

本地 DNS → TLD 服务器
               ↓
          返回权威服务器信息

本地 DNS → 权威服务器
               ↓
            得到答案
```

这里真正逐级向其他服务器发出查询的是：

**本地 DNS**

**迭代查询关键** 被查询服务器不负责替查询者完成全部后续查询。 它可以返回转介信息。

**递归与迭代对比**

| 项目 | 递归查询 | 迭代查询 |
|---|---|---|
| 谁继续查询 | 被查询服务器 | 原查询者 |
| 返回内容 | 最终结果或失败 | 结果或下一步信息 |
| 查询者是否逐级联系服务器 | 通常不需要 | 通常需要 |
| 408 常见场景 | 主机到本地 DNS | 本地 DNS 到其他 DNS |

**标准的递归 + 迭代过程** 假设： `www.example.com` 所有相关缓存均未命中。 过程如下：

```text
① 主机
   │
   │ 递归请求
   ▼
② 本地 DNS
   │
   │ 迭代请求
   ▼
③ 根服务器
   │
   │ 返回 .com TLD 信息
   ▼
④ 本地 DNS
   │
   │ 迭代请求
   ▼
⑤ .com TLD
   │
   │ 返回权威 DNS 信息
   ▼
⑥ 本地 DNS
   │
   │ 查询权威 DNS
   ▼
⑦ 权威 DNS
   │
   │ 返回 IP
   ▼
⑧ 本地 DNS
   │
   │ 返回最终 IP
   ▼
⑨ 主机
```

注意：根服务器、顶级域名服务器通常不会直接替本地解析器完成后续全部查询。

### DNS 查询次数计算

这一类题目的难点不是 DNS 本身，而是：

**到底在统计谁发出的请求？**

**三种完全不同的问法**

**问法一** 用户主机发出几次 DNS 查询？ 如果主机只向本地 DNS 提交一次请求： $\boxed{N=1}$

**问法二** 本地域名服务器发出几次查询？ 需要看：是否缓存命中；采用递归还是迭代；需要访问哪些服务器。

**问法三** 整个域名解析过程一共产生多少次 DNS 查询？ 需要统计所有相关服务器发出的查询。 不能把上述三种问题混为一谈。

**真题：2010 年 DNS 递归查询**

**题目** 如果本地域名服务器没有缓存，采用递归方法解析另一网络某主机域名。 用户主机与本地域名服务器发送的 DNS 查询消息数分别是多少？ A. 1、1 B. 1、多条 C. 多条、1 D. 多条、多条

**答案**

**A**

**解析** 第一步：用户主机向本地域名服务器发出一次递归查询。 因此主机发送： $N_H=1$ 第二步：按照本题的全递归查询模型，本地 DNS 向下一台 DNS 服务器发出一次递归请求。 之后由接受递归请求的服务器继续查询。 因此本地 DNS 发送： $N_L=1$ 最终： $\boxed{(N_H,N_L)=(1,1)}$

**本题陷阱** 错误想法： “域名解析要访问很多 DNS 服务器，所以本地 DNS 一定发出很多查询。” 问题就在于题目明确限定：

**递归查询** 而不是迭代查询。

**考试提醒** 现实公共 DNS 系统中，根服务器和多数权威服务器通常不为普通递归解析器承担完整递归工作。 这道题采用的是教材中的全递归假设。

**真题：2016 年 DNS 迭代查询**

**题目条件** 查询域名： `www.abc.xyz.com` 所有 DNS 服务器采用迭代查询。 求某本地域名服务器可能发出的查询次数：最少多少次？ 最多多少次？ 选项： A. 1、3 B. 0、3 C. 0、4 D. 1、4

**答案**

**C**

**第一种情况：缓存命中** 如果本地域名服务器缓存中已有完整解析结果：无需向外继续查询。 因此： $\boxed{N_{\min}=0}$

**第二种情况：全部缓存未命中** 根据本题给定的 DNS 层次，需要依次查询：

```text
① 根 DNS

② com 顶级 DNS

③ xyz.com DNS

④ abc.xyz.com 权威 DNS
```

因此： $\boxed{N_{\max}=4}$ 最终： $\boxed{(0,4)}$

**为什么不是 3？** 因为本题的层次中，除根和顶级服务器外，还涉及： `xyz.com` `abc.xyz.com` 两个不同层次的域名服务器。

**特别注意** 不能机械地按域名标签数量数服务器。 本题得出 4 次，是因为题设允许存在相应的四级查询路径。 现实解析中的委派结构、缓存和 CNAME 都可能改变查询次数。

**模拟题：全部采用递归查询**

题目：所有域名服务器均采用递归方式。 查询： `www.aaa.bbb.com` 问本地域名服务器发出 DNS 查询的最少次数和最多次数。

**答案** $\boxed{0,\ 1}$

**解析** 缓存命中： $N_{\min}=0$ 缓存未命中：按照全递归教学模型，本地 DNS 向下一台服务器提交一次递归请求。 $N_{\max}=1$

**总结**

| 情况 | 本地 DNS 向外发出的查询 |
|---|---|
| 有完整有效缓存 | 0 |
| 全递归模型，无缓存 | 通常 1 |
| 迭代模型，无缓存 | 按实际服务器数量统计 |

**DNS 缓存与 TTL**

**DNS 缓存为什么存在？** 假设每个用户访问一个网站，都必须重新向根服务器查询。 全球查询量会非常大。 为了提高效率，DNS 广泛使用缓存。 可能存在缓存的位置包括：浏览器或应用；操作系统解析器；本地递归 DNS；其他具备缓存功能的解析节点。

**缓存命中**

```text
查询 www.example.com
         ↓
     本地缓存
         ↓
    已经存在记录
         ↓
    直接返回 IP
```

不用重新访问根、TLD、权威服务器。

**缓存未命中**

```text
本地缓存无记录
         ↓
     向外查询
         ↓
     得到结果
         ↓
     保存缓存
```

**TTL** TTL 即 Time To Live。 DNS 资源记录上的 TTL，表示该缓存记录可以保持有效的时间。 例如： `TTL = 3600s` 表示允许缓存的有效时间为 3600 秒。

**TTL 较大** 优点：减少查询；降低延迟；减轻 DNS 服务器压力。 缺点：

- 更新后的记录可能较晚被用户重新获取。

**TTL 较小** 优点：

- 更快重新获取变化后的记录。

缺点：

- DNS 查询次数增加。

**注意区分两个 TTL** DNS TTL：用于控制 DNS 记录的缓存有效时间。 IPv4 首部 TTL：用于限制 IP 数据报经过的路由器跳数。 二者名称相同，但不是同一个字段。

### DNS 查询时延

**RTT 的含义** RTT： Round Trip Time。 往返时间。 即报文从发送方发出，到收到相应应答所经历的时间。 经典题中：一次 DNS 查询及其响应： $T_{\mathrm{DNS}}=RTT$ 前提是题目明确忽略处理、排队和实际发送等其他时延。

**多次串行查询** 如果 DNS 需要依次访问 $n$ 台服务器。 每次 RTT 相同：

$$
\boxed{
T_{\mathrm{DNS}}=nRTT
}
$$

如果 RTT 不同：

$$
\boxed{
T_{\mathrm{DNS}}=
\sum_{i=1}^{n}RTT_i
}
$$

例如：

```text
根服务器：10ms
TLD：20ms
权威服务器：30ms
```

总时间： $T=10+20+30$ $\boxed{T=60\mathrm{ms}}$

**关键陷阱** 如果本地 DNS 已有缓存，可能根本不需要访问这些服务器。 如果题目明确给出了主机到本地 DNS 的 RTT，也要按照计时范围考虑是否计入。

### DNS + HTTP 综合真题：2020 年

这是一道必须掌握的经典题。

**题目** 主机通过超链接访问 `http://www.abc.com/index.html`。题设：本地 DNS 提供递归查询；其他 DNS 服务器提供迭代查询；相关 Internet 服务器 RTT 为 10ms；忽略其他各种时延；请求的是一个纯文本 Web 页面。 求从点击超链接到接收到网页的：最短时间、最长时间。 选项： A. 10ms、40ms B. 10ms、50ms C. 20ms、40ms D. 20ms、50ms

**答案**

**D** $\boxed{20\mathrm{ms},50\mathrm{ms}}$

**最短时间** 最短情况：本地 DNS 已缓存目标 IP。 因此不需要向 Internet DNS 服务器继续查询。 然后：

**第一步：TCP 三次握手** 需要： $1RTT$

**第二步：HTTP 请求与响应** 需要： $1RTT$ 因此： $T_{\min}=1RTT+1RTT$ $T_{\min}=2RTT$ 代入： $T_{\min}=2\times10$ $\boxed{T_{\min}=20\mathrm{ms}}$

**最长时间** 缓存全部未命中。 本地 DNS 依次向：

```text
根 DNS
   ↓
com TLD
   ↓
abc.com 权威 DNS
```

发送查询。 因此 DNS 阶段需要： $3RTT$ 建立 TCP： $1RTT$ HTTP 请求与响应： $1RTT$ 总时间： $T_{\max}=3RTT+1RTT+1RTT$ $T_{\max}=5RTT$ $T_{\max}=5\times10$ $\boxed{T_{\max}=50\mathrm{ms}}$

**这道题真正考什么？** 不是单纯考 DNS。 而是考：

```text
DNS
 +
TCP 三次握手
 +
HTTP 请求响应
```

最容易遗漏的是：

**TCP 建连的 1 RTT。** 另一个容易出错的地方是：不清楚 DNS 查询是否需要计入。

**一般模型** 若 DNS 解析需 $n$ 个 RTT，之后获取一个很小的 HTTP 对象：

$$
\boxed{
T=nRTT_{\mathrm{DNS}}+2RTT_{\mathrm{Web}}
}
$$

若各次 DNS RTT 不同：

$$
\boxed{
T=\sum_{i=1}^{n}RTT_i+2RTT_{\mathrm{Web}}
}
$$

这里的 2 RTT 来自：

- TCP 建连；
- HTTP 请求及响应。

使用的是传统非预建连接、忽略其他时延的模型。

## FTP：控制连接与数据连接

### 6.3 文件传输协议 FTP

**FTP 的作用** FTP： File Transfer Protocol。 即文件传输协议。 用于：上传文件；下载文件；获取目录列表；管理服务器目录；删除、重命名文件等。 FTP 属于应用层协议。 使用：

**TCP**

**FTP 最核心特点** FTP 把：

**控制信息与数据传输分开。** 即使用两种不同的 TCP 连接。

**FTP 控制连接** 控制连接用于传输：

- 用户名；
- 密码；
- 命令；
- 状态码；
- 文件操作请求。

服务器默认使用：

**TCP 21 端口** 过程：

```text
FTP 客户端
     │
     │ TCP 连接
     ▼
FTP 服务器:21
```

控制连接通常在整个会话期间保持。 常见命令：

```text
USER：用户名
PASS：密码
LIST：请求目录列表
RETR：下载文件
STOR：上传文件
QUIT：退出
```

注意： LIST 命令本身经控制连接发送，但目录列表数据通常经数据连接传输。

**FTP 数据连接** 数据连接负责：

- 文件内容；
- 目录列表等数据。

数据连接通常按数据传输任务建立。 传输完成后关闭。 例如：

```text
FTP 会话开始
      ↓
建立控制连接
      ↓
下载文件 A
      ↓
建立数据连接 1
      ↓
传输完成后关闭
      ↓
下载文件 B
      ↓
建立数据连接 2
      ↓
传输完成后关闭
      ↓
FTP 会话结束
      ↓
关闭控制连接
```

因此：

**一个 FTP 会话不是永远只有两条 TCP 连接。**

**FTP 连接数量计算** 假设：登录一次；获取一次目录列表；下载两个文件。 如果每次数据操作都建立独立数据连接：控制连接： $1$ 数据连接： $1+2=3$ 总连接数： $\boxed{1+3=4}$

**注意题目措辞** “总共建立了多少条 TCP 连接？” 需要累计。 “某一时刻同时存在多少条 TCP 连接？” 需要看时间线。 通常控制连接长期存在，数据连接按需建立。 二者不能混淆。

### FTP 主动模式与被动模式

**主动模式** 主动模式： Active Mode。 核心：

**服务器主动发起数据连接。** 过程：

```text
① 客户端 → 服务器:21
   建立控制连接

② 客户端告诉服务器自己的数据端口

③ 服务器主动连接客户端的数据端口

④ 建立数据连接

⑤ 传输文件
```

经典主动模式下： `服务器数据连接源端口：20` 例如：

```text
客户端:临时端口
      ↑
      │ TCP 数据连接
      │
FTP 服务器:20
```

**记忆** 主动模式：

**服务器主动连接客户端。** 但这里指的是数据连接。 不是控制连接。

**被动模式** 被动模式： Passive Mode。 核心：

**客户端主动发起数据连接。** 过程：

```text
① 客户端连接服务器:21

② 客户端发送 PASV 等命令

③ 服务器开放一个协商的数据端口

④ 服务器把端口信息告诉客户端

⑤ 客户端主动连接这个端口

⑥ 传输文件
```

例如：

```text
客户端:临时端口
       │
       │ TCP 数据连接
       ▼
FTP 服务器:协商端口
```

**记忆** 被动模式：

**服务器被动等待客户端建立数据连接。**

**两种模式对比**

| 项目 | 主动模式 | 被动模式 |
|---|---|---|
| 控制连接发起者 | 客户端 | 客户端 |
| 控制连接服务器端口 | 21 | 21 |
| 数据连接发起者 | 服务器 | 客户端 |
| 服务器数据端口 | 传统使用 20 | 协商端口 |
| 谁等待数据连接 | 客户端 | 服务器 |

**高频误区** “FTP 主动模式的控制连接由服务器建立。” 错误。 无论主动还是被动：控制连接通常都是客户端主动连接服务器的 21 端口。 主动与被动主要描述数据连接的建立方式。

**FTP 文件表示方式** FTP 可以指定文件的传输表示类型。 例如： `TYPE A` 表示 ASCII 类型。 `TYPE I` 表示二进制类型。 所以： “FTP 不允许客户端指定文件类型和格式。” 错误。

**真题：2009 年 FTP**

题目： FTP 客户端和服务器之间传递 FTP 命令，使用什么连接？ A. TCP 控制连接 B. TCP 数据连接 C. UDP 数据连接 D. UDP 控制连接

**答案**

**A**

**解析** FTP 使用 TCP。 命令通过控制连接传输。 文件内容通过数据连接传输。 因此： $\boxed{\text{TCP 控制连接}}$

**真题：2017 年 FTP** 题目问错误的叙述。 A. 数据连接通常在一次数据传输结束后关闭 B. 控制连接通常在整个会话中保持 C. 服务器与客户端的 TCP 20 端口建立数据连接 D. 客户端连接服务器 TCP 21 端口建立控制连接

**答案**

**C**

**解析** TCP 20 是传统主动模式下服务器使用的数据端口。 不能说客户端数据端口固定为 20。 也不能说所有 FTP 数据连接都必须使用服务器 20 端口。 被动模式使用协商的数据端口。

**总结** FTP 题主要检查：

1. TCP 还是 UDP；
2. 控制连接与数据连接；
3. 21 和 20 的区别；
4. 主动与被动；
5. 连接建立次数。

## 电子邮件：SMTP、POP3、IMAP 与 MIME

### 6.4 电子邮件系统

**电子邮件系统组成** 主要包括：

1. 用户代理 UA；
2. 邮件服务器；
3. 邮件传输和访问协议。

典型过程：

```text
发送方用户代理
       │
       │ SMTP
       ▼
发送方邮件服务器
       │
       │ SMTP
       ▼
接收方邮件服务器
       │
       │ POP3 / IMAP
       ▼
接收方用户代理
```

这张流程图必须掌握。

**用户代理 UA** UA： User Agent。 用户代理即用户直接使用的邮件程序。 例如：桌面邮件客户端；手机邮件 App；Web 邮箱界面。 功能：编写邮件；发送邮件；阅读邮件；回复邮件；管理邮箱。

注意：用户代理不是邮件服务器。

**邮件服务器** 邮件服务器负责：接收邮件；保存邮件；转发邮件；维护用户邮箱。 例如：用户 A 给用户 B 发邮件。 A 与 B 使用不同邮件服务器。 过程：

```text
A 邮件服务器
       │
       │ SMTP
       ▼
B 邮件服务器
```

邮件到达 B 的邮件服务器之后，B 可以稍后读取。 这就是电子邮件能够支持异步通信的重要原因。

### SMTP

**SMTP 是什么？** SMTP： Simple Mail Transfer Protocol。 简单邮件传输协议。 核心作用：

**发送与转发邮件。** 在 408 经典模型中：应用层协议；使用 TCP；服务器传统端口 25；采用 Push 模式。

**Push 是什么？** Push 表示推送。 发送方主动将邮件提交或传送给下一方。 例如：

```text
发送方邮件服务器
          │
          │ SMTP
          ▼
接收方邮件服务器
```

**SMTP 可以完成哪些操作？**

**操作一：用户代理发送邮件** `用户代理 → 邮件服务器` 传统教材模型中可以使用 SMTP。

**操作二：邮件服务器转发邮件** `邮件服务器 A → 邮件服务器 B` 使用 SMTP。

**操作三：收件人读取邮件** `邮件服务器 → 收件人客户端` 通常使用 POP3 或 IMAP。 所以： SMTP 不是用户读取邮箱的主要协议。

**SMTP 端口补充** 408 经典记忆： `SMTP：TCP 25` 现代实际部署中还经常出现： `邮件提交：TCP 587` `隐式 TLS 提交：TCP 465` 考试若问传统 SMTP 端口，通常答 25。 如果题目明确讨论邮件提交服务或 TLS，应按题设判断。

**SMTP 与 ASCII** 传统 SMTP 的基本邮件内容传输模型使用 7 位 ASCII。 例如： `Hello world!` 可以直接表示。 但是：

- JPEG；
- PNG；
- 视频；
- 二进制可执行文件；
- 非 ASCII 文本；

往往需要通过 MIME 等扩展机制进行表示或编码。

**注意** “传统 SMTP 基本模型是 7 位 ASCII”属于经典考试知识点。 现代 ESMTP 扩展已经支持更多传输能力，不能将经典教学模型误解为当今所有邮件服务器只能处理 7 位 ASCII。

### POP3

**POP3 是什么？** POP3： Post Office Protocol Version 3。 邮局协议第 3 版。 作用：

**从邮件服务器下载邮件。** 使用： `TCP 110` 典型过程：

```text
用户代理
   │
   │ 请求邮件
   ▼
邮件服务器
   │
   │ 返回邮件
   ▼
用户代理
```

POP3 体现 Pull 模式。 Pull 表示拉取。

**POP3 的特点** 客户端主动请求获取邮件；可以将邮件下载到本地；传统使用方式偏向本地邮件管理；是否保留服务器副本取决于客户端和服务器配置。

**易错点** “POP3 下载邮件后，服务器上的邮件一定删除。” 错误。 是否删除不能绝对化。

### IMAP

**IMAP 是什么？** IMAP： Internet Message Access Protocol。 互联网邮件访问协议。 使用： `TCP 143` 核心：

**访问和同步服务器上的邮箱。** 与 POP3 相比，IMAP 更强调服务器端邮箱管理。 例如：手机 A： `把邮件标记为已读` 电脑 B： `同步之后也显示已读` 这就是 IMAP 适合多设备管理邮箱的重要原因。

**POP3 与 IMAP 对比**

| 比较 | POP3 | IMAP |
|---|---|---|
| 主要用途 | 下载邮件 | 在线访问和同步 |
| 管理重心 | 偏本地 | 偏服务器 |
| 多设备状态同步 | 较弱 | 较强 |
| 服务器端口 | 110 | 143 |
| 传输层 | TCP | TCP |

现代加密连接也有常见端口： `POP3S：995` `IMAPS：993` 但 408 基础题主要记忆 110、143。

### MIME 与邮件格式

**MIME 是什么？** MIME： Multipurpose Internet Mail Extensions。 多用途互联网邮件扩展。 作用：让电子邮件能够表示：

- 不同字符集的文本；
- 图片；
- 音频；
- 视频；
- 附件；
- 多部分邮件内容。

例如：

```text
邮件
 │
 ├── 文本正文
 │
 ├── HTML 正文
 │
 └── PDF 附件
```

**MIME 与 SMTP 的区别** SMTP：负责邮件传输。 MIME：负责邮件内容类型、编码和多部分结构等表示问题。 不能把 MIME 当成 SMTP 的替代协议。

**邮件信封与邮件内容** 电子邮件可以分为：

```text
邮件信封
   │
   └── 用于 SMTP 投递的信息

邮件内容
   │
   ├── 首部
   │
   └── 主体
```

例如：

```text
From: alice@example.com
To: bob@example.net
Subject: Test

Hello!
```

其中： From 是邮件首部字段；To 是邮件首部字段；Subject 是邮件主题；空行后是邮件主体。

注意： SMTP 信封收件人和邮件首部的 To 字段并不是完全相同的概念。

### 电子邮件真题解析

**2012 年真题：邮件传输全过程** 题目给出：

```text
用户 1
   ↓ ①
用户 1 的邮件服务器
   ↓ ②
用户 2 的邮件服务器
   ↓ ③
用户 2
```

问三个阶段的协议。

**答案**

**SMTP、SMTP、POP3**

**解析** ① 用户 1 提交邮件： SMTP。 ② 邮件服务器之间传送： SMTP。 ③ 用户 2 获取邮件： POP3，也可能使用 IMAP。 本题备选组合中使用 POP3。

**记忆**

```text
发送：SMTP
转发：SMTP
接收访问：POP3 / IMAP
```

**2013 年真题：SMTP 功能** 判断： I. 传统 SMTP 直接传输 7 位 ASCII 内容 II. 支持邮件服务器之间发送邮件 III. 支持用户代理向邮件服务器发送邮件 IV. 用于邮件服务器向用户代理提供取信服务

**答案**

**I、II、III**

**解析** I 正确。 经典 SMTP 基础传输模型采用 7 位 ASCII。 II 正确。 SMTP 能完成服务器之间的邮件传输。 III 正确。 SMTP 可以完成客户端邮件提交。 IV 错误。 取信主要使用 POP3 或 IMAP。

**2015 年真题：POP3 的传输服务** POP3 使用何种传输层服务？

**答案**

**面向连接、可靠传输服务。**

**原因** POP3 基于 TCP。 TCP 提供：

- 连接建立；
- 序号；
- 确认；
- 超时重传；
- 可靠的有序字节流服务。

因此： $\boxed{\text{面向连接、可靠}}$

**2018 年真题：SMTP 可直接传输什么？** 选项： A. JPEG 图像 B. MPEG 视频 C. EXE 文件 D. ASCII 文本

**答案**

**D**

**解析** 传统 SMTP 基本传输模型支持 ASCII 文本。 二进制文件通常需要 MIME 等机制进行合适的表示与编码。

**电子邮件协议总表**

| 协议 | 功能 | 传输层 | 默认服务器端口 |
|---|---|---|---|
| SMTP | 发送、转发 | TCP | 25 |
| POP3 | 下载邮件 | TCP | 110 |
| IMAP | 邮箱访问、同步 | TCP | 143 |
| MIME | 内容表示与编码扩展 | 非独立传输协议 | 无固定传输端口 |
| HTTP | 浏览器访问 Webmail | 经典场景 TCP | 80 |
| HTTPS | 加密 Webmail | 经典场景 TLS/TCP | 443 |

**特别容易混淆的情况** 用户打开浏览器访问 Gmail 等 Web 邮箱。 浏览器与 Web 服务器之间主要使用： HTTP/HTTPS。 不能因为访问的是电子邮件，就认为浏览器一定直接通过 SMTP 或 POP3 与 Webmail 页面通信。

## 万维网与 HTTP 基础

### 6.5 万维网 WWW

**WWW 是什么？** WWW： World Wide Web。 即万维网。 通过超链接组织和访问网络资源。 常见概念：

- URL；
- HTTP；
- HTML；
- 浏览器；
- Web 服务器。

**必须区分** URL：资源地址。 HTTP：资源传输协议。 HTML：网页内容和结构的标记语言。 三者职责不同。

**URL 的结构** 例如 `https://www.example.com:443/index.html`，可以拆成：

```text
https
  │
  └── 协议方案

www.example.com
  │
  └── 主机名

443
  │
  └── 端口

/index.html
  │
  └── 资源路径
```

一般结构： `scheme://host:port/path` 端口可以省略。 默认：

```text
HTTP：80

HTTPS：443
```

**注意** URL 不一定总是先通过 DNS。 如果直接使用 IP 字面量，可能不需要普通域名解析。

### HTTP 协议基础

**HTTP 是什么？** HTTP： HyperText Transfer Protocol。 超文本传输协议。 属于应用层。 采用请求/响应模式。

```text
浏览器
   │
   │ HTTP Request
   ▼
Web 服务器
   │
   │ HTTP Response
   ▼
浏览器
```

**HTTP 的职责** 定义：

- 请求方法；
- 资源标识；
- 报文首部；
- 状态码；
- 请求与响应语义。

**TCP 的职责** 在 HTTP/1.x 和 HTTP/2 的典型场景中提供：可靠字节流；按序交付；流量控制；拥塞控制。

注意： HTTP 本身不是 TCP 的可靠传输机制。

**HTTP 版本**

| 版本 | 典型特征 |
|---|---|
| HTTP/1.0 | 默认非持续连接 |
| HTTP/1.1 | 默认持续连接 |
| HTTP/2 | 多路复用，通常基于 TCP |
| HTTP/3 | 基于 QUIC/UDP |

**HTTP/1.0** 经典默认：每个对象单独建立一条 TCP 连接。

**HTTP/1.1** 经典默认：一条 TCP 连接可以被多个 HTTP 请求复用。

**HTTP/2** 支持在同一连接上并发传输多个流。 可以缓解 HTTP/1.1 流水线的应用层队头阻塞。 但由于通常基于 TCP，仍可能受到 TCP 层队头阻塞影响。

**HTTP/3** 基于 QUIC。 QUIC 使用 UDP 承载，并在其上实现可靠传输、加密和流管理等功能。 因此： “所有 HTTP 都使用 TCP。” 对于 HTTP/3 不成立。 但 408 传统 HTTP 题若未涉及现代版本，通常按题目指定的 HTTP/1.0 或 HTTP/1.1 模型分析。

### HTTP 请求报文与响应报文

**HTTP 请求报文** 经典 HTTP/1.1 请求报文结构：

```text
请求行
请求首部
空行
可选请求体
```

例如：

```text
GET /index.html HTTP/1.1
Host: www.example.com
Connection: keep-alive
Cookie: id=123
```

**请求行** `GET /index.html HTTP/1.1` 包括：请求方法 GET；请求目标 /index.html；HTTP 版本 1.1。

**Host** `Host: www.example.com` 表示目标服务器主机名。 不是客户端主机名。

**Connection** `Connection: keep-alive` 表示希望复用连接。 `Connection: close` 表示本次通信后关闭连接。

**Cookie** `Cookie: id=123` 浏览器在满足相关规则时携带之前保存的 Cookie。

**HTTP 响应报文** 结构：

```text
状态行
响应首部
空行
可选响应体
```

例如：

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1000

<html>...</html>
```

**状态行** `HTTP/1.1 200 OK` 包括：

- HTTP 版本；
- 状态码；
- 原因短语。

**Content-Type** 表示消息体的媒体类型。 例如：

```text
text/html
application/json
image/png
```

**Content-Length** 表示消息体的长度。 注意它不是包括整个以太网帧、IP 首部和 TCP 首部在内的总长度。

### HTTP 请求方法

**GET** 主要用于获取资源。 例如： `GET /index.html HTTP/1.1` 服务器返回指定资源的表示。

**POST** 主要用于提交数据，让服务器进行处理。 例如：表单提交；创建业务记录；上传内容。

**PUT** 主要用于创建或替换目标资源的状态。

**DELETE** 请求删除指定资源。

**HEAD** 与 GET 类似，但服务器通常不返回正常响应主体。 主要用于获取资源的相关元数据。

**安全与幂等性** 这是可用于进一步辨析 HTTP 方法的知识点。

**安全方法** 客户端请求的语义本身不要求改变服务器资源状态。 典型：

- GET；
- HEAD。

**幂等方法** 同一个请求执行一次与多次，对服务器目标资源产生的预期效果相同。 典型：

- GET；
- HEAD；
- PUT；
- DELETE。

POST 一般不保证幂等。 例如：连续执行两次创建订单的 POST 请求，可能产生两张订单。

**注意** 幂等不等于每次响应完全相同。 例如 DELETE 第一次返回成功，第二次可能返回资源不存在，但删除后的目标状态相同。

### HTTP 状态码

状态码分为五类。

| 类别 | 含义 |
|---|---|
| 1xx | 信息性响应 |
| 2xx | 成功 |
| 3xx | 重定向 |
| 4xx | 客户端侧请求错误 |
| 5xx | 服务器侧错误 |

**常见状态码**

**200 OK** 请求成功。

**201 Created** 资源创建成功。

**301 Moved Permanently** 永久重定向。

**302 Found** 临时重定向的常见状态码。

**304 Not Modified** 资源未修改。 常用于条件请求与缓存验证。

**400 Bad Request** 请求存在问题。

**401 Unauthorized** 通常表示需要有效认证信息。

**403 Forbidden** 服务器拒绝访问。

**404 Not Found** 请求的资源不存在。

**500 Internal Server Error** 服务器内部错误。

**503 Service Unavailable** 服务暂时不可用。

**HTTP 无状态**

**什么是无状态？** HTTP 的无状态性表示： HTTP 协议本身不要求服务器自动记住前一次请求的应用状态。 例如：

```text
GET /login
      ↓
GET /profile
```

仅凭这两个 HTTP 请求，服务器不会天然知道它们属于同一登录用户。

**重要** HTTP 无状态：不等于 Web 网站不能保存登录状态。 也不等于底层 TCP 没有连接状态。 这三个概念完全不同。

### Cookie 与 Session

**Cookie** Cookie 是浏览器保存的数据。 服务器可以发送： `Set-Cookie: sessionId=abc123` 浏览器在符合 Cookie 作用域和其他发送规则时，后续请求携带： `Cookie: sessionId=abc123` 这样服务器能够把请求与已有会话关联起来。

**Cookie 的本质** Cookie 是数据。 不是服务器发给浏览器执行的程序。

**Session** Session 通常表示服务器侧维护的应用会话状态。 例如：

```text
浏览器 Cookie
      │
      │ sessionId=abc123
      ▼
服务器查找 Session
      │
      ▼
找到当前用户会话
```

**区别** Cookie：通常保存在客户端。 Session：常由服务器维护状态。 需要注意，现代 Web 认证也可以采用无状态 Token 等机制，不是所有网站都必须在服务器保存传统 Session。

**真题：2015 年 HTTP 报文** 题目给出：

```text
GET /index.html HTTP/1.1
Host: www.test.edu.cn
Connection: Close
Cookie: 123456
```

判断错误的叙述。 关键选项： “浏览器请求使用持续连接。”

**答案** 错误。

**解析** 虽然： `HTTP/1.1` 默认支持持续连接。 但是报文中明确： `Connection: Close` 因此本次请求结束后应关闭连接。 不能机械地看见 HTTP/1.1 就认定一定继续保持连接。

**其他考点** Host：目标网站。 Cookie：表明客户端携带了该站点相关状态数据。 它通常意味着此前已经取得相应 Cookie，但不能仅凭一个 Cookie 值认定已经完成身份认证。

### Web 缓存

**Web 缓存的作用** Web 缓存保存近期获取的 Web 对象。 例如：

```text
浏览器请求图片
       ↓
    Web 缓存
       ↓
   缓存有效
       ↓
   直接返回图片
```

优点：降低访问时延；减少跨网络流量；减轻源服务器压力。

**DNS 缓存与 Web 缓存的区别**

| 项目 | DNS 缓存 | Web 缓存 |
|---|---|---|
| 缓存内容 | 域名解析结果 | HTTP 资源 |
| 主要作用 | 减少域名查询 | 减少对象重复获取 |
| 常见机制 | DNS TTL | HTTP 缓存控制与验证 |

**条件 GET** 当缓存中已有资源，但需要检查是否更新时，可以进行条件请求。 例如： `If-None-Match: "abc123"` 服务器根据资源验证信息判断：如果没有改变： `304 Not Modified` 客户端继续使用已有缓存。 如果已经改变：服务器返回新的资源表示。

**考试提醒** 如果题目明确说明： “请求对象已经存在有效缓存中。” 就不能仍然机械地对这个对象计算完整的远端请求和下载时间。

## HTTP 连接方式、流水线与时延

### HTTP 持续连接与非持续连接

这是本章最重要的计算基础。

**非持续连接** Non-Persistent HTTP。 基本特点：一个 TCP 连接通常只传输一个 HTTP 请求及其响应对象。 过程：

```text
建立 TCP
   ↓
发送 GET
   ↓
接收对象
   ↓
关闭 TCP
```

如果网页有多个对象：可能重复建立多个 TCP 连接。

**注意** 非持续连接并不必然意味着各连接完全串行。 浏览器也可能并行建立多个非持续 TCP 连接。 题目若明确“不支持并行”，才能直接按串行方式计算。

**持续连接** Persistent HTTP。 多个 HTTP 请求与响应可以复用一条 TCP 连接。 例如：

```text
建立 TCP
   ↓
GET HTML
   ↓
返回 HTML
   ↓
GET image1
   ↓
返回 image1
   ↓
GET image2
   ↓
返回 image2
   ↓
最后关闭连接
```

优点：减少反复建立 TCP 连接的开销。

### HTTP 非流水线与流水线

**持续非流水线** Non-Pipelining。 特点：同一连接上，必须等待前一个响应返回后，才能发送下一个请求。 例如：

```text
GET HTML
   ↓
收到 HTML
   ↓
GET 图片 1
   ↓
收到图片 1
   ↓
GET 图片 2
   ↓
收到图片 2
```

如果有 5 张图片：就要依次请求 5 次。

**持续流水线** Pipelining。 特点：可以在没有收到前一个响应的情况下，继续发送后续请求。 例如：

```text
GET image1 ──────→
GET image2 ──────→
GET image3 ──────→

          ←────── 响应 image1
          ←────── 响应 image2
          ←────── 响应 image3
```

如果：所有对象地址都已知；同一服务器；对象很小；忽略传输时间；采用理想流水线模型。 那么多个对象可能只增加约 1 RTT。

**非常重要** HTML 引用的图片地址，可能必须先获取 HTML 才能知道。 因此：

**HTML 请求与其引用对象的请求不能无条件放在同一轮。**

**并行连接** 并行连接：同时建立多条 TCP 连接。 例如：

```text
TCP 连接 1 → 图片 1
TCP 连接 2 → 图片 2
TCP 连接 3 → 图片 3
```

这与流水线不同。

**对比**

| 类型 | TCP 连接数 | 请求方式 |
|---|---|---|
| 非持续串行 | 多条，依次 | 每连接一个对象 |
| 非持续并行 | 多条，同时 | 每连接一个对象 |
| 持续非流水线 | 可为一条 | 逐个请求 |
| 持续流水线 | 可为一条 | 连续发多个请求 |

**HTTP 队头阻塞**

**HTTP/1.1 流水线队头阻塞** 假设：

```text
请求 1：处理很慢
请求 2：很快
请求 3：很快
```

HTTP/1.1 流水线的响应顺序受到限制。 如果请求 1 的响应很慢，后续响应可能需要等待。 这就是应用层队头阻塞的一种表现。

**HTTP/2** HTTP/2 可以多路复用。 不同请求使用不同流。 它能够缓解 HTTP/1.1 流水线的应用层队头阻塞。 但多个流通常仍共享 TCP 连接。 如果 TCP 丢失某段数据，后续字节可能必须等待重传。

**HTTP/3** HTTP/3 使用 QUIC。 QUIC 提供多个独立的数据流。 因此能够避免因单条 TCP 字节流按序交付产生的跨流队头阻塞。 但不意味着网络拥塞或丢包不再影响时延。

### HTTP RTT 计算：最重要的基础

**获取一个小对象** 假设： TCP 尚未建立；DNS 已解析；使用经典 HTTP/TCP；忽略数据传输时间；忽略服务器处理时间；HTTP 请求没有提前包含在 TCP 握手阶段。 那么：

**TCP 三次握手** 需要： $1RTT$

**HTTP 请求与响应** 需要： $1RTT$ 总时间： $\boxed{T=2RTT}$ 这就是经典公式。

**若考虑对象发送时间** 对象大小： $L\ \mathrm{bit}$ 链路发送速率： $R\ \mathrm{bit/s}$ 则理想发送时延： $T_{\mathrm{tx}}=\frac{L}{R}$ 所以： $\boxed{T\approx2RTT+\frac{L}{R}}$ 前提仍是题目所采用的简化网络模型。

### HTML + 多张图片：四种经典模型

假设：一个 HTML 页面引用 $n$ 张小图片。 因此对象总数： $\boxed{N=n+1}$ 统一假设： DNS 已完成；TCP 尚未建立；所有资源来自同一 Web 服务器；所有 RTT 相同；忽略对象发送时间；HTML 接收完成后才能知道图片 URL。

**模型一：非持续、完全串行** 每个对象： $2RTT$ 一共有： $n+1$ 个对象。 因此： $T=2(n+1)RTT$ 最终： $\boxed{T_{\mathrm{NP}}=2(n+1)RTT}$

**例子** HTML 引用 4 张图片。 总对象数： $1+4=5$ 时间： $T=2\times5RTT$ $\boxed{10RTT}$

**模型二：持续、非流水线** 只建立一次 TCP： $1RTT$ 请求 HTML： $1RTT$ 之后 $n$ 张图片逐个请求： $nRTT$ 因此： $T=(1+1+n)RTT$ 最终： $\boxed{T_{\mathrm{P,nonpipe}}=(n+2)RTT}$

**例子** HTML 引用 4 张图片。 $T=(4+2)RTT$ $\boxed{6RTT}$

**模型三：持续、流水线** 建立 TCP： $1RTT$ 获取 HTML： $1RTT$ 浏览器解析 HTML。 然后对已知的 $n$ 张图片连续发送请求。 在理想小对象模型下： $1RTT$ 因此： $T=1RTT+1RTT+1RTT$ 最终： $\boxed{T_{\mathrm{P,pipe}}=3RTT}$

注意：这里默认 $n\geq1$。 如果没有任何引用对象，只需要获取 HTML，则是： $2RTT$

**模型四：非持续、并行连接** 假设： HTML 引用 $n$ 个对象；最多同时建立 $m$ 条 TCP 连接；各对象很小；每批非持续连接可并行完成；各批次之间按需依次执行。

**第一步：HTML** 先获取 HTML： $2RTT$

**第二步：图片分批** 图片批次数： $k=\left\lceil\frac{n}{m}\right\rceil$ 每批消耗： $2RTT$ 因此： $T=2RTT+2kRTT$ 最终：

$$
\boxed{
T=
\left(
2+2\left\lceil\frac{n}{m}\right\rceil
\right)RTT
}
$$

**例子** HTML 引用 10 张图片。 最多同时建立 5 条 TCP 连接。 批次数： $k=\left\lceil\frac{10}{5}\right\rceil=2$ HTML： $2RTT$ 两批图片： $4RTT$ 总时间： $\boxed{T=6RTT}$

### HTTP 四种模型总表

| 模型 | 经典时间 |
|---|---|
| 非持续串行 | $2(n+1)RTT$ |
| 持续非流水线 | $(n+2)RTT$ |
| 持续流水线 | $3RTT$ |
| 非持续并行 | $\left(2+2\left\lceil n/m\right\rceil\right)RTT$ |

其中：

- $n$：HTML 引用的额外对象数；
- $m$：允许同时建立的非持续 TCP 连接数。

**使用公式前必须检查**

1. 是否需要 DNS？
2. TCP 是否已建立？
3. 是否使用 HTTPS？
4. 是否有 TLS 握手？
5. 是否允许并行？
6. 是否支持流水线？
7. 对象是否很小？
8. 是否给出了对象大小和发送速率？
9. 是否考虑 TCP 拥塞窗口？
10. 从什么时刻开始计时？

这些公式不是无条件成立的网络定律。

### 2024 年真题：非持续 HTTP RTT

**题目** 浏览器：不支持并行 TCP 连接；使用非持续 HTTP/1.0；请求一个网页；网页引用 7 张小图片。 从建立第一个 TCP 连接开始，到全部对象接收完成。 需要多少 RTT？ A. 4 B. 9 C. 14 D. 16

**答案**

**D**

**解题过程** 基础 HTML： $1$ 图片： $7$ 总对象数： $N=1+7=8$ 非持续 HTTP：每个对象需要： $2RTT$ 不能并行。 所以： $T=8\times2RTT$ $\boxed{T=16RTT}$

**为什么不是 14？** 因为漏掉了基础 HTML。

**为什么不是 9？** 9 RTT 对应：一次 TCP 建连： $1RTT$ 加 8 个顺序请求： $8RTT$ 这是持续非流水线模型，不是本题。

### 模拟题：持续非流水线 HTTP

**题目** 某主机使用 HTTP/1.1。 HTML 大小： $1MSS$ HTML 引用 4 张 JPEG 图片。 每张大小： $0.5MSS$ 采用持续非流水线方式。 从请求建立 TCP 连接开始计时。 忽略额外传输时延。 求 RTT 数量。

**答案** $\boxed{6RTT}$

**解析** 建立 TCP： $1RTT$ 获取 HTML： $1RTT$ 获取 4 张图片： $4RTT$ 所以： $T=1+1+4$ $\boxed{T=6RTT}$

**为什么不是 5 RTT？** 因为不能漏掉 TCP 三次握手。

**为什么不是 3 RTT？** 因为题目明确是：

**非流水线** 不能把图片请求合并成一个理想流水线阶段。

**MSS 的作用** 本题给出 MSS，但同时规定每次小对象请求—响应按题设的 RTT 模型计算。 不能只因为图片大小为 $0.5MSS$，就认为每张图片额外需要多个 RTT。

### 模拟综合题：DNS + HTTP

题库 中收录的第 6 套第 47 题，是非常适合系统复习的综合题。

**题设** 用户点击 URL。 没有目标域名 IP 缓存。 需要依次查询 $n$ 台 DNS 服务器。 每次 DNS 查询耗时： $RTT$ 主机与 Web 服务器的 RTT 为： $RTT_w$ 题目采用明文 HTTP，并忽略其他指定时延。

**第一问** 如果只下载一张小图片，需要多长时间？

**第二问** 如果下载：

- 1 个 HTML；
- 3 个小对象；

分别计算：

1. 非持续串行；
2. 持续非流水线；
3. 持续流水线。

**第一问** DNS： $nRTT$ TCP： $1RTT_w$ HTTP： $1RTT_w$ 所以：

$$
\boxed{
T_1=nRTT+2RTT_w
}
$$

**第二问：非持续串行** 总对象数： $1+3=4$ 每个对象： $2RTT_w$ 所以：

$$
\boxed{
T_{\mathrm{NP}}=nRTT+8RTT_w
}
$$

**持续非流水线** DNS： $nRTT$ TCP： $1RTT_w$ HTML： $1RTT_w$ 3 个对象： $3RTT_w$ 因此：

$$
\boxed{
T_{\mathrm{P,nonpipe}}=nRTT+5RTT_w
}
$$

**持续流水线** DNS： $nRTT$ TCP： $1RTT_w$ HTML： $1RTT_w$ 3 个图片请求采用理想流水线： $1RTT_w$ 因此：

$$
\boxed{
T_{\mathrm{P,pipe}}=nRTT+3RTT_w
}
$$

**最终结果**

| 模式 | 总时间 |
|---|---|
| 单个对象 | $nRTT+2RTT_w$ |
| 非持续串行，4 对象 | $nRTT+8RTT_w$ |
| 持续非流水线，4 对象 | $nRTT+5RTT_w$ |
| 持续流水线，4 对象 | $nRTT+3RTT_w$ |

**本题最重要的思想** DNS RTT 与 Web RTT 可能不同。 不能把它们直接合并成一个相同数值的 RTT。 另外： HTML 没有获取之前，不一定知道图片地址。 因此不能把 HTML 和图片全部作为同一批已知请求处理。

## HTTP 与 TCP 联合计算、跨层真题

**HTTP 与 TCP 慢开始综合题** 这是难度较高的跨层计算。

**为什么 HTTP 时延题会考 TCP？** 因为 HTTP/1.1 运行在 TCP 之上。 即使 HTTP 请求已经发送： TCP 也不一定能够立刻发送全部响应数据。 可能受到：

- 拥塞窗口；
- 接收窗口；
- MSS；
- ACK；
- 慢开始；

等条件限制。

**TCP 慢开始回顾** 假设初始拥塞窗口： $cwnd=1MSS$ 理想慢开始模型：

```text
第 1 轮：1 MSS
第 2 轮：2 MSS
第 3 轮：4 MSS
第 4 轮：8 MSS
```

因此发送窗口按轮次近似翻倍： $1,\ 2,\ 4,\ 8,\ldots$ 前 $r$ 轮最多发送： $S_r=1+2+4+\cdots+2^{r-1}$ 所以： $\boxed{S_r=2^r-1}$ 单位是 MSS。 若初始窗口为 $wMSS$： $\boxed{S_r=w(2^r-1)}$ 若需要传输 $K$ 个 MSS： $w(2^r-1)\geq K$ 所以：

$$
\boxed{
r=
\left\lceil
\log_2\left(\frac{K}{w}+1\right)
\right\rceil
}
$$

**注意** 这个公式只统计理想慢开始的发送轮数。 不一定等于整个 HTTP 页面加载的 RTT 数量。 因为还可能存在： TCP 建连；HTML 解析；新的 HTTP 请求；接收端窗口限制；应答时序。

### 2022 年真题：HTTP + TCP 慢开始

**题目** 主机 H 通过 HTTP/1.1 访问： `news408.html` HTML 大小： $1MSS$ 页面引用一张图片。 图片大小： $3MSS$ RTT： $10\mathrm{ms}$ 已经完成 DNS 解析。 忽略题设指定的传输和首部开销。 从请求建立 TCP 连接开始，到全部内容收到。 至少需要多长时间？ A. 30ms B. 40ms C. 50ms D. 60ms

**答案**

**B** $\boxed{40\mathrm{ms}}$

**解题思路** 本题不能直接使用： $T=3RTT$ 因为响应数据不是可以完全忽略的极小对象，而且 TCP 拥塞窗口限制了发送量。 题目采用最短传输模型： TCP 初始拥塞窗口按 $1MSS$ 考虑；可以利用第三次握手携带 HTTP 请求；慢开始按题目预期的发送轮次推进。

**第一步：TCP 建连** 大约： $1RTT$ 为了得到最短时间，客户端可以在第三次握手的 ACK 中携带第一个 HTTP 请求。

**第二步：HTML** HTML 大小： $1MSS$ 初始： $cwnd=1MSS$ 服务器可以发送 HTML。 收到相应确认后： $cwnd:1\rightarrow2MSS$

**第三步：图片第一批数据** 图片共有： $3MSS$ 当前拥塞窗口： $2MSS$ 所以先发送： $2MSS$ 确认后： $cwnd:2\rightarrow4MSS$

**第四步：图片剩余数据** 剩余： $3MSS-2MSS=1MSS$ 再发送： $1MSS$ 按照真题采用的最短 RTT 轮次计数： $T=4RTT$ 因此： $T=4\times10$ $\boxed{T=40\mathrm{ms}}$

**本题重点** 这道题综合考查：

1. HTTP/1.1 持续连接；
2. TCP 三次握手；
3. 第三次握手可以携带数据；
4. HTTP 请求之间的依赖关系；
5. TCP 初始拥塞窗口；
6. TCP 慢开始；
7. MSS 与 RTT。

**必须注意** 不能把“总共 4 MSS 数据”直接等同于“4 RTT”。 也不能把所有慢开始题都套成这道题的 4 RTT。 如果题目改变：初始拥塞窗口；是否允许握手中携带请求；图片大小；HTML 大小；请求发送时机；接收窗口。 就必须重新画时间线。

### 2011 年第 47 题：HTTP + ARP + IP + NAT

这是应用层最值得掌握的跨层大题之一。

**题目背景** 主机 MAC： `00-15-C5-C1-5E-28` 主机 IP： `10.2.128.100` 主机访问 Internet 上的 Web 服务器。 题目给出：网络拓扑；以太网帧十六进制数据；HTTP/1.1 工作方式；NAT 路由器。 主要问题：

1. Web 服务器 IP；
2. 默认网关 MAC；
3. ARP 请求；
4. HTTP RTT；
5. 路由器修改的 IP 首部字段。

**第一问：以太网帧解析** 题目中相关字节：

```text
00 21 27 21 51 EE
00 15 C5 C1 5E 28
08 00
```

以太网 II 帧首部结构：

| 字段 | 长度 |
|---|---|
| 目的 MAC | 6B |
| 源 MAC | 6B |
| 类型 | 2B |

因此：目的 MAC： `00-21-27-21-51-EE` 源 MAC： `00-15-C5-C1-5E-28` 类型： `08 00` 表示 IPv4。

**为什么目的 MAC 是默认网关？** 因为 Web 服务器位于远端网络。 IP 分组最终目的地址是 Web 服务器。 但是当前以太网帧只需要发送到下一跳。 下一跳是默认网关。 因此：

```text
IPv4 目的地址：远端 Web 服务器

以太网目的 MAC：默认网关接口
```

**重要区别** IP 地址通常用于标识端到端通信的目标。 MAC 地址用于标识当前链路上的接收方。

**解析目的 IPv4 地址** IPv4 首部中目的地址字节： `40 AA 62 20` 十六进制转十进制： $40_{16}=64$ $AA_{16}=170$ $62_{16}=98$ $20_{16}=32$ 因此： $\boxed{64.170.98.32}$ 即 Web 服务器 IP。

**易错点** 以太网帧前面有 14B 首部。 不能直接把帧第一个字节当成 IPv4 首部第一个字节。 对于没有 IP 选项的 IPv4 首部：

```text
以太网前 14B
      ↓
IPv4 首部开始
      ↓
IPv4 第 13～16B 是源 IP
IPv4 第 17～20B 是目的 IP
```

**2011 年真题：ARP 部分**

**ARP 的作用** ARP： Address Resolution Protocol。 地址解析协议。 用于在典型 IPv4 以太网环境下获得下一跳 IPv4 地址对应的 MAC 地址。 例如：

```text
默认网关 IP
     ↓
    ARP
     ↓
默认网关 MAC
```

**ARP 请求** 通常使用广播。 目的 MAC： `FF-FF-FF-FF-FF-FF`

**ARP 应答** 典型情况下使用单播。

**为什么不能查询远端 Web 服务器 MAC？** 因为远端 Web 服务器不在当前局域网。 主机不需要知道远端服务器的 MAC。 主机只需要把帧发送给下一跳路由器。 因此：

```text
Web 服务器 IP：64.170.98.32

ARP 查询目标：默认网关 IP
```

**考试结论**

**ARP 解析的是当前链路需要通信的 IPv4 下一跳。** 不要把它与 DNS 混淆。 DNS： `域名 → IP` ARP： `下一跳 IPv4 → MAC`

**2011 年真题：HTTP RTT 部分**

**题设** HTTP/1.1；持续连接；非流水线；基础 HTML；HTML 引用 5 张 JPEG；一次请求响应耗时 1 RTT；从题图中 HTTP 请求发出时开始计时。 问需要多少 RTT。

**答案** $\boxed{6RTT}$

**解析** 请求 HTML： $1RTT$ 请求 5 张图片： $5RTT$ 总时间： $T=1RTT+5RTT$ $\boxed{T=6RTT}$

**关键陷阱** 为什么不是： $7RTT$ 因为题目不是从 TCP 三次握手之前开始计时。 而是：

**从 HTTP 请求已经发出时开始。** 因此 TCP 建连已经发生，不需要重复计入。

**2011 年真题：NAT 与路由转发**

**NAT** NAT： Network Address Translation。 网络地址转换。 主机私有 IP： `10.2.128.100` 转换为公网 IP： `101.12.123.15` 因此：

$$
10.2.128.100
\rightarrow
101.12.123.15
$$

需要修改 IPv4 首部的源地址。

**TTL** 每经过一台正常转发该 IPv4 数据报的路由器： TTL 减 1。 $\boxed{TTL_{\mathrm{out}}=TTL_{\mathrm{in}}-1}$ 例如： $64\rightarrow63$

**IPv4 首部校验和** 由于 IPv4 首部发生变化：

- TTL 改变；
- 源 IP 改变；

因此必须更新 IPv4 首部校验和。

**最终答案** 本题需要修改：

1. 源 IP 地址；
2. TTL；
3. IPv4 首部校验和。

**注意** 不是所有路由器转发时都必须修改源 IP。 普通路由转发主要涉及 TTL、校验和及必要的其他处理。 本题需要改变源 IP，是因为题设中的出口路由器进行了 NAT。 另外，路由器转发时还会按照下一段链路重新封装相应链路层帧。 但 MAC 地址属于链路层首部，不属于 IPv4 首部。

### 2021 年第 47 题：DNS + ARP + 交换机自学习

这也是本章非常重要的综合题。

**题目背景** 网络包含：主机 H1；主机 H2；本地 DNS 服务器；交换机 S；路由器 R；Internet 上的 Web 服务器。 H1 通过域名： `www.abc.com` 访问 Web 服务器。 初始： H1 的 ARP 缓存为空；交换机 MAC 地址表为空；没有无关通信。 在某时刻，交换机第一次收到 HTTP 请求帧。 题目要求：

1. HTTP 之外使用什么应用层协议？
2. 协议如何封装？
3. 交换机学到哪些 MAC 地址？
4. H2 至少收到多少个帧？

**第一问：还需要什么应用层协议？**

答案：

**DNS** 原因：用户访问的是域名。 需要先通过 DNS 获取 Web 服务器对应的 IP。 典型普通 DNS 查询采用 UDP。 因此封装：

```text
DNS 应用层报文
       ↓
UDP 用户数据报
       ↓
IPv4 数据报
       ↓
以太网帧
```

即：

$$
\boxed{
DNS\rightarrow UDP\rightarrow IP\rightarrow Ethernet
}
$$

**易错点** ARP 虽然也可能发生，但不能用 ARP 回答： “HTTP 之外还使用了什么应用层协议？” 因为 ARP 不属于这里要回答的应用层协议。

**第二问：交换机自学习** 交换机学习 MAC 地址的核心规则：

**根据收到帧的源 MAC 地址和入端口学习。** 例如：

```text
交换机端口 4
     ↑
     │
收到来自 H1 的帧
```

交换机学到： `H1 MAC → 端口 4`

**本题结果**

| 设备 | MAC | 交换机端口 |
|---|---|---|
| 本地 DNS | 00-11-22-33-44-BB | 1 |
| 路由器 R | 00-11-22-33-44-AA | 2 |
| H1 | 00-11-22-33-44-CC | 4 |

**为什么没有 H2？** 因为 H2 没有发送帧。 交换机向 H2 转发广播帧：不等于交换机能够学习到 H2 的 MAC 地址。

**重点** 交换机：根据源 MAC 学习。 根据目的 MAC 决定转发方式。 两者不能颠倒。

### 2021 年真题：为什么 H2 至少收到两个广播帧？

**第一阶段：查询 DNS** 题目中本地 DNS 与 H1 位于同一子网。 H1 的 ARP 缓存为空。 所以： H1 要先获得本地 DNS 的 MAC。 发送： `ARP Request` 目的 MAC： `FF-FF-FF-FF-FF-FF` 交换机在同一广播域内洪泛。 H2 会收到。 这是第一个广播帧。

**第二阶段：访问远端 Web** DNS 查询结束后： H1 得到 Web 服务器 IP。 因为 Web 服务器在远端网络： H1 需要通过默认网关发送数据。 但是 H1 的 ARP 缓存中还没有网关 MAC。 所以： H1 再发送一次 ARP 请求。 目的 MAC： `FF-FF-FF-FF-FF-FF` 交换机再次洪泛。 H2 再收到一个广播帧。

**最终答案** H2 至少收到： $\boxed{2}$ 个与此次访问有关的广播帧。 都是： ARP 请求帧。 目的 MAC： `FF-FF-FF-FF-FF-FF`

**为什么不把 TCP 和 HTTP 帧全部算进去？** 因为 TCP、HTTP 的普通通信帧通常采用单播转发。 交换机已经学习到相应的目的 MAC 所在端口。 因此不能认为同一个广播域内的其他主机一定收到所有单播帧。

**资料中需要特别辨析的地方** 题库 中，2021 年真题的不同整理页面对两次 ARP 广播的发起过程存在不同表述。 根据综合应用题页面提供的拓扑和地址条件： H1 与本地 DNS 在同一子网；H1 初始 ARP 缓存为空；Web 服务器位于远端网络。 因此更清晰的最小通信过程是：

```text
H1 ARP 查询本地 DNS 的 MAC
            ↓
         DNS 查询
            ↓
H1 ARP 查询默认网关的 MAC
            ↓
         TCP 建连
            ↓
         HTTP 请求
```

这个分析能够直接解释两次 ARP 请求。 做类似题时，应以实际拓扑、路由关系及 ARP 缓存条件为准，而不是死记广播次数。

**ARP 广播次数的拓展题**

**情况一：本地 DNS 与主机同子网** 假设：

```text
H：192.168.1.10/24

DNS：192.168.1.53/24

网关：192.168.1.1

Web：203.0.113.20
```

初始： ARP 缓存为空。 那么 H 至少需要分别解析： `DNS 服务器 MAC` 以及： `默认网关 MAC` 因此需要： $\boxed{2}$ 次 ARP 请求。

**情况二：DNS 在远端网络** 假设：

```text
H：192.168.1.10/24

DNS：192.168.2.53

网关：192.168.1.1

Web：203.0.113.20
```

DNS 和 Web 都在远端。 H 发送 DNS 请求时：先解析： `默认网关 MAC` 之后访问 Web 服务器：仍然通过相同默认网关。 如果 ARP 缓存有效：不需要再发第二次 ARP。 因此： $\boxed{1}$ 次 ARP 请求。

**结论** ARP 请求次数不由应用层协议数量决定。 而取决于：

- 实际下一跳；
- ARP 缓存；
- 子网划分；
- 路由表；
- 网络拓扑。

## 综合解题方法与强化训练

### 网页访问全过程：跨层统一模型

这部分建议作为全章最后的综合框架掌握。 假设用户输入 `https://www.example.com`，主机使用传统 HTTPS/TCP。 相关缓存不存在。

**第一阶段：IP 配置** 如果主机尚未获得有效网络配置，可能使用 DHCP。 经典 DHCP 过程：

```text
DHCPDISCOVER
      ↓
DHCPOFFER
      ↓
DHCPREQUEST
      ↓
DHCPACK
```

常见端口：

```text
DHCP 服务器：UDP 67

DHCP 客户端：UDP 68
```

注意：不是每次浏览网页都需要重新 DHCP。

**第二阶段：DNS**

解析： `www.example.com` 得到： `Web 服务器 IP` 主机通常先向配置的本地 DNS 查询。 缓存未命中时，解析器再进行必要的后续查询。

**第三阶段：确定下一跳** 主机查询自己的路由表。 如果目标在同一子网：通常直接发送到目标。 如果目标在远端网络：通过相应下一跳路由器。

**第四阶段：ARP** 如果下一跳是通过 IPv4 以太网通信且 MAC 未知：通过 ARP 查询下一跳 MAC。 ARP 请求：通常广播。 ARP 应答：通常单播。

**第五阶段：TCP 建立连接** 三次握手：

```text
SYN
  ↓
SYN + ACK
  ↓
ACK
```

经典 RTT 模型中： $1RTT$

**第六阶段：TLS** 由于是 HTTPS：还涉及 TLS。 TLS 用于提供：

- 加密；
- 完整性保护；
- 身份认证等安全能力。

TLS 握手耗时取决于具体版本、是否恢复会话等条件。 如果 408 题明确忽略 TLS，则不能自行添加额外 RTT。

**第七阶段：HTTP** 浏览器发送： `GET /` 服务器返回： `HTML` 之后浏览器解析 HTML。

**第八阶段：下载附加资源** 例如：

- CSS；
- JavaScript；
- 图片；
- 字体；
- 视频等。

浏览器可能：复用 TCP 连接；使用多路复用；建立其他连接；访问其他域名；使用 Web 缓存。 具体过程由协议版本和题目条件决定。

**第九阶段：下层网络转发** 交换机：根据源 MAC 学习；根据目的 MAC 转发；在相应广播域内洪泛广播帧。 路由器：查路由表；确定下一跳；IPv4 TTL 减 1；更新相关首部字段；根据下一段链路重新封装。 NAT：在配置并命中相关规则时，还可能修改 IP 地址和端口。

### 五类综合题的统一解法

**类型一：协议判断题** 问： “某场景使用什么协议？” 解题步骤：

1. 确定应用场景；
2. 判断通信双方；
3. 判断正在执行的操作；
4. 判断协议；
5. 判断 TCP/UDP；
6. 判断端口。

例如：浏览器请求网页： HTTP/HTTPS。 邮件服务器之间传送邮件： SMTP。 用户下载邮箱中的邮件： POP3 或 IMAP。 文件传输： FTP。 域名解析： DNS。

**类型二：DNS 查询次数题** 步骤：

1. 是否缓存命中？
2. 是递归还是迭代？
3. 问的是谁发送的查询？
4. 需要访问多少级 DNS？
5. 是否存在题设指定的特殊委派？

例如：全递归，无缓存：本地 DNS 典型发送 1 次递归请求。 迭代，无缓存：按实际查询路径统计。

**类型三：FTP 连接数量题** 步骤：

1. 控制连接多少条？
2. 有多少次数据操作？
3. 每次是否单独建立数据连接？
4. 是否问累计连接数？
5. 还是问某时刻同时存在的连接数？

**类型四：HTTP RTT 题** 步骤：

1. 圈出计时起点；
2. 判断 DNS 是否需要；
3. 判断 TCP 是否已建立；
4. 计算对象数量；
5. 判断持续还是非持续；
6. 判断流水线；
7. 判断并行连接；
8. 判断对象大小及拥塞窗口；
9. 画时间线；
10. 累加串行时延。

**一个最重要的原则**

**只有确实必须先后等待的阶段，才能直接相加。** 如果允许并行，就不能把全部操作简单相加。

**类型五：跨层综合题** 步骤：

1. 找出最终目的 IP；
2. 判断下一跳；
3. 确定 ARP 查询对象；
4. 分析 MAC 地址；
5. 分析交换机转发表；
6. 分析 DNS；
7. 分析 TCP；
8. 分析 HTTP；
9. 分析 NAT；
10. 分析 TTL 和校验和。

### 综合强化练习

**练习 1：DNS + HTTP**

题目：一个网页包含：

- 1 个 HTML；
- 6 张小图片。

DNS 需要依次访问 3 台服务器。 每次 DNS RTT： $5\mathrm{ms}$ Web RTT： $20\mathrm{ms}$ 采用 HTTP/1.1 持续非流水线。 TCP 尚未建立。 忽略其他时延。 求总时间。

<Accordions>
<Accordion title="查看第 1 题答案与解析" id="net6-practice-1">
**解答** DNS： $T_{\mathrm{DNS}}=3\times5=15\mathrm{ms}$ TCP： $20\mathrm{ms}$ HTML： $20\mathrm{ms}$ 6 张图片： $6\times20=120\mathrm{ms}$ 因此： $T=15+20+20+120$ $\boxed{T=175\mathrm{ms}}$

**若改为理想持续流水线？** DNS： $15\mathrm{ms}$ TCP： $20\mathrm{ms}$ HTML： $20\mathrm{ms}$ 6 张图片流水线： $20\mathrm{ms}$ 所以： $\boxed{T=75\mathrm{ms}}$

</Accordion>
</Accordions>

**练习 2：HTTP 并行连接**

题目： HTML 引用 11 张小图片。 HTTP 非持续。 最多同时建立 4 条 TCP 连接。 忽略传输时间。 求 RTT。

<Accordions>
<Accordion title="查看第 2 题答案与解析" id="net6-practice-2">
**解答** 先获取 HTML： $2RTT$ 图片分批： $k=\left\lceil\frac{11}{4}\right\rceil$ $k=3$ 每批： $2RTT$ 总时间： $T=2+3\times2$ $\boxed{8RTT}$

</Accordion>
</Accordions>

**练习 3：FTP 连接数量**

题目：某 FTP 会话：登录一次；获取目录列表两次；下载文件三次；上传文件一次。 假设每次目录或文件数据操作都建立独立的数据连接。 问总共建立多少条 TCP 连接？

<Accordions>
<Accordion title="查看第 3 题答案与解析" id="net6-practice-3">
**解答** 控制连接： $1$ 数据连接： $2+3+1=6$ 总数： $1+6$ $\boxed{7}$

注意：这是累计建立的连接总数。 不是同时存在 7 条连接。

</Accordion>
</Accordions>

**练习 4：ARP + DNS**

题目：主机： `192.168.10.10/24` 本地 DNS： `192.168.10.53/24` 默认网关： `192.168.10.1` Web 服务器： `203.0.113.100` 主机 ARP 缓存为空。 问访问 Web 前，主机至少需要解析哪些 IPv4 地址对应的 MAC？

<Accordions>
<Accordion title="查看第 4 题答案与解析" id="net6-practice-4">
**解答** 首先：本地 DNS 与主机同子网。 需要解析： `192.168.10.53` 然后： Web 服务器在远端。 需要交给网关。 因此解析： `192.168.10.1`

答案： $\boxed{2}$ 个不同的下一跳地址需要进行 ARP 解析。

</Accordion>
</Accordions>

**练习 5：HTTP 计时起点**

题目： HTML 引用 5 张图片。 采用持续非流水线 HTTP。 求以下三种情况需要多少 RTT。

<Accordions>
<Accordion title="查看第 5 题答案与解析" id="net6-practice-5">
**情况 A** 从 TCP 建连开始。

解答： $1+1+5$ $\boxed{7RTT}$

**情况 B** TCP 已建立。 从发送 HTML GET 开始。

解答： $1+5$ $\boxed{6RTT}$

**情况 C** HTML 已经接收完成。 从发送第一张图片请求开始。

解答： $\boxed{5RTT}$

**总结** 同一网页：不同计时起点，会导致不同答案。 所以 HTTP 计算题的第一步永远应该是：

**确认起点和终点。**

## 易混概念、公式和考前总结

### 应用层高频易混概念对比

**DNS 与 ARP**

| 项目 | DNS | ARP |
|---|---|---|
| 作用 | 域名解析 | IPv4 地址解析为链路层地址 |
| 输入 | 域名 | 下一跳 IPv4 地址 |
| 输出 | 资源记录，常见为 IP | MAC 地址 |
| 主要作用范围 | DNS 分布式系统 | 当前链路或广播域 |
| 是否应用层 | 是 | 不按这里的应用层协议处理 |

**TCP 与 UDP**

| 项目 | TCP | UDP |
|---|---|---|
| 是否建立连接 | 是 | 否 |
| 可靠性 | 提供可靠字节流 | 本身不保证可靠交付 |
| 顺序控制 | 有 | 本身没有 |
| 拥塞控制 | 有 | 本身不提供 TCP 式拥塞控制 |
| 典型应用 | FTP、SMTP、HTTP/1.x | 传统 DNS 查询、DHCP |

注意： HTTP/3 使用 QUIC/UDP，因此不能把现代所有 Web 传输都归入 TCP。

**HTTP 与 FTP**

| 比较 | HTTP | FTP |
|---|---|---|
| 典型用途 | 获取 Web 资源 | 文件传输 |
| 是否基于 TCP | HTTP/1.x、HTTP/2 通常是 | 是 |
| 控制与数据连接 | 不采用 FTP 式双连接 | 分离 |
| 服务器控制端口 | HTTP 80 | FTP 21 |
| 数据连接 | 依 HTTP 版本与模式 | 独立数据连接 |

**SMTP 与 POP3**

| 比较 | SMTP | POP3 |
|---|---|---|
| 功能 | 发送邮件 | 下载邮件 |
| 模式 | Push | Pull |
| 传输层 | TCP | TCP |
| 端口 | 25 | 110 |

**HTTP 持续连接与无状态** 持续连接：描述底层连接能否复用。 无状态：描述 HTTP 应用协议是否天然记录先前请求的应用状态。 两者不冲突。 因此： HTTP/1.1 可以同时具有：

- 无状态；
- 持续连接。

**流水线与并行** 流水线：一条连接上连续发送多个请求。 并行：同时使用多条连接。 二者不是同一概念。

### 本章所有重要公式

**DNS 查询时间**

$$
\boxed{
T_{\mathrm{DNS}}=\sum_{i=1}^{n}RTT_i
}
$$

相同 RTT 时：

$$
\boxed{
T_{\mathrm{DNS}}=nRTT
}
$$

**单个 HTTP 小对象**

$$
\boxed{
T=2RTT
}
$$

考虑对象理想发送时延：

$$
\boxed{
T\approx2RTT+\frac{L}{R}
}
$$

**非持续串行 HTTP**

$$
\boxed{
T=2(n+1)RTT
}
$$

**持续非流水线 HTTP**

$$
\boxed{
T=(n+2)RTT
}
$$

**持续流水线 HTTP** 在至少存在一个引用对象的经典理想模型中：

$$
\boxed{
T=3RTT
}
$$

**非持续并行 HTTP**

$$
\boxed{
T=
\left(
2+2\left\lceil\frac{n}{m}\right\rceil
\right)RTT
}
$$

**DNS + HTTP** 单个小对象：

$$
\boxed{
T_{\mathrm{total}}
=
T_{\mathrm{DNS}}+2RTT_{\mathrm{Web}}
}
$$

**慢开始累计发送量**

$$
\boxed{
S_r=w(2^r-1)
}
$$

**慢开始最少轮数**

$$
\boxed{
r=
\left\lceil
\log_2\left(\frac{K}{w}+1\right)
\right\rceil
}
$$

**C/S 文件分发**

$$
\boxed{
D_{CS}\geq
\max\left\{
\frac{NF}{u_s},
\frac{F}{d_{\min}}
\right\}
}
$$

**P2P 文件分发**

$$
\boxed{
D_{P2P}\geq
\max\left\{
\frac{F}{u_s},
\frac{F}{d_{\min}},
\frac{NF}{u_s+\sum_{i=1}^{N}u_i}
\right\}
}
$$
