本章按网络应用模型、DNS、FTP、电子邮件、HTTP 与跨层综合题展开，重点掌握通信时序、协议选择与 RTT 计算。

## 一、先建立整章知识框架

第 6 章叫应用层（Application Layer），是计算机网络体系结构中直接为网络应用提供通信服务的一层。

这一章与前面几章的区别在于：

- 物理层解决比特如何传输。
- 数据链路层解决相邻节点之间的帧传输。
- 网络层解决分组如何跨网络到达目的主机。
- 传输层解决不同主机上的进程如何通信。
- 应用层解决应用进程之间按照什么规则交换信息。

例如，在浏览器中输入一个网址，背后可能同时涉及：

```text
用户输入 https://www.example.com

          │
          ▼
① DNS：查询域名对应的 IP 地址
          │
          ▼
② TCP：与服务器建立可靠连接
          │
          ▼
③ TLS：HTTPS 场景下建立安全通信
          │
          ▼
④ HTTP：请求 HTML 页面
          │
          ▼
⑤ HTTP：获取图片、CSS、JavaScript 等资源
          │
          ▼
⑥ 浏览器解析、渲染页面
```

在典型 408 题目中，如果采用明文 HTTP/1.1，通常只考虑 DNS、TCP、HTTP 及相关网络层、链路层过程；如果明确使用 HTTPS 或 HTTP/3，则应按题目指定的技术条件分析。

## 二、网络应用模型：C/S 与 P2P

这是本章的基础概念部分，主要考选择题，但会与端口、连接建立及文件分发结合考查。

### 2.1 客户/服务器模型（C/S）

C/S 即 Client/Server。

基本结构：

```text
          客户端 A
             │
             ▼
客户端 B → 服务器 ← 客户端 C
             ▲
             │
          客户端 D
```

客户端的特点：

1. 主动发起服务请求。
2. 通常不需要一直运行。
3. 通常需要知道服务器的地址。
4. 一般使用临时端口与服务器通信。

服务器的特点：

1. 通常长期运行。
2. 被动等待客户端的初始连接或请求。
3. 通常具有稳定的访问地址。
4. 监听特定服务端口。
5. 可以同时服务多个客户端。

典型应用包括 DNS、FTP、Web 和电子邮件服务。

### 2.2 两个容易混淆的问题

问题一：服务器必须提前知道客户端 IP 吗？

不需要。

例如：

```text
客户端 192.168.1.10:50000

             │ TCP 连接请求
             ▼

服务器 203.0.113.10:80
```

服务器收到连接请求之后，可以根据报文中的源地址和源端口识别客户端。

因此：

- 客户端需要知道服务器的目标地址与端口。
- 服务器通常不需要预先知道每个客户端的地址。

问题二：服务器能主动给客户端发送数据吗？

当然可以。

客户端主动建立初始连接，并不意味着服务器以后只能被动接收数据。

例如 HTTP：

```text
客户端 → HTTP GET 请求 → 服务器
客户端 ← HTML 响应 ← 服务器
```

服务器自然需要发送响应数据。

TCP 本身提供全双工通信能力。

### 2.3 P2P 对等模型

P2P 即 Peer-to-Peer。

其核心是：每个对等节点既可以获取资源，也可以向其他节点提供资源。

```text
       节点 A
      ↗      ↘
   节点 B ↔ 节点 C
      ↘      ↗
       节点 D
```

典型例子是 BitTorrent 文件共享。

假设有 100 个用户下载一个文件。

在 C/S 模型下，文件主要由中心服务器上传。

在 P2P 模型下：

```text
用户 A 下载一部分
       ↓
把已经获得的部分上传给 B

用户 B 下载另一部分
       ↓
又把这一部分上传给 C
```

因此，随着节点数量增加，系统可能获得更多上传能力。

但不能因此断言 P2P 一定比 C/S 安全、稳定或速度快。

### 2.4 两种模型比较

| 比较内容      | C/S         | P2P          |
| --------- | ----------- | ------------ |
| 角色        | 客户、服务器相对固定  | 节点可以兼任双方     |
| 数据位置      | 通常集中        | 相对分散         |
| 管理        | 比较集中        | 比较分散         |
| 扩展能力      | 容易受到服务器性能限制 | 节点可以贡献额外资源   |
| 单点故障      | 中心服务器可能成为单点 | 可以减少对中心服务的依赖 |
| 安全管理      | 便于集中实施      | 节点信任问题更复杂    |
| 是否允许服务器存在 | 需要服务器       | 也可以存在辅助服务器   |

P2P 不等于系统中完全不存在服务器。

### 2.5 2019 年 408 真题

题目：下列关于网络应用模型的叙述中，错误的是哪一项？

A. P2P 模型中节点之间具有对等关系。

B. C/S 模型中客户与客户之间可以直接通信。

C. C/S 模型中主动发起通信的是客户。

D. 向大量用户分发同一个文件时，P2P 通常具有时间优势。

答案：B。

解析：

- A 正确。P2P 的核心是对等节点共享资源。
- B 错误。在典型 C/S 应用结构中，客户之间主要通过服务器交换应用数据。
- C 正确。客户端主动发起初始通信。
- D 正确。P2P 中节点可以相互上传，增加整体上传能力。

注意 B 的判断范围是题目讨论的 C/S 应用模型，并不是说两个客户端在整个互联网中永远不能建立直接连接。

考试结论： 客户端主动请求、服务器提供服务；P2P 节点可以兼任请求者与提供者。

## 三、DNS 域名系统：应用层第一大重点

DNS 是本章高频考点，尤其容易考查询次数、递归与迭代以及访问网页的总时延。

### 3.1 DNS 解决什么问题？

DNS 的完整名称是 Domain Name System，即域名系统。

例如：

```text
www.example.com
       │
       │ DNS 查询
       ▼
203.0.113.10
```

DNS 将人容易记忆的域名解析为网络通信所需的地址。

不过，DNS 不只是简单的域名—IP 对照表。

它具有三个核心特点：

1. 层次化命名空间。
2. 分布式数据库。
3. 分布式查询和缓存机制。

### 3.2 DNS 的域名层次结构

例如：

```text
www.cs.example.com
```

从右向左分析：

```text
根域 .
  │
  └── com                 顶级域
       │
       └── example        二级域
            │
            └── cs        下级域
                 │
                 └── www  主机标签
```

注意：从逻辑上看，一个完整域名最右侧还存在根域 `.`，通常书写时省略。

常见顶级域：

| 域名     | 说明                  |
| ------ | ------------------- |
| `.com` | 通用顶级域               |
| `.org` | 通用顶级域               |
| `.net` | 通用顶级域               |
| `.cn`  | 中国国家和地区顶级域          |
| `.edu` | 教育相关顶级域，使用范围受注册规则限制 |

DNS 层次化命名不是说一台服务器管理所有域名。

相反，正是为了把不同域的管理权分散给不同服务器。

### 3.3 DNS 资源记录

DNS 还保存各种资源记录（Resource Record，RR）。

| 类型    | 功能              | 举例                                     |
| ----- | --------------- | -------------------------------------- |
| A     | 域名映射到 IPv4 地址   | `www.example.com → 203.0.113.10`       |
| AAAA  | 域名映射到 IPv6 地址   | `www.example.com → 2001:db8::1`        |
| NS    | 指定区域的权威 DNS 服务器 | `example.com → ns1.example.com`        |
| CNAME | 域名别名            | `www.example.com → server.example.com` |
| MX    | 指定邮件接收服务器       | `example.com → mail.example.com`       |

408 常见判断：

- 查询网页服务器地址：通常涉及 A 或 AAAA。
- 查询邮件服务器：可能涉及 MX。
- 查询域名别名：涉及 CNAME。
- 查找某个域的权威服务器：涉及 NS。

DNS 查询不一定都是查询 A 记录。

### 3.4 四种重要域名服务器

这是必背知识点。

#### ① 根域名服务器

根服务器位于 DNS 权威层次结构的顶端。

例如需要解析：

```text
www.example.com
```

根服务器一般不会直接返回目标主机的 IP，而是提供负责 `.com` 顶级域的服务器信息。

可以理解为：

> 我不直接负责这个网站，但我知道应该去哪个顶级域服务器继续查询。

经典 DNS 根服务有 13 个逻辑标识（A～M），不等于全球只有 13 台物理服务器。

#### ② 顶级域名服务器

例如 `.com` 的顶级域服务器。

它可以告诉递归解析器，应该向哪个权威服务器继续查询 `example.com` 相关记录。

#### ③ 权威域名服务器

权威服务器保存自己负责区域的 DNS 数据。

例如：

```text
example.com 的权威服务器
```

可能保存：

```text
www.example.com → 203.0.113.10
mail.example.com → 203.0.113.20
```

如果它负责对应记录，可以给出权威回答。

#### ④ 本地域名服务器

也常称为本地 DNS 服务器或递归解析器。

它通常由 ISP、学校、企业或公共 DNS 服务商提供。

主要负责：

- 接收主机的查询请求。
- 检查缓存。
- 缓存未命中时继续解析。
- 将最终结果返回主机。
- 缓存查询结果。

注意：

本地域名服务器并不处在“根—顶级域—权威服务器”这一权威层次中的固定一级。

它是站在客户端一侧提供解析服务的角色。

### 3.5 DNS 递归查询与迭代查询

这是整章最重要的概念区别之一。

#### ① 递归查询

定义：

查询者向服务器提出查询后，被查询服务器需要负责后续查询，并最终返回结果。

通俗理解：

> 我把问题交给你，你负责查到底。

示意：

```text
主机 H
  │
  │ 递归请求
  ▼
本地 DNS
  │
  │ 继续查询
  ▼
其他 DNS 服务器
```

主机只需要等待最终结果。

#### ② 迭代查询

定义：

被查询服务器如果没有最终答案，可以告诉查询者下一步应该找谁。

通俗理解：

> 我不知道最终答案，但我告诉你下一站去哪儿。

示意：

```text
             本地 DNS
                 │
                 │ 查询
                 ▼
              根 DNS
                 │
                 │ 返回顶级域服务器信息
                 ▼
             本地 DNS
                 │
                 │ 再次查询
                 ▼
              TLD DNS
                 │
                 │ 返回权威服务器信息
                 ▼
             本地 DNS
                 │
                 │ 再次查询
                 ▼
              权威 DNS
                 │
                 │ 返回最终记录
                 ▼
             本地 DNS
```

关键区别如下：

| 对比        | 递归查询      | 迭代查询           |
| --------- | --------- | -------------- |
| 谁继续查询     | 被查询服务器    | 查询者            |
| 查询结果      | 最终答案或失败   | 最终答案或下一站信息     |
| 查询者负担     | 较小        | 较大             |
| 典型 408 场景 | 主机到本地 DNS | 本地 DNS 到其他 DNS |

### 3.6 最典型的 DNS 解析全过程

假设主机 H 要访问：

```text
www.example.com
```

条件：

- 没有 DNS 缓存。
- 主机采用递归查询。
- 本地 DNS 采用迭代查询。

完整过程：

<Steps>

<Step>

    ### 主机向本地 DNS 发起递归查询

    主机 H 查询 `www.example.com`，本地 DNS 缓存未命中。

</Step>

<Step>

    ### 本地 DNS 向根服务器查询

    根服务器返回 `.com` 顶级域服务器的转介信息。

</Step>

<Step>

    ### 向顶级域服务器查询

    `.com` 服务器返回负责 `example.com` 的权威服务器信息。

</Step>

<Step>

    ### 向权威服务器查询并返回结果

    权威服务器回答目标地址；本地 DNS 将结果缓存并返回主机。

</Step>

</Steps>

注意主机一般不是自己分别查询根服务器、顶级域服务器和权威服务器。

典型情况下，本地 DNS 帮它完成后续工作。

### 3.7 DNS 缓存与 TTL

DNS 为了避免重复查询，会缓存解析结果。

例如：

```text
第一次访问 www.example.com

本地DNS没有缓存
       ↓
查询根、顶级域、权威服务器
       ↓
得到IP并缓存
```

第二次访问：

```text
本地DNS缓存命中
       ↓
直接返回IP
```

TTL 即 Time To Live。

假设：


$$
TTL=3600\text{ s}
$$

表示相应 DNS 记录可以按有效 TTL 在缓存中保留。

一般而言：

- TTL 较大：缓存命中机会更高、查询负担更小，但记录变化传播可能较慢。
- TTL 较小：更新更快被重新发现，但查询流量可能增加。

注意 DNS 记录 TTL 与 IPv4 首部中的 TTL 不是同一个含义。

DNS TTL 是以时间为单位的缓存有效期；IPv4 TTL 是限制分组转发寿命的字段，路由转发时通常减 1。

### 3.8 DNS 查询次数计算

这是真题非常喜欢设置陷阱的地方。

假设本地 DNS 使用迭代查询，缓存全部未命中，解析过程需要依次访问：

```text
根服务器
    ↓
顶级域服务器
    ↓
权威服务器
```

那么本地 DNS 发出：


$$
N=3
$$

次查询。

但是，如果本地 DNS 缓存已经命中：


$$
N=0
$$

如果题目规定全部使用递归查询，且本地 DNS 无缓存，那么在经典全递归教学模型中，本地 DNS 可以只向下一服务器发出一次递归查询：


$$
N=1
$$

注意题目问的是谁发出了多少次查询。

不能把所有服务器的查询数混在一起。

### 3.9 2010 年 408 真题：递归查询数量

题意：

本地域名服务器没有缓存，采用递归方式解析其他网络的主机域名。

问：用户主机和本地域名服务器分别发送多少条查询请求？

答案：1 条、1 条。

解析：

主机只向本地 DNS 发出一个请求。

本地 DNS 在经典全递归模型中继续向其他服务器发出一个递归请求。

后续查询由被请求的服务器负责。

因此：


$$
N_{\text{主机}}=1
$$


$$
N_{\text{本地DNS}}=1
$$

这道题最容易错在把递归查询和迭代查询混淆。

### 3.10 2016 年 408 真题：最少、最多查询次数

题目给出：

```text
www.abc.xyz.com
```

假设所有相关 DNS 服务器采用迭代方式。

问：指定 DNS 服务器完成解析时，可能发出查询的最少次数和最多次数是多少？

答案：0 次、4 次。

最少情况：

服务器有目标域名的有效缓存。


$$
N_{\min}=0
$$

最多情况：

根据原题给定的域名层次及委派结构，可能依次查询：

```text
根 DNS
   ↓
com DNS
   ↓
xyz.com DNS
   ↓
abc.xyz.com DNS
```

因此：


$$
N_{\max}=4
$$

记住：

查询次数不是简单等于域名中点号的数量。

实际查询多少次，还取决于缓存、委派层次，以及题目是否明确划分了独立 DNS 区域。

### 3.11 DNS 查询时延

假设需要依次完成 \$k\$ 次 DNS 请求—响应。

每次往返时延分别为：


$$
RTT_1,RTT_2,\ldots,RTT_k
$$

若不存在并行查询，并且忽略其他处理时延：


$$
\boxed{T_{\mathrm{DNS}}=\sum_{i=1}^{k}RTT_i}
$$

例如：

| 阶段       | RTT   |
| -------- | ----- |
| 查询根服务器   | 10 ms |
| 查询顶级域服务器 | 20 ms |
| 查询权威服务器  | 30 ms |

则：


$$
T_{\mathrm{DNS}}=10+20+30=60\text{ ms}
$$

但还要注意：

如果题目从主机发出 DNS 请求开始计时，并且单独给出了主机到本地 DNS 的通信时延，也应该按题设计入。

如果本地 DNS 缓存命中，可能省略后续查询。

DNS 计算的关键不是数服务器总数，而是数实际发生的串行查询往返。

## 四、FTP 文件传输协议

FTP（File Transfer Protocol）主要解决文件传输问题。

它采用 C/S 模型，使用 TCP。

### 4.1 FTP 最重要的特点：双连接

FTP 不通过一条 TCP 连接同时完成全部控制和数据交换，而是将两种连接分开。

```text
FTP 客户端                    FTP 服务器

     │                             │
     ├──── 控制连接 TCP 21 ────────┤
     │                             │
     ├════ 数据连接 ═══════════════┤
     │                             │
```

#### 控制连接

用于传输：

- 用户名和密码。
- 文件操作命令。
- 目录操作命令。
- 服务器状态与响应。

例如：

```text
USER
PASS
LIST
RETR
STOR
QUIT
```

控制连接一般在整个 FTP 会话期间保持打开。

其服务器端口：


$$
21
$$

#### 数据连接

用于传输：

- 文件内容。
- 目录列表。

数据连接通常按需要建立，完成一次传输后关闭。

因此：

```text
一次FTP会话

1条控制连接
+
若干条数据连接
```

<Tabs items={['主动模式 PORT', '被动模式 PASV']} defaultIndex={0}>

<Tab value="主动模式 PORT">

在主动模式下：

FTP 服务器主动建立数据连接。

过程：

```text
1. 客户端连接服务器21端口
2. 建立控制连接
3. 客户端告知自己的数据端口
4. 服务器主动连接客户端的数据端口
5. 传输文件
```

示意：

```text
客户端                          服务器

   │                               │
   ├─────────────→ TCP 21           │
   │       建立控制连接              │
   │                               │
   │       TCP 20 ←─────────────────┤
   │          建立数据连接           │
```

传统主动模式中：

- 控制连接：服务器端口 21。
- 数据连接：服务器通常使用本地端口 20。

注意数据连接是服务器主动向客户端建立的。

</Tab>

<Tab value="被动模式 PASV">

被动模式下：

客户端主动建立数据连接。

过程：

```text
1. 客户端连接服务器21端口
2. 建立控制连接
3. 客户端发送PASV
4. 服务器告诉客户端数据端口
5. 客户端主动连接服务器数据端口
6. 传输文件
```

示意：

```text
客户端                            服务器

   │                                 │
   ├─────────────→ TCP 21             │
   │          控制连接                │
   │                                 │
   ├─────────────→ 协商出的数据端口    │
   │          数据连接                │
```

被动模式的数据端口不要求固定为 20。

</Tab>

</Tabs>

### 4.4 主动模式与被动模式比较

| 内容        | 主动模式    | 被动模式       |
| --------- | ------- | ---------- |
| 控制连接发起方   | 客户端     | 客户端        |
| 控制连接服务器端口 | 21      | 21         |
| 数据连接发起方   | 服务器     | 客户端        |
| 服务器传统数据端口 | 20      | 协商端口       |
| 区分依据      | 服务器主动连接 | 服务器等待客户端连接 |

记忆：

FTP 的主动与被动，只看数据连接由谁主动建立。

### 4.5 FTP 连接数量计算

假设用户登录 FTP 服务器后：

1. 查看一次目录。
2. 下载两个文件。
3. 上传一个文件。
4. 最后退出。

若每次目录或文件数据传输单独建立数据连接，则：

目录列表：1 条数据连接。

下载两个文件：2 条数据连接。

上传一个文件：1 条数据连接。

再加控制连接：


$$
N=1+1+2+1=5
$$

总共建立 5 条 TCP 连接。

但如果问的是某个时刻同时存在几条连接，通常就不能直接回答 5。

在逐次建立并关闭数据连接的情况下，传输某个文件时可能只同时存在：

```text
1条控制连接 + 1条数据连接
```

即 2 条。

### 4.6 FTP 的 ASCII 模式和二进制模式

FTP 可以指定文件传输表示方式。

| 方式     | 适合对象       | 特点         |
| ------ | ---------- | ---------- |
| ASCII  | 文本文件       | 可能进行文本格式转换 |
| Binary | 图片、压缩包、程序等 | 保持原始字节     |

例如传输 `.zip` 压缩包，应该采用二进制方式，以免因文本转换破坏数据。

### 4.7 2009 年 408 真题

题意：FTP 客户端与服务器之间传递 FTP 命令时，使用什么连接？

答案：建立在 TCP 上的控制连接。

这是最基本的 FTP 考点。

```text
FTP命令 → TCP控制连接
文件数据 → TCP数据连接
```

### 4.8 2017 年 408 真题

题目要求判断关于 FTP 的错误叙述。

其中错误项认为：

FTP 服务器一定与客户端的 TCP 20 端口建立数据连接。

答案：该叙述错误。

原因：

主动模式下，20 通常是服务器的数据连接本地端口，并不是客户端固定使用的端口。

被动模式下，服务器一般使用协商出的数据端口。

所以不能说 FTP 的数据连接总是固定使用 20 端口。

这一题实际上同时考查：

1. FTP 控制连接与数据连接的分离。
2. FTP 主动/被动模式。
3. 服务器端口与客户端端口的区别。

## 五、电子邮件系统：SMTP、POP3、IMAP、MIME

这部分主要考协议分工、传输方向、端口以及传统邮件内容格式。

### 5.1 电子邮件系统的组成

主要有三个部分：

1. 用户代理 UA。
2. 邮件服务器。
3. 邮件相关协议。

典型邮件传输过程：

```text
用户 A
  │
  │ SMTP
  ▼
发送方邮件服务器
  │
  │ SMTP
  ▼
接收方邮件服务器
  │
  │ POP3 / IMAP
  ▼
用户 B
```

记住这张图，电子邮件相关选择题基本就有了判断基础。

<Tabs items={['SMTP 发送', 'POP3 下载', 'IMAP 同步']} defaultIndex={0}>

<Tab value="SMTP 发送">

SMTP 全称 Simple Mail Transfer Protocol。

主要负责：

- 客户端向邮件服务器发送邮件。
- 邮件服务器之间转发邮件。

经典 408 考试口径：

```text
SMTP
TCP
服务器端口25
Push（推送）
```

Push 的含义是发送方主动把邮件提交或推送到目标邮件服务器。

SMTP 不负责典型邮件客户端从邮箱服务器读取已有邮件的过程。

</Tab>

<Tab value="POP3 下载">

POP3 全称 Post Office Protocol Version 3。

主要用于客户端从邮件服务器获取邮件。

```text
POP3
TCP
服务器端口110
Pull（拉取）
```

例如：

```text
用户打开邮件客户端
       ↓
客户端连接邮件服务器
       ↓
下载收件箱中的邮件
```

POP3 更强调下载邮件。

传统用法可能把邮件下载后从服务器删除，但也可以配置保留服务器副本。

所以：

POP3 不意味着服务器上的邮件一定在下载后被删除。

</Tab>

<Tab value="IMAP 同步">

IMAP 全称 Internet Message Access Protocol。

默认：

```text
IMAP
TCP
服务器端口143
```

与 POP3 相比，IMAP 更适合：

- 多设备访问同一邮箱。
- 服务器端文件夹管理。
- 已读、未读状态同步。
- 邮件在线管理。

例如一个用户同时使用手机和电脑。

通过 IMAP，手机上将一封邮件标为已读之后，电脑上通常也可以同步看到已读状态。

</Tab>

</Tabs>

### 5.5 SMTP、POP3、IMAP 对比

| 项目           | SMTP    | POP3    | IMAP       |
| ------------ | ------- | ------- | ---------- |
| 主要作用         | 发送与转发   | 下载邮件    | 在线访问与同步    |
| 通信方向         | 发送方主动提交 | 客户端主动取信 | 客户端主动访问与同步 |
| 传输层          | TCP     | TCP     | TCP        |
| 经典端口         | 25      | 110     | 143        |
| 典型特点         | Push    | Pull    | 服务器端状态同步   |
| 是否用于邮件服务器间转发 | 是       | 否       | 否          |

补充：现实邮件系统还经常使用邮件提交端口 587、隐式 TLS 邮件提交端口 465，以及加密邮件访问端口 993、995。408 基础题通常优先考 25、110、143。

### 5.6 MIME：解决附件和非 ASCII 内容

传统 SMTP 面向 ASCII 文本。

但电子邮件中可能有：

- 中文。
- 图片。
- 视频。
- 音频。
- PDF 附件。
- 压缩包。

因此需要扩展邮件内容表示能力。

MIME（Multipurpose Internet Mail Extensions）主要用于描述和编码邮件内容。

例如：

```text
电子邮件
   │
   ├── 文本正文
   │
   ├── HTML正文
   │
   └── 图片或PDF附件
```

MIME 可以提供：

- 内容类型说明。
- 字符集描述。
- 内容传输编码。
- 多部分邮件结构。

例如 Base64 可将二进制内容表示成适于文本传输的形式。

但必须强调：

MIME 不是替代 SMTP 的邮件传输协议。

SMTP 负责传送，MIME 主要负责内容表示。

### 5.7 邮件信封与首部

电子邮件可以区分：

```text
邮件
 ├── 信封
 └── 内容
      ├── 首部
      └── 主体
```

例如邮件内容：

```text
From: alice@example.com
To: bob@example.net
Subject: Hello

Hello Bob!
```

其中：

- `From`：邮件内容中的发件人字段。
- `To`：邮件内容中的收件人字段。
- `Subject`：主题。
- 空行后为正文。

SMTP 投递使用的信封收件人信息与内容首部中的 `To` 字段不必完全一致。

### 5.8 2012 年 408 真题：邮件完整流程

题意：给出用户 1 向用户 2 发送电子邮件的完整流程，判断三个通信阶段使用的协议。

正确组合：

```text
SMTP → SMTP → POP3
```

答案：D。

分析：

第一阶段：

发送方用户代理向邮件服务器发送邮件。

使用 SMTP。

第二阶段：

发送方邮件服务器向接收方邮件服务器转发邮件。

使用 SMTP。

第三阶段：

接收方客户端获取邮件。

可以使用 POP3。

记忆：

SMTP 送信，POP3 取信。

### 5.9 2013 年 408 真题：SMTP 的适用范围

题目判断以下说法：

I. 传统 SMTP 直接传输内容采用 7 位 ASCII 表示。

II. SMTP 可以在邮件服务器之间发送邮件。

III. SMTP 可以将邮件从用户代理发送到邮件服务器。

IV. SMTP 可以从邮件服务器向用户代理提供取信服务。

正确项是：


$$
I,\ II,\ III
$$

IV 错误，因为取信通常由 POP3 或 IMAP 负责。

注意 I 指经典 SMTP 基础协议口径。现代邮件系统存在 MIME 和 SMTP 扩展，不能把这一教材表述理解为现实中永远不能传输非 ASCII 内容。

### 5.10 2015 年与 2018 年真题

2015 年考点：POP3 使用哪种传输层服务？

POP3 使用 TCP，因此属于：

有连接、可靠的传输服务。

2018 年考点：以下哪种内容无需转换即可由传统 SMTP 直接传输？

选项包括 JPEG、MPEG、EXE、ASCII 文本。

答案：ASCII 文本。

二进制数据通常需要经过适当内容编码。

### 5.11 Webmail 是什么协议？

例如：

通过浏览器访问某个网页邮箱。

浏览器与网页服务器之间使用：

```text
HTTP / HTTPS
```

并不是说打开网页邮箱，浏览器就一定在直接使用 POP3。

网页邮箱的后台系统仍可能使用 SMTP、IMAP 等邮件协议。

## 六、WWW 与 HTTP：本章最重要的综合计算考点

这一部分不仅考概念，而且经常与 DNS、TCP、ARP、NAT 等内容结合出题。

尤其是 HTTP RTT 计算，必须真正理解。

### 6.1 WWW、URL、HTTP、HTML 的区别

WWW（World Wide Web）即万维网。

互联网、万维网、HTTP 不是同一个概念。

| 概念       | 含义                |
| -------- | ----------------- |
| Internet | 互联网络              |
| WWW      | 通过超链接组织的 Web 信息系统 |
| URL      | 统一资源定位符           |
| HTTP     | 超文本传输协议           |
| HTML     | 超文本标记语言           |
| 浏览器      | Web 客户端           |
| Web 服务器  | 提供 Web 资源的服务器     |

例如：

```text
https://www.example.com:443/index.html
```

可以拆成：

```text
https          协议方案
www.example.com 主机名
443            端口
/index.html    资源路径
```

URL 的典型形式为：

```text
scheme://host:port/path
```

其中端口经常可以省略。

HTTP 默认使用 80，HTTPS 默认使用 443。

### 6.2 HTTP 的基本工作方式

HTTP 采用请求—响应模式。

<Steps>

<Step>

    ### 请求 HTML

    浏览器发出 `GET /index.html`，服务器返回 HTML 响应。

</Step>

<Step>

    ### 请求页面依赖资源

    浏览器解析 HTML，按需要请求 `GET /logo.png` 等资源，服务器返回数据。

</Step>

</Steps>

最重要的理解是：

一个网页不一定只有一个 HTTP 对象。

例如：

```text
index.html
    │
    ├── logo.png
    ├── photo1.jpg
    ├── photo2.jpg
    ├── style.css
    └── app.js
```

这里一共涉及：

$$
1+5=6
$$

个资源对象。

如果这些对象都需要从服务器获取，通常需要相应的 HTTP 请求。

但这不代表必须建立 6 条 TCP 连接。

TCP 连接数量取决于是否允许复用、并行等。

### 6.3 HTTP 请求报文

典型 HTTP/1.1 请求：

```text
GET /index.html HTTP/1.1
Host: www.example.com
Connection: keep-alive
User-Agent: ExampleBrowser
Cookie: session=abc123
```

结构：

```text
请求行
  │
请求首部
  │
空行
  │
可选请求体
```

请求行：

```text
GET /index.html HTTP/1.1
```

含义分别为：

- `GET`：请求方法。
- `/index.html`：目标资源。
- `HTTP/1.1`：协议版本。

常见请求方法：

| 方法     | 作用               |
| ------ | ---------------- |
| GET    | 获取资源             |
| POST   | 提交数据供服务器处理       |
| HEAD   | 获取响应首部，通常不返回响应主体 |
| PUT    | 创建或替换指定资源        |
| DELETE | 删除指定资源           |

注意，GET 并不是“完全不能提交参数”，POST 也不意味着每个 POST 一定修改服务器数据。

考试主要关注方法的典型语义。

### 6.4 HTTP 响应报文

例如：

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 120

<html>...</html>
```

结构：

```text
状态行
  │
响应首部
  │
空行
  │
响应体
```

状态码分类：

| 状态码 | 含义       |
| --- | -------- |
| 1xx | 信息性响应    |
| 2xx | 请求成功     |
| 3xx | 重定向      |
| 4xx | 客户端侧请求错误 |
| 5xx | 服务器侧错误   |

常见状态码：

| 状态码 | 含义                    |
| --- | --------------------- |
| 200 | OK，请求成功               |
| 301 | 永久重定向                 |
| 302 | 临时重定向                 |
| 304 | 条件请求下，资源未修改           |
| 400 | Bad Request           |
| 403 | Forbidden             |
| 404 | Not Found             |
| 500 | Internal Server Error |
| 503 | Service Unavailable   |

例如：

服务器返回 `404`，说明请求的目标资源没有找到，并不意味着 TCP 连接一定建立失败。

这两个问题位于不同协议层次。

### 6.5 HTTP 的无状态性

这是非常典型的选择题考点。

HTTP 是无状态协议。

含义：

HTTP 协议本身不要求服务器自动记住客户端此前各次请求的应用状态。

例如：

```text
第一次请求：GET /home
第二次请求：GET /profile
```

仅凭 HTTP 的基本请求—响应规则，服务器不会天然知道第二次请求对应哪个已登录用户。

那么网站为什么可以保持登录状态？

因为可以利用：

- Cookie。
- Session。
- Token。

等额外机制。

因此：

```text
HTTP无状态
     ≠
网站无法记住用户
```

### 6.6 Cookie 与 Session

假设用户第一次登录。

服务器可能返回：

```text
Set-Cookie: sessionId=ABC123
```

浏览器保存后，后续符合条件的请求会发送：

```text
Cookie: sessionId=ABC123
```

服务器可以通过会话标识查找用户的 Session。

示意：

```text
用户登录
   ↓
服务器创建会话信息
   ↓
服务器发送Set-Cookie
   ↓
浏览器保存Cookie
   ↓
后续请求携带Cookie
   ↓
服务器关联对应Session
```

区别：

| Cookie        | Session            |
| ------------- | ------------------ |
| 由客户端保存并携带相关数据 | 通常由服务器维护会话状态       |
| 可以保存会话标识      | 可以保存用户相关会话信息       |
| 通过 HTTP 首部传递  | 不属于 HTTP 报文的固定组成部分 |

注意：

Cookie 不是程序代码，而是数据。

同时，Cookie 的存在也不代表用户一定已经通过身份认证。

### 6.7 2015 年 408 真题：HTTP 报文分析

题目给出：

```text
GET /index.html HTTP/1.1
Host: www.test.edu.cn
Connection: Close
Cookie: 123456
```

问：哪项说法错误？

其中一个选项认为：

浏览器请求使用持续连接。

这项错误。

因为：

```text
Connection: Close
```

表明客户端要求当前请求—响应结束后关闭连接。

即使使用 HTTP/1.1，题目也明确要求关闭连接。

由此总结：

- HTTP/1.1 默认通常采用持久连接。
- `Connection: close` 可以明确要求关闭。
- `Host` 表示目标服务器或虚拟主机，而不是客户端。
- `Cookie` 表示客户端携带的 Cookie 数据。

## 七、HTTP 持久连接、非持久连接与流水线

这是第 6 章最重要的计算部分。

必须分清三个不同概念：

持久连接、流水线、并行连接。

### 7.1 非持久 HTTP 连接

非持久连接的典型含义：

每获取一个对象，重新建立一条 TCP 连接。

过程：

```text
建立TCP连接
    ↓
请求对象1
    ↓
返回对象1
    ↓
关闭连接

建立新的TCP连接
    ↓
请求对象2
    ↓
返回对象2
    ↓
关闭连接
```

经典 HTTP/1.0 默认按照非持久连接模型分析。

### 7.2 持久 HTTP 连接

持久连接：

多个 HTTP 请求与响应可以复用同一条 TCP 连接。

过程：

```text
建立TCP连接
    ↓
请求对象1
    ↓
返回对象1
    ↓
请求对象2
    ↓
返回对象2
    ↓
请求对象3
    ↓
返回对象3
    ↓
关闭TCP连接
```

HTTP/1.1 默认使用持久连接。

好处是避免每个对象都重复进行 TCP 三次握手。

### 7.3 非流水线持久连接

非流水线要求：

前一个请求的响应完成后，才能在该连接上继续发送下一个请求。

```text
请求1 ───────────→
      ←────────── 响应1

请求2 ───────────→
      ←────────── 响应2

请求3 ───────────→
      ←────────── 响应3
```

虽然复用同一条 TCP 连接，但请求仍然按顺序进行。

### 7.4 流水线持久连接

流水线允许：

在收到前一个响应之前，继续发送后续请求。

```text
请求1 ─────→
请求2 ─────→
请求3 ─────→

      ←──── 响应1
      ←──── 响应2
      ←──── 响应3
```

在经典 408 简化时延模型下，如果多个请求可以连续发送，忽略对象发送时间和处理时间，那么这些对象的请求—响应过程可以近似按一个 RTT 计算。

但是：

如果图片地址只有获取 HTML 之后才能知道，那么不能在 HTML 尚未返回时就提前请求这些图片。

这个依赖关系是 HTTP 综合题最容易漏掉的条件。

### 7.5 并行 TCP 连接

并行连接与流水线不同。

并行连接指同时建立多条 TCP 连接。

例如：

```text
               ┌──TCP连接1──图片1
浏览器 ─────────┼──TCP连接2──图片2
               └──TCP连接3──图片3
```

与流水线比较：

| 概念   | 关键区别                  |
| ---- | --------------------- |
| 持久连接 | 一条 TCP 连接能否复用         |
| 流水线  | 同一连接能否连续发送多个尚未收到响应的请求 |
| 并行连接 | 是否同时使用多条 TCP 连接       |

HTTP/2 还支持多路复用，它和经典 HTTP/1.1 流水线不完全相同。

### 7.6 HTTP 队头阻塞

HTTP/1.1 流水线的响应顺序会造成应用层队头阻塞。

例如：

```text
请求A：大文件
请求B：小图片
请求C：小文本
```

如果 A 的响应迟迟无法完成，后面的响应可能被迫等待。

HTTP/2 通过多路复用缓解 HTTP/1.1 流水线的应用层队头阻塞。

但 HTTP/2 通常基于 TCP。如果 TCP 字节流有缺失数据，多个 HTTP/2 流仍可能受到传输层队头阻塞影响。

HTTP/3 使用 QUIC，在不同流之间处理丢包阻塞的方式又有所不同。

408 基础时延题若没有明确要求，通常不需要把这些现代实现细节加入经典 HTTP/1.x 计算。

<Callout type="warn" title="时间计算的适用范围">

以下经典 RTT 模型默认对象很小、忽略传输与处理时延，并按题设明确的 HTTP 连接方式计算。HTTPS/TLS、HTTP/2 多路复用及 HTTP/3/QUIC 不能机械套用 HTTP/1.x 简化公式。

</Callout>

## 八、HTTP RTT 时间计算：必须彻底掌握

下面建立完整的计算模型。

### 8.1 先理解一个 RTT 是什么

RTT（Round-Trip Time）是往返时延。

例如：

```text
客户端发出请求
       │
       ▼
     服务器
       │
       ▼
客户端收到响应
```

一次请求—响应经过的往返时间，近似为一个 RTT。

在经典简化模型下：

建立 TCP 连接需要一个 RTT。

发送 HTTP 请求并收到小对象需要一个 RTT。

因此，从开始建立 TCP 连接到取回一个小对象：

$$
\boxed{T=2RTT}
$$

这里忽略对象发送时间、处理时间等。

如果需要计入对象发送时间：

$$
T\approx 2RTT+T_{\mathrm{tx}}
$$

其中：

$$
T_{\mathrm{tx}}=\frac{L}{R}
$$

$L$ 为对象长度（bit），$R$ 为相应链路的有效发送速率（bit/s），且假设该简单发送时延模型适用。

<Tabs items={['非持久串行', '持久非流水线', '持久流水线', '非持久并行']} defaultIndex={0}>

<Tab value="非持久串行">

假设：

- 一个 HTML 文件。
- $n$ 个嵌入对象。
- 不允许并行连接。
- 忽略对象传输时间。
- DNS 已经解析完成。

总对象数：

$$
N=n+1
$$

每个对象需要：

$$
2RTT
$$

因此：

$$
\boxed{T_{\mathrm{NP}}=2(n+1)RTT}
$$

例如，HTML 引用了 5 张图片：

$$
n=5
$$

$$
T=2(5+1)RTT
$$

$$
\boxed{T=12RTT}
$$

</Tab>

<Tab value="持久非流水线">

仍然是一个 HTML 加 $n$ 个嵌入对象。

但是所有对象复用一条 TCP 连接。

时间分解：

| 操作                 | RTT     |
| ------------------ | ------- |
| 建立 TCP 连接          | 1       |
| 获取 HTML            | 1       |
| 依次获取 $n$ 个嵌入对象 | $n$ |

因此：

$$
\boxed{T_{\mathrm{P,nonpipe}}=(n+2)RTT}
$$

例如：

HTML + 5 张图片。

$$
T=(5+2)RTT
$$

$$
\boxed{T=7RTT}
$$

注意为什么不是 6 RTT：

因为题目从建立 TCP 连接开始计时，所以还要加上首次握手的 1 RTT。

</Tab>

<Tab value="持久流水线">

仍然使用一条 TCP 连接。

时间分解：

| 操作          | RTT |
| ----------- | --- |
| 建立 TCP 连接   | 1   |
| 获取 HTML     | 1   |
| 流水线请求所有嵌入对象 | 1   |

因此：

$$
\boxed{T_{\mathrm{P,pipe}}\approx 3RTT}
$$

注意这个 3 RTT 是在理想简化模型下的结果。

假如嵌入对象很大、传输速率有限，或者 TCP 拥塞窗口限制发送，那么不能直接套用。

</Tab>

<Tab value="非持久并行">

假设：

- HTML 包含 $n$ 个嵌入对象。
- 最多并行建立 $m$ 条非持久连接。
- 基础 HTML 必须首先获取。
- 对象大小忽略。
- 每一批对象需要 2 RTT。
- 每批可同时建立新的连接。

那么嵌入对象需要分成：

$$
k=\left\lceil\frac{n}{m}\right\rceil
$$

批次。

获取基础 HTML 需要 2 RTT。

因此：

$$
\boxed{ T_{\mathrm{parallel}} = 2RTT+ 2\left\lceil\frac{n}{m}\right\rceil RTT }
$$

例如：

一个 HTML 引用了 7 张图片，最多同时使用 3 条非持久 TCP 连接。

图片分批：

```text
第1批：图片1、2、3
第2批：图片4、5、6
第3批：图片7
```

需要：

$$
\left\lceil\frac{7}{3}\right\rceil=3
$$

批。

所以：

$$
T=2RTT+3\times 2RTT
$$

$$
\boxed{T=8RTT}
$$

</Tab>

### 8.6 四种模型汇总

设一个 HTML 引用 $n$ 个对象，全部来自同一服务器，DNS 已完成，TCP 尚未建立，忽略对象发送和处理时间。

| HTTP 模式              | RTT 总数                               |
| -------------------- | ------------------------------------ |
| 非持久、完全串行             | $2(n+1)$                         |
| 持久、非流水线              | $n+2$                            |
| 持久、理想流水线             | $3$                              |
| 非持久、最多 $m$ 条并行连接 | $2+2\left\lceil n/m\right\rceil$ |

这张表非常重要，但只适用于上述模型。

### 8.7 2024 年 408 真题

题意：

浏览器不支持并行 TCP 连接，使用非持久 HTTP/1.0，请求一个网页。

网页引用了 7 个小图像文件。

从浏览器开始建立 TCP 连接，到接收完全部内容，需要多少 RTT？

答案：16 RTT。

解析：

一个 HTML：

$$
1
$$

7 个图像：

$$
7
$$

一共：

$$
N=8
$$

因为非持久连接且不支持并行：

$$
T=2N\cdot RTT
$$

$$
T=2\times8RTT
$$

$$
\boxed{T=16RTT}
$$

易错答案是 14 RTT。

错误原因是只计算了 7 张图片，没有计算 HTML 本身。

### 8.8 2011 年 408 真题：持续非流水线

题意：

某 HTTP/1.1 页面引用 5 个 JPEG 小图像。

采用持续非流水线方式。

从首个 HTTP 请求已经发出时刻计时，到全部资源收到为止，需要多少 RTT？

答案：6 RTT。

解析：

```text
请求HTML并接收        1RTT
请求图片1             1RTT
请求图片2             1RTT
请求图片3             1RTT
请求图片4             1RTT
请求图片5             1RTT
```

所以：

$$
\boxed{T=6RTT}
$$

为什么不是 7 RTT？

因为题目计时起点是HTTP 请求已经发出，不再包含此前的 TCP 三次握手。

这说明：

HTTP 计算题第一件事，就是看清计时起点。

### 8.9 2020 年 408 真题：DNS + TCP + HTTP

题意：

- 主机访问远程纯文本 Web 页。
- RTT 为 10 ms。
- 本地 DNS 可能有缓存，也可能完全没有缓存。
- 忽略其他时延。
- 按原题图示 DNS 查询结构计算。

问最短、最长访问时间。

答案：20 ms、50 ms。

最短情况：

本地 DNS 已有有效缓存，题设不另计本地解析时延。

需要：

```text
TCP建连        1RTT
HTTP请求响应   1RTT
```

所以：

$$
T_{\min}=2\times10=20\text{ ms}
$$

最长情况：

本地 DNS 无缓存，需要依次查询：

```text
根DNS
顶级域DNS
权威DNS
```

共 3 RTT。

然后：

TCP 建连 1 RTT。

HTTP 请求响应 1 RTT。

所以：

$$
T_{\max}=(3+1+1)RTT
$$

$$
T_{\max}=5\times10
$$

$$
\boxed{T_{\max}=50\text{ ms}}
$$

这道题的本质是：

$$
\boxed{ T_{\mathrm{total}} = T_{\mathrm{DNS}} + T_{\mathrm{TCP}} + T_{\mathrm{HTTP}} }
$$

但如果题目另给出主机访问本地 DNS 的 RTT，不能一概省略；本题的 20 ms 和 50 ms 是按原题网络及计时条件得到的。

### 8.10 2022 年 408 真题：HTTP 与 TCP 慢开始

这一题比普通 RTT 题更难，因为它融合了第 5 章 TCP 的拥塞控制。

题意：

- HTTP/1.1。
- HTML 大小为 1 MSS。
- 页面引用一个大小为 3 MSS 的图像。
- RTT 为 10 ms。
- DNS 已经解析。
- 从建立 TCP 连接开始计时。
- 忽略 HTTP 首部和 TCP 段发送时延。
- 根据原题采用的 TCP 慢开始与最短传输时序计算。

答案：40 ms。

为什么不能直接套普通 HTTP 的 3 RTT？

因为图像不是一个可以忽略发送过程的小对象，而且受到 TCP 拥塞窗口限制。

按本题最短时序：

| 阶段      | 作用                        |
| ------- | ------------------------- |
| 第 1 RTT | TCP 握手，第三次握手可携带首个 HTTP 请求 |
| 第 2 RTT | 传输 1 MSS 的 HTML，拥塞窗口增长    |
| 第 3 RTT | 传输图像中的 2 MSS              |
| 第 4 RTT | 传输图像剩余的 1 MSS             |

因此：

$$
T=4RTT
$$

$$
T=4\times10
$$

$$
\boxed{T=40\text{ ms}}
$$

核心是：不能把 TCP 的拥塞窗口限制忽略掉。

还要注意，第三次握手是否携带应用请求会影响最短时序。原题按最短情况处理，而一般教学题可能采用“完整握手后才发送 HTTP 请求”的简化约定。

考试时必须以题目给出的 TCP 时序、窗口及计时条件为准。

## 九、综合大题：2011 年第 47 题

这是 章节练习中的历年大题整理中收录的应用层重点真题之一。

它把以下知识点结合在了一起：

- 以太网帧分析。
- IPv4 地址读取。
- ARP。
- HTTP 时延。
- NAT。
- 路由器转发。

### 9.1 题目主要条件

某主机：

```text
MAC：00-15-C5-C1-5E-28
IP：10.2.128.100
```

给出网络拓扑和部分以太网帧十六进制内容。

要求分析目的 IP、默认网关 MAC、ARP 广播、HTTP 时延和路由器转发行为。

### 9.2 第一问：解析以太网帧

典型 Ethernet II 帧首部：

```text
目的MAC       6B
源MAC         6B
类型字段      2B
----------------
以太网首部    14B
```

原题帧首部：

```text
00 21 27 21 51 EE
00 15 C5 C1 5E 28
08 00
```

其中：

```text
00-21-27-21-51-EE
```

是目的 MAC。

主机访问的是远程 Web 服务器。

目的 MAC 为默认网关的 MAC，而不是远程 Web 服务器的 MAC。

所以：

默认网关 MAC：

```text
00-21-27-21-51-EE
```

IPv4 首部中的目的地址字节：

```text
40 AA 62 20
```

将每个十六进制字节转换为十进制：

$$
40_{16}=64
$$

$$
AA_{16}=170
$$

$$
62_{16}=98
$$

$$
20_{16}=32
$$

所以：

```text
64.170.98.32
```

即 Web 服务器地址。

### 9.3 第二问：ARP

假设主机要向远程服务器发报文。

它首先根据路由表判断应交给默认网关。

如果不知道默认网关的 MAC 地址，就需要 ARP。

```text
已知网关IP
    ↓
ARP请求
    ↓
获得网关MAC
```

ARP 请求使用广播：

```text
FF-FF-FF-FF-FF-FF
```

因此：

- 协议：ARP。
- 请求帧目的 MAC：广播地址。

注意：

ARP 不是用于查询远程网站 IP 的。

DNS 负责域名解析。

ARP 负责当前链路上下一跳的 IPv4 地址到 MAC 地址的解析。

### 9.4 第三问：HTTP 时延

题目规定：

- 持续 HTTP/1.1。
- 非流水线。
- HTML 引用 5 张 JPEG。
- 从 HTTP 请求发出开始计时。

因此：

$$
T=1RTT+5RTT
$$

$$
\boxed{T=6RTT}
$$

### 9.5 第四问：路由器转发

原题路由器执行 NAT。

主机源地址：

```text
10.2.128.100
```

转换为公网源地址：

```text
101.12.123.15
```

因此路由器需要修改：

1. 源 IP 地址。
2. TTL。
3. IPv4 首部校验和。

这里特别注意：

普通 IPv4 路由器转发时需要使 TTL 减 1，并更新首部校验和。

但不是所有路由器转发都需要修改源 IP 地址。

只有本题执行 NAT，才额外修改了源 IP 地址。

本题未发生 IP 分片，因此不需要因为分片而修改片偏移等字段。

### 9.6 这道大题的解题方法

以后遇到“网络抓包 + HTTP + 路由”题，可以按照下面顺序：

```text
第一步：识别以太网帧首部
第二步：读取源、目的MAC
第三步：读取源、目的IP
第四步：判断目标是否同子网
第五步：确定下一跳
第六步：判断是否需要ARP
第七步：分析TCP/HTTP时序
第八步：判断路由器是否执行NAT
第九步：检查TTL、校验和、分片
```

这种题目非常考验跨章节知识的连接能力。

## 十、综合大题：2021 年第 47 题

这是另一道非常重要的跨层综合题。

考点包括：

- DNS 报文封装。
- ARP 广播。
- 交换机 MAC 地址自学习。
- Web 访问流程。

### 10.1 题目背景

拓扑包含：

```text
H1
 │
 │
交换机 S ─── 本地DNS服务器
 │
 ├── H2
 │
 └── 路由器 R ─── Internet ─── Web服务器
```

条件：

- 初始 H1 的 ARP 表为空。
- 交换机 S 的学习表为空。
- H1 使用域名访问 Web 服务器。
- H2 在此过程中不主动发送无关帧。
- 问首次 HTTP 请求到达交换机之前发生什么。

### 10.2 第一问：DNS 的封装过程

访问网站使用域名：

```text
www.abc.com
```

因此需要 DNS。

经典 DNS 查询通常采用 UDP。

封装：

```text
DNS报文
   ↓
UDP用户数据报
   ↓
IP数据报
   ↓
以太网帧
```

写成：

$$
\boxed{ DNS\rightarrow UDP\rightarrow IP\rightarrow Ethernet }
$$

这是非常标准的 408 简答题答案。

注意 ARP 虽然也可能发生，但它不属于题目所问的应用层协议。

### 10.3 第二问：交换机如何自学习？

交换机自学习的核心规则：

根据收到帧的源 MAC 地址和入端口建立表项。

例如：

```text
H1 → 交换机端口4
```

交换机收到 H1 的帧：

```text
源MAC = H1的MAC
入端口 = 4
```

于是建立：

```text
H1_MAC → 4
```

接着：

```text
DNS服务器 → 交换机端口1
```

交换机学习：

```text
DNS_MAC → 1
```

然后路由器发送相关应答：

```text
R_MAC → 2
```

因此原题得到三条表项：

| MAC 地址              | 端口 |
| ------------------- | -- |
| `00-11-22-33-44-BB` | S1 |
| `00-11-22-33-44-AA` | S2 |
| `00-11-22-33-44-CC` | S4 |

为什么没有 H2？

因为交换机不能通过“某个主机收到广播帧”就学习到该主机 MAC。

必须收到以该 MAC 为源地址的帧，才能进行相应的源地址学习。

### 10.4 第三问：H2 至少收到几个广播帧？

答案：2 个。

为什么？

第一阶段，H1 需要查询本地 DNS。

如果本地 DNS 在同一个子网，并且 H1 没有其 MAC 缓存：

```text
H1 ──ARP广播──> 查询本地DNS的MAC
```

第二阶段，H1 要访问 Internet 上的 Web 服务器。

需要向默认网关发送数据：

```text
H1 ──ARP广播──> 查询默认网关的MAC
```

因此至少发生两次 ARP 广播。

同一广播域中的 H2 会接收到这两次广播。

两个请求帧的目的 MAC 均为：

```text
FF-FF-FF-FF-FF-FF
```

注意这里有一个容易忽略的条件：

如果 DNS 服务器位于远程子网，主机访问 DNS 和 Web 服务器可能使用同一个默认网关 MAC，ARP 次数就可能不同。

因此不能无条件背诵“访问一次网站必定发送两个 ARP 请求”。

要看本地 DNS 的实际网络位置和 ARP 缓存状态。

## 十一、2027 模拟综合题：DNS + HTTP 三种模式

章节练习中的王道冲刺八套卷中，第 6 套第 47 题是一道非常适合系统掌握本章的综合计算题。

### 11.1 题目条件

某用户点击 URL：

- 本地没有目标域名 IP 的缓存。
- 需要依次查询 $n$ 台 DNS 服务器。
- 每次 DNS 查询耗时 $RTT$。
- 主机到 Web 服务器的往返时延为 $RTT_w$。
- TCP 建立连接需要 1 个 $RTT_w$。
- 忽略对象实际发送时延。
- 采用明文 HTTP，不计 TLS。
- 不使用并行 TCP 连接。

要求计算：

1. 只获取一个小图片。
2. HTML + 3 个嵌入对象，采用非持久 HTTP。
3. HTML + 3 个嵌入对象，采用持久非流水线。
4. HTML + 3 个嵌入对象，采用持久流水线。

### 11.2 第一问：只获取一个小图片

DNS：

$$
T_{\mathrm{DNS}}=nRTT
$$

TCP：

$$
T_{\mathrm{TCP}}=RTT_w
$$

HTTP：

$$
T_{\mathrm{HTTP}}=RTT_w
$$

所以：

$$
\boxed{T_1=nRTT+2RTT_w}
$$

### 11.3 第二问：非持久 HTTP

HTML + 3 个对象：

$$
N=4
$$

每个对象重新建立 TCP 连接：

$$
T_{\mathrm{HTTP}}=4\times2RTT_w
$$

因此：

$$
\boxed{ T_{\mathrm{NP}}=nRTT+8RTT_w }
$$

### 11.4 第三问：持久非流水线

只建立一次 TCP 连接：

$$
1RTT_w
$$

获取 HTML：

$$
1RTT_w
$$

获取三个对象：

$$
3RTT_w
$$

因此：

$$
\boxed{ T_{\mathrm{P,nonpipe}} = nRTT+5RTT_w }
$$

### 11.5 第四问：持久流水线

TCP 建连：

$$
1RTT_w
$$

HTML 请求与响应：

$$
1RTT_w
$$

获取 HTML 后，流水线请求三个对象：

$$
1RTT_w
$$

所以：

$$
\boxed{ T_{\mathrm{P,pipe}} = nRTT+3RTT_w }
$$

### 11.6 四种情况对比

| 场景           | 总时间               |
| ------------ | ----------------- |
| 单个小对象        | $nRTT+2RTT_w$ |
| 4 个对象，非持久串行  | $nRTT+8RTT_w$ |
| 4 个对象，持久非流水线 | $nRTT+5RTT_w$ |
| 4 个对象，持久流水线  | $nRTT+3RTT_w$ |

这道题非常值得反复练习。

因为它覆盖了本章计算题最核心的三件事：

DNS 查询、TCP 建连、HTTP 对象请求。

## 十二、模拟选择题中的高频陷阱

以下整理模拟选择题中的常见陷阱。

### 12.1 DNS 缓存与传输层

模拟题：

下列关于 DNS 的说法，正确的是：

A. 即使已经知道目标 IP，也必须查询 DNS。

B. DNS 缓存可以减少查询流量。

C. DNS 只使用 TCP。

D. 权威服务器无法回答时一定返回普通查询失败。

答案：B。

分析：

DNS 不是每次 IP 通信的必经步骤。

普通 DNS 查询通常使用 UDP，也可以使用 TCP。

DNS 缓存能够减少重复解析。

### 12.2 全递归查询次数

模拟题：

所有 DNS 服务器均采用递归查询，本地 DNS 向外部发送查询的最少和最多次数是多少？

答案：0 次、1 次。

最少：

缓存命中。

最多：

按照题目设定的经典全递归模型，向下一服务器发出一次递归请求。

与 2016 年的迭代查询题形成对比。

### 12.3 FTP 的数据表示方式

模拟题：

FTP 是否允许客户端指定数据的类型和格式？

允许。

ASCII 模式和二进制模式就是典型例子。

因此“FTP 不允许指定文件传输表示类型”的说法错误。

### 12.4 HTTP 的端口

模拟题：

HTTP 客户端和服务器是否都默认使用 TCP 80 端口？

不是。

HTTP 服务器通常监听 80。

客户端一般使用临时源端口。

例如：

```text
客户端：
192.0.2.10:53124

服务器：
203.0.113.20:80
```

### 12.5 HTTP 是否有状态？

模拟题：

HTTP 是有状态协议吗？

不是。

但网站可以通过 Cookie、Session 等实现状态管理。

### 12.6 HTTP/1.1 非流水线

模拟题：

HTML 大小 1 MSS，包含 4 张图片，每张 0.5 MSS。

采用持久非流水线 HTTP/1.1，从 TCP 连接请求开始计时，按照题目简化模型求 RTT 总数。

答案：6 RTT。

计算：

$$
T=1RTT+1RTT+4RTT
$$

$$
\boxed{T=6RTT}
$$

其中：

- 握手：1 RTT。
- HTML：1 RTT。
- 四张图片：4 RTT。

这题与 2024 真题很容易混淆。

2024 真题是非持久 HTTP/1.0。

本题是持久非流水线 HTTP/1.1。

连接方式不同，公式也不同。

#### 强化题 1：DNS + HTTP + 并行

某浏览器访问一个网页。

条件：

- DNS 需要串行完成 3 次查询。

求总访问时间。

<Accordions>

$$
T=30+40+80
$$

$$
\boxed{T=150\text{ ms}}
$$

#### 强化题 3：完整 Web 访问与 ARP

假设：

```text

本地DNS：192.168.1.53/24
默认网关：192.168.1.1
Web服务器：203.0.113.20
```

初始：

- DNS 缓存为空。
- ARP 缓存为空。
- Web 服务器 IP 未知。
- 使用普通 UDP DNS 查询。
- 使用 HTTP/1.1。

问从开始访问域名到第一次 HTTP 请求发出，可能发生哪些主要步骤？

<Accordions>

<Accordion title="展开参考答案与详细计算">

解：

第一步：

主机需要查询 DNS 服务器。

本地 DNS 与 H 位于同一个子网。

先广播 ARP，获取 DNS 服务器 MAC。

第二步：

向 DNS 服务器发送查询：

```text

```

第三步：

向 Web 服务器发起 TCP 三次握手。

第七步：

建立连接后发送 HTTP 请求。

```text

        ↓
DNS查询
        ↓

        ↓

        ↓
TCP三次握手
        ↓
HTTP请求
```

## 十四、最容易混淆的 20 个考点

| 易错说法                 | 正确理解                  |
| -------------------- | --------------------- |
| C/S 中服务器不能主动发送数据     | 服务器可以发送响应，TCP 是全双工的   |
| P2P 一定没有服务器          | 可以有辅助服务器              |
| DNS 每次都要访问根服务器       | 先检查缓存                 |
| DNS 只使用 UDP          | 也可以使用 TCP             |
| DNS 查询一定是递归的         | 可采用递归或迭代              |
| 域名有几个层次就一定查询几次       | 还取决于委派结构与缓存           |
| 本地 DNS 是根与顶级域之间的一层   | 本地递归解析器不属于固定权威层级      |
| FTP 全部使用 TCP 21      | 21 用于控制连接             |
| FTP 主动模式是客户端主动建立数据连接 | 传统主动模式由服务器建立数据连接      |
| FTP 被动模式使用固定服务器端口 20 | 通常使用协商出的数据端口          |
| FTP 只有两条 TCP 连接      | 一条控制连接可配合多条数据连接       |
| SMTP 用来下载邮件          | SMTP 主要发送与转发          |
| POP3 一定删除服务器邮件       | 是否保留取决于使用方式和配置        |
| MIME 是传输协议           | MIME 主要扩展内容表示         |
| HTTP 有状态             | HTTP 协议语义本身无状态        |
| HTTP 无状态意味着不能登录      | 可用 Cookie、Session 等机制 |
| HTTP/1.1 一定使用非持久连接   | 默认使用持久连接              |
| 持久连接就是流水线            | 持久连接不意味着流水线           |
| 一个网页只有一个 HTTP 请求     | 嵌入资源通常还需要额外请求         |
| 使用 HTTP 就一定需要 TCP    | HTTP/3 基于 QUIC/UDP    |

其中最后一条要结合考试口径。

如果题目明确考 HTTP/1.0、HTTP/1.1 或 HTTP/2，按 TCP 分析。

如果明确考 HTTP/3，则应考虑 QUIC/UDP。

## 十五、本章所有重要计算公式

### 15.1 DNS 串行查询

$$
\boxed{ T_{\mathrm{DNS}} = \sum_{i=1}^{k}RTT_i }
$$

### 15.2 经典 HTTP 单对象

$$
\boxed{ T_{\mathrm{HTTP}} \approx2RTT+T_{\mathrm{tx}} }
$$

前提是从 TCP 建连开始计时。

### 15.3 非持久 HTTP 顺序获取对象

$$
\boxed{ T=2(n+1)RTT }
$$

这里 $n$ 是嵌入对象数，不包括 HTML 本身。

### 15.4 持久 HTTP 非流水线

$$
\boxed{ T=(n+2)RTT }
$$

### 15.5 持久 HTTP 理想流水线

$$
\boxed{ T\approx3RTT }
$$

### 15.6 非持久 HTTP 并行

$$
\boxed{ T= \left( 2+2\left\lceil\frac{n}{m}\right\rceil \right)RTT }
$$

其中 $m$ 是最多并行连接数。

### 15.7 DNS 与 HTTP 联合

$$
\boxed{ T_{\mathrm{total}} = T_{\mathrm{DNS}} + T_{\mathrm{TCP/HTTP}} + T_{\mathrm{other}} }
$$

其中 $T_{\mathrm{other}}$ 可以包含题目没有忽略的对象发送、排队、处理、TLS 握手等时间。

如果某些阶段可以并行完成，不能把它们全部机械相加。

## 十六、408 考场标准解题方法

### 16.1 DNS 题五步法

1. 看缓存是否命中。
2. 看采用递归还是迭代。
3. 看题目问的是哪个服务器发出的查询。
4. 画出实际查询过程。
5. 根据真实发生的查询次数或 RTT 计算。

### 16.2 FTP 题五步法

1. 确认 FTP 使用 TCP。
2. 确认控制连接服务器端口 21。
3. 判断主动还是被动模式。
4. 看谁发起数据连接。
5. 区分累计连接数量与同时存在的连接数量。

### 16.3 邮件题五步法

1. 判断谁向谁发送数据。
2. 发送与转发选 SMTP。
3. 下载选 POP3。
4. 服务器端同步管理选 IMAP。
5. 内容表示、附件问题选 MIME。

### 16.4 HTTP 计算六步法

第一步：确定计时起点。

从 DNS 查询开始、TCP 建连开始，还是 HTTP 请求已经发出？

第二步：判断 DNS 是否需要时间。

是否已经解析完成？

第三步：判断 TCP 是否已经建立。

若已建立，就不重复加握手 RTT。

第四步：统计对象数量。

一个 HTML 引用 $n$ 个图片，通常意味着：

$$
N=n+1
$$

个对象。

第五步：判断 HTTP 连接方式。

非持久、持久非流水线、流水线，还是并行 TCP？

第六步：画时间线并相加。

不要直接根据对象数量猜答案。
