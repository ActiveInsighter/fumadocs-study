### 高频边界与易错条件

<Callout type="warn" title="RTT 速算公式只适用于题目给定的理想 HTTP/1.x 模型">

- 经典 HTTP 习题通常**假定每个对象的传输与处理时延可忽略**、无丢包、无缓存命中、已知目标 IP 且每次 TCP 握手耗 1 RTT。
- 若一个 HTML 文档含 $n$ 张图片，非持续**串行**连接常需 $2(n+1)$ RTT；持续非流水线常需 $(n+2)$ RTT；持续流水线的理想上限模型为 3 RTT（均从建连前起计）。
- DNS 时延、TLS 握手、拥塞窗口限制、服务端处理、对象大小、并行连接数及 HTTP/2、HTTP/3 多路复用均会改变结果。**不能把 HTTP/1.x 的课堂公式直接套到所有现代网页。**

</Callout>

### 核心公式与概念对照

<Tabs items={["DNS 查询", "FTP 连接", "HTTP 理想 RTT", "Web 访问链"]} defaultIndex={0}>

<Tab value="DNS 查询">

本地 DNS 若已缓存某一级委派或最终记录，应跳过相应查询；区分“**主机发给本地 DNS 一次请求**”和“**本地 DNS 再向外部 DNS 发送多少次查询**”。TTL 是记录可缓存时长，不是网络层的 IP TTL。

</Tab>

<Tab value="FTP 连接">

典型 FTP 一条持久**控制 TCP 连接**，再为目录列表或文件传输建立相应**数据连接**。累计连接条数与某时刻同时存在的连接条数不同；主动 FTP 服务器通常用 TCP 20 作数据连接的源端口，被动 FTP 服务端通常选择监听的非固定数据端口。

</Tab>

<Tab value="HTTP 理想 RTT">

设 $n$ 个独立图片、初始无 TCP 连接，并忽略传输、排队、处理、TLS 与 DNS 等耗时：

$$
\begin{aligned}
T_{\mathrm{nonpersistent,serial}}&=2(n+1)\,RTT,\\
T_{\mathrm{persistent,serial}}&=(n+2)\,RTT,\\
T_{\mathrm{persistent,pipelined}}&\approx3\,RTT.
\end{aligned}
$$

上述最后一式要求理想流水线响应在一个额外 RTT 阶段完成；若题目从**已建立连接后**开始计时，还要减去建连 RTT。

</Tab>

<Tab value="Web 访问链">

常见教学情形：配置网络参数 → DNS 解析 → 确定下一跳并 ARP → TCP 建连 →（HTTPS 时）TLS 握手 → HTTP 请求 / 响应 → 解析 HTML 并获取对象。真实浏览器也可能复用 DNS/TCP/TLS 连接、命中缓存或使用 QUIC（HTTP/3），需要按题设判断。

</Tab>

</Tabs>

## 二、6.1 网络应用模型

### 2.1 客户/服务器模型 C/S

C/S（Client/Server）的核心思想是：

客户端主动请求服务，服务器通常长期运行并等待请求。

典型过程：

```text
客户端 Client                  服务器 Server
      │                              │
      │────── 建立连接/发送请求 ─────→│
      │                              │
      │←──────── 返回服务结果 ───────│
      │                              │
```

#### 基本特点

客户端通常需要知道服务器的 IP 地址或域名，以及服务器的服务端口。

服务器并不需要提前知道所有客户端的 IP 地址。客户端发起连接后，服务器即可获得对方的连接信息。

C/S 模型的优点是集中管理方便，身份验证和权限控制相对容易实现。

缺点是服务器容易成为瓶颈，并可能形成单点故障。

典型应用包括 HTTP、FTP、DNS 和电子邮件服务。

#### 高频陷阱

客户端主动建立连接，不代表服务器在连接建立后不能发送数据。

例如 TCP 是全双工协议：

- 客户端可以发送数据；
- 服务器也可以发送数据；
- 双方可以同时传输数据。

但要区分 TCP 的双向传输能力和 HTTP 请求/响应的应用规则。经典 HTTP/1.1 服务器通常仍按请求返回响应，而不是任意发送未请求的 HTTP 对象。

### 2.2 P2P 模型

P2P（Peer-to-Peer，对等模型）的核心是：

每个对等节点既可以请求资源，也可以提供资源。

例如一个文件被分散在许多节点上：

```text
       节点 A
       ↗   ↘
    节点 B──节点 C
       ↖   ↙
       节点 D
```

节点 B 下载资源的同时，也可以将自己已经下载的部分上传给节点 C。

#### C/S 与 P2P 对比

| 比较   | C/S         | P2P            |
| ---- | ----------- | -------------- |
| 节点角色 | 客户端、服务器相对明确 | 对等节点可同时请求和提供服务 |
| 资源位置 | 较集中         | 分布式            |
| 管理方式 | 集中管理        | 分散管理           |
| 扩展性  | 依赖服务器能力     | 新节点也可能贡献资源     |
| 安全管理 | 通常较容易集中实施   | 节点动态变化，管理更复杂   |
| 典型应用 | Web、FTP     | BitTorrent     |

P2P 不等于完全不存在服务器。有些 P2P 系统仍依靠中心服务器协调节点发现、身份验证或资源索引。

### 2.3 真题：2019 年网络应用模型

题目： 下列叙述中，错误的是：

A. P2P 模型中结点之间具有对等关系。

B. C/S 模型中客户与客户之间可以直接通信。

C. C/S 模型中主动发起通信的是客户。

D. 向大量用户分发文件时，P2P 通常比 C/S 更快。

答案：B。

逐项理解：

A 正确。P2P 节点地位对等。

B 错误。在典型 C/S 应用模型中，客户主要与服务器通信。两个客户的业务交互通常需要服务器参与。

C 正确。客户端一般主动向服务器请求服务。

D 正确。P2P 的优势在于各节点能够共享上传带宽，不再完全依赖单台中心服务器。

#### 进一步理解：为什么 P2P 分发可能更快？

假设一个大小为 $F$ 的文件，需要分发给 $N$ 个用户。

服务器上传速率为 $u_s$，最慢客户端下载速率为 $d_{\min}$。

在纯 C/S 模型中，服务器需要向所有用户提供数据，因此分发时间至少满足：

$$
D_{\mathrm{CS}}\geq \max\left\{ \frac{NF}{u_s}, \frac{F}{d_{\min}} \right\}
$$

其中 $\frac{NF}{u_s}$ 反映服务器总上传量的限制。

在理想 P2P 模型中，如果所有节点贡献上传速率 $u_i$，则：

$$
D_{\mathrm{P2P}}\geq \max\left\{ \frac{F}{u_s}, \frac{F}{d_{\min}}, \frac{NF}{u_s+\sum_{i=1}^{N}u_i} \right\}
$$

这是一种理论下界，不是所有 P2P 系统都能达到。

理解这一点即可解释：用户数量增加时，P2P 系统可能同时获得更多上传能力。

## 三、6.2 DNS 域名系统——第一个重点

DNS（Domain Name System）是一个分布式、层次化的命名系统。

其最经典的功能是：

$$
\text{域名}\longrightarrow\text{IP 地址}
$$

例如：

```text
www.example.com
       ↓ DNS
93.184.215.14（示意地址）
```

DNS 使用户不必记住大量 IP 地址。

但 DNS 不只是一个域名与 IP 的简单映射表，还涉及层次结构、域名服务器、缓存以及分布式查询过程。

### 3.1 DNS 的基本属性

| 项目    | 内容            |
| ----- | ------------- |
| 所属层次  | 应用层           |
| 组织形式  | 分布式、层次化       |
| 普通查询  | 通常使用 UDP      |
| 服务器端口 | 53            |
| 特殊情况  | 可使用 TCP       |
| 加速手段  | 缓存            |
| 核心题型  | 递归、迭代、查询次数与时延 |

普通 DNS 查询一般使用 UDP，因为报文通常较小，避免了额外的 TCP 连接建立过程。

不过 DNS 也支持 TCP，例如区域传送，或者需要通过 TCP 获取较大响应等情形。

因此：

- “DNS 通常使用 UDP”正确。
- “DNS 只能使用 UDP”错误。

### 3.2 层次域名空间

以：

`www.abc.xyz.com`

为例，从右向左看：

```text
                根域 .
                   │
                  com
                   │
                 xyz
                   │
                 abc
                   │
                 www
```

最右边的 `com` 是顶级域。

域名中的各标签体现分级命名关系。

常见顶级域包括：

- 国家或地区顶级域，例如 `.cn`、`.uk`；
- 通用顶级域，例如 `.com`、`.org`、`.edu`；
- 基础结构顶级域，例如 `.arpa`。

DNS 使用层次化管理，可以避免所有域名信息集中保存在一个服务器中。

### 3.3 四种 DNS 服务器

这是必考内容。

| 服务器     | 作用               |
| ------- | ---------------- |
| 根域名服务器  | 指出相关顶级域服务器       |
| 顶级域名服务器 | 指出相关域的权威服务器      |
| 权威域名服务器 | 保存并回答负责区域的权威记录   |
| 本地域名服务器 | 接收主机查询，进行递归解析和缓存 |

#### 根服务器

根服务器位于 DNS 权威层次的顶部。

当本地 DNS 查询 `www.example.com` 时，根服务器通常不会直接给出最终 IP，而是提供 `.com` 顶级域服务器的信息。

需要注意，全球常说的 13 个根服务器，是 13 个逻辑标识，并不代表世界只有 13 台物理服务器。

#### 顶级域服务器

负责顶级域相应的委派信息。

例如：

```text
根 DNS
   ↓
.com DNS
   ↓
example.com 权威 DNS
```

#### 权威域名服务器

负责特定 DNS 区域中的权威资源记录。

假设某权威服务器负责 `example.com`，它可以为所属区域中的相关记录提供权威回答。

#### 本地域名服务器

主机一般先把 DNS 请求发送给配置的本地递归解析器。

本地 DNS 会：

1. 查询缓存；
2. 缓存未命中时，继续执行 DNS 解析；
3. 获取结果；
4. 将结果返回主机；
5. 按 TTL 缓存结果。

本地域名服务器并不是 DNS 权威层次树中固定的一级。

它是客户端一侧的查询服务角色。

### 3.4 DNS 资源记录

DNS 能处理很多种记录：

| 记录类型  | 含义           |
| ----- | ------------ |
| A     | 域名对应 IPv4 地址 |
| AAAA  | 域名对应 IPv6 地址 |
| NS    | 指定权威域名服务器    |
| CNAME | 域名别名映射       |
| MX    | 邮件交换服务器      |
| PTR   | 反向地址解析       |
| TXT   | 文本信息         |

考研重点掌握前五种即可，尤其是 A、NS、MX。

例如发送电子邮件时，邮件服务器可以查询收件人域名的 MX 记录，寻找负责接收该域邮件的服务器。

**DNS 查询‘次数’与 DNS 的 RTT 不必相等**

  计算 DNS 查询次数先弄清统计主体是主机、本地递归解析器还是全链路的全部 DNS 交互；再依据缓存命中、迭代/递归、是否并行进行计数。DNS 常用 UDP 53，但也可使用 TCP 53，另有加密的 DoT/DoH 等部署方式。

### 3.5 递归查询与迭代查询——最核心的概念

这部分一定不能只背定义。

真正的区别是：

收到查询请求的 DNS 服务器，是否要替查询者继续完成后续查询。

#### 递归查询

递归查询可以理解为：

“我只问你，后面的事情你负责。”

例如：

```text
主机 → 本地 DNS → 根 DNS
                      ↓
                    TLD DNS
                      ↓
                   权威 DNS
```

在严格逐级递归的教学模型中：

- 主机向本地 DNS 发一次请求；
- 本地 DNS 向下一台服务器发一次请求；
- 后续服务器继续向下请求；
- 结果逐级返回。

因此，本地 DNS 不需要自己向所有服务器分别发请求。

#### 迭代查询

迭代查询可以理解为：

“你不知道最终答案，就告诉我下一步应该问谁。”

例如：

```text
             根 DNS
            ↗     ↘ 返回 .com 信息
本地 DNS ────────────
            ↘     ↗
             .com DNS
            ↗     ↘ 返回权威 DNS 信息
本地 DNS ────────────
            ↘     ↗
            权威 DNS
            ↗     ↘ 返回最终 IP
本地 DNS ────────────
```

在这个过程中，本地 DNS 需要分别访问：

根服务器、顶级域服务器和权威服务器。

#### 一张表彻底区分

| 项目        | 递归查询      | 迭代查询           |
| --------- | --------- | -------------- |
| 后续查询者     | 被查询服务器    | 当前查询者          |
| 返回内容      | 最终答案或失败   | 最终答案或下一服务器信息   |
| 当前查询者请求数量 | 通常较少      | 可能多次           |
| 408 典型场景  | 主机到本地 DNS | 本地 DNS 到其他 DNS |

经典 DNS 工作方式经常是：

主机到本地 DNS 使用递归查询；本地 DNS 到根、TLD、权威 DNS 使用迭代查询。

### 3.6 真题：2010 年 DNS 递归查询次数

题目：

本地域名服务器没有缓存，采用递归方法解析另一网络的主机域名。

用户主机、本地域名服务器发送的 DNS 请求消息数分别为多少？

A. 1、1

B. 1、多条

C. 多条、1

D. 多条、多条

答案：A。

解析：

用户主机只向本地 DNS 发送一次请求。

本地 DNS 再向下一台 DNS 服务器发送一次递归请求。

后续 DNS 服务器负责继续查询。

因此：

$$
N_{\mathrm{主机}}=1
$$

$$
N_{\mathrm{本地DNS}}=1
$$

这道题最容易错在将“整个 DNS 系统发出的请求数”误认为“本地 DNS 自己发出的请求数”。

题目问谁，就只统计谁。

### 3.7 真题：2016 年 DNS 最少与最多查询次数

题目：

所有 DNS 服务器均采用迭代查询。

某主机访问：

`www.abc.xyz.com`

本地域名服务器完成解析过程中，可能发送 DNS 查询的最少和最多次数是多少？

A. 1、3

B. 0、3

C. 0、4

D. 1、4

答案：C。

#### 最少次数

如果本地 DNS 缓存中已有该域名的有效结果，就不需要向其他 DNS 服务器发查询。

因此：

$$
N_{\min}=0
$$

#### 最多次数

在题目允许的完整四级查询情况下：

```text
第 1 次：根 DNS
第 2 次：com 顶级 DNS
第 3 次：xyz.com DNS
第 4 次：abc.xyz.com 权威 DNS
```

因此：

$$
N_{\max}=4
$$

所以答案为：

$$
\boxed{(0,4)}
$$

#### 这道题真正考什么？

不是考背诵“四次”。

而是考：

1. 是否存在有效缓存；
2. 是递归还是迭代；
3. 查询对象有多少级；
4. 是哪一台服务器发送请求。

现实中的 DNS 委派层次不一定严格等于域名标签数量。真题中要依据给定服务器结构和缓存条件统计。

### 3.8 模拟题：全部采用递归查询

你的模拟题中有一道：

所有域名服务器采用递归查询，解析 `www.aaa.bbb.com`，本地域名服务器最少和最多需要发送几次查询？

答案：0 次、1 次。

有缓存：

$$
N_{\min}=0
$$

没有缓存，本地 DNS 将递归请求交给下一台服务器：

$$
N_{\max}=1
$$

这与 2016 年迭代查询真题构成非常重要的一组对比。

| 条件         | 本地 DNS 查询次数 |
| ---------- | ----------- |
| 缓存直接命中     | 0           |
| 无缓存，完全递归模型 | 1           |
| 无缓存，迭代模型   | 根据实际层数确定    |

### 3.9 DNS 缓存与 TTL

TTL（Time To Live）表示缓存记录剩余的有效时间。

例如一条 DNS 记录的 TTL 为：

$$
TTL=3600\text{ s}
$$

缓存记录还未过期时，DNS 解析器可以直接使用有效结果。

缓存的意义包括：

- 减少 DNS 查询次数；
- 缩短解析时间；
- 降低根服务器和权威服务器负载；
- 减少网络流量。

#### 延伸考法：中间委派信息被缓存

假设本地 DNS 已缓存 `.com` 服务器信息，但没有 `www.example.com` 的最终记录。

此时不必重新查询根服务器。

它可以直接从已知的 `.com` 服务器继续解析。

因此 DNS 缓存不只是“完全命中或者完全未命中”，还可能只缓存了某些中间层级的信息。

这一点特别适合出查询次数的变化题。

## 四、6.3 FTP 文件传输协议

FTP（File Transfer Protocol）基于 TCP，采用 C/S 模型。

最重要的性质是：

FTP 将控制信息与文件数据放在不同的 TCP 连接中传输。

### 4.1 控制连接和数据连接

```text
FTP 客户端                        FTP 服务器
    │                                 │
    │══════ TCP 控制连接 ═════════════│ 21端口
    │                                 │
    │──── 用户名、口令、命令 ─────────→│
    │←──── 状态响应 ─────────────────│
    │                                 │
    │══════ TCP 数据连接 ═════════════│
    │                                 │
    │←──── 文件或目录信息 ────────────│
    │                                 │
```

#### 控制连接

控制连接负责：

- 用户登录；
- 身份验证；
- 目录操作；
- 文件传输命令；
- 服务器状态响应。

它通常贯穿整个 FTP 会话。

服务器端口：

$$
21
$$

#### 数据连接

数据连接负责：

- 文件内容；
- 目录列表；
- 其他需要独立传输的数据。

典型 FTP 工作方式中，每完成一次数据传输，相应的数据连接通常关闭。

因此一次 FTP 会话可以包含：

$$
1\text{ 条控制连接}+n\text{ 条数据连接}
$$

这里 $n$ 是实际建立的数据连接数量。

**FTP 的 20/21 端口要分模式讨论**

  FTP 控制连接的服务器端口通常为 TCP 21。经典主动模式的数据连接通常由服务器 TCP 20 发起；被动模式由客户端连接服务器公告的数据端口，不应把所有 FTP 数据连接都视为固定使用服务器 20 端口。

### 4.2 主动模式与被动模式

#### 主动模式（PORT）

主动模式是服务器主动发起数据连接。

```text
客户端 ───控制连接───→ 服务器:21

客户端:临时端口 ←──数据连接── 服务器:20
```

典型过程：

1. 客户端连接服务器 TCP 21；
2. 客户端告诉服务器自己的数据端口；
3. 服务器主动连接客户端的数据端口；
4. 建立数据连接后传输文件。

传统主动模式中，服务器数据连接通常使用 TCP 20 端口。

#### 被动模式（PASV）

被动模式是客户端主动建立数据连接。

```text
客户端 ───控制连接───→ 服务器:21

客户端 ───数据连接───→ 服务器:协商端口
```

典型过程：

1. 客户端建立控制连接；
2. 客户端发送 PASV 请求；
3. 服务器告知开放的数据端口；
4. 客户端主动连接该端口；
5. 传输数据。

#### 对比表

| 项目        | 主动模式          | 被动模式               |
| --------- | ------------- | ------------------ |
| 控制连接发起者   | 客户端           | 客户端                |
| 控制连接目的端口  | 服务器 21        | 服务器 21             |
| 数据连接发起者   | 服务器           | 客户端                |
| 传统服务器数据端口 | 20            | 动态协商端口             |
| 防火墙适应性    | 客户端可能需要允许入站连接 | 通常更便于客户端通过 NAT/防火墙 |

FTP 的主动与被动只针对数据连接，不针对控制连接。

### 4.3 真题：2009 年 FTP

FTP 客户端与服务器之间传递 FTP 命令时使用什么连接？

A. TCP 控制连接

B. TCP 数据连接

C. UDP 数据连接

D. UDP 控制连接

答案：A。

FTP 命令通过 TCP 控制连接传递。

文件内容通过 TCP 数据连接传递。

### 4.4 真题：2017 年 FTP 端口陷阱

下面哪个说法错误？

A. 数据连接通常在一次数据传输结束后关闭。

B. 控制连接在整个会话期间保持。

C. 服务器与客户端的 TCP 20 端口建立数据连接。

D. 客户端连接服务器的 TCP 21 端口建立控制连接。

答案：C。

这里的错误在于把 TCP 20 端口理解成客户端的固定数据端口。

传统主动模式下，20 是服务器一侧通常使用的数据端口。

客户端对应的是协商出的端口。

被动模式下服务器数据端口也不必是 20。

因此不能说 FTP 的数据连接必然使用固定的两个 20 端口。

### 4.5 FTP 连接数量计算

假设一次 FTP 会话中，用户执行：

```text
连接 FTP 服务器
      ↓
登录
      ↓
获取一次目录列表
      ↓
下载文件 A
      ↓
下载文件 B
      ↓
退出
```

若每次数据操作分别建立一条数据连接，则：

控制连接：

$$
1
$$

目录列表：

$$
1
$$

下载两个文件：

$$
2
$$

总共建立：

$$
N=1+1+2=\boxed{4}
$$

条 TCP 连接。

#### 注意题目问法

“某时刻同时存在几条连接”和“整个会话一共建立几条连接”不同。

例如顺序下载两个文件：

- 控制连接持续存在；
- 文件 A 的数据连接关闭后；
- 再建立文件 B 的数据连接。

典型情况下，某一时刻同时存在 2 条连接，但整个会话累计建立过 3 条。

## 五、6.4 电子邮件系统

电子邮件系统主要包括用户代理、邮件服务器和邮件协议。

这一节最容易考协议对应关系。

### 5.1 一封邮件的完整传输流程

```text
用户 A
  │
  │ 编写邮件
  ▼
用户代理 UA
  │
  │ SMTP
  ▼
A 的邮件服务器
  │
  │ SMTP
  ▼
B 的邮件服务器
  │
  │ POP3 / IMAP
  ▼
B 的用户代理
  │
  ▼
用户 B 阅读邮件
```

核心口诀：

SMTP 负责发送和转发；POP3、IMAP 负责邮件访问。

**电子邮件协议要区分‘投递’与‘访问’**

  典型教学中 SMTP 在服务器之间负责邮件传输，POP3/IMAP 用于收取或同步邮件；现代客户端提交邮件也常使用 SMTP Submission（例如 587）或隐式 TLS 端口（例如 465）。端口问题以题目指明的服务和场景为准。

### 5.2 SMTP

SMTP（Simple Mail Transfer Protocol）用于发送、提交和转发邮件。

经典 408 口径：

| 项目           | 特点        |
| ------------ | --------- |
| 传输层          | TCP       |
| 服务器间邮件传输常用端口 | 25        |
| 应用行为         | Push，推送   |
| 主要功能         | 发送和转发电子邮件 |

用户代理可通过 SMTP 将邮件提交给发送方邮件服务器。

邮件服务器之间也通过 SMTP 转发邮件。

现实中邮件客户端提交邮件还广泛使用 587 或 465 端口，408 传统协议辨析题主要记住 TCP 25。

#### SMTP 三个阶段

SMTP 经典工作过程可以分成：

1. 建立连接；
2. 邮件传送；
3. 连接释放。

传送过程中常见命令有：

```text
HELO / EHLO
MAIL FROM
RCPT TO
DATA
QUIT
```

例如：

```text
MAIL FROM:<a@example.com>
RCPT TO:<b@example.net>
DATA

Hello!

.
QUIT
```

`MAIL FROM` 指定信封发件人，`RCPT TO` 指定信封收件人。

`DATA` 后面开始传输邮件内容。

经典 SMTP 中，用单独一行的句点结束 DATA 内容。

### 5.3 SMTP 的 ASCII 限制

这是历年真题考过的知识点。

传统 SMTP 主要面向 7 位 ASCII 文本。

因此 ASCII 文本可以直接传输。

对于图片、视频、二进制附件，需要通过 MIME 等机制处理内容表示和编码。

现代 SMTP 存在 8BITMIME 等扩展，但 408 传统试题考的是经典 SMTP 模型。

#### MIME

MIME（Multipurpose Internet Mail Extensions）是多用途互联网邮件扩展。

它主要负责描述和编码：

- 不同语言与字符集；
- 图片；
- 音频；
- 视频；
- 附件；
- 多部分邮件。

它不是取代 SMTP 的新传输协议。

可以理解成：

```text
SMTP：负责把邮件送过去

MIME：负责让邮件能够表示复杂内容
```

例如附件可能通过 Base64 编码，使二进制数据可以用文本形式表示。

### 5.4 POP3

POP3（Post Office Protocol Version 3）用于客户端从邮件服务器下载邮件。

| 项目    | 内容   |
| ----- | ---- |
| 传输层   | TCP  |
| 服务器端口 | 110  |
| 应用行为  | Pull |
| 主要功能  | 下载邮件 |

POP3 传统上偏向本地下载和管理。

但 POP3 并不是一定删除服务器上的邮件。客户端可根据配置保留服务器副本。

### 5.5 IMAP

IMAP（Internet Message Access Protocol）用于在线访问和管理邮箱。

默认 TCP 143 端口。

与 POP3 相比，它更强调服务器端邮件状态管理。

例如：

- 已读状态；
- 未读状态；
- 邮件文件夹；
- 删除标记；
- 多设备同步。

#### POP3 与 IMAP 对比

| 项目          | POP3  | IMAP      |
| ----------- | ----- | --------- |
| 核心用途        | 下载邮件  | 在线访问和同步邮箱 |
| 默认 TCP 端口   | 110   | 143       |
| 管理重心        | 更偏客户端 | 更偏服务器     |
| 多设备同步       | 相对有限  | 更完善       |
| 是否一定删除服务器邮件 | 否     | 否         |

### 5.6 Webmail 是一个重要陷阱

假设用户 A 使用浏览器登录某网页邮箱，然后给 B 发邮件。

浏览器访问网页邮箱时，使用的主要协议是：

HTTP/HTTPS。

但邮件系统内部仍可能使用 SMTP。

如果 B 使用传统邮件客户端收取邮件，则可以使用 POP3 或 IMAP。

因此：

```text
A 浏览器 ──HTTPS──→ 网页邮箱服务器

发送服务器 ──SMTP──→ 接收服务器

B 客户端 ──IMAP/POP3──→ 接收服务器
```

不能看到“电子邮件”就认为每段通信都使用 SMTP。

### 5.7 真题：2012 年电子邮件协议

题目给出：

发送方用户代理 → 发送方邮件服务器 → 接收方邮件服务器 → 接收方用户代理。

问三个阶段分别使用什么应用层协议。

答案：SMTP、SMTP、POP3。

原因：

第一段是提交邮件。

第二段是服务器之间转发邮件。

第三段是收件人读取邮件。

因此：

$$
\boxed{\text{SMTP}\rightarrow\text{SMTP}\rightarrow\text{POP3}}
$$

第三段也可以使用 IMAP，但真题给出的可选组合是 POP3。

### 5.8 真题：2013 年 SMTP

题目判断：

I. 传统 SMTP 直接支持 7 位 ASCII 内容。

II. SMTP 支持邮件服务器之间传送邮件。

III. SMTP 支持用户代理向邮件服务器发送邮件。

IV. SMTP 支持邮件服务器向用户代理发送邮件，作为收信协议。

答案：I、II、III。

IV 错误，因为客户端读取邮箱主要使用 POP3 或 IMAP。

### 5.9 真题：2015 年 POP3

使用 POP3 接收邮件，运输层提供什么服务？

答案：有连接、可靠传输。

因为 POP3 使用 TCP。

### 5.10 真题：2018 年 SMTP

传统 SMTP 不进行内容转换就能直接传输什么？

A. JPEG 图像

B. MPEG 视频

C. EXE 文件

D. ASCII 文本

答案：D。

#### 电子邮件专题总结

记住四组关系即可解决大部分选择题：

$$
\begin{aligned} \text{SMTP}&:\text{发送、转发}\\ \text{POP3}&:\text{下载邮件}\\ \text{IMAP}&:\text{在线同步}\\ \text{MIME}&:\text{内容表示与编码} \end{aligned}
$$

## 六、6.5 万维网 WWW 与 HTTP——第二个重点

WWW（World Wide Web）通过超链接组织大量 Web 资源。

必须区分：

| 概念      | 作用                  |
| ------- | ------------------- |
| URL     | 标识资源位置和访问方式         |
| HTTP    | 定义 Web 请求、响应和资源传输语义 |
| HTML    | 描述网页内容及结构           |
| 浏览器     | Web 客户端             |
| Web 服务器 | 提供 Web 资源           |
| DNS     | 解析域名                |
| TCP     | 为经典 HTTP 提供可靠传输     |

### 6.1 URL 的结构

例如：

`https://www.example.com:443/docs/index.html`

可以分解为：

```text
https://
   │
   ├── 协议方案：https
   │
www.example.com
   │
   ├── 主机名
   │
:443
   │
   ├── 端口
   │
/docs/index.html
   │
   └── 资源路径
```

如果没有显式指定端口：

- HTTP 默认使用 80；
- HTTPS 默认使用 443。

### 6.2 HTTP 的请求与响应

经典 HTTP 通信遵循请求/响应模式。

```text
浏览器                           Web服务器
   │                                 │
   │──────── HTTP Request ─────────→│
   │                                 │
   │←─────── HTTP Response ─────────│
   │                                 │
```

HTTP 定义应用层请求与响应的规则。

TCP 负责可靠传输、序号、重传、流量控制和拥塞控制等。

### 6.3 HTTP 请求报文

HTTP/1.1 请求报文典型结构：

```text
请求行
请求首部
空行
可选消息体
```

例如：

```text
GET /index.html HTTP/1.1
Host: www.example.com
Connection: keep-alive
User-Agent: ExampleBrowser
Cookie: session=abc123
```

#### 请求行

`GET /index.html HTTP/1.1`

包括：

- 方法：GET；
- 请求目标：`/index.html`；
- 协议版本：HTTP/1.1。

#### Host

`Host: www.example.com`

表示客户端请求的服务器主机名。

它不是客户端自己的主机名。

#### Connection

`Connection: keep-alive`

表示希望保持连接。

`Connection: close`

表示连接在当前请求/响应完成后关闭。

#### Cookie

`Cookie: session=abc123`

表示浏览器向服务器发送已经保存的 Cookie 数据。

### 6.4 HTTP 常见方法

| 方法     | 作用               |
| ------ | ---------------- |
| GET    | 获取资源             |
| POST   | 提交数据供服务器处理       |
| HEAD   | 获取响应首部，通常不获取响应主体 |
| PUT    | 创建或替换目标资源        |
| DELETE | 删除目标资源           |

注意：

POST 不等于只能上传文件，也不保证幂等。

GET 通常用于读取资源，HEAD 可以用来检查资源元数据。

### 6.5 HTTP 响应报文

HTTP/1.1 响应报文典型结构：

```text
状态行
响应首部
空行
可选消息体
```

例如：

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1250
Connection: keep-alive

<html>
...
</html>
```

#### 常见状态码

| 状态码 | 含义          |
| --- | ----------- |
| 200 | 请求成功        |
| 201 | 已创建资源       |
| 301 | 永久重定向       |
| 302 | 临时重定向       |
| 304 | 资源未修改，可复用缓存 |
| 400 | 请求格式错误      |
| 401 | 需要认证        |
| 403 | 拒绝访问        |
| 404 | 资源不存在       |
| 500 | 服务器内部错误     |
| 503 | 服务暂时不可用     |

状态码类别：

$$
\begin{aligned} 1xx&:\text{信息性响应}\\ 2xx&:\text{成功}\\ 3xx&:\text{重定向}\\ 4xx&:\text{客户端侧请求问题}\\ 5xx&:\text{服务器侧错误} \end{aligned}
$$

**HTTP 无状态不等于网站无法维持会话**

  无状态描述协议请求本身不自动保留应用上下文。服务端 Session、Cookie、Token 等机制可以建立登录状态；HTTP/1.1 持久 TCP 连接和应用会话状态也不是同一个概念。

### 6.6 HTTP 无状态

HTTP 是无状态协议。

其含义是：

HTTP 协议本身不要求服务器自动记住此前某个客户端的应用状态。

例如：

```text
GET /login
GET /profile
```

仅凭 HTTP 请求/响应机制，服务器不能自动推断第二个请求一定来自刚刚登录的用户。

但网站可以通过 Cookie、Session 或 Token 维持登录状态。

所以：

“HTTP 无状态”正确。

“HTTP 网站不能保存登录状态”错误。

#### Cookie 与 Session

典型过程：

```text
用户登录
   ↓
服务器创建会话状态
   ↓
服务器响应 Set-Cookie
   ↓
浏览器保存 Cookie
   ↓
后续请求携带 Cookie
   ↓
服务器识别会话
```

Cookie 通常由浏览器保存、携带。

Session 通常指服务器端维护的会话状态。

Cookie 本质上是数据，不是浏览器执行的程序。

### 6.7 Web 缓存

Web 缓存用于保存近期访问的 Web 对象。

缓存命中时，可以减少到源服务器的请求。

DNS 缓存和 Web 缓存的区别：

| 项目   | DNS 缓存    | Web 缓存    |
| ---- | --------- | --------- |
| 保存内容 | 域名解析记录    | Web 对象或响应 |
| 作用阶段 | 域名解析      | HTTP 资源访问 |
| 主要目的 | 减少 DNS 查询 | 减少资源重复传输  |

HTTP 还可通过条件请求验证缓存。

例如：

`If-Modified-Since` 或 `If-None-Match`。

若服务器认为缓存仍有效，可返回 `304 Not Modified`，避免重新传输完整资源内容。

### 6.8 真题：2015 年 HTTP 请求首部

题目给出：

```text
GET /index.html HTTP/1.1
Host: www.test.edu.cn
Connection: Close
Cookie: 123456
```

问哪项错误。

其中一项说：

“该浏览器请求使用持续连接。”

答案：该项错误。

因为：

`Connection: Close`

明确要求连接在完成本次请求/响应后关闭。

即使 HTTP/1.1 默认使用持续连接，也要服从题目中明确给出的连接控制信息。

另外，Cookie 字段表明浏览器携带了该站点的 Cookie 信息，但不能因此绝对认定用户一定已经通过身份验证。

## 七、HTTP 持续连接、流水线和并行连接

这是 HTTP 计算题的核心基础。

一定要区分三个概念：

1. 是否使用持续连接；
2. 是否支持流水线；
3. 是否允许并行建立多条 TCP 连接。

它们不是一回事。

### 7.1 非持续连接

非持续连接是：

通常每个 HTTP 对象使用一条单独的 TCP 连接。

```text
建立 TCP
请求 HTML
收到 HTML
关闭连接

建立新 TCP
请求图片 1
收到图片 1
关闭连接
```

HTTP/1.0 在传统 408 题中默认按非持续连接处理。

### 7.2 持续连接

持续连接允许多个 HTTP 对象复用同一条 TCP 连接。

```text
建立一次 TCP
      ↓
请求 HTML
      ↓
请求图片 1
      ↓
请求图片 2
      ↓
请求图片 3
      ↓
关闭 TCP
```

HTTP/1.1 默认支持持续连接。

持续连接最重要的好处是避免反复建立 TCP 连接。

### 7.3 持续非流水线

持续非流水线是：

发送一个 HTTP 请求后，必须等对应响应回来，才能发送下一个请求。

```text
请求 HTML → 收到 HTML
请求图片1 → 收到图片1
请求图片2 → 收到图片2
```

虽然 TCP 连接只有一条，但 HTTP 请求仍然需要依次等待。

**教学中的 HTTP/1.1 流水线 ≠ HTTP/2 多路复用**

  HTTP/1.1 流水线在同一连接按序发送多个请求，但响应通常仍需遵循请求顺序；HTTP/2 多路复用可以交错传输不同流。HTTP/3 还改用 QUIC 作为传输基础。408 经典 RTT 公式通常指简化的 HTTP/1.x，而非现代浏览器的真实加载时间。

### 7.4 持续流水线

持续流水线允许：

不等待前一个响应完成，就继续在同一条连接上发送后续请求。

例如：

```text
请求图片 1 ─────→
请求图片 2 ─────→
请求图片 3 ─────→

         ←───── 响应图片 1
         ←───── 响应图片 2
         ←───── 响应图片 3
```

经典 HTTP/1.1 流水线仍受到响应顺序的限制。

HTTP/2 则支持流的多路复用，可以缓解 HTTP/1.1 的应用层队头阻塞。

但 HTTP/2 通常运行在 TCP 上，因此 TCP 丢包仍可能导致多个流同时受影响。

HTTP/3 基于 QUIC，可以避免不同 QUIC 流因同一 TCP 字节流缺失而共同阻塞的问题。

### 7.5 并行 TCP 连接

并行连接是同时建立多条 TCP 连接。

例如：

```text
TCP 连接 1 → 图片 A
TCP 连接 2 → 图片 B
TCP 连接 3 → 图片 C
TCP 连接 4 → 图片 D
```

与流水线的区别是：

- 流水线：一条 TCP 连接上连续发多个请求；
- 并行连接：多条 TCP 连接同时工作。

这些区别直接决定 HTTP RTT 计算方法。

## 八、HTTP RTT 时延计算——全章最重要的计算题

这一部分要掌握到可以不看公式，自己画时间线推导。

### 8.1 RTT 是什么？

RTT（Round-Trip Time）表示从发送请求或探测消息到收到对应响应所经历的往返时间。

注意：

RTT 不等于单程传播时延。

假设单程传播时延为 $5\,\mathrm{ms}$，处理和发送时延忽略，那么：

$$
RTT=10\,\mathrm{ms}
$$

408 HTTP 简化题常使用：

- TCP 建立连接：约 1 RTT；
- HTTP 请求并收到一个很小的对象：约 1 RTT。

因此，一个非持续 HTTP 对象通常约需：

$$
\boxed{2RTT}
$$

但这是在没有提前建立 TCP 连接、忽略其他时延的条件下成立。

### 8.2 为什么一个对象是 2 RTT？

```text
客户端                         服务器
   │                               │
   │──────── SYN ─────────────────→│
   │                               │
   │←────── SYN+ACK ───────────────│
   │                               │
   │──────── ACK ─────────────────→│
   │
   │     约 1 RTT 完成 TCP 建连
   │
   │──────── HTTP GET ────────────→│
   │                               │
   │←────── HTTP Response ─────────│
   │
   │     约 1 RTT 完成请求/响应
```

所以：

$$
T_{\mathrm{object}} \approx 2RTT
$$

如果对象较大，则需要考虑传输时间：

$$
T\approx2RTT+T_{\mathrm{tx}}
$$

其中：

$$
T_{\mathrm{tx}}=\frac{L}{R}
$$

$L$ 是数据长度（bit），$R$ 是发送速率（bit/s）。

实际多分组传输还可能受到 TCP 拥塞窗口、流量控制、丢包和其他瓶颈影响。

**每个对象 2 RTT 并非通用定理**

  “建立一次 TCP 连接耗 1 RTT，再发 GET 并收到很小的对象耗 1 RTT”成立于理想忽略对象发送、处理、排队、TLS 的模型。若已有 TCP 连接、可以在握手阶段传数据、使用 TLS、缓存或对象跨多次 RTT 发送，需重新画时间轴。

### 8.3 统一模型：HTML + $n$ 个图片

假设：

- 基础 HTML 为 1 个对象；
- HTML 引用了 $n$ 张图片；
- 图片 URL 必须等 HTML 收到后才知道；
- 所有对象来自同一服务器；
- RTT 相同；
- 忽略数据发送和处理时延；
- 从建立 TCP 连接前开始计时。

因此共有：

$$
N_{\mathrm{objects}}=n+1
$$

个对象。

#### 情况一：非持续连接，完全串行

每个对象：

$$
2RTT
$$

总共：

$$
n+1
$$

个对象。

所以：

$$
\boxed{T=2(n+1)RTT}
$$

#### 情况二：持续连接，非流水线

只建立一次 TCP：

$$
1RTT
$$

获取 HTML：

$$
1RTT
$$

然后逐个请求 $n$ 张图片：

$$
nRTT
$$

所以：

$$
\boxed{T=(n+2)RTT}
$$

#### 情况三：持续连接，流水线

建立 TCP：

$$
1RTT
$$

获取 HTML：

$$
1RTT
$$

收到 HTML 后，通过流水线请求所有已知图片：

$$
1RTT
$$

因此在经典理想模型中：

$$
\boxed{T=3RTT}
$$

注意，这个结论忽略了响应数据发送、排队等额外时延，并且要求这些对象可以在一个流水线阶段完成。

### 8.4 三种 HTTP 模式公式汇总

| HTTP 模式 | 计时条件              | 总 RTT        |
| ------- | ----------------- | ------------ |
| 非持续、串行  | 从 TCP 建连前开始       | $2(n+1)$ |
| 持续、非流水线 | 从 TCP 建连前开始       | $n+2$    |
| 持续、流水线  | 从 TCP 建连前开始，理想小对象 | $3$      |

其中 $n$ 是 HTML 引用的额外对象数，不包括基础 HTML。

公式最容易出错的地方是计时起点。

如果 TCP 已经建立，则持续连接情形要减少 1 RTT。

如果题目已经发出了 HTTP 请求，则还不能把 TCP 建连重新加一遍。

### 8.5 真题：2024 年 HTTP/1.0 RTT

题目：

浏览器不支持并行 TCP 连接。

使用非持续 HTTP/1.0 请求一个网页，网页中引用了 7 张小图片。

从建立第一个 TCP 连接开始，到全部对象接收完毕，需要多少 RTT？

选项：

A. 4

B. 9

C. 14

D. 16

答案：D。

分析：

基础 HTML：

$$
1
$$

张图片：

$$
7
$$

对象总数：

$$
N=1+7=8
$$

每个对象需要：

$$
2RTT
$$

因此：

$$
T=8\times2RTT
$$

$$
\boxed{T=16RTT}
$$

#### 为什么不是 14？

因为容易漏掉基础 HTML 文件。

#### 为什么不是 9？

9 RTT 对应“一次 TCP 建连 + 8 次独立请求/响应”的持续非流水线模型，而不是本题的非持续连接。

### 8.6 模拟题：持续非流水线 HTTP

原稿列举的资料库中有一道模拟题：

HTML 大小为 1 MSS，引用 4 张图片。

每张图片大小为 0.5 MSS。

采用 HTTP/1.1 持续非流水线方式。

从 TCP 建连开始计算，忽略额外传输时延。

需要多少 RTT？

分析：

建立 TCP：

$$
1RTT
$$

HTML：

$$
1RTT
$$

4 张图片：

$$
4RTT
$$

总时间：

$$
T=(1+1+4)RTT
$$

$$
\boxed{T=6RTT}
$$

答案：6 RTT。

这里的 MSS 信息并不意味着每个图片都必须额外消耗一个 RTT。

题目采用简化请求/响应模型，且文件较小，因而按对象的顺序请求进行计算。

### 8.7 并行非持续连接

这是对 2024 年真题的常见变式。

假设 HTML 引用 10 张图片。

浏览器允许最多同时建立 5 条 TCP 连接。

HTTP 为非持续连接。

忽略传输时间。

#### 第一步：基础 HTML

由于还不知道图片 URL，先独立获取 HTML。

需要：

$$
2RTT
$$

#### 第二步：图片分批并行

10 张图片，一批最多 5 张。

批次数：

$$
k=\left\lceil\frac{10}{5}\right\rceil=2
$$

每批的 5 条 TCP 连接同时建立。

每批耗时：

$$
2RTT
$$

两批：

$$
4RTT
$$

总时间：

$$
T=2RTT+4RTT
$$

$$
\boxed{T=6RTT}
$$

#### 一般公式

最多并行 $m$ 条非持续 TCP 连接，HTML 引用 $n$ 个对象时：

$$
\boxed{ T=\left(2+2\left\lceil\frac{n}{m}\right\rceil\right)RTT }
$$

这个公式同样要求：

- 忽略对象传输时间；
- 每批连接可以并行建立；
- HTML 必须先接收完；
- 不考虑其他连接数限制。

## 九、DNS + HTTP 综合时延

这一类题将应用层的 DNS 与 HTTP 组合起来，是高频考法。

### 9.1 真题：2020 年 DNS + TCP + HTTP

题目概要：

主机访问：

`http://www.abc.com/index.html`

相关 Internet 服务器 RTT 均为：

$$
RTT=10\,\mathrm{ms}
$$

本地 DNS 向主机提供递归解析服务。

其他 DNS 服务器采用迭代查询。

忽略题目指定的其他时延。

问点击超链接到接收完整纯文本网页，最短与最长耗时。

选项：

A. 10ms、40ms

B. 10ms、50ms

C. 20ms、40ms

D. 20ms、50ms

答案：D。

#### 最短时间

若本地 DNS 已缓存目标 IP，则不需要向 Internet 中的 DNS 服务器查询。

接下来：

建立 TCP：

$$
1RTT
$$

发送 HTTP 请求并收到网页：

$$
1RTT
$$

因此：

$$
T_{\min}=2RTT
$$

代入：

$$
T_{\min}=2\times10=20\,\mathrm{ms}
$$

#### 最长时间

假设缓存未命中。

本地 DNS 依次向：

```text
根域名服务器
      ↓
com 顶级域名服务器
      ↓
abc.com 权威域名服务器
```

进行 3 次迭代查询。

DNS 耗时：

$$
T_{\mathrm{DNS}}=3RTT
$$

TCP 建连：

$$
T_{\mathrm{TCP}}=1RTT
$$

HTTP 请求：

$$
T_{\mathrm{HTTP}}=1RTT
$$

因此：

$$
T_{\max}=(3+1+1)RTT
$$

$$
T_{\max}=5\times10=50\,\mathrm{ms}
$$

最终：

$$
\boxed{ T_{\min}=20\,\mathrm{ms}, \quad T_{\max}=50\,\mathrm{ms} }
$$

#### 特别注意

这里没有额外计算主机到本地 DNS 的 RTT，因为题目对相关局域网时延采用了忽略处理。

如果题目另外给出主机与本地 DNS 的查询 RTT，就必须根据计时范围将其算进去。

#### 统一解题方法

$$
\boxed{ T_{\mathrm{total}} = T_{\mathrm{DNS}} + T_{\mathrm{TCP}} + T_{\mathrm{HTTP}} + T_{\mathrm{其他}} }
$$

重点是只加真正需要串行等待的阶段。

## 十、HTTP 与 TCP 慢开始——难度较高的综合题

这是应用层和传输层联合命题的代表。

### 10.1 真题：2022 年 HTTP + TCP 拥塞窗口

题目概要：

主机 H 通过 HTTP/1.1 请求一个 HTML 页面。

HTML 文件大小为：

$$
1MSS
$$

HTML 引用一张图片，图片大小为：

$$
3MSS
$$

已完成 DNS 解析。

$$
RTT=10\,\mathrm{ms}
$$

忽略题设中的传输及首部开销。

从开始请求建立 TCP 连接，到全部数据接收完成，至少需要多长时间？

选项：

A. 30ms

B. 40ms

C. 50ms

D. 60ms

答案：B，40ms。

#### 第一阶段：建立 TCP

三次握手在经典模型下约需：

$$
1RTT
$$

为取得最短时间，可将 HTTP GET 请求携带在第三次握手报文段中。

#### 第二阶段：传输 HTML

设初始拥塞窗口为：

$$
cwnd=1MSS
$$

HTML 只有：

$$
1MSS
$$

因此可以发送 HTML。

收到相应确认后，按照题设的慢开始模型：

$$
cwnd:1\rightarrow2MSS
$$

这部分占一个 RTT 轮次。

#### 第三阶段：传输图片前 2 MSS

图片共有：

$$
3MSS
$$

当前拥塞窗口：

$$
2MSS
$$

所以先发送：

$$
2MSS
$$

收到确认后：

$$
cwnd:2\rightarrow4MSS
$$

#### 第四阶段：传输剩余图片

图片剩余：

$$
3MSS-2MSS=1MSS
$$

再发送剩余 1 MSS。

按照真题采用的 RTT 轮次计数：

$$
T=4RTT
$$

$$
T=4\times10=40\,\mathrm{ms}
$$

因此：

$$
\boxed{40\,\mathrm{ms}}
$$

#### 本题真正的难点

不是文件一共有 4 MSS 就机械地认为需要 4 RTT。

它同时考查：

- HTTP/1.1 持续连接；
- TCP 第三次握手可携带数据；
- HTML 收到后才知道图片地址；
- TCP 初始拥塞窗口；
- 慢开始导致拥塞窗口增长；
- 分阶段发送数据。

这里采用的是题目给定的理想化慢开始和 RTT 计数模型。实际传输时间还会受到 ACK 到达时刻、接收窗口和发送策略等因素影响。

### 10.2 慢开始的一般计算

假设初始拥塞窗口为：

$$
wMSS
$$

慢开始阶段按轮次翻倍：

$$
w,\ 2w,\ 4w,\ 8w,\ldots
$$

前 $r$ 轮总共可以发送：

$$
S_r=w(1+2+\cdots+2^{r-1})
$$

即：

$$
S_r=w(2^r-1)
$$

若需要发送 $K$ 个 MSS，则满足：

$$
w(2^r-1)\geq K
$$

因此理想情况下：

$$
\boxed{ r= \left\lceil \log_2\left(\frac{K}{w}+1\right) \right\rceil }
$$

这里 $r$ 是满足数据量要求的最少发送轮数，不等于任何实际连接的完整耗时。

如果中间存在必须等待 HTML 解析、HTTP 请求、TCP ACK 等阶段，必须把这些依赖纳入时间线。

## 十一、2011 年综合大题：HTTP + ARP + IP + NAT

这是全章非常重要的跨层真题。

题目给出：

- 主机 MAC 地址；
- 主机私有 IPv4 地址；
- 网络拓扑；
- 一段以太网帧的十六进制内容；
- HTTP/1.1 传输方式。

要求求出：

1. Web 服务器 IP；
2. 默认网关 MAC；
3. ARP 工作过程；
4. 获取网页所需 RTT；
5. 路由器转发时需要修改的 IP 首部字段。

### 11.1 如何分析十六进制以太网帧？

典型以太网 II 帧：

```text
目的 MAC       6B
源 MAC         6B
类型字段       2B
数据载荷       ...
```

题中可分析的开头内容为：

```text
00 21 27 21 51 EE
00 15 C5 C1 5E 28
08 00
```

前 6 字节：

```text
00-21-27-21-51-EE
```

是目的 MAC。

接下来 6 字节：

```text
00-15-C5-C1-5E-28
```

是源 MAC。

类型字段：

```text
08 00
```

表示上层数据为 IPv4。

#### 为什么帧的目的 MAC 是网关？

因为 Web 服务器在远端 Internet 上。

主机发出 IP 分组时：

```text
IP 目的地址：远端 Web 服务器 IP

以太网目的 MAC：当前链路的下一跳 MAC
```

当目标不在同一个子网中时，下一跳通常是默认网关。

这就是网络层与数据链路层的重要区别：

IP 地址指向最终目标，MAC 地址负责当前这一跳。

### 11.2 从 IPv4 首部提取目的地址

题目中的目的 IP 字节为：

```text
40 AA 62 20
```

转成十进制：

$$
40_{16}=64
$$

$$
AA_{16}=170
$$

$$
62_{16}=98
$$

$$
20_{16}=32
$$

所以：

$$
\boxed{\mathrm{IP}=64.170.98.32}
$$

默认网关 MAC 地址为：

`00-21-27-21-51-EE`

### 11.3 ARP 如何获得目的 MAC？

假设主机已知道默认网关 IP，但不知道默认网关 MAC。

主机会广播 ARP 请求。

ARP 请求所在以太网帧的目的 MAC 地址为：

`FF-FF-FF-FF-FF-FF`

即广播 MAC 地址。

默认网关收到请求后，通常发送单播 ARP 应答。

主机由此建立 IP 与 MAC 的对应关系。

#### 注意

ARP 解决的是：

$$
\text{下一跳 IPv4 地址}\rightarrow\text{下一跳 MAC 地址}
$$

不是通过 ARP 去互联网直接查找远端 Web 服务器的 MAC。

### 11.4 HTTP 时延计算

题目规定：

- HTTP/1.1 持续连接；
- 非流水线；
- 页面包含基础 HTML 和 5 张 JPEG；
- 从发出题图 HTTP 请求开始计时；
- 忽略其他时延。

基础 HTML：

$$
1RTT
$$

5 张 JPEG：

$$
5RTT
$$

所以：

$$
T=1RTT+5RTT
$$

$$
\boxed{T=6RTT}
$$

这里不能再额外加 TCP 建连的 1 RTT。

因为计时起点已经是 HTTP 请求发出时。

这就是本题最重要的陷阱。

### 11.5 NAT 与路由器转发

题中主机的私有地址为：

`10.2.128.100`

路由器进行源地址转换后使用公网地址：

`101.12.123.15`

因此需要修改 IPv4 首部中的：

源 IP 地址、TTL、首部校验和。

原因：

源 IP：

```text
10.2.128.100
      ↓ NAT
101.12.123.15
```

TTL：

$$
TTL_{\mathrm{out}}=TTL_{\mathrm{in}}-1
$$

IPv4 首部内容发生变化后，需要重新计算首部校验和。

如果 NAT 同时转换 TCP/UDP 端口，还需要更新有关的运输层字段和校验和，但本题重点是 IPv4 首部。

普通路由器转发也会重新封装下一段链路的二层帧。

## 十二、2021 年综合大题：DNS + ARP + 交换机自学习

这道题非常值得研究。

它把“打开浏览器访问网页”拆成应用层、传输层、网络层、数据链路层的连续过程。

### 12.1 题目条件

网络中有：

- H1；
- H2；
- 本地 DNS 服务器；
- 交换机 S；
- 路由器 R；
- Internet 上的 Web 服务器。

H1 通过域名：

`www.abc.com`

访问 Web 服务器。

初始时：

- H1 的 ARP 表为空；
- 交换机 S 的交换表为空；
- 网络中没有其他无关通信。

问：

1. H1 除 HTTP 外还运行什么应用层协议？
2. DNS 如何逐层封装？
3. 交换机学到了哪些 MAC 表项？
4. H2 至少收到几个相关以太网帧？

### 12.2 第一问：使用 DNS

H1 使用的是域名，而不是已经解析好的 IP。

因此需要 DNS。

在题目的经典 UDP 查询情形下：

```text
DNS 应用层报文
      ↓
UDP 用户数据报
      ↓
IP 数据报
      ↓
以太网帧
```

所以：

$$
\boxed{ DNS\rightarrow UDP\rightarrow IP\rightarrow Ethernet }
$$

注意 DNS 是应用层协议，ARP 用于局域网中的地址解析，不属于这里要回答的其他应用层协议。

### 12.3 第二问：交换机自学习

交换机的工作规则：

根据收到帧的源 MAC 地址和入端口学习交换表。

不是根据目的 MAC 学习。

题目中的 MAC 和端口如下：

| 设备     | MAC 地址            | 交换机端口 |
| ------ | ----------------- | ----- |
| H1     | 00-11-22-33-44-CC | 4     |
| 本地 DNS | 00-11-22-33-44-BB | 1     |
| 路由器 R  | 00-11-22-33-44-AA | 2     |

因此到题设时刻，交换机至少已经学习到上述三个表项。

为什么没有 H2？

因为 H2 没有主动发送以它自身 MAC 为源地址的帧。

交换机向 H2 转发广播帧，不等于交换机能够学习 H2 的 MAC 地址。

### 12.4 第三问：H2 为什么会收到两个广播帧？

原题中 H1 和本地域名服务器位于同一子网。

H1 的 ARP 缓存为空。

第一次 ARP：

H1 要先知道本地 DNS 服务器的 MAC。

因此广播 ARP 请求。

第二次 ARP：

H1 获得 Web 服务器 IP 后，发现目标在远端网络，需要经过默认网关。

但 H1 还不知道网关 MAC。

因此再次广播 ARP 请求。

所以 H2 至少接收到：

$$
\boxed{2}
$$

个与此次访问有关的广播帧。

它们的目的 MAC 均为：

`FF-FF-FF-FF-FF-FF`

这一结论也能在独立的 2021 年真题整理中得到验证。

[image](https://www.google.com/s2/favicons?domain=https://csgraduates.com\&sz=32)

计算机考研杂货铺

+1

#### 一个值得注意的资料细节

原稿引用的 Fumadocs 分类真题中，有一处 2021 年解析把第二次 ARP 的发起过程描述得不够准确。

结合题目实际拓扑，正确的最小广播过程是：

H1 先解析同网段 DNS 的 MAC，再解析默认网关的 MAC。

按这个过程理解更严谨。

## 十三、网页访问全过程：408 跨层综合题的统一模型

这是本章最重要的一条主线。

假设一台刚接入网络的主机打开浏览器，输入：

`https://www.example.com`

在没有相关缓存且使用传统 HTTPS/TCP 的情况下，可以按下面的过程推演。

### 阶段 1：获取网络参数

如果主机尚未配置 IP 地址，可能使用 DHCP。

典型 DHCP 过程是：

```text
DISCOVER
   ↓
OFFER
   ↓
REQUEST
   ↓
ACK
```

DHCP 通常使用 UDP：

- 服务器端口 67；
- 客户端端口 68。

但注意，不是每次浏览网页都需要执行 DHCP。

如果主机已经有有效网络配置，则不必重新进行这一步。

**网页跨层分析先问本地是否已有缓存**

  浏览器、系统解析器、本地 DNS 可能缓存结果；ARP 表、交换机 MAC 表和 TCP/TLS 会话也可能已有状态。是否必须产生 DNS/ARP 请求、是否需要 TCP/TLS 建连应服从题设，不能默认每次打开页面都执行全链路流程。

### 阶段 2：DNS 解析

浏览器需要获得域名对应的 IP 地址。

先检查相关缓存。

未命中时向本地 DNS 查询。

本地 DNS 可能继续查询根、顶级域和权威服务器。

获得最终 IP 后，DNS 阶段结束。

### 阶段 3：判断目标是否在同一子网

主机根据目的 IP、子网掩码和路由信息判断下一跳。

同一子网：

直接发送给目标主机。

不同子网：

通常交给默认网关。

### 阶段 4：ARP

如果不知道下一跳的 MAC 地址，就需要 ARP。

ARP 请求广播。

ARP 响应通常单播。

得到下一跳 MAC 后，主机可以构造以太网帧。

### 阶段 5：TCP 建立连接

传统 HTTPS 通信需要建立 TCP 连接。

```text
SYN
 ↓
SYN+ACK
 ↓
ACK
```

经典模型下约占一个 RTT。

### 阶段 6：TLS

如果使用 HTTPS，还需要根据具体 TLS 版本完成相关握手。

HTTP/1.x 或 HTTP/2 over TLS 的真实访问耗时，可能包含 TLS 握手过程。

408 题若明确“忽略 SSL/TLS 握手”，或者只考普通 HTTP，就不应自行添加额外的 TLS RTT。

### 阶段 7：HTTP 请求

浏览器发送 HTTP 请求。

服务器返回 HTML。

### 阶段 8：浏览器解析 HTML

浏览器发现 HTML 中引用了图片、CSS、JavaScript 等资源。

随后请求这些对象。

如果资源来自其他域名，还可能产生新的 DNS 查询与连接。

### 阶段 9：交换机与路由器工作

整个过程中：

交换机：

- 根据源 MAC 自学习；
- 根据目的 MAC 转发；
- 广播、未知单播等可能触发洪泛。

路由器：

- 根据目标 IP 查找路由；
- TTL 减 1；
- 更新 IPv4 首部校验和；
- 重新进行下一跳链路层封装。

NAT 网关在配置并命中转换规则时，还可能修改 IP 地址与端口。

#### 最终形成的知识链

```text
用户输入 URL
      ↓
DNS 域名解析
      ↓
获得 Web 服务器 IP
      ↓
查询路由，确定下一跳
      ↓
ARP 获取下一跳 MAC
      ↓
TCP 三次握手
      ↓
TLS 握手（HTTPS 情况）
      ↓
HTTP 请求基础 HTML
      ↓
服务器返回 HTML
      ↓
浏览器解析 HTML
      ↓
请求图片、CSS、JS 等对象
      ↓
TCP 可靠传输、流量控制、拥塞控制
      ↓
Web 页面加载
```

这条流程能将计算机网络前五章的大量知识点与应用层统一起来。

## 十五、全章高频易错点总结

| 易错说法                   | 正确理解               |
| ---------------------- | ------------------ |
| P2P 完全没有服务器            | P2P 可以存在辅助服务器      |
| C/S 中服务器不能主动发送数据       | 建立连接后 TCP 可以双向传输   |
| DNS 每次都查询根服务器          | 先判断缓存是否命中          |
| DNS 只能使用 UDP           | DNS 也支持 TCP        |
| 主机直接查询根 DNS            | 典型情况下先查询本地 DNS     |
| 根服务器直接返回所有网站 IP        | 通常返回相关服务器的委派信息     |
| 递归与迭代是按查询层数区分          | 应看谁负责继续查询          |
| FTP 只有一条 TCP 连接        | 控制与数据连接分开          |
| FTP 所有数据连接都使用服务器 20    | 被动模式使用协商的数据端口      |
| FTP 主动模式是客户端主动发数据连接    | 主动模式由服务器主动发起数据连接   |
| SMTP 用于接收邮件            | SMTP 主要负责发送、提交和转发  |
| POP3 一定删除服务器邮件         | 可配置保留邮件副本          |
| MIME 是新的邮件传输协议         | MIME 负责内容表示与编码     |
| HTTP 本身有状态             | HTTP 本身无状态         |
| HTTP/1.1 默认非持续连接       | HTTP/1.1 默认持续连接    |
| 持续连接必然是流水线             | 持续、流水线是两个独立概念      |
| 流水线与并行 TCP 是同一回事       | 前者一条连接，后者多条连接      |
| HTTP 所有对象只需一次请求        | 通常每个独立对象需要相应请求     |
| HTTP 服务器和客户端都使用 80     | 80 通常是 HTTP 服务器端口  |
| 访问远端主机时 ARP 获取其 MAC    | ARP 获取本地链路下一跳的 MAC |
| 交换机从目的 MAC 学习表项        | 根据收到帧的源 MAC 和入端口学习 |
| 所有 HTTP 对象一律需要 2 RTT   | 取决于连接是否已建立、是否复用    |
| 计算网页耗时必须算 TCP 建连       | 取决于题目计时起点          |
| TCP 发送多少 MSS 就需要多少 RTT | 还要考虑拥塞窗口与传输轮次      |

### 第二梯队：熟练辨析

控制连接 TCP 21；数据连接独立建立；主动模式服务器发起数据连接，被动模式客户端发起数据连接。

电子邮件要能够马上说出：

SMTP 发送和转发；POP3 下载；IMAP 在线同步；MIME 处理复杂内容。

HTTP 基础要能够马上说出：

HTTP 本身无状态；HTTP/1.1 默认持续连接；GET、POST、Host、Cookie、Connection、状态码的含义。

### 第三梯队：进阶综合

进一步练习：

- DNS 部分缓存命中；
- 多台服务器采用不同 RTT；
- HTTP 并行连接分批；
- TCP 慢开始与对象传输；
- HTTPS 与 TLS 握手；
- DHCP、DNS、ARP、HTTP 混合过程；
- NAT 和交换机自学习；
- 以太网帧十六进制解析。

#### 本章最终结论

第 6 章虽然有很多协议、端口和概念需要记忆，但真正拉开分数差距的是能否把不同协议放到同一次网络通信中分析。

如果能做到以下三点，就基本具备了解决本章典型 408 题目的能力：

1. 准确识别协议及职责：DNS、FTP、SMTP、POP3、HTTP，以及下层 TCP、UDP、IP、ARP。
2. 自己推导通信过程与时间：DNS 查询次数、TCP 建连、HTTP 请求、对象传输、流水线、并行连接和慢开始。
