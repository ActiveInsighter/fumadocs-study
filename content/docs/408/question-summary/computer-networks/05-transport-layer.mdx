<Callout type="warn" title="TCP 计算题要同时维护三份账本">

1. **序号账本**：一个数据字节占 1 个序号，SYN 与 FIN 各占 1 个序号，纯 ACK 通常不占序号。
2. **窗口账本**：$\min(\mathrm{cwnd},\mathrm{rwnd})$ 是经典模型下的允许在途上界，**还能新发的数据**通常还需扣除已发未确认字节；真实实现还受发送缓冲、应用数据与其他限制。
3. **时间账本**：一个 RTT 对应一次请求传播与确认返回的往返时间；**收到第 8 个 ACK**不等于**经过第 8 个 RTT**。

</Callout>

<Tabs items={['ACK 与下一个序号','发送窗口','慢开始','超时与三次重复 ACK']} defaultIndex={0}>
<Tab value="ACK 与下一个序号">

连续收到的 TCP 字节序号到 $b$，且不存在未确认缺口时，下一个期望序号是 $b+1$。若中途缺少字节区间，累计 ACK 必须停留在**首个缺失字节**。

</Tab>
<Tab value="发送窗口">

在考试的经典窗口模型中：

$$
W=\min(\mathrm{rwnd},\mathrm{cwnd}),\qquad
W_{\mathrm{new}}=\max\{0, W-U\},
$$

其中 $U$ 为**当前已经发送且尚未确认的数据量**。序号起点、广告窗口更新时刻和实现细节均由题设决定。

</Tab>
<Tab value="慢开始">

按每收到一个合格的确认推动窗口增长、每 RTT 大致确认一个当前窗口数据量的经典简化模型：

$$
1,\ 2,\ 4,\ 8,\ldots \ (\mathrm{MSS}).
$$

这是理想无丢包、接收窗口不限制、无延迟 ACK 等假设下的**按 RTT 轮次近似模型**，不是所有现代 TCP 实现的统一算法。

</Tab>
<Tab value="超时与三次重复 ACK">

经典 Reno / 408 教材抽象模型中，超时通常重置拥塞窗口并进入慢开始；3 个重复 ACK 可触发快速重传，配合快恢复与新门限处理。新门限和更新时刻必须遵循题设的具体版本；不可把二者视为同一次事件。

</Tab>
</Tabs>

## 二、传输层基础：为什么需要传输层？

### 2.1 网络层与传输层的区别

先考虑一个场景。

你的电脑有一个 IP 地址：

`192.168.1.100`

此时同时运行浏览器、QQ、微信和游戏客户端。

当网络数据到达你的电脑时，IP 协议已经完成了任务：

把数据报送到 `192.168.1.100`。

但操作系统还不知道：

这个数据究竟属于哪个应用程序？

这就是传输层需要解决的问题。

| 层次    | 通信对象   | 地址     |
| ----- | ------ | ------ |
| 数据链路层 | 相邻节点   | MAC 地址 |
| 网络层   | 主机之间   | IP 地址  |
| 传输层   | 应用进程之间 | 端口号    |

因此：

- IP 地址主要用来定位主机。
- 端口号用来标识主机中的应用通信端点。
- IP 地址与端口号结合，可定位通信端点。

特别注意：端口号是传输层的概念，不是网络层的概念。

路由器根据网络层信息进行 IP 转发，不需要通过 TCP 目的端口号决定普通 IP 数据报的路由。

### 2.2 复用与分用

这是 408 经常考的小概念。

#### 发送方：复用

不同应用程序产生的数据，经过 TCP 或 UDP 封装后交给网络层。

```text
浏览器 ──┐
QQ    ──┼──> TCP/UDP ──> IP
游戏  ──┘
```

多个应用共享传输层协议服务。

这叫复用。

#### 接收方：分用

网络层把数据交给传输层后，传输层根据相关首部信息，将数据交给正确的套接字。

```text
IP ──> TCP/UDP
             │
             ├──> 浏览器
             ├──> QQ
             └──> 游戏
```

这叫分用。

其中：

- UDP 的常规分用主要依据目的 IP、目的端口及协议等信息定位 UDP 套接字。
- TCP 连接通过源 IP、源端口、目的 IP、目的端口构成的四元组来区分。

对于 2018 年真题，如果只问 UDP 首部的哪个字段用于分用，答案就是目的端口号。

### 2.3 端口号分类

TCP 和 UDP 的端口号均为 16 位。

因此：

$$
2^{16}=65536
$$

端口号范围：

$$
0\sim65535
$$

| 范围          | 名称      | 作用       |
| ----------- | ------- | -------- |
| 0～1023      | 熟知端口    | 常见网络服务   |
| 1024～49151  | 登记端口    | 已登记的应用服务 |
| 49152～65535 | 动态/私有端口 | 常用作临时端口  |

常见端口：

| 协议或服务    | 默认端口 | 传输层协议                   |
| -------- | ---- | ----------------------- |
| HTTP     | 80   | TCP                     |
| HTTPS    | 443  | TCP（传统 HTTP/1.1、HTTP/2） |
| FTP 控制连接 | 21   | TCP                     |
| SSH      | 22   | TCP                     |
| DNS      | 53   | UDP/TCP                 |
| DHCP 服务器 | 67   | UDP                     |
| DHCP 客户端 | 68   | UDP                     |
| SMTP     | 25   | TCP                     |
| POP3     | 110  | TCP                     |

注意：HTTP/3 使用 QUIC，运行在 UDP 之上，因此不能绝对地说 HTTPS 只能使用 TCP。

### 2.4 TCP 连接的四元组

TCP 连接由四元组唯一标识：

$$
\boxed{ (\text{源IP},\text{源端口},\text{目的IP},\text{目的端口}) }
$$

例如：

```text
客户端 A：
192.168.1.2:50001
       |
       v
服务器：
10.0.0.1:80
```

另一个客户端可以同时建立：

```text
客户端 B：
192.168.1.3:50001
       |
       v
服务器：
10.0.0.1:80
```

服务器使用的都是 80 端口，但源 IP 不同，因此是两个不同的 TCP 连接。

甚至同一客户端只要使用不同源端口，也可以与同一个服务器建立多个连接。

考研陷阱：一个端口号并不只能对应一条 TCP 连接。

### 模拟题：端口数量与连接数量

判断：

I. 一台主机上的 TCP 端口号种类不超过 65536。

II. 一台主机最多只能同时建立 65536 条 TCP 连接。

III. TCP 连接关闭后，端口号可再次使用。

IV. 一个服务器端口可以对应多个 TCP 连接。

正确组合：

$$
\boxed{\text{I、III、IV}}
$$

## 三、TCP 与 UDP 的根本区别

这是学习后续知识的基础。

| 对比         | UDP            | TCP                     |
| ---------- | -------------- | ----------------------- |
| 是否建立连接     | 无连接            | 面向连接                    |
| 数据传输形式     | 面向报文           | 面向字节流                   |
| 是否保证可靠     | 不保证            | 保证可靠、按序交付               |
| 是否提供确认和重传  | 不提供            | 提供                      |
| 是否提供流量控制   | 不提供            | 提供                      |
| 是否提供拥塞控制   | 不提供            | 提供                      |
| 首部最小长度     | 8B             | 20B                     |
| 是否保留应用消息边界 | 保留             | 不保留                     |
| 交付方式       | 保留数据报边界        | 连续字节流                   |
| 是否支持广播/多播  | 可以             | 不支持                     |
| 典型应用       | DNS、实时音视频、QUIC | HTTP/1.1、HTTP/2、SSH、FTP |

### 3.1 UDP 面向报文

假设应用层发送三个报文：

```text
报文 A：100B
报文 B：200B
报文 C：300B
```

UDP 不会主动把它们合并成一个应用报文，也不会将一个应用报文拆成多个 UDP 数据报。

应用发送多少个 UDP 报文，UDP 就处理多少个独立的数据报。

注意：网络层仍可能发生 IP 分片。

### 3.2 TCP 面向字节流

假设应用层连续写入：

```text
第1次：100B
第2次：200B
第3次：300B
```

TCP 关注的是：

$$
100+200+300=600\text{B}
$$

它把这些数据看成连续的字节流。

TCP 完全可能：

- 一次发送 600B；
- 分两次发送 300B；
- 分六次发送 100B；
- 按其他合适大小分段。

接收端应用程序读取到的字节边界，也不保证与发送端每次写入的边界相同。

这就是 TCP 编程中常见的消息粘连、拆分现象的根源。

严格说，TCP 并没有丢失字节，而是没有提供应用消息边界。应用必须自己定义消息格式，例如长度字段、分隔符等。

<Callout type="warn" title="检验和能检错，不等于可靠交付">

  UDP 检验和不能替代 ACK、重传、按序交付与拥塞控制。IPv4 上 UDP 校验和可按协议规定为零（表示不使用）；IPv6 一般要求 UDP 校验和，标准允许的例外须满足特定条件；典型 408 计算题一般按题设给出是否计算校验和。

</Callout>

### 3.3 为什么 UDP 不可靠，但还能检测差错？

这是很容易混淆的一点。

UDP 可以通过检验和发现数据错误。

但是：

差错检测不等于可靠传输。

可靠传输至少还需要考虑：

- 数据丢失；
- 数据重复；
- 数据乱序；
- 超时重传；
- 确认机制。

UDP 本身不提供这些可靠交付保障。

因此 2014 年真题：

I. UDP 提供无连接服务。

II. UDP 提供复用与分用服务。

III. UDP 通过差错校验保障可靠传输。

正确的是 I、II，答案 B。

## 四、UDP 首部、长度与检验和

### 4.1 UDP 首部结构

UDP 首部固定 8B。

```text
       0              15 16             31
      +----------------+----------------+
      |    源端口号     |    目的端口号    |
      +----------------+----------------+
      |    UDP 长度     |     检验和      |
      +----------------+----------------+
      |            数据载荷 ...          |
      +---------------------------------+
```

每个字段 16 位：

| 字段      | 长度    | 作用            |
| ------- | ----- | ------------- |
| 源端口号    | 16bit | 标识发送端口        |
| 目的端口号   | 16bit | 标识接收端口        |
| UDP 长度  | 16bit | UDP 首部加数据的总长度 |
| UDP 检验和 | 16bit | 检测差错          |

因此：

$$
\boxed{ L_{\text{UDP数据}}=L_{\text{UDP总长}}-8 }
$$

假设一个 UDP 数据报的长度字段为 200。

那么应用层数据长度：

$$
200-8=\boxed{192\text{B}}
$$

这里的 UDP 长度不包含 IP 首部。

### 4.2 模拟题：UDP 十六进制首部

Fumadocs 王道模拟题：

给定 UDP 首部：

```text
CB84000D001C001C
```

问各字段含义。

第一步，按 16 位拆分：

```text
CB84 | 000D | 001C | 001C
```

对应：

```text
源端口 | 目的端口 | UDP长度 | 校验和
```

第二步，十六进制转换。

源端口：

$$
\begin{aligned} \texttt{CB84}_{16} &=203\times256+132\\ &=\boxed{52100} \end{aligned}
$$

目的端口：

$$
\texttt{000D}_{16}=13
$$

UDP 长度：

$$
\texttt{001C}_{16}=28
$$

第三步，计算数据长度：

$$
28-8=\boxed{20\text{B}}
$$

所以：

| 项目      | 正确结果  |
| ------- | ----- |
| 源端口     | 52100 |
| 目的端口    | 13    |
| UDP 总长度 | 28B   |
| 应用数据长度  | 20B   |

由于源端口处于动态端口范围，目的端口为熟知端口，该报文很可能由客户端发往服务器，但不能仅凭端口号绝对确定应用角色。

### 4.3 UDP 检验和：重点计算题

UDP 使用 16 位反码求和。

必须掌握三个步骤：

1. 把参与校验的数据按 16 位分组。
2. 使用反码加法，最高位产生的进位加回低 16 位。
3. 最后按位取反，得到检验和。

这里的核心是：

回卷进位（end-around carry）。

普通二进制加法出现第 17 位进位时，不能直接丢弃，而是要加回低 16 位。

#### 2024 年 408 真题

已知 UDP 校验和计算过程中的中间结果为：

```text
1011100110110110
```

最后还需要加上：

```text
0110010111000101
```

求最终 UDP 检验和。

第一步：普通二进制加法。

```text
  1011100110110110
+ 0110010111000101
------------------
1 0001111101111011
```

第二步：处理最高位进位。

把最左边的 `1` 加回低 16 位：

```text
  0001111101111011
+ 0000000000000001
------------------
  0001111101111100
```

第三步：按位取反。

```text
0001111101111100
        ↓
1110000010000011
```

最终：

$$
\boxed{1110000010000011}
$$

原题答案 C。

#### 这类题的固定口诀

先求和，进位加回，再取反。

常见错误：

- 把最高位进位直接丢弃；
- 把普通补码运算当成反码加法；
- 已经取反后又取反一次；
- 把计算结果全 1 与全 0 的含义混淆。

### 4.4 伪首部是什么？

TCP 和 UDP 计算检验和时，都需要使用伪首部。

以 IPv4 为例，伪首部包含：

```text
源 IP 地址           32 bit
目的 IP 地址         32 bit
全 0                  8 bit
协议号                 8 bit
TCP/UDP 长度          16 bit
```

需要注意：

伪首部不是实际发送出去的 TCP 或 UDP 首部的一部分。

它只用于检验和计算。

为什么需要它？

因为 TCP/UDP 不仅需要检查传输层数据，还需要防止部分网络层关键信息出错导致错误交付。

例如目的 IP 地址变化可能影响数据交付对象，因此伪首部将目的 IP 纳入检验。

#### 伪首部易错点

| 判断                | 正误 |
| ----------------- | -- |
| 只有 UDP 才需要伪首部     | 错  |
| TCP 也使用伪首部        | 对  |
| 伪首部需要通过网络传输       | 错  |
| IPv4 首部检验和使用伪首部   | 错  |
| 伪首部包含源和目的 IP 地址   | 对  |
| UDP 检验和只覆盖 UDP 首部 | 错  |

还有两个细节：

第一，IPv4 中 UDP 检验和可以不使用。

此时检验和字段置为全 0。

如果实际计算得到的 UDP 检验和恰好为全 0，则发送时使用全 1 表示，以免和未使用检验和混淆。

第二，IPv6 中 UDP 检验和通常是强制使用的。

IPv6 存在特定隧道场景的零检验和例外，但一般 408 题目按必须使用理解即可。

## 五、TCP 首部结构——必须熟悉每个字段

TCP 是本章的核心。后面所有综合题，几乎都要用到 TCP 首部中的某些字段。

### 5.1 TCP 首部的基本结构

TCP 首部最短 20B，最长 60B。

```text
 0                  15 16                 31
+--------------------+--------------------+
|      源端口号       |      目的端口号      |
+--------------------+--------------------+
|                序号 seq                 |
+-----------------------------------------+
|              确认号 ack                 |
+-----------------------------------------+
|数据偏移| 保留及标志位 |       窗口大小      |
+--------------------+--------------------+
|       检验和        |       紧急指针       |
+--------------------+--------------------+
|               选项和填充                |
+-----------------------------------------+
|                数据部分                 |
+-----------------------------------------+
```

| 字段       | 长度     | 核心意义            |
| -------- | ------ | --------------- |
| 源端口、目的端口 | 各16bit | 标识通信端点          |
| 序号 seq   | 32bit  | 本段第一个数据字节的序号    |
| 确认号 ack  | 32bit  | 下一个期望收到的字节序号    |
| 数据偏移     | 4bit   | TCP 首部长度        |
| 控制标志     | 多个位    | 控制连接状态及数据处理     |
| 窗口字段     | 16bit  | 通告接收窗口          |
| 检验和      | 16bit  | 检测 TCP 段错误      |
| 紧急指针     | 16bit  | 与 URG 标志配合      |
| 选项       | 可变长    | MSS、窗口扩大、SACK 等 |

### 5.2 数据偏移为什么乘 4？

TCP 数据偏移字段以 4B 为单位。

如果数据偏移字段为 5：

$$
L_{\text{TCP首部}}=5\times4=20\text{B}
$$

如果数据偏移字段为 8：

$$
L_{\text{TCP首部}}=8\times4=32\text{B}
$$

字段为 15 时：

$$
15\times4=60\text{B}
$$

所以：

$$
\boxed{20\text{B}\leq L_{\text{TCP首部}}\leq60\text{B}}
$$

不能认为所有 TCP 首部都是 20B。

例如题目给出：

- IPv4 总长度：100B；
- IPv4 首部：20B；
- TCP 数据偏移：8。

应用数据长度：

$$
100-20-8\times4=\boxed{48\text{B}}
$$

这里不能错误地计算为 60B。

### 5.3 TCP 控制标志

| 标志      | 名称   | 作用          |
| ------- | ---- | ----------- |
| SYN     | 同步   | 建立连接、同步序号   |
| ACK     | 确认   | 表示确认号字段有效   |
| FIN     | 结束   | 发送方不再发送数据   |
| RST     | 复位   | 拒绝或异常终止连接   |
| PSH     | 推送   | 请求及时向应用交付数据 |
| URG     | 紧急   | 表明紧急指针有效    |
| ECE、CWR | 拥塞通知 | 与 ECN 机制有关  |

注意三个最重要的事实：

第一，SYN 占用一个序号。

第二，FIN 占用一个序号。

第三，普通纯 ACK 不占用序号。

这三个规则将贯穿所有题目。

TCP 数据段的发送序号与确认号定义还可以在 [TCP 标准 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) 中核对。

<Callout type="idea" title="典型以太网下的 1460B MSS 如何得到？">

  若链路 MTU 是 $1500\,\mathrm B$，使用没有选项的 IPv4 20B 首部和 TCP 20B 首部，则 $MSS=1500-20-20=1460\,\mathrm B$。IPv6、IP/TCP 选项和隧道封装会改变可用值，题目给定 MSS 时直接按题设。

</Callout>

### 5.4 MSS 与 MTU 的区别

MSS 是 TCP 最大报文段长度，通常指一个 TCP 段中的最大数据载荷长度。

MTU 是链路层能够承载的最大网络层分组长度。

假设：

- 以太网 MTU 为 1500B；
- IPv4 首部 20B；
- TCP 首部 20B。

则常见的 TCP MSS 为：

$$
MSS=1500-20-20
$$

$$
\boxed{MSS=1460\text{B}}
$$

两者区别：

| MSS             | MTU              |
| --------------- | ---------------- |
| TCP 数据载荷上限      | 链路层所承载网络层分组的大小上限 |
| 不包括 TCP 首部      | 包括 IP 首部         |
| TCP 层的重要参数      | 链路层相关参数          |
| 通常通过 SYN 中的选项通告 | 由链路技术和路径限制决定     |

如果 IPv4 或 TCP 携带选项，或者使用隧道封装，实际可用 MSS 还可能减少。

## 六、TCP 序号和确认号——全章计算的基础

这是整章最应该彻底掌握的部分。

### 6.1 序号以字节为单位

假设一个 TCP 段：

```text
seq = 1000
数据长度 = 500B
```

它携带的字节序号为：

$$
1000\sim1499
$$

接收方全部正确收到后，返回：

$$
\boxed{ack=1500}
$$

为什么不是 1499？

因为 ACK 表示：

原稿已经连续收到前面的所有字节，下一次希望收到序号为 1500 的字节。

基本公式：

$$
\boxed{ack=seq+L}
$$

其中 $L$ 是连续收到的数据字节数。

如果报文段包含 SYN 或 FIN，还需要计算其占用的序号。

更通用地：

$$
\boxed{ ack=seq+L+I_{\mathrm{SYN}}+I_{\mathrm{FIN}} }
$$

这里要求该段及之前的数据连续到达，没有留下序号缺口。

### 6.2 2009 年真题：连续发送两个段

题目：

甲向乙发送两个连续 TCP 段：

- 第一个段序号为 200，长度 300B；
- 第二个段长度 500B。

乙全部正确收到，问确认号。

第一个段范围：

$$
200\sim499
$$

第二个段范围：

$$
500\sim999
$$

所以：

$$
ack=200+300+500
$$

$$
\boxed{ack=1000}
$$

原题答案 D。

这是一切复杂序号题的基础。

### 6.3 2011 年真题：中间报文段丢失

这是累计确认的经典题。

甲连续发送三个 TCP 数据段：

| 报文段   | 数据长度 |
| ----- | ---- |
| 第 1 段 | 300B |
| 第 2 段 | 400B |
| 第 3 段 | 500B |

已知第三段序号为 900。

乙只正确收到第 1 段和第 3 段，第二段丢失。

问乙返回的确认号。

#### 第一步：反推第一段序号

第三段之前共有：

$$
300+400=700\text{B}
$$

因此第一段起始序号：

$$
900-700=200
$$

#### 第二步：列出序号区间

| 报文段   | 序号区间     | 接收情况 |
| ----- | -------- | ---- |
| 第 1 段 | 200～499  | 收到   |
| 第 2 段 | 500～899  | 丢失   |
| 第 3 段 | 900～1399 | 收到   |

#### 第三步：确定 ACK

虽然第三段已经收到，但中间缺少 500～899。

因此乙只能确认到连续部分的末尾。

$$
\boxed{ack=500}
$$

原题答案 B。

TCP 的累计确认不能越过序号缺口。

应当理解累计确认的边界：ACK 只指示首个尚未按序收到的字节。

如果缺少第二段，后面即使收到了 100 个数据段，普通累计 ACK 仍然不能越过第二段的缺口。

SACK 选项可以额外告诉发送方后面哪些区间已收到，但不会改变普通累计 ACK 的含义。

### 6.4 双向通信：两套独立的序号空间

TCP 是全双工通信。

甲向乙发送的数据，与乙向甲发送的数据，分别使用各自的序号空间。

因此：

收到的 seq 与收到的 ack，描述的是两个不同方向的数据。

#### 2013 年真题

甲收到乙发来的 TCP 报文段：

```text
seq = 1913
ack = 2046
数据长度 = 100B
```

问甲立即向乙发送的 TCP 段的序号和确认号。

第一步，看乙发来了多少数据。

乙发送的数据序号为：

$$
1913\sim2012
$$

所以甲希望乙下一次发送：

$$
\boxed{ack=2013}
$$

第二步，看乙对甲的确认。

收到的 `ack=2046` 表示：

乙已经连续收到甲发送到序号 2045 的数据。

甲下一次从：

$$
\boxed{seq=2046}
$$

开始发送新数据。

答案：

$$
\boxed{seq=2046,\quad ack=2013}
$$

原题答案 B。

这是非常经典的双向序号题。

<Callout type="info" title="TCP 序号为 32 位循环空间">

  TCP 序号按字节计数，逻辑上模 $2^{32}$ 循环；SYN 和 FIN 各消耗一个序号，纯 ACK 通常不消耗新的序号。涉及完整序号回绕或窗口比较时，不应简单使用无界整数直减。

</Callout>

### 6.5 SYN 与 FIN 为什么会额外加 1？

假设客户端发出：

```text
SYN=1
seq=1000
```

服务器确认：

$$
ack=1001
$$

因为 SYN 自身占用一个序号。

建立连接后，第一个数据字节序号为：

$$
1001
$$

假设传输了 4000B。

数据序号：

$$
1001\sim5000
$$

随后发送 FIN：

$$
seq=5001
$$

服务器确认 FIN：

$$
ack=5002
$$

整个序号变化：

```text
SYN：1000
       ↓ +1
数据：1001～5000
       ↓
FIN：5001
       ↓ +1
ACK：5002
```

这就解释了 2020 年真题。

已知：

- SYN 的 `seq=1000`；
- FIN 的 `seq=5001`。

问应用数据多少字节。

$$
5001-(1000+1)=\boxed{4000\text{B}}
$$

原题答案 C。

## 七、TCP 三次握手

### 7.1 三次握手全过程

设客户端初始序号为 $x$，服务器初始序号为 $y$。

```text
客户端 A                         服务器 B
CLOSED                           LISTEN
  |                                |
  |  SYN=1, seq=x                  |
  |------------------------------->|
  |                                |
  |  SYN=1, ACK=1                  |
  |  seq=y, ack=x+1                |
  |<-------------------------------|
  |                                |
  |  ACK=1                         |
  |  seq=x+1, ack=y+1              |
  |------------------------------->|
  |                                |
ESTABLISHED                    ESTABLISHED
```

#### 第一次握手

客户端发送：

```text
SYN=1
seq=x
```

客户端进入：

`SYN_SENT`

#### 第二次握手

服务器回复：

```text
SYN=1
ACK=1
seq=y
ack=x+1
```

服务器进入：

`SYN_RCVD`

#### 第三次握手

客户端发送：

```text
ACK=1
seq=x+1
ack=y+1
```

客户端进入：

`ESTABLISHED`

服务器收到第三次握手后进入 `ESTABLISHED`。

### 7.2 为什么需要三次握手？

这个问题有两个层次。

#### 第一层：同步双方初始序号

TCP 是全双工通信。

客户端和服务器都需要确定：

- 自己发送数据时的初始序号；
- 对方发送数据时的初始序号；
- 对方是否已经收到并确认自己的 SYN。

第三次握手使服务器能够确认客户端确实收到了服务器的 SYN。

#### 第二层：防止失效连接请求造成错误

假设客户端过去发送了一个 SYN。

由于网络延迟，这个 SYN 长时间滞留。

后来客户端重新建立了正常连接，而旧 SYN 又突然到达服务器。

如果只需要两次握手，服务器可能根据旧请求建立一个不必要的连接。

三次握手要求客户端进一步确认服务器的响应，避免服务器仅凭旧 SYN 就认为正常连接已经完全建立。

更准确地说，三次握手承担了双方初始序号同步和连接请求验证的任务。

### 7.3 真题：2019 年第三次握手

已知：

```text
客户端初始 seq = 2018
服务器初始 seq = 2046
```

问第三次握手中客户端发送的确认号。

第三次握手确认服务器的 SYN。

因此：

$$
ack=2046+1
$$

$$
\boxed{ack=2047}
$$

原题答案 D。

不要把客户端自己的初始序号 2018 加 1 当成确认号。

### 7.4 握手时间如何计算？

假设 RTT 为 10ms。

```text
t=0ms          客户端发送 SYN

t=5ms          服务器收到 SYN
               回复 SYN+ACK

t=10ms         客户端收到 SYN+ACK
               发送第三次握手 ACK

t=15ms         服务器收到第三次握手
```

所以从客户端发出 SYN，到客户端可以发送第三次握手：

$$
\boxed{1RTT}
$$

特别重要：

第三次握手 ACK 可以与首个数据段一起发送。

因此许多 408 时间计算题中，不需要在收到 SYN+ACK 后，再等待一个 RTT 才开始发送数据。

## 八、TCP 四次挥手与连接状态

### 8.1 为什么断开连接通常需要四次挥手？

因为 TCP 是全双工通信。

客户端停止发送，并不意味着服务器已经发送完自己的数据。

所以两个方向需要分别关闭。

```text
客户端 A                       服务器 B
ESTABLISHED                    ESTABLISHED
    |                              |
    | FIN=1, seq=u                 |
    |----------------------------->|
    |                              |
FIN_WAIT_1                    CLOSE_WAIT
    |                              |
    | ACK=1, ack=u+1               |
    |<-----------------------------|
    |                              |
FIN_WAIT_2                         |
    |                              |
    | FIN=1, seq=v                 |
    |<-----------------------------|
    |                              |
    | ACK=1, ack=v+1               |
    |----------------------------->|
    |                              |
TIME_WAIT                      CLOSED
    |
    | 等待 2MSL
    |
 CLOSED
```

#### 第一次挥手

主动关闭方发送：

```text
FIN=1
seq=u
```

进入 `FIN_WAIT_1`。

#### 第二次挥手

被动关闭方确认：

```text
ACK=1
ack=u+1
```

进入 `CLOSE_WAIT`。

主动关闭方收到 ACK 后进入 `FIN_WAIT_2`。

#### 第三次挥手

被动关闭方完成剩余数据发送后：

```text
FIN=1
seq=v
```

进入 `LAST_ACK`。

#### 第四次挥手

主动关闭方确认：

```text
ACK=1
ack=v+1
```

进入 `TIME_WAIT`。

经过 $2MSL$ 后进入 `CLOSED`。

### 8.2 CLOSE_WAIT 和 TIME_WAIT 的区别

这是常见选择题考点。

| 状态         | 一般属于谁 | 意义                 |
| ---------- | ----- | ------------------ |
| FIN_WAIT_1 | 主动关闭方 | 等待自己的 FIN 被确认      |
| FIN_WAIT_2 | 主动关闭方 | 等待对方 FIN           |
| CLOSE_WAIT | 被动关闭方 | 已收到对方 FIN，等待本地应用关闭 |
| LAST_ACK   | 被动关闭方 | 已发送 FIN，等待最终 ACK   |
| TIME_WAIT  | 主动关闭方 | 等待 $2MSL$      |
| CLOSED     | 双方    | 连接关闭               |

注意：主动关闭方不一定是客户端。

服务器也完全可以主动关闭连接。

### 8.3 为什么 TIME_WAIT 要等待 $2MSL$？

两个目的。

#### 目的 1：确保最终 ACK 能被重新发送

假设最后一个 ACK 丢失。

服务器没有收到 ACK，就可能重传 FIN。

如果客户端已经立即关闭，就不能正确处理这个重传 FIN。

因此客户端需要在 TIME_WAIT 中保留连接状态。

#### 目的 2：让旧报文在网络中消失

等待足够长的时间，降低旧连接中的迟到报文干扰后续连接的风险。

这里：

$$
\boxed{T_{\text{TIME\\\_WAIT}}=2MSL}
$$

MSL 是一个报文段可能在网络中存活的最长时间。

RTT 与 MSL 不是同一个概念。

### 8.4 2022 年真题：连接释放时间

已知：

$$
RTT=50\text{ms}
$$

$$
MSL=800\text{ms}
$$

客户端 C 主动关闭。

求从发送 FIN 开始，C 和服务器 S 最快何时进入 CLOSED。

假设单向传播时延为：

$$
\frac{RTT}{2}=25\text{ms}
$$

服务器在 25ms 收到 FIN，立即发送 ACK 和 FIN。

客户端在 50ms 收到服务器 FIN，发送最终 ACK，并进入 TIME_WAIT。

客户端此后等待：

$$
2MSL=1600\text{ms}
$$

因此客户端进入 CLOSED：

$$
50+1600=\boxed{1650\text{ms}}
$$

服务器还要等最终 ACK 传回来：

$$
50+25=\boxed{75\text{ms}}
$$

最终：

$$
\boxed{ T_C=1650\text{ms},\quad T_S=75\text{ms} }
$$

原题答案 D。

这个题最容易错在把服务器的 CLOSED 时间也加上 $2MSL$。

<Callout type="warn" title="四次挥手没有适用于所有场景的固定 RTT 数">

  FIN 和 ACK 可以合并，应用可能尚有数据要发送，ACK 也可能延迟；主动关闭方经历 TIME_WAIT 的具体起点取决于确认对端 FIN 的事件。若题目给出“立即 FIN”“忽略处理时延”，应画传播时间轴推导，不能只背一句固定的 $1.5RTT$。

</Callout>

### 8.5 四次挥手时间万能公式

如果题目明确说明：

- 主动关闭方发出 FIN；
- 服务器收到 FIN 后可立即发送自己的 FIN；
- 忽略处理时延与发送时延；
- 单向传播时延为 $RTT/2$；

那么：

主动关闭方进入 TIME_WAIT：

$$
\boxed{T=RTT}
$$

被动关闭方进入 CLOSED：

$$
\boxed{T=\frac32 RTT}
$$

主动关闭方进入 CLOSED：

$$
\boxed{T=RTT+2MSL}
$$

这组公式适用于上述最短时间模型。

如果服务器还有数据没发完，就必须画时间轴，不能直接套公式。

## 九、TCP 可靠传输

TCP 通过多个机制共同实现可靠的字节流交付。

其核心包括：

- 字节编号；
- 累计确认；
- 检验和；
- 超时重传；
- 快速重传；
- 接收缓存与重排序；
- 去除重复数据。

### 9.1 累计确认

假设发送了：

```text
段1：1000～1499
段2：1500～1999
段3：2000～2499
段4：2500～2999
```

如果段 2 丢失，而段 3、4 到达：

```text
段1：收到
段2：丢失
段3：收到
段4：收到
```

接收端仍然无法累计确认到 3000。

它通常返回：

$$
\boxed{ack=1500}
$$

因为 1500 是当前最早缺失字节。

### 9.2 超时重传

发送端发出需要确认的数据后，会根据重传超时计时器判断是否需要重新发送。

如果超时前没有收到有效确认，就会重传相应数据。

```text
发送数据
   ↓
等待 ACK
   ↓
超时仍未确认
   ↓
重传
```

注意：

超时不一定代表数据真的丢失。

可能是：

- 原始数据丢失；
- ACK 丢失；
- 网络延迟过大；
- 路径发生变化。

因此 TCP 会根据测量到的 RTT 动态调整 RTO，而不是始终使用固定值。

一个常见的 RTT 平滑估计形式为：

$$
SRTT_{\text{new}} =(1-\alpha)SRTT_{\text{old}} +\alpha RTT_{\text{sample}}
$$

其中 $\alpha$ 是新样本权重。

实际 RTO 还需要考虑 RTT 波动情况，并使用相应的退避机制。

### 9.3 快速重传

这是 408 特别重要的考点。

为什么不能所有丢包都等到超时？

因为超时可能很慢。

TCP 可以利用重复 ACK 推测丢包。

经典快速重传规则：

$$
\boxed{\text{收到3个重复ACK，触发快速重传}}
$$

#### 2019 年真题

发送端之前第一次收到：

```text
ACK=100
```

随后发送：

```text
seq=100
```

这个段丢失。

后续数据段正常到达接收端，接收端连续返回：

```text
ACK=100
ACK=100
ACK=100
```

发送端收到第三个重复 ACK 时，立即重传丢失的数据段。

题目中对应时刻为：

$$
\boxed{t_3}
$$

原题答案 C。

#### 为什么不是第二个 ACK 就重传？

因为乱序不一定意味着丢失。

网络可能先把后面的数据段送到了接收端。

连续收到 3 个重复 ACK，能够提供更强的丢包迹象。

但必须注意：

三个重复 ACK 不等于三个任意 ACK。

必须是与此前确认相同、满足快速重传条件的重复确认。

### 9.4 ACK 丢失一定会重传数据吗？

不一定。

例如：

```text
发送段1 → ACK=1500 丢失
发送段2 → ACK=2000 收到
```

第二个 ACK 是累计确认。

它意味着：

序号 2000 之前的数据都已经连续收到。

所以第一个 ACK 丢失，通常不会导致对应数据重传。

这也是 TCP 累计确认的优点。

但如果没有任何后续有效 ACK 覆盖之前的数据，发送方可能最终超时重传。

## 十、TCP 流量控制——rwnd

这是第 5 章的重点计算题。

### 10.1 为什么需要流量控制？

假设发送端速度为：

$$
100\text{MB/s}
$$

接收端应用程序只能处理：

$$
10\text{MB/s}
$$

如果发送端不加限制，接收缓存会越来越满。

最终缓存溢出。

因此 TCP 需要让接收方告诉发送方：

我现在还能接收多少数据。

这个限制由接收窗口 $rwnd$ 表示。

### 10.2 接收窗口 rwnd

假设服务器接收缓存为 20KB。

其中已经存入 8KB 数据，应用程序还没有读取。

剩余空间：

$$
rwnd=20-8
$$

$$
\boxed{rwnd=12\text{KB}}
$$

如果应用程序随后读取了 5KB，且没有新的数据写入：

$$
rwnd=12+5=17\text{KB}
$$

所以接收窗口不仅会减小，也可能增大。

### 10.3 真正的发送窗口

发送端同时受到两种限制：

第一，接收方是否有空间。

由 $rwnd$ 决定。

第二，网络能否承受相应的数据量。

由拥塞窗口 $cwnd$ 决定。

所以：

$$
\boxed{ W_s=\min(rwnd,cwnd) }
$$

例如：

$$
rwnd=10\text{KB}
$$

$$
cwnd=16\text{KB}
$$

则发送窗口上限：

$$
\boxed{W_s=10\text{KB}}
$$

注意这个公式给出的是窗口约束，而不一定是此刻还能立刻发送的新数据量。

<Callout type="warn" title="cwnd/rwnd 不是尚可继续发送的数据量">

  在经典题设中，$W=\min(cwnd,rwnd)$ 表示可在途上限；若已有 $U$ 字节未确认，则通常还可新发 $\max(0,W-U)$ 字节。按题目说明判断窗口从哪一个 ACK 及哪一段序号起计算。

</Callout>

### 10.4 已发送未确认数据必须扣除

这是很多人做错窗口题的关键。

例如：

$$
rwnd=5000\text{B}
$$

$$
cwnd=8000\text{B}
$$

于是：

$$
W_s=5000\text{B}
$$

但发送端已经发送了 3000B，还没有收到确认。

因此当前剩余可用额度：

$$
5000-3000=\boxed{2000\text{B}}
$$

可写为：

$$
\boxed{ W_{\text{可新增}} =\max\left(0,\min(cwnd,rwnd)-\text{在途未确认字节数}\right) }
$$

这是 408 简化窗口模型下非常有用的公式。具体计算还需要以当前累计 ACK 和有效通告窗口为准。

### 10.5 2010 年真题：还能发送多少数据？

已知：

- MSS = 1000B；
- cwnd = 4000B；
- 已连续发送两个 MSS；
- 收到第一个数据段的 ACK；
- 最新通告的 rwnd = 2000B。

问还能发送多少字节。

已经发送：

$$
2\times1000=2000\text{B}
$$

收到第一个段的 ACK，因此还有：

$$
1000\text{B}
$$

尚未确认。

当前窗口限制：

$$
\min(4000,2000)=2000\text{B}
$$

因此还可以发送：

$$
2000-1000=\boxed{1000\text{B}}
$$

原题答案 A。

错误做法是直接回答 2000B。

发送窗口上限不等于剩余可发送数据量。

### 10.6 2021 年真题：计算可发送序号范围

已知发送端先发送：

```text
seq=501
长度=200B
```

随后收到：

```text
ack=501
rwnd=500B
```

问尚未收到新的确认之前，还可以继续发送哪些序号的数据。

首先：

$$
ack=501
$$

说明接收窗口左边界为 501。

接收窗口大小为 500B。

因此接收窗口允许的区间：

$$
501\sim1000
$$

但发送端已经发送：

$$
501\sim700
$$

于是剩余可发送：

$$
\boxed{701\sim1000}
$$

原题答案 C。

这里要学会画数轴：

```text
501           700 701                  1000
 |-------------| |----------------------|
   已发送未确认          还可发送
```

### 10.7 零窗口与持续计时器

如果接收缓存被填满：

$$
rwnd=0
$$

那么发送方通常不能继续发送普通新数据。

但可能发生一个问题。

接收方应用程序读取数据后，窗口重新打开，并发送窗口更新通知。

如果这个窗口更新报文丢失：

- 发送方以为窗口仍为 0；
- 接收方以为已经通知发送方；
- 双方可能陷入长期等待。

TCP 使用**持续计时器（Persist Timer）**&#x2060;解决这个问题。

发送端可以发送零窗口探测，促使接收端重新通告接收窗口。

注意：

| 机制            | 解决问题           |
| ------------- | -------------- |
| 重传计时器         | 数据可能丢失         |
| 持续计时器         | 零窗口死锁          |
| 保活计时器         | 长时间空闲连接的对端存活检查 |
| TIME_WAIT 计时器 | 连接关闭后的等待       |

## 十一、TCP 拥塞控制——本章最重要的算法

理解拥塞控制，先分清：

流量控制关注接收方，拥塞控制关注网络。

### 11.1 cwnd 与 ssthresh

TCP 经典拥塞控制主要使用：

$$
cwnd
$$

拥塞窗口。

以及：

$$
ssthresh
$$

慢开始门限。

$cwnd$ 控制发送方允许保持在网络中的未确认数据量。

$ssthresh$ 用来区分慢开始和拥塞避免阶段。

### 11.2 慢开始 Slow Start

虽然叫慢开始，但其增长速度很快。

按 408 传统模型：

$$
cwnd_{\text{初始}}=1MSS
$$

慢开始阶段，每收到一个确认新数据的 ACK：

$$
cwnd\leftarrow cwnd+1MSS
$$

如果每个数据段分别确认，一个 RTT 内发出的数据全部得到确认，则下一轮窗口大致翻倍。

```text
RTT轮次     cwnd
  0          1
  1          2
  2          4
  3          8
  4         16
  5         32
```

因此：

$$
\boxed{cwnd_n=2^n MSS}
$$

这个公式只适用于没有提前碰到门限或其他限制，并采用相应 ACK 和按轮增长模型的情况。

“每 RTT 翻倍”是宏观结果，“每 ACK 增长”是细粒度计算方式。

实际 TCP 的初始拥塞窗口可以大于 1 MSS；真实拥塞控制算法与 408 经典简化模型也可能不同。考试计算题应优先遵守题设。

### 11.3 拥塞避免 Congestion Avoidance

当拥塞窗口达到慢开始门限后，转为拥塞避免。

经典考试模型：

每经过一个 RTT，拥塞窗口大约增加 1 MSS。

$$
\boxed{ cwnd_{\text{下一轮}}\approx cwnd_{\text{当前}}+1MSS }
$$

例如：

$$
ssthresh=8MSS
$$

则：

```text
1 → 2 → 4 → 8 → 9 → 10 → 11 → 12
  慢开始       拥塞避免
```

可以记成：

慢开始是指数增长，拥塞避免是线性增长。

在具体 TCP 标准中，$cwnd=ssthresh$ 时可以采用两种阶段处理方式之一；408 常见题目约定达到门限后进入拥塞避免。

### 11.4 发生超时怎么办？

这是绝对核心。

假设：

$$
cwnd=16MSS
$$

发生重传超时。

传统 408 模型：

第一步，设置门限：

$$
ssthresh=\frac{16}{2}=8MSS
$$

第二步，将拥塞窗口重新设置为：

$$
cwnd=1MSS
$$

第三步，重新慢开始。

窗口变化：

```text
超时前：
16

发生超时：
 1

恢复过程：
1 → 2 → 4 → 8 → 9 → 10 → ...
```

注意：

超时以后 cwnd 不是从 8 开始，而是从 1 MSS 重新开始。

### 11.5 2009 年真题：超时后 4 个 RTT

已知：

- MSS = 1KB；
- 超时前 cwnd = 16KB；
- 后续 4 个 RTT 均成功传输；
- 求第 4 个 RTT 的所有数据确认后 cwnd。

超时后：

$$
ssthresh=8\text{KB}
$$

$$
cwnd=1\text{KB}
$$

逐轮计算：

| 时刻        | cwnd |
| --------- | ---- |
| 刚超时       | 1KB  |
| 第 1 RTT 后 | 2KB  |
| 第 2 RTT 后 | 4KB  |
| 第 3 RTT 后 | 8KB  |
| 第 4 RTT 后 | 9KB  |

因此：

$$
\boxed{cwnd=9\text{KB}}
$$

原题答案 C。

### 11.6 2022 年真题：重新增长到 16KB

已知：

$$
MSS=1\text{KB}
$$

超时前：

$$
cwnd=16\text{KB}
$$

问超时后，重新增长到 16KB，最少需要几个 RTT。

超时后：

$$
ssthresh=8\text{KB}
$$

慢开始：

$$
1\to2\to4\to8
$$

需要 3 个 RTT。

然后拥塞避免：

$$
8\to9\to10\to\cdots\to16
$$

需要：

$$
16-8=8RTT
$$

总时间：

$$
3+8=\boxed{11RTT}
$$

原题答案 C。

<Callout type="info" title="教材 Reno 模型与真实 TCP 实现要区分">

  408 经典练习常以慢开始、拥塞避免、Tahoe/Reno 的阈值调整为模型；现代 TCP 可采用不同拥塞控制算法、有限的初始窗口、SACK/RACK 等机制。题目明确算法与时刻时遵循题设，未给出时先声明采用的教材抽象。

</Callout>

### 11.7 收到 3 个重复 ACK 怎么办？

在经典 TCP Reno 模型下：

收到 3 个重复 ACK：

1. 认为部分数据可能丢失；
2. 快速重传；
3. 将慢开始门限设置为拥塞窗口的大约一半；
4. 进入快速恢复。

例如：

$$
cwnd=16MSS
$$

则：

$$
ssthresh=8MSS
$$

在传统 Reno 快速恢复过程中，会临时对拥塞窗口进行调整；收到覆盖重传数据的有效确认并退出快速恢复后，窗口通常回到门限附近，再进行拥塞避免。

需要区分两种教材描述：

| 情况        | 408 常用简化结果       |
| --------- | ---------------- |
| 重传超时      | cwnd 变为 1 MSS    |
| 3 个重复 ACK | 快重传，门限约减半，随后快速恢复 |

但要注意：经典 Tahoe 不采用 Reno 式快速恢复；现代 TCP 还存在 CUBIC 等不同拥塞控制算法。

题目没有说明具体实现时，按照教材指定的经典模型计算。

### 11.8 2017 年真题：窗口增长时间

已知：

$$
MSS=1\text{KB}
$$

$$
RTT=5\text{ms}
$$

接收缓存为 64KB。

问连接建立成功后，发送窗口最快多久达到 32KB。

按照经典慢开始：

$$
1\to2\to4\to8\to16\to32
$$

需要 5 个 RTT。

因此：

$$
5\times5=\boxed{25\text{ms}}
$$

原题答案 A。

### 11.9 2020 年真题：为什么问“最长时间”？

已知：

- MSS = 1KB；
- RTT = 2ms；
- 拥塞窗口从 8KB 增长到 32KB；
- 不发生拥塞。

问最长时间。

注意“最长”两个字。

慢开始增长很快。

拥塞避免增长比较慢。

所以按拥塞避免计算：

$$
32-8=24MSS
$$

需要：

$$
24RTT
$$

时间：

$$
24\times2=\boxed{48\text{ms}}
$$

原题答案 D。

### 11.10 拥塞控制的标准做题表

碰到任何拥塞控制题，建议先画表：

| RTT | 阶段   | cwnd | ssthresh | 事件    |
| --- | ---- | ---- | -------- | ----- |
| 0   | 慢开始  | 1    | 8        | 初始    |
| 1   | 慢开始  | 2    | 8        | 正常    |
| 2   | 慢开始  | 4    | 8        | 正常    |
| 3   | 达到门限 | 8    | 8        | 正常    |
| 4   | 拥塞避免 | 9    | 8        | 正常    |
| 5   | 拥塞避免 | 10   | 8        | 正常    |
| 6   | 超时   | 1    | 5        | 超时后重置 |
| 7   | 慢开始  | 2    | 5        | 正常    |

第 6 轮原窗口 10，超时后门限为 5。

有了表格，绝大多数拥塞控制题都不会乱。

## 十二、综合大题精讲：2012 年抓包题

这道题将三层协议知识综合到一起。

原题可在 [2012 年 TCP/IP 报文综合题](https://exam.any1.tech/docs/408/past-exams-large-questions/04-5f0066b8/05-f3c4091b/#question-2012-47) 查看。

题设：

主机 H：

`192.168.0.8`

服务器 S：

`211.68.71.80`

给出 5 个 IP 数据报前 40 字节的十六进制内容。

要求判断：

1. 哪些由 H 发送；
2. 哪些完成 TCP 三次握手；
3. 哪些以太网帧需要填充；
4. S 收到了多少应用数据；
5. 经过多少个路由器。

### 12.1 如何分析 IP 首部？

假设前一个字节是：

```text
45
```

拆分：

```text
4 → IPv4
5 → IHL
```

IPv4 首部长度：

$$
5\times4=20\text{B}
$$

因此 TCP 首部从整个 IP 数据报的第 21 个字节开始。

IPv4 常用字段位置：

| 字段       | IP 首部字节位置  |
| -------- | ---------- |
| 版本、首部长度  | 第 1 字节     |
| 总长度      | 第 3～4 字节   |
| 标识       | 第 5～6 字节   |
| TTL      | 第 9 字节     |
| 协议       | 第 10 字节    |
| 源 IP 地址  | 第 13～16 字节 |
| 目的 IP 地址 | 第 17～20 字节 |

本题中：

```text
C0 A8 00 08
```

表示：

$$
192.168.0.8
$$

所以源 IP 为这个地址的分组由 H 发送。

原题结论：

$$
\boxed{1,3,4}
$$

号分组由 H 发送。

### 12.2 如何判断三次握手？

查看 TCP 标志位：

- 第 1 个分组：SYN；
- 第 2 个分组：SYN+ACK；
- 第 3 个分组：ACK。

因此：

$$
\boxed{1,2,3}
$$

构成三次握手。

### 12.3 为什么有的以太网帧需要填充？

普通以太网最小帧长为 64B，包含：

- 14B MAC 首部；
- 至少 46B 数据；
- 4B FCS。

因此：

$$
64-14-4=46\text{B}
$$

如果封装的 IP 数据报不足 46B，就需要填充。

本题分组 3 和 5 的 IP 总长度为：

$$
\texttt{0028}_{16}=40\text{B}
$$

需要填充：

$$
46-40=\boxed{6\text{B}}
$$

所以需要填充的是：

$$
\boxed{3,5}
$$

注意：填充字节不属于 IP 总长度，也不属于 TCP 应用数据。

### 12.4 如何根据 ACK 反推数据量？

本题连接建立后，H 第一个数据字节序号为：

```text
0x846B41C6
```

服务器返回确认号：

```text
0x846B41D6
```

两者相减：

$$
\texttt{0x846B41D6} - \texttt{0x846B41C6} = \texttt{0x10}
$$

所以：

$$
\boxed{16\text{B}}
$$

也可以从对应 IP 分组长度计算：

$$
56-20-20=16\text{B}
$$

### 12.5 根据 TTL 求路由器数量

服务器发送时：

$$
TTL=64
$$

H 捕获时：

$$
TTL=49
$$

每经过一台正常转发的路由器，TTL 至少减 1。

在本题常规模型下：

$$
64-49=\boxed{15}
$$

即经过 15 台路由器。

#### 本题最终答案

| 小问      | 答案    |
| ------- | ----- |
| H 发送的分组 | 1、3、4 |
| 三次握手分组  | 1、2、3 |
| 需要以太网填充 | 3、5   |
| 应用层数据量  | 16B   |
| 经过的路由器  | 15    |

这类题以后只要看到十六进制抓包，就固定按：

IP 首部 → TCP 首部 → 标志位 → 序号 → ACK → IP 长度 → TTL

逐项分析。

## 十三、综合大题精讲：2016 年 TCP 窗口题

这道题尤其重要，因为它同时考查了整个 TCP 系统。

[查看 Fumadocs 2016 年第 41 题](https://exam.any1.tech/docs/408/past-exams-large-questions/04-5f0066b8/05-f3c4091b/#question-2016-41)

### 13.1 题设

已知：

$$
MSS=1\text{KB}
$$

$$
RTT=200\text{ms}
$$

接收缓存：

$$
20\text{KB}
$$

初始慢开始门限：

$$
ssthresh=32\text{KB}
$$

客户端初始序号：

$$
seq=100
$$

服务器收到数据后立即确认，但应用程序始终不读取缓存。

### 13.2 第一问：第二次握手

客户端 SYN：

$$
seq=100
$$

服务器回复：

```text
SYN=1
ACK=1
ack=101
```

所以：

$$
\boxed{ack=101}
$$

### 13.3 第二问：第 8 个 ACK 到达后的窗口

服务器缓存最初是 20KB。

每收到一个 1KB 数据段，缓存可用空间减少 1KB。

收到 8 个数据段后：

$$
rwnd=20-8=\boxed{12\text{KB}}
$$

再看拥塞窗口。

初始：

$$
cwnd=1MSS
$$

每收到一个确认新数据的 ACK，增加 1 MSS。

所以收到第 8 个 ACK 后：

$$
cwnd=1+8=\boxed{9MSS}
$$

也就是：

$$
cwnd=9\text{KB}
$$

发送窗口：

$$
W_s=\min(9,12)
$$

$$
\boxed{W_s=9\text{KB}}
$$

这里最容易出错。

不能说：

“经过第 8 个 ACK，所以窗口应该是 $2^8$”。

因为题目问的是第 8 个确认段到达时，不是经过 8 个 RTT。

### 13.4 第三问：缓存填满后的序号

接收缓存为：

$$
20\text{KB}=20480\text{B}
$$

客户端 SYN 使用序号 100。

因此第一个数据字节：

$$
101
$$

总计发送并确认 20480B 后，下一个数据字节序号：

$$
101+20480
$$

$$
\boxed{20581}
$$

### 13.5 数据传输用了几个 RTT？

初始 cwnd 为 1 MSS。

采用经典慢开始、逐段立即确认、按 RTT 轮次计算：

| 轮次      | 本轮发送 | 累计收到数据 |
| ------- | ---- | ------ |
| 第 1 RTT | 1KB  | 1KB    |
| 第 2 RTT | 2KB  | 3KB    |
| 第 3 RTT | 4KB  | 7KB    |
| 第 4 RTT | 8KB  | 15KB   |
| 第 5 RTT | 5KB  | 20KB   |

为什么最后只发送 5KB？

因为缓存只剩：

$$
20-15=5\text{KB}
$$

第五轮接收并确认后，服务器通告零窗口。

总时间：

$$
5\times200\text{ms}=1\text{s}
$$

平均数据传输速率：

$$
v=\frac{20\times1024}{1}
$$

$$
\boxed{20480\text{B/s}}
$$

换成 bit/s：

$$
20480\times8=163840\text{bit/s}
$$

因此：

$$
\boxed{163.84\text{kb/s}}
$$

这里有一个需要纠正的单位问题。

20KB/s 不是 20kb/s。

本题题设：

$$
1\text{KB}=1024\text{B}
$$

而：

$$
1\text{B}=8\text{bit}
$$

所以换算时必须乘 8。

### 13.6 第四问：服务器最快多久释放连接？

客户端主动关闭。

已知：

$$
RTT=200\text{ms}
$$

服务器无剩余数据，可立即发送自己的 FIN。

服务器最快进入 CLOSED：

$$
T_S=\frac32 RTT
$$

$$
T_S=\frac32\times200
$$

$$
\boxed{300\text{ms}}
$$

#### 本题答案汇总

| 问题             | 答案         |
| -------------- | ---------- |
| 第二次握手 SYN      | 1          |
| 第二次握手 ACK      | 1          |
| 确认号            | 101        |
| 第 8 个确认后的 rwnd | 12KB       |
| 第 8 个确认后的 cwnd | 9KB        |
| 发送窗口           | 9KB        |
| 缓存满后的下一序号      | 20581      |
| 平均数据速率         | 163.84kb/s |
| 服务器最快释放时间      | 300ms      |

这道题建议至少独立做三遍。

## 十四、综合大题精讲：2023 年 FTP + TCP

[查看 Fumadocs 2023 年第 47 题](https://exam.any1.tech/docs/408/past-exams-large-questions/04-5f0066b8/05-f3c4091b/#question-2023-47)

这是应用层与传输层联合命题的典型题。

### 14.1 题设

客户端上传文件：

$$
L=18000\text{B}
$$

TCP 数据连接初始序号：

$$
seq=100
$$

最大报文段长度：

$$
MSS=1000\text{B}
$$

初始门限：

$$
ssthresh=4MSS
$$

RTT：

$$
RTT=10\text{ms}
$$

无差错、无丢包、无乱序。

### 14.2 第一问：FTP 的两种连接

FTP 使用两种 TCP 连接。

| 连接   | 功能        | 传统 FTP 模型 |
| ---- | --------- | --------- |
| 控制连接 | 登录、命令与响应  | 持久        |
| 数据连接 | 文件传输、目录信息 | 非持久       |

登录服务器时首先建立：

$$
\boxed{\text{控制连接}}
$$

### 14.3 第二问：文件第一个字节序号

SYN 占用一个序号。

所以：

$$
100+1=\boxed{101}
$$

文件有 18000B。

最后一个数据字节：

$$
101+18000-1=18100
$$

FIN 序号：

$$
18101
$$

服务器确认 FIN：

$$
18101+1=\boxed{18102}
$$

注意题目问的是第二次挥手 ACK 的确认号，不是 FIN 的序号。

### 14.4 第三问：ACK=2101 时 cwnd 是多少？

文件第一个字节序号：

$$
101
$$

收到：

$$
ack=2101
$$

代表已经累计确认：

$$
2101-101=2000\text{B}
$$

也就是两个 MSS。

在本题逐段确认的经典模型下：

```text
初始 cwnd = 1MSS

第 1 个 ACK 后：
cwnd = 2MSS

第 2 个 ACK 后：
cwnd = 3MSS
```

因此：

$$
\boxed{cwnd=3MSS}
$$

这里有一个细节：ACK 值本身只说明累计确认了多少字节；要推断具体拥塞窗口，还需要题目规定或默认的 ACK 产生方式与拥塞增长规则。本题采用逐段确认的计算模型。

### 14.5 ACK=7101 时 cwnd 是多少？

首先：

$$
7101-101=7000\text{B}
$$

即累计确认 7 个 MSS。

窗口达到：

$$
4MSS
$$

之后进入拥塞避免。

根据本题按 RTT 轮次的经典增长模型，累计确认前 7 个数据段后：

$$
\boxed{cwnd=5MSS}
$$

### 14.6 第四问：发送完整文件需要多久？

总数据量：

$$
18000\text{B}
$$

MSS：

$$
1000\text{B}
$$

因此共有：

$$
18
$$

个数据段。

逐轮分析：

| 数据 RTT | cwnd 上限 | 本轮发送 | 累计发送 |
| ------ | ------- | ---- | ---- |
| 第 1 轮  | 1MSS    | 1    | 1    |
| 第 2 轮  | 2MSS    | 2    | 3    |
| 第 3 轮  | 4MSS    | 4    | 7    |
| 第 4 轮  | 5MSS    | 5    | 12   |
| 第 5 轮  | 6MSS    | 6    | 18   |

数据发送并被确认需要：

$$
5RTT
$$

但题目从请求建立 TCP 数据连接开始计时。

建立连接到客户端可发送首个数据，还需要：

$$
1RTT
$$

所以：

$$
T=(1+5)RTT
$$

$$
T=6\times10\text{ms}
$$

$$
\boxed{T=60\text{ms}}
$$

### 14.7 平均发送速率

$$
v=\frac{18000\text{B}}{0.06\text{s}}
$$

$$
v=300000\text{B/s}
$$

乘以 8：

$$
v=2400000\text{bit/s}
$$

$$
\boxed{v=2.4\text{Mb/s}}
$$

#### 这道题最关键的三个思想

第一，传输起点包括建连，终点不包括释放连接，因为题目明确要求从建立数据连接到确认文件完整接收。

第二，慢开始和拥塞避免必须分段计算。

第三，应用层文件数据长度与 TCP 的 SYN、FIN 所消耗的序号不能混在一起。

## 十五、2024 年真题：连接建立、数据传输与关闭

这是典型的时间轴题。

### 15.1 题设

$$
L=3000\text{B}
$$

$$
MSS=1000\text{B}
$$

$$
RTT=10\text{ms}
$$

$$
MSL=30\text{s}
$$

H 主动关闭 TCP 连接。

求从请求建立 TCP 连接开始，到 H 进入 CLOSED，最少需要多长时间。

### 15.2 建立连接

H 发出 SYN。

经过：

$$
1RTT=10\text{ms}
$$

收到 SYN+ACK。

第三次握手 ACK 可以同时携带第一个数据段。

所以：

```text
t=0ms：发送 SYN

t=10ms：收到 SYN+ACK
        发送 ACK+第1个数据段
```

### 15.3 数据传输

共：

$$
3000/1000=3MSS
$$

按照初始 1 MSS 的经典慢开始：

第 1 轮：

发送 1 MSS。

在 20ms 收到确认。

第 2 轮：

发送剩余 2 MSS。

在 30ms 收到确认。

因此：

$$
\boxed{t=30\text{ms}}
$$

时 H 确认全部数据已经到达服务器。

### 15.4 释放连接

H 在 30ms 发送 FIN。

最短情况下，经过一个 RTT：

$$
t=40\text{ms}
$$

H 收到服务器 FIN，发送最终 ACK，进入 TIME_WAIT。

等待：

$$
2MSL=60\text{s}
$$

因此：

$$
T=60\text{s}+0.04\text{s}
$$

$$
\boxed{60.04\text{s}}
$$

原题答案 D。

#### 时间轴总结

```text
0ms          10ms         20ms        30ms       40ms
 |-------------|------------|-----------|----------|
   TCP握手       第1个MSS     后2个MSS      挥手
                                               |
                                               v
                                            TIME_WAIT
                                               |
                                             2MSL
                                               |
                                               v
                                             CLOSED
```

牢记：

TIME_WAIT 是 2MSL，而不是 2RTT。

## 十六、站内 2026 年综合题：接收窗口限制与拥塞窗口联合计算

Fumadocs 大题库还收录了标注为 2026 年第 47 题的题目，可以作为额外综合训练。

### 16.1 题设

客户端发送文件：

$$
L=2000\text{B}
$$

$$
MSS=500\text{B}
$$

$$
ssthresh=8MSS
$$

服务器始终通告：

$$
rwnd=1000\text{B}
$$

RTT：

$$
RTT=5\text{ms}
$$

客户端初始序号：

$$
seq_C=1000
$$

服务器初始序号：

$$
seq_S=2000
$$

### 16.2 握手确认号

客户端 SYN 占一个序号。

服务器第二次握手：

$$
\boxed{ack=1001}
$$

### 16.3 收到 ACK=2001 后的窗口

题目采用逐段确认的慢开始模型。

从第一个数据字节 1001 开始：

- 第一个 500B 段被确认；
- 第二个 500B 段被确认。

因此收到累计确认号 2001 的 ACK 后：

$$
cwnd=3MSS
$$

$$
cwnd=1500\text{B}
$$

但服务器接收窗口只有：

$$
rwnd=1000\text{B}
$$

所以发送窗口：

$$
W_s=\min(1500,1000)
$$

$$
\boxed{W_s=1000\text{B}}
$$

### 16.4 FIN 与 ACK

文件第一个字节：

$$
1001
$$

文件最后一个字节：

$$
1001+2000-1=3000
$$

客户端 FIN：

$$
seq=3001
$$

服务器确认：

$$
ack=3002
$$

如果服务器未发送应用数据，其 SYN 序号为 2000，因此服务器 FIN 序号为：

$$
2001
$$

客户端收到的最后一个服务器报文段可为：

```text
seq=2001
ack=3002
FIN=1
```

### 16.5 完整传输时间

文件共有：

$$
2000/500=4MSS
$$

数据传输按轮次：

```text
第1轮：1MSS
第2轮：2MSS
第3轮：1MSS
```

共 3 个数据 RTT。

连接建立还需要 1 RTT。

所以：

$$
T=4RTT
$$

$$
T=4\times5
$$

$$
\boxed{20\text{ms}}
$$

这一题重点体现：

cwnd 增长了，不代表真实发送窗口一定增长，因为 rwnd 可能成为限制因素。

## 十七、模拟题强化：五类常考变式

下面结合站内模拟题，提炼更容易拉开分数的题型。

### 17.1 题型一：固定接收窗口限制

某 TCP 连接：

- MSS = 1000B；
- 初始 cwnd = 1 MSS；
- ssthresh = 8 MSS；
- rwnd 始终为 6 MSS。

发送 24000B 文件。

假设服务器持续读取数据，使窗口始终维持 6 MSS。

逐轮：

| RTT | cwnd 上限 | 实际可发段数 | 累计段数 |
| --- | ------- | ------ | ---- |
| 1   | 1       | 1      | 1    |
| 2   | 2       | 2      | 3    |
| 3   | 4       | 4      | 7    |
| 4   | 8       | 6      | 13   |
| 5   | 约 9     | 6      | 19   |
| 6   | 约 10    | 5      | 24   |

文件全部发完，需要 6 轮发送。

如果 RTT 为 10ms，首段在 $t=0$ 发出：

- 末轮在 50ms 发出；
- 末轮 ACK 在 60ms 返回。

如果允许将 FIN 紧接末段发送，并且服务器收到 FIN 后立即回送 FIN，服务器进入 CLOSED 的最短时间可以进一步按三个单向传播时延计算。

此类题必须特别注意题目给出的计时终点，是最后数据发出、最后 ACK 返回、服务器 CLOSED，还是客户端 CLOSED。

### 17.2 题型二：反推初始门限

假设：

- 初始 cwnd = 1 MSS；
- 经过 20 个 RTT；
- 首次发生 3 个重复 ACK；
- 新门限恰好等于初始门限；
- 每 RTT 按经典模型增长。

设初始门限为 $S$ MSS。

发生丢包时：

$$
cwnd=2S
$$

如果：

$$
S=16
$$

慢开始：

$$
1\to2\to4\to8\to16
$$

需要 4 RTT。

之后剩余 16 RTT 进入拥塞避免：

$$
16+16=32
$$

发生拥塞时减半：

$$
32/2=16
$$

恰好等于初始门限。

因此：

$$
\boxed{ssthresh=16MSS}
$$

这是站内模拟题的典型解法。

### 17.3 题型三：FIN 之后的序号

已知：

```text
FIN=1
seq=1000
```

连接关闭的最后 ACK 不携带新数据。

那么最后 ACK 的序号：

$$
\boxed{seq=1001}
$$

因为 FIN 消耗一个序号，纯 ACK 不再消耗序号。

注意：

这里问的是最后 ACK 的 `seq`，不是 `ack`。

二者完全不同。

### 17.4 题型四：根据 ACK 反推数据量

服务器的 SYN：

$$
seq=1000
$$

客户端某报文：

$$
ack=6001
$$

且服务器没有发送其他消耗序号的控制信息。

服务器首个数据字节：

$$
1001
$$

客户端已累计确认：

$$
1001\sim6000
$$

因此应用数据量：

$$
6001-1001=\boxed{5000\text{B}}
$$

### 17.5 题型五：快恢复与接收窗口

假设：

$$
cwnd=8MSS
$$

$$
rwnd=5MSS
$$

发生丢包，接收 3 个重复 ACK。

按照简化 Reno 模型，退出快恢复后：

$$
cwnd\approx4MSS
$$

发送窗口上限：

$$
W_s=\min(4,5)
$$

$$
\boxed{4MSS}
$$

但如果接收窗口只有 2 MSS：

$$
W_s=\min(4,2)=\boxed{2MSS}
$$

所以这种题一定要先更新拥塞窗口，再与接收窗口取最小值。

| --- | ------------------------ | ---------------------------- |
| 1   | TCP 序号按报文段编号             | 按字节编号                        |
| 2   | ACK 是最后收到的字节序号           | ACK 是下一个期望字节序号               |
| 3   | SYN 不占序号                 | SYN 占 1 个序号                  |
| 4   | FIN 不占序号                 | FIN 占 1 个序号                  |
| 5   | 纯 ACK 占序号                | 纯 ACK 不占序号                   |
| 6   | 后面的段到了，就能越过丢失段确认         | 累计 ACK 不能越过缺口                |
| 7   | UDP 有检验和，所以可靠            | 差错检测不等于可靠传输                  |
| 8   | UDP 伪首部需要传输              | 伪首部不实际传输                     |
| 9   | TCP 首部恒为 20B             | 有选项时可达 60B                   |
| 10  | MSS 就是 MTU               | MSS 不包括 TCP/IP 首部            |
| 11  | cwnd 就是实际发送窗口            | 还要考虑 rwnd                    |
| 12  | 发送窗口等于还能发送的数据量           | 还要考虑已发未确认数据                  |
| 13  | 慢开始是线性增长                 | 典型情况下指数增长                    |
| 14  | 拥塞避免是指数增长                | 经典模型下线性增长                    |
| 15  | 超时后 cwnd 变成原来一半          | 经典模型下变成 1 MSS                |
| 16  | 3 个重复 ACK 等于超时           | 快重传与超时处理不同                   |
| 17  | 第 8 个 ACK 等于第 8 个 RTT    | ACK 数量与 RTT 轮次不同             |
| 18  | rwnd 为 0 说明网络拥塞          | 表示接收窗口耗尽                     |
| 19  | TIME_WAIT 发生在服务器         | 通常发生在主动关闭方                   |
| 20  | TIME_WAIT 等待 2RTT        | 经典模型等待 2MSL                  |
| 21  | 建连一定需要完整 1.5 RTT 后才能发送数据 | 客户端收到 SYN+ACK 后可立即发送第三次握手和数据 |
| 22  | 服务器接收 FIN 后必须立即发 FIN     | 可能还有数据需要发送                   |
| 23  | TCP ACK 丢失必然导致重传         | 后续累计 ACK 可能覆盖                |
| 24  | TCP 的窗口字段可以无限扩大          | 基本字段 16 位，扩展需窗口扩大选项          |
| 25  | 传输速率 MB/s 与 Mb/s 相同      | 相差 8 倍                       |

尤其要注意第 17 条。

ACK 驱动的窗口变化与按 RTT 轮次推演，是两个不同层次的计算方法。

## 十九、三道综合强化练习

下面给出三道仿照 408 命题方式设计的练习题。

它们是强化练习，不是历年真题。

### 练习一：序号、累计确认与快速重传

发送端连续发送 5 个 TCP 数据段，MSS 为 1000B。

各段序号：

```text
1000
2000
3000
4000
5000
```

其中序号为 2000 的数据段丢失，其余全部按序到达接收端。

问：

1. 收到第一个段后返回什么 ACK？
2. 收到第三个段后返回什么 ACK？
3. 收到第四个段后返回什么 ACK？
4. 收到第五个段后返回什么 ACK？
5. 发送方何时可以触发经典快速重传？
6. 丢失段重传成功后，如果接收端缓存了全部后续数据，返回什么 ACK？

<Accordions>
<Accordion title="展开：参考答案与推导" id="net5-practice-01">

#### 解析

第一个段：

$$
1000\sim1999
$$

所以：

$$
ACK=2000
$$

第二段丢失。

第三、四、五段虽然到达，但不能越过缺口累计确认。

因此：

| 事件      | 返回 ACK |
| ------- | ------ |
| 收到第 1 段 | 2000   |
| 收到第 3 段 | 2000   |
| 收到第 4 段 | 2000   |
| 收到第 5 段 | 2000   |

后面三个 ACK 是针对同一缺口产生的三个重复 ACK。

因此可以触发快速重传。

如果重传的第二段成功到达，之前的第三、四、五段已经缓存：

$$
1000\sim5999
$$

全部连续收到。

所以：

$$
\boxed{ACK=6000}
$$

最终答案：

$$
\boxed{2000,\ 2000,\ 2000,\ 2000,\ 6000}
$$

其中后三次重复确认触发快重传。

</Accordion>
</Accordions>

### 练习二：接收缓存与拥塞窗口

某 TCP 连接：

$$
MSS=1\text{KB}
$$

$$
RTT=100\text{ms}
$$

初始：

$$
cwnd=1MSS
$$

$$
ssthresh=16MSS
$$

接收缓存为 10KB。

接收端应用程序不读取数据。

求：

1. 前三轮分别发送多少数据？
2. 第三轮全部确认后，rwnd、cwnd 和发送窗口是多少？
3. 服务器接收缓存被填满时，总共收到了多少数据？
4. 从首段发送到零窗口通知到达发送方，需要多少 RTT？

<Accordions>
<Accordion title="展开：参考答案与推导" id="net5-practice-02">

#### 解析

第一轮：

$$
1\text{KB}
$$

第二轮：

$$
2\text{KB}
$$

第三轮：

$$
4\text{KB}
$$

累计：

$$
1+2+4=7\text{KB}
$$

服务器剩余缓存：

$$
rwnd=10-7=\boxed{3\text{KB}}
$$

此时：

$$
cwnd=8\text{KB}
$$

发送窗口：

$$
W_s=\min(8,3)=\boxed{3\text{KB}}
$$

第四轮最多再发 3KB。

总计：

$$
7+3=10\text{KB}
$$

缓存被填满。

从首个数据段发出，到最后一批数据确认并通告零窗口到达：

$$
4RTT
$$

$$
4\times100=\boxed{400\text{ms}}
$$

</Accordion>
</Accordions>

### 练习三：TCP 完整时间轴

某客户端 C 向服务器 S 发送 7000B 文件。

已知：

$$
MSS=1000\text{B}
$$

$$
RTT=20\text{ms}
$$

$$
MSL=30\text{s}
$$

初始拥塞窗口为 1 MSS，慢开始门限为 8 MSS，接收窗口足够大。

文件传输无丢包。

发送完并确认全部文件后，C 主动请求关闭连接，服务器可立即发送 FIN。

求：

1. 数据至少需要几个 RTT 被全部确认？
2. 从请求建连到确认数据全部接收需要多久？
3. 从请求建连到服务器 CLOSED 需要多久？
4. 从请求建连到客户端 CLOSED 需要多久？

<Accordions>
<Accordion title="展开：参考答案与推导" id="net5-practice-03">

#### 解析

文件共：

$$
7000/1000=7MSS
$$

慢开始轮次：

$$
1,\ 2,\ 4
$$

累计：

$$
1+2+4=7MSS
$$

因此数据需要：

$$
3RTT
$$

建立连接：

$$
1RTT
$$

所以确认文件全部接收：

$$
(1+3)RTT=4RTT
$$

$$
\boxed{80\text{ms}}
$$

然后 C 发送 FIN。

服务器进入 CLOSED 还需要：

$$
\frac32 RTT=30\text{ms}
$$

所以服务器 CLOSED：

$$
80+30=\boxed{110\text{ms}}
$$

客户端从发送 FIN 到进入 TIME_WAIT 需要：

$$
1RTT=20\text{ms}
$$

再等待：

$$
2MSL=60\text{s}
$$

因此客户端 CLOSED：

$$
80\text{ms}+20\text{ms}+60\text{s}
$$

$$
\boxed{60.10\text{s}}
$$

这道题综合了：

- TCP 三次握手；
- 慢开始；
- 分轮发送；
- RTT 计算；
- 主动关闭；
- TIME_WAIT。

</Accordion>
</Accordions>

## 二十、TCP 综合题通用解题模板

以后遇到一道 TCP 大题，只要题目同时给出：

```text
初始 seq
MSS
RTT
ssthresh
rwnd
文件大小
丢包情况
MSL
```

就按下面的顺序处理。

### 第一步：先写序号账本

```text
SYN序号：
首个数据字节：
最后一个数据字节：
FIN序号：
对FIN的确认号：
```

基本公式：

$$
\boxed{\text{首数据序号}=ISN+1}
$$

$$
\boxed{\text{FIN序号}=ISN+1+L}
$$

$$
\boxed{\text{FIN确认号}=ISN+2+L}
$$

这里假设只有一次 SYN、连续发送 $L$ 字节应用数据，没有其他消耗序号的信息。

### 第二步：写窗口约束

$$
\boxed{W_s=\min(cwnd,rwnd)}
$$

如果问还能继续发多少：

$$
\boxed{ W_{\text{剩余}}= \max(0,W_s-\text{在途未确认数据}) }
$$

### 第三步：画拥塞窗口变化表

```text
初始 cwnd
    ↓
慢开始
    ↓
达到 ssthresh
    ↓
拥塞避免
    ↓
发生丢包？
    ├─ 超时：cwnd回到1MSS
    └─ 3个重复ACK：快重传/快恢复
```

### 第四步：按 RTT 统计发送量

例如：

| RTT | cwnd | rwnd | 本轮发送 | 累计 |
| --- | ---- | ---- | ---- | -- |
| 1   | 1    | 10   | 1    | 1  |
| 2   | 2    | 10   | 2    | 3  |
| 3   | 4    | 10   | 4    | 7  |
| 4   | 8    | 10   | 8    | 15 |

必须分清：

- 本轮能发多少；
- 已累计发送多少；
- 已累计确认多少；
- 当前还有多少数据在途；
- 缓存还有多少空闲空间。

### 第五步：画时间轴

```text
TCP建连
   ↓
首个数据发送
   ↓
数据分轮传输
   ↓
最后ACK到达
   ↓
主动发送FIN
   ↓
对方ACK/FIN
   ↓
最终ACK
   ↓
TIME_WAIT
   ↓
CLOSED
```

然后根据题目终点，决定应该计算到哪一步。

这就是第 5 章综合大题最稳定的解题方法。

## 二十二、本章如何复习到能够稳定拿分？

根据 Fumadocs 收录的题目，建议分四个层次完成复习。

### 第一层：先掌握基本概念

必须熟悉：

- UDP 首部和检验和；

这一层主要保证基础选择题。

### 第二层：熟练完成六类计算

2. cwnd、ssthresh 的变化；

4. TCP 快速重传；
5. TCP 连接释放时间；
6. 传输速率和 RTT。

这一层解决大多数中等难度题。

### 第三层：精练四道综合大题

### 第四层：进一步训练混合场景

真正有区分度的综合题可能同时给出：

$$
MSS,\ RTT,\ rwnd,\ cwnd,\ ssthresh,\ seq,\ MSL
$$

然后加入一次中间段丢失。

要求你判断：

- 哪些 ACK 会重复；

序号表、窗口变化表、时间轴。

### 最后总结

第 5 章表面上知识点很多，但核心其实只有五句话：

第一，TCP 按字节编号，ACK 表示下一个期望字节。

第二，SYN 和 FIN 各占一个序号，普通纯 ACK 不占序号。

第三，流量控制看 rwnd，拥塞控制看 cwnd，发送窗口受两者共同约束。

第四，慢开始快增长、拥塞避免慢增长；超时与三个重复 ACK 的处理不同。

第五，综合题不要凭感觉算 RTT，而要把握手、数据传输、挥手和 TIME_WAIT 分别画到时间轴上。

从考研 408 的角度，这一章最值得投入时间的不是反复背 TCP、UDP 的定义，而是把序号、累计确认、接收窗口、拥塞窗口与时间计算真正联系起来。

只要掌握这套统一模型，即使题目把网络层、数据链路层和应用层知识混在一起，也能按照协议层次逐步拆解，而不是靠记忆某一道真题的答案。
