### 1.2 本章最重要的五个问题

学习 TCP 时，要始终围绕五个问题：

1. 数据应该交给哪个应用进程？
2. 连接如何建立、如何关闭？
3. 数据丢失、乱序、重复后如何保证可靠交付？
4. 接收方来不及处理数据怎么办？
5. 网络发生拥塞时，发送方应该如何调整速率？

分别对应：

| 问题 | 解决机制 |
|---|---|
| 应用定位 | 端口、Socket、复用与分用 |
| 连接管理 | 三次握手、四次挥手 |
| 可靠传输 | 序号、ACK、重传、滑动窗口 |
| 流量控制 | 接收窗口 rwnd |
| 拥塞控制 | cwnd、ssthresh、慢开始、拥塞避免 |

理解这五个问题，就能建立整章的逻辑框架。

## 二、传输层的基本功能

### 2.1 为什么需要传输层？

网络层提供的是主机之间的逻辑通信。

例如：

    主机 A：192.168.1.10

    主机 B：192.168.1.20

网络层可以把 IP 数据报送到主机 B。

但是主机 B 可能同时运行：

- 浏览器
- 游戏客户端
- 聊天软件
- FTP 服务
- DNS 服务

数据抵达主机 B 后，还必须确定交给哪个应用进程。

因此：

**传输层负责向应用进程提供端到端的逻辑通信服务。**

对比：

| 层次 | 通信对象 | 典型标识 |
|---|---|---|
| 数据链路层 | 相邻节点 | MAC 地址 |
| 网络层 | 主机 | IP 地址 |
| 传输层 | 应用进程的通信端点 | 端口号 |

注意：

网络层的 IP 地址通常定位主机或网络接口。

传输层使用端口号定位应用通信端点。

严格来说，端口号不能直接等同于操作系统进程，一个进程可以使用多个 Socket。

### 2.2 复用与分用

#### 复用

发送端将多个应用进程的数据交给传输层。

    浏览器 ───┐
              │
    游戏 ─────┼── TCP/UDP ── IP
              │
    邮件 ─────┘

这是复用。

#### 分用

接收端把数据交给对应的应用进程。

    IP
     │
     ▼
    TCP/UDP
     │
     ├── 浏览器
     ├── 游戏
     └── 邮件

这是分用。

两者的区别：

- 复用发生在发送端。
- 分用发生在接收端。

#### 真题：2018 年 UDP 分用

题目：

UDP 实现分用时，主要依据首部中的哪个字段？

A. 源端口号
B. 目的端口号
C. 长度
D. 检验和

答案：B。

解析：

接收端根据目的端口号，把 UDP 数据报交给对应的 Socket。

这里一定要分清：

源端口号标识发送端的端口，目的端口号标识接收端的端口。

在基础题中，UDP 分用的直接判断依据是目的端口号。

更严格的 Socket 分用还涉及本地 IP、协议类型及绑定规则。


## 三、端口号、Socket 与 TCP 连接

### 3.1 端口号的长度

TCP 和 UDP 的端口字段均为 16 位。

因此：

$$
2^{16}=65536
$$

端口号范围：

$$
0\sim65535
$$

端口分类：

| 范围 | 类型 |
|---|---|
| 0～1023 | 熟知端口 |
| 1024～49151 | 注册端口 |
| 49152～65535 | 动态或私有端口 |

常见服务端口：

| 服务 | 端口 | 传输协议 |
|---|---|---|
| HTTP | 80 | TCP |
| HTTPS（HTTP/1.1、HTTP/2） | 443 | TCP |
| FTP 控制连接 | 21 | TCP |
| SSH | 22 | TCP |
| SMTP | 25 | TCP |
| DNS | 53 | UDP/TCP |
| DHCP 服务器 | 67 | UDP |
| DHCP 客户端 | 68 | UDP |
| POP3 | 110 | TCP |

注意：

HTTP/3 基于 QUIC，QUIC 运行在 UDP 之上，通常使用 UDP 443。

所以不能笼统认为所有 HTTPS 通信都必须使用 TCP。

### 3.2 Socket

Socket 可以理解为应用程序使用的网络通信端点。

在 408 基础模型中，可以抽象为：

$$
\text{Socket}=(IP,\ Port)
$$

但一条 TCP 连接不能仅由一个端点确定。

### 3.3 TCP 连接四元组

一条 TCP 连接由以下四元组区分：

$$
\boxed{
(\text{源IP},\text{源端口},\text{目的IP},\text{目的端口})
}
$$

例如：

    客户端 A
    192.168.1.10:50000
           │
           ▼
    服务器
    10.0.0.1:80

同时：

    客户端 B
    192.168.1.11:50000
           │
           ▼
    服务器
    10.0.0.1:80

服务器使用同一个 80 端口，却可以同时维护这两条连接。

因为源 IP 不同，连接四元组不同。

#### 高频陷阱

错误说法：

一台服务器只有 65536 个端口，因此最多建立 65536 条 TCP 连接。

正确理解：

端口号有 65536 种数值，并不意味着 TCP 连接总数最多只有 65536 条。

同一个服务器端口可以对应大量不同的 TCP 连接。

#### 模拟题

判断：

I. 一台主机的 TCP 端口号数值种类不超过 65536。
II. 一台主机最多同时建立 65536 条 TCP 连接。
III. TCP 连接释放后，端口号可以再次使用。
IV. 一个服务器端口可以同时对应多个 TCP 连接。

答案：

$$
\boxed{\text{I、III、IV}}
$$

说明：

该模拟题的原始选项缺少正确组合，应以计算结果为准。

这是不能直接背诵原题选项的典型例子。


## 四、UDP 协议

### 4.1 UDP 的特点

UDP（User Datagram Protocol）是用户数据报协议。

主要特点：

1. 无连接。
2. 面向报文。
3. 尽最大努力交付。
4. 不保证可靠、按序、不重复交付。
5. 首部固定为 8B。
6. UDP 本身不提供 TCP 式流量控制。
7. UDP 本身不提供拥塞控制。
8. 可以支持广播和多播。

#### 什么叫无连接？

UDP 在发送数据前，不需要像 TCP 一样执行三次握手。

应用可以直接构造 UDP 数据报并交给网络层发送。

#### 什么叫面向报文？

假设应用发送：

    报文 A：100B
    报文 B：200B
    报文 C：300B

UDP 将它们视为三个独立的应用报文。

发送端通常一次应用发送对应一个 UDP 数据报。

接收端也保留数据报的边界。

TCP 则不同。

TCP 将应用数据视为连续字节流，不保留应用写入时的消息边界。

注意：

UDP 保留应用报文边界，不代表底层 IP 一定不会分片。

### 4.2 UDP 为什么不可靠？

UDP 可以进行差错检测，但不提供完整的可靠交付机制。

例如：

    发送方：

    A → B → C → D

网络实际传输：

    A → C → D

B 丢失。

UDP 本身不会自动要求发送方重传 B。

因此：

**检验和只能检测部分差错，不能保证可靠交付。**

但这不代表 UDP 上层的应用无法提供可靠性。

例如 QUIC 通过在 UDP 之上增加确认、重传、拥塞控制等机制，可以实现可靠传输。

#### 真题：2014 年

I. UDP 提供无连接服务。
II. UDP 提供复用和分用服务。
III. UDP 通过差错校验保障可靠数据传输。

答案：I、II。

原因：

III 错在把差错检测等同于可靠传输。


## 五、UDP 首部结构与长度计算

### 5.1 UDP 首部

UDP 首部固定为 8B。

结构：

    0                 15 16                31
    ┌──────────────────┬───────────────────┐
    │      源端口       │      目的端口      │
    ├──────────────────┼───────────────────┤
    │      UDP长度      │       检验和       │
    └──────────────────┴───────────────────┘
    │               数据部分               │
    └─────────────────────────────────────┘

四个字段均为 16 位：

| 字段 | 长度 |
|---|---|
| 源端口号 | 16bit |
| 目的端口号 | 16bit |
| UDP 长度 | 16bit |
| UDP 检验和 | 16bit |

### 5.2 UDP 长度公式

UDP 长度字段包含：

$$
L_{UDP}=L_{\text{首部}}+L_{\text{数据}}
$$

UDP 首部固定为 8B。

因此：

$$
\boxed{
L_{\text{数据}}=L_{UDP}-8
}
$$

例如：

某 UDP 数据报长度为 200B。

求应用数据长度。

$$
L=200-8=192B
$$

注意：

UDP 长度字段不包括 IP 首部。

### 5.3 模拟题：十六进制首部解析

题目给出：

    CB84000D001C001C

要求判断：

I. 源端口号为 52096。
II. 目的端口号为 13。
III. UDP 数据长度为 28B。
IV. 该数据报属于客户端向服务器发送的通信。

#### 第一步：按 16 位分组

    CB84 | 000D | 001C | 001C

对应：

    源端口 | 目的端口 | UDP长度 | 检验和

#### 第二步：计算源端口

$$
\begin{aligned}
\texttt{0xCB84}
&=12\times16^3+11\times16^2+8\times16+4\\
&=52100
\end{aligned}
$$

因此 I 错误。

#### 第三步：计算目的端口

$$
\texttt{0x000D}=13
$$

II 正确。

#### 第四步：计算数据长度

$$
\texttt{0x001C}=28
$$

这是 UDP 总长度。

真正的应用数据长度：

$$
28-8=20B
$$

III 错误。

#### 第五步：判断通信方向

源端口 52100 为动态端口，目的端口 13 是传统 Daytime 服务端口。

在典型客户端请求服务器的场景下，可推测为客户端到服务器。

IV 按题目预设场景正确。

但要注意：仅从端口数值不能严格证明通信双方的业务角色。

最终答案：

$$
\boxed{\text{II、IV}}
$$


## 六、UDP 检验和

这是 UDP 部分最重要的计算考点。

### 6.1 UDP 检验范围

UDP 检验和覆盖：

    UDP 伪首部
         +
    UDP 首部
         +
    UDP 数据

注意：

伪首部只参加检验和计算，不作为 UDP 报文的一部分发送。

### 6.2 IPv4 UDP 伪首部

伪首部主要包含：

| 字段 | 长度 |
|---|---|
| 源 IP 地址 | 32bit |
| 目的 IP 地址 | 32bit |
| 全 0 | 8bit |
| 协议号 | 8bit |
| UDP 长度 | 16bit |

其中 UDP 的 IP 协议号为：

$$
17
$$

TCP 的 IP 协议号为：

$$
6
$$

### 6.3 UDP 检验和的计算步骤

采用 16 位反码加法。

基本步骤：

1. 将 UDP 检验和字段暂时置 0。
2. 构造伪首部。
3. 拼接伪首部、UDP 首部和数据。
4. 按 16 位分组。
5. 进行反码加法。
6. 对产生的进位进行回卷。
7. 将最终结果逐位取反。

#### 什么叫回卷进位？

例如：

$$
\texttt{0xFFFF}+\texttt{0x0001}
=\texttt{0x10000}
$$

结果出现第 17 位进位。

不能简单截断成 0。

需要把最高位的进位加回低 16 位：

$$
\texttt{0x0000}+\texttt{0x0001}
=\texttt{0x0001}
$$

然后再取反。

### 6.4 真题：2024 年 UDP 检验和

题目：

已知中间结果：

    1011100110110110

还需要加上最后一个 16 位数：

    0110010111000101

求最终检验和。

#### 第一步：相加

$$
\begin{aligned}
&1011100110110110\\
+&0110010111000101\\
=&1\,0001111101111011
\end{aligned}
$$

出现最高位进位 1。

#### 第二步：回卷进位

低 16 位为：

    0001111101111011

加上进位 1：

    0001111101111100

#### 第三步：逐位取反

    1110000010000011

因此：

$$
\boxed{1110000010000011}
$$

答案：C。

这道题重点不是普通二进制加法，而是：

**进位回卷后，还必须逐位取反。**

### 6.5 接收端如何检验？

接收端把收到的检验和字段也参与 16 位反码加法。

如果未检测到错误，最终求和结果应为：

$$
\boxed{\texttt{0xFFFF}}
$$

需要注意：

检验和不是能够检测所有可能错误的绝对保证。

它是一种差错检测机制，不提供纠错功能，也不保证可靠交付。

### 6.6 IPv4 UDP 的特殊规定

在 IPv4 中：

- 校验和字段为 `0x0000` 可以表示不使用 UDP 检验和。
- 如果实际算出的校验和值为 `0x0000`，发送时应写为 `0xFFFF`。
- 如果计算结果本来就是 `0xFFFF`，则保留该值。

IPv6 下 UDP 校验和通常是必需的，标准规定的特定例外另论。

### 6.7 三种检验和的区别

| 检验机制 | 检验范围 |
|---|---|
| IPv4 首部检验和 | IPv4 首部 |
| UDP 检验和 | 伪首部、UDP 首部、UDP 数据 |
| TCP 检验和 | 伪首部、TCP 首部、TCP 数据 |

特别注意：

TCP 和 UDP 都使用伪首部。

伪首部不是把完整 IP 首部复制一份，也不会被实际发送。


## 七、TCP 的基本特点

TCP（Transmission Control Protocol）提供：

- 面向连接
- 可靠传输
- 有序交付
- 全双工通信
- 面向字节流
- 流量控制
- 拥塞控制

### 7.1 TCP 与 UDP 对比

| 对比 | UDP | TCP |
|---|---|---|
| 是否连接 | 无连接 | 面向连接 |
| 数据单位 | 报文 | 字节流 |
| 可靠交付 | 不保证 | 保证 |
| 按序交付 | 不保证 | 保证 |
| 自动重传 | 无 | 有 |
| 流量控制 | 无内建机制 | 有 |
| 拥塞控制 | 无内建机制 | 有 |
| 最小首部 | 8B | 20B |
| 广播和多播 | 支持 | 不支持 |
| 应用消息边界 | 保留 | 不保留 |

### 7.2 TCP 为什么是面向字节流？

假设应用调用三次发送操作：

    第一次：100B
    第二次：200B
    第三次：300B

TCP 认为它们组成：

$$
100+200+300=600B
$$

的连续字节流。

TCP 可能：

- 按 100B、200B、300B 分段；
- 将 600B 合并为一个报文段；
- 分成多个更小的报文段。

TCP 并不保证接收端每次读取数据的边界与发送端应用的写入边界相同。

因此应用协议必须自行定义消息边界。

常见方法：

- 固定长度
- 长度字段
- 特殊分隔符
- 自描述数据格式

### 7.3 TCP 可靠传输依靠什么？

主要机制：

    校验和：发现差错

    序列号：识别字节位置

    累计确认：反馈接收进度

    重传：恢复丢失数据

    滑动窗口：提高传输效率

    接收缓存：处理速率差异与乱序

    流量控制：避免接收端缓存溢出

这些机制配合才能实现可靠字节流。


## 八、TCP 首部结构

### 8.1 TCP 首部长度

TCP 首部最小长度：

$$
20B
$$

最大长度：

$$
60B
$$

原因：

TCP 数据偏移字段占 4bit。

其单位为 4B。

因此最大首部长度为：

$$
15\times4=60B
$$

最小为：

$$
5\times4=20B
$$

### 8.2 TCP 首部重点字段

| 字段 | 长度 | 含义 |
|---|---|---|
| 源端口 | 16bit | 发送端端口 |
| 目的端口 | 16bit | 接收端端口 |
| 序号 | 32bit | 当前段首个数据字节序号 |
| 确认号 | 32bit | 下一个期望收到的字节序号 |
| 数据偏移 | 4bit | TCP 首部长度 |
| 控制位 | 若干位 | 连接及控制信息 |
| 窗口 | 16bit | 通告接收窗口 |
| 检验和 | 16bit | 检验首部和数据 |
| 紧急指针 | 16bit | 配合 URG 使用 |
| 选项 | 可变 | MSS、SACK 等 |

#### 必须注意

TCP 首部的 Window 字段表示：

$$
rwnd
$$

即接收窗口。

不是：

$$
cwnd
$$

拥塞窗口由发送方本地维护，不直接写入 TCP 首部。

### 8.3 TCP 的六个经典控制位

| 控制位 | 含义 |
|---|---|
| URG | 紧急指针有效 |
| ACK | 确认号有效 |
| PSH | 推送数据 |
| RST | 复位连接 |
| SYN | 同步序号、建立连接 |
| FIN | 结束本方向发送 |

需要重点理解：

SYN：建立连接。

ACK：确认号有效。

FIN：关闭当前方向的数据发送。

RST：复位或拒绝连接。

注意：

`ACK=1` 不等于确认号为 1。

它只是表示确认号字段有效。

### 8.4 MSS 和 MTU

MSS 表示：

**TCP 报文段最大数据部分长度。**

MTU 表示：

**网络层数据报在相应链路上的最大传输单元。**

在无 IP/TCP 选项的 IPv4 典型场景下：

$$
MSS=MTU-20-20
$$

如果：

$$
MTU=1500B
$$

则：

$$
MSS=1500-20-20
$$

$$
\boxed{MSS=1460B}
$$

注意：

MSS 不包含 TCP 首部，也不包含 IP 首部。

TCP 首部存在选项时，实际单个报文段可容纳的数据还可能进一步受到限制。

### 8.5 TCP 首部效率题

真题：2021 年。

分别用一个 UDP 数据报和一个 TCP 报文段传输 12B 应用数据，求最大有效载荷效率。

UDP：

$$
\eta_{UDP}=\frac{12}{12+8}
$$

$$
\boxed{\eta_{UDP}=60\%}
$$

TCP：

$$
\eta_{TCP}=\frac{12}{12+20}
$$

$$
\boxed{\eta_{TCP}=37.5\%}
$$

这里仅考虑传输层首部，没有计入 IP 首部和链路层开销。


## 九、TCP 序列号与确认号

这是整个传输层最重要的基础。

### 9.1 TCP 按字节编号

TCP 序号字段为 32 位。

序号空间：

$$
2^{32}
$$

TCP 不是对报文段编号，而是对字节流编号。

例如：

    第一个报文段：

    seq = 100
    数据 = 300B

它包含的字节序号为：

    100～399

第二个报文段的起始序号：

    400

如果第二段携带 500B，则字节序号为：

    400～899

接收方连续收到两个段后：

    ACK = 900

### 9.2 最重要的公式

一个段：

$$
seq=S
$$

数据长度：

$$
L
$$

则其数据字节区间为：

$$
[S,S+L-1]
$$

连续接收后：

$$
\boxed{ACK=S+L}
$$

### 9.3 ACK 的含义

$$
ACK=N
$$

表示：

已经连续收到序号小于 $N$ 的字节，下一步期望收到序号为 $N$ 的字节。

例如：

    ACK = 1001

表示：

    1000 及之前的连续字节已收到

    下一个期望字节：1001

不是表示已经收到了 1001B 数据。

必须结合本方向的初始数据序号判断已收到多少字节。

### 9.4 SYN 与 FIN 消耗序号

这是容易漏算的地方。

规则：

- SYN 消耗 1 个序号。
- FIN 消耗 1 个序号。
- 一个数据字节消耗 1 个序号。
- 不携带数据的纯 ACK 通常不消耗序号。

统一公式：

$$
\boxed{
seq_{\text{next}}
=
seq_{\text{current}}
+L+I_{SYN}+I_{FIN}
}
$$

其中：

$$
I_{SYN},I_{FIN}\in\{0,1\}
$$

#### 例题

某 TCP 段：

    seq = 1000
    数据长度 = 500B
    FIN = 1

则：

$$
ACK=1000+500+1
$$

$$
\boxed{ACK=1501}
$$

如果没有 FIN，则为：

$$
ACK=1500
$$

### 9.5 真题：2009 年

题目：

第一个 TCP 段的序号为 200，两个连续数据段分别携带 300B、500B。

接收方正确收到后，确认号是多少？

计算：

$$
200+300+500=1000
$$

答案：

$$
\boxed{1000}
$$

### 9.6 真题：2013 年，双向序号

题目：

甲收到乙发来的 TCP 段：

    seq = 1913
    ack = 2046
    数据长度 = 100B

甲立即回复的 TCP 段，其序号与确认号分别是多少？

#### 第一步：确定甲发送方向的序号

乙发来的：

    ack = 2046

表示乙希望接下来收到甲发送的字节序号为 2046。

因此甲可以使用：

$$
seq=2046
$$

#### 第二步：确定甲对乙的确认号

乙发送的数据从 1913 开始，共 100B。

$$
ACK=1913+100
$$

$$
ACK=2013
$$

答案：

$$
\boxed{seq=2046,\ ACK=2013}
$$

#### 本题最重要的理解

TCP 是全双工通信。

甲发送方向和乙发送方向拥有各自独立的序号空间。

不能把收到报文中的 seq 和 ack 混为同一方向的数据。


## 十、TCP 累计确认、乱序与丢包

### 10.1 什么叫累计确认？

TCP 的 ACK 确认的是：

**当前已经连续收到的字节范围。**

例如：

    段1：1～1000
    段2：1001～2000
    段3：2001～3000

若按序收到：

    段1

则：

    ACK = 1001

收到段2：

    ACK = 2001

收到段3：

    ACK = 3001

### 10.2 如果中间数据丢失？

假设：

    段1：1～1000       收到

    段2：1001～2000    丢失

    段3：2001～3000    收到

    段4：3001～4000    收到

即使段3、段4已经收到，累计确认号依然是：

$$
\boxed{ACK=1001}
$$

因为缺少：

    1001～2000

这部分字节。

#### 为什么不能 ACK=4001？

因为：

    ACK = 4001

表示序号小于 4001 的数据都已连续收到。

但段2没有收到。

因此不能这样确认。

### 10.3 真题：2011 年

题目：

甲连续发送三个 TCP 段：

    第1段：300B
    第2段：400B
    第3段：500B

第三段起始序号为 900。

乙只收到第1段和第3段。

求确认号。

#### 第一步：反推第1段起始序号

第三段之前有：

$$
300+400=700B
$$

因此：

$$
seq_1=900-700=200
$$

#### 第二步：确定第1段序号范围

$$
200\sim499
$$

#### 第三步：确定丢失的数据

第2段应从：

$$
500
$$

开始。

因为第2段丢失，所以：

$$
\boxed{ACK=500}
$$

答案：B。

### 10.4 ACK 丢失是否必然重传？

不一定。

例如：

    段1收到 → ACK=1001

    ACK=1001 丢失

    段2收到 → ACK=2001

    ACK=2001 到达

由于后一个 ACK 已经累计确认前面的数据，发送方不需要因为前一个 ACK 丢失就重传段1。

因此：

**ACK 丢失不等于数据一定重传。**

如果没有任何后续有效确认到达，发送方才可能因 RTO 超时而重传。

### 10.5 TCP 是否等于 GBN 或 SR？

不等于。

对比：

| 特征 | GBN | SR | TCP |
|---|---|---|---|
| 编号单位 | 帧 | 帧 | 字节 |
| ACK | 累计确认 | 选择确认 | 主要使用累计确认 |
| 乱序数据 | 通常丢弃 | 缓存 | 可缓存 |
| 重传 | 回退重传 | 选择性重传 | 超时、快重传、可配合 SACK |

TCP 有自己的复杂机制，不能简单认为：

    TCP = GBN

或者：

    TCP = SR


## 十一、TCP 三次握手

### 11.1 为什么要建立连接？

TCP 是面向连接的协议。

通信前必须让双方明确：

- 双方愿意建立连接。
- 双方的初始序列号。
- 对端的序列号已经被接收。
- 后续数据能够按照约定的状态进行传输。

### 11.2 三次握手过程

假设：

客户端初始序列号：

$$
x
$$

服务器初始序列号：

$$
y
$$

<Steps>
<Step>
#### 第一次握手

客户端发送：

    SYN = 1
    ACK = 0
    seq = x

状态：

    CLOSED → SYN-SENT

SYN 消耗 1 个序号。

</Step>
<Step>
#### 第二次握手

服务器发送：

    SYN = 1
    ACK = 1
    seq = y
    ack = x+1

状态：

    LISTEN → SYN-RECEIVED

服务器确认客户端的 SYN，并同步自己的初始序列号。

</Step>
<Step>
#### 第三次握手

客户端发送：

    SYN = 0
    ACK = 1
    seq = x+1
    ack = y+1

客户端进入：

    ESTABLISHED

服务器收到后也进入：

    ESTABLISHED

时序：

```text
客户端                         服务器
   │                              │
   │──── SYN, seq=x ─────────────>│
   │                              │
   │<── SYN+ACK, seq=y, ack=x+1 ─│
   │                              │
   │──── ACK, ack=y+1 ───────────>│
   │                              │
   │       连接建立完成            │
```

</Step>
</Steps>

### 11.3 为什么是三次，不是两次？

核心原因：

双方不仅要同步序列号，还要确认对方收到了自己的连接请求信息。

假设只有两次：

    客户端 → SYN → 服务器

    客户端 ← SYN+ACK ← 服务器

服务器不知道客户端是否真正收到了第二次握手中的 SYN。

如果网络中存在一个滞留的旧 SYN，服务器可能误认为客户端发起了新的连接。

第三次握手能够帮助解决这个问题。

### 11.4 第三次握手能否携带数据？

可以。

例如：

客户端初始序号：

$$
x=1000
$$

第一次握手的 SYN 占用序号 1000。

因此第三次握手如果携带数据，则数据起始序号可以是：

$$
\boxed{1001}
$$

第三次握手的纯 ACK 不额外消耗一个序号。

### 11.5 真题：2019 年

题目：

甲、乙初始序列号分别为：

$$
ISN_A=2018
$$

$$
ISN_B=2046
$$

第三次握手的确认号是多少？

第三次握手是甲确认乙的 SYN。

因此：

$$
ACK=2046+1
$$

$$
\boxed{ACK=2047}
$$

答案：D。

### 11.6 真题：2011 年

甲发送：

    SYN=1
    seq=11220

服务器若接受连接，第二次握手应该满足：

    SYN=1
    ACK=1
    ack=11221

服务器自己的 seq 可以独立选择。

因此：

    SYN=1
    ACK=1
    seq=11221
    ack=11221

是可能的合法应答。

重点：

**第二次握手的 seq 不要求等于客户端的序号。**


## 十二、TCP 四次挥手

### 12.1 为什么通常需要四次？

TCP 是全双工通信。

两个方向都需要独立终止发送。

一方发送 FIN，只表示：

**自己不会继续发送新的数据。**

不表示对方也已经发送完毕。

因此一般要分别关闭两个方向。

### 12.2 四次挥手过程

假设 A 主动关闭连接。

A 当前序号：

$$
u
$$

B 发送 FIN 时的序号：

$$
w
$$

<Steps>
<Step>
#### 第一次挥手

A：

    FIN=1
    seq=u

状态：

    ESTABLISHED → FIN-WAIT-1

</Step>
<Step>
#### 第二次挥手

B：

    ACK=1
    ack=u+1

状态：

    ESTABLISHED → CLOSE-WAIT

A 收到后：

    FIN-WAIT-1 → FIN-WAIT-2

</Step>
<Step>
#### 第三次挥手

B 确认自己也没有数据要继续发送。

B 发送：

    FIN=1
    seq=w

状态：

    CLOSE-WAIT → LAST-ACK

</Step>
<Step>
#### 第四次挥手

A：

    ACK=1
    ack=w+1

状态：

    FIN-WAIT-2 → TIME-WAIT

B 收到最终 ACK：

    LAST-ACK → CLOSED

A 经过：

$$
2MSL
$$

后：

    TIME-WAIT → CLOSED

时序：

```text
主动关闭方 A                 被动关闭方 B
     │                            │
     │──── FIN, seq=u ───────────>│
     │                            │
     │<─── ACK, ack=u+1 ─────────│
     │                            │
     │      B可能继续发送数据       │
     │                            │
     │<─── FIN, seq=w ───────────│
     │                            │
     │──── ACK, ack=w+1 ─────────>│
     │                            │
  TIME-WAIT                     CLOSED
     │
     │ 等待 2MSL
     ▼
   CLOSED
```

</Step>
</Steps>

### 12.3 为什么不能把第二次和第三次挥手总是合并？

因为 B 收到 A 的 FIN 后，可能还有应用数据没有发送完。

例如：

A 不再发送数据，但 B 还有一份文件需要传给 A。

B 可以先确认 A 的 FIN，再继续发送文件数据。

完成之后才发送自己的 FIN。

因此：

四次挥手是经典流程。

如果 B 没有剩余数据，ACK 与 FIN 可以合并，报文段数量不一定恰好为四个。

### 12.4 半关闭

假设 A 已经发送 FIN。

意味着：

    A → B

方向的数据发送结束。

但：

    B → A

方向仍然可能继续发送数据。

这就是 TCP 半关闭的重要含义。

### 12.5 TIME-WAIT 为什么等待 2MSL？

两个主要原因：

#### 原因一：保证最后 ACK 可以重传

如果 A 发送的最后 ACK 丢失：

B 没有收到 ACK，就可能重新发送 FIN。

A 仍在 TIME-WAIT，便可以再次回复 ACK。

#### 原因二：让旧连接的迟到报文失效

等待足够时间，降低旧连接中的延迟报文干扰后续同一四元组新连接的风险。

### 12.6 真题：2021 年

题目：

客户端主动发送 FIN，收到服务器 FIN 并回复最后 ACK 后，客户端进入什么状态？

答案：

$$
\boxed{TIME\text{-}WAIT}
$$

### 12.7 真题：2020 年，SYN 与 FIN 序号

题目：

甲建立 TCP 连接时：

    SYN seq=1000

关闭连接时：

    FIN seq=5001

求甲发送的应用数据字节数。

SYN 消耗一个序号。

因此第一个数据字节：

$$
1001
$$

FIN 之前最后一个数据字节：

$$
5000
$$

数据长度：

$$
5000-1001+1=4000
$$

答案：

$$
\boxed{4000B}
$$

也可以直接计算：

$$
5001-(1000+1)=4000
$$


## 十三、TCP 关闭连接时间计算

### 13.1 RTT 与单向传播时延

RTT 是往返时间。

在题目假设往返路径对称、忽略处理及发送时延时：

$$
T_{\text{单向}}=\frac{RTT}{2}
$$

注意：

真实网络的两个方向时延不一定相同。

408 的这种公式依赖理想化题设。

### 13.2 主动关闭方与被动关闭方

假设：

A 主动关闭。

B 被动关闭。

并且 B 收到 FIN 后可以立即发送 ACK 和自己的 FIN。

设 A 在：

$$
t=0
$$

发出 FIN。

则：

| 时刻 | 事件 |
|---|---|
| 0 | A 发 FIN |
| RTT/2 | B 收 FIN，回复 ACK+FIN |
| RTT | A 收到 FIN，发最后 ACK，进入 TIME-WAIT |
| 3RTT/2 | B 收到最后 ACK，进入 CLOSED |
| RTT+2MSL | A 退出 TIME-WAIT，进入 CLOSED |

所以：

被动关闭方最快进入 CLOSED：

$$
\boxed{T_B=\frac{3RTT}{2}}
$$

主动关闭方最快进入 CLOSED：

$$
\boxed{T_A=RTT+2MSL}
$$

以上公式不包含其他等待时间，且要求题目满足立即合并应答的条件。

### 13.3 真题：2022 年

已知：

$$
RTT=50ms
$$

$$
MSL=800ms
$$

客户端 C 主动关闭连接。

求从 C 发出 FIN 开始，C 和服务器 S 进入 CLOSED 的最短时间。

#### 客户端

$$
T_C=RTT+2MSL
$$

$$
=50+1600
$$

$$
\boxed{T_C=1650ms}
$$

#### 服务器

$$
T_S=\frac{3RTT}{2}
$$

$$
=\frac{3\times50}{2}
$$

$$
\boxed{T_S=75ms}
$$

答案：

$$
\boxed{1650ms,\ 75ms}
$$

### 13.4 模拟题：剩余 TIME-WAIT 时间

假设：

$$
RTT=100ms
$$

$$
MSL=500ms
$$

客户端主动关闭。

题目问：

服务器进入 CLOSED 后，客户端还需要多久才能进入 CLOSED？

#### 第一步

客户端发送最后 ACK 时进入 TIME-WAIT。

服务器收到这个 ACK 需要：

$$
RTT/2=50ms
$$

#### 第二步

客户端总等待时间：

$$
2MSL=1000ms
$$

#### 第三步

服务器 CLOSED 时，客户端已经等待 50ms。

因此剩余：

$$
1000-50
$$

$$
\boxed{950ms}
$$

#### 必须区分

题目可能问：

1. 从第一次 FIN 发出到主动方 CLOSED。
2. 从第一次 FIN 发出到被动方 CLOSED。
3. 从被动方 CLOSED 到主动方 CLOSED。

这三种题目的时间起点完全不同。


## 十四、TCP 滑动窗口

### 14.1 为什么需要滑动窗口？

假设 RTT 为：

$$
100ms
$$

每次只发送一个 1000B 数据段，然后等待 ACK。

发送一段需要经历一个往返确认过程。

发送效率会很低。

滑动窗口允许发送方：

**不必等待每个数据段的 ACK，就可以连续发送多个数据段。**

这就是流水线传输思想。

### 14.2 发送窗口的四个区域

发送方字节流可以划分为：

    ┌──────────┬─────────────┬─────────────┬─────────────┐
    │ 已确认数据 │ 已发送未确认 │ 可发送未发送 │ 暂时不可发送 │
    └──────────┴─────────────┴─────────────┴─────────────┘

其中：

    已发送未确认 + 可发送未发送

构成当前发送窗口。

如果收到新的有效 ACK：

发送窗口左边界向右移动。

已经确认的数据退出窗口。

新的待发送数据进入窗口。

这就是窗口滑动。

### 14.3 发送窗口的重要变量

TCP 发送端可用几个状态量描述：

`SND.UNA`：

最早尚未确认的字节序号。

`SND.NXT`：

下一个准备发送的新字节序号。

因此：

$$
FlightSize=SND.NXT-SND.UNA
$$

这里采用普通、未跨越序号回绕的教材场景。

`FlightSize` 表示已经发送但尚未确认的数据量。

### 14.4 接收窗口

接收方存在接收缓存。

假设接收缓存总容量：

$$
R
$$

目前缓存中尚未被应用取走的数据：

$$
B
$$

在简化模型下：

$$
\boxed{rwnd=R-B}
$$

如果应用一直不读取数据：

随着接收的数据增多：

$$
rwnd
$$

会越来越小。

当缓存满时：

$$
rwnd=0
$$


## 十五、流量控制

<Callout type="warn" title="窗口上限不等于新增可发送量">

发送窗口上限通常取 rwnd 和 cwnd 的较小值；还能发送多少新数据，还要扣除已发送但未确认的在途数据，并按题目模型处理接收窗口更新。

</Callout>


### 15.1 流量控制解决什么问题？

流量控制解决的是：

**发送方发送过快，接收方来不及接收或处理。**

例如：

发送方每秒能发送 100MB 数据。

接收方应用每秒只能处理 10MB。

如果无限制地发送，接收缓冲区就可能被占满。

TCP 使用接收窗口：

$$
rwnd
$$

限制发送方。

### 15.2 拥塞窗口与接收窗口

TCP 发送方还受到网络拥塞控制的限制。

因此有两个关键变量：

$$
rwnd
$$

接收窗口。

由接收方根据接收缓存空间决定。

$$
cwnd
$$

拥塞窗口。

由发送方根据网络反馈决定。

### 15.3 实际发送窗口公式

经典教材模型：

$$
\boxed{
W=\min(rwnd,cwnd)
}
$$

解释：

假设：

$$
rwnd=9000B
$$

$$
cwnd=6000B
$$

则：

$$
W=\min(9000,6000)
$$

$$
\boxed{W=6000B}
$$

虽然接收方允许 9000B，但网络拥塞控制只允许 6000B 的窗口额度。

### 15.4 最容易做错的公式

题目可能不是问：

发送窗口大小是多少？

而是问：

**此刻还能继续发送多少新数据？**

这时不能只计算：

$$
\min(rwnd,cwnd)
$$

还必须减去已经发送但尚未确认的数据。

因此：

$$
\boxed{
L_{\text{可新发}}
=
\max\left(
0,\min(rwnd,cwnd)-FlightSize
\right)
}
$$

严格使用该简化公式时，还要确认题目使用的窗口通告、在途量和窗口基准属于同一状态。

在复杂真实 TCP 场景中，还应考虑窗口右边界、发送缓存及其他限制。

### 15.5 典型例题

已知：

$$
rwnd=9000B
$$

$$
cwnd=6000B
$$

已经发送但尚未确认：

$$
FlightSize=4200B
$$

求还能继续发送多少字节。

#### 第一步：发送窗口上限

$$
W=\min(9000,6000)=6000B
$$

#### 第二步：扣除在途数据

$$
6000-4200=1800B
$$

答案：

$$
\boxed{1800B}
$$

如果：

$$
MSS=1000B
$$

题目问最多还能发送几个**完整 MSS** 数据段：

答案是：

$$
\boxed{1\text{ 个}}
$$

但如果允许发送不足 MSS 的短段，1800B 可以分成多个报文段发送。


## 十六、真题：2010 年 TCP 窗口

题目：

主机甲与乙已经建立 TCP 连接。

已知：

$$
MSS=1000B
$$

$$
cwnd=4000B
$$

甲连续发送两个完整 MSS 段。

随后收到第一个数据段的确认。

确认报文通告：

$$
rwnd=2000B
$$

求甲还能发送多少字节。

### 16.1 第一步：已经发送多少？

两个段：

$$
2\times1000=2000B
$$

### 16.2 第二步：确认了多少？

第一个段确认了：

$$
1000B
$$

因此还未确认：

$$
FlightSize=1000B
$$

### 16.3 第三步：计算窗口

$$
W=\min(4000,2000)=2000B
$$

### 16.4 第四步：扣除在途数据

$$
L=2000-1000
$$

$$
\boxed{L=1000B}
$$

答案：A。

#### 易错点

有人会认为：

    cwnd=4000

    rwnd=2000

所以还能发 2000B。

这是错误的。

因为其中已有 1000B 数据占用窗口。


## 十七、真题：2021 年发送序号范围

题目：

甲发送：

    seq=501
    数据长度=200B

之后收到乙发来的：

    ack=501
    rwnd=500B

求甲在没有收到新确认之前，还能继续发送的数据序号范围。

### 17.1 接收窗口范围

ACK=501 表示接收方仍然等待序号 501。

rwnd=500B。

因此接收窗口覆盖：

$$
501\sim1000
$$

### 17.2 已经发送的序号范围

甲之前发送：

$$
501\sim700
$$

这部分数据虽然尚未确认，但已经占据发送窗口。

### 17.3 可继续发送的范围

因此：

$$
\boxed{701\sim1000}
$$

答案：C。

注意：

这里的 ACK 没有向前推进，但通告了 500B 的窗口。

判断还能发送哪些字节，要同时考虑：

- 当前窗口左边界；

## 十八、零窗口与持续计时器

### 18.1 零窗口

如果：

$$
rwnd=0
$$

表示接收方当前没有空间继续接收普通新数据。

发送方应停止发送普通新数据。

但 TCP 连接没有断开。

### 18.2 为什么需要持续计时器？

考虑：

    接收方缓存满

        ↓

    接收方发送 rwnd=0

        ↓

    发送方停止发送

        ↓

    接收方应用读取数据

        ↓

    接收方发送窗口更新

        ↓

    窗口更新报文丢失

此时：

发送方以为窗口仍为 0。

接收方以为已经通知发送方窗口恢复。

双方可能长期等待。

因此 TCP 使用持续计时器：

$$
Persist\ Timer
$$

发送零窗口探测。

目的是获知接收窗口是否重新打开。

### 18.3 零窗口与拥塞的区别

零窗口：

$$
rwnd=0
$$

表示接收端暂时没有可用接收缓存。

拥塞窗口缩小：

$$
cwnd\downarrow
$$

表示发送端根据网络反馈收紧发送限制。

二者不是同一问题。


## 十九、TCP 重传机制

TCP 主要使用两种经典重传机制：

1. 超时重传。
2. 快速重传。

### 19.1 超时重传

发送端发送数据后，需要等待对应的确认。

如果一定时间内没有得到足够的确认：

触发 RTO。

RTO：

$$
Retransmission\ Timeout
$$

即重传超时时间。

发送端重传相关尚未确认的数据。

#### 超时不一定意味着数据丢失

可能原因：

- 数据确实丢失。
- ACK 丢失。
- RTT 突然增大。
- 网络严重排队。

因此超时只是一种恢复触发信号。

### 19.2 快速重传

假设：

    段1：正常收到

    段2：丢失

    段3：正常收到

    段4：正常收到

    段5：正常收到

接收方发现缺口后，会持续确认同一个缺失位置。

发送端收到足够多的重复 ACK 后，可以判断前面的数据可能丢失。

典型触发条件：

$$
\boxed{3\text{ 个重复 ACK}}
$$

随后立即重传相关数据，不必等待 RTO。

### 19.3 三个重复 ACK 怎么计数？

特别注意：

**第一次收到某个 ACK 值，不属于后续的重复 ACK。**

例如：

    ACK=1001    第一次

    ACK=1001    重复1

    ACK=1001    重复2

    ACK=1001    重复3

收到第三个重复 ACK 时，触发快速重传。

所以常见图示中一共出现四次相同的 ACK 值。

### 19.4 真题：2019 年

题目场景：

客户端在 $t_0$ 第一次收到：

    ACK=100

随后发送：

    seq=100

但该段丢失。

后续更高序号的段正常到达接收端。

重复 ACK 依次于：

$$
t_1,\ t_2,\ t_3
$$

到达发送端。

问什么时候重传 seq=100？

由于：

- $t_0$：首次 ACK。
- $t_1$：第一个重复 ACK。
- $t_2$：第二个重复 ACK。
- $t_3$：第三个重复 ACK。

因此：

$$
\boxed{t_3}
$$

答案：C。


## 二十、TCP RTT 估计与 RTO

TCP 的 RTT 会波动。

因此不能总使用一个固定的超时时间。

教材常见平滑 RTT 估计：

$$
EstimatedRTT_{\text{new}}
=
(1-\alpha)EstimatedRTT_{\text{old}}
+\alpha SampleRTT
$$

其中常见：

$$
\alpha=0.125
$$

RTT 偏差估计：

$$
DevRTT_{\text{new}}
=
(1-\beta)DevRTT_{\text{old}}
+\beta
\left|
SampleRTT-EstimatedRTT_{\text{new}}
\right|
$$

常见：

$$
\beta=0.25
$$

随后：

$$
\boxed{
RTO=EstimatedRTT+4DevRTT
}
$$

实际 TCP 还涉及 RTO 下限、退避、重传样本处理等规则。

考场若给出具体公式和更新顺序，应严格按题设计算。

### 20.1 计算示例

假设：

$$
EstimatedRTT_{\text{old}}=100ms
$$

$$
DevRTT_{\text{old}}=20ms
$$

$$
SampleRTT=140ms
$$

第一步：

$$
EstimatedRTT_{\text{new}}
=
0.875\times100+0.125\times140
$$

$$
=105ms
$$

第二步：

$$
DevRTT_{\text{new}}
=
0.75\times20+0.25\times|140-105|
$$

$$
=15+8.75
$$

$$
=23.75ms
$$

第三步：

$$
RTO=105+4\times23.75
$$

$$
\boxed{RTO=200ms}
$$

注意：

题目问 RTO 时，不能把 RTT 直接当作 RTO。


## 二十一、TCP 拥塞控制总框架

这是第五章计算题最多、最容易出现连续错误的部分。

### 21.1 什么叫网络拥塞？

假设：

网络链路最多能处理：

$$
10Mb/s
$$

但大量发送方合计向其中注入：

$$
100Mb/s
$$

数据。

路由器队列可能不断增长。

最终出现：

- 排队延迟增加；
- 缓冲区溢出；
- 丢包；
- 重传增多；
- 有效吞吐量下降。

TCP 通过调整拥塞窗口，控制发送到网络中的未确认数据量。

### 21.2 三个核心变量

#### MSS

最大 TCP 数据段长度。

#### cwnd

拥塞窗口。

由发送方维护。

#### ssthresh

慢开始门限。

决定经典模型下慢开始与拥塞避免的阶段切换。

### 21.3 四种经典机制

| 机制 | 主要作用 |
|---|---|
| 慢开始 | 快速探测网络容量 |
| 拥塞避免 | 逐步增加发送能力 |
| 快速重传 | 尽早恢复疑似丢失的数据 |
| 快速恢复 | 避免局部丢包后过度降低发送能力 |

<Tab value="慢开始">
## 二十二、慢开始

### 22.1 慢开始的规则

在经典 408 简化模型中：

初始：

$$
cwnd=1MSS
$$

如果没有丢包，且接收窗口不限制发送，拥塞窗口大约每经过一个 RTT 翻倍。

即：

$$
1\rightarrow2\rightarrow4\rightarrow8\rightarrow16
$$

单位为 MSS。

### 22.2 为什么叫慢开始，却增长很快？

慢开始是相对于一开始直接发送大量数据而言的。

它从较小窗口开始探测网络容量。

但其增长呈近似指数规律。

因此：

**慢开始不是线性增长，而是指数增长。**

### 22.3 每收到一个 ACK，窗口是否翻倍？

不是。

在经典模型中：

每收到一个确认新数据的 ACK，慢开始窗口通常增加约 1 MSS。

如果当前：

$$
cwnd=4MSS
$$

这一轮发出 4 个 MSS，收到四个相应的新数据确认。

则：

$$
4+1+1+1+1=8MSS
$$

所以从 RTT 轮次角度看，窗口近似翻倍。

注意：

真实实现受延迟 ACK、初始窗口、字节计数等机制影响，并非所有 TCP 都严格遵循 $1,2,4,8$。

408 计算题以题设规定的教材模型为准。

### 22.4 慢开始门限

如果：

$$
ssthresh=16MSS
$$

则经典轨迹为：

$$
1\rightarrow2\rightarrow4\rightarrow8\rightarrow16
$$

当窗口达到门限后，转入拥塞避免。

之后：

$$
16\rightarrow17\rightarrow18\rightarrow19
$$

不能继续简单翻倍到 32。

</Tab>
<Tab value="拥塞避免">
## 二十三、拥塞避免

### 23.1 拥塞避免的增长方式

拥塞避免阶段采用近似线性增长。

经典 408 模型：

$$
\boxed{
cwnd\text{ 每经过一个 RTT 增加 }1MSS
}
$$

例如：

$$
cwnd=10MSS
$$

则：

$$
10\rightarrow11\rightarrow12\rightarrow13
$$

### 23.2 为什么是线性增长？

慢开始阶段增长较快，适用于初期探测。

达到门限以后，为避免迅速压垮网络，需要更谨慎地增长。

这就是加性增大思想。

### 23.3 拥塞避免逐 ACK 公式

如果用 MSS 为单位表示窗口为 $w$，经典近似规则为：

$$
w_{\text{new}}=w+\frac1w
$$

在一个 RTT 内，如果大约收到 $w$ 个独立新数据确认，则总增量约为 1 MSS。

因此：

$$
w\rightarrow w+1
$$

</Tab>
</Tabs>

## 二十四、超时后的拥塞窗口变化

### 24.1 经典教材规则

如果发生 RTO 超时：

1. 慢开始门限通常设为拥塞前窗口的一半。
2. 拥塞窗口重置为 1 MSS。
3. 重新进入慢开始。

即：

$$
ssthresh_{\text{new}}
=
\frac{cwnd_{\text{before}}}{2}
$$

$$
\boxed{
cwnd_{\text{new}}=1MSS
}
$$

这里是经典 408 简化模型。

实际 TCP 规范常将门限计算与实际在途数据量联系起来，并有最小门限限制。

### 24.2 例题

假设：

$$
cwnd=16MSS
$$

发生超时。

则：

$$
ssthresh=8MSS
$$

$$
cwnd=1MSS
$$

之后：

$$
1\rightarrow2\rightarrow4\rightarrow8
$$

达到新门限后：

$$
8\rightarrow9\rightarrow10
$$

### 24.3 真题：2009 年

题目：

$$
MSS=1KB
$$

当：

$$
cwnd=16KB
$$

发生超时。

之后四个 RTT 都成功传输。

求第 4 个 RTT 结束后的拥塞窗口。

超时后：

$$
ssthresh=8KB
$$

$$
cwnd=1KB
$$

逐轮计算：

| RTT | 结束后的 cwnd |
|---|---|
| 第1轮 | 2KB |
| 第2轮 | 4KB |
| 第3轮 | 8KB |
| 第4轮 | 9KB |

答案：

$$
\boxed{9KB}
$$

#### 为什么不是 16KB？

因为达到：

$$
ssthresh=8KB
$$

后，不能继续按慢开始翻倍，而应进入拥塞避免。


## 二十五、快速重传与快速恢复

<Callout type="idea" title="区分超时与三个重复 ACK">

教材题里超时通常降低门限并重新慢开始；收到三个重复 ACK 的处理还取决于采用 Tahoe、Reno 或题目明确给定的模型，不能直接套同一条轨迹。

</Callout>


### 25.1 三个重复 ACK 后的处理

经典 Reno 简化模型中：

收到 3 个重复 ACK：

先快速重传推测丢失的数据段。

然后调整慢开始门限。

教材常简化为：

$$
ssthresh=\frac{cwnd}{2}
$$

快速恢复结束后：

$$
cwnd=ssthresh
$$

随后进入拥塞避免。

### 25.2 例题

发生三个重复 ACK 时：

$$
cwnd=16MSS
$$

则简化模型：

$$
ssthresh=8MSS
$$

$$
cwnd=8MSS
$$

之后：

$$
8\rightarrow9\rightarrow10
$$

### 25.3 Reno 的更精确规则

经典 Reno 快速恢复过程中，收到第三个重复 ACK 后，可能临时设置：

$$
cwnd=ssthresh+3MSS
$$

随后根据额外的重复 ACK、恢复 ACK 等事件更新状态。

所以：

教材题中直接将 cwnd 减半，与真实 Reno 快速恢复的内部状态并不完全相同。

### 25.4 Tahoe 与 Reno

| TCP 模型 | 三个重复 ACK 后 |
|---|---|
| Tahoe | 快速重传后重新慢开始 |
| Reno | 快速重传并进入快速恢复 |

因此解题时必须判断采用哪种拥塞控制模型。

### 25.5 超时与三个重复 ACK 对比

| 事件 | 经典模型中的处理 |
|---|---|
| RTO 超时 | cwnd 降到 1 MSS，重新慢开始 |
| 三个重复 ACK | 快速重传，Reno 通过快恢复调整窗口 |
| 无拥塞 | 根据当前阶段增长窗口 |

最重要的区别：

**不能把三个重复 ACK 一律当成超时。**

原拥塞窗口：

3RTT

## 二十七、真题：2020 年最长增长时间

题目：

$$
MSS=1KB
$$

$$
RTT=2ms
$$

## 三十、带宽时延积与窗口吞吐率

### 30.1 窗口与吞吐率

假设有效发送窗口为：

$$
W
$$

往返时间为：

$$
RTT
$$

在理想稳定、窗口限制占主导的模型中：

$$
\boxed{
R\approx\frac{W}{RTT}
}
$$

例如：

$$
W=10000B
$$

$$
RTT=0.1s
$$

则：

$$
R\approx\frac{10000}{0.1}
$$

$$
=100000B/s
$$

转换成 bit/s：

$$
R=800000bit/s
$$

即：

$$
\boxed{0.8Mb/s}
$$

注意：

这是窗口限制下的近似速率，不是物理链路的最大可能速率。

### 30.2 带宽时延积 BDP

带宽时延积：

$$
\boxed{BDP=B\times RTT}
$$

其中：

- $B$：链路瓶颈带宽。
- $RTT$：往返时间。

BDP 可以理解为：

为了充分利用链路，网络路径中大约需要维持多少在途数据。

#### 例题

$$
B=100Mb/s
$$

$$
RTT=40ms
$$

则：

$$
BDP=100\times10^6\times0.04
$$

$$
=4\times10^6bit
$$

换算为字节：

$$
BDP=\frac{4\times10^6}{8}
$$

$$
\boxed{500000B}
$$

即约 500KB（十进制）。

如果有效窗口远小于这个值，即使链路带宽很高，吞吐率也可能被窗口限制。

### 30.3 速率题两种计算方法

#### 方法一：长期稳态窗口限制

$$
R\approx\frac{W}{RTT}
$$

#### 方法二：有限文件平均速率

$$
\boxed{
R_{\text{avg}}
=
\frac{\text{文件有效数据比特数}}{\text{题目规定的总时间}}
}
$$

第二类才是 408 综合大题常见的计算口径。

建连是否计入时间、最后 ACK 是否计入时间，都要看题目明确的起止时刻。


## 三十一、综合大题：2012 年 TCP 抓包

本题综合考查：

- IPv4 首部。
- TCP 三次握手。
- TCP 序号和 ACK。
- 以太网最小帧。

### 31.1 题目条件

主机 H：

    192.168.0.8

服务器 S：

    211.68.71.80

抓包得到五个 IP 分组。

要求：

1. 判断哪些由 H 发送。
2. 找出 TCP 三次握手。
3. 判断哪些 IP 分组封装以太网帧时需要填充。
4. 判断服务器收到的应用数据字节数。
5. 计算经过的路由器数量。

### 31.2 第一步：识别发送方向

IPv4 首部中：

源 IP 位于第 12～15 字节。

目的 IP 位于第 16～19 字节。

通过源 IP 判断：

H 发出的分组：

$$
\boxed{1,3,4}
$$

S 发出的分组：

$$
\boxed{2,5}
$$

### 31.3 第二步：判断三次握手

利用 TCP 控制位：

第1包：

    SYN=1

第2包：

    SYN=1
    ACK=1

第3包：

    ACK=1

因此三次握手：

$$
\boxed{1,2,3}
$$

判断时还应核对 ACK 是否为对方 SYN 序号加 1。

### 31.4 第三步：计算以太网填充

Ethernet II 最小帧长：

$$
64B
$$

其中：

以太网首部：

$$
14B
$$

FCS：

$$
4B
$$

因此最小数据字段长度：

$$
64-14-4=46B
$$

题目中第3包、第5包 IP 总长度：

$$
40B
$$

所以需要填充：

$$
46-40=6B
$$

答案：

$$
\boxed{3,5\text{ 号包各填充 }6B}
$$

注意：

填充数据属于数据链路层，不应算入 IP 总长度或 TCP 应用数据长度。

### 31.5 第四步：计算应用数据

服务器返回的累计确认号：

    0x846B41D6

客户端的第一个数据字节序号：

    0x846B41C6

两者相减：

$$
\texttt{0x846B41D6}
-
\texttt{0x846B41C6}
=
\texttt{0x10}
$$

$$
\boxed{16B}
$$

### 31.6 第五步：计算路由器数量

服务器发出时：

$$
TTL=64
$$

主机 H 收到时：

$$
TTL=49
$$

因此：

$$
64-49=15
$$

答案：

$$
\boxed{15\text{ 台路由器}}
$$

前提是对照的是同一个 IP 数据报。

二层交换机不使 IP TTL 减 1。

### 31.7 这类抓包题的通用步骤

1. 根据 IPv4 首字节确定 IP 首部长度。
2. 找协议号判断 TCP、UDP 或 ICMP。
3. 根据源 IP、目的 IP 判断方向。
4. 找 TCP 控制位判断握手与挥手。
5. 找 TCP 序号、确认号。
6. 根据 IP 总长度和首部长度求 TCP 数据量。
7. 用以太网最小数据字段判断填充。
8. 若比较同一 IP 数据报的 TTL，可计算路由器转发次数。


## 三十二、综合大题：2016 年流量控制与拥塞控制

这道题非常重要。

它把：

- MSS

- 拥塞窗口

- TCP 释放连接

全部结合在一起。

### 32.1 已知条件

客户端 H3 建立 TCP 连接。

初始 SYN 序号：

$$
100
$$

MSS：

$$
1KB
$$

接收方缓存：

$$
20KB
$$

初始慢开始门限：

$$
32KB
$$

RTT：

$$
200ms
$$

服务器接收数据后：

**应用程序始终不从缓存中读取数据。**

服务器对每个收到的数据段立即发送确认。

### 32.2 第一问：第二次握手

客户端第一次握手：

    SYN=1
    seq=100

服务器第二次握手：

    SYN=1
    ACK=1
    ack=101

答案：

$$
\boxed{SYN=1,\ ACK=1,\ ack=101}
$$

### 32.3 第二问：收到第8个数据 ACK

题目要求分别计算：

- 接收窗口。
- 拥塞窗口。
- 发送窗口。

#### 接收窗口

服务器总缓存：

$$
20KB
$$

收到8个新的 1KB 数据段：

$$
8KB
$$

应用没有读取。

因此：

$$
rwnd=20-8
$$

$$
\boxed{rwnd=12KB}
$$

#### 拥塞窗口

初始：

$$
cwnd=1KB
$$

慢开始阶段，每个确认新数据的逐段 ACK 增加 1 MSS。

收到第8个新数据 ACK 后：

$$
cwnd=1+8
$$

$$
\boxed{cwnd=9KB}
$$

#### 发送窗口

$$
W=\min(12,9)
$$

$$
\boxed{W=9KB}
$$

#### 为什么不是 8KB？

因为题目问的是收到第8个数据 ACK 后的窗口。

初始窗口本身已经是：

$$
1KB
$$

收到八个新数据 ACK，分别增加 1KB。

因此：

$$
1+8=9KB
$$

### 32.4 第三问：缓存什么时候满？

服务器缓存：

$$
20KB
$$

慢开始发送：

    第1轮：1KB

    第2轮：2KB

    第3轮：4KB

    第4轮：8KB

前四轮合计：

$$
1+2+4+8=15KB
$$

还剩：

$$
20-15=5KB
$$

第五轮最多还能接收：

$$
5KB
$$

之后缓存满：

$$
rwnd=0
$$

### 32.5 下一个待发送数据字节序号

SYN 初始序号：

$$
100
$$

第一个应用数据字节：

$$
101
$$

已发送并确认的数据：

$$
20\times1024=20480B
$$

所以下一个数据字节序号：

$$
101+20480
$$

$$
\boxed{20581}
$$

### 32.6 平均数据传输速率

从发送第一批数据到收到零窗口通知：

$$
5RTT
$$

因此：

$$
T=5\times200ms=1000ms
$$

$$
T=1s
$$

有效应用数据：

$$
20\times1024=20480B
$$

转为 bit：

$$
20480\times8=163840bit
$$

平均速率：

$$
R=\frac{163840}{1}
$$

$$
\boxed{R=163840bit/s}
$$

即：

$$
\boxed{163.84kb/s}
$$

这里的小写 `kb/s` 采用十进制：

$$
1kb/s=1000bit/s
$$

### 32.7 第四问：服务器释放连接的时间

客户端在时刻：

$$
t
$$

发起关闭。

服务器没有待发送数据，并可立即回复。

最短关闭时间：

$$
T=\frac{3RTT}{2}
$$

$$
=\frac{3\times200}{2}
$$

$$
\boxed{300ms}
$$

注意：

服务器是被动关闭方。

客户端才需要经历典型的 TIME-WAIT 等待。

所以不能把客户端的 $2MSL$ 直接加到服务器的关闭时间上。

### 32.8 本题必须掌握的三个时间概念

第一：

收到第8个 ACK，是按 ACK 数量计算窗口。

第二：

接收缓存填满，是按 RTT 发送轮次计算总数据量。

第三：

释放连接时间，是按 FIN/ACK 的传播过程计算。

三种计数方式必须分开。

\boxed{\texttt{0x5B9FF71D}}
$$

### 35.2 第二问：不同应用数据字节总量

题目中的关键数据：

| 报文 | TCP 数据长度 | 起始序号 |
|---|---:|---|
| 5 | 16B | 0x2268B991 |
| 7 | 16B | 0x2268B9A1 |
| 8 | 32B | 0x2268B9A1 |

注意：

报文7和报文8具有相同的起始序号。

报文8前16B与报文7的数据序号范围重叠。

因此不能直接把：

$$
16+16+32=64B
$$

当成不同应用字节总量。

正确计算：

$$
16+16+(32-16)
$$

$$
\boxed{48B}
$$

#### 本题的重要思想

TCP 根据字节序号识别数据。

是否属于相同的应用数据字节，主要看字节序号范围是否重叠。

不能只根据：

- 报文段数量
- 数据内容是否相同
- TCP 负载长度总和

来判断不同应用字节数量。

### 35.3 第三问：累计 ACK

服务器正确收到所有相关数据后：

下一个期望字节为：

    0x2268B9C1

因此：

$$
\boxed{ACK=\texttt{0x2268B9C1}}
$$

### 35.4 第四问：还能发送多少新数据？

服务器最近一次通告：

$$
rwnd=8192B
$$

客户端还有：

$$
32B
$$

数据已经发送但尚未收到相应的新确认。

题目明确忽略拥塞窗口限制。

因此：

$$
L_{\text{new}}=8192-32
$$

$$
\boxed{8160B}
$$

#### 关键判断

服务器已经收到数据，不等于客户端已经收到服务器的 ACK。

在 ACK 尚未抵达客户端之前，这些已发送数据仍然占据发送端的未确认窗口。

## 三十七、综合题专用：三本账本法

遇到复杂 TCP 大题，建议一定分开记录三类信息。

### 37.1 序号账本

记录：

- 本方向 SYN 初始序号。
- 第一个应用数据序号。
- 每段数据起始序号。
- 每段数据长度。
- 当前 ACK。
- FIN 序号。

例如：

| 事件 | seq/ack |
|---|---|
| SYN | seq=1000 |
| 首数据 | seq=1001 |
| 发送500B后 | 下一seq=1501 |
| 再发送500B后 | 下一seq=2001 |
| FIN | seq=2001 |
| 对FIN确认 | ack=2002 |

### 37.2 窗口账本

记录：

- rwnd
- cwnd
- ssthresh
- FlightSize
- 当前发送窗口
- 还能发送多少新数据

推荐表格：

| 时刻 | rwnd | cwnd | FlightSize | 可新发 |
|---|---:|---:|---:|---:|
| t1 | 8000 | 4000 | 0 | 4000 |
| t2 | 8000 | 4000 | 2000 | 2000 |
| t3 | 3000 | 5000 | 1000 | 2000 |
| t4 | 0 | 6000 | 0 | 0 |

这里按简化的同一窗口基准进行演示。

### 37.3 时间账本

记录：

- 握手时间。
- 每轮 RTT。
- 每轮发送数据段数。
- 最后一次数据 ACK。
- FIN/ACK 时间。
- TIME-WAIT。

例如：

| RTT 轮次 | cwnd | 实际发送 |
|---|---:|---:|
| 1 | 1MSS | 1MSS |
| 2 | 2MSS | 2MSS |
| 3 | 4MSS | 4MSS |
| 4 | 5MSS | 5MSS |

必须分清：

收到第几个 ACK，与经过第几个 RTT，不是相同的概念。


## 三十八、综合计算通用解题模板

### 38.1 第一步：确定 TCP 建连

读取：

$$
ISN_A,\ ISN_B
$$

得到：

$$
seq_{A,\text{first data}}=ISN_A+1
$$

$$
seq_{B,\text{first data}}=ISN_B+1
$$

### 38.2 第二步：计算应用数据段数

已知文件大小：

$$
F
$$

MSS：

$$
M
$$

则最少数据段数：

$$
\boxed{
N=\left\lceil\frac FM\right\rceil
}
$$

其中最后一段可能不足 MSS。

### 38.3 第三步：建立窗口轨迹

记录：

$$
cwnd_0
$$

$$
ssthresh_0
$$

$$
rwnd
$$

无丢包时，按题目给定的慢开始和拥塞避免规则更新拥塞窗口。

如果接收窗口也限制发送，每轮可发送量还需要受到：

$$
\min(cwnd,rwnd)
$$

约束。

### 38.4 第四步：计算每轮数据量

如果第 $i$ 轮实际发送：

$$
n_i
$$

个完整 MSS 段，则该轮数据量：

$$
D_i=n_iMSS
$$

累计数据：

$$
D_{\text{total}}=\sum_iD_i
$$

当累计数据达到文件长度时，停止继续分配新数据。

### 38.5 第五步：计算时间

若：

- 建连需要 1RTT；
- 数据发送并确认需要 $k$ 轮 RTT；
- 不考虑挥手；

则典型模型：

$$
\boxed{
T=(1+k)RTT
}
$$

如果时间起点是已经建连后的首段发送时刻，则通常：

$$
T=kRTT
$$

具体还要考虑题目是否允许第三次握手携带数据。

### 38.6 第六步：计算平均速率

$$
\boxed{
R=\frac{8F}{T}
}
$$

其中：

- $F$：文件字节数。
- $T$：秒。
- $R$：bit/s。

### 38.7 第七步：计算连接关闭

若由发送方主动关闭：

先确定：

$$
seq_{FIN}
$$

再确定：

$$
ACK_{FIN}=seq_{FIN}+1
$$

最后根据题目终点判断是否要计算：

$$
2MSL
$$

## 四十、本章高频易错点总整理

### 40.1 端口与连接

错误：

一个 TCP 端口只能对应一条连接。

正确：

多个连接可以使用同一个服务器端口，只要四元组不同。

### 40.2 UDP 与可靠性

错误：

UDP 有检验和，所以提供可靠传输。

正确：

UDP 本身不提供可靠交付保证。

### 40.3 UDP 长度

错误：

UDP 长度字段只包括数据。

正确：

UDP 长度包括 8B 首部和数据。

### 40.4 伪首部

错误：

伪首部会作为 UDP 或 TCP 数据发送。

正确：

伪首部只用于计算检验和。

### 40.5 TCP 字节流

错误：

一次应用发送一定对应一个 TCP 段。

正确：

TCP 不保留应用消息边界。

### 40.6 MSS 与 MTU

错误：

MSS 等于整个 TCP 报文段长度。

正确：

MSS 主要限制 TCP 数据部分。

### 40.7 序号与确认号

错误：

ACK=1001 表示已经收到了 1001B 数据。

正确：

ACK=1001 表示下一个期望字节序号为 1001。

### 40.8 SYN 与 FIN

错误：

SYN 和 FIN 不带数据，所以不消耗序号。

正确：

SYN、FIN 各消耗一个序号。

### 40.9 纯 ACK

错误：

纯 ACK 必须让本方向 seq 加 1。

正确：

纯 ACK 通常不消耗新序号。

### 40.10 累计确认

错误：

接收方收到较高序号的段，ACK 必须立即增加。

正确：

如果前面存在缺口，累计 ACK 不能越过缺口。

### 40.11 ACK 丢失

错误：

一个 ACK 丢失必然重传对应数据。

正确：

后续较大的累计 ACK 可能覆盖该确认。

### 40.12 三次握手

错误：

第三次握手一定不能携带应用数据。

正确：

第三次握手可以携带数据。

### 40.13 四次挥手

错误：

主动关闭方永远是客户端。

正确：

任意一方都可以主动关闭。

### 40.14 TIME-WAIT

错误：

服务器一定等待 2MSL。

正确：

典型情况下主动关闭方进入 TIME-WAIT。

### 40.15 rwnd 与 cwnd

错误：

TCP 首部 Window 字段表示 cwnd。

正确：

TCP 首部 Window 字段通告接收窗口 rwnd。

### 40.16 发送窗口与可发送量

错误：

还能发送的数据量恒等于：

$$
\min(rwnd,cwnd)
$$

正确：

在经典同一窗口基准下，还要扣除尚未确认的在途数据。

### 40.17 零窗口

错误：

rwnd=0 表示连接已经断开。

正确：

零窗口表示接收方暂时不能接收普通新数据。

### 40.18 慢开始

错误：

慢开始每 RTT 线性增加 1MSS。

正确：

经典模型下慢开始近似每 RTT 翻倍。

### 40.19 拥塞避免

错误：

拥塞避免每 RTT 翻倍。

正确：

经典模型下大约每 RTT 增加 1MSS。

### 40.20 超时与快重传

错误：

超时与三个重复 ACK 之后的窗口变化完全相同。

正确：

它们属于不同的拥塞反馈，具体处理依赖 TCP 算法和题设。

### 40.21 RTT 与 ACK

错误：

收到第8个 ACK，意味着已经经过8个 RTT。

正确：

一个 RTT 内可能收到多个 ACK。

### 40.22 平均速率

错误：

文件大小除以 RTT 就一定得到平均速率。

正确：

必须先求整个题目规定的传输时间，再用有效数据总量除以该时间。

## 四十二、考前复习建议

### 第一阶段：先掌握最基础的概念

要求能够准确解释：

- UDP 与 TCP 的区别。
- TCP 端口和连接四元组。
- UDP 首部与检验和。
- TCP 首部。
- seq、ack、SYN、FIN。
- rwnd、cwnd、ssthresh。

这一阶段最重要的是概念不能混淆。

### 第二阶段：专练 TCP 序号题

应熟练完成：

1. SYN 初始序号求首数据序号。
2. 根据数据长度求 ACK。
3. 根据 ACK 反推已确认数据量。
4. 根据 FIN 反推数据字节数。
5. 双向 seq 与 ack 的独立计算。
6. 乱序或丢包后的累计确认。
7. 重传数据的序号范围去重。

要求看到题目后能立即列出字节范围。

### 第三阶段：专练窗口计算

重点练：

- 接收缓存剩余量。
- cwnd 更新。
- rwnd 更新。
- 实际发送窗口。
- 在途未确认数据。
- 还能发送多少新数据。
- 零窗口探测。

尤其不能把：

$$
\min(rwnd,cwnd)
$$

直接当成每道题的最终答案。

### 第四阶段：专练拥塞窗口轨迹

应该能在纸上快速写出：

    初始门限16：

    1 → 2 → 4 → 8 → 16

    进入拥塞避免：

    16 → 17 → 18 → 19

    若在20超时：

    ssthresh=10

    cwnd=1

    之后：

    1 → 2 → 4 → 8 → 10 → 11 …

这里到门限附近的增长应遵守题目具体规定，不能盲目越过门限继续翻倍。

### 第五阶段：集中训练综合大题

推荐顺序：

1. 2012 年抓包、握手与序号题。
2. 2016 年流量控制与接收缓存题。
3. 2023 年 FTP、拥塞窗口与传输速率题。

掌握这些题型后，应能够独立完成大部分常规 TCP 综合计算。


## 四十三、全章最终总结

TCP 的所有核心机制，都可以围绕以下五句话理解。

**第一句：序号解决顺序问题。**

TCP 给每个应用数据字节编号，能够识别数据位置、乱序、重复和缺失。

**第二句：ACK 与重传解决可靠传输问题。**

累计确认告诉发送方哪些字节已经连续收到。

超时重传和快速重传用于恢复丢失数据。

**第三句：rwnd 解决接收方处理能力问题。**

接收方根据缓存空间控制发送方，不让发送方无限制地注入新数据。

**第四句：cwnd 解决网络拥塞问题。**

发送方根据网络反馈，通过慢开始、拥塞避免和丢包恢复调整拥塞窗口。

**第五句：握手与挥手管理 TCP 连接生命周期。**

三次握手同步初始序号并建立连接。

四次挥手分别关闭两个方向的数据流。

TIME-WAIT 用于处理最后确认重传和旧报文残留风险。

整章最核心的综合计算关系为：

$$
\boxed{
W=\min(rwnd,cwnd)
}
$$

$$
\boxed{
L_{\text{new}}
=
\max(0,W-FlightSize)
}
$$

$$
\boxed{
ACK=\text{下一个期望收到的字节序号}
}
$$

做 TCP 综合大题时，始终记住：

**先建立序号账本，再建立窗口账本，最后建立 RTT 时间账本。**

这三个账本分清楚，TCP 综合题的绝大多数计算就能转化为清晰的加减法、分段计数和时间统计。
