### 1.3 最重要的三个公式
整章的综合计算，首先记住：

公式一：累计确认号

$$
\boxed{ACK=\text{下一个期望接收的字节序号}}
$$

公式二：发送窗口上限

$$
\boxed{W=\min(rwnd,cwnd)}
$$

公式三：当前还能发送的新数据量

$$
\boxed{L_{\text{new}}=\max(0,W-FlightSize)}
$$

其中：

- $rwnd$：接收方通告的接收窗口。
- $cwnd$：发送方维护的拥塞窗口。
- $FlightSize$：已经发送、但尚未被确认的在途数据量。

注意，第二个公式求的是窗口约束，第三个才是在教材简化模型下当前还能发送的新数据量。这是本章综合题最容易混淆的区别之一。

## 二、传输层基础：TCP 和 UDP 为什么存在？
### 2.1 传输层的作用
先考虑这样一个问题。

你的电脑同时运行：

- 浏览器；
- 微信；
- 在线游戏；
- 文件下载程序。

网络层 IP 协议可以把数据报送到你的电脑。

但是到了电脑以后，究竟应该把数据交给浏览器，还是交给微信？

这就需要传输层。

网络层解决主机到主机的通信问题，传输层解决进程到进程的通信问题。

| 层次    | 主要通信对象       | 主要标识       |
| ----- | ------------ | ---------- |
| 数据链路层 | 相邻节点或网络接口    | MAC 地址     |
| 网络层   | 源主机与目的主机     | IP 地址      |
| 传输层   | 源应用端点与目的应用端点 | 端口号、Socket |
| 应用层   | 具体应用服务       | 应用层协议      |

传输层协议主要运行在通信的两个端系统中。普通中间路由器通常不会替通信双方维护 TCP 连接状态。

### 2.2 端口号
TCP 和 UDP 的端口号都是 16 位。

因此端口号的取值范围为：

$$
0\sim 2^{16}-1=65535
$$

共有：

$$
2^{16}=65536
$$

种可能取值。

端口号可以理解为应用通信端点的逻辑编号，而不是计算机上的物理接口。

#### 端口号分类
| 端口范围        | 类型      | 说明             |
| ----------- | ------- | -------------- |
| 0～1023      | 熟知端口    | HTTP、DNS 等常见服务 |
| 1024～49151  | 注册端口    | 注册应用服务         |
| 49152～65535 | 动态/私有端口 | 常用于客户端临时端口     |

常见服务端口包括：

| 应用协议            | 常见端口 | 传输协议              |
| --------------- | ---- | ----------------- |
| HTTP            | 80   | TCP               |
| HTTPS           | 443  | TCP，也可基于 UDP/QUIC |
| FTP 控制连接        | 21   | TCP               |
| FTP 主动模式服务端数据端口 | 20   | TCP               |
| SSH             | 22   | TCP               |
| SMTP            | 25   | TCP               |
| DNS             | 53   | UDP/TCP           |
| DHCP 服务器        | 67   | UDP               |
| DHCP 客户端        | 68   | UDP               |
| POP3            | 110  | TCP               |
| IMAP            | 143  | TCP               |

这里特别要注意：TCP 和 UDP 的端口号属于各自的协议空间。

TCP 53 和 UDP 53 不是同一个传输层通信端点。

### 2.3 Socket 与 TCP 四元组
一个通信端点可以用 IP 地址和端口号表示：

$$
Socket=(IP,\ Port)
$$

例如：

```text
192.168.1.10:50000
```

代表某个 IP 地址上的一个传输层通信端点。

一条 TCP 连接由四元组唯一标识：

$$
\boxed{ (\text{源IP},\text{源端口},\text{目的IP},\text{目的端口}) }
$$

例如：

```text
客户端A：
192.168.1.10:50000

服务器：
10.0.0.1:80
```

另一台客户端：

```text
客户端B：
192.168.1.20:50001

服务器：
10.0.0.1:80
```

服务器的目的端口都是 80，但两条 TCP 连接的四元组不同，因此能够同时存在。

常考陷阱：一个服务器端口是否只能建立一条 TCP 连接？

答案：不是。

服务器可以通过同一个监听端口同时服务多个客户端。

### 2.4 复用与分用
复用发生在发送端：

```text
浏览器 ─┐
微信   ─┼──→ 传输层 ──→ 网络层
游戏   ─┘
```

多个应用进程的数据交给传输层统一向下发送。

分用发生在接收端：

```text
               ┌──→ 浏览器
网络层 → 传输层 ┼──→ 微信
               └──→ 游戏
```

传输层根据端口和 Socket 信息，决定把数据交给哪个应用端点。

这里有两个重要区别：

- UDP 基础题通常重点考查依据目的端口号进行分用。
- TCP 已建立连接后，要结合源 IP、源端口、目的 IP、目的端口四元组确定具体连接。

#### 真题：2018 年 UDP 分用
题目：UDP 协议实现分用时，所依据的头部字段是什么？

A. 源端口号\
B. 目的端口号\
C. 长度\
D. 校验和

答案：B。

因为接收端要知道这个 UDP 数据报应该交给哪个应用端点，直接使用的关键字段是目的端口号。

## 三、UDP 协议：特点、首部与检验和
UDP 是这一章比较容易拿分的部分，但它的检验和计算需要特别熟悉。

### 3.1 UDP 的特点
UDP 的全称是 User Datagram Protocol，即用户数据报协议。

它的核心特点是：

| 特点        | 具体含义                 |
| --------- | -------------------- |
| 无连接       | 发送之前不需要三次握手          |
| 面向报文      | 保留应用层交付的消息边界         |
| 尽最大努力交付   | 不保证可靠、按序、不重复         |
| 首部开销小     | 固定 8B                |
| 无内建可靠传输机制 | 没有 TCP 那样的确认和重传      |
| 无内建流量控制   | UDP 本身不利用 rwnd 控制发送量 |
| 无内建拥塞控制   | 应用需要时自行实现            |
| 支持广播与组播   | 可以进行一对多数据报通信         |

#### 为什么说 UDP 面向报文？
假设应用程序依次向 UDP 交付：

```text
报文A：100B
报文B：200B
报文C：300B
```

UDP 会保留这些报文的边界，分别作为独立的数据报处理。

如果一个数据报丢失，UDP 不会自行重新发送。

与之对应，TCP 把应用交付的数据看作连续字节流，不保留应用写入时的消息边界。

UDP 不保证可靠，不代表所有采用 UDP 的应用都不可靠。

应用层可以自行设计确认、重传、排序和拥塞控制机制。例如 QUIC 基于 UDP 运行，但自身提供可靠传输机制。

#### 真题：2014 年 UDP 特性
判断以下说法：

Ⅰ. UDP 提供无连接服务。\
Ⅱ. UDP 提供复用和分用服务。\
Ⅲ. UDP 通过差错校验保障可靠数据传输。

分析：

- Ⅰ正确，无需建立连接。
- Ⅱ正确，UDP 使用端口实现复用、分用。
- Ⅲ错误，检验和只能发现一部分传输差错，不能保证数据恢复和可靠交付。

答案：仅Ⅰ、Ⅱ，选 B。

注意：检错不等于可靠传输。

### 3.2 UDP 首部
UDP 首部固定为 8B。

```text
  0                 15 16                31
  ┌──────────────────┬────────────────────┐
  │    源端口号       │     目的端口号       │
  ├──────────────────┼────────────────────┤
  │    UDP长度       │      UDP检验和       │
  └──────────────────┴────────────────────┘
  │                数据部分                │
  └───────────────────────────────────────┘
```

四个字段，每个都是 16 bit。

特别注意 UDP 长度字段：

$$
\boxed{L_{UDP}=8+L_{\text{数据}}}
$$

例如 UDP 长度字段的值为 100，那么：

$$
L_{\text{数据}}=100-8=92\text{ B}
$$

不是 100B。

#### 模拟题：十六进制 UDP 首部
典型模拟选择题给出：

```text
CB84 000D 001C 001C
```

按 16 位划分：

| 字段     | 十六进制 | 十进制   |
| ------ | ---- | ----- |
| 源端口    | CB84 | 52100 |
| 目的端口   | 000D | 13    |
| UDP 长度 | 001C | 28    |
| 检验和    | 001C | 28    |

所以：

$$
L_{\text{payload}}=28-8=20\text{ B}
$$

题目还依据临时源端口与服务器熟知端口，判断这是典型的客户端向服务器发送数据的方向。

但是要特别理解：根据端口号通常只能推测应用角色，不能仅凭端口号严格证明谁是客户端。

### 3.3 UDP 检验和
这是选择题计算重点。

UDP 检验和使用 16 位反码求和。

参与计算的内容包括：

$$
\boxed{ \text{UDP伪首部}+\text{UDP首部}+\text{UDP数据} }
$$

#### 什么是伪首部？
以 IPv4 为例，UDP 伪首部包括：

| 字段         | 长度     |
| ---------- | ------ |
| 源 IPv4 地址  | 32 bit |
| 目的 IPv4 地址 | 32 bit |
| 全零字段       | 8 bit  |
| 协议号        | 8 bit  |
| UDP 长度     | 16 bit |

UDP 的 IP 协议号为 17。

伪首部用于把部分网络层信息纳入检验和计算。

伪首部不会作为 UDP 首部的一部分实际发送。

TCP 计算检验和时也使用伪首部。

#### 16 位反码求和的步骤
1. 将检验和字段暂时置零。
2. 将参与计算的数据按 16 位分组。
3. 如果出现奇数字节，在末尾临时补零。
4. 按二进制进行加法。
5. 超出 16 位的最高进位，要回卷加到最低位。
6. 最后将 16 位结果逐位取反。

记忆为：

16 位分组 → 相加 → 回卷进位 → 取反。

### 3.4 真题：2024 年 UDP 检验和
题目给出两个 16 位数：

```text
1011100110110110
0110010111000101
```

求最终 UDP 检验和。

第一步：直接相加。

$$
\begin{aligned} &1011100110110110\\ +{}&0110010111000101\\ ={}&1\,0001111101111011 \end{aligned}
$$

出现了第 17 位进位。

第二步：回卷进位。

先取低 16 位：

```text
0001111101111011
```

再加最高位进位 1：

```text
0001111101111100
```

第三步：逐位取反。

```text
1110000010000011
```

因此：

$$
\boxed{1110000010000011}
$$

答案：C。

这道题最容易犯两个错误：忘记回卷进位，或者回卷以后忘记取反。

#### UDP 检验和其他易错点
- IPv4 中 UDP 检验和字段为 0 可以表示没有使用检验和；常规 IPv6 UDP 则要求计算检验和。
- 如果正常计算出的 UDP 检验和恰好为全零，在线路上通常以全 1 表示，避免与 IPv4 的“未使用检验和”混淆。
- UDP 检验和错误一般丢弃数据报，不提供自动重传。
- 检验和通过不意味着绝对不存在差错，因为它不是能够检测所有错误模式的机制。

## 四、TCP 协议基础：首部、序列号、确认号
这是后面所有 TCP 计算题的基础。

### 4.1 TCP 的基本特点
TCP 提供：

面向连接、可靠、有序、全双工、面向字节流的通信服务。

逐个理解：

| 特点    | 含义                |
| ----- | ----------------- |
| 面向连接  | 传输前建立 TCP 连接      |
| 可靠    | 通过确认、重传等机制恢复丢失数据  |
| 有序    | 对应用交付有序字节流        |
| 全双工   | 双方可以同时发送和接收       |
| 面向字节流 | 以连续字节序列为处理对象      |
| 点到点   | 一条 TCP 连接只有两个通信端点 |

#### TCP 为什么不保留消息边界？
应用可能先写入 100B，再写入 200B。

TCP 可能将它们：

- 合并成一个 300B 的报文段；
- 分成多个更小的报文段；
- 根据实际发送条件采用其他分段方式。

因此接收应用不能假设一次读取就恰好得到一次发送写入的全部内容。

应用层需要自行定义消息边界，例如长度字段、固定格式或分隔符。

### 4.2 TCP 首部结构
TCP 首部最短 20B，最长 60B。

核心结构：

```text
┌─────────────────┬──────────────────┐
│ 源端口号 16bit   │ 目的端口号 16bit   │
├────────────────────────────────────┤
│            序列号 32bit             │
├────────────────────────────────────┤
│            确认号 32bit             │
├────────┬──────────────┬────────────┤
│首部长度│  保留/控制位   │  窗口大小    │
├────────┴──────────────┴────────────┤
│      检验和         │     紧急指针    │
├────────────────────────────────────┤
│            选项与填充               │
└────────────────────────────────────┘
```

需要重点掌握的字段：

| 字段       | 长度       | 考试含义            |
| -------- | -------- | --------------- |
| 源端口、目的端口 | 各 16 bit | 连接标识            |
| 序列号      | 32 bit   | 数据第一个字节的序号      |
| 确认号      | 32 bit   | 下一个期望收到的字节      |
| 数据偏移     | 4 bit    | TCP 首部长度        |
| 窗口       | 16 bit   | 接收方通告的 rwnd     |
| 检验和      | 16 bit   | 检测报文段差错         |
| 紧急指针     | 16 bit   | 与 URG 配合        |
| 选项       | 可变       | MSS、窗口扩大、SACK 等 |

#### 首部长度计算
TCP 数据偏移字段占 4 位，单位为 4B。

若字段值为 $k$，则：

$$
L_{\text{TCP首部}}=4k\text{ B}
$$

最小值：

$$
5\times4=20\text{ B}
$$

最大值：

$$
15\times4=60\text{ B}
$$

因此，题目给 TCP 数据偏移为 8：

$$
L=8\times4=32\text{ B}
$$

TCP 选项和填充占：

$$
32-20=12\text{ B}
$$

注意数据偏移不是应用数据长度。

### 4.3 六个经典 TCP 控制标志
| 标志  | 含义     | 重点       |
| --- | ------ | -------- |
| URG | 紧急指针有效 | 紧急数据机制   |
| ACK | 确认号有效  | 建连后通常置 1 |
| PSH | 推送     | 提示尽快交付应用 |
| RST | 复位     | 异常复位连接   |
| SYN | 同步序列号  | 建立连接     |
| FIN | 结束发送   | 关闭一个发送方向 |

其中最重要的是：

$$
SYN,\ ACK,\ FIN,\ RST
$$

尤其注意：

ACK 标志位为 1，与确认号数值为 1，是两回事。

`ACK=1` 表示确认字段有效；`ack_seq=2001` 才表示下一个期望的字节序号为 2001。

### 4.4 MSS 与 MTU
MSS：最大报文段数据长度。

MTU：网络层数据报能够承载的最大长度，通常讨论某条链路的 MTU。

两者关系：

$$
\boxed{ MSS=MTU-L_{IP首部}-L_{TCP首部} }
$$

例如以太网 MTU 为 1500B，IPv4 首部 20B，TCP 首部 20B：

$$
MSS=1500-20-20
$$

$$
\boxed{MSS=1460\text{ B}}
$$

注意：

- MSS 不包含 TCP 首部。
- TCP 报文段长度包含 TCP 首部和 TCP 数据。
- IP 数据报还要包含 IP 首部。
- 如果 IP 或 TCP 有选项，首部可能大于 20B。

因此不能不看题目条件就套用 MSS=1460B。

### 4.5 TCP 序列号：按字节编号
这是全章最重要的基础规则。

假设一个 TCP 报文段：

```text
seq = 1000
数据长度 = 500B
```

它携带的字节序号为：

```text
1000 ～ 1499
```

下一段连续数据从：

```text
1500
```

开始。

公式：

$$
\boxed{ \text{末字节序号}=seq+L-1 }
$$

$$
\boxed{ \text{下一字节序号}=seq+L }
$$

#### TCP 的序号空间
序列号字段长 32 位：

$$
2^{32}
$$

种取值。

序列号按模 $2^{32}$ 循环使用。

### 4.6 TCP 确认号：累计确认
TCP 确认号不是“已经收到的最后一个字节”，而是：

$$
\boxed{ ACK=\text{下一个期望收到的字节序号} }
$$

例如：

```text
收到 1000～1499
```

回复：

```text
ACK = 1500
```

这代表此前连续的数据已收到，下一步希望收到 1500。

#### 真题：2009 年序列号
题目：甲向乙发送两个连续的 TCP 段：

- 第一段：300B，序号为 200。
- 第二段：500B。

全部正确收到，乙回复的确认号是多少？

第一段：

$$
200\sim499
$$

第二段：

$$
500\sim999
$$

因此：

$$
ACK=200+300+500
$$

$$
\boxed{ACK=1000}
$$

答案 D。

这一题不要把确认号误算为 999，也不要误认为 TCP 序号是第几个段。

### 4.7 乱序接收与累计确认
这是比基础序号计算更重要的进阶考法。

#### 真题：2011 年累计确认
主机甲依次发送三个 TCP 段：

| 段 | 数据长度 |
| - | ---- |
| 1 | 300B |
| 2 | 400B |
| 3 | 500B |

第三段的起始序号为 900。

乙只收到第 1 段和第 3 段，第二段丢失。

求确认号。

第一步，倒推第一段起始序号。

第三段前共有：

$$
300+400=700\text{ B}
$$

所以：

$$
seq_1=900-700=200
$$

第二步，确定三个段的序号：

| 段 | 字节范围     | 是否到达 |
| - | -------- | ---- |
| 1 | 200～499  | 到达   |
| 2 | 500～899  | 丢失   |
| 3 | 900～1399 | 到达   |

虽然第三段已经到达，但第二段缺失。

TCP 的累计确认号不能越过前面的缺口。

因此：

$$
\boxed{ACK=500}
$$

答案：B。

这道题的核心不是计算最后一个收到的字节，而是寻找第一个缺失字节。

#### 再看一个例子

```text
接收方已连续收到：1001～1500

段A：1501～2000 丢失
段B：2001～2500 到达
段C：2501～3000 到达
```

此时即使 B、C 已到达：

$$
ACK=1501
$$

当 A 重传并正确到达，假设 B、C 已被缓存：

$$
ACK=3001
$$

确认号可以一次跳过很大一段，但前提是所有这些字节已经连续到达。

### 4.8 真题：2013 年双向 seq 与 ack
乙向甲发送一个 TCP 段：

```text
seq = 1913
ack = 2046
数据长度 = 100B
```

问甲立即回复时的序号和确认号。

先看乙发送的数据：

$$
1913\sim2012
$$

甲下一步期望乙发送：

$$
ACK=2013
$$

再看乙的确认号 2046：

它表明乙已经连续收到甲的数据，下一步期望甲发送序号 2046 的字节。

因此甲下一段可用：

```text
seq = 2046
ack = 2013
```

答案：B。

这里一定要分别维护两个方向的序号，不能把甲发送方向与乙发送方向混为一谈。

## 五、TCP 连接管理：三次握手与四次挥手
这部分既考协议原理，也考序号、确认号和时间计算。

### 5.1 三次握手

假设客户端 A 的初始序列号为 $x$，服务器 B 的初始序列号为 $y$。

```text
客户端 A                         服务器 B
    │                               │
    │──── SYN=1, seq=x ────────────>│
    │                               │
    │<── SYN=1, ACK=1 ──────────────│
    │    seq=y, ack=x+1             │
    │                               │
    │──── ACK=1 ───────────────────>│
    │     seq=x+1, ack=y+1          │
    │                               │
    │         连接建立完成           │
```

<Steps>
  <Step>

    ### 第一次握手

客户端发起连接：

```text
SYN = 1
ACK = 0
seq = x
```

客户端状态：

```text
CLOSED → SYN-SENT
```

  </Step>
  <Step>

    ### 第二次握手

服务器同意连接：

```text
SYN = 1
ACK = 1
seq = y
ack = x+1
```

服务器状态：

```text
LISTEN → SYN-RECEIVED
```

为什么确认号是 $x+1$？

因为 SYN 即使没有应用数据，也要消耗一个序号。

  </Step>
  <Step>

    ### 第三次握手

客户端确认服务器的 SYN：

```text
SYN = 0
ACK = 1
seq = x+1
ack = y+1
```

客户端发送后进入 `ESTABLISHED`。

服务器收到后也进入 `ESTABLISHED`。

#### 为什么需要三次而不是两次？
主要解决两个问题：

1. 双方能够同步并确认各自的初始序列号。
2. 避免服务器仅凭可能滞留的旧 SYN 就把一个不存在的新连接当作已经建立。

更严格地说，第三次握手让服务器确认客户端已经收到服务器的 SYN 及其初始序列号。

#### 三次握手的易错点
| 问题                | 正确理解    |
| ----------------- | ------- |
| SYN 是否消耗序号？       | 是，消耗 1  |
| 第二次握手是否带 SYN？     | 是       |
| 第二次握手是否带 ACK？     | 是       |
| 第三次握手是否还能带 SYN？   | 正常情况下不带 |
| 第三次握手能否携带数据？      | 可以      |
| 不带数据的纯 ACK 消耗序号吗？ | 通常不消耗   |

  </Step>
</Steps>

### 5.2 真题：2019 年第三次握手
甲主动发起 TCP 连接：

```text
甲 ISN = 2018
乙 ISN = 2046
```

问第三次握手的确认号。

第三次握手由甲发送，它需要确认乙的 SYN。

所以：

$$
ACK=2046+1
$$

$$
\boxed{ACK=2047}
$$

答案 D。

这道题不需要用甲的 ISN=2018 来计算第三次握手的 ACK。

因为 ACK 表示确认对方发送方向的数据。

### 5.3 TCP 四次挥手

TCP 是全双工协议。

这意味着：

```text
A → B
B → A
```

两个方向可以分别关闭。

典型过程：

```text
主动关闭方 A                       被动关闭方 B
    │                                  │
    │──── FIN=1, seq=u ───────────────>│
    │                                  │
    │<─── ACK=1, ack=u+1 ──────────────│
    │                                  │
    │        B 可能继续发送数据         │
    │                                  │
    │<─── FIN=1, seq=v ────────────────│
    │                                  │
    │──── ACK=1, ack=v+1 ─────────────>│
    │                                  │
    │
 TIME-WAIT                           CLOSED
    │
 等待2MSL
    │
 CLOSED
```

<Steps>
  <Step>

    ### 第一次挥手

A 发送 FIN，表示自己不再发送数据。

状态：

```text
ESTABLISHED → FIN-WAIT-1
```

  </Step>
  <Step>

    ### 第二次挥手

B 确认 A 的 FIN。

B 进入：

```text
CLOSE-WAIT
```

A 收到确认后进入：

```text
FIN-WAIT-2
```

此时 B 仍可向 A 发送剩余数据。

这称为半关闭。

  </Step>
  <Step>

    ### 第三次挥手

B 也完成数据发送，发出自己的 FIN。

B 进入：

```text
LAST-ACK
```

  </Step>
  <Step>

    ### 第四次挥手

A 收到 B 的 FIN，回复 ACK。

A 进入：

```text
TIME-WAIT
```

B 收到最后 ACK 后进入 `CLOSED`。

A 经过 $2MSL$ 后进入 `CLOSED`。

  </Step>
</Steps>

### 5.4 为什么通常需要四次挥手？
建立连接时：

```text
确认 SYN
+
发送本方 SYN
```

可以合成一个 SYN+ACK。

但是关闭时，收到对方 FIN，并不代表自己已经没有数据发送。

所以通常：

```text
确认对方关闭
```

与：

```text
关闭自己的发送方向
```

分开进行。

因此通常需要四次。

不过，如果 B 收到 FIN 时也已经没有数据要发送，可以把 ACK 和 FIN 合并。

所以四次挥手是经典流程，不表示实际报文数量永远只能是四个。

### 5.5 FIN 是否消耗序号？
消耗。

假设客户端：

```text
SYN seq = 1000
```

随后发送 4000B 数据。

第一个数据字节序号：

$$
1001
$$

最后一个数据字节序号：

$$
1001+4000-1=5000
$$

FIN 序号：

$$
5001
$$

对方确认 FIN：

$$
ACK=5002
$$

#### 真题：2020 年数据长度
题目给出：

```text
SYN seq = 1000
FIN seq = 5001
```

无任何重传，求已经发送的应用数据字节数。

因为 SYN 占一个序号：

$$
\boxed{L=5001-1000-1=4000\text{ B}}
$$

答案 C。

这里不能忘记减去 SYN 占用的一个序号。

### 5.6 TIME-WAIT 与 2MSL
MSL 是一个报文段在网络中允许存活的最长时间。

在经典 TCP 连接关闭模型中，主动关闭方发送最后一个 ACK 后，需要等待：

$$
\boxed{2MSL}
$$

主要目的有两个。

第一，确保能够处理最后 ACK 丢失的情况。

如果最后 ACK 丢失，服务器可能重新发送 FIN。

主动关闭方仍处于 TIME-WAIT，就可以再次回应 ACK。

第二，使旧连接中残留的报文失效。

降低旧数据干扰后来重用相同连接标识的风险。

#### 真题：2021 年 TCP 状态
题目：客户端首先发送 FIN，随后收到服务器 FIN 并回复 ACK，此时客户端进入什么状态？

答案：

$$
\boxed{\text{TIME-WAIT}}
$$

因为客户端是主动关闭方。

注意，主动关闭方不一定是客户端；服务器也可以主动关闭。

### 5.7 四次挥手时间计算
这是很容易和 RTT、MSL 结合的大题考点。

假设：

- A 主动关闭；
- B 被动关闭；
- B 收到 FIN 后立即回复 ACK 和自己的 FIN；
- 单向传播时延为 $RTT/2$；
- 忽略发送时延和处理时延。

则：

| 时刻             | 事件                                |
| -------------- | --------------------------------- |
| $0$        | A 发 FIN                           |
| $RTT/2$    | B 收到 FIN，回复 ACK+FIN               |
| $RTT$      | A 收到 B 的 FIN，发最后 ACK，进入 TIME-WAIT |
| $3RTT/2$   | B 收到最后 ACK，进入 CLOSED              |
| $RTT+2MSL$ | A 结束 TIME-WAIT，进入 CLOSED          |

得到：

主动关闭方进入 CLOSED：

$$
\boxed{T_A=RTT+2MSL}
$$

被动关闭方进入 CLOSED：

$$
\boxed{T_B=\frac{3RTT}{2}}
$$

以上是满足前述条件时的最短时间公式，不能不看题目条件直接套用。

### 5.8 真题：2022 年连接关闭时间
已知：

$$
RTT=50\text{ ms}
$$

$$
MSL=800\text{ ms}
$$

客户端 C 主动关闭连接。

问从客户端发出第一个 FIN 开始，客户端和服务器分别至少多久进入 CLOSED。

首先：

$$
2MSL=1600\text{ ms}
$$

客户端：

$$
T_C=50+1600
$$

$$
\boxed{T_C=1650\text{ ms}}
$$

服务器：

$$
T_S=\frac32\times50
$$

$$
\boxed{T_S=75\text{ ms}}
$$

答案：D，1650ms、75ms。

为什么服务器不是 50ms？

因为服务器还需要等客户端最后一个 ACK 再传播半个 RTT。

### 5.9 真题：2024 年完整连接生命周期
题目给出：

- TCP 应用数据 3000B；
- MSS=1000B；
- RTT=10ms；
- MSL=30s；
- 初始拥塞窗口按 1 MSS；
- 忽略发送时延；
- 客户端主动关闭。

问：从发出 SYN 到最终进入 CLOSED，最少需要多久？

先分段：

$$
3000/1000=3\text{ 段}
$$

按题设的慢开始模型：

| 时间   | 事件                            |
| ---- | ----------------------------- |
| 0ms  | 发 SYN                         |
| 10ms | 收到 SYN+ACK，发送第三次握手及首个数据段      |
| 20ms | 首段确认到达，可发后两段                  |
| 30ms | 后两段确认到达，发送 FIN                |
| 40ms | 收到服务器 FIN，回复 ACK，进入 TIME-WAIT |

再加：

$$
2MSL=60\text{ s}
$$

因此：

$$
T=0.04+60
$$

$$
\boxed{T=60.04\text{ s}}
$$

答案：D。

这道题的考点不是简单的四次挥手，而是把握手、慢开始、数据确认和 TIME-WAIT 全部串在一起。

## 六、TCP 可靠传输：滑动窗口、累计 ACK 和重传
这一部分与拥塞控制共同构成全章计算题的核心。

### 6.1 TCP 可靠性是怎么实现的？
TCP 运行在 IP 提供的尽力而为服务之上。

IP 数据报可能出现丢失、乱序、重复或传输差错，因此 TCP 需要组合多种机制。

| 机制       | 作用               |
| -------- | ---------------- |
| 检验和      | 检测部分比特差错         |
| 序列号      | 给字节编号，识别顺序       |
| 累计确认 ACK | 告诉发送方连续收到哪里      |
| 滑动窗口     | 允许多个数据段同时在途      |
| 超时重传     | ACK 长时间没有推进时恢复数据 |
| 快速重传     | 利用重复 ACK 尽早重传    |
| 接收缓存     | 缓存尚未被应用读取的数据     |
| SACK 选项  | 提供非连续接收数据的额外信息   |

因此，TCP 的可靠性并不是简单的“收到一个报文就回复 ACK”。

### 6.2 为什么需要滑动窗口？
假设发送方发送一个 1000B 的 TCP 报文段，然后必须等待 100ms 才能收到 ACK。

如果每次只发送一个段：

```text
发送1000B
    ↓
等待100ms
    ↓
收到ACK
    ↓
继续发送1000B
```

即使网络带宽很高，发送方也会浪费大量时间等待。

滑动窗口允许：

```text
发送段1
发送段2
发送段3
发送段4
     ↓
依次收到ACK
     ↓
窗口向右移动
     ↓
继续发送新数据
```

核心思想是：不用每发送一个段就等待它的确认，而是允许一定数量的未确认数据同时存在于网络中。

### 6.3 TCP 发送窗口的四个区域
可以把 TCP 字节序列划分为：

```text
┌───────────┬───────────────┬───────────────┬──────────────┐
│ 已确认数据 │ 已发送未确认数据 │ 可发送未发送数据 │ 暂时不能发送 │
└───────────┴───────────────┴───────────────┴──────────────┘
            ↑                               ↑
         窗口左边界                       窗口右边界
```

其中：

```text
已发送未确认 + 可发送未发送
```

构成当前发送窗口所允许的字节范围。

#### 三个关键变量
| 变量           | 含义          |
| ------------ | ----------- |
| `SND.UNA`    | 最早尚未被确认的字节  |
| `SND.NXT`    | 下一个准备发送的新字节 |
| `FlightSize` | 已发送但未确认的数据量 |

在不考虑序号回绕的普通题目中：

$$
\boxed{ FlightSize=SND.NXT-SND.UNA }
$$

发送窗口受两个变量共同限制：

$$
\boxed{ W=\min(rwnd,cwnd) }
$$

在题目假设窗口和在途数据按同一时刻计算时：

$$
\boxed{ L_{\text{new}}=\max(0,W-FlightSize) }
$$

这三个量一定要分清楚。

### 6.4 真题：2010 年发送窗口计算
题目条件：

- TCP 最大段长为 1000B；
- 当前拥塞窗口 $cwnd=4000\text{ B}$；
- 甲已连续发送两个 1000B 段；
- 收到第一个段的确认；
- 该 ACK 通告的接收窗口为 2000B。

问：此时甲还可以发送多少字节？

第一步：计算当前窗口上限。

$$
W=\min(4000,2000)=2000\text{ B}
$$

第二步：计算在途数据。

两个段共发送：

$$
2000\text{ B}
$$

第一个段已经被确认，剩余：

$$
FlightSize=1000\text{ B}
$$

第三步：扣除在途数据。

$$
L_{\text{new}}=2000-1000
$$

$$
\boxed{L_{\text{new}}=1000\text{ B}}
$$

答案：A。

这道题极其典型。

如果直接回答 2000B，说明把窗口上限误认为了当前还可以新发的数据量。

### 6.5 真题：2021 年序列号窗口范围
题目条件：

甲已经发送：

```text
seq = 501
数据长度 = 200B
```

随后收到乙的 TCP 段：

```text
ack_seq = 501
rwnd = 500B
```

问甲在没有收到新的确认之前，还能继续发送哪些序号的数据？

第一步：根据 ACK 求窗口左边界。

$$
L=501
$$

第二步：接收窗口范围长度为 500B。

因此窗口覆盖：

$$
501\sim1000
$$

第三步：已经发送的数据：

$$
501\sim700
$$

第四步：减去已发送部分。

剩余可发送范围：

$$
\boxed{701\sim1000}
$$

答案：C。

特别注意，题目给出的是 `ack_seq=501`，说明已经发出的 501～700 还没有获得累计确认。

不能把这些字节重新当作新的可发送额度。

<Callout type="idea" title="rwnd 与 cwnd 控制的约束不同">

$rwnd$ 取决于接收端缓冲能力，$cwnd$ 取决于发送端拥塞控制。教材常用模型中发送窗口上限 $W=\min(rwnd,cwnd)$，新数据可发送量还须扣除未确认的在途数据。

</Callout>

### 6.6 TCP 接收窗口 rwnd
假设接收方有 16KB 接收缓存。

TCP 收到的数据先存入缓存，等待应用程序读取。

```text
网络接收数据
      ↓
TCP接收缓存
      ↓
应用程序读取
```

如果应用程序读取速度太慢，接收缓存就会逐渐被占满。

接收方使用 `rwnd` 告诉发送方还能接收多少数据。

在普通计算题中：

$$
\boxed{ rwnd=RcvBuffer-\text{已占用缓存大小} }
$$

例如：

$$
RcvBuffer=16\text{ KB}
$$

已经缓存：

$$
11\text{ KB}
$$

则：

$$
rwnd=16-11=5\text{ KB}
$$

如果应用读取了 4KB：

$$
rwnd=5+4=9\text{ KB}
$$

注意，应用读走数据后，接收窗口可以增大。

#### rwnd 和 cwnd 的本质区别
| 比较项            | rwnd        | cwnd       |
| -------------- | ----------- | ---------- |
| 中文             | 接收窗口        | 拥塞窗口       |
| 保护谁            | 接收方         | 网络         |
| 决定者            | 接收方         | 发送方        |
| 依据             | 接收缓存空闲空间    | ACK、丢包、超时等 |
| 是否在 TCP 首部直接通告 | 是，Window 字段 | 否          |
| 太小意味着          | 接收方处理不过来    | 网络承载能力受限   |

### 6.7 真题：2015 年接收缓存与慢开始
这道题能很好地说明为什么不能只计算拥塞窗口。

已知：

$$
RcvBuffer=16\text{ KB}
$$

$$
MSS=1\text{ KB}
$$

$$
ssthresh=32\text{ KB}
$$

初始拥塞窗口：

$$
cwnd=1\text{ KB}
$$

接收方不从缓存中读取数据。

问经过 4 个 RTT 后，甲的发送窗口大小。

先计算各轮发送量：

| RTT | 该轮发送量 | 累计进入缓存 | 轮末 cwnd |
| --- | ----- | ------ | ------- |
| 1   | 1KB   | 1KB    | 2KB     |
| 2   | 2KB   | 3KB    | 4KB     |
| 3   | 4KB   | 7KB    | 8KB     |
| 4   | 8KB   | 15KB   | 16KB    |

第四轮结束后：

$$
cwnd=16\text{ KB}
$$

但接收缓存只剩：

$$
rwnd=16-15=1\text{ KB}
$$

所以：

$$
W=\min(16,1)
$$

$$
\boxed{W=1\text{ KB}}
$$

答案：A。

这里有一个很重要的结论：

即使拥塞窗口非常大，只要接收窗口很小，发送窗口也会受接收方限制。

### 6.8 零窗口与持续计时器
当：

$$
rwnd=0
$$

接收方表示：

> 我的接收缓存暂时没有空间了，请先不要发送普通新数据。

但是存在一个问题。

如果接收方后来读走了数据，通告窗口重新打开，而这次窗口更新报文丢失：

```text
发送方：等你窗口变大
接收方：已经通知你窗口变大
```

双方可能陷入等待。

TCP 因此使用持续计时器（Persist Timer）。

发送方通过零窗口探测，询问接收方的窗口是否恢复。

零窗口不意味着连接已经断开，也不代表发生了网络拥塞。

### 6.9 超时重传 RTO
发送方发出数据后，如果长时间没有收到有效确认，就可能触发超时重传。

这个超时时间叫作：

$$
RTO
$$

即 Retransmission Timeout。

为什么不能把 RTO 设置得特别小？

因为 ACK 可能只是由于排队、网络拥塞或链路时延波动而暂时没有返回。

RTO 太小会导致不必要的重传。

RTO 太大又会使真正丢包后的恢复速度很慢。

因此 TCP 会估计 RTT，并据此调整 RTO。

#### RTT 平滑估计
常见教材公式：

$$
EstimatedRTT_{\text{new}} =(1-\alpha)EstimatedRTT_{\text{old}} +\alpha SampleRTT
$$

其中常用：

$$
\alpha=\frac18
$$

RTT 偏差估计：

$$
DevRTT_{\text{new}} =(1-\beta)DevRTT_{\text{old}} +\beta\left|SampleRTT-EstimatedRTT_{\text{new}}\right|
$$

其中常用：

$$
\beta=\frac14
$$

RTO 估计：

$$
\boxed{ RTO=EstimatedRTT+4DevRTT }
$$

#### 例题
已知：

$$
EstimatedRTT_{\text{old}}=100\text{ ms}
$$

$$
DevRTT_{\text{old}}=20\text{ ms}
$$

$$
SampleRTT=140\text{ ms}
$$

第一步：

$$
EstimatedRTT_{\text{new}} =0.875\times100+0.125\times140 =105\text{ ms}
$$

第二步：

$$
\begin{aligned} DevRTT_{\text{new}} &=0.75\times20+0.25|140-105|\\ &=15+8.75\\ &=23.75\text{ ms} \end{aligned}
$$

第三步：

$$
RTO=105+4\times23.75
$$

$$
\boxed{RTO=200\text{ ms}}
$$

注意：题目给定更新顺序时，应严格按照题设，不能直接把 $RTT$ 当作 $RTO$。

### 6.10 快速重传
TCP 不一定需要等到超时才能发现数据丢失。

假设发送：

```text
段1：收到
段2：丢失
段3：收到
段4：收到
段5：收到
```

接收端发现段 2 缺失，即使后面的段继续到达，仍重复发送指向段 2 起始字节的累计 ACK。

如果发送方收到 3 个重复 ACK，就可以触发快速重传。

要注意“重复”两个字：

```text
第一次收到 ACK=2001  → 正常确认
第二次收到 ACK=2001  → 重复ACK 1
第三次收到 ACK=2001  → 重复ACK 2
第四次收到 ACK=2001  → 重复ACK 3
```

第 4 次收到这个相同 ACK 值时，已经累计出现 3 个重复 ACK。

#### 真题：2019 年快速重传
题目中的客户端在 $t_0$ 首次收到：

```text
ACK=100
```

随后 `seq=100` 的数据段丢失。

后续连续出现多个针对缺失位置的 ACK。

题目所给时间图中，第三个重复 ACK 在 $t_3$ 到达，因此客户端立即重传。

答案：C，$t_3$。

不能把 $t_0$ 首次收到的 ACK=100 也算成重复 ACK。

### 6.11 TCP 和 GBN、SR 的联系
第 3 章学过：

- GBN：回退 N 帧。
- SR：选择重传。

TCP 与它们有联系，但不能简单等同。

| 特性   | GBN  | SR    | TCP            |
| ---- | ---- | ----- | -------------- |
| 编号对象 | 帧    | 帧     | 字节             |
| ACK  | 累计确认 | 可逐帧确认 | 以累计确认为基础       |
| 乱序到达 | 通常丢弃 | 缓存    | 通常可缓存          |
| 重传   | 回退一批 | 选择性重传 | 超时、快速重传、SACK 等 |

因此：

TCP 既不是纯粹的 GBN，也不是纯粹的 SR。

TCP 的累计 ACK 与 GBN 类似，但现代 TCP 可以缓存乱序数据，还可利用 SACK 提供选择性确认信息。

## 七、TCP 拥塞控制：全章计算的重点
建议把这一部分当作一道完整的大题来学习。

### 7.1 流量控制和拥塞控制的区别
流量控制关心的是：

> 接收方还有没有空间接收数据？

拥塞控制关心的是：

> 网络还能不能承受发送方继续注入大量数据？

假设接收方缓存还有 100KB，但是路由器队列已接近溢出。

即使：

$$
rwnd=100\text{ KB}
$$

也不代表发送方可以立即发送 100KB。

它还要受到拥塞窗口 $cwnd$ 的约束。

因此：

$$
\boxed{W=\min(rwnd,cwnd)}
$$

### 7.2 拥塞控制的三个核心变量
#### MSS
一个 TCP 报文段允许携带的最大 TCP 数据量。

例如：

$$
MSS=1000\text{ B}
$$

#### cwnd
拥塞窗口。

表示发送方依据拥塞控制机制允许的在途数据额度。

例如：

$$
cwnd=8MSS
$$

意味着：

$$
cwnd=8\times1000=8000\text{ B}
$$

#### ssthresh
慢开始门限。

决定经典模型中什么时候从慢开始转向拥塞避免。

在教材简化模型中：

$$
cwnd<ssthresh
$$

处于慢开始阶段。

$$
cwnd\ge ssthresh
$$

转入拥塞避免阶段。

<Tabs items={['慢开始', '拥塞避免']} defaultIndex={0}>
  <Tab value="慢开始">

在经典 408 计算模型中，经常假设：

$$
cwnd_0=1MSS
$$

在数据持续发送、每个 MSS 都及时得到确认的理想条件下：

```text
RTT 0：1 MSS
RTT 1：2 MSS
RTT 2：4 MSS
RTT 3：8 MSS
RTT 4：16 MSS
RTT 5：32 MSS
```

即：

$$
\boxed{cwnd_k=2^kMSS}
$$

但这个公式只适用于没有受到门限、接收窗口或丢包事件限制的理想慢开始阶段。

#### 为什么叫慢开始，却指数增长？
因为最初的窗口比较小，发送方是在逐步探测网络承载能力。

它不是线性地慢慢增长。

经典慢开始的特点是：

- 每收到一个确认新数据的 ACK，拥塞窗口增加一定额度；
- 一个 RTT 中收到一批 ACK；
- 如果满窗口数据都被及时确认，下一轮窗口规模约翻倍。

这里尤其不要误解为：

> 每收到一个 ACK，cwnd 就直接翻倍。

真实 TCP 的窗口增长要结合 ACK 及其确认的数据量，408 整 RTT 题目采用的是理想化近似。

  </Tab>
  <Tab value="拥塞避免">

当：

$$
cwnd\ge ssthresh
$$

进入拥塞避免。

经典教材模型：

$$
\boxed{\text{每经过一个 RTT，cwnd 约增加 }1MSS}
$$

例如：

```text
8 → 9 → 10 → 11 → 12
```

而不是：

```text
8 → 16 → 32
```

这体现的是加性增大思想。

  </Tab>
</Tabs>

### 7.5 慢开始与拥塞避免的完整例子
设：

$$
cwnd_0=1MSS
$$

$$
ssthresh=8MSS
$$

无丢包。

| RTT | 轮次开始 cwnd | 当前阶段 | 轮次结束 cwnd |
| --- | --------- | ---- | --------- |
| 1   | 1         | 慢开始  | 2         |
| 2   | 2         | 慢开始  | 4         |
| 3   | 4         | 慢开始  | 8         |
| 4   | 8         | 拥塞避免 | 9         |
| 5   | 9         | 拥塞避免 | 10        |
| 6   | 10        | 拥塞避免 | 11        |

所以：

$$
\boxed{cwnd_6=11MSS}
$$

这也是本章强化训练中的典型计算。

注意，恰好达到慢开始门限后，下一轮进入拥塞避免。

### 7.6 超时之后怎样调整？
假设发送方原来的拥塞窗口：

$$
cwnd=16MSS
$$

此时发生 RTO 超时。

经典 408 简化模型通常规定：

第一步：慢开始门限减半。

$$
ssthresh=\frac{16}{2}=8MSS
$$

第二步：拥塞窗口重新回到 1 MSS。

$$
cwnd=1MSS
$$

第三步：重新慢开始。

之后窗口变化：

```text
1 → 2 → 4 → 8 → 9 → 10 → 11 ...
```

特别注意：

不是超时之后继续从 8 开始，也不是永远保持指数增长。

### 7.7 真题：2009 年超时后的窗口
题目给出：

- MSS=1KB；
- 超时前 $cwnd=16\text{ KB}$；
- 后续 4 个 RTT 传输均成功。

求第 4 个 RTT 中的段全部得到确认之后的拥塞窗口。

超时后：

$$
ssthresh=8\text{ KB}
$$

$$
cwnd=1\text{ KB}
$$

逐轮计算：

| RTT 结束 | cwnd |
| ------ | ---- |
| 第 1 轮  | 2KB  |
| 第 2 轮  | 4KB  |
| 第 3 轮  | 8KB  |
| 第 4 轮  | 9KB  |

所以：

$$
\boxed{cwnd=9\text{ KB}}
$$

答案 C。

这是典型的“先指数增长到门限，再线性增加”。

### 7.8 真题：2022 年窗口恢复到原值
已知：

$$
MSS=1\text{ KB}
$$

超时前：

$$
cwnd=16\text{ KB}
$$

问再次增长到 16KB，至少需要几个 RTT？

超时后：

$$
ssthresh=8\text{ KB}
$$

$$
cwnd=1\text{ KB}
$$

慢开始：

```text
1 → 2 → 4 → 8
```

需要：

$$
3RTT
$$

拥塞避免：

```text
8 → 9 → 10 → 11 → 12 → 13 → 14 → 15 → 16
```

需要：

$$
8RTT
$$

因此：

$$
T=3RTT+8RTT
$$

$$
\boxed{T=11RTT}
$$

答案：C。

很多人会误认为：

$$
1\rightarrow2\rightarrow4\rightarrow8\rightarrow16
$$

只需要 4RTT。

错误原因是达到门限后，不能再按慢开始指数增长。

<Callout type="warn" title="拥塞算法与教材口径必须对应">

超时与 3 个重复 ACK 的处理不同；Tahoe、Reno 及现代实现存在差异，解题时以题目指明的协议和经典教材规则为准。

</Callout>

### 7.9 快速重传与快速恢复
与超时重传不同，3 个重复 ACK 通常表示：

- 某些数据可能丢失；
- 但后续数据仍然可以到达；
- 网络不一定发生了严重拥塞。

因此 TCP Reno 类算法通常不会像超时那样直接退回初始慢开始状态。

<Tabs items={['教材简化模型', 'Tahoe 与 Reno', 'Reno 细节']} defaultIndex={0}>
  <Tab value="教材简化模型">

假设：

$$
cwnd=16MSS
$$

出现 3 个重复 ACK。

则：

$$
ssthresh=8MSS
$$

快速恢复结束后：

$$
cwnd=8MSS
$$

然后进入拥塞避免。

  </Tab>
  <Tab value="Tahoe 与 Reno">

| 事件           | Tahoe 典型处理 | Reno 典型处理       |
| ------------ | ---------- | --------------- |
| RTO 超时       | 缩小门限、重新慢开始 | 缩小门限、重新慢开始      |
| 3 个重复 ACK    | 快速重传后重新慢开始 | 快速重传、快速恢复       |
| 丢包后是否直接回到慢开始 | 是          | 3 个重复 ACK 时通常不是 |

  </Tab>
  <Tab value="Reno 细节">

在经典 Reno 快速恢复过程中，收到第 3 个重复 ACK 后可能暂时设置：

$$
cwnd=ssthresh+3MSS
$$

随后根据重复 ACK、新的累计 ACK 继续调整。

因此必须区分：

- 进入快速恢复时的临时窗口；
- 恢复完成后用于拥塞避免的窗口。

408 有些题使用简化规则：

$$
cwnd\leftarrow ssthresh
$$

有些题会给出更详细的 Reno 行为。

如果题目明确给出拥塞控制算法和调整规则，必须以题设为准。

  </Tab>
</Tabs>

### 7.10 超时与三次重复 ACK 的终极区别
| 比较         | 超时           | 3 个重复 ACK       |
| ---------- | ------------ | --------------- |
| 如何发现       | RTO 到期       | 收到 3 个重复 ACK    |
| 是否等待 RTO   | 是            | 不需要             |
| 网络反馈       | 较严重          | 后续数据仍可能到达       |
| 新 ssthresh | 通常按题设减半      | 通常按题设减半         |
| 后续 cwnd    | 教材模型回到 1 MSS | Reno 快速恢复后约为新门限 |
| 后续阶段       | 慢开始          | 快速恢复/拥塞避免       |

考试时看到“发生丢包”，先不要立即计算。

必须判断：

题目说的是超时，还是连续收到 3 个重复 ACK？

不同事件，后面的窗口轨迹完全不同。

### 7.11 真题：2020 年拥塞窗口最长增长时间
题目给出：

$$
MSS=1\text{ KB}
$$

$$
RTT=2\text{ ms}
$$

窗口从：

$$
8\text{ KB}\rightarrow32\text{ KB}
$$

问在不发生拥塞的前提下所需的最长时间。

注意关键词：最长。

若使用慢开始，增长较快。

若一直处于拥塞避免，每 RTT 只增长 1KB，时间更长。

需要增长：

$$
32-8=24\text{ KB}
$$

需要：

$$
24RTT
$$

所以：

$$
T=24\times2
$$

$$
\boxed{T=48\text{ ms}}
$$

答案：D。

这类题一定要先判断“最长”还是“最短”，再决定使用哪种增长方式。

## 八、TCP 吞吐率、带宽时延积与 RTT 综合计算
### 8.1 窗口为什么会限制吞吐率？
假设：

$$
W=10000\text{ B}
$$

$$
RTT=100\text{ ms}=0.1\text{ s}
$$

如果在一个 RTT 中，最多保持 10000B 的数据在途，那么理想稳定状态下，由窗口限定的吞吐率约为：

$$
R\approx\frac{W}{RTT}
$$

所以：

$$
R\approx\frac{10000\times8}{0.1}
$$

$$
\boxed{R=800000\text{ bit/s}=0.8\text{ Mb/s}}
$$

但如果链路本身只有 500kb/s，显然不可能凭增大窗口突破链路物理容量。

因此常用近似：

$$
\boxed{ R\lesssim\min\left(B,\frac{8W}{RTT}\right) }
$$

这里 $B$ 的单位为 bit/s，$W$ 的单位为 Byte。

这只是理想化窗口吞吐率估算，真实 TCP 还受到拥塞控制、应用发送量、协议开销和丢包等因素影响。

### 8.2 带宽时延积 BDP
带宽时延积：

$$
\boxed{BDP=B\times RTT}
$$

其物理含义是：

> 在一个 RTT 中，链路能够传输的数据量。

例如：

$$
B=100\text{ Mb/s}
$$

$$
RTT=40\text{ ms}
$$

则：

$$
BDP=100\times10^6\times0.04
$$

$$
=4\times10^6\text{ bit}
$$

换算为字节：

$$
\boxed{BDP=500000\text{ B}}
$$

要在这种链路上持续保持较高利用率，通常需要足够大的在途数据窗口。

如果有效窗口远小于 BDP，发送方可能频繁等待 ACK，无法充分利用带宽。

### 8.3 有限文件传输与长期吞吐率不同
408 经常给出：

- 文件大小；
- MSS；
- RTT；
- 初始 cwnd；
- ssthresh；
- 接收窗口；
- 是否丢包。

这类题要求的是：

从某个时刻开始，到文件全部发送并得到确认为止，共需要多少 RTT。

它不能直接套用稳态公式 $W/RTT$。

需要模拟每一轮具体发送多少个段。

#### 解题模板
设文件大小：

$$
F
$$

每个数据段最大携带：

$$
MSS
$$

则需要的数据段数：

$$
N=\left\lceil\frac{F}{MSS}\right\rceil
$$

但这里有一个注意点：最后一段可能不足 MSS。

后续逐轮计算：

$$
\text{本轮可发送量} =\min(\text{剩余数据},rwnd,cwnd)
$$

并同时考虑：

- 当前还有多少数据在途；
- 是否有 ACK 返回；
- 拥塞窗口是否增长；
- 是否达到门限；
- 是否丢包；
- 文件最后一轮 ACK 是否已经返回。

最后再按照题目给定的时间起点和终点，计算 RTT 总数。

### 9.1 2012 年第 47 题：TCP 抓包综合题
#### 题目背景
主机 H：

```text
192.168.0.8
```

服务器 S：

```text
211.68.71.80
```

主机 H 捕获了 5 个 IP 分组，每个给出前 40B 十六进制数据。

题目要求判断：

1. 哪些包由 H 发送？
2. 哪些包完成 TCP 三次握手？
3. 哪些包需要以太网填充？
4. 服务器接收了多少 TCP 应用数据？
5. 分组经过了多少台路由器？

#### 考点一：通过 IP 首部判断发送方向
IPv4 无选项时，首部长度为 20B。

重点字段位置：

| 字段     | 从 IP 首部开始的字节偏移 |
| ------ | -------------- |
| IP 总长度 | 2～3            |
| TTL    | 8              |
| 协议号    | 9              |
| 源 IP   | 12～15          |
| 目的 IP  | 16～19          |

主机 H 的 IP：

```text
192.168.0.8
```

写成十六进制：

```text
C0 A8 00 08
```

因此找到源 IP 为 `C0 A8 00 08` 的包。

答案：

$$
\boxed{1、3、4}
$$

不能根据包的排列顺序猜测哪一方发送。

#### 考点二：通过 TCP 标志位识别三次握手
找到：

```text
SYN
SYN + ACK
ACK
```

对应：

$$
\boxed{1、2、3}
$$

这里需要利用 TCP 控制位与 SYN 消耗序号的规则共同判断。

#### 考点三：以太网帧最短长度
标准 Ethernet II 帧最短为 64B，包含：

- MAC 首部 14B；
- 数据字段；
- FCS 4B。

因此数据字段至少：

$$
64-14-4=46\text{ B}
$$

题目中第 3、5 个 IP 分组长度为：

$$
40\text{ B}
$$

所以需要填充：

$$
46-40=6\text{ B}
$$

结论：

$$
\boxed{\text{第3、5个包各填充6B}}
$$

注意填充属于数据链路层，不计入 IP 总长度。

#### 考点四：十六进制 TCP ACK 求应用数据量
题目中，服务器累计确认号从客户端首数据序号：

```text
846B41C6H
```

前进到：

```text
846B41D6H
```

因此已确认的数据量为：

$$
\begin{aligned} L &=\texttt{0x846B41D6}-\texttt{0x846B41C6}\\ &=\texttt{0x10}\\ &=16\text{ B} \end{aligned}
$$

所以：

$$
\boxed{16\text{ B}}
$$

这里要算的是 TCP 应用数据，不包括 IP、TCP 首部，也不能把重传数据重复计入。

#### 考点五：TTL 求路由器数量
同一个 IP 分组：

服务器发送时：

$$
TTL=0x40=64
$$

主机 H 收到时：

$$
TTL=0x31=49
$$

每经过一个路由器进行 IP 转发，TTL 减少 1。

因此：

$$
N=64-49
$$

$$
\boxed{N=15}
$$

#### 本题最终答案
| 问题        | 答案       |
| --------- | -------- |
| H 发送的分组   | 1、3、4    |
| 三次握手分组    | 1、2、3    |
| 需要填充的分组   | 3、5，各 6B |
| S 接收的应用数据 | 16B      |
| 经过的路由器数量  | 15       |

这道题最值得学习的是：不要把抓包题理解为单纯的 TCP 题。它同时考查网络层、传输层和数据链路层。

以后遇到原始报文字节，按照：

```text
IP首部
→ TCP首部
→ TCP数据
→ TCP序号和确认号
→ 链路层封装
```

这样的顺序处理。

### 9.2 2016 年第 41 题：流量控制与拥塞控制综合题
这是非常值得反复练习的一道大题。

#### 已知条件
客户端 H3 向服务器 S 发送数据。

$$
RcvBuffer=20\text{ KB}
$$

$$
MSS=1\text{ KB}
$$

$$
RTT=200\text{ ms}
$$

$$
ssthresh=32\text{ KB}
$$

客户端初始序列号：

$$
ISN=100
$$

服务器接收应用程序始终不读取缓存中的数据。

服务器收到每个段都会立即确认。

#### 第一问：第二次握手的 SYN、ACK 和确认号
客户端第一次握手：

```text
SYN=1
seq=100
```

服务器第二次握手：

```text
SYN=1
ACK=1
ack=101
```

因此：

$$
\boxed{SYN=1,\ ACK=1,\ ack=101}
$$

#### 第二问：收到第 8 个 ACK 后的窗口
服务器缓存总共：

$$
20\text{ KB}
$$

已经收到 8 个 MSS 大小的数据段：

$$
8\text{ KB}
$$

因为应用不读取，所以：

$$
rwnd=20-8
$$

$$
\boxed{rwnd=12\text{ KB}}
$$

发送方初始：

$$
cwnd=1MSS
$$

题设规定每个数据段单独立即确认，在慢开始阶段，每收到一个新的满 MSS 数据段的确认，窗口增加 1MSS。

所以收到第 8 个新的数据 ACK 后：

$$
cwnd=1+8=9MSS
$$

即：

$$
\boxed{cwnd=9\text{ KB}}
$$

发送窗口上限：

$$
W=\min(12,9)
$$

$$
\boxed{W=9\text{ KB}}
$$

这一问最容易犯的错误是把：

$$
rwnd=12
$$

误当成发送窗口答案。

#### 第三问：窗口何时变成 0？
服务器有 20KB 缓存。

应用一直不读取。

因此客户端最多让 20KB 数据进入服务器缓存，之后：

$$
rwnd=0
$$

按 RTT 轮次计算：

| 轮次 | 本轮发送 | 累计接收 | 剩余接收窗口 |
| -- | ---- | ---- | ------ |
| 1  | 1KB  | 1KB  | 19KB   |
| 2  | 2KB  | 3KB  | 17KB   |
| 3  | 4KB  | 7KB  | 13KB   |
| 4  | 8KB  | 15KB | 5KB    |
| 5  | 5KB  | 20KB | 0KB    |

注意第五轮。

此时拥塞窗口虽然可以继续增长，但接收窗口只剩下 5KB。

所以第五轮只能使最后 5KB 进入缓存。

不能继续按照：

```text
1, 2, 4, 8, 16
```

发送完整的 16KB。

#### 第四问：下一个待发送字节的序列号
SYN 序号为：

$$
100
$$

因此第一个数据字节序号为：

$$
101
$$

共发送：

$$
20\times1024=20480\text{ B}
$$

所以下一个字节序号为：

$$
101+20480
$$

$$
\boxed{20581}
$$

这里有两个常见错误：

- 忘记 SYN 占用序号，把起点设成 100。
- 把 20KB 误写成 20000B，而题目规定 $1KB=1024B$。

#### 第五问：平均传输速率
共需要：

$$
5RTT
$$

因此：

$$
T=5\times200\text{ ms}
$$

$$
T=1\text{ s}
$$

总应用数据：

$$
20480\text{ B}
$$

转成 bit：

$$
20480\times8=163840\text{ bit}
$$

平均速率：

$$
R=\frac{163840}{1}
$$

$$
\boxed{R=163840\text{ bit/s}=163.84\text{ kb/s}}
$$

#### 第六问：服务器最快什么时候释放连接？
客户端在 $t$ 时刻主动发出 FIN。

题设允许服务器收到后立即回复 ACK 和自己的 FIN。

服务器最终进入 CLOSED，需要收到客户端最后的 ACK。

所以：

$$
T=\frac32RTT
$$

$$
T=\frac32\times200
$$

$$
\boxed{T=300\text{ ms}}
$$

不能给服务器额外加上 $2MSL$。

因为在这道题中，TIME-WAIT 由主动关闭方客户端承担。

#### 2016 年大题的核心价值
这道题同时考查了三种不同的“数量”：

第一，累计收到多少个新数据 ACK。

用于确定某一时刻的拥塞窗口增长。

第二，接收缓存一共存入多少字节。

用于确定接收窗口。

第三，经历了多少个 RTT 轮次。

用于确定数据完成传输的时间。

这三种数量不能混着计算。

### 9.3 2023 年第 47 题：FTP + TCP + 拥塞控制 + 吞吐率
这是非常典型的跨层综合题。

#### 已知条件
FTP 上传文件：

$$
F=18000\text{ B}
$$

$$
MSS=1000\text{ B}
$$

$$
RTT=10\text{ ms}
$$

$$
ssthresh=4MSS
$$

客户端初始序号：

$$
ISN=100
$$

无差错、丢包、乱序。

#### 第一问：FTP 的两条 TCP 连接
FTP 使用控制连接和数据连接。

| 连接   | 功能           | 题目中的连接特点 |
| ---- | ------------ | -------- |
| 控制连接 | 登录、发送 FTP 命令 | 持久       |
| 数据连接 | 实际传送文件       | 非持久      |

因此：

- FTP 控制连接是持久连接；
- 数据连接是非持久连接；
- 登录服务器首先建立控制连接。

这属于第 6 章应用层与第 5 章传输层的综合。

#### 第二问：文件第一个字节的序号
客户端 SYN 使用：

$$
seq=100
$$

SYN 消耗一个序号。

所以：

$$
\boxed{seq_{\text{first}}=101}
$$

#### 第三问：释放连接时的确认号
文件大小：

$$
18000\text{ B}
$$

数据从序号 101 开始。

最后一个数据字节：

$$
101+18000-1=18100
$$

客户端 FIN 的序号为：

$$
18101
$$

FIN 又消耗一个序号，所以服务器确认 FIN：

$$
\boxed{ACK=18102}
$$

#### 第四问：收到 ACK=2101 时 cwnd 是多少？
起始数据序号：

$$
101
$$

ACK 为：

$$
2101
$$

所以已经确认：

$$
2101-101=2000\text{ B}
$$

即：

$$
2MSS
$$

初始：

$$
cwnd=1MSS
$$

确认第一个 MSS 后：

$$
cwnd=2MSS
$$

确认第二个 MSS 后：

$$
cwnd=3MSS
$$

因此：

$$
\boxed{cwnd=3MSS}
$$

注意，收到 ACK=2101 表示已经确认了两个数据段，并不是只确认了“第 2101 个字节”。

#### 第五问：收到 ACK=7101 时 cwnd 是多少？
已经确认的数据量：

$$
7101-101=7000\text{ B}
$$

即：

$$
7MSS
$$

按题设的整 RTT 模型：

| 轮次 | 本轮发送段数 | 累计确认段数 | 下一轮 cwnd |
| -- | ------ | ------ | -------- |
| 1  | 1      | 1      | 2        |
| 2  | 2      | 3      | 4        |
| 3  | 4      | 7      | 5        |

因此：

$$
\boxed{cwnd=5MSS}
$$

因为达到 4MSS 门限后，进入了拥塞避免阶段。

#### 第六问：完整发送 18000B 需要多久？
文件共有：

$$
N=\frac{18000}{1000}=18\text{ 段}
$$

依照慢开始和拥塞避免：

| RTT | cwnd | 发送段数 | 累计发送 |
| --- | ---- | ---- | ---- |
| 1   | 1    | 1    | 1    |
| 2   | 2    | 2    | 3    |
| 3   | 4    | 4    | 7    |
| 4   | 5    | 5    | 12   |
| 5   | 6    | 6    | 18   |

所以文件数据发送并全部得到确认需要：

$$
5RTT
$$

但是题目从请求建立 TCP 数据连接开始计时。

还要加上：

$$
1RTT
$$

的连接建立时间。

因此：

$$
T=1RTT+5RTT
$$

$$
=6\times10\text{ ms}
$$

$$
\boxed{T=60\text{ ms}}
$$

#### 第七问：平均应用数据发送速率
数据量：

$$
18000\times8=144000\text{ bit}
$$

时间：

$$
60\text{ ms}=0.06\text{ s}
$$

因此：

$$
R=\frac{144000}{0.06}
$$

$$
\boxed{R=2.4\text{ Mb/s}}
$$

#### 本题最重要的结论
计算文件传输时间时，必须看清题目：

- 从发送 SYN 开始，还是从连接建立完成开始？
- 到文件最后一个字节发出，还是最后一个 ACK 返回？
- 是否还要计算四次挥手？
- 是计算应用层有效速率，还是链路物理带宽？

这些条件会直接影响结果。

### 9.4 2026 年第 47 题：完整 TCP 生命周期
这道题很适合用来检查是否真正掌握了序号与窗口。

#### 已知条件
客户端 C 上传文件：

$$
F=2000\text{ B}
$$

$$
MSS=500\text{ B}
$$

$$
RTT=5\text{ ms}
$$

$$
ssthresh=8MSS
$$

接收窗口始终：

$$
rwnd=1000\text{ B}
$$

客户端 ISN：

$$
1000
$$

服务器 ISN：

$$
2000
$$

#### 第一问：三次握手的确认号
客户端第一次握手：

```text
SYN=1
seq=1000
```

服务器第二次握手：

```text
SYN=1
ACK=1
seq=2000
ack=1001
```

答案：

$$
\boxed{1001}
$$

#### 第二问：收到 ACK=2001 后 cwnd 和发送窗口
文件分成 4 个段：

| 段  | 起始 seq | 长度   | 收到后的 ACK |
| -- | ------ | ---- | -------- |
| D1 | 1001   | 500B | 1501     |
| D2 | 1501   | 500B | 2001     |
| D3 | 2001   | 500B | 2501     |
| D4 | 2501   | 500B | 3001     |

收到 ACK=2001，说明已经确认前两个段。

按照题设每个段单独确认的慢开始模型：

$$
cwnd=1+2=3MSS
$$

所以：

$$
cwnd=3\times500=1500\text{ B}
$$

但是：

$$
rwnd=1000\text{ B}
$$

发送窗口上限：

$$
W=\min(1500,1000)
$$

$$
\boxed{W=1000\text{ B}}
$$

这又一次说明：拥塞窗口变大，不代表发送窗口也一定同步变大。

#### 第三问：四次挥手中的 seq 与 ack
客户端一共发送 2000B 文件。

数据从：

$$
1001
$$

开始，最后一个数据字节为：

$$
3000
$$

因此客户端 FIN：

```text
seq=3001
```

服务器确认 FIN：

```text
ack=3002
```

服务器没有发送应用数据，自己的 SYN 已占用序号 2000，因此服务器 FIN 序号为：

```text
seq=2001
```

所以 C 最后收到的服务器 FIN：

```text
seq=2001
ack=3002
FIN=1
```

注意要分别维护客户端和服务器两个发送方向的序号。

#### 第四问：文件传完至少需要多久？
按题设的理想 RTT 模型：

| 时刻   | 事件                     |
| ---- | ---------------------- |
| 0ms  | 客户端发 SYN               |
| 5ms  | 收到 SYN+ACK，可发送第 1 个数据段 |
| 10ms | 第 1 段得到确认，可发送第 2、3 段   |
| 15ms | 第 2、3 段得到确认，可发送最后一段    |
| 20ms | 收到最后一个数据段的 ACK         |

所以：

$$
T=4RTT
$$

$$
=4\times5
$$

$$
\boxed{T=20\text{ ms}}
$$

此处题目终点是服务器已经完整接收文件且客户端知道这一结果，不需要把后续关闭连接的时间算进去。

## 十、2027 王道八套卷：模拟综合题精讲
2027 王道冲刺八套卷中有两道传输层综合应用题。

这两道题的意义在于：它们把 TCP 计算从传统的“已知数值直接代公式”，提升到了“阅读真实报文字段、分析连接状态、计算真实剩余发送额度”。

### 10.1 第 7 套第 47 题：十六进制抓包与滑动窗口
题目给出 8 个 IP 数据报。

其中部分报文由主机 A 发出，部分由主机 B 发出，还有一个不属于该 TCP 连接的 ICMP 数据报。

需要完成以下分析。

#### 第一：识别 TCP 握手
IPv4 首部中的协议字段：

```text
06：TCP
01：ICMP
```

先排除不属于 TCP 连接的 ICMP 报文。

再通过 SYN、ACK 位及序号，确定：

$$
\boxed{\text{握手报文为 }1\rightarrow3\rightarrow4}
$$

服务器 B 的初始序号是：

```text
0x5B9FF71C
```

因此 B 的第一个数据字节序号：

```text
0x5B9FF71D
```

#### 第二：处理重复或重叠数据
题目中有这样的数据情况：

| 数据报 | 起始序号      | 数据长度 |
| --- | --------- | ---- |
| 5   | `...B991` | 16B  |
| 7   | `...B9A1` | 16B  |
| 8   | `...B9A1` | 32B  |

注意：

第 7、8 个报文从相同序号开始，其中一部分数据范围重叠。

所以不能简单相加：

$$
16+16+32=64\text{ B}
$$

因为第 8 个报文前 16B 与第 7 个报文对应相同的字节序号。

实际不同的应用数据字节量：

$$
16+16+(32-16)
$$

$$
\boxed{48\text{ B}}
$$

这道题考查的是：TCP 统计的是字节序号覆盖的不同数据，而不是简单累加每个抓到的报文负载。

#### 第三：计算还能发送多少新数据
题目中，B 最近通告：

$$
rwnd=8192\text{ B}
$$

发送方已经发送但尚未从 ACK 获得确认的数据：

$$
FlightSize=32\text{ B}
$$

题目在此小问不考虑更小的拥塞窗口限制。

因此：

$$
L_{\text{new}}=8192-32
$$

$$
\boxed{L_{\text{new}}=8160\text{ B}}
$$

这道题又一次说明：

接收方实际上已经收到某些数据，不代表发送方已经收到对应 ACK。

计算发送方剩余窗口时，要站在发送方当时掌握的信息上。

### 10.2 第 8 套第 47 题：HTTP 与 TCP 综合分析
这道题给出了 HTTP 下载过程中的 14 个 TCP 报文段。

需要判断握手标志、应用层消息、序列号、确认号及窗口变化。

#### 第一：三次握手标志位
| 报文 | SYN | ACK |
| -- | --- | --- |
| S1 | 1   | 0   |
| S2 | 1   | 1   |
| S3 | 0   | 1   |

这是最基础的判断。

#### 第二：HTTP 请求报文
浏览器向服务器请求下载文件，常用方法为：

```text
GET
```

题目中的 S4 是客户端发送的 HTTP 请求报文。

#### 第三：计算缺失的数据长度
题目给出：

```text
S8：
seq=2001
```

之后累计确认：

```text
ACK=3001
```

因此：

$$
L=3001-2001
$$

$$
\boxed{L=1000\text{ B}}
$$

#### 第四：计算后续确认号
按题目明确的连续满 MSS 条件，服务器后续发送到序号：

```text
6001～7000
```

所以接收方累计确认：

$$
\boxed{ACK=7001}
$$

#### 第五：慢开始和拥塞避免的不同窗口
题目给出：

$$
MSS=1000\text{ B}
$$

$$
rwnd=6000\text{ B}
$$

并且当前讨论的此前数据已全部确认。

按题设的教材轮次模型：

如果继续慢开始：

$$
cwnd:4MSS\rightarrow8MSS
$$

发送窗口：

$$
W=\min(8000,6000)
$$

$$
\boxed{W=6000\text{ B}}
$$

如果进入拥塞避免：

$$
cwnd:4MSS\rightarrow5MSS
$$

发送窗口：

$$
W=\min(5000,6000)
$$

$$
\boxed{W=5000\text{ B}}
$$

这两个结果分别对应题目要求比较的两种假设。

需要特别注意：真实 TCP 实现中的逐 ACK 拥塞窗口增长，不一定与教材整轮翻倍模型完全一致。一次累计 ACK 确认多个 MSS，也不能在没有额外条件时直接等同于收到了多个独立 ACK。

| TCP 序号按报文段编号           | TCP 按字节编号            |
| ACK=N 表示收到第 N 个字节      | 表示下一个期望字节序号为 N       |
| SYN 不携带数据，所以不占序号       | SYN 消耗 1 个序号         |
| FIN 不携带数据，所以不占序号       | FIN 消耗 1 个序号         |
| 纯 ACK 占一个序号            | 通常不消耗                |
| 第三次握手不能携带数据            | 可以携带数据               |
| TCP 建连只需两次握手           | 经典 TCP 使用三次握手        |
| TCP 断开一定恰好四个报文段        | ACK 和 FIN 可合并        |
| TIME-WAIT 一定在客户端       | 通常在主动关闭方             |
| 服务器关闭必须等待 2MSL         | 是否等待取决于关闭角色          |
| TCP 首部 Window 就是 cwnd  | Window 通告的是接收窗口 rwnd |

| 发送窗口为 8000B 就还能发 8000B | 还需减去在途数据             |
| 慢开始表示线性慢增长             | 理想模型下按 RTT 约指数增长     |
| 达到 ssthresh 后继续翻倍      | 转为拥塞避免               |
| 超时后 cwnd 直接减半          | 教材模型通常回到 1MSS        |
| 3 个重复 ACK 等同于超时        | 两种事件的窗口处理不同          |
| TCP 完全等于 GBN           | TCP 还有乱序缓存、SACK 等机制  |

| 文件发出最后一个段就完成题目计时       | 可能还需等最终 ACK 返回       |

## 十二、公式速查：考前必须熟练使用
| 类型             | 公式或规则                                             |
| -------------- | ------------------------------------------------- |
| UDP 数据长度       | $L_{\text{payload}}=L_{\text{UDP}}-8$       |
| TCP 首部长度       | $L_{\text{header}}=4\times\text{DataOffset}$ |
| MSS            | $MSS=MTU-L_{IP}-L_{TCP}$                    |
| 数据末字节序号        | $seq+L-1$                                     |
| 下一个数据序号        | $seq+L$                                       |
| 累计确认号          | $ACK=\text{下一个期望字节序号}$                        |
| SYN 后下一个序号     | $seq+1$                                       |
| FIN 后确认号       | $seq+1$，若 FIN 携带数据还需加数据长度                     |
| TCP 发送窗口上限     | $W=\min(rwnd,cwnd)$                           |
| 在途数据           | $FlightSize=SND.NXT-SND.UNA$                  |
| 当前可新发数据        | $\max(0,W-FlightSize)$                        |
| 接收窗口           | $rwnd=RcvBuffer-\text{缓存占用量}$                 |
| 理想慢开始          | $cwnd_k\approx2^kMSS$，仅限适用阶段                  |
| 拥塞避免           | 每 RTT 约增加 $1MSS$                              |
| 超时后门限          | 教材模型常设为超时前窗口的一半                                   |
| 超时后 cwnd       | 经典教材模型为 $1MSS$                                |
| 窗口限制下的吞吐率      | $R\approx8W/RTT$                              |
| 带宽时延积          | $BDP=B\times RTT$                             |
| 文件需要的 MSS 段数   | $\left\lceil F/MSS\right\rceil$               |
| 主动关闭方最快 CLOSED | $RTT+2MSL$                                    |
| 被动关闭方最快 CLOSED | $3RTT/2$                                      |
| RTO 估计         | $RTO=EstimatedRTT+4DevRTT$                    |

注：拥塞控制、文件传输轮次和连接关闭时间的公式，都依赖题目规定的算法及理想化时序假设。

## 十四、真正做 TCP 综合大题的统一方法

我建议考试时建立“三本账”。

<Steps>
  <Step>

    ### 第一本账：序号账本

只记录每个方向的序号变化。

| 事件        | 序号处理   |
| --------- | ------ |
| SYN       | 占用 1   |
| 发送 L 字节数据 | 占用 L   |
| FIN       | 占用 1   |
| 纯 ACK     | 通常占用 0 |

核心公式：

$$
\boxed{ seq_{\text{next}}=seq+L+I_{SYN}+I_{FIN} }
$$

其中指示变量：

$$
I_{SYN},I_{FIN}\in\{0,1\}
$$

同时维护两个独立方向：

```text
客户端 → 服务器：一套seq
服务器 → 客户端：另一套seq
```

不要把双方序号加在同一个账本中。

  </Step>
  <Step>

    ### 第二本账：窗口账本

记录：

```text
rwnd
cwnd
ssthresh
FlightSize
```

每次计算都先问：

接收方有没有空间？

查看：

$$
rwnd
$$

网络拥塞允许多少？

查看：

$$
cwnd
$$

已经发送但尚未确认多少？

查看：

$$
FlightSize
$$

然后计算：

$$
W=\min(rwnd,cwnd)
$$

$$
L_{\text{new}}=\max(0,W-FlightSize)
$$

如果题目问的是窗口上限，到第一步即可；如果问的是还能继续发送多少，再做第二步。

  </Step>
  <Step>

    ### 第三本账：时间账本

记录：

```text
握手消耗多少 RTT
第1轮发送多少
第2轮发送多少
...
最终ACK何时返回
FIN何时发出
什么时候进入TIME-WAIT
什么时候结束2MSL
```

尤其注意：

$$
RTT\neq \frac{RTT}{2}
$$

在题目规定对称传播且忽略其他时延时：

$$
T_{\text{单向}}=\frac{RTT}{2}
$$

而一个数据段从发送到收到确认，通常按一个 RTT 计算。

  </Step>
</Steps>

## 十五、复习顺序与掌握标准
这章最有效的复习顺序是：

第一阶段：打牢序号与确认号。

必须做到看到 SYN、数据长度、FIN，能立刻写出下一个序号。看到乱序接收，能找出第一个缺失字节。

第二阶段：彻底区分三种窗口相关的量。

必须熟悉：

$$
rwnd,\quad cwnd,\quad FlightSize
$$

特别是 2010 年窗口题和 2015 年接收缓存题。

第三阶段：熟练绘制拥塞窗口轨迹。

必须能在纸上快速写出：

```text
慢开始：1 → 2 → 4 → 8

达到门限：8 → 9 → 10

超时：门限减半，重新慢开始

3重复ACK：按题设快速重传/快速恢复
```

第四阶段：训练完整的 RTT 时间轴。

重点研究 2016、2023 和 2024 年的题目，练习区分：

- 握手时间；
- 数据发送时间；
- ACK 返回时间；
- 挥手时间；
- TIME-WAIT 时间。

第五阶段：练习跨层综合题。

重点掌握 2012 年抓包题，以及王道模拟卷中的十六进制报文分析。
