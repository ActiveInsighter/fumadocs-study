<Tab value="调度时间指标">

设进程 $i$ 的到达时间 $A_i$、首次开始时刻 $S_i$、完成时刻 $C_i$、CPU 服务时间 $B_i$，不考虑额外 I/O 等待：

$$
T_i=C_i-A_i,\qquad W_i=T_i-B_i,\qquad R_i=S_i-A_i.
$$

**周转**是到达至完成；**响应**是到达至首次被调度执行；**等待**应扣除实际 CPU 执行时间及题设允许的 I/O 阻塞时间，不可无条件使用单 CPU-burst 公式。

</Tab>
<Tab value="P/V 三类用途">

**互斥**：`mutex=1`；**前驱同步**：`ready=0`，先 `V(ready)` 后方可 `P(ready)`；**容量计数**：`empty=N, full=0`。对多生产者/消费者，阻塞式资源 P 操作应放在获取保护互斥量之前，以免持锁等待造成死锁。

</Tab>
<Tab value="死锁与不安全">

死锁是相关执行主体已因循环或其他资源等待无法继续；**不安全状态**是当前分配下无法构造能保证所有进程完成的安全序列，并不意味着此刻必然已经死锁。

</Tab>
<Tab value="安全性算法">

先算 $Need=Max-Allocation$，令 $Work=Available$；反复找未完成且 $Need_i\le Work$ 的进程并执行 $Work\leftarrow Work+Allocation_i$，最终所有进程能完成才说明存在安全序列。

</Tab>
</Tabs>

## 二、进程与线程：操作系统究竟调度什么？

### 2.1 程序与进程的本质区别

程序是静态的，进程是动态的。

例如磁盘中存在一个 `hello.exe`，它只是程序文件。

当你执行该文件时，操作系统为这次运行建立执行环境、进程管理信息和资源映射。

这次执行活动就构成一个进程。

| 比较          | 程序             | 进程          |
| ----------- | -------------- | ----------- |
| 性质          | 静态             | 动态          |
| 是否具有生命周期    | 程序文件本身没有执行生命周期 | 有创建到终止的生命周期 |
| 是否需要 PCB    | 不需要            | 需要          |
| 是否参与 CPU 调度 | 不直接参与          | 其执行实体参与     |
| 数量关系        | 一个程序可多次执行      | 多个进程可执行同一程序 |

注意两个细节：

- 一个程序能够对应多个同时运行的进程。
- 一个进程在生命周期中也可以通过 `exec` 执行不同的程序映像。

因此进程和程序并不是简单的一一对应关系。

### 2.2 为什么必须引入进程？

假设操作系统同时运行浏览器、音乐播放器和编译器。

操作系统需要知道：

- 每个程序拥有哪些内存和文件资源；
- 谁正在使用 CPU；
- 谁正在等待磁盘数据；
- 谁可以被中断或恢复；
- 某个程序崩溃后，应该清理哪些资源。

仅有程序文件无法解决这些问题。

操作系统需要能够描述运行中的活动及其资源，这就是进程抽象的价值。

经典定义是：

进程是程序的一次执行过程，是系统进行资源分配和保护的基本单位。

在支持线程的操作系统中：

线程是处理机调度和执行的基本单位。

简单记忆：

> 进程解决资源归属问题，线程解决执行问题。

### 2.3 PCB：进程存在的唯一标志

PCB（Process Control Block，进程控制块）是操作系统管理进程的核心数据结构。

408 常用教材强调：

PCB 是进程存在的唯一标志。

这意味着进程即使暂时没有执行，操作系统也能够通过 PCB 知道它的存在和状态。

PCB 通常包含：

| PCB 内容 | 具体信息             | 用途        |
| ------ | ---------------- | --------- |
| 标识信息   | PID、用户标识         | 区分进程      |
| 处理机现场  | PC、寄存器、PSW、SP    | 保存和恢复执行   |
| 调度信息   | 状态、优先级、队列指针      | 决定谁获得 CPU |
| 资源信息   | 内存映射、打开文件、I/O 状态 | 管理进程资源    |

重点理解：PCB 不等于程序代码，也不等于整个进程的内存空间。

PCB 是内核用来管理该进程的控制结构。

#### 典型选择题

下列关于 PCB 的说法，正确的是：

A. PCB 存储在程序的代码段中\
B. 进程运行时才存在 PCB\
C. PCB 是操作系统管理进程的重要依据\
D. PCB 只记录程序计数器

答案：C。

解析：

A 错：PCB 通常由内核管理，不属于普通用户程序的代码段。

B 错：就绪态、阻塞态的进程也有 PCB。

D 错：PCB 包含标识、状态、资源、现场等多类信息。

### 2.4 进程具有哪些基本特征？

考研中通常归纳为五个特征。

| 特征  | 含义                |
| --- | ----------------- |
| 动态性 | 进程具有创建、执行、终止的生命周期 |
| 并发性 | 多个进程在一段时间内交替推进    |
| 独立性 | 进程具有相对独立的资源和运行环境  |
| 异步性 | 各进程执行进度具有不可预知性    |
| 结构性 | 进程由程序、数据和 PCB 等组成 |

其中，动态性是进程最基本的特征。

并发性、异步性又是后面学习同步互斥的原因。

## 三、进程状态与状态转换

这是本章最基础、也最容易被细节题考倒的知识点。

### 3.1 进程五状态模型

| 状态             | 含义         | 最重要的判断      |
| -------------- | ---------- | ----------- |
| 创建态 New        | 正在建立进程运行环境 | 尚未正常进入调度    |
| 就绪态 Ready      | 已具备运行条件    | 只缺 CPU      |
| 运行态 Running    | 正占用 CPU    | 正在执行        |
| 阻塞态 Blocked    | 等待事件或资源    | 有 CPU 也无法继续 |
| 终止态 Terminated | 执行结束       | 等待清理        |

用下面的状态关系理解：

```text
       创建态
          │
          ▼
        就绪态 ◄──────────── 阻塞态
          │                   ▲
          │ 调度              │ 等待I/O/资源
          ▼                   │
        运行态 ───────────────┘
          │  ▲
          │  │
          └──┘
        抢占后回就绪态

运行态 ──执行结束──► 终止态
```

更准确地说，运行态和就绪态之间存在双向转换，而阻塞态通常需要先回到就绪态。

<Callout type="warn" title="阻塞解除后通常先回到就绪，不是直接运行">

发生 I/O 完成、信号量可用等事件时，阻塞进程一般由**阻塞态转就绪态**；只有取得 CPU 才进入运行态。时间片用完通常由运行态回就绪态，不是阻塞态。

</Callout>

### 3.2 六种核心状态转换

| 事件         | 状态变化    | 原因             |
| ---------- | ------- | -------------- |
| 创建成功       | 创建 → 就绪 | 已具备执行条件        |
| 被调度        | 就绪 → 运行 | 获得 CPU         |
| 时间片耗尽      | 运行 → 就绪 | 仍能执行，但暂时失去 CPU |
| 更高优先级进程抢占  | 运行 → 就绪 | CPU 被重新分配      |
| 等待 I/O 或资源 | 运行 → 阻塞 | 当前无法继续执行       |
| 等待事件完成     | 阻塞 → 就绪 | 恢复执行条件         |

核心口诀：

- 时间片耗尽，不是阻塞，而是就绪。
- I/O 请求可能导致阻塞。
- I/O 完成通常转为就绪，而不是直接运行。
- 唤醒不等于立即运行。

### 3.3 为什么阻塞态不能直接转运行态？

假设进程 A 发起磁盘读取，随后进入阻塞态。

磁盘完成读取后，进程 A 已经能够继续执行。

但是 CPU 此刻可能正在运行进程 B。

因此：

$$
\text{Blocked}\rightarrow\text{Ready}
$$

只有调度器以后选择 A，才会发生：

$$
\text{Ready}\rightarrow\text{Running}
$$

教材中的基本状态图通常不画阻塞态直接到运行态的转换。

即使现代系统在同一轮调度过程中迅速唤醒并运行该进程，逻辑上仍然经历了恢复可运行资格和获得 CPU 两个步骤。

### 3.4 阻塞与挂起的区别

两者绝对不能混淆。

阻塞： 进程等待事件。

挂起： 进程被暂停参与正常调度；在经典进程状态模型中，挂起状态常与进程映像换出内存联系在一起。

例如：

- 进程等待键盘输入：阻塞。
- 进程已具备运行条件，但被换出内存：就绪挂起。
- 进程等待磁盘读取，同时被换出：阻塞挂起。

因此，阻塞和挂起可以同时存在。

进一步考虑：

某进程处于阻塞挂起态，等待的 I/O 已经完成，但是它仍然没有被换回内存。

此时可转换为：

$$
\text{阻塞挂起}\rightarrow\text{就绪挂起}
$$

而不是直接进入运行态。

### 3.5 真题思路：什么事件会造成阻塞？

判断以下操作的后果：

I. 时间片耗尽\
II. 执行 P 操作但没有可用资源\
III. 等待磁盘读取完成\
IV. 被更高优先级进程抢占

会导致运行态转为阻塞态的是：

II、III。

理由：

- I：仍然可以运行，只是没有 CPU。
- II：信号量资源不满足，采用阻塞式 P 操作时需要等待。
- III：若采用阻塞式 I/O，进程无法继续执行。
- IV：仍然可以运行，只是被抢占。

特别注意题设中的“可能”与“必然”：

执行 P 操作不一定阻塞。

当资源可以立即获得时，P 操作完成后进程可继续运行。

## 四、进程控制、`fork` 与上下文

### 4.1 四类核心进程控制原语

原语（Primitive）的本质特征是：相关操作必须保持原子性，不允许并发交错破坏中间状态。

| 原语类型 | 主要任务                  |
| ---- | --------------------- |
| 创建原语 | 分配 PID、初始化 PCB、建立执行环境 |
| 终止原语 | 清理资源、记录退出状态、完成回收      |
| 阻塞原语 | 改变状态并进入等待队列           |
| 唤醒原语 | 从等待队列移出并进入就绪队列        |

这里有一个常考细节：

阻塞往往由当前运行的进程主动触发，而唤醒通常由其他执行实体、内核或设备事件触发。

例如：

- A 调用阻塞式 `read()`，主动等待数据。
- 磁盘完成 I/O，触发中断处理。
- 内核唤醒等待该 I/O 的 A。

### 4.2 `fork()`：创建子进程

Unix/Linux 中，`fork()` 用于创建子进程。

```text
pid_t pid = fork();

if (pid == 0) {
    printf("child\n");
} else if (pid > 0) {
    printf("parent\n");
} else {
    printf("error\n");
}
```

一次成功的 `fork()` 会产生两个继续执行的执行流：

- 父进程：返回子进程 PID。
- 子进程：返回 0。

父子进程从 `fork()` 调用返回之后的位置继续。

#### 高频代码题

```c
int main() {
    fork();
    fork();
    printf("A\n");
    return 0;
}
```

假设两次 `fork()` 均成功，标准输出不发生额外异常。

第一次：

$$
1\rightarrow2
$$

第二次：已有的两个进程各创建一个子进程。

$$
2\rightarrow4
$$

因此总共执行四次 `printf`。

输出：

```text
A
A
A
A
```

其中四行的执行先后不确定。

推广：如果有 $n$ 次顺序执行的无条件 `fork()`，且全部成功：

$$
N_{\text{进程}}=2^n
$$

这里计算的是最终包含原始进程在内的进程总数。

若问新创建的子进程数：

$$
N_{\text{新建}}=2^n-1
$$

该公式不能机械用于存在 `if`、提前退出、`exec` 或创建失败的情形。

### 4.3 写时复制 COW

一个很容易产生误解的问题是：

`fork()` 后父子进程是否共享内存？

准确理解：

- 父子进程具有逻辑上独立的虚拟地址空间。
- 创建时可以暂时共享某些物理页面。
- 一方修改共享的写时复制页面时，内核会在必要时复制页面，使修改不影响另一方。

例如：

```c
int x = 10;
pid_t pid = fork();

if (pid == 0) {
    x = 20;
}
```

子进程修改普通私有变量后，不会直接把父进程中的 `x` 改为 20。

这与同一进程内线程共享全局变量的情况不同。

### 4.4 `fork`、`exec`、`wait` 的区别

| 系统调用     | 作用            | 创建新进程？ |
| -------- | ------------- | ------ |
| `fork()` | 创建子进程         | 是      |
| `exec()` | 替换当前程序映像      | 否      |
| `wait()` | 等待并回收子进程的退出状态 | 否      |

常见模式：

```text
pid_t pid = fork();

if (pid == 0) {
    execl("/bin/ls", "ls", NULL);
} else if (pid > 0) {
    wait(NULL);
}
```

执行逻辑是：

父进程创建子进程，子进程执行 `ls`，父进程等待并回收子进程。

成功的 `exec()` 不创建新进程，也不会正常返回原来的程序继续执行。

### 4.5 僵尸进程与孤儿进程

| 类型   | 产生原因               | 核心特点              |
| ---- | ------------------ | ----------------- |
| 僵尸进程 | 子进程已退出，父进程尚未回收退出状态 | 已不运行，但仍保留少量内核信息   |
| 孤儿进程 | 父进程先退出，子进程仍存在      | 可继续执行，由系统适当的收养者接管 |

僵尸进程不是仍在占用 CPU 的进程。

它已经停止执行，只是退出状态尚未完全回收。

## 五、线程与多线程模型

### 5.1 为什么引入线程？

假设浏览器需要同时完成：

- 响应鼠标键盘；
- 渲染页面；
- 下载网络数据；
- 执行后台计算。

如果全部放在单一执行流中，某项耗时操作可能使其他工作长时间得不到处理。

多线程让同一个进程拥有多条执行流。

线程可以共享进程级资源，同时独立地被调度执行。

### 5.2 进程与线程的区别

| 属性    | 进程           | 线程          |
| ----- | ------------ | ----------- |
| 主要作用  | 资源分配与隔离      | 执行与调度       |
| 地址空间  | 不同进程通常独立     | 同进程线程共享     |
| 创建开销  | 通常较大         | 通常较小        |
| 切换开销  | 通常较大         | 同进程线程切换通常较小 |
| 通信方式  | IPC 等        | 共享变量等       |
| 程序计数器 | 每条执行流有自己的 PC | 各线程独有       |
| 栈     | 执行流需要独立栈     | 各线程独有       |

### 5.3 哪些资源共享？哪些资源独有？

这张表属于必背内容。

| 资源           | 同一进程内线程之间 |
| ------------ | --------- |
| 代码段          | 共享        |
| 全局变量         | 共享        |
| 静态变量         | 共享        |
| 堆            | 共享        |
| 虚拟地址空间       | 共享        |
| 打开文件的进程级描述符表 | 共享        |
| 程序计数器 PC     | 独有        |
| 通用寄存器现场      | 独有        |
| 栈指针          | 独有        |
| 线程栈          | 各自独立      |
| 线程状态         | 各自独立      |

最容易错的是栈。

各线程共享地址空间，但不共享同一条调用栈。

不过，因为线程栈位于共享的进程虚拟地址空间内，一个线程仍可能通过错误指针访问其他线程的栈内存。

独立的栈不是独立的内存保护边界。

### 5.4 用户级线程与内核级线程

#### 用户级线程 ULT

线程管理主要由用户态线程库完成。

优点：

- 用户级切换通常无需进入内核；
- 切换开销较小；
- 调度策略比较灵活。

缺点取决于映射模型。

在经典多对一模型中，一个用户线程发起阻塞系统调用，可能导致整个内核调度实体被阻塞。

多个用户线程也无法同时使用多个 CPU 核心执行。

#### 内核级线程 KLT

操作系统内核直接识别并调度这些线程。

优点：

- 可独立调度；
- 一个线程阻塞，其他内核线程仍可能执行；
- 能够充分利用多核处理器。

代价：

- 内核参与线程管理；
- 创建和切换通常需要更多系统开销。

### 5.5 三种线程映射模型

| 模型  | 映射方式            | 是否可多核并行 |
| --- | --------------- | ------- |
| 多对一 | 多个用户线程映射到一个内核线程 | 否       |
| 一对一 | 一个用户线程对应一个内核线程  | 是       |
| 多对多 | 多个用户线程映射到多个内核线程 | 是       |

注意：

能否实现真正多核并行，关键在于是否存在多个可同时调度的内核执行实体。

不能笼统地认为凡是用户级线程都不可能利用多核。

### 5.6 典型题：线程资源共享

某进程有三个线程，以下资源中不能由三个线程共享同一份执行现场的是：

A. 全局变量\
B. 代码段\
C. 程序计数器\
D. 打开的文件描述符表

答案：C。

每个线程必须知道自己下一条执行什么指令，因此有自己的 PC。

### 5.7 进程上下文切换与线程切换

上下文切换是保存当前执行实体的现场，再恢复另一个执行实体的现场。

通常涉及：

- 程序计数器；
- 寄存器；
- 栈指针；
- 调度状态；
- 必要时切换地址空间相关信息。

要区分三个概念：

| 操作        | 主要含义             |
| --------- | ---------------- |
| 用户态 → 内核态 | 处理器特权级变化         |
| 线程上下文切换   | 执行线程发生变化         |
| 进程上下文切换   | 执行实体及相应进程上下文发生变化 |

发生系统调用不一定意味着发生进程切换。

例如进程发起一个很快完成的系统调用，内核处理后可以返回原进程继续执行。

同一进程两个线程切换时，通常不需要更换整个进程地址空间；不同进程切换时，往往需要切换地址空间相关状态。

不过不同体系结构及操作系统的切换成本存在差异，不能绝对认为线程切换没有开销。

## 六、进程间通信 IPC

### 6.1 为什么不同进程不能直接读写彼此变量？

通常情况下，不同用户进程具有不同的虚拟地址空间和内存保护边界。

某个进程中的虚拟地址 `0x1000`，并不意味着另一个进程的同名虚拟地址指向同一个物理内存。

因此，需要操作系统提供进程间通信机制。

### 6.2 常见 IPC 机制比较

| 机制   | 基本特征         | 典型用途    |
| ---- | ------------ | ------- |
| 共享内存 | 不同进程共同映射内存区域 | 大量数据交换  |
| 管道   | 内核管理字节流缓冲区   | 父子进程通信  |
| 消息队列 | 按消息单位收发      | 结构化消息通信 |
| 套接字  | 提供通信端点       | 本机或网络通信 |
| 信号   | 异步事件通知       | 通知某个事件  |
| 信号量  | 同步与资源计数      | 同步互斥    |

#### 共享内存

例如两个进程：

$$
VPN_A\rightarrow PPN_{100}
$$

$$
VPN_B\rightarrow PPN_{100}
$$

两个不同的虚拟页可以映射到同一个物理页。

因此，一个进程的写入能被另一个进程观察到。

但要牢记：

共享内存解决的是数据共享问题，不自动解决同步互斥问题。

两个进程同时写入同一块共享内存，仍可能发生竞争。

#### 管道

普通匿名管道一般用于具有亲缘关系的进程。

它通常具有以下特征：

- 按字节流传输；
- 容量有限；
- 空管道读取可能阻塞；
- 满管道写入可能阻塞；
- 一条普通管道通常只提供一个方向的数据传输。

有名管道 FIFO 则允许没有父子关系的进程通过约定的名称进行通信。

#### 消息队列

与普通字节流管道不同，消息队列具有消息单位的概念。

可以理解为：

```text
发送方
  │
  ▼
[消息1][消息2][消息3]
  │
  ▼
接收方
```

具体系统实现还可能支持消息优先级或消息类型。

### 6.3 IPC 选择题的判断方法

题目出现以下线索时：

- 共享大量数据、减少复制开销： 优先考虑共享内存。
- 父子进程、顺序字节流： 优先考虑匿名管道。
- 具有消息边界： 优先考虑消息队列。
- 不同计算机通过网络通信： 优先考虑套接字。
- 控制访问次序和互斥： 考虑信号量、锁等同步机制。

但不要混淆 Unix/Linux 的 signal 与 semaphore，它们不是同一种机制。

## 七、CPU 调度算法：逐步计算与真题精讲

调度题是本章第一类重点计算题。

掌握的关键不是记住算法名称，而是能够根据到达时间、服务时间和调度规则，准确画出 CPU 执行时间轴。

参考讲义：[处理机调度与上下文切换](https://fumadocscf.any1.tech/docs/408/knowledge2/operating_system/02-process-management/02-scheduling/)

### 7.1 必须掌握的七个时间指标

设：

- $A_i$：进程到达时间。
- $S_i$：第一次获得 CPU 的时间。
- $C_i$：完成时间。
- $B_i$：CPU 服务时间。

则有：

周转时间

$$
T_i=C_i-A_i
$$

带权周转时间

$$
W_i=\frac{T_i}{B_i}
$$

响应时间

$$
R_i=S_i-A_i
$$

若整个模型中没有单独计算 I/O 阻塞时间，则：

等待时间

$$
WT_i=T_i-B_i
$$

平均周转时间：

$$
\overline{T}=\frac{1}{n}\sum_{i=1}^{n}T_i
$$

平均带权周转时间：

$$
\overline{W}=\frac{1}{n}\sum_{i=1}^{n}W_i
$$

注意：

带权周转时间没有时间单位，是一个比值。

存在 I/O 阻塞时，不能直接把周转时间减去 CPU 时间全部当成就绪等待时间。 因为进程可能还有一段时间在等待 I/O。

<Callout type="info" title="统一调度示例的适用范围">

本节示例默认单 CPU、进程仅有一段 CPU 服务时间、忽略上下文切换与额外 I/O 阻塞。若题目包含多次 CPU burst、I/O、抢占或优先级动态变化，等待时间需按实际就绪队列停留时间累计。

</Callout>

### 7.2 统一例题：比较 FCFS、SJF、SRTF 和 RR

假设三个进程如下：

| 进程 | 到达时间 | CPU 服务时间 |
| -- | ---- | -------- |
| P1 | 0    | 8        |
| P2 | 1    | 4        |
| P3 | 2    | 2        |

单 CPU，忽略上下文切换开销。

### 第一种：FCFS 先来先服务

按到达顺序执行：

```text
时间  0        8    12   14
      |---P1---|--P2-|P3|
```

完成时间：

$$
C_1=8,\quad C_2=12,\quad C_3=14
$$

周转时间：

$$
T_1=8-0=8
$$

$$
T_2=12-1=11
$$

$$
T_3=14-2=12
$$

平均周转时间：

$$
\overline{T}_{FCFS} =\frac{8+11+12}{3} =\frac{31}{3}\approx10.33
$$

等待时间：

$$
WT_1=0,\quad WT_2=7,\quad WT_3=10
$$

平均等待时间：

$$
\overline{WT}_{FCFS}=\frac{17}{3}\approx5.67
$$

FCFS 最大的问题是：一个长进程可能让后来到达的短进程等待很久。

这就是护航效应。

### 第二种：SJF 最短作业优先

经典 SJF 是非抢占式。

在 $t=0$ 时，只有 P1 到达，因此必须选择 P1。

即使 P2、P3 后来到达，P1 也不会被抢占。

到 $t=8$ 时：

- P2 服务时间 4；
- P3 服务时间 2。

先执行 P3，再执行 P2。

```text
时间  0        8   10     14
      |---P1---|-P3|--P2--|
```

完成时间：

$$
C_1=8,\quad C_2=14,\quad C_3=10
$$

平均周转时间：

$$
\overline{T}_{SJF} =\frac{8+(14-1)+(10-2)}{3} =\frac{29}{3}\approx9.67
$$

关键陷阱：SJF 不是一开始就把所有进程按照服务时间排序。

尚未到达的进程不参与当前调度决策。

### 第三种：SRTF 最短剩余时间优先

这是抢占式算法。

逐个事件分析。

时刻 $t=0$

只有 P1，开始运行。

时刻 $t=1$

P2 到达。

此时：

$$
Remaining(P1)=7
$$

$$
Remaining(P2)=4
$$

因为 $4<7$，所以 P2 抢占 P1。

时刻 $t=2$

P3 到达。

此时：

$$
Remaining(P2)=3
$$

$$
Remaining(P3)=2
$$

因为 $2<3$，所以 P3 抢占 P2。

后续：

- P3 在 $t=4$ 完成；
- P2 在 $t=4\sim7$ 完成；
- P1 最后运行到 $t=14$。

```text
时间  0  1  2    4     7          14
      |P1|P2| P3 |  P2 |    P1     |
```

周转时间：

$$
T_1=14
$$

$$
T_2=7-1=6
$$

$$
T_3=4-2=2
$$

平均周转时间：

$$
\overline{T}_{SRTF} =\frac{14+6+2}{3} =\frac{22}{3}\approx7.33
$$

等待时间：

$$
WT_1=14-8=6
$$

$$
WT_2=6-4=2
$$

$$
WT_3=2-2=0
$$

平均等待时间：

$$
\overline{WT}_{SRTF}=\frac{8}{3}\approx2.67
$$

这里可以看到：

对于这组进程，SRTF 的平均等待时间明显小于 FCFS。

但它可能造成长作业饥饿，并且需要频繁重新评估剩余运行时间。

#### 第四种：RR 时间片轮转

设：

$$
q=2
$$

每个进程一次最多执行两个时间单位。

假设在时间片到期与新进程到达恰好同时发生时，先将新到达进程入队，再把未完成的当前进程放到队尾。

时间轴：

```text
时间  0  2  4  6  8  10 12 14
      |P1|P2|P3|P1|P2|P1|P1|
```

运行过程：

| 时间区间  | 运行进程 | 执行后剩余时间 |
| ----- | ---- | ------- |
| 0～2   | P1   | 6       |
| 2～4   | P2   | 2       |
| 4～6   | P3   | 0       |
| 6～8   | P1   | 4       |
| 8～10  | P2   | 0       |
| 10～12 | P1   | 2       |
| 12～14 | P1   | 0       |

完成时间：

$$
C_1=14,\quad C_2=10,\quad C_3=6
$$

周转时间：

$$
T_1=14,\quad T_2=9,\quad T_3=4
$$

平均周转时间：

$$
\overline{T}_{RR}=\frac{27}{3}=9
$$

首次响应时间：

$$
R_1=0,\quad R_2=1,\quad R_3=2
$$

RR 的优势主要在交互响应和时间分配公平性。

时间片轮转不保证平均周转时间最小。

#### 四种算法最终对比

| 算法            | 平均周转时间 | 平均等待时间 |
| ------------- | ------ | ------ |
| FCFS          | 10.33  | 5.67   |
| SJF           | 9.67   | 5.00   |
| SRTF          | 7.33   | 2.67   |
| RR（$q=2$） | 9.00   | 4.33   |

这些结果只针对上面的具体例子。

不能据此断言 RR 在所有情形下都优于 SJF，或者任何算法都能对所有指标同时最优。

### 7.3 HRRN 最高响应比优先

公式必须记住：

$$
R=\frac{W+S}{S}=1+\frac{W}{S}
$$

其中：

- $W$：当前已等待时间；
- $S$：所需服务时间。

例如当前时刻为 10：

| 进程 | 到达时间 | 服务时间 |
| -- | ---- | ---- |
| A  | 0    | 8    |
| B  | 4    | 2    |
| C  | 6    | 3    |

假设三者均处于就绪态。

计算响应比：

$$
R_A=1+\frac{10}{8}=2.25
$$

$$
R_B=1+\frac{6}{2}=4
$$

$$
R_C=1+\frac{4}{3}\approx2.33
$$

因此选择 B。

一个常见误区是把 HRRN 中的“响应比”与响应时间混淆。

HRRN 响应比不是首次响应时间。

它综合考虑等待时间与服务时间，是调度优先程度的指标。

### 7.4 2016 年真题：动态优先级与饥饿

原稿引用的大题库收录了 2016 年第 46 题。

题目给定：

- `nice`：静态优先数；
- `cpuTime`：运行时累计时间；
- `waitTime`：就绪等待时累计时间；
- 优先数越小，优先级越高。

问如何避免低优先级进程长期饥饿。

可以设计：

$$
priority=nice+\alpha\cdot cpuTime-\beta\cdot waitTime
$$

其中：

$$
\alpha>0,\qquad\beta>0
$$

理解：

运行越久：

$$
cpuTime\uparrow \Rightarrow priority\uparrow
$$

由于数值越小越优先，因此当前任务的相对优先程度下降。

等待越久：

$$
waitTime\uparrow \Rightarrow priority\downarrow
$$

于是等待任务的相对优先程度上升。

这就是老化思想。

在适当的有界任务和调度假设下，持续增长的等待补偿可以防止任务一直被高优先级进程压制。

考试尤其要注意优先数方向：本题是数值越小越优先。

如果把 `waitTime` 写成正号，就会让等待越久的进程优先级越来越低，适得其反。

<Callout type="warn" title="优先级调度：中断是抢占检查点，不一定代表上下文切换">

进程到达的时刻与实际抢占的时刻可不同；当题设只允许在时钟中断时进行抢占判断，必须在该时刻重新比较优先级。时间片耗尽、优先级抢占、同优先级入队三条规则应分别处理。中断次数和进程调度次数不能互换。

</Callout>

### 7.5 2026 年大题：优先级 + 时间片 + 定时抢占

原稿引用的大题库中还收录了 2026 年第 45 题。这一题适合检验调度知识是否真正掌握。

题设：

- 优先级数值越大越优先。
- 时间片为 50 ms。
- 时钟中断每 10 ms 发生一次。
- 只有时钟中断才能触发优先级抢占。
- 时间片耗尽后优先级减 1。
- 被高优先级进程抢占，不降低优先级。
- 同优先级按进入就绪队列的先后排序。

进程信息：

| 进程 | 到达时间 ms | 初始优先级 | CPU 时间 ms |
| -- | ------- | ----- | --------- |
| P1 | 10      | 3     | 95        |
| P2 | 10      | 4     | 20        |
| P3 | 12      | 2     | 40        |
| P4 | 14      | 5     | 60        |

#### 逐步推导

第一步：10 ms 开始。

P1、P2 同时到达。

P2 优先级 4 高于 P1 的 3，先选 P2。

第二步：12 ms、14 ms。

P3 和 P4 到达。

尽管 P4 的优先级最高，但题目规定只能在时钟中断时触发抢占。

因此 14 ms 不会立即抢占 P2。

直到 20 ms 才发生调度变化。

第三步：20 ms。

P4 抢占 P2。

P2 已运行 10 ms，还剩 10 ms，优先级保持 4。

P4 开始运行。

第四步：70 ms。

P4 已执行完整的 50 ms 时间片，还剩 10 ms。

其优先级由 5 降为 4。

此时 P2 与 P4 均为优先级 4，但 P2 更早进入就绪队列，所以先执行 P2。

第五步：后续运行。

完整时间轴：

| 时间区间 ms | 运行进程 | 事件         |
| ------- | ---- | ---------- |
| 10～20   | P2   | 被 P4 抢占    |
| 20～70   | P4   | 时间片耗尽，降优先级 |
| 70～80   | P2   | 完成         |
| 80～90   | P4   | 完成         |
| 90～140  | P1   | 时间片耗尽，降优先级 |
| 140～180 | P3   | 完成         |
| 180～225 | P1   | 完成         |

首次获得 CPU 的时间：

$$
S_1=90,\quad S_2=10
$$

$$
S_3=140,\quad S_4=20
$$

因此首次响应时间为：

$$
R_1=90-10=80
$$

$$
R_2=10-10=0
$$

$$
R_3=140-12=128
$$

$$
R_4=20-14=6
$$

按题库采用的从 10 ms 起统计时钟中断、并将开始时刻的时钟事件计入的口径，共有 22 次时钟中断、7 次 CPU 调度。

这里需要特别理解：

时钟中断次数不等于调度次数，也不等于进程上下文切换次数。

一个时钟中断可能只更新计时信息，而不导致执行进程改变。

若将时间片增加为 100 ms，按同样规则重新模拟，运行片段数减少到 5 段。

若时钟中断周期从 10 ms 缩短至 1 ms，定时中断频率提高，系统处理时钟中断的开销通常增加。

这题可归纳成三个必考判断：

1. 进程到达时刻不一定就是抢占时刻。
2. 时间片耗尽和高优先级抢占，可能具有不同后果。
3. 同一优先级下，需要进一步判断就绪队列顺序。

## 八、进程同步与互斥：第二章的核心原理

参考讲义：[同步、互斥、信号量与管程](https://fumadocscf.any1.tech/docs/408/knowledge2/operating_system/02-process-management/03-synchronization/)

### 8.1 为什么需要同步与互斥？

假设有一个共享变量：

```c
int count = 5;
```

两个线程各执行一次：

```text
count++;
```

直觉上：

$$
count=7
$$

但 `count++` 不一定是原子操作。

可能被分解为：

```text
读取 count
加 1
写回 count
```

一种错误交错：

| 步骤 | 线程 A | 线程 B |
| -- | ---- | ---- |
| 1  | 读取 5 |      |
| 2  |      | 读取 5 |
| 3  | 计算 6 |      |
| 4  |      | 计算 6 |
| 5  | 写入 6 |      |
| 6  |      | 写入 6 |

最终：

$$
count=6
$$

一次更新被覆盖。

这种由于并发执行顺序不同而导致错误结果的现象，就是竞态条件。

### 8.2 四个基础概念

临界资源： 需要互斥访问的共享资源。

临界区： 程序中访问临界资源、需要互斥保护的代码段。

互斥： 不允许多个执行实体同时执行冲突操作。

同步： 多个执行实体必须满足一定先后次序。

互斥是“不能同时”，同步是“必须按顺序”。

例如：

两个线程同时修改银行余额，需要互斥。

生产者必须先生产，消费者才能取走产品，需要同步。

生产者与消费者访问同一个缓冲区内部数据结构时，还可能需要互斥。

### 8.3 临界区问题的四项经典原则

| 原则   | 含义                   |
| ---- | -------------------- |
| 空闲让进 | 临界区空闲时，应允许申请者进入      |
| 忙则等待 | 有线程正在临界区时，其他冲突线程不能进入 |
| 有限等待 | 不应使申请者无期限等待          |
| 让权等待 | 无法进入时应尽量放弃 CPU       |

注意：教材介绍的不同互斥方法，并不一定全部满足四项要求。

例如自旋锁无法进入时持续占用 CPU，因此不满足经典意义上的让权等待。

### 8.4 为什么普通布尔锁不可靠？

错误代码：

```text
while (lock == true);

lock = true;

critical_section();

lock = false;
```

问题发生在：

```text
检查 lock
设置 lock
```

这两步之间存在时间间隙。

两个线程完全可能同时读到 `false`。

因此，判断锁是否空闲与占有锁的动作必须具有原子性。

### 8.5 Peterson 算法

这是经典的双进程软件互斥算法。

共享变量：

```c
bool flag[2] = {false, false};
int turn = 0;
```

线程 0：

```text
flag[0] = true;
turn = 1;

while (flag[1] && turn == 1);

// 临界区

flag[0] = false;
```

线程 1：

```text
flag[1] = true;
turn = 0;

while (flag[0] && turn == 0);

// 临界区

flag[1] = false;
```

#### 为什么能互斥？

考虑两个线程都希望进入临界区。

于是：

$$
flag[0]=true
$$

$$
flag[1]=true
$$

两个线程都执行了 `turn` 赋值。

最终共享的 `turn` 只可能是 0 或 1。

如果：

$$
turn=0
$$

那么线程 1 的等待条件为：

```text
flag[0] && turn == 0
```

成立。

线程 1 等待，线程 0 可以进入。

反过来：

$$
turn=1
$$

线程 0 等待，线程 1 可以进入。

因此双方不可能同时越过等待条件进入临界区。

#### Peterson 的重要局限

它是用于理解互斥原理的经典算法。

普通共享变量版本依赖特定的顺序一致性假设。

现代编译器和多核 CPU 可能重排内存操作，因此不能直接把这种教材伪代码当作可靠的生产环境锁实现。

此外，Peterson 算法使用忙等，不满足让权等待。

### 8.6 硬件互斥：TSL、Swap、CAS

#### TSL：测试并设置

Test-and-Set 的关键不是简单地读取变量，而是：

读取原值与写入新值必须是不可分割的原子操作。

例如：

```text
while (TestAndSet(&lock)) {
    // 自旋等待
}

// 临界区

lock = false;
```

当锁原值是 `false` 时，第一个线程获得锁。

其他线程只能持续等待。

#### Swap：原子交换

共享变量：

```text
bool lock = false;
```

正确的基本互斥写法：

```text
bool key = true;

while (key == true) {
    Swap(key, lock);
}

// 临界区

lock = false;
```

如果 `Swap` 是硬件原子指令，交换动作不会被其他线程插入破坏。

#### CAS：比较并交换

CAS 的思想是：

只有当内存中的值仍然等于预期旧值时，才将其修改为新值。

例如：

```text
while (!CAS(&lock, false, true)) {
    // 等待
}

// 临界区

lock = false;
```

实际 CAS 接口的参数和返回值形式可能不同，做题以题设定义为准。

#### 三者共同点

它们都依赖原子读—改—写能力，避免多个线程同时通过不安全的检查步骤。

但要区分：

- 原子性：操作不会被并发干扰。
- 让权等待：等待期间不无意义占用 CPU。
- 有限等待：最终能够获得机会。

原子指令本身不自动保证公平，也不自动避免饥饿。

### 8.7 2023 年真题：Swap 互斥代码改错

原稿引用的大题库收录的 2023 年第 45 题，直接考查 Swap。

错误代码的核心结构为：

```text
bool key = true;

if (key == true)
    swap(key, lock);

// 临界区

lock = true;
```

要求改错且不增加语句条数。

错误一：`if` 应改成 `while`。

原因：

如果交换后没有取得锁，`if` 仅执行一次就继续往下走，仍可能进入临界区。

应持续尝试直到成功。

错误二：退出临界区时应设置 `lock=false`。

因为：

```text
true  = 被占用
false = 空闲
```

正确结构：

```text
bool key = true;

while (key == true)
    swap(key, lock);

// 临界区

lock = false;
```

题目进一步询问：

能否用普通 C 函数实现的变量交换，代替原子 Swap 指令？

不能直接代替。

例如：

```c
void newSwap(bool *a, bool *b) {
    bool temp = *a;
    *a = *b;
    *b = temp;
}
```

这由多个普通读写操作构成。

执行过程中可能被其他线程穿插，无法保证原子交换语义。

因此 2023 年这题的真正考点不是背代码，而是理解：

> 看起来功能相同的交换代码，不一定具有相同的并发语义。

### 8.8 自旋锁与阻塞锁

| 对比        | 自旋锁     | 阻塞式互斥锁  |
| --------- | ------- | ------- |
| 等待方式      | 循环检查    | 阻塞并等待唤醒 |
| 是否持续占 CPU | 通常是     | 阻塞期间否   |
| 是否需要睡眠/唤醒 | 不必      | 通常需要    |
| 更适合       | 预期等待非常短 | 预期等待较长  |
| 典型问题      | 浪费 CPU  | 阻塞唤醒开销  |

注意：

持有锁不意味着不可被抢占。

一个线程进入临界区后，操作系统仍可能暂时调度其他线程。

但其他竞争同一把锁的线程不能同时进入受保护临界区。

### 8.9 条件变量与管程

管程是一种高级同步抽象。

它将共享状态、操作过程、互斥规则和条件变量统一组织。

典型代码：

```text
lock(mutex);

while (!condition) {
    wait(cond, mutex);
}

// 在条件满足时访问共享数据

unlock(mutex);
```

这里 `wait(cond, mutex)` 的关键特点是：

原子地释放互斥锁并进入等待状态。

被唤醒后，还必须重新获得互斥锁，才能从等待操作返回。

为什么通常使用 `while` 而不是 `if`？

因为被唤醒不保证当前共享条件仍然成立。

其他线程可能已经改变条件，某些条件变量实现还允许伪唤醒。

因此必须重新检查。

#### 信号量与条件变量区别

| 对比        | 信号量      | 条件变量                  |
| --------- | -------- | --------------------- |
| 主要作用      | 计数、互斥、同步 | 等待共享状态变化              |
| 是否积累通知    | 计数许可可以积累 | 通常不会                  |
| 是否需要搭配互斥锁 | 依设计而定    | 典型用法需要                |
| 操作        | P/V      | wait/signal/broadcast |

这个区别很重要。

例如信号量初值为 0，即使没人等待，执行一次 `V(S)`，也可以让后续一次 `P(S)`通过。

但是对一个没有等待者的条件变量执行 `signal()`，通常不会保存一个供未来使用的通知。

## 九、P/V 信号量：必须彻底掌握的综合题工具

### 9.1 P/V 操作到底是什么？

信号量是一种同步抽象。

可以把信号量理解成一个具有原子操作保证的许可计数器。

对于阻塞式信号量：

- P：申请一份许可，拿不到就等待。
- V：释放一份许可，必要时唤醒等待者。

一种经典教材定义：

```text
P(S) {
    S.value--;

    if (S.value < 0) {
        block();
    }
}
```

```text
V(S) {
    S.value++;

    if (S.value <= 0) {
        wakeup();
    }
}
```

这里 `block()` 和 `wakeup()` 只是说明同步语义的抽象伪代码。

真正实现必须确保计数修改、等待入队和唤醒不会发生破坏性竞争。

<Callout type="info" title="负信号量取决于所用 P/V 记账语义">

在教材的**整数信号量/记录型信号量**模型中，若先递减再睡眠，负值可表征等待进程数量；在某些实际信号量 API 实现中，内部计数不会直接以负数暴露。判题先遵循所给 P/V 定义。

</Callout>

### 9.2 信号量为什么可能是负数？

在上述经典定义中：

若：

$$
S=3
$$

表示尚有 3 个可用许可。

若：

$$
S=0
$$

表示没有空闲许可。

若：

$$
S=-2
$$

表示已经有两个执行实体因该信号量而等待。

注意这是允许负值的教材信号量模型。

有些实际操作系统 API 使用始终非负的计数器并单独管理等待队列，因此不能认为所有信号量实现都直接以负数表示等待者数量。

### 9.3 P/V 最重要的三种模型

#### 模型一：互斥

题目说：

> 同一时刻最多只允许一个进程使用。

写成：

```c
semaphore mutex = 1;

P(mutex);

critical_section();

V(mutex);
```

信号量初值为 1，因为开始时只有一个独占许可。

#### 模型二：前驱同步

题目说：

> B 必须在 A 完成后执行。

写成：

```c
semaphore S = 0;

process A {
    operation_A();
    V(S);
}

process B {
    P(S);
    operation_B();
}
```

初值为 0，表示 A 尚未完成。

这是本章极其重要的一条规律：

A 完成后 V，B 开始前 P。

#### 模型三：资源容量

题目说：

> 最多允许 5 个进程同时使用某类资源。

写成：

```c
semaphore resource = 5;

P(resource);

use_resource();

V(resource);
```

信号量初值等于资源容量。

### 9.4 前驱关系图：2020 年真题

题设有五个操作：

$$
A,B,C,D,E
$$

要求：

- C 必须在 A 和 B 都完成后执行；
- E 必须在 C 和 D 都完成后执行。

画前驱关系：

```text
A ─┐
   ├──► C ──┐
B ─┘        ├──► E
D ──────────┘
```

可以给四条直接前驱边分别设一个信号量：

$$
S_{AC}=S_{BC}=S_{CE}=S_{DE}=0
$$

对应代码：

```c
semaphore ac = 0;
semaphore bc = 0;
semaphore ce = 0;
semaphore de = 0;

process PA {
    A;
    V(ac);
}

process PB {
    B;
    V(bc);
}

process PC {
    P(ac);
    P(bc);

    C;

    V(ce);
}

process PD {
    D;
    V(de);
}

process PE {
    P(ce);
    P(de);

    E;
}
```

#### 为什么 C 前面要两个 P？

因为 C 的执行条件是：

$$
A\text{ 完成}\land B\text{ 完成}
$$

不是：

$$
A\text{ 完成}\lor B\text{ 完成}
$$

所以：

```text
P(ac);
P(bc);
```

两次等待都必须通过，C 才能执行。

#### 为什么不需要给 A、B、D 加互斥锁？

因为题目没有要求它们不能同时执行。

强行加互斥锁会人为减少并发程度。

P/V 大题不是信号量越多越安全，而是要准确满足约束，并尽可能保留允许的并发。

### 9.5 2022 年真题：最少同步信号量

原题给定两个线程：

线程 T1：

```text
A → E → F
```

线程 T2：

```text
B → C → D
```

额外要求：

- C 在 A、B 完成后执行；
- D、E 在 C 完成后执行；
- F 在 E 完成后执行。

首先利用同一线程天然存在的程序顺序。

T2 中：

$$
B\rightarrow C\rightarrow D
$$

已经保证 B 先于 C、C 先于 D。

T1 中：

$$
A\rightarrow E\rightarrow F
$$

已经保证 A 先于 E、E 先于 F。

所以实际需要额外同步的跨线程关系只有：

$$
A\rightarrow C
$$

$$
C\rightarrow E
$$

只需要两个信号量！

```c
semaphore SA = 0;
semaphore SC = 0;

thread T1 {
    A;
    V(SA);

    P(SC);
    E;
    F;
}

thread T2 {
    B;
    P(SA);

    C;
    V(SC);

    D;
}
```

这是非常重要的高阶技巧：

先利用线程内部已有的执行顺序，再为跨线程的必要依赖设置同步信号量。

不能看到前驱图有五条箭头，就机械设置五个信号量。

<Callout type="error" title="高频错误：持有 mutex 后再等待 empty/full">

在有界缓冲区中，先 `P(mutex)` 后阻塞于 `P(empty)` 或 `P(full)`，可能阻止另一方进入临界区以改变缓冲状态，形成死锁。典型正确顺序：**先 P 资源计数，再 P 互斥量；退出时先 V 互斥量，再 V 对应资源计数**。

</Callout>

### 9.6 P/V 顺序错误为什么会造成死锁？

假设有一个容量为 1 的缓冲区。

生产者和消费者共享：

```c
semaphore mutex = 1;
semaphore empty = 1;
semaphore full = 0;
```

某消费者错误地执行：

```text
P(mutex);
P(full);
```

此时缓冲区为空：

$$
full=0
$$

消费者取得 `mutex` 后，阻塞于 `P(full)`。

生产者想放入产品：

```text
P(empty);
P(mutex);
```

生产者虽然可以获得 `empty`，却无法获得 `mutex`。

于是：

```text
消费者：
持有 mutex
等待 full

生产者：
需要 mutex
才能生产并 V(full)
```

双方都无法继续。

这就形成死锁。

正确顺序是：

```text
P(full);
P(mutex);
```

先等待需要的资源条件，再进入互斥临界区。

P/V 大题一定优先检查 P 操作的顺序。

## 十、经典同步问题：综合大题重点

参考讲义：[经典同步问题专题](https://fumadocscf.any1.tech/docs/408/knowledge2/operating_system/02-process-management/04-classic-sync/)

### 10.1 生产者—消费者问题

设一个容量为 $N$ 的缓冲区。

生产者：

```text
生产产品 → 放入缓冲区
```

消费者：

```text
从缓冲区取产品 → 消费产品
```

需要解决三个问题：

1. 缓冲区满，生产者必须等待。
2. 缓冲区空，消费者必须等待。
3. 多个进程访问共享缓冲区的冲突操作必须互斥。

因此设置：

```c
semaphore empty = N;
semaphore full = 0;
semaphore mutex = 1;
```

#### 标准答案

```c
producer() {
    while (true) {
        item = produce();

        P(empty);
        P(mutex);

        put(item);

        V(mutex);
        V(full);
    }
}
```

```c
consumer() {
    while (true) {
        P(full);
        P(mutex);

        item = get();

        V(mutex);
        V(empty);

        consume(item);
    }
}
```

#### 三个信号量分别解决什么问题？

| 信号量   | 初值 | 作用           |
| ----- | -- | ------------ |
| empty | N  | 控制空缓冲区数量     |
| full  | 0  | 控制已有产品数量     |
| mutex | 1  | 保证冲突的缓冲区操作互斥 |

这里还有一个容易被误记的细节。

常说的：

$$
empty+full=N
$$

表示容量守恒的基本思想。

但如果把 `empty` 和 `full` 理解成实际信号量内部的瞬时数值，则不能保证任意指令执行时二者之和恒等于 $N$。

因为生产者可能已经执行 `P(empty)`，但尚未执行 `V(full)`，这时一个槽位已经被预留，却尚未正式计入满槽许可。

正确的不变量应把在途的预留许可也考虑进去。

考研概念题通常使用“空槽 + 满槽 = 容量”的宏观资源模型；在分析代码交错和不变量时，要进一步考虑正在执行中的操作。

### 10.2 2009 年真题：奇偶数生产者—消费者

原题设置：

- 生产者 P1 产生正整数；
- 消费者 P2 专门取奇数；
- 消费者 P3 专门取偶数；
- 共享一个容量为 $N$ 的缓冲区。

这里不是普通的一个消费者，而是按产品类别区分消费者。

#### 第一步：分析资源

缓冲区共 $N$ 个槽。

所以：

$$
empty=N
$$

奇数数量初始为 0：

$$
odd=0
$$

偶数数量初始为 0：

$$
even=0
$$

保护缓冲区：

$$
mutex=1
$$

#### 第二步：写生产者

```c
semaphore empty = N;
semaphore odd = 0;
semaphore even = 0;
semaphore mutex = 1;

process P1 {
    while (true) {
        int x = produce();

        P(empty);
        P(mutex);

        put(x);

        V(mutex);

        if (x % 2 == 1)
            V(odd);
        else
            V(even);
    }
}
```

#### 第三步：写奇数消费者

```c
process P2 {
    while (true) {
        P(odd);
        P(mutex);

        int x = getodd();

        V(mutex);
        V(empty);

        countodd(x);
    }
}
```

#### 第四步：写偶数消费者

```c
process P3 {
    while (true) {
        P(even);
        P(mutex);

        int x = geteven();

        V(mutex);
        V(empty);

        counteven(x);
    }
}
```

#### 这题最关键的思路

为什么不能只有一个 `full`？

因为：

- 奇数消费者只能消费奇数；
- 偶数消费者只能消费偶数。

如果所有产品共用一个满槽信号量，它只表示“缓冲区非空”，无法保证被唤醒的消费者能够取到自己需要的类别。

因此应设置两个产品计数信号量。

这类题的通用方法是：

有多少种需要被独立等待的资源或产品条件，就考虑为多少种条件建立同步计数。

当然，仍要避免机械增加不必要的信号量。

### 10.3 2014 年真题：连续取 10 件产品

题设：

- 环形缓冲区容量为 1000。
- 多个生产者与多个消费者。
- 缓冲区初始为空。
- 一个消费者必须连续取出 10 件产品，其他消费者才能开始取产品。

普通生产者—消费者模型无法直接保证“连续 10 件”。

为什么？

因为：

```text
消费者 A 取 1 件
消费者 B 取 1 件
消费者 A 再取 1 件
```

虽然缓冲区访问互斥，但 A 并没有连续取够 10 件。

#### 核心技巧：增加组级互斥

除了普通的三个信号量：

```c
semaphore empty = 1000;
semaphore full = 0;
semaphore mutex = 1;
```

还需要：

```c
semaphore group = 1;
```

消费者：

```c
consumer() {
    while (true) {
        P(group);

        for (int i = 0; i < 10; i++) {
            P(full);
            P(mutex);

            item = get();

            V(mutex);
            V(empty);

            consume(item);
        }

        V(group);
    }
}
```

生产者依旧按照标准生产者代码执行。

#### 为什么组级锁不能直接使用 mutex？

如果消费者 A 持有 `mutex`，还想等待 10 件产品全部到达，则可能阻止生产者进入缓冲区。

生产者不能放产品，消费者又一直等产品，系统可能死锁。

因此要区分：

- `mutex`：单次访问共享缓冲区的互斥。
- `group`：不同消费者之间的整组操作互斥。

当消费者 A 暂时等待产品时，它可以继续持有 `group`，因为生产者不需要这把锁。

但不能持有缓冲区 `mutex` 等待产品。

这也是大题的重要思想：

不同层级的互斥约束，可能需要不同的信号量。

### 10.4 读者—写者问题

问题要求：

- 多个读者可以同时读取；
- 写者必须独占；
- 写者之间必须互斥；
- 读者和写者不能同时访问。

三种常见策略：

| 策略   | 核心特点             | 潜在问题   |
| ---- | ---------------- | ------ |
| 读者优先 | 只要持续有读者，新读者也可能加入 | 写者饥饿   |
| 写者优先 | 有写者等待后，限制新读者进入   | 读者可能饥饿 |
| 公平策略 | 按排队或批次规则分配访问机会   | 实现相对复杂 |

#### 读者优先算法

共享变量：

```c
int read_count = 0;

semaphore rmutex = 1;
semaphore rw = 1;
```

读者：

```c
reader() {
    while (true) {
        P(rmutex);

        read_count++;

        if (read_count == 1)
            P(rw);

        V(rmutex);

        read();

        P(rmutex);

        read_count--;

        if (read_count == 0)
            V(rw);

        V(rmutex);
    }
}
```

写者：

```c
writer() {
    while (true) {
        P(rw);

        write();

        V(rw);
    }
}
```

#### 为什么第一个读者要 P(rw)？

当：

$$
read\\_count=0
$$

新的读者进来，计数变成：

$$
read\\_count=1
$$

此时必须阻止写者。

所以第一个读者执行：

```text
P(rw);
```

#### 为什么后来的读者不需要再 P(rw)？

因为已有读者群体取得了读取权限。

新读者可以加入该群体并发读取。

#### 为什么最后一个读者要 V(rw)？

当：

$$
read\\_count=0
$$

说明所有读者都已退出。

此时才允许写者独占。

这套设计可以概括为：

第一个读者负责加写锁，最后一个读者负责释放写锁。

但注意：`read_count` 也是共享变量，所以增减它需要互斥保护。

#### 写者优先与公平设计

写者优先需要额外控制新读者入口。

可以设置：

```c
int write_count = 0;

semaphore write_mutex = 1;
semaphore readTry = 1;
```

第一个等待写入的写者通过 `P(readTry)` 关闭新读者入口，最后一个写者通过 `V(readTry)` 开放入口。

具体实现还需要与 `rw`、读者计数及对应锁配合。

考研通常重点考三个问题：

1. 为什么可以同时有多个读者？
2. 为什么写者需要独占？
3. 不同优先策略为什么可能导致饥饿？

公平策略还需明确底层等待队列的公平规则，单纯增加一个信号量不自动保证严格 FIFO 公平。

### 10.5 哲学家就餐问题

设有 $n$ 个哲学家围坐。

每人需要左右两根筷子才能吃饭。

如果所有人都是：

```text
P(left);
P(right);

eat();

V(right);
V(left);
```

则可能出现：

```text
P0 拿左筷子，等右筷子
P1 拿左筷子，等右筷子
P2 拿左筷子，等右筷子
...
```

形成循环等待。

#### 方法一：限制最多 $n-1$ 人同时取筷子

```c
semaphore room = n - 1;
semaphore chopstick[n] = {1};

philosopher(int i) {
    while (true) {
        think();

        P(room);

        P(chopstick[i]);
        P(chopstick[(i + 1) % n]);

        eat();

        V(chopstick[(i + 1) % n]);
        V(chopstick[i]);

        V(room);
    }
}
```

因为至少有一个哲学家没有参与竞争，无法形成所有哲学家各占一根筷子的完整等待环。

#### 方法二：统一资源申请顺序

所有筷子编号：

$$
0,1,2,\ldots,n-1
$$

每个哲学家总是先申请编号较小的筷子，再申请编号较大的筷子。

这样避免形成沿资源编号严格递增又回到起点的循环等待。

#### 方法三：奇偶哲学家采用不同取筷顺序

例如偶数编号先取左边，奇数编号先取右边。

在合理、对称的资源定义下，这可以破坏原来所有人按同一方向取筷子导致的完整循环等待。

#### 方法四：一次性获取两根筷子

通过额外互斥机制或管程，确保确认左右两根筷子均可用时才同时占有。

这种方法的核心是避免“只占有一根并等待另一根”。

### 10.6 2019 年真题：哲学家 + 碗

这是真题中的经典升级模型。

共有：

- $n$ 位哲学家；
- $m$ 个碗；
- $n$ 根筷子。

每位哲学家吃饭需要：

- 一个碗；
- 两侧两根筷子。

要求：

1. 防止死锁；
2. 尽可能多的人同时吃饭。

#### 第一步：识别资源

筷子是具有位置约束的独占资源。

每根筷子设置一个二元信号量：

$$
chopstick[i]=1
$$

碗是同类计数资源。

#### 第二步：防止循环等待

最多只允许 $n-1$ 位哲学家进入拿筷子阶段。

同时，不能超过实际碗数量 $m$。

因此：

$$
bowl=\min(m,n-1)
$$

#### 第三步：完整代码

```c
semaphore bowl = min(m, n - 1);
semaphore chopstick[n] = {1};

philosopher(int i) {
    while (true) {
        think();

        P(bowl);

        P(chopstick[i]);
        P(chopstick[(i + 1) % n]);

        eat();

        V(chopstick[(i + 1) % n]);
        V(chopstick[i]);

        V(bowl);
    }
}
```

#### 第四步：最大并发就餐人数

相邻哲学家不能同时吃饭，因为他们共享一根筷子。

因此同时吃饭人数不超过：

$$
\left\lfloor\frac{n}{2}\right\rfloor
$$

也不能超过碗数 $m$。

所以物理上界为：

$$
\boxed{N_{\max}=\min\left(m,\left\lfloor\frac{n}{2}\right\rfloor\right)}
$$

例如：

$$
n=7,\qquad m=3
$$

则：

$$
N_{\max}=\min(3,3)=3
$$

注意：

`bowl` 的初值 $3$ 是进入取筷子阶段的许可数量，不是筷子数量。

能同时进入取筷子阶段，不代表都能立即获得两根筷子并吃饭。

### 10.7 2024 年真题：最少信号量

题设有一个只能存放一个数据分组的缓冲区 B。

操作包括：

- C1：写入一个数据分组；
- C2：读出一个数据分组；
- C3：修改已有的数据分组。

#### 问题一：两个进程执行 C1，是否涉及临界区？

是。

两个进程都要操作共享缓冲区。

若并发写入，可能导致数据覆盖或状态不一致。

因此 C1 属于需要互斥保护的临界区操作。

#### 问题二：初始为空，P1 写一次，P2 读一次

要求：

$$
C1\rightarrow C2
$$

只需要：

```c
semaphore full = 0;

process P1 {
    C1;
    V(full);
}

process P2 {
    P(full);
    C2;
}
```

为什么不需要额外 mutex？

因为只有一次写入和一次读出，而且同步关系已经强制：

$$
C1\text{ 完成后才能 }C2
$$

两个操作不会重叠。

因此一个同步信号量就足够。

#### 问题三：初始非空，两个进程各执行一次 C3

两个进程均修改同一个数据分组。

需要互斥：

```c
semaphore mutex = 1;

process P1 {
    P(mutex);
    C3;
    V(mutex);
}

process P2 {
    P(mutex);
    C3;
    V(mutex);
}
```

不需要额外 `full`，因为数据初始已经存在，而且题设没有新的生产、消费依赖。

这道题特别说明：

设计同步算法时，先看实际执行次数、初始状态和操作之间的依赖，再决定最少需要多少信号量。

不能看到缓冲区就无条件使用 `empty/full/mutex` 三件套。

### 10.8 2025 年真题：植树流水线

原题有甲、乙、丙三人：

```text
甲挖坑
  ↓
乙放树苗、填土
  ↓
丙浇水
```

要求：

- 甲和乙共用一把铁锹。
- 丙使用水桶浇水。
- 未被乙处理的树坑最多 3 个。
- 初始没有树坑。

#### 第一步：整理约束

约束一：最多 3 个待处理树坑。

设置：

$$
slots=3
$$

约束二：乙必须等待甲挖好坑。

设置：

$$
pits=0
$$

约束三：丙必须等待乙完成栽种。

设置：

$$
water=0
$$

约束四：甲乙共用铁锹。

设置：

$$
shovel=1
$$

共四个信号量。

#### 第二步：完整代码

```c
semaphore slots = 3;
semaphore pits = 0;
semaphore water = 0;
semaphore shovel = 1;
```

甲：

```c
Jia() {
    while (true) {
        P(slots);
        P(shovel);

        dig();

        V(shovel);
        V(pits);
    }
}
```

乙：

```c
Yi() {
    while (true) {
        P(pits);
        P(shovel);

        plant_and_fill();

        V(shovel);
        V(slots);
        V(water);
    }
}
```

丙：

```c
Bing() {
    while (true) {
        P(water);

        water_tree();
    }
}
```

#### 为什么甲必须先 P(slots)，后 P(shovel)？

如果反过来：

```text
P(shovel);
P(slots);
```

可能出现：

1. 三个树坑已经达到容量限制。
2. 甲拿到铁锹。
3. 甲因为没有空余树坑名额而等待。
4. 乙需要铁锹填土，才能处理树坑并释放名额。
5. 铁锹却始终被甲占有。

于是死锁。

正确的逻辑是：

先确认存在允许执行的任务额度，再占有执行任务所需的互斥资源。

#### 为什么丙不需要额外的水桶互斥量？

题目只有一个浇水者丙。

没有其他并发执行实体竞争水桶，所以不需要额外的互斥控制。

如果再增加一个浇水者丁，两人共用一个水桶，则需要考虑新增：

```c
semaphore bucket = 1;
```

用于水桶互斥。

#### 这类大题怎么总结？

可以将它看成：

生产者—消费者 + 多阶段流水线 + 容量限制 + 共享工具互斥。

这是十分有代表性的综合题模型。

## 十一、死锁：概念、四个必要条件与判断方法

参考讲义：[死锁与综合解题框架](https://fumadocscf.any1.tech/docs/408/knowledge2/operating_system/02-process-management/05-deadlock/)

### 11.1 什么是死锁？

假设有两个进程：

进程 P1：

```text
占有资源 R1
等待资源 R2
```

进程 P2：

```text
占有资源 R2
等待资源 R1
```

那么：

```text
P1 ─等待──► P2
▲           │
│           │
└──等待─────┘
```

P1 不释放 R1，P2 就无法继续。

P2 不释放 R2，P1 就无法继续。

双方互相等待，无法推进。

这就是经典的资源死锁。

### 11.2 死锁四个必要条件

必须全部掌握，而且要理解每个条件。

| 条件    | 含义            | 典型表现            |
| ----- | ------------- | --------------- |
| 互斥条件  | 资源只能被一个进程独占   | 独占设备、互斥锁        |
| 请求并保持 | 占有已有资源时继续申请资源 | 拿着 R1 等 R2      |
| 不可剥夺  | 资源不能被强制收回     | 必须由持有者主动释放      |
| 循环等待  | 存在闭合的等待链      | P1 等 P2、P2 等 P1 |

关键逻辑：

$$
\text{死锁}\Rightarrow\text{四个必要条件同时成立}
$$

但不能简单反过来说：

$$
\text{四条件成立}\Rightarrow\text{一定已经死锁}
$$

某些条件描述的是资源系统允许形成死锁的规则，并不代表当前已经出现实际的死锁等待关系。

真正判断当前是否死锁，还要考察实际的资源分配和请求状态。

<Callout type="warn" title="区分死锁、饥饿和不安全状态">

死锁需要分析实际等待关系；饥饿是个别主体可能长期得不到资源；不安全状态表示当前分配**无法保证**所有进程按最大需求都能顺利完成，但不代表当前已经死锁。多实例资源分配图即使有环，也不必然已经死锁。

</Callout>

### 11.3 死锁与饥饿的区别

| 对比         | 死锁             | 饥饿              |
| ---------- | -------------- | --------------- |
| 典型原因       | 一组进程相互等待       | 调度或资源分配不公平      |
| 是否存在循环等待   | 经典资源死锁通常存在     | 不一定             |
| 其他进程是否可以推进 | 死锁集合内部无法推进     | 其他进程可能一直运行      |
| 典型例子       | 两个进程分别持锁等待另一把锁 | 低优先级进程一直得不到 CPU |

例如：

某系统不断产生高优先级进程，导致一个低优先级进程长期得不到调度。

它可能发生饥饿。

但系统整体仍在正常推进，并不存在必须相互等待的死锁集合。

### 11.4 死锁的四种处理方法

#### 方法一：死锁预防 Prevention

预先破坏四个必要条件中的至少一个。

| 破坏条件  | 典型方法          |
| ----- | ------------- |
| 互斥    | 尽可能共享资源       |
| 请求并保持 | 一次性申请全部所需资源   |
| 不可剥夺  | 允许适当收回或回滚资源   |
| 循环等待  | 对资源统一编号，按顺序申请 |

例如规定：

$$
R_1<R_2<R_3
$$

所有进程只能按照编号递增的顺序申请资源。

就不允许：

```text
进程 A：先 R2，再 R1
```

因为它违反全局资源申请顺序。

这种方式破坏循环等待。

#### 方法二：死锁避免 Avoidance

允许进程逐步申请资源。

但在每一次资源分配前，先判断分配之后系统是否仍然安全。

经典算法是：

银行家算法。

注意：

死锁预防和死锁避免不是一回事。

预防通过改变资源申请规则来消除死锁条件。

避免通过动态检查来拒绝危险的资源分配。

#### 方法三：死锁检测 Detection

允许资源分配继续进行，甚至允许死锁出现。

系统通过资源分配与请求信息检测当前是否已经死锁。

#### 方法四：死锁解除 Recovery

检测到死锁后，通过：

- 终止部分进程；
- 剥夺可回收资源；
- 回滚进程到检查点；

等方式恢复。

### 11.5 2013 年真题：银行家算法的性质

题目考查：

A. 银行家算法属于死锁预防\
B. 安全状态下一定不存在死锁\
C. 不安全状态下一定存在死锁\
D. 银行家算法破坏请求并保持条件

答案：B。

最重要的逻辑关系为：

$$
\boxed{\text{安全状态}\Rightarrow\text{当前没有死锁}}
$$

$$
\boxed{\text{当前死锁}\Rightarrow\text{不安全状态}}
$$

但是：

$$
\boxed{\text{不安全状态}\not\Rightarrow\text{当前死锁}}
$$

为什么？

因为不安全意味着系统已经无法保证所有进程都能够在最大资源需求下完成。

但真实进程未来可能不再请求最大数量的资源，或者某些进程提前完成并释放资源。

因此系统虽然不安全，当前却未必死锁。

## 十二、银行家算法：计算题彻底讲解

银行家算法是本章另一项需要熟练手算的知识点。

### 12.1 四种数据结构

假设有 $n$ 个进程、$m$ 类资源。

Max 矩阵

表示各进程对各类资源的最大需求。

Allocation 矩阵

表示各进程当前已经获得的资源。

Need 矩阵

表示各进程最多还需要多少资源。

$$
\boxed{Need=Max-Allocation}
$$

Available 向量

表示系统当前尚未分配的资源。

$$
\boxed{Available=Total-\sum Allocation_i}
$$

其中各种资源数量分别计算。

<Callout type="idea" title="银行家算法四个量及释放方向">

$Need=Max-Allocation$；$Available=Total-\sum Allocation$；安全性模拟时令 $Work=Available$，完成进程 $i$ 后应执行 $Work\leftarrow Work+Allocation_i$，**不是**增加 $Max_i$ 或仅增加 $Need_i$。存在安全序列才称安全。

</Callout>

### 12.2 安全性算法的完整步骤

先定义：

$$
Work=Available
$$

对于尚未完成的进程，寻找：

$$
Need_i\le Work
$$

注意是各资源分量分别比较。

例如：

$$
Need_i=(1,2,3)
$$

$$
Work=(2,3,2)
$$

虽然某些资源有富余，但第三类资源：

$$
3>2
$$

因此该进程暂时不能获得全部剩余需求。

如果某个进程满足条件，就假设它能够完成并释放当前占有的资源：

$$
Work\leftarrow Work+Allocation_i
$$

然后继续寻找下一个进程。

如果最终全部进程都能依次完成，说明存在安全序列。

### 12.3 2020 年真题：完整安全序列计算

系统有 A、B 两种资源，各 6 个。

| 进程 | 已分配 A | 已分配 B | 最大需求 A | 最大需求 B |
| -- | ----- | ----- | ------ | ------ |
| P1 | 2     | 3     | 4      | 4      |
| P2 | 2     | 1     | 3      | 1      |
| P3 | 1     | 2     | 3      | 4      |

#### 第一步：计算 Available

A 类资源已分配：

$$
2+2+1=5
$$

B 类资源已分配：

$$
3+1+2=6
$$

所以：

$$
Available=(6-5,6-6)
$$

得到：

$$
\boxed{Available=(1,0)}
$$

#### 第二步：计算 Need

由：

$$
Need=Max-Allocation
$$

可得：

| 进程 | Need A | Need B |
| -- | ------ | ------ |
| P1 | 2      | 1      |
| P2 | 1      | 0      |
| P3 | 2      | 2      |

#### 第三步：寻找第一个能够完成的进程

当前：

$$
Work=(1,0)
$$

P1 还需要：

$$
Need_1=(2,1)
$$

无法满足。

P2 还需要：

$$
Need_2=(1,0)
$$

满足：

$$
Need_2\le Work
$$

因此先让 P2 完成。

P2 原来占有：

$$
Allocation_2=(2,1)
$$

完成后：

$$
Work=(1,0)+(2,1)
$$

所以：

$$
\boxed{Work=(3,1)}
$$

#### 第四步：寻找第二个进程

当前：

$$
Work=(3,1)
$$

P1 需要：

$$
Need_1=(2,1)
$$

满足条件。

因此 P1 可以完成。

P1 原来占有：

$$
Allocation_1=(2,3)
$$

释放后：

$$
Work=(3,1)+(2,3)
$$

得到：

$$
\boxed{Work=(5,4)}
$$

#### 第五步：P3 完成

P3 需要：

$$
Need_3=(2,2)
$$

当前：

$$
Work=(5,4)
$$

资源足够。

P3 完成后，释放：

$$
Allocation_3=(1,2)
$$

于是：

$$
Work=(6,6)
$$

全部进程能够完成。

因此存在安全序列：

$$
\boxed{P2\rightarrow P1\rightarrow P3}
$$

系统处于安全状态。

#### 用标准表格快速作答

| 步骤 | 进程 | 执行前 Work | Need  | 释放后 Work |
| -- | -- | -------- | ----- | -------- |
| 1  | P2 | (1,0)    | (1,0) | (3,1)    |
| 2  | P1 | (3,1)    | (2,1) | (5,4)    |
| 3  | P3 | (5,4)    | (2,2) | (6,6)    |

考场上建议直接画这种表。

比反复用文字描述快得多，也更不容易漏掉资源。

### 12.4 为什么完成后加 Allocation，不是 Max？

这个问题必须真正理解。

假设进程 P2：

已分配：

$$
Allocation_2=(2,1)
$$

还需要：

$$
Need_2=(1,0)
$$

系统先临时给它：

$$
(1,0)
$$

它最终完成时归还：

$$
Max_2=(3,1)
$$

看起来是不是应该加：

$$
(3,1)
$$

但注意，系统刚才已经临时支出了：

$$
(1,0)
$$

因此从试运行之前的 `Work` 来看，净增加量为：

$$
(3,1)-(1,0)=(2,1)
$$

也就是：

$$
Allocation_2
$$

所以安全性算法直接使用：

$$
\boxed{Work=Work+Allocation_i}
$$

### 12.5 2018 年真题：没有安全序列的特殊情况

系统有 4 个同类资源。

三个进程的最大需求：

$$
Max=(4,3,1)
$$

已分配数量：

$$
Allocation=(2,1,0)
$$

#### 第一步：计算可用资源

$$
Available=4-(2+1+0)=1
$$

#### 第二步：计算 Need

$$
Need=(4-2,3-1,1-0)
$$

所以：

$$
Need=(2,2,1)
$$

#### 第三步：寻找可完成的进程

当前可用资源：

$$
Work=1
$$

P1 还需 2，不满足。

P2 还需 2，不满足。

P3 还需 1，可以完成。

但是：

$$
Allocation_3=0
$$

也就是说，P3 原来没有占有任何资源。

即使 P3 完成：

$$
Work=1+0=1
$$

P1、P2 仍然需要 2 个资源。

无法继续。

因此：

$$
\boxed{\text{不存在安全序列}}
$$

系统是不安全状态。

#### 这题最容易错在哪里？

很多同学认为：

“只要找到一个能够执行完的进程，系统就安全了。”

这是错误的。

必须能够构造所有进程都能完成的完整序列。

特别要注意：

某进程能够完成，但它并不一定释放额外资源。

### 12.6 安全序列有多少条？

假设当前：

$$
Available=(1,3,2)
$$

三个进程的 Need 为：

$$
Need_0=(0,2,1)
$$

$$
Need_1=(1,2,3)
$$

$$
Need_2=(0,1,3)
$$

一开始只有 P0 满足条件。

因此 P0 必须第一个完成。

假设 P0 完成后：

$$
Work=(3,3,3)
$$

此时 P1、P2 均满足需求。

可以：

$$
P0\rightarrow P1\rightarrow P2
$$

也可以：

$$
P0\rightarrow P2\rightarrow P1
$$

因此安全序列有：

$$
\boxed{2\text{ 条}}
$$

求安全序列数量的关键是列出每一步所有可选进程，而不是只找到一条序列就结束。

### 12.7 银行家算法的资源请求处理

假设当前系统处于安全状态。

进程 Pi 提出请求：

$$
Request_i
$$

首先检查：

$$
Request_i\le Need_i
$$

如果不满足，说明它要求的资源超过了事先声明的最大需求。

再检查：

$$
Request_i\le Available
$$

如果不满足，当前资源不足，不能立即满足。

如果两个条件都满足，才进行试分配：

$$
Available'=Available-Request_i
$$

$$
Allocation_i'=Allocation_i+Request_i
$$

$$
Need_i'=Need_i-Request_i
$$

之后重新执行安全性算法。

如果安全，批准。

如果不安全，撤销试分配。

必须牢记：资源数量足够，不代表可以直接批准请求。

## 十三、同类资源死锁计算：重要公式与真题

<Callout type="warn" title="最少资源保证式的适用条件">

$R_{\min}=\sum_i(R_i-1)+1$ 针对**同类可互换的独占资源**、每个进程最大需求 $R_i$ 已知、资源可逐步申请并在完成后全部释放的经典问题。多个资源类型或其他同步依赖不能直接套用该式。

</Callout>

### 13.1 确保不死锁的最少资源数

设有 $n$ 个并发进程。

第 $i$ 个进程最多需要：

$$
R_i
$$

个同类、可独占、逐步申请的资源。

假设进程最终能够正常完成并释放资源。

考虑最坏情况：

每个进程都占有：

$$
R_i-1
$$

个资源，但还差最后一个。

系统至少应该再有一个空闲资源，才能使某个进程获得最后一个资源并完成。

因此，保证不发生此类资源死锁的充分且紧的资源数量界限为：

$$
\boxed{ R_{\min}=\sum_{i=1}^{n}(R_i-1)+1 }
$$

即：

$$
\boxed{ R_{\min}=\sum_{i=1}^{n}R_i-n+1 }
$$

对于所有进程最大需求相同、均为 $k$ 的情形：

$$
\boxed{R_{\min}=n(k-1)+1}
$$

注意适用条件：单一类型的可互换资源、进程的最大需求已知、资源逐步申请、进程完成后释放资源。

不能无条件把它套用到多个不同类型资源或存在其他复杂等待条件的系统。

### 13.2 2014 年真题：最少需要多少台设备？

三个进程分别最多需要：

$$
3,\quad4,\quad5
$$

台同类设备。

问至少有多少台设备才能确保不发生死锁。

直接计算：

$$
R_{\min}=(3-1)+(4-1)+(5-1)+1
$$

$$
=2+3+4+1
$$

所以：

$$
\boxed{R_{\min}=10}
$$

#### 为什么 9 台不够？

构造最坏情况：

- P1 占有 2 台，还需要 1 台；
- P2 占有 3 台，还需要 1 台；
- P3 占有 4 台，还需要 1 台。

共占有：

$$
2+3+4=9
$$

台设备。

没有任何空闲设备。

三个进程都可能继续等待最后一台设备，无法完成并释放现有资源。

所以 9 台不能保证不死锁。

10 台则可以保证至少有一个进程能取得最后一个资源并完成，进而释放资源。

### 13.3 2009 年真题：至少多少进程可能死锁？

系统有 8 台打印机。

每个进程最多需要 3 台。

问进程数量 $K$ 最少是多少时，系统可能发生死锁。

这里问的是：

固定资源数量，最少多少个进程才能构造死锁。

而不是问保证不死锁的最少资源数。

考虑让每个进程先占有 2 台打印机，再等待第三台。

当：

$$
K=4
$$

时：

$$
2K=8
$$

四个进程恰好占完全部 8 台打印机。

每个进程都还需要 1 台才能完成。

于是可能死锁。

若只有 3 个进程，在每个进程最多需要 3 台的前提下，总有机会满足某个进程的剩余需求，不会形成这种全体都无法完成的资源死锁。

因此：

$$
\boxed{K_{\min}=4}
$$

#### 两类题的区别

| 题目要求             | 解题方法             |
| ---------------- | ---------------- |
| 至少多少资源确保不死锁      | 使用资源数量下界公式       |
| 固定资源数，至少多少进程可能死锁 | 构造每个进程都还差资源的最坏状态 |
| 当前资源分配是否安全       | 银行家安全性算法         |
| 当前是否已经死锁         | 根据实际请求、分配及检测算法判断 |

### 13.4 资源分配图的环

资源分配图中：

- 进程 → 资源：表示请求；
- 资源 → 进程：表示已分配。

要区分两类情形。

所有资源类型都只有一个实例：

$$
\text{有环}\Leftrightarrow\text{有死锁}
$$

存在多实例资源类型：

有环不一定意味着死锁。

原因是即使存在等待环，某个资源类型的其他实例也可能允许相关进程继续执行并释放资源。

因此，多实例资源图通常还需要进行进一步化简或死锁检测。

## 十四、容易遗漏的其他真题模型

前面讲了最主要的几类大题。原稿引用的大题库中还收录了若干特殊场景，它们能够帮助理解同一模型的变形。

### 14.1 2013 年真题：博物馆容量与出入口互斥

题目给定：

- 博物馆最多容纳 500 人；
- 只有一个出入口；
- 出入口一次只允许一个人通过。

需要两个信号量：

```c
semaphore capacity = 500;
semaphore gate = 1;
```

参观者：

```c
visitor() {
    P(capacity);
    P(gate);

    enter();

    V(gate);

    visit();

    P(gate);

    leave();

    V(gate);
    V(capacity);
}
```

这里：

- `capacity` 控制馆内人数；
- `gate` 控制出入口互斥。

最重要的 P 顺序是：

```text
P(capacity);
P(gate);
```

为什么不能反过来？

假设馆内已有 500 人。

某个新游客先占用出入口，再因为容量已满而等待。

那么馆内游客无法获得出入口离开。

馆内没人能够离开，新游客就永远等不到容量。

于是可能死锁。

这与生产者—消费者中“先 P 资源，再 P 互斥”的原理完全相同。

### 14.2 2015 年真题：两个信箱互相传递邮件

题目给定：

- A 信箱容量为 $M$；
- B 信箱容量为 $N$；
- A 信箱初始有 $x$ 封邮件；
- B 信箱初始有 $y$ 封邮件。

A 从 A 信箱取邮件，回复后向 B 信箱放邮件。

B 从 B 信箱取邮件，回复后向 A 信箱放邮件。

设置：

$$
Afull=x,\qquad Aempty=M-x
$$

$$
Bfull=y,\qquad Bempty=N-y
$$

A 的操作：

```c
A() {
    while (true) {
        P(Afull);

        mail = get_A();

        V(Aempty);

        reply = answer(mail);

        P(Bempty);

        put_B(reply);

        V(Bfull);
    }
}
```

B 的操作：

```c
B() {
    while (true) {
        P(Bfull);

        mail = get_B();

        V(Bempty);

        reply = answer(mail);

        P(Aempty);

        put_A(reply);

        V(Afull);
    }
}
```

在题目采用的抽象模型下，每个信箱只有一个取件者和一个投件者，且取件、投件作为不可被破坏的操作处理，因此无需额外设置同类竞争者之间的互斥量。

但在具体工程实现中，如果读写操作还会并发修改共享元数据，就需要另外检查是否有竞争。

这题的特点是：

两个有界缓冲区首尾相连，构成双向生产者—消费者系统。

### 14.3 2021 年真题：关中断实现 P/V

题目给出两种方案。

第一种：

```text
disable_interrupt();

while (S <= 0);

S--;

enable_interrupt();
```

这在单处理机环境下有严重问题。

如果：

$$
S=0
$$

当前进程关闭中断后持续忙等。

其他本来应该执行 `V(S)` 的进程可能无法得到 CPU。

所以程序可能永远无法继续。

第二种方案在等待过程中暂时打开中断，使其他执行实体有机会运行。

这可以避免第一种方案长期关闭中断造成的问题。

但还要注意两个边界：

1. 关中断是特权操作，普通用户程序不能直接任意执行。
2. 在多核处理器中，关闭本核中断不意味着其他 CPU 核心停止运行，因此不能仅凭本核关中断保证跨核互斥。

所以实际多核同步需要合适的原子指令、锁及内存顺序机制。

### 14.4 2017 年真题：多个变量分别加锁

题目有三个共享复数：

```text
cnum x, y, z;
```

三个线程：

```text
线程1：读取 x、y
线程2：读取 y、z
线程3：修改 z、修改 y
```

要求保证正确性，同时尽可能提高并发度。

分析：

- x 只有读操作，不需要加锁。
- y 存在读写冲突，需要互斥。
- z 存在读写冲突，需要互斥。

因此可以设置：

```c
semaphore my = 1;
semaphore mz = 1;
```

线程 1 读取 y 时持有 `my`。

线程 2 同时读取 y、z 时，需要在读取期间保护两个变量。

线程 3 修改哪个变量，就保护哪个变量。

这样比所有操作共用一把全局大锁具有更高的潜在并发度。

如果多个线程都需要同时持有多把锁，必须注意统一加锁顺序，避免形成循环等待。

### 15.2 综合预测题一：调度 + 抢占

设三个进程：

| 进程 | 到达 | CPU 时间 |
| -- | -- | ------ |
| A  | 0  | 6      |
| B  | 2  | 2      |
| C  | 3  | 1      |

使用 SRTF 调度。

在剩余时间相同时，当前正在运行的进程继续运行。

求完成顺序。

<Accordions>
<Accordion title="展开：综合预测题答案与推导" id="os2-mock-01">

#### 解析

$t=0$：A 开始执行。

$t=2$：A 还剩 4，B 需要 2，因此 B 抢占 A。

$t=3$：B 还剩 1，C 需要 1。

根据题设，相同剩余时间时当前进程继续运行，因此 B 不被抢占。

B 在 $t=4$ 完成。

之后 C 执行至 $t=5$。

最后 A 执行剩余 4 个时间单位至 $t=9$。

时间轴：

```text
0      2    4   5        9
|  A   | B  | C |    A   |
```

完成顺序：

$$
\boxed{B\rightarrow C\rightarrow A}
$$

这题专门考查：剩余时间相等时的处理规则必须看题设。

</Accordion>
</Accordions>

### 15.3 综合预测题二：单槽缓冲区与最少信号量

一个单槽缓冲区初始为空。

线程 A 只执行一次写入，线程 B 只执行一次读取。

问最少几个信号量？

<Accordions>
<Accordion title="展开：综合预测题答案与推导" id="os2-mock-02">

答案：一个。

```c
semaphore S = 0;

A() {
    write();
    V(S);
}

B() {
    P(S);
    read();
}
```

因为一次性前驱同步已经使两次操作不能同时进行，不需要额外互斥。

如果改成多个生产者和消费者反复访问，通常需要重新建立容量计数与互斥模型。

</Accordion>
</Accordions>

### 15.4 综合预测题三：信号量初值设计

有 3 台同类设备。

一个进程需要同时获得 2 台设备才能完成工作。

问资源计数信号量初值应为多少？

<Accordions>
<Accordion title="展开：综合预测题答案与推导" id="os2-mock-03">

答案：

$$
S=3
$$

但如果进程必须同时占有两台设备，那么连续两次执行 P：

```text
P(S);
P(S);
```

可能出现多个进程分别占有一台设备、再等待第二台设备的局面。

因此：

资源计数正确，不代表多资源获取过程一定没有死锁。

应根据题目要求考虑：

- 原子地申请两个许可；
- 设置并发入口限制；
- 资源有序分配；
- 银行家算法等方式。

</Accordion>
</Accordions>

### 15.5 综合预测题四：安全性算法

现有某种资源共 7 个。

三个进程最大需求分别为：

$$
3,\quad4,\quad5
$$

当前分配：

$$
2,\quad2,\quad2
$$

问是否安全？

<Accordions>
<Accordion title="展开：综合预测题答案与推导" id="os2-mock-04">

#### 解析

已分配：

$$
2+2+2=6
$$

可用：

$$
Available=1
$$

尚需：

$$
Need=(1,2,3)
$$

只有 P1 能先完成。

释放 P1 当前占有的 2 个资源：

$$
Work=1+2=3
$$

之后 P2、P3 都可以完成。

例如：

$$
P1\rightarrow P2\rightarrow P3
$$

所以：

$$
\boxed{\text{系统安全}}
$$

</Accordion>
</Accordions>

### 15.6 综合预测题五：锁顺序

线程 A：

```text
P(m1);
P(m2);

work();

V(m2);
V(m1);
```

线程 B：

```text
P(m2);
P(m1);

work();

V(m1);
V(m2);
```

是否可能死锁？

<Accordions>
<Accordion title="展开：综合预测题答案与推导" id="os2-mock-05">

可能。

构造：

```text
A 已获得 m1，等待 m2
B 已获得 m2，等待 m1
```

形成循环等待。

改进方式：

让两个线程都先申请 `m1`，再申请 `m2`。

即为资源建立统一申请顺序。

</Accordion>
</Accordions>

## 十七、第二章综合解题方法总结

从真题和模拟题看，本章大题虽然故事背景不同，但解法可以归纳为四种固定模式。

### 17.1 模型一：状态转换

先问：

> 如果现在给这个进程 CPU，它能否继续执行？

能，但是当前没有 CPU：

就绪态。

不能，因为仍然等待资源或事件：

阻塞态。

这个方法可以解决大多数基础状态判断题。

### 17.2 模型二：调度时间轴

看到调度题，立即写五类信息：

```text
到达时间
服务时间
优先级方向
是否可抢占
时间片大小
```

然后根据调度事件逐段画时间轴。

最终统一计算：

$$
T_i=C_i-A_i
$$

$$
R_i=S_i-A_i
$$

没有额外阻塞时：

$$
WT_i=T_i-B_i
$$

不要把周转时间、等待时间和响应时间混在一起。

### 17.3 模型三：P/V 自然语言翻译

将题目条件翻译为信号量模型：

| 题目中的话     | 对应解题思路           |
| --------- | ---------------- |
| 同一时刻最多一个  | 二元互斥信号量          |
| 最多 N 个    | 计数信号量初值 N        |
| A 完成后才能 B | A 后 V，B 前 P，初值 0 |
| 必须等待多个前驱  | 分别确认各前驱完成        |
| 空了不能取     | 等待 full          |
| 满了不能放     | 等待 empty         |
| 连续执行 K 次  | 考虑组级互斥           |
| 两种产品分别消费  | 考虑分类计数           |
| 多把锁同时使用   | 考虑全局固定申请顺序       |
| 尽可能少的信号量  | 删除冗余约束，复用天然程序顺序  |

### 17.4 模型四：死锁资源向量

先写：

$$
Need=Max-Allocation
$$

$$
Available=Total-\sum Allocation_i
$$

然后不断寻找：

$$
Need_i\le Work
$$

找到可完成进程后：

$$
Work\leftarrow Work+Allocation_i
$$

直到：

- 全部完成，系统安全；
- 无法继续，系统不安全。

遇到“至少多少资源”“至少多少进程”时，则优先考虑最坏资源分配状态，而不是直接套银行家算法。

## 十八、最后的复习安排

建议把本章复习分为三个阶段。

第一阶段：建立概念。 重点掌握进程状态、PCB、进程与线程区别、调度与上下文切换、同步与互斥、死锁条件。这部分要求能够快速解释每个概念，并判断错误表述。
