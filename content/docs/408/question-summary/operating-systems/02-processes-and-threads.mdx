## 二、进程与线程

### 2.1 程序与进程

#### 2.1.1 什么是程序？

程序是静态的指令和数据集合。

例如磁盘中存储一个 `hello.exe`，它本质上是一份可执行文件。

即使没有运行，它仍然存在。

#### 2.1.2 什么是进程？

进程是程序的一次执行过程。

一个进程不仅包括代码，还包括：

- 正在执行的指令位置；
- CPU 寄存器的内容；
- 地址空间；
- 运行时数据；
- 系统分配的资源；
- 进程的状态及管理信息。

例如：

```text
磁盘上的 chrome 程序
          │
          ├── 进程P1
          │
          ├── 进程P2
          │
          └── 进程P3
```

同一个程序可以对应多个进程。

反过来，一个进程也可能通过 `exec` 装载不同的程序。

因此：

**程序和进程并不是一一对应的。**

#### 2.1.3 程序与进程对比

| 项目 | 程序 | 进程 |
|---|---|---|
| 性质 | 静态 | 动态 |
| 生命周期 | 文件存在期间 | 创建到终止 |
| PCB | 没有 | 有 |
| 资源管理 | 程序本身不拥有运行时资源 | 拥有运行时资源环境 |
| CPU 调度 | 不直接参与 | 其执行实体参与调度 |
| 数量关系 | 一个程序可以被多次运行 | 一个进程也可执行不同程序映像 |

#### 2.1.4 进程的基本特征

传统教材通常总结为五个方面。

**动态性**

进程具有创建、运行、终止的生命周期。

动态性是进程最基本的特征。

**并发性**

多个进程可以在一段时间内交替推进。

单核处理器上：

```text
时间 ─────────────────►

CPU  P1 | P2 | P1 | P3 | P2 | P1
```

看起来多个程序同时运行，实际上同一时刻通常只有一个执行实体占用这个 CPU 核心。

**独立性**

不同进程通常具有独立的地址空间和资源保护边界。

**异步性**

进程执行速度具有不可预知性。

例如两个并发进程：

```c
P1: x = x + 1;
P2: x = x + 1;
```

如果没有同步机制，不能简单认为两条语句一定按照固定顺序执行。

**结构性**

传统进程可抽象为：

```text
进程
├── PCB
├── 程序段
└── 数据段
```

在现代系统中还要考虑地址空间、线程和其他内核资源对象。

### 2.2 PCB：进程控制块

PCB 的英文是 Process Control Block。

它是操作系统描述和管理进程的核心数据结构。

408 教材中的重要结论：

**PCB 是进程存在的唯一标志。**

理解这句话，不是说进程只有 PCB，而是说操作系统通过 PCB 识别和管理一个存在的进程。

#### 2.2.1 PCB 包含什么？

| 类别 | 典型信息 | 用途 |
|---|---|---|
| 进程标识 | PID、用户标识 | 区分进程 |
| 进程状态 | 就绪、运行、阻塞等 | 状态管理 |
| 调度信息 | 优先级、队列指针 | CPU 调度 |
| 处理机现场 | PC、SP、寄存器、PSW | 保存和恢复运行 |
| 内存管理信息 | 地址空间、页表等 | 内存管理 |
| 资源信息 | 打开文件、设备等 | 资源管理 |

例如：

```text
PCB(P1)
│
├── PID = 1001
├── State = Ready
├── Priority = 5
├── PC = 0x00401000
├── SP = 0x7FFF0000
├── PageTable = ...
└── OpenFiles = ...
```

#### 2.2.2 为什么要保存 PC 和寄存器？

假设进程 P1 正在执行：

```text
指令1
指令2
指令3  ← 当前执行位置
指令4
指令5
```

此时 P1 被抢占，CPU 开始执行 P2。

稍后 P1 再次获得 CPU。

操作系统必须知道：

- P1 执行到了哪里；
- 通用寄存器之前是什么值；
- 栈指针在哪里；
- 当前处理机状态是什么。

所以要保存处理机现场。

否则无法正确恢复执行。

#### 2.2.3 PCB 与进程地址空间

一定要区分：

```text
PCB：内核管理进程的信息结构

进程地址空间：
├── 代码段
├── 数据段
├── BSS
├── 堆
├── 内存映射区
└── 栈
```

PCB 通常由内核管理，并不是存储在用户程序代码段中。

### 2.3 进程状态与转换

这是选择题中的高频考点。

#### 2.3.1 五状态模型

| 状态 | 英文 | 含义 |
|---|---|---|
| 创建态 | New | 正在建立进程 |
| 就绪态 | Ready | 一切运行条件满足，只缺 CPU |
| 运行态 | Running | 正在占用 CPU |
| 阻塞态 | Blocked | 正在等待事件或资源 |
| 终止态 | Terminated | 已完成执行，等待清理 |

核心状态转换：

```text
                      创建
                       │
                       ▼
                     就绪
                       │ ▲
               调度    │ │ 抢占、时间片耗尽
                       ▼ │
                     运行 ──────► 终止
                       │
                       │ 等待I/O或资源
                       ▼
                     阻塞
                       │
                       │ 等待事件完成
                       └────────► 就绪
```

#### 2.3.2 就绪态与阻塞态的本质区别

这是整个进程状态题最重要的判断依据。

**假设现在立刻把 CPU 给这个进程，它能不能继续执行？**

如果能：

它处于就绪态。

如果不能：

它还在等待某个事件，处于阻塞态。

例如：

```text
P1：时间片用完
```

P1 仍然能够执行，只是没有 CPU。

所以：

$$
\mathrm{Running}\rightarrow\mathrm{Ready}
$$

再例如：

```text
P2：等待磁盘读操作完成
```

即使现在把 CPU 给 P2，磁盘数据没有到达，它仍然无法完成当前等待操作。

所以：

$$
\mathrm{Running}\rightarrow\mathrm{Blocked}
$$

#### 2.3.3 常见状态转换

| 事件 | 状态转换 |
|---|---|
| 进程创建成功 | 创建→就绪 |
| 获得 CPU | 就绪→运行 |
| 时间片耗尽 | 运行→就绪 |
| 被更高优先级进程抢占 | 运行→就绪 |
| 主动让出 CPU 且不等待事件 | 运行→就绪 |
| 等待 I/O | 运行→阻塞 |
| 申请不可用信号量 | 运行→阻塞 |
| 等待子进程结束 | 运行→阻塞 |
| I/O 完成 | 阻塞→就绪 |
| 等待的资源可用 | 阻塞→就绪 |
| 正常执行完成 | 运行→终止 |

注意：

`P(S)` 不一定导致阻塞。

只有对应资源不可用，而且采用阻塞式等待机制时，才会阻塞。

类似地，发起 I/O 也不必然阻塞，异步 I/O 可以让程序继续执行。

#### 2.3.4 为什么阻塞态不直接变为运行态？

假设：

```text
时刻0：P1正在运行
时刻1：P1请求磁盘I/O，进入阻塞
时刻2：P2开始运行
时刻3：P1的磁盘I/O完成
```

时刻 3，P1 已经具备执行条件。

但是 CPU 正在执行 P2。

因此 P1 首先进入就绪态。

至于是否立即抢占 P2，取决于调度策略。

所以：

$$
\mathrm{Blocked}\rightarrow\mathrm{Ready}
$$

然后在获得 CPU 时：

$$
\mathrm{Ready}\rightarrow\mathrm{Running}
$$

#### 2.3.5 就绪态能不能直接转阻塞态？

经典三状态模型中：

**不能直接转换。**

因为一个就绪进程尚未运行，不能主动执行新的阻塞操作。

必须先获得 CPU：

```text
就绪 → 运行 → 阻塞
```

### 2.4 进程挂起

不要把挂起和阻塞混淆。

#### 阻塞

描述的是：

**进程正在等待某个事件。**

#### 挂起

描述的是：

**进程暂时不参与正常调度。**

在经典教材的换入换出模型中，挂起经常与进程映像被移出内存有关。

因此可以有：

- 就绪挂起；
- 阻塞挂起。

例如：

```text
P1等待磁盘数据
      │
      ▼
   阻塞态
      │
      │ 被换出内存
      ▼
  阻塞挂起态
      │
      │ 磁盘数据到达
      ▼
  就绪挂起态
      │
      │ 被换回内存
      ▼
    就绪态
```

关键考点：

**等待事件完成，不意味着挂起状态自动解除。**

### 2.5 进程控制原语

原语的核心特征是原子性。

即相关操作在逻辑上不可被其他并发操作破坏。

主要包括：

| 原语 | 功能 |
|---|---|
| 创建原语 | 创建 PCB、分配必要资源 |
| 终止原语 | 回收资源、处理退出状态 |
| 阻塞原语 | 将执行实体加入等待队列 |
| 唤醒原语 | 将等待实体转入就绪队列 |

这里有一个容易混淆的区别：

**阻塞往往由当前运行进程主动触发。**

**唤醒通常由内核、其他执行实体或外部事件触发。**

例如：

```text
P1执行read()
     ↓
等待数据
     ↓
P1阻塞
     ↓
磁盘完成读取
     ↓
设备中断
     ↓
操作系统唤醒P1
     ↓
P1进入就绪队列
```

#### 真题：2014 年进程状态

题意：

一个进程的读磁盘操作完成后，操作系统针对该进程应做什么？

答案：

**将等待该 I/O 的阻塞进程转为就绪态。**

它不一定立刻运行。

也不意味着必须改变优先级或时间片大小。

#### 真题：2015 年进程状态

题意：

哪个事件会导致进程由运行态变为就绪态？

正确答案：

被高优先级进程抢占。

理由：

进程并未失去运行条件，只是失去了 CPU。

#### 真题：2018 年进程阻塞

三个事件：

1. 申请临界资源；
2. 从磁盘读取数据；
3. CPU 被分配给高优先级进程。

可能导致阻塞的是：

**1、2。**

第三个属于运行态转就绪态。

### 2.6 fork、exec 与 wait

#### 2.6.1 fork：创建子进程

UNIX/Linux 中：

```c
pid_t pid = fork();
```

成功后：

| 执行主体 | 返回值 |
|---|---|
| 父进程 | 子进程 PID |
| 子进程 | 0 |
| 创建失败 | 父进程得到 -1 |

例如：

```c
int main() {
    pid_t pid = fork();

    if (pid == 0) {
        printf("child\n");
    } else if (pid > 0) {
        printf("parent\n");
    }

    return 0;
}
```

成功调用之后会有父子两个执行流。

不保证谁先输出。

#### 2.6.2 fork 数量题

```c
int main() {
    fork();
    fork();
    fork();
    printf("A\n");
}
```

假设所有 `fork()` 成功，且没有其他控制流限制。

第一次：

$$
1\rightarrow2
$$

第二次：

$$
2\rightarrow4
$$

第三次：

$$
4\rightarrow8
$$

因此执行 `printf` 的进程数为：

$$
\boxed{8}
$$

输出 A 共 8 次。

推广：

$$
N=2^k
$$

其中 $k$ 表示所有现存进程都会执行的连续 `fork()` 次数。

但注意：

这个公式只适用于每次 `fork()` 都会被全部现存执行流执行的情况。

若存在条件分支，需要画进程树。

#### 2.6.3 写时复制 COW

现代操作系统一般不会在 `fork()` 时立即复制所有物理内存页。

常用 Copy On Write：

```text
fork前

父进程虚拟页 ───► 物理页A


fork后，尚未写入

父进程虚拟页 ───┐
                 ├──► 物理页A
子进程虚拟页 ───┘


子进程写入后

父进程虚拟页 ───► 物理页A

子进程虚拟页 ───► 物理页B
```

所以：

**父子进程具有独立的虚拟地址空间语义，但可以暂时共享物理页。**

#### 2.6.4 exec：替换程序映像

`exec` 的作用：

用新程序替换当前进程的程序映像。

它不会因为替换程序而创建新的进程。

典型执行过程：

```text
父进程
   │
   ├── fork
   │      │
   │      ▼
   │    子进程
   │      │
   │      └── exec
   │             │
   │             ▼
   │          新程序
   │
   └── wait
```

成功执行 `exec` 后，当前进程通常保留 PID 等身份，但代码、数据和执行栈等程序映像已经被替换。

#### 2.6.5 wait：等待并回收子进程

父进程调用：

```c
wait(NULL);
```

可以等待并回收已终止子进程的退出状态。

如果子进程还没有结束，父进程可能阻塞。

#### 2.6.6 僵尸进程和孤儿进程

| 类型 | 含义 |
|---|---|
| 僵尸进程 | 子进程已经退出，退出状态尚未被父进程回收 |
| 孤儿进程 | 原父进程已退出，子进程仍然存在 |

僵尸进程不再执行用户程序。

但内核仍需保留少量退出信息。

孤儿进程通常可以继续执行，随后由其他适当的进程接管。

### 2.7 进程与线程

#### 2.7.1 为什么要有线程？

假设浏览器同时需要：

- 渲染页面；
- 处理用户输入；
- 执行 JavaScript；
- 进行网络通信。

如果所有工作都由一条执行流串行完成，容易造成界面卡顿。

多线程允许一个进程内存在多个执行流。

#### 2.7.2 最重要的两个基本单位

**进程是资源分配和保护的基本单位。**

**线程是处理机调度和执行的基本单位。**

可以记成：

```text
进程：资源归谁？

线程：CPU执行谁？
```

#### 2.7.3 同一进程的线程共享什么？

通常共享：

- 虚拟地址空间；
- 代码段；
- 全局变量；
- 静态变量；
- 堆；
- 打开的文件等进程级资源。

各线程独有：

- 程序计数器；
- 寄存器现场；
- 栈；
- 线程状态；
- 线程标识。

#### 2.7.4 PCB 与 TCB

```text
进程P
│
├── PCB
│   ├── 地址空间
│   ├── 文件资源
│   └── 进程管理信息
│
├── 线程T1
│   └── TCB1
│       ├── PC
│       ├── SP
│       └── 寄存器
│
├── 线程T2
│   └── TCB2
│
└── 线程T3
    └── TCB3
```

TCB 是线程控制块。

PCB 负责进程级管理。

TCB 负责线程级执行现场和调度信息。

#### 真题：2011 年

题目：

同一进程创建的多个线程不能共享什么？

选项包括：

- 代码段；
- 打开的文件；
- 全局变量；
- 某线程的栈指针。

答案：

**某线程的栈指针。**

因为每个线程必须拥有自己的执行现场。

#### 真题：2024 年

某线程打开文件获得文件描述符 `fd`，随后创建两个线程。

两个新线程可以共享：

1. 进程地址空间；
2. 原线程的栈；
3. 文件描述符 `fd`。

答案：

**1、3。**

同一进程的线程共享文件描述符表。

但是每个线程具有自己的栈。

需要注意，线程栈虽然逻辑上各自独立，但仍属于同一个进程的虚拟地址空间，并不是硬件隔离的私有地址空间。

---

### 2.8 用户级线程与内核级线程

<Tabs items={["用户级线程 ULT", "内核级线程 KLT"]} defaultIndex={0}>
  <Tab value="用户级线程 ULT">

#### 2.8.1 用户级线程 ULT

用户级线程由用户空间线程库管理。

特点：

- 用户线程之间切换可以不陷入内核；
- 创建、切换开销通常较小；
- 内核可能不知道每一条用户线程；
- 能否多核并行取决于底层内核线程映射。

  </Tab>
  <Tab value="内核级线程 KLT">

#### 2.8.2 内核级线程 KLT

由操作系统内核直接管理和调度。

特点：

- 内核能够分别调度；
- 某个线程阻塞通常不影响同进程其他内核线程获得 CPU；
- 可以在多个处理器核心上并行运行；
- 线程创建和管理涉及内核，通常开销更高。

  </Tab>
</Tabs>

#### 2.8.3 三种线程映射模型

| 模型 | 映射 | 多核并行 |
|---|---|---|
| 多对一 | 多个用户线程映射一个内核线程 | 不能真正多核并行 |
| 一对一 | 每个用户线程映射一个内核线程 | 可以 |
| 多对多 | 多个用户线程映射多个内核线程 | 可以 |

多对一模型：

```text
用户线程T1 ─┐
用户线程T2 ─┼──► 内核线程K1
用户线程T3 ─┘
```

如果 K1 阻塞，这些用户线程可能全部无法继续执行。

一对一模型：

```text
T1 ───► K1
T2 ───► K2
T3 ───► K3
```

可以由不同 CPU 核心并行执行。

#### 高频陷阱

不能笼统地说：

“用户级线程一定不能多核并行。”

多对多模型也能让多个用户线程通过多个内核调度实体获得并行能力。

---

### 2.9 进程间通信 IPC

#### 2.9.1 为什么需要 IPC？

不同进程通常拥有独立的虚拟地址空间。

例如：

```text
进程P1：地址空间A

进程P2：地址空间B
```

P1 不能直接任意访问 P2 的普通私有数据。

所以需要进程间通信。

#### 2.9.2 三类基本方式

**共享存储**

多个进程共同访问一块共享内存。

**消息传递**

通过发送和接收消息交换数据。

**管道通信**

通过管道缓冲区传输顺序字节流。

#### 2.9.3 管道 Pipe

```text
进程P1
   │
   ▼
写入管道
   │
   ▼
内核缓冲区
   │
   ▼
读取管道
   │
   ▼
进程P2
```

主要特点：

- 经典管道通常是半双工；
- 数据按字节流传递；
- 容量有限；
- 管道空时，读取可能阻塞；
- 管道满时，写入可能阻塞。

#### 真题：2014 年

正确叙述：

**进程对管道进行读操作和写操作都可能被阻塞。**

不要认为只有读操作会阻塞。

#### 2.9.4 共享内存

两个进程的不同虚拟页可以映射到同一物理页：

$$
VPN_A\rightarrow PPN_X
$$

$$
VPN_B\rightarrow PPN_X
$$

共享内存的优势：

建立映射后，进程可直接访问共享页。

但关键问题是：

**共享内存不自动保证互斥和同步。**

多个进程访问共享内存时，仍然需要正确的并发控制。

#### 2.9.5 消息队列

消息队列将数据以消息为单位组织。

与普通字节流管道相比，消息队列通常能够保留逻辑消息边界。

#### 2.9.6 Signal 与 Semaphore

这两个术语不要混淆。

| 机制 | 含义 |
|---|---|
| Signal | 异步事件通知 |
| Semaphore | 信号量，同步和互斥工具 |

## 三、CPU 调度

### 3.1 调度到底在解决什么？

假设：

```text
P1：需要运行8ms
P2：需要运行3ms
P3：需要运行5ms
```

三个进程都处于就绪态。

但是只有一个 CPU 核心。

操作系统需要决定：

**下一步应该运行哪个进程？**

这就是 CPU 调度。

---

### 3.2 三级调度

| 调度类型 | 别名 | 核心作用 |
|---|---|---|
| 高级调度 | 长程调度 | 决定哪些作业进入系统 |
| 中级调度 | 中程调度 | 控制进程换入、换出 |
| 低级调度 | 短程调度 | 决定就绪进程谁获得 CPU |

#### 高频结论

**低级调度最频繁。**

因为 CPU 经常需要在不同执行实体之间切换。

因此低级调度要求开销尽量小。

---

### 3.3 调度时机

典型调度事件：

1. 当前进程执行结束；
2. 当前进程主动阻塞；
3. 新进程进入就绪队列；
4. 阻塞进程被唤醒；
5. 当前时间片耗尽。

需要区分：

**发生调度事件，不意味着一定切换到其他进程。**

例如：

```text
P1正在运行
P2被唤醒
```

如果 P1 的优先级仍然更高，调度器可能继续选择 P1。

---

### 3.4 抢占式与非抢占式

<Callout type="warn" title="调度约定优先于默认假设">

到达时刻是否抢占、比较优先级的方向以及时间片到期规则，应严格依照题设；不要直接套通用调度结论。

</Callout>


#### 非抢占式

获得 CPU 后，只要没有结束或阻塞，通常继续执行。

例如：

```text
P1在0时刻开始运行，需要10ms
P2在2时刻到达，只需要1ms
```

非抢占 SJF 下：

```text
0────────────10─11
     P1        P2
```

虽然 P2 很短，也不能立即打断 P1。

#### 抢占式

允许操作系统剥夺当前进程的 CPU。

抢占式 SRTF：

```text
0──2─3────────11
 P1 P2    P1
```

P2 到来时剩余执行时间更短，所以抢占 P1。

---

### 3.5 CPU 调度的性能指标

这是所有调度计算题的基础。

设：

- $A_i$：到达时间；
- $B_i$：CPU 服务时间；
- $S_i$：首次运行时刻；
- $C_i$：完成时刻。

#### 3.5.1 周转时间

$$
T_i=C_i-A_i
$$

含义：

从任务到达到任务完成的总时间。

#### 3.5.2 带权周转时间

$$
W_i=\frac{T_i}{B_i}
$$

带权周转时间是无量纲比值。

例如：

一个进程执行 2ms，却在系统中停留 10ms。

则：

$$
W=\frac{10}{2}=5
$$

#### 3.5.3 等待时间

在不涉及独立 I/O 阻塞等其他时间的简单模型中：

$$
WT_i=T_i-B_i
$$

注意：

**等待时间统计的是在就绪队列中等待 CPU 的累计时间。**

若存在阻塞式 I/O：

$$
T_i=WT_i+B_i+I_i
$$

其中 $I_i$ 为独立阻塞时间，假设各类时间互不重叠。

因此：

$$
WT_i=T_i-B_i-I_i
$$

不能无条件使用 $WT=T-B$。

#### 3.5.4 响应时间

$$
RT_i=S_i-A_i
$$

响应时间只考虑第一次获得 CPU 的时间。

它不等于累计等待时间。

#### 3.5.5 平均周转时间

$$
\overline{T}=\frac{1}{n}\sum_{i=1}^{n}T_i
$$

#### 3.5.6 平均带权周转时间

$$
\overline{W}=\frac{1}{n}\sum_{i=1}^{n}\frac{T_i}{B_i}
$$

注意必须先分别计算每个进程的带权周转时间，再取平均。

#### 3.5.7 CPU 利用率

$$
U=\frac{\text{CPU忙碌时间}}{\text{观察总时间}}
$$

例如：

CPU 在 10ms 中空闲 0.5ms。

$$
U=\frac{9.5}{10}=95\%
$$

#### 3.5.8 吞吐量

$$
\text{Throughput}
=
\frac{\text{完成任务数}}{\text{观察时间}}
$$

---

### 3.6 FCFS：先来先服务

First Come First Served。

规则：

谁先进入就绪队列，谁先获得 CPU。

通常为非抢占式。

#### 例题

| 进程 | 到达时间 | 服务时间 |
|---|---:|---:|
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |

FCFS：

```text
0       7      11 12
|  P1   |  P2  |P3|
```

完成时间：

$$
C_1=7,\quad C_2=11,\quad C_3=12
$$

周转时间：

$$
T_1=7-0=7
$$

$$
T_2=11-2=9
$$

$$
T_3=12-4=8
$$

等待时间：

$$
WT_1=7-7=0
$$

$$
WT_2=9-4=5
$$

$$
WT_3=8-1=7
$$

平均等待时间：

$$
\overline{WT}=\frac{0+5+7}{3}=4
$$

#### 优缺点

优点：

- 简单；
- 管理开销较小；
- 按到达顺序服务。

缺点：

**护航效应。**

长作业挡住后面的短作业，导致平均等待时间变长。

---

### 3.7 SJF：短作业优先

Shortest Job First。

每次选择当前已经到达、服务时间最短的作业。

经典 SJF 为非抢占式。

仍然使用上题数据。

时刻 0 只有 P1 到达。

所以先运行 P1。

时刻 7：

P2、P3 都已到达。

P3 只需要 1 个时间单位。

因此先选 P3。

```text
0       7 8      12
|  P1   |P3|  P2   |
```

完成时间：

$$
C_1=7,\quad C_2=12,\quad C_3=8
$$

等待时间：

$$
WT_1=0
$$

$$
WT_2=12-2-4=6
$$

$$
WT_3=8-4-1=3
$$

平均等待时间：

$$
\overline{WT}=\frac{0+6+3}{3}=3
$$

比 FCFS 的 4 更小。

#### 高频陷阱

SJF 并不是把所有进程按照服务时间从小到大直接排序。

**只能在已经到达的进程中选择。**

如果一个最短作业还没到达，调度器不能提前选择它。

#### SJF 的缺点

长作业可能一直被后续短作业插队。

导致饥饿。

---

### 3.8 SRTF：最短剩余时间优先

Shortest Remaining Time First。

它是 SJF 的抢占式版本。

继续使用：

| 进程 | 到达时间 | 服务时间 |
|---|---:|---:|
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |

#### 第一步：时刻 0

只有 P1 到达。

运行 P1。

#### 第二步：时刻 2

P1 已执行 2 个时间单位。

剩余：

$$
7-2=5
$$

P2 到达，需要 4。

比较：

$$
4<5
$$

所以 P2 抢占 P1。

#### 第三步：时刻 4

P2 已执行 2 个时间单位。

剩余：

$$
4-2=2
$$

P3 到达，需要 1。

比较：

$$
1<2
$$

所以 P3 抢占 P2。

#### 第四步：时刻 5

P3 完成。

此时：

- P1 剩余 5；
- P2 剩余 2。

选择 P2。

#### 第五步：时刻 7

P2 完成。

最后运行 P1。

甘特图：

```text
0    2    4 5    7         12
| P1 | P2 |P3| P2 |    P1    |
```

完成时间：

$$
C_1=12,\quad C_2=7,\quad C_3=5
$$

等待时间：

$$
WT_1=12-0-7=5
$$

$$
WT_2=7-2-4=1
$$

$$
WT_3=5-4-1=0
$$

平均等待时间：

$$
\overline{WT}=\frac{5+1+0}{3}=2
$$

#### SRTF 的核心

每当更短任务到达：

**比较的是剩余执行时间，而不是原来的总服务时间。**

---

### 3.9 HRRN：最高响应比优先

Highest Response Ratio Next。

响应比为：

$$
R=\frac{WT+BT}{BT}
$$

也可以写成：

$$
\boxed{R=1+\frac{WT}{BT}}
$$

其中：

- $WT$：当前已经等待的时间；
- $BT$：服务时间。

HRRN 经典形式是非抢占式。

#### 例题

某时刻有三个已到达作业：

| 作业 | 已等待时间 | 服务时间 |
|---|---:|---:|
| P1 | 4 | 2 |
| P2 | 8 | 8 |
| P3 | 3 | 1 |

分别计算：

$$
R_1=1+\frac42=3
$$

$$
R_2=1+\frac88=2
$$

$$
R_3=1+\frac31=4
$$

选择 P3。

#### 为什么 HRRN 能兼顾长短作业？

因为：

$$
R=1+\frac{WT}{BT}
$$

服务时间短：

响应比容易较大。

等待时间长：

响应比也会逐渐增大。

因此能够缓解 SJF 的长作业饥饿问题。

#### 真题：2009 年

综合考虑等待时间和执行时间的调度算法是：

**最高响应比优先 HRRN。**

---

### 3.10 优先级调度

规则：

优先级最高的就绪进程获得 CPU。

可分为：

- 抢占式；
- 非抢占式。

#### 最重要的细节

**优先级数值大的进程，不一定优先级高。**

必须看题目定义。

例如：

```text
方案A：
priority越大，优先级越高。

方案B：
priority越小，优先级越高。
```

不同系统可以采用不同约定。

#### 3.10.1 静态优先级

进程创建后优先级基本不改变。

问题：

低优先级进程可能饥饿。

#### 3.10.2 动态优先级

可以根据：

- 等待时间；
- 已运行时间；
- 任务类型；

动态改变优先级。

#### 真题：2016 年动态优先级

题目约定：

**优先数越小，优先级越高。**

可设计：

$$
\boxed{
priority=nice+a\cdot cpuTime-b\cdot waitTime
}
$$

其中：

$$
a>0,\qquad b>0
$$

解释：

运行越久：

$$
cpuTime\uparrow
$$

使优先数增大，从而降低优先级。

等待越久：

$$
waitTime\uparrow
$$

使优先数减小，从而提高优先级。

这就是老化机制 Aging。

其目的是降低低优先级进程长期饥饿的风险。

---

### 3.11 RR：时间片轮转

Round Robin。

调度流程：

```text
就绪队列：
P1 → P2 → P3 → P4
```

每个进程最多执行一个时间片。

如果没有完成，就重新进入就绪队列尾部。

#### 3.11.1 时间片过大

若时间片很大：

$$
q\rightarrow\infty
$$

RR 逐渐接近 FCFS。

缺点：

交互响应较慢。

#### 3.11.2 时间片过小

优点：

每个进程更快获得运行机会。

缺点：

上下文切换频繁，系统开销增大。

#### 3.11.3 RR 计算例题

| 进程 | 到达时间 | 服务时间 |
|---|---:|---:|
| P1 | 0 | 7 |
| P2 | 2 | 4 |
| P3 | 4 | 1 |

时间片：

$$
q=2
$$

约定同时发生新进程到达与时间片结束时，先将新到达进程入队，再将未完成进程放到队尾。

调度过程：

```text
0-2    P1
2-4    P2
4-6    P1
6-7    P3
7-9    P2
9-11   P1
11-12  P1
```

甘特图：

```text
0  2  4  6 7  9  11 12
|P1|P2|P1|P3|P2|P1|P1|
```

完成时间：

$$
C_1=12,\quad C_2=9,\quad C_3=7
$$

等待时间：

$$
WT_1=12-0-7=5
$$

$$
WT_2=9-2-4=3
$$

$$
WT_3=7-4-1=2
$$

平均等待时间：

$$
\overline{WT}=\frac{5+3+2}{3}
=\frac{10}{3}
$$

#### RR 最容易错的地方

1. 没有维护真实的就绪队列；
2. 忘记新进程的到达时刻；
3. 忘记时间片用完要重新入队；
4. 忘记计算被抢占后剩余执行时间；
5. 把时间片结束理解成阻塞；
6. 忽略同一时刻入队的先后约定。

---

### 3.12 多级队列与多级反馈队列

#### 多级队列

任务根据类别分入不同队列。

例如：

```text
Q1：交互任务
Q2：批处理任务
Q3：后台任务
```

队列类别通常较固定。

#### 多级反馈队列 MLFQ

任务能够根据运行行为在不同队列之间移动。

例如：

```text
Q1：最高优先级，时间片 10ms
Q2：中等优先级，时间片 20ms
Q3：最低优先级，时间片 40ms
```

新进程通常先进入高优先级队列。

如果用完整个时间片仍没完成，就可能被降级。

交互型任务通常 CPU burst 较短，更容易保持较高优先级。

CPU 密集型任务可能逐步进入低优先级队列。

#### 真题：2019 年二级反馈队列

条件：

- Q1 使用 RR，时间片 10ms；
- Q2 使用 SJF；
- Q1 优先级高于 Q2；
- 新进程首先进入 Q1；
- 用完 Q1 时间片仍未完成则进入 Q2。

两个进程同时到达：

| 进程 | CPU需求 |
|---|---:|
| P1 | 30ms |
| P2 | 20ms |

假设 P1 先进入 Q1。

调度：

```text
0-10    P1  剩余20，降至Q2
10-20   P2  剩余10，降至Q2
20-30   P2  Q2中剩余时间更短
30-50   P1
```

完成时间：

$$
C_1=50,\quad C_2=30
$$

等待时间：

$$
WT_1=50-30=20
$$

$$
WT_2=30-20=10
$$

平均等待时间：

$$
\boxed{\overline{WT}=15\mathrm{ms}}
$$

这是 MLFQ 常见计算思路。

---

### 3.13 上下文切换

上下文切换指 CPU 从一个执行实体切换到另一个执行实体时，保存并恢复处理机现场。

例如：

```text
P1正在运行
     │
     ▼
保存P1现场
     │
     ▼
选择P2
     │
     ▼
恢复P2现场
     │
     ▼
P2继续运行
```

典型保存内容：

- PC；
- SP；
- 通用寄存器；
- 状态寄存器；
- 调度相关信息。

不同进程之间的切换还可能涉及地址空间切换。

#### 重点辨析

| 概念 | 含义 |
|---|---|
| 模式切换 | 用户态与内核态切换 |
| 调度 | 决定运行谁 |
| 上下文切换 | 保存当前执行实体并恢复另一个 |
| 中断 | CPU响应某个事件 |

执行系统调用：

```text
用户态 → 内核态 → 用户态
```

不一定发生进程上下文切换。

时钟中断发生，也不一定切换进程。

#### 高频结论

**中断次数不等于调度次数。**

**调度次数也不一定等于完整上下文切换次数。**

尤其在复杂调度题中，必须先明确“调度次数”的统计口径。

## 四、CPU 调度综合真题精讲

### 4.1 2026 年第 45 题：优先级与时间片混合调度

这是一道综合性较强的调度题。

#### 题目条件

- 优先级数值越大，优先级越高；
- 时钟中断间隔为 10ms；
- 初始时间片为 50ms；
- 仅在时钟中断时检查高优先级抢占；
- 时间片耗尽，优先级减 1；
- 被高优先级进程抢占时，优先级不变；
- 同级按进入就绪队列的先后调度。

| 进程 | 到达时间 | 初始优先级 | CPU需求 |
|---|---:|---:|---:|
| P1 | 10 | 3 | 95 |
| P2 | 10 | 4 | 20 |
| P3 | 12 | 2 | 40 |
| P4 | 14 | 5 | 60 |

#### 第一步：时刻 10

P1、P2 同时就绪。

P2 优先级更高。

选择 P2。

#### 第二步：时刻 14

P4 到达。

P4 的优先级为 5，高于 P2 的 4。

但是题目规定：

**只能在时钟中断时检查抢占。**

所以 P4 不能在时刻 14 立即抢占。

#### 第三步：时刻 20

发生时钟中断。

P4 抢占 P2。

此时 P2 已运行 10ms，还剩 10ms。

因为是被抢占，不是时间片耗尽：

P2 优先级保持为 4。

#### 第四步：P4 运行

P4 从 20ms 运行到 70ms。

用完 50ms 时间片。

剩余：

$$
60-50=10\mathrm{ms}
$$

其优先级：

$$
5\rightarrow4
$$

#### 第五步：时刻 70

P2 与 P4 的优先级都为 4。

按照进入就绪队列的先后，选择 P2。

P2 继续执行 10ms。

在时刻 80 完成。

#### 第六步：时刻 80

P4 剩余 10ms。

选择 P4。

时刻 90 完成。

#### 第七步：P1 运行

时刻 90，P1 优先级为 3，高于 P3 的 2。

P1 运行 50ms：

```text
90-140
```

时间片耗尽后：

$$
priority_1:3\rightarrow2
$$

P1 仍剩：

$$
95-50=45\mathrm{ms}
$$

#### 第八步：时刻 140

P1、P3 都是优先级 2。

P3 先前已经进入就绪队列。

所以选择 P3。

```text
140-180：P3
```

P3 完成后：

```text
180-225：P1
```

```text

| P2  |   P4    | P2 | P4 |    P1    |    P3    |    P1    |
```

#### 最终结果

| 20～70 | P4 |
| 70～80 | P2 |
| 80～90 | P4 |
| 90～140 | P1 |
| 140～180 | P3 |
| 180～225 | P1 |

按资料采用的统计口径：

- 时钟中断：22 次；
- CPU 调度：7 次。

这里 22 次将时刻 10ms 的时钟中断计入，统计的是 10、20、……、220ms。若题目把时刻 10 视为已完成的初始调度点、不计入随后发生的中断，则需要相应调整统计口径。

## 五、同步、互斥与临界区

### 5.1 为什么会发生并发错误？

假设共享变量：

```c
int x = 0;
```

两个线程同时执行：

```c
x++;
```

从高级语言看只是简单的一条语句。

但是可能被编译成：

```asm
load R1, x
add  R1, 1
store x, R1
```

假设两个线程交错执行：

```text
初始 x=0

T1读取x，得到0
T2读取x，得到0

T1加1，得到1
T2加1，得到1

T1写回x=1
T2写回x=1
```

最终：

$$
x=1
$$

而不是预期的 2。

这是典型的丢失更新。

#### 真题：2011 年竞争条件

共享变量初始：

$$
x=1
$$

P1 对 x 加 1。

P2 对 x 减 1。

如果两个操作都不是原子的，不同指令交错可能得到：

$$
\boxed{x\in\{0,1,2\}}
$$

不是只能得到 1。

#### 考点本质

**多个操作都读写同一共享变量，而且至少有一个写操作时，可能发生竞争。**

如果没有同步机制，结果可能依赖执行顺序。

---

### 5.2 临界资源与临界区

#### 临界资源

一次只允许一个执行主体访问的共享资源。

例如：

- 独占打印机；
- 需要互斥保护的共享计数器；
- 某些共享队列结构。

#### 临界区

访问临界资源的代码段。

```c
P(mutex);

// 临界区
count++;

V(mutex);
```

#### 四项经典原则

1. 空闲让进；
2. 忙则等待；
3. 有限等待；
4. 让权等待。

理解：

**空闲让进**

临界资源空闲时，不应无故阻止有资格的进程进入。

**忙则等待**

资源已被占用时，其他竞争者不能同时进入。

**有限等待**

应避免某个进程永远得不到进入机会。

**让权等待**

无法进入时，最好让出 CPU，而不是无意义地一直忙等。

注意：传统教材会把四项一起列出，但互斥安全性与等待方式并不是同一个性质。自旋锁可以保证互斥，却不满足让权等待。

---

### 5.3 软件互斥算法

#### 5.3.1 单纯的锁变量为什么不行？

错误算法：

```c
while (lock == true) {
}

lock = true;

// critical section

lock = false;
```

问题：

检查和修改不是原子的。

可能发生：

```text
T1看到lock=false
T2看到lock=false

T1设置lock=true
T2设置lock=true
```

最后两个线程都进入临界区。

#### 关键结论

**检查锁状态和修改锁状态必须具有适当的原子性。**

---

### 5.4 Peterson 算法

经典双进程软件互斥算法。

共享变量：

```c
bool flag[2] = {false, false};
int turn = 0;
```

对于进程 $P_i$，另一个进程记为 $P_j$。

```c
flag[i] = true;
turn = j;

while (flag[j] && turn == j) {
    ;
}

// critical section

flag[i] = false;
```

其中：

`flag[i]` 表示自己想进入临界区。

`turn` 表示双方竞争时倾向让另一方先进入。

#### 为什么能互斥？

如果两个进程都想进入：

```text
flag[0]=true
flag[1]=true
```

最终 `turn` 只可能是 0 或 1。

因此不可能两个进程都同时满足各自退出等待循环的条件。

#### 为什么不满足让权等待？

等待循环持续占用 CPU。

属于忙等。

#### 注意

该算法用于理解经典互斥思想。

真实多核系统中的正确实现还涉及内存模型、编译器重排序和内存同步语义，不能直接把普通变量版本当作工程级线程锁。

---

### 5.5 Test-and-Set、Swap、CAS

#### 5.5.1 Test-and-Set

其逻辑：

```c
bool test_and_set(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
```

硬件必须保证读取旧值和设置新值整体原子。

使用：

```c
while (test_and_set(&lock)) {
    ;
}

// critical section

lock = false;
```

实际工程代码还需要保证锁操作具有适当的内存获取、释放语义。

#### 5.5.2 Swap

原子交换两个变量的值。

核心：

```text
swap(key, lock)
```

与普通的多指令交换函数不同：

**原子 Swap 不允许其他线程在交换操作的中间观察到不一致状态。**

#### 5.5.3 CAS

Compare-and-Swap。

逻辑：

```text
如果内存当前值 == expected：
    将新值写入内存
    返回成功
否则：
    返回失败
```

常用于实现：

- 自旋锁；
- 无锁数据结构；
- 原子计数；
- 并发状态更新。

#### 真题：2023 年 Swap

原资料中有两处核心错误。

错误一：

```c
if (key == TRUE)
    swap(key, lock);
```

应在失败时继续尝试：

```c
while (key == TRUE)
    swap(key, lock);
```

错误二：

退出临界区：

```c
lock = TRUE;
```

应当释放锁：

```c
lock = FALSE;
```

此外，不能把硬件原子交换随意替换成普通函数实现的交换。

原因：

普通函数可能包含多个可交错执行的读写步骤。

---

### 5.6 自旋锁与阻塞锁

| 项目 | 自旋锁 | 阻塞锁 |
|---|---|---|
| 获取失败 | 循环检查 | 阻塞等待 |
| 是否持续消耗 CPU | 是 | 通常否 |
| 是否涉及睡眠唤醒 | 通常不需要 | 通常需要 |
| 适合情况 | 预计等待很短 | 预计等待较长 |
| 是否必然公平 | 否 | 否 |

#### 真题：2016 年

使用 TSL 实现互斥时：

```c
while (TSL(&lock)) {
}
```

等待者通常不会主动放弃 CPU。

因此属于忙等待。

## 六、信号量与 P/V 操作

### 6.1 什么是信号量？

信号量 Semaphore 是一个用于同步、互斥或资源计数的抽象对象。

它支持两个原子操作：

```text
P(S)：申请许可或等待事件

V(S)：释放许可或发送通知
```

也经常写成：

```text
wait(S)
signal(S)
```

---

### 6.2 P 操作

经典教材中的一种记录型信号量定义：

```c
P(S) {
    S.value--;

    if (S.value < 0) {
        block();
    }
}
```

其中 `block()` 表示加入对应等待队列并阻塞。

整个操作必须按原子语义实现。

### 6.3 V 操作

```c
V(S) {
    S.value++;

    if (S.value <= 0) {
        wakeup();
    }
}
```

其中 `wakeup()` 通常唤醒一个等待者。

注意：

不同教材采用的信号量表示方式可能不同。

有的允许负值。

有的将许可数保持非负，并另外维护等待队列。

要根据题目给出的定义判断。

#### 6.3.1 负值的含义

对于上述经典记录型定义：

$$
S.value=-k
$$

表示有 $k$ 个进程因该信号量等待。

例如：

$$
S=-3
$$

有 3 个等待进程。

执行一次 V：

$$
S=-2
$$

唤醒一个等待进程。

但被唤醒者通常只是进入就绪态，不代表立刻运行。

---

### 6.4 信号量的三个基本用途

#### 用途一：互斥

```c
semaphore mutex = 1;

P(mutex);

critical_section();

V(mutex);
```

初值：

$$
mutex=1
$$

#### 用途二：前驱同步

要求 A 完成后，B 才能开始。

```c
semaphore s = 0;

process A {
    do_A();
    V(s);
}

process B {
    P(s);
    do_B();
}
```

初值：

$$
s=0
$$

含义：

B 必须等待 A 发送完成通知。

#### 用途三：资源容量

假设系统有 5 个同类资源。

```c
semaphore resource = 5;

P(resource);

use_resource();

V(resource);
```

初值：

$$
resource=5
$$

最多允许五个资源许可同时被持有。

---

### 6.5 P/V 的最重要解题方法

把题目中的条件分成三类。

| 题目语言 | 本质 | 常用初值 |
|---|---|---|
| 同时只能一个 | 互斥 | 1 |
| A 完成后才能 B | 前驱同步 | 0 |
| 最多允许 N 个 | 资源容量 | N |

#### 例题

题目：

博物馆最多容纳 500 人，同时只有一个进出口，每次只允许一个人经过。

分析：

限制一：

最多 500 人。

需要：

```c
semaphore capacity = 500;
```

限制二：

进出口只能一人使用。

需要：

```c
semaphore gate = 1;
```

这两个信号量解决的是不同问题。

不能只设其中一个。

---

### 6.6 为什么 P 的顺序非常重要？

<Callout type="warn" title="先申请容量，后进入临界区">

典型有界缓冲区应先取得 empty/full 资源许可再取得 mutex，否则可能因持锁等待而发生死锁。

</Callout>


假设：

```c
semaphore mutex = 1;
semaphore full = 0;
```

错误写法：

```c
P(mutex);
P(full);

get_item();

V(mutex);
```

如果缓冲区为空：

1. 消费者取得 mutex；
2. 执行 `P(full)`；
3. 因为没有产品，消费者阻塞；
4. 消费者仍然持有 mutex；
5. 生产者需要 mutex 才能放入产品；
6. 生产者无法取得 mutex。

于是：

```text
消费者等待生产者放入产品

生产者等待消费者释放mutex
```

形成死锁。

#### 正确写法

```c
P(full);
P(mutex);

get_item();

V(mutex);
V(empty);
```

先等待业务条件。

再获得短时间持有的互斥锁。

#### 记忆

**先申请可能阻塞的资源许可，再进入共享数据临界区。**

这不是所有复杂并发程序的绝对通用顺序定律，但它是经典有界缓冲区题目的关键规则。

---

## 七、经典同步问题

### 7.1 生产者—消费者问题

这是最核心的 P/V 模型。

#### 问题

一个缓冲区能够容纳 $N$ 件产品。

生产者不断放入产品。

消费者不断取走产品。

必须满足：

1. 缓冲区满时，生产者等待；
2. 缓冲区空时，消费者等待；
3. 缓冲区共享数据结构需要互斥访问。

#### 信号量

```c
semaphore empty = N;
semaphore full = 0;
semaphore mutex = 1;
```

含义：

| 信号量 | 初值 | 含义 |
|---|---:|---|
| empty | N | 可申请的空位 |
| full | 0 | 可申请的产品 |
| mutex | 1 | 缓冲区互斥锁 |

#### 生产者

```c
producer() {
    while (true) {
        item x = produce();

        P(empty);
        P(mutex);

        put(x);

        V(mutex);
        V(full);
    }
}
```

#### 消费者

```c
consumer() {
    while (true) {
        P(full);
        P(mutex);

        item x = get();

        V(mutex);
        V(empty);

        consume(x);
    }
}
```

#### 为什么这套代码正确？

生产者：

```text
P(empty)
```

保证存在一个可预订空位。

```text
P(mutex)
```

保证共享缓冲区修改过程互斥。

```text
V(full)
```

表示新产品已经实际写入。

消费者：

```text
P(full)
```

保证存在可取产品。

```text
V(empty)
```

表示一个产品已被取走，释放空位。

#### 最重要的资源守恒关系

在没有未完成的预订、写入或取出操作的稳定状态下：

$$
empty+full=N
$$

但注意：

如果生产者已经执行 `P(empty)`，尚未放入产品，某个空位已被预订。

所以这条等式并不在每条 P/V 指令之间的任意瞬间都直接等于物理空位数与实物产品数。

#### 易错点

- 不能先 P(mutex) 再等待 full；
- 不能在真正放入产品前 V(full)；
- 不能在真正取出产品前 V(empty)；
- 不应将普通生产和消费计算全部放进临界区；
- 多生产者、多消费者必须保护共享队列结构。

### 7.2 真题：2009 年第 45 题，奇偶消费者

#### 题目

有三个进程：

P1：生成正整数。

P2：只能取奇数。

P3：只能取偶数。

共享缓冲区容量为 $N$。

#### 问题本质

普通生产者消费者只有两种资源计数：

```text
empty
full
```

但这道题有两个不同的消费条件：

```text
奇数可用
偶数可用
```

所以普通的一个 full 不够。

#### 信号量设计

```c
semaphore empty = N;
semaphore odd = 0;
semaphore even = 0;
semaphore mutex = 1;
```

#### 生产者

```c
process P1 {
    while (true) {
        int x = produce();

        P(empty);
        P(mutex);

        put(x);

        V(mutex);

        if (x % 2 == 0) {
            V(even);
        } else {
            V(odd);
        }
    }
}
```

#### 奇数消费者

```c
process P2 {
    while (true) {
        P(odd);
        P(mutex);

        int x = getodd();

        V(mutex);
        V(empty);

        countodd(x);
    }
}
```

#### 偶数消费者

```c
process P3 {
    while (true) {
        P(even);
        P(mutex);

        int x = geteven();

        V(mutex);
        V(empty);

        counteven(x);
    }
}
```

#### 为什么要两个满缓冲区计数？

假设缓冲区已有：

```text
2、4、6
```

此时：

```text
even = 3
odd = 0
```

偶数消费者可以取数。

奇数消费者必须等待。

如果只用一个 full，就不能区分到底哪一种产品可取。

#### 本题的推广方法

当消费者需要不同类型的数据时：

**通常需要按照消费条件分别组织可用许可。**

例如：

```text
A类产品
B类产品
C类产品
```

可以分别使用：

```text
fullA
fullB
fullC
```

前提是共享缓冲区支持按类别正确查找和删除产品。

### 7.3 真题：2014 年第 47 题，连续取 10 件产品

#### 题目

多个生产者和消费者共享容量 1000 的缓冲区。

要求：

**一个消费者必须连续取出 10 件产品后，其他消费者才能取产品。**

#### 核心区别

普通生产者消费者只需要保证：

一次取出一件产品时互斥。

这道题还要求：

**一个消费者的连续 10 次取出操作不能被其他消费者插入。**

因此需要额外设置一把消费者组锁。

#### 信号量

```c
semaphore empty = 1000;
semaphore full = 0;
semaphore mutex = 1;
semaphore group = 1;
```

#### 消费者

```c
consumer() {
    while (true) {
        item batch[10];

        P(group);

        for (int i = 0; i < 10; i++) {
            P(full);
            P(mutex);

            batch[i] = get();

            V(mutex);
            V(empty);
        }

        V(group);

        for (int i = 0; i < 10; i++) {
            consume(batch[i]);
        }
    }
}
```

#### 为什么不能只使用 mutex？

因为每次执行：

```c
V(mutex);
```

之后，其他消费者就可能获得 mutex。

会出现：

```text
C1取第1件
C1取第2件
C2取第1件
C1取第3件
```

这违反连续取 10 件的要求。

#### 为什么 group 可以跨越多次取数？

因为 group 只由消费者竞争。

它不阻止生产者继续向缓冲区生产产品。

#### 为什么不能一直持有 mutex？

如果消费者拿着 mutex 等待第 10 件产品，而缓冲区只剩 9 件：

消费者无法继续。

生产者也无法进入临界区放入第 10 件。

形成死锁。

#### 本题最重要的思想

**单次访问互斥和一组操作的独占权，是两个不同约束。**

以后遇到：

- 连续取 5 件；
- 一次处理一批任务；
- 一个顾客连续办理多项业务；

都要考虑是否需要额外的“批次独占权”。

### 7.4 读者—写者问题

#### 题目

有多个读者和写者共享数据。

规则：

- 多个读者可以同时读取；
- 写者必须独占；
- 写者不能与读者同时访问；
- 两个写者不能同时写。

#### 读者优先方案

```c
int read_count = 0;

semaphore mutex = 1;
semaphore wrt = 1;
```

读者：

```c
reader() {
    while (true) {
        P(mutex);

        read_count++;

        if (read_count == 1) {
            P(wrt);
        }

        V(mutex);

        read_data();

        P(mutex);

        read_count--;

        if (read_count == 0) {
            V(wrt);
        }

        V(mutex);
    }
}
```

写者：

```c
writer() {
    while (true) {
        P(wrt);

        write_data();

        V(wrt);
    }
}
```

#### 为什么第一个读者需要 P(wrt)？

因为第一个读者进入后：

必须禁止写者进入。

#### 为什么其他读者不用再 P(wrt)？

因为：

第一个读者已经代表读者群体占有写者锁。

其他读者可以共享读取权限。

#### 为什么最后一个读者才 V(wrt)？

因为只要还存在读者，写者就不能进入。

#### 读者优先的缺点

如果读者持续到达：

```text
读者1进入
读者2进入
读者3进入
读者4进入
...
```

读者群体可能一直不清空。

写者长期拿不到 wrt。

这会导致写者饥饿。

#### 写者优先

可以加入额外入口控制：

当写者等待时，禁止新的读者无限制插队。

#### 公平策略

增加统一排队入口，必要时采用 FIFO 等公平唤醒机制。

但注意：

普通信号量不自动保证严格 FIFO 公平性。

### 7.5 哲学家就餐问题

#### 基本问题

有 $n$ 位哲学家围成一圈。

相邻哲学家共享一根筷子。

每位哲学家吃饭必须同时获得左右两根筷子。

错误策略：

```text
所有人先拿左筷
再拿右筷
```

可能出现：

```text
P0：拿左筷，等右筷
P1：拿左筷，等右筷
P2：拿左筷，等右筷
...
```

构成循环等待。

#### 解决方案一：最多允许 n-1 人尝试拿筷子

```c
semaphore room = n - 1;
semaphore chopstick[n] = {1, 1, ..., 1};
```

```c
philosopher(int i) {
    while (true) {
        think();

        P(room);

        P(chopstick[i]);
        P(chopstick[(i + 1) % n]);

        eat();

        V(chopstick[(i + 1) % n]);
        V(chopstick[i]);

        V(room);
    }
}
```

因为不允许所有 $n$ 位哲学家同时进入取筷阶段，可以避免经典的全部各持一根筷子的闭环。

#### 解决方案二：统一资源顺序

给所有筷子编号。

所有哲学家都先申请编号小的筷子，再申请编号大的筷子。

这样可以破坏循环等待。

#### 解决方案三：一次性取得两根筷子

通过服务员、管程等机制：

只有两根筷子都可用时才允许取得。

避免只占有一根后继续等待另一根。

### 7.6 真题：2019 年哲学家与碗

#### 题目

有：

- $n$ 位哲学家；
- $n$ 根筷子；
- $m$ 个碗。

每个人需要：

- 一个碗；
- 左筷；
- 右筷。

要求：

尽可能提高并发程度，同时避免死锁。

#### 信号量

```c
semaphore chop[n] = {1, 1, ..., 1};
semaphore ticket = min(m, n - 1);
```

#### 伪代码

```c
philosopher(int i) {
    while (true) {
        think();

        P(ticket);
        P(chop[i]);
        P(chop[(i + 1) % n]);

        eat();

        V(chop[(i + 1) % n]);
        V(chop[i]);
        V(ticket);
    }
}
```

#### 为什么 ticket 是 min(m,n-1)？

有两个独立限制。

限制一：

最多只有 $m$ 个碗。

限制二：

不能让 $n$ 位哲学家全部进入取筷阶段。

因此：

$$
\boxed{ticket=\min(m,n-1)}
$$

#### 最多能有多少人同时就餐？

每个人需要相邻两根筷子。

因此不能让相邻哲学家同时就餐。

筷子限制：

$$
\left\lfloor\frac n2\right\rfloor
$$

碗限制：

$$
m
$$

所以：

$$
\boxed{
N_{\max}=
\min\left(m,\left\lfloor\frac n2\right\rfloor\right)
}
$$

注意：

这是物理上的最大并发人数。

不是保证任何调度时刻都能达到该人数。

## 八、前驱关系与 P/V 综合设计

### 8.1 前驱图的基本思想

假设：

```text
A ─┐
   ├──► C ───► E
B ─┘          ▲
              │
D ────────────┘
```

要求：

- A、B 都完成后才能 C；
- C、D 都完成后才能 E。

#### 基本规则

每条跨执行流的前驱关系可以对应一个初值为 0 的信号量。

例如：

```text
A → C
```

使用：

```c
semaphore ac = 0;
```

A 完成：

```c
V(ac);
```

C 开始：

```c
P(ac);
```

---

### 8.2 真题：2020 年第 45 题

#### 题目

有五个操作：

```text
A、B、C、D、E
```

约束：

```text
A、B完成 → C

C、D完成 → E
```

#### 信号量

```c
semaphore ac = 0;
semaphore bc = 0;
semaphore ce = 0;
semaphore de = 0;
```

#### 伪代码

```c
process PA {
    A();
    V(ac);
}

process PB {
    B();
    V(bc);
}

process PC {
    P(ac);
    P(bc);

    C();

    V(ce);
}

process PD {
    D();
    V(de);
}

process PE {
    P(ce);
    P(de);

    E();
}
```

#### 为什么 C 要执行两次 P？

因为 C 有两个独立前驱：

```text
A → C

B → C
```

两个前驱都完成，C 才可以开始。

不能只等待其中一个。

#### 为什么 A 和 B 不需要互斥？

因为题目并没有规定 A 与 B 不能同时执行。

不能人为增加不必要的执行顺序。

### 8.3 真题：2022 年第 46 题

#### 题目

两个线程：

```text
T1：A → E → F

T2：B → C → D
```

另外要求：

- C 在 A、B 完成后执行；
- D、E 在 C 完成后执行；
- F 在 E 完成后执行。

#### 正确分析

有些前驱关系已经由程序顺序保证。

例如：

```text
B → C
```

本来就在 T2 内部。

不需要额外信号量。

同理：

```text
C → D

E → F
```

也已经由线程内部顺序保证。

真正需要跨线程同步的是：

```text
A → C

C → E
```

#### 最简信号量

```c
semaphore AC = 0;
semaphore CE = 0;
```

#### T1

```c
thread T1 {
    A();

    V(AC);

    P(CE);

    E();
    F();
}
```

#### T2

```c
thread T2 {
    B();

    P(AC);

    C();

    V(CE);

    D();
}
```

#### 这道题最重要的能力

**先删除线程内部已经天然保证的前驱边，再对跨线程依赖设置同步信号量。**

这能减少不必要的信号量。

也能提高并发程度。

## 九、其他高价值历年综合题

### 9.1 真题：2013 年博物馆问题

#### 题目

博物馆：

- 最多 500 人；
- 一个进出口；
- 进出都只能一次通过一人。

#### 信号量

```c
semaphore capacity = 500;
semaphore gate = 1;
```

#### 进程

```c
visitor() {
    P(capacity);

    P(gate);
    enter();
    V(gate);

    visit();

    P(gate);
    exit();
    V(gate);

    V(capacity);
}
```

#### 核心解释

`capacity` 控制馆内人数。

`gate` 控制进出通道。

进门时先取得容量许可。

离馆之后才能释放容量许可。

#### 典型错误

```c
P(gate);
P(capacity);
```

若馆内已满，进门者拿着 gate 等待容量。

馆内的人却必须经过 gate 才能出去。

于是可能死锁。

这正是：

**持有互斥资源时等待另一种可能不可用的资源。**

### 9.2 真题：2015 年双向信箱问题

#### 题目

A、B 互相发送邮件。

A 信箱容量：

$$
M
$$

初始邮件数：

$$
x
$$

B 信箱容量：

$$
N
$$

初始邮件数：

$$
y
$$

每人：

1. 从自己的信箱取一封邮件；
2. 处理；
3. 发一封邮件到对方信箱。

#### 信号量初值

```c
semaphore Afull = x;
semaphore Aempty = M - x;

semaphore Bfull = y;
semaphore Bempty = N - y;
```

如果每个信箱可能被多个执行流并发访问，还要设置对应的互斥锁。

#### A 的主要流程

```c
A() {
    while (true) {
        P(Afull);
        remove_from_A();
        V(Aempty);

        make_reply();

        P(Bempty);
        insert_into_B();
        V(Bfull);
    }
}
```

B 对称：

```c
B() {
    while (true) {
        P(Bfull);
        remove_from_B();
        V(Bempty);

        make_reply();

        P(Aempty);
        insert_into_A();
        V(Afull);
    }
}
```

这里为突出同步关系，省略了对共享信箱内部数据结构的互斥操作；完整多执行流版本应在实际 `remove/insert` 周围加入对应的信箱锁。

#### 这道题的核心

**两个方向分别存在独立的有界缓冲区。**

不能把 A、B 的空位和邮件数混成同一个信号量。

### 9.3 真题：2024 年第 46 题

#### 题目

单槽缓冲区 B 有三种操作：

```text
C1：写入分组
C2：读出分组
C3：修改分组
```

条件：

- B 为空才能 C1；
- B 非空才能 C2、C3。

#### 第一问

两个进程都执行 C1。

是否属于临界区？

答案：

**属于。**

因为两个进程可能同时观察 B 为空并尝试写入，产生竞争。

#### 第二问

B 初始为空。

P1 执行 C1 一次。

P2 执行 C2 一次。

因为只有一个生产者和一个消费者，而且各执行一次，使用一个同步信号量即可。

```c
semaphore full = 0;

P1() {
    C1();
    V(full);
}

P2() {
    P(full);
    C2();
}
```

#### 第三问

B 初始非空。

P1、P2 都要执行 C3。

使用互斥信号量：

```c
semaphore mutex = 1;
```

```c
P1() {
    P(mutex);
    C3();
    V(mutex);
}

P2() {
    P(mutex);
    C3();
    V(mutex);
}
```

#### 核心思想

**只有先后依赖时，使用同步信号量。**

**有并发写入冲突时，使用互斥信号量。**

不是所有共享数据题都必须同时设置多个锁。

### 9.4 真题：2025 年第 45 题，三人植树

#### 题目

三个人：

```text
甲：挖坑

乙：放树苗、填土

丙：浇水
```

顺序：

```text
挖坑 → 填土 → 浇水
```

资源：

- 铁锹一把；
- 水桶一个；
- 尚未被乙处理的树坑数量不能超过 3。

甲、乙都需要铁锹。

丙独自使用水桶。

#### 信号量

```c
semaphore slots = 3;
semaphore pits = 0;
semaphore water = 0;
semaphore shovel = 1;
```

#### 甲

```c
Jia() {
    while (true) {
        P(slots);

        P(shovel);
        dig();
        V(shovel);

        V(pits);
    }
}
```

#### 乙

```c
Yi() {
    while (true) {
        P(pits);

        P(shovel);
        plant_and_cover();
        V(shovel);

        V(slots);
        V(water);
    }
}
```

#### 丙

```c
Bing() {
    while (true) {
        P(water);

        water_plant();
    }
}
```

#### 为什么 slots 初值是 3？

因为甲最多只能提前准备 3 个尚未由乙处理的树坑。

`slots` 表示可以预订的未处理树坑名额。

#### 为什么 pits 初值为 0？

因为初始没有已挖好的树坑。

乙必须等待甲完成挖坑。

#### 为什么 water 初值为 0？

因为初始还没有完成填土、可以浇水的树苗。

#### 为什么 shovel 初值为 1？

因为只有一把铁锹。

甲和乙不能同时使用。

#### 为什么没有 bucket？

因为题设只有丙使用水桶。

没有多个执行主体竞争这只水桶，所以不需要额外设置水桶互斥信号量。

#### 最容易错的地方

把：

```c
P(shovel);
P(slots);
```

写在甲的代码中。

当甲拿到铁锹，却因 3 个名额都被占用而等待时，乙可能拿不到铁锹来填土。

于是形成死锁。

正确顺序应为：

```c
P(slots);
P(shovel);
```

## 十、2027 王道冲刺模拟综合题

### 10.1 多生产者与多接收者广播问题

#### 题目

多个发送进程共享 $m$ 个缓冲区。

每条消息必须被所有 $n_2$ 个接收者各读取一次。

只有所有接收者都读过后，该缓冲区才能重新使用。

#### 为什么普通生产者消费者不适用？

普通模型：

```text
生产者写入一条消息
       ↓
一个消费者读取
       ↓
消息被删除
       ↓
缓冲区释放
```

但广播模型要求：

```text
生产者写入一条消息
       ↓
接收者1读取
接收者2读取
接收者3读取
...
       ↓
所有接收者读完
       ↓
缓冲区释放
```

#### 正确设计思路

需要：

- `empty=m`：可重用缓冲区数；
- `ready[j]=0`：接收者 j 尚未读取的消息许可；
- `remain[k]`：第 k 个缓冲区还有多少接收者未读；
- `mutex=1`：保护共享队列和计数；
- 每个接收者独立的读取指针；
- 全体发送者共享写入指针。

#### 最关键的不变量

对于缓冲区 $k$：

$$
0\le remain[k]\le n_2
$$

只有：

$$
remain[k]=0
$$

才允许：

```c
V(empty);
```

#### 核心陷阱

一个接收者读完，不等于消息可以删除。

必须所有接收者都读完。

这种题目属于：

**生产者—消费者的“一写多读、全部确认后回收”变形。**

---

### 10.2 三阶段双缓冲流水线问题

#### 题目

三个进程：

```text
PA：磁盘读取 → 缓冲区1

PB：缓冲区1 → 缓冲区2

PC：缓冲区2 → 打印
```

两个缓冲区容量都为 1。

#### 信号量

```c
semaphore empty1 = 1;
semaphore full1 = 0;

semaphore empty2 = 1;
semaphore full2 = 0;
```

#### PA

```c
PA() {
    while (true) {
        item x = disk_read();

        P(empty1);
        buffer1 = x;
        V(full1);
    }
}
```

#### PB

```c
PB() {
    while (true) {
        P(full1);
        P(empty2);

        item x = buffer1;
        buffer2 = x;

        V(empty1);
        V(full2);
    }
}
```

#### PC

```c
PC() {
    while (true) {
        P(full2);

        item x = buffer2;
        print(x);

        V(empty2);
    }
}
```

以上展示的是稳态流水线的同步骨架，省略了有限文件结束时的退出协议。完整程序应加入结束标记，确保最后一条记录被传递和处理后再退出。

#### 为什么不需要额外 mutex？

在题设中：

- 缓冲区1只有一个写者和一个读者；
- 缓冲区2只有一个写者和一个读者；
- 空满信号量已经保证写入和读取不会重叠。

如果扩展为多个生产者或消费者，才需要进一步保护共享队列指针等数据结构。

#### 核心思想

这是多个生产者—消费者关系首尾连接形成的流水线。

### 10.3 双向猴子过绳问题

#### 题目

一根绳索允许：

- 多只同方向猴子同时通过；
- 不允许相反方向同时通过。

#### 本质

这其实是读者—写者问题的变形。

同方向：

可以共享。

反方向：

必须互斥。

#### 设计思路

设置：

```c
semaphore rope = 1;
semaphore mutexN = 1;
semaphore mutexS = 1;

int north = 0;
int south = 0;
```

第一个北行猴子：

申请 `rope`。

后续北行猴子：

只增加北行数量。

最后一个北行猴子：

释放 `rope`。

南行猴子对称。

#### 为什么还要考虑公平性？

如果北行猴子不断到达：

北行数量可能一直不降为 0。

南行猴子可能长期等待。

因此需要进一步考虑：

- 公平入口；
- FIFO 排队；
- 限制新同方向猴子插队。

#### 迁移方法

以后遇到：

- 单车道桥梁；
- 双方向隧道；
- 同方向多人通行；
- 相反方向互斥；

都可以从读者—写者的“首进末出”模型入手。

## 十一、死锁

### 11.1 什么是死锁？

死锁是：

一组执行主体互相等待只能由彼此释放的资源或触发的事件，导致所有相关执行主体都无法继续推进。

例如：

```text
P1持有R1，等待R2

P2持有R2，等待R1
```

形成：

```text
P1 ──等待──► P2
▲            │
│            │
└──等待──────┘
```

如果没有其他机制打破等待关系，就会形成死锁。

---

### 11.2 死锁四个必要条件

必须掌握：

#### 条件一：互斥

资源不能被多个进程同时使用。

#### 条件二：占有并等待

进程已经占有部分资源，同时继续申请其他资源。

#### 条件三：非抢占

已经分配的资源不能被系统随意强制收回。

#### 条件四：循环等待

多个进程形成封闭等待链。

```text
P1等待P2
P2等待P3
P3等待P1
```

#### 四条件的逻辑关系

对于经典资源死锁：

四个必要条件缺少任何一个，就不会形成这种资源死锁。

但要注意：

**不能只看到某个条件成立，就判断已经死锁。**

必须分析实际资源分配和等待情况。

---

### 11.3 死锁、饥饿、忙等区别

| 概念 | 核心 |
|---|---|
| 死锁 | 一组执行主体互相等待，整体无法推进 |
| 饥饿 | 某个执行主体长期得不到资源或调度机会 |
| 忙等 | 不断执行循环检查条件 |
| 阻塞 | 放弃运行资格，等待事件 |

#### 例子

优先级调度中：

高优先级进程持续到达。

低优先级进程一直无法运行。

这属于饥饿。

不一定存在死锁。

再例如：

```c
while (lock) {
}
```

这是忙等。

如果很快获得锁，不一定发生饥饿。

---

### 11.4 死锁预防

死锁预防的核心：

**破坏至少一个必要条件。**

#### 破坏互斥

让资源可共享。

但某些资源天然需要独占，无法这么做。

#### 破坏占有并等待

方式一：

一次性申请全部需要的资源。

方式二：

申请新资源前，先释放已经占有的资源。

缺点：

可能降低资源利用率。

#### 破坏非抢占

允许系统在适当条件下强制回收资源。

注意：

CPU 抢占不等于资源抢占。

抢占式 CPU 调度不能直接说明系统能够强制夺走打印机或互斥锁。

#### 破坏循环等待

对资源统一编号：

$$
R_1<R_2<R_3
$$

所有进程只按资源编号从小到大申请。

这样可以防止形成反向闭合申请链。

---

### 11.5 死锁避免

与死锁预防不同：

死锁避免不要求破坏四个必要条件。

而是：

**每次分配资源前，判断分配后系统是否仍处于安全状态。**

典型方法：

银行家算法。

---

## 十二、银行家算法

<Callout type="idea" title="判断安全序列的顺序">

依次计算 Need、检查 Request、试分配、执行安全性检查；Work 的增加来自能够完成的进程释放的 Allocation。

</Callout>


### 12.1 核心数据结构

必须记住四个量。

#### Available

当前系统剩余可用资源。

#### Max

每个进程声明的最大资源需求。

#### Allocation

当前已经分配给各进程的资源。

#### Need

进程未来最多还需要多少资源。

关系：

$$
\boxed{Need=Max-Allocation}
$$

---

### 12.2 银行家算法的请求过程

假设进程 $P_i$ 请求：

$$
Request_i
$$

#### 第一步：检查是否超过剩余最大需求

$$
Request_i\le Need_i
$$

如果超过，属于非法请求。

#### 第二步：检查当前资源是否够用

$$
Request_i\le Available
$$

如果不满足：

当前无法分配。

#### 第三步：试分配

$$
Available'=Available-Request_i
$$

$$
Allocation_i'=Allocation_i+Request_i
$$

$$
Need_i'=Need_i-Request_i
$$

#### 第四步：安全性检查

如果试分配后仍然安全：

允许正式分配。

如果不安全：

撤销试分配。

#### 高频陷阱

$$
Request_i\le Available
$$

只表示：

当前资源数量够用。

不表示：

分配后一定安全。

---

### 12.3 安全状态与安全序列

#### 安全状态

存在至少一个进程序列，使得按照这个顺序，每个进程都能获得最终完成所需的资源。

#### 不安全状态

不存在这样的安全序列。

#### 重要关系

**死锁状态一定不安全。**

**不安全状态不一定已经死锁。**

原因：

不安全只说明无法保证未来所有进程都能完成。

不代表当前所有相关进程已经形成实际等待死锁。

---

### 12.4 安全性算法

初始化：

$$
Work=Available
$$

对于每个进程：

```text
Finish[i] = false
```

然后反复寻找：

$$
Need_i\le Work
$$

的未完成进程。

找到后：

假设它完成并释放资源。

$$
\boxed{Work=Work+Allocation_i}
$$

然后：

```text
Finish[i] = true
```

直到：

- 所有进程都完成：安全；
- 没有任何进程能够继续完成：不安全。

#### 为什么只加 Allocation？

这是很容易混淆的知识点。

假设进程还有：

$$
Need_i
$$

资源需求。

先从 Work 中给它这些资源：

$$
Work-Need_i
$$

进程完成后归还：

$$
Allocation_i+Need_i
$$

所以最终：

$$
Work-Need_i+Allocation_i+Need_i
$$

化简：

$$
\boxed{Work+Allocation_i}
$$

因此安全性算法中只需要加回原先已分配的资源。

---

### 12.5 真题：2020 年银行家算法

#### 题目

系统有 A、B 两类资源，各 6 个。

| 进程 | 已分配A | 已分配B | 最大需求A | 最大需求B |
|---|---:|---:|---:|---:|
| P1 | 2 | 3 | 4 | 4 |
| P2 | 2 | 1 | 3 | 1 |
| P3 | 1 | 2 | 3 | 4 |

#### 第一步：计算 Available

A 已分配：

$$
2+2+1=5
$$

剩余：

$$
Available_A=6-5=1
$$

B 已分配：

$$
3+1+2=6
$$

剩余：

$$
Available_B=6-6=0
$$

因此：

$$
\boxed{Available=(1,0)}
$$

#### 第二步：计算 Need

P1：

$$
Need_1=(4,4)-(2,3)=(2,1)
$$

P2：

$$
Need_2=(3,1)-(2,1)=(1,0)
$$

P3：

$$
Need_3=(3,4)-(1,2)=(2,2)
$$

#### 第三步：寻找可完成进程

初始：

$$
Work=(1,0)
$$

比较：

```text
P1需要(2,1)：不满足

P2需要(1,0)：满足

P3需要(2,2)：不满足
```

所以先选择 P2。

P2 完成后释放：

$$
Allocation_2=(2,1)
$$

更新：

$$
Work=(1,0)+(2,1)=(3,1)
$$

#### 第四步：继续检查

现在：

$$
Work=(3,1)
$$

P1 的需求：

$$
Need_1=(2,1)
$$

满足。

P1 完成后释放：

$$
Allocation_1=(2,3)
$$

更新：

$$
Work=(3,1)+(2,3)=(5,4)
$$

#### 第五步：检查 P3

P3 需求：

$$
Need_3=(2,2)
$$

当前：

$$
Work=(5,4)
$$

满足。

P3 完成后：

$$
Work=(5,4)+(1,2)=(6,6)
$$

#### 安全序列

$$
\boxed{P2\rightarrow P1\rightarrow P3}
$$

所以系统处于安全状态。

#### 考场标准表格

| 步骤 | 执行进程 | Work执行前 | Need | Allocation | Work执行后 |
|---|---|---|---|---|---|
| 1 | P2 | (1,0) | (1,0) | (2,1) | (3,1) |
| 2 | P1 | (3,1) | (2,1) | (2,3) | (5,4) |
| 3 | P3 | (5,4) | (2,2) | (1,2) | (6,6) |

### 12.6 真题：2022 年安全序列计数

有三个进程：

| 进程 | Allocation | Need |
|---|---|---|
| P0 | (2,0,1) | (0,2,1) |
| P1 | (0,2,0) | (1,2,3) |
| P2 | (1,0,1) | (0,1,3) |

初始：

$$
Available=(1,3,2)
$$

#### 第一步

P0：

$$
Need_0=(0,2,1)\le(1,3,2)
$$

可以完成。

P1：

$$
Need_1=(1,2,3)
$$

第三类资源不足。

P2：

$$
Need_2=(0,1,3)
$$

第三类资源不足。

因此：

**第一位只能是 P0。**

#### 第二步

P0 完成后：

$$
Work=(1,3,2)+(2,0,1)=(3,3,3)
$$

此时 P1、P2 都可以完成。

所以后两位有两种排列：

```text
P0 → P1 → P2

P0 → P2 → P1
```

安全序列数量：

$$
\boxed{2}
$$

#### 这类题的标准方法

求安全序列数量时：

1. 找出第一步所有可执行进程；
2. 对每一种选择分别向下展开；
3. 每条完整可行分支对应一条安全序列；
4. 注意不能把中间某一步的一种选择误认为最终只有一条序列。

## 十三、死锁资源数量计算题

### 13.1 同类资源的防死锁公式

假设：

- $n$ 个进程；
- 每个进程最多需要 $w$ 个同类资源；
- 资源可逐个申请和释放；
- 每个进程最终能够完成并归还资源。

若要确保不因这种同类资源竞争而发生死锁，一个经典充分资源条件是：

$$
\boxed{m\ge n(w-1)+1}
$$

其中：

$m$ 为系统拥有的资源总数量。

#### 为什么？

最坏情况下：

每个进程已经占有：

$$
w-1
$$

个资源。

但是每个进程还缺 1 个才能完成。

所有进程一共占有：

$$
n(w-1)
$$

个资源。

只要额外还有 1 个资源，就可以满足至少一个进程的最后需求。

它完成后会释放已占有资源。

然后其他进程也能陆续完成。

所以：

$$
m_{\min}=n(w-1)+1
$$

这是在所述模型下保证不发生这种死锁的充分资源界限，不表示资源低于该值就必然发生死锁。

---

### 13.2 真题：2009 年打印机

题目：

系统有 8 台打印机。

每个进程最多需要 3 台打印机。

问：

至少有多少个进程竞争时，可能发生死锁？

公式：

$$
m_{\min}=n(3-1)+1
$$

即：

$$
m_{\min}=2n+1
$$

若系统只有 8 台：

要构造可能死锁的情况：

$$
8\le 2n
$$

得到：

$$
n\ge4
$$

所以：

$$
\boxed{n=4}
$$

#### 构造验证

4 个进程各占有 2 台打印机：

```text
P1：2台，还需1台

P2：2台，还需1台

P3：2台，还需1台

P4：2台，还需1台
```

8 台全部被占有。

没有空闲打印机。

所有进程都无法取得最后一台。

因此可能发生死锁。

---

### 13.3 真题：2014 年设备数量

三个进程最大需求分别是：

$$
3,\quad4,\quad5
$$

问：

保证不死锁的最小资源数量。

推广：

$$
\boxed{
m_{\min}=\sum_{i=1}^{n}(r_i-1)+1
}
$$

代入：

$$
m_{\min}
=(3-1)+(4-1)+(5-1)+1
$$

$$
=2+3+4+1
$$

$$
\boxed{m_{\min}=10}
$$

#### 为什么不是 12？

12 是三个进程的最大需求总和。

但不需要保证三个进程同时取得全部资源。

只要能够保证至少一个进程完成并释放资源，就可以使系统继续推进。

这正是资源安全性分析的本质。

## 十四、死锁检测与解除

### 14.1 资源分配图

资源分配图包含：

- 进程节点；
- 资源节点；
- 请求边；
- 分配边。

#### 请求边

```text
进程 → 资源
```

表示进程正在申请资源。

#### 分配边

```text
资源 → 进程
```

表示资源已经分配给进程。

---

### 14.2 单实例资源

如果每一类资源只有一个实例：

$$
\boxed{\text{有环}\Longleftrightarrow\text{存在死锁}}
$$

适用于经典资源分配图模型。

---

### 14.3 多实例资源

如果某类资源有多个实例：

**资源分配图有环，不一定已经死锁。**

原因：

某个进程可能还能通过其他可用实例完成，随后释放资源打破等待关系。

因此必须结合：

- 当前可用资源；
- 已分配资源；
- 当前请求资源；

进行进一步判断。

---

### 14.4 死锁检测算法

与银行家算法相似，但有一个重要区别。

银行家算法使用：

$$
Need
$$

代表未来最大剩余需求。

死锁检测使用：

$$
Request
$$

代表当前实际尚未满足的请求。

这是两者最容易混淆的地方。

#### 检测过程

初始化：

$$
Work=Available
$$

寻找可以满足当前请求的进程：

$$
Request_i\le Work
$$

假设它完成并释放已分配资源：

$$
Work=Work+Allocation_i
$$

重复执行。

如果仍有无法完成的相关进程，则可能检测出死锁集合。

---

### 14.5 死锁解除

主要有三种方式。

#### 方式一：终止进程

终止一个或多个死锁进程，释放其资源。

#### 方式二：资源抢占

从部分进程收回资源。

前提是该资源允许安全地抢占或恢复。

#### 方式三：回滚

如果系统支持检查点，可将进程恢复到较早状态。

#### 注意

死锁解除不意味着必须直接终止所有进程。

可以选择代价较小的恢复方案。

---

## 十五、全章高频易错点

### 15.1 进程与线程

| 错误理解 | 正确理解 |
|---|---|
| 程序就是进程 | 程序是静态的，进程是执行活动 |
| PCB只记录进程状态 | PCB还包括资源、现场等信息 |
| 所有线程共享寄存器 | 各线程独立保存寄存器现场 |
| 同一进程线程有独立地址空间 | 通常共享同一进程地址空间 |
| 用户级线程一定不能多核运行 | 取决于最终的内核线程映射 |
| fork一定立即复制所有物理页 | 现代实现常使用COW |
| exec会创建新进程 | exec替换当前进程程序映像 |

### 15.2 状态转换

| 错误理解 | 正确理解 |
|---|---|
| 时间片耗尽→阻塞 | 时间片耗尽→就绪 |
| 高优先级抢占→阻塞 | 高优先级抢占→就绪 |
| I/O完成→运行 | 通常先进入就绪 |
| 执行P一定阻塞 | 许可不足时才可能阻塞 |
| 进程唤醒后立即运行 | 唤醒后仍需获得CPU |
| 阻塞等于挂起 | 两者描述不同维度 |

### 15.3 CPU调度

| 错误理解 | 正确理解 |
|---|---|
| SJF一定抢占 | 经典SJF非抢占 |
| SRTF比较原始执行时间 | 比较剩余执行时间 |
| HRRN只考虑等待时间 | 同时考虑等待和服务时间 |
| RR时间片越小越好 | 太小导致频繁切换 |
| 抢占式调度一定基于时间片 | 也可能基于优先级等条件 |
| 进程到达即可抢占 | 取决于调度规则和检查时机 |
| 时钟中断必然上下文切换 | 不一定 |
| 响应时间等于等待时间 | 响应只计算首次运行前的等待 |

### 15.4 同步与互斥

| 错误理解 | 正确理解 |
|---|---|
| 共享变量一定需要禁止所有读者并发 | 多个只读访问可以并发 |
| 互斥和同步是一回事 | 互斥限制并发，同步协调顺序 |
| 一个信号量能自动解决所有约束 | 容量、顺序、互斥需分别分析 |
| V操作一定唤醒进程 | 无等待者时可只增加许可 |
| P操作一定阻塞 | 许可足够时可直接通过 |
| 持有mutex等待full没问题 | 可能死锁 |
| signal等于条件永久成立 | 条件变量通知不保证条件仍然成立 |
| CAS保证公平性 | CAS仅提供相应原子操作语义 |

### 15.5 死锁

| 错误理解 | 正确理解 |
|---|---|
| 有循环等待就一定死锁 | 多实例资源还需进一步分析 |
| 不安全就是已经死锁 | 不安全不一定死锁 |
| 银行家算法属于死锁预防 | 属于死锁避免 |
| Request与Need相同 | 一个是当前请求，一个是最大剩余需求 |
| Available够就一定能分配 | 还必须检查试分配后的安全性 |
| 安全序列只有一条 | 可能有多条 |
| Work更新加Need | 应加Allocation |
| 抢占式CPU调度能破坏资源非抢占条件 | CPU抢占与资源抢占不是一回事 |

## 十六、P/V 综合大题万能解题框架

这部分需要真正掌握，而不是死记代码。

<Steps>
  <Step>

### 第一步：识别并发主体

先问：

**谁在并发执行？**

例如：

```text
生产者P1
消费者P2
消费者P3
```

分别确定每个角色的循环过程。


  </Step>
  <Step>

### 第二步：列出所有共享资源

例如：

```text
共享缓冲区
打印机
取号机
计数器
共享队列
```

找出哪些资源必须互斥访问。


  </Step>
  <Step>

### 第三步：区分三类约束

#### 互斥约束

例如：

```text
同一时刻只能一人使用打印机
```

设置：

```c
semaphore printer = 1;
```

#### 容量约束

例如：

```text
最多允许5件产品
```

设置：

```c
semaphore empty = 5;
```

#### 前驱约束

例如：

```text
A完成之后，B才能开始
```

设置：

```c
semaphore s = 0;
```

A：

```c
V(s);
```

B：

```c
P(s);
```


  </Step>
  <Step>

### 第四步：检查每个信号量初值

一般规律：

```text
互斥资源：
初值 = 1

前驱同步：
初值 = 0

资源容量：
初值 = 资源数

初始已有k件产品：
full = k

容量N，初始已有k件：
empty = N-k
```


  </Step>
  <Step>

### 第五步：确定 P/V 位置

申请资源：

```text
P(resource)
```

必须发生在使用资源之前。

释放资源：

```text
V(resource)
```

必须发生在资源真正可复用之后。

发布事件：

```text
V(sync)
```

必须发生在前驱动作真正完成之后。


  </Step>
  <Step>

### 第六步：检查是否可能死锁

重点寻找：

```text
进程A持有mutex等待资源X

进程B需要mutex才能释放资源X
```

如果存在类似依赖，就可能死锁。


  </Step>
  <Step>

### 第七步：检查不变量

生产者—消费者：

```text
不会取空
不会写满
不会同时破坏共享队列
```

批量消费者：

```text
一次批次期间不会被其他消费者插入
```

读者—写者：

```text
写者独占
多个读者可并发
```

前驱图：

```text
所有必需前驱完成后，后继才能执行
```

死锁问题：

```text
不存在不可推进的循环资源等待
```


  </Step>
  <Step>

### 第八步：检查是否过度同步

例如：

两个线程都只是读取共享变量：

```c
T1: read(x);
T2: read(x);
```

通常不需要为了读操作本身将它们完全串行化。

又如：

生产者计算产品的过程不访问共享缓冲区。

```c
produce();
```

一般不应放入缓冲区临界区。

#### 最终原则

**同步必须充分，但不能无故限制原本允许的并发。**


  </Step>
</Steps>

## 十七、典型题型与快速判断方法

### 题型一：进程状态判断

核心问题：

**现在给 CPU，进程能否继续？**

能：

就绪。

不能：

阻塞。

如果已经占用 CPU：

运行。

### 题型二：调度算法计算

先确定：

```text
到达时间
执行时间
是否抢占
时间片
优先级方向
调度检查时机
```

然后：

```text
画甘特图
→ 求首次运行时间
→ 求完成时间
→ 求响应时间
→ 求周转时间
→ 求等待时间
```

### 题型三：P/V 设计

识别：

```text
只能一个？
→ mutex=1

必须先后？
→ sync=0

最多N个？
→ resource=N
```

再检查操作顺序。

---

### 题型四：经典同步变形

看到：

```text
连续取多个产品
```

考虑：

批次独占权。

看到：

```text
一种生产，多种消费者
```

考虑：

按条件分别计数。

看到：

```text
多个读者，写者独占
```

考虑：

读者—写者。

看到：

```text
多个阶段按顺序处理
```

考虑：

流水线同步。

看到：

```text
同方向共享，反方向互斥
```

考虑：

读者—写者的首进末出模型。

---

### 题型五：银行家算法

必须按固定顺序：

```text
Need = Max - Allocation

检查Request <= Need

检查Request <= Available

试分配

计算安全序列

安全则批准
不安全则恢复
```

---

### 题型六：资源数量防死锁

同类资源：

$$
\boxed{m_{\min}=n(w-1)+1}
$$

不同最大需求：

$$
\boxed{
m_{\min}=\sum_{i=1}^{n}(r_i-1)+1
}
$$

使用前先确认题目满足这类模型的假设。

## 十九、全章最终知识体系总结

学习这一章，最重要的不是记住几十段代码，而是建立统一的并发系统分析方法。

可以将整章理解成一条完整逻辑链：

```text
程序运行
   │
   ▼
产生进程
   │
   ▼
PCB负责描述和管理进程
   │
   ▼
一个进程可以包含多个线程
   │
   ▼
CPU调度器决定谁执行
   │
   ▼
多个执行流并发推进
   │
   ▼
共享数据可能产生竞态
   │
   ▼
通过互斥与同步保证正确执行
   │
   ▼
信号量、锁、管程实现并发控制
   │
   ▼
多个资源之间可能出现循环等待
   │
   ▼
形成死锁风险
   │
   ▼
使用预防、避免、检测和解除策略处理
```

### 最后必须掌握的 10 个核心结论

**1. 进程与线程**

进程是资源分配和保护的基本单位，线程是处理机调度和执行的基本单位。

**2. 状态转换**

被抢占通常进入就绪态；等待事件进入阻塞态；等待事件完成通常先回到就绪态。

**3. CPU调度**

所有调度题都应该先建立事件时间轴，再计算性能指标。

**4. 抢占式调度**

新任务到达是否能够抢占，取决于算法和题设规定的抢占检查时机。

**5. 互斥与同步**

互斥解决“谁能同时访问”，同步解决“必须按什么顺序执行”。

**6. P/V信号量**

初值为 1 常用于互斥，初值为 0 常用于前驱同步，初值为 N 常用于容量限制。

**7. 经典同步问题**

先识别所有独立约束，再设计信号量，不能只凭题目名称直接套代码。

**8. 死锁四条件**

互斥、占有并等待、非抢占、循环等待。

**9. 银行家算法**

$$
Need=Max-Allocation
$$

安全性算法中：

$$
Work=Work+Allocation_i
$$

**10. 安全状态与死锁**

死锁状态一定不安全，但不安全状态并不意味着当前已经死锁。
