本章是操作系统最重要的章节之一，尤其是 进程调度、P/V 操作、经典同步问题、银行家算法，不仅要理解概念，还必须能够独立完成计算与程序设计。

## 一、先建立整章的知识框架

本章所有知识实际上围绕一个问题展开：

当多个程序需要同时运行、共享 CPU 和其他资源时，操作系统怎样保证它们高效、正确、有序地执行？

| 处理机调度  | CPU 应该分配给谁？     | 甘特图、时间计算、算法比较 | ★★★★★ |

- 进程与线程： 资源拥有和 CPU 执行。

## 第一部分：进程与线程

### 二、进程的概念、组成和基本特征

#### 2.1 为什么需要进程？

假设计算机同时运行：

- 浏览器；
- 音乐播放器；
- 下载程序；
- 文档编辑器。

这些程序需要竞争 CPU、内存、磁盘等资源。

操作系统必须知道每个正在执行的程序：

1. 当前执行到哪里？
2. 已经分配了哪些资源？
3. 是否正在等待某个事件？
4. 如果暂停，之后应该从哪里继续？

因此引入进程。

进程是程序的一次执行过程，是系统进行资源分配和保护的基本单位。

#### 2.2 程序和进程的区别

| 对比   | 程序             | 进程           |
| ---- | -------------- | ------------ |
| 性质   | 静态             | 动态           |
| 内容   | 指令和数据          | 程序、运行状态及所需资源 |
| 生命周期 | 文件可以长期存在       | 有创建、运行、终止过程  |
| 唯一性  | 同一个程序可以运行多次    | 每次执行通常形成独立进程 |
| 调度   | 程序本身不接受 CPU 调度 | 进程及其线程参与调度   |

例如：

```text
磁盘上的 Chrome 程序
         │
         ├── 进程 P1
         ├── 进程 P2
         └── 进程 P3
```

同一个程序可以对应多个进程。

反过来，一个进程也可以在其生命周期中执行不同的程序映像，例如通过 `exec()`。

#### 2.3 进程的组成

经典教材把进程实体概括为：

$$
\boxed{\text{进程实体}=\text{程序段}+\text{数据段}+\text{PCB}}
$$

其中最重要的是 PCB。

#### 2.4 PCB：进程控制块

PCB（Process Control Block）是操作系统管理进程的核心数据结构。

按照 408 教材口径，PCB 是进程存在的唯一标志。

PCB 记录的信息主要有：

| 信息        | 作用          |
| --------- | ----------- |
| PID、用户标识  | 标识进程        |
| 进程状态      | 判断就绪、运行、阻塞等 |
| PC 程序计数器  | 记录下一条要执行的指令 |
| CPU 寄存器   | 保存运行现场      |
| 优先级、队列指针  | 实现调度        |
| 页表及内存信息   | 管理地址空间      |
| 打开文件与设备信息 | 管理资源        |

需要理解：

进程暂停之后能继续执行，并不是因为 CPU 记住了它，而是操作系统保存了足够的运行现场。

#### 真题：2021 年进程创建

创建新进程时必须完成哪些操作？

Ⅰ. 申请空白 PCB

Ⅱ. 初始化 PCB

Ⅲ. 设置进程状态为执行态

答案：Ⅰ、Ⅱ。

因为新进程创建完成后，通常先进入就绪态，并不意味着立即获得 CPU。

这类题的关键在于：

$$
\boxed{\text{进程创建完成}\neq\text{立即运行}}
$$

### 三、进程状态及其转换

这是概念选择题最重要的考点之一。

#### 3.1 五种基本状态

| 状态             | 含义      | 判断依据          |
| -------------- | ------- | ------------- |
| 创建态 New        | 正在建立进程  | 尚未完成初始化       |
| 就绪态 Ready      | 具备执行条件  | 只缺 CPU        |
| 运行态 Running    | 正在执行    | 当前占用 CPU      |
| 阻塞态 Blocked    | 等待事件或资源 | 即使给 CPU 也无法继续 |
| 终止态 Terminated | 执行结束    | 等待资源回收        |

最重要的区别：

就绪态：想运行，但没有 CPU。

阻塞态：即使有 CPU，也暂时无法继续。

#### 3.2 必须掌握的状态转换图

```text
              创建态
                │
                ▼
              就绪态 ◄───────── 阻塞态
                │                ▲
          CPU调度│                │
                ▼                │
              运行态 ────────────┘
                │        等待事件
                │
                ▼
              终止态

运行态 ──时间片耗尽/被抢占──► 就绪态
阻塞态 ──等待事件完成──────► 就绪态
```

正常三态模型中，关键转换共有四种。

① 就绪 → 运行

调度器选择该进程并分配 CPU。

② 运行 → 就绪

典型原因：

- 时间片耗尽；
- 被高优先级进程抢占；
- 主动让出 CPU，但没有等待其他事件。

③ 运行 → 阻塞

典型原因：

- 等待磁盘 I/O；
- 等待键盘输入；
- 申请暂不可用的资源；
- 执行无法立即满足的 P 操作；
- 等待其他进程产生数据。

④ 阻塞 → 就绪

等待条件满足，例如：

- I/O 完成；
- 信号量获得许可；
- 所需数据到达；
- 定时器到期。

#### 3.3 为什么没有“阻塞 → 运行”的直接转换？

因为阻塞结束只说明进程重新具备执行条件。

它能否得到 CPU，仍然取决于调度器。

因此通常是：

$$
\boxed{\text{阻塞}\rightarrow\text{就绪}\rightarrow\text{运行}}
$$

#### 3.4 为什么没有“就绪 → 阻塞”的直接转换？

因为就绪进程没有占用 CPU。

它无法执行导致自身阻塞的代码。

必须先获得 CPU 才可能主动申请资源或发起阻塞操作。

#### 3.5 真题：2018 年状态转换

题目问：哪些事件可能导致当前进程 P 阻塞？

Ⅰ. 申请临界资源

Ⅱ. 从磁盘读取数据

Ⅲ. CPU 被分配给高优先级进程

答案为 Ⅰ、Ⅱ。

分析：

- Ⅰ：资源被占用时，申请者可能阻塞。
- Ⅱ：同步磁盘读操作可能需要等待 I/O。
- Ⅲ：进程只是失去 CPU，仍可继续执行，因此进入就绪态。

考场判断方法：

> 只失去 CPU → 就绪。\
> 需要等待事件 → 阻塞。

#### 3.6 真题：2023 年键盘输入与状态转换大题

历年大题中的 2023 年第 46 题，给出六个事件：

① 将进程 P 插入就绪队列。

② 将进程 P 插入阻塞队列。

③ 将字符从键盘控制器读入系统缓冲区。

④ 启动键盘中断处理程序。

⑤ 进程 P 从系统调用返回。

⑥ 用户输入字符。

根据题目描述，六个关键事件的逻辑顺序为：

$$
\boxed{②\rightarrow⑥\rightarrow④\rightarrow③\rightarrow①\rightarrow⑤}
$$

完整过程：

```text
进程P发起读取键盘的系统调用
               ↓
键盘数据尚未到达
               ↓
P进入阻塞队列
               ↓
CPU调度其他进程
               ↓
用户按键
               ↓
键盘产生中断
               ↓
CPU执行中断处理程序
               ↓
驱动程序读取字符
               ↓
操作系统唤醒P
               ↓
P进入就绪队列
               ↓
P再次获得CPU
               ↓
从系统调用返回
```

需要掌握四个结论：

1. 进程 P 阻塞之后，CPU 必须选择其他可运行任务或空闲任务。
2. 键盘中断处理期间，CPU 执行的是内核代码。
3. I/O 完成只能让 P 获得就绪资格。
4. 系统调用、设备中断和进程上下文切换是不同概念。

这道题实际上将第 1 章的中断、系统调用与第 2 章的进程状态结合起来考查。

### 四、挂起状态与进程控制

#### 4.1 挂起和阻塞不是同一个概念

阻塞表示：

还在等待某个事件。

挂起表示：

进程暂时停止参与正常调度，典型情形是进程映像被换出内存。

因此可以有：

- 就绪挂起；
- 阻塞挂起。

例如一个进程正在等待磁盘数据，同时它的进程映像被换出内存。

这就是阻塞挂起。

之后磁盘数据到达：

```text
阻塞挂起
    ↓ I/O完成
就绪挂起
    ↓ 换入内存
就绪
    ↓ CPU调度
运行
```

不能把“事件已经完成”理解为进程可以立即运行。

#### 4.2 进程控制原语

主要有：

| 原语 | 作用           | 常见状态变化  |
| -- | ------------ | ------- |
| 创建 | 建立 PCB、初始化资源 | 创建 → 就绪 |
| 撤销 | 终止并回收资源      | 运行 → 终止 |
| 阻塞 | 等待事件         | 运行 → 阻塞 |
| 唤醒 | 等待条件满足       | 阻塞 → 就绪 |

所谓原语，是指具有原子语义、不会向其他并发执行流暴露不一致中间状态的操作。

原语不等于“一条机器指令”。

它可以由多条指令组成，只要相关关键操作的原子性得到保证。

### 五、fork、exec、wait 与父子进程

这是本节需要重点掌握的知识点。

#### 5.1 fork：创建子进程

在类 UNIX 系统中：

```c
pid_t pid = fork();
```

成功后：

- 父进程得到子进程 PID，即正返回值；
- 子进程得到 0；
- 创建失败时，调用者得到 -1。

例如：

```c
int x = 10;
pid_t pid = fork();

if (pid == 0) {
    x = 20;
    printf("child: %d\n", x);
} else if (pid > 0) {
    printf("parent: %d\n", x);
}
```

子进程修改自己的 `x`，一般不会改变父进程中的 `x`。

原因是父子进程拥有独立的虚拟地址空间语义。

#### 5.2 写时复制 COW

现代操作系统通常不在 `fork()` 后立即复制全部物理内存。

而是使用写时复制：

```text
fork 后

父进程虚拟页 ──┐
               ├──► 同一个物理页
子进程虚拟页 ──┘

某一方准备写入
         ↓
触发保护异常
         ↓
操作系统复制物理页
         ↓
双方分别修改自己的页
```

注意：

共享底层物理页，不等于共享同一个虚拟地址空间。

#### 5.3 fork、exec、wait 的区别

| 调用       | 核心作用        | 创建新进程吗 |
| -------- | ----------- | ------ |
| `fork()` | 创建子进程       | 是      |
| `exec()` | 替换当前进程的程序映像 | 否      |
| `wait()` | 等待并回收子进程    | 否      |

`exec()` 成功后，当前进程执行新的程序映像，而不是另外建立一个进程。

<Accordions>
  <Accordion title="拓展辨析：僵尸进程与孤儿进程">

僵尸进程： 子进程已经结束，但退出信息尚未被父进程回收。

孤儿进程： 父进程先结束，子进程仍然存在。

| 对比      | 僵尸进程     | 孤儿进程          |
| ------- | -------- | ------------- |
| 子进程是否终止 | 已终止      | 通常未终止         |
| 能否继续运行  | 不能       | 可以            |
| 主要问题    | 退出状态尚未回收 | 需要重新建立父进程管理关系 |

#### 真题：2020 年父子进程

题目问：父子进程是否共享虚拟地址空间？

答案：不共享同一个虚拟地址空间。

不要与同一进程内部的多线程相混淆。

### 六、线程的概念与多线程模型

#### 6.1 为什么引入线程？

假设浏览器需要同时：

- 接受用户输入；
- 渲染网页；
- 下载文件；
- 执行后台任务。

如果每个任务都必须通过独立进程完成，进程创建、通信和资源管理成本可能较高。

于是引入线程。

线程是处理机调度和执行的基本单位。

必须牢记：

$$
\boxed{\text{进程：资源分配单位}}
$$

$$
\boxed{\text{线程：CPU 调度单位}}
$$

这里采用支持内核线程的现代多线程系统这一常见教材模型。

#### 6.2 同一进程内线程共享什么？

共享：

- 虚拟地址空间；
- 程序代码；
- 全局变量；
- 静态变量；
- 堆；
- 打开的文件等进程级资源。

不共享各自的执行现场：

- 程序计数器 PC；
- 寄存器现场；
- 栈指针；
- 各自的调用栈；
- 线程状态和调度信息。

可以抽象为：

```text
               进程 P
       ┌───────────────────┐
       │ 代码段            │
       │ 全局变量          │
       │ 堆                │
       │ 打开文件          │
       │                   │
       │ 线程T1   线程T2   │
       │   PC1      PC2    │
       │   栈1      栈2    │
       │   寄存器1  寄存器2│
       └───────────────────┘
```

这里还有一个细节：

线程栈彼此独立，但仍处于共享虚拟地址空间中。

所以一个线程通过错误指针仍可能修改另一个线程栈中的数据。

#### 6.3 真题：2011 年线程共享资源

问：同一进程创建的多个线程不能共享什么？

A. 代码段

B. 打开的文件

C. 全局变量

D. 某线程的栈指针

答案：D。

这类题不要死记选项，而应从线程执行机制理解：

两个线程可能同时执行不同函数，所以必须分别记录自己的调用位置和寄存器状态。

#### 6.4 用户级线程与内核级线程

| 对比   | 用户级线程 ULT    | 内核级线程 KLT         |
| ---- | ------------ | ----------------- |
| 管理者  | 用户空间线程库      | 操作系统内核            |
| 切换   | 可以在用户态完成     | 由内核参与             |
| 开销   | 通常较小         | 通常较大              |
| 调度   | 用户线程库负责逻辑调度  | 内核直接调度            |
| 阻塞影响 | 取决于映射模型      | 一条线程阻塞通常不影响其他内核线程 |
| 多核并行 | 取决于底层 KLT 数量 | 可以利用多核            |

#### 6.5 三种映射模型

多对一模型

```text
ULT1 ──┐
ULT2 ──┼──► KLT1
ULT3 ──┘
```

多个用户线程只对应一个内核线程。

缺点：

- 一个阻塞系统调用可能使整个映射实体阻塞；
- 不能同时在多个核心执行这些用户线程。

一对一模型

```text
ULT1 ──► KLT1
ULT2 ──► KLT2
ULT3 ──► KLT3
```

优点：

- 一个线程阻塞，其他线程仍可执行；
- 可以多核并行。

缺点：

\- 内核线程管理成本较高。

多对多模型

```text
ULT1 ──┐
ULT2 ──┼──► 多个KLT
ULT3 ──┤
ULT4 ──┘
```

多个用户线程映射到多个内核线程，兼顾灵活性和并行能力，但实现较复杂。

#### 6.6 真题：2019 年用户级线程

题目问错误说法：

> 操作系统为每个用户级线程建立一个线程控制块。

该说法错误。

因为在纯用户级线程模型下，用户线程的管理信息由用户态线程库维护，内核不一定感知每一条用户线程。

#### 6.7 真题：2026 年线程模型

2026 年第 25 题涉及这一考点。

核心判断不能机械使用：

“用户级线程一定无法在多核上并行”。

正确条件是：

$$
\boxed{\text{并行能力取决于底层可调度的内核线程数量}}
$$

多对多模型同样可能实现多核并行。

### 七、进程的内存映像与 IPC

#### 7.1 典型进程虚拟地址空间

```text
较高虚拟地址
┌──────────────────────┐
│ 内核空间              │
├──────────────────────┤
│ 用户栈 Stack          │
│         ↓            │
│                      │
│ mmap映射区            │
│                      │
│         ↑            │
│ 堆 Heap               │
├──────────────────────┤
│ BSS                  │
├──────────────────────┤
│ Data                 │
├──────────────────────┤
│ Text / 只读数据       │
└──────────────────────┘
较低虚拟地址
```

这是典型教学示意，实际地址排列可能因操作系统、体系结构和地址空间随机化而不同。

| 区域    | 典型内容           |
| ----- | -------------- |
| Text  | 程序机器指令         |
| Data  | 已初始化全局、静态变量    |
| BSS   | 未显式初始化的全局、静态变量 |
| Heap  | 动态分配的对象        |
| Stack | 函数栈帧、局部变量、返回信息 |
| mmap  | 文件映射、动态库、共享内存等 |

例如：

```c
int g = 10;         // Data
int h;              // BSS

void f() {
    int x = 5;      // 典型情况：栈或寄存器
    int *p = malloc(sizeof(int));
                     // p：栈或寄存器
                     // *p：堆
}
```

模拟选择题还考查 `.text`、`.rodata` 的区别：

节（section）不同，不代表运行时一定处于不同装入段（segment）。

因此判断变量存储位置时，要注意题目是在问“通常”“必然”还是“可能”。

#### 7.2 IPC：进程间通信

独立进程通常具有独立的虚拟地址空间，因此需要通过操作系统提供的机制通信。

主要方式如下：

| 方式            | 特征         | 典型场景       |
| ------------- | ---------- | ---------- |
| 共享内存          | 多进程映射共同物理页 | 大量数据交换     |
| 管道 Pipe       | 内核缓冲、字节流   | 生产者—消费者式传输 |
| 消息队列          | 以消息为单位交换数据 | 消息型任务协作    |
| Socket        | 通过通信端点收发数据 | 本机或网络通信    |
| 信号 Signal     | 异步事件通知     | 中断、终止等通知   |
| 信号量 Semaphore | 同步或资源数量控制  | 互斥、前驱约束    |

#### 7.3 共享内存

例如：

```text
进程A虚拟地址 ───┐
                 ├──► 物理页X
进程B虚拟地址 ───┘
```

双方可以通过自己的虚拟地址访问同一物理页。

优点：建立映射后，大量数据交换通常能够减少反复复制的开销。

但要注意：

$$
\boxed{\text{共享内存}\neq\text{自动同步}}
$$

如果两个进程同时修改共享计数器，仍可能出现竞态条件。

#### 7.4 管道通信

```text
写进程 → 内核管道缓冲区 → 读进程
```

特点：

- 数据按字节流传输；
- 容量有限；
- 管道空时，读可能阻塞；
- 管道满时，写可能阻塞；
- 普通匿名管道通常是单向数据通道；
- 有名管道可以用于没有亲缘关系的进程。

#### 真题：2014 年管道通信

正确选项：

对管道进行读操作和写操作，都可能发生阻塞。

不要认为只有读操作可能阻塞。

## 第二部分：处理机调度

### 八、调度的基本概念

处理机调度要解决：

有多个进程或线程处于就绪状态时，CPU 下一步应该执行哪一个？

#### 8.1 三级调度

| 调度类型 | 别名        | 主要任务         | 频率 |
| ---- | --------- | ------------ | -- |
| 高级调度 | 作业调度、长程调度 | 决定哪些作业进入系统   | 低  |
| 中级调度 | 中程调度      | 进程换入、换出与挂起管理 | 中  |
| 低级调度 | 进程调度、短程调度 | 决定谁获得 CPU    | 高  |

重点：

高级调度决定谁进入系统，低级调度决定谁使用 CPU。

#### 8.2 抢占式与非抢占式

非抢占式：

进程获得 CPU 后，一般运行到完成或主动阻塞。

新来的高优先级进程不能立即抢走 CPU。

抢占式：

满足条件时，调度器可以强制剥夺 CPU。

例如：

- 时间片耗尽；
- 更高优先级进程到达；
- 更短剩余时间的进程到达。

#### 8.3 调度时机

常见触发事件包括：

- 当前进程完成；
- 当前进程主动阻塞；
- 时间片耗尽；
- 新进程就绪；
- 阻塞进程被唤醒。

但调度时机出现，不代表一定发生进程切换。

例如时钟中断发生后，调度器仍可能选择原进程继续运行。

### 九、调度评价指标与必背公式

假设：

- $AT$：到达时间；
- $BT$：CPU 服务时间；
- $ST$：第一次开始运行时间；
- $CT$：完成时间。

#### 9.1 周转时间

从进入系统到全部完成的时间：

$$
\boxed{TAT=CT-AT}
$$

#### 9.2 带权周转时间

$$
\boxed{W=\frac{TAT}{BT}}
$$

越接近 1，通常说明任务相对于自身服务时间的额外等待越少。

#### 9.3 等待时间

在没有额外 I/O 阻塞阶段的简化模型中：

$$
\boxed{WT=TAT-BT}
$$

如果存在独立的 I/O 阻塞时间，则应扣除这些阻塞时间：

$$
WT=TAT-BT-T_{\text{blocked}}
$$

这里假设总服务需求都已正确统计，等待时间专指在就绪队列中等待 CPU 的累计时间。

#### 9.4 响应时间

$$
\boxed{RT=ST-AT}
$$

注意：

响应时间只统计第一次获得 CPU 之前的等待。

不是整个运行过程中全部等待时间。

#### 9.5 平均周转时间

$$
\boxed{\overline{TAT}=\frac{\sum_{i=1}^{n}TAT_i}{n}}
$$

#### 9.6 CPU 利用率

$$
\text{CPU利用率} = \frac{\text{CPU忙碌时间}}{\text{总观察时间}} \times100\%
$$

计算时必须明确题目是否要求把内核调度、上下文切换等时间计入忙碌时间或有效工作时间。

#### 9.7 真正的计算顺序

考试中不要直接算平均值。

应按照：

$$
\boxed{ \text{画时间轴} \rightarrow CT \rightarrow TAT \rightarrow WT \rightarrow RT }
$$

先把每个进程的运行区间确定，再进行所有指标计算。

### 十、六大经典调度算法

#### 10.1 FCFS：先来先服务

FCFS（First-Come, First-Served）

按照进程到达顺序调度。

通常非抢占。

例如三个进程同时到达：

| 进程 | 服务时间 |
| -- | ---- |
| P1 | 8    |
| P2 | 4    |
| P3 | 2    |

执行顺序：

```text
0         8     12   14
|----P1---|--P2--|P3|
```

等待时间：

$$
WT_1=0
$$

$$
WT_2=8
$$

$$
WT_3=12
$$

平均等待时间：

$$
\overline{WT}=\frac{0+8+12}{3} =\frac{20}{3}
$$

缺点是护航效应：

一个长进程可能让很多短进程排队等待。

#### 10.2 SJF：短作业优先

SJF（Shortest Job First）

从当前已经到达的任务中选择服务时间最短者。

经典 SJF 为非抢占式。

仍以上表为例：

```text
0    2      6          14
| P3 |  P2  |    P1    |
```

等待时间：

$$
WT_3=0,\quad WT_2=2,\quad WT_1=6
$$

平均等待时间：

$$
\overline{WT}=\frac{0+2+6}{3} =\frac83
$$

比 FCFS 明显更低。

优点：

在所有任务同时可用、服务时间已知、没有额外约束等典型条件下，能得到较低的平均等待时间。

缺点：

长作业可能长期等待。

#### 10.3 SRTF：最短剩余时间优先

SRTF 是 SJF 的抢占式版本。

关键不是比较原来的服务时间，而是：

$$
\boxed{\text{比较剩余 CPU 时间}}
$$

例如：

| 进程 | 到达时间 | 服务时间 |
| -- | ---- | ---- |
| P1 | 0    | 8    |
| P2 | 2    | 3    |
| P3 | 4    | 1    |

执行过程：

0 时刻：只有 P1，运行 P1。

2 时刻：P1 已执行 2，剩余 6；P2 需要 3。

所以 P2 抢占 P1。

4 时刻：P2 剩余 1；P3 需要 1。若题设规定剩余时间相同不抢占，则 P2 继续完成。

得到：

```text
0    2      5  6               12
| P1 |  P2  |P3|       P1       |
```

所以：

$$
CT_1=12,\quad CT_2=5,\quad CT_3=6
$$

周转时间：

$$
TAT_1=12
$$

$$
TAT_2=5-2=3
$$

$$
TAT_3=6-4=2
$$

平均周转时间：

$$
\overline{TAT}=\frac{12+3+2}{3} =\frac{17}{3}
$$

陷阱： 新任务到达不一定抢占，必须比较剩余时间，并按题设处理相同值。

#### 10.4 HRRN：高响应比优先

高响应比优先同时考虑等待时间和服务时间。

公式：

$$
\boxed{ R=\frac{WT+BT}{BT} =1+\frac{WT}{BT} }
$$

这里 $R$ 是响应比，不是前面定义的响应时间。

例如：

| 进程 | 已等待时间 | 服务时间 |
| -- | ----- | ---- |
| P1 | 20    | 5    |
| P2 | 30    | 10   |
| P3 | 10    | 2    |

计算：

$$
R_1=1+\frac{20}{5}=5
$$

$$
R_2=1+\frac{30}{10}=4
$$

$$
R_3=1+\frac{10}{2}=6
$$

因此选择 P3。

HRRN 的核心是：

- 短作业容易获得较高响应比；
- 长期等待的作业响应比会不断增加；
- 能兼顾短作业优先和等待公平性。

#### 真题：2009 年调度算法

题目问：

哪种调度算法综合考虑等待时间和执行时间？

答案：高响应比优先。

它的数学依据就是：

$$
R=1+\frac{WT}{BT}
$$

#### 10.5 RR：时间片轮转

RR（Round Robin）

每个进程每次最多运行一个时间片 $q$。

时间片用完而未结束，就重新进入就绪队列。

例如：

| 进程 | 到达时间 | 服务时间 |
| -- | ---- | ---- |
| P1 | 0    | 5    |
| P2 | 0    | 3    |
| P3 | 0    | 4    |

规定初始队列顺序为 P1、P2、P3，时间片：

$$
q=2
$$

执行过程：

```text
0    2    4    6    8   9   11  13
| P1 | P2 | P3 | P1 |P2| P3 | P1 |
```

注意最后两段应按实际剩余时间分别计算：

- P1：0—2、6—8、12—13；
- P2：2—4、8—9；
- P3：4—6、9—11。

所以正确完整时间轴为：

```text
0    2    4    6    8   9    11  12  13
| P1 | P2 | P3 | P1 |P2| P3  |P1?|
```

为避免文字图中不等宽造成误读，以实际区间为准：

| 区间    | 进程 | 运行后剩余 |
| ----- | -- | ----- |
| 0—2   | P1 | 3     |
| 2—4   | P2 | 1     |
| 4—6   | P3 | 2     |
| 6—8   | P1 | 1     |
| 8—9   | P2 | 0     |
| 9—11  | P3 | 0     |
| 11—12 | P1 | 0     |

最终完成时间：

$$
CT_1=12,\quad CT_2=9,\quad CT_3=11
$$

因为三个进程均在 0 时刻到达：

$$
WT_1=12-5=7
$$

$$
WT_2=9-3=6
$$

$$
WT_3=11-4=7
$$

平均等待时间：

$$
\overline{WT}=\frac{7+6+7}{3} =\frac{20}{3}
$$

这类题的核心不是死记运行顺序，而是维护三个信息：

当前队列、当前时刻、各进程剩余时间。

#### 时间片大小的影响

时间片太小：

- 进程响应更及时；
- 上下文切换次数增加；
- 系统开销增大。

时间片太大：

- 上下文切换次数减少；
- 交互响应可能变慢；
- RR 逐渐接近 FCFS。

#### 10.6 多级反馈队列 MLFQ

MLFQ（Multilevel Feedback Queue）综合了多种调度思想。

典型设计：

```text
Q1：最高优先级，时间片 10ms
              ↓ 用完时间片
Q2：中等优先级，时间片 20ms
              ↓ 用完时间片
Q3：较低优先级，时间片 40ms
```

基本规则：

1. 新进程通常进入最高优先级队列。
2. 高优先级队列优先获得 CPU。
3. 使用完整时间片仍未结束的任务可能降级。
4. 交互型任务通常更容易及时响应。
5. 可以通过优先级提升缓解低级队列饥饿。

注意：

多级队列与多级反馈队列并不相同。

多级队列通常根据类别固定分队列。

多级反馈队列允许进程根据执行行为改变所在队列。

### 十一、真题：2019 年多级反馈队列计算

题设：

Q1：时间片轮转，时间片为 10ms。

Q2：短进程优先。

Q1 优先级高于 Q2，只有 Q1 为空才调度 Q2。

两个进程：

| 进程 | 服务时间 |
| -- | ---- |
| P1 | 30ms |
| P2 | 20ms |

二者依次进入 Q1。

#### 第一步：Q1 调度

P1 执行 10ms：

剩余：

$$
30-10=20\text{ms}
$$

降入 Q2。

P2 执行 10ms：

剩余：

$$
20-10=10\text{ms}
$$

降入 Q2。

此时时间为 20ms。

#### 第二步：Q2 调度

Q2 中：

- P1 剩余 20ms；
- P2 剩余 10ms。

按短进程优先：

先执行 P2，再执行 P1。

```text
0      10      20     30          50
| P1   | P2    | P2   |    P1      |
   Q1     Q1      Q2       Q2
```

#### 第三步：计算等待时间

P1：

$$
WT_1=50-30=20\text{ms}
$$

P2：

$$
WT_2=30-20=10\text{ms}
$$

因此：

$$
\boxed{ \overline{WT}=\frac{20+10}{2}=15\text{ms} }
$$

这道题最容易错的地方：

进入低优先级队列之后，不代表立即运行。

必须先把更高优先级队列中的任务处理完，再按低级队列自己的算法排序。

### 十二、真题：2026 年优先级、时间片和时钟中断综合题

这是历年大题资料中一个非常值得练习的综合调度模型。

题设：

- 优先级数值越大越高；
- 时间片 50ms；
- 时钟中断间隔 10ms；
- 只有时钟中断发生时才允许高优先级进程抢占；
- 时间片耗尽后，优先级减 1。

| 进程 | 到达时间 | 初始优先级 | CPU 时间 |
| -- | ---- | ----- | ------ |
| P1 | 10   | 3     | 95     |
| P2 | 10   | 4     | 20     |
| P3 | 12   | 2     | 40     |
| P4 | 14   | 5     | 60     |

#### 12.1 为什么 P4 到达后不能立即抢占？

P4 在 14ms 到达。

虽然其优先级 5 高于 P2 的 4，但题目规定：

只有发生时钟中断才允许进行优先级抢占。

因此 P4 需要等到 20ms 才有机会抢占 P2。

这是本题最重要的限定条件。

#### 12.2 完整执行时间表

| 时间区间    | 执行进程 | 关键事件          |
| ------- | ---- | ------------- |
| 10—20   | P2   | 20ms 被 P4 抢占  |
| 20—70   | P4   | 时间片用完，优先级降为 4 |
| 70—80   | P2   | 完成            |
| 80—90   | P4   | 完成            |
| 90—140  | P1   | 时间片用完，优先级降为 2 |
| 140—180 | P3   | 完成            |
| 180—225 | P1   | 完成            |

因此首次获得 CPU 的时刻：

$$
\boxed{ ST_1=90,\quad ST_2=10,\quad ST_3=140,\quad ST_4=20 }
$$

根据题目给定到达时间，首次响应时间分别为：

$$
RT_1=90-10=80\text{ms}
$$

$$
RT_2=10-10=0
$$

$$
RT_3=140-12=128\text{ms}
$$

$$
RT_4=20-14=6\text{ms}
$$

本题按包含 10 ms 起始时钟边界的计数口径，可得到 7 次调度、22 次时钟中断；若只统计 10 ms 之后至完成前的周期性时钟事件，则为 21 次。务必说明计数边界。

#### 12.3 本题反复强调的三个概念

到达时间 ≠ 抢占时间。

时间片耗尽 ≠ CPU 执行完成。

时钟中断 ≠ 一定发生上下文切换。

遇到复杂调度题时，必须将这三个概念分别记录。

### 十三、CPU 与 I/O 并行：流水线调度计算

这一类题容易与普通 CPU 调度题混淆。

#### 13.1 真题：2016 年输入、计算、输出流水线

有三个作业，每个作业都必须按照：

```text
输入 → 计算 → 输出
```

执行。

其中：

- 输入时间：2ms；
- CPU 计算时间：3ms；
- 输出时间：4ms。

系统只有：

- 1 台输入设备；
- 1 个 CPU；
- 1 台输出设备。

问三个作业最少需要多长时间？

#### 13.2 关键思想

不同资源可以同时工作。

一个作业正在输出时，另一个作业可以计算，第三个作业可以输入。

排程如下：

| 作业 | 输入  | 计算   | 输出    |
| -- | --- | ---- | ----- |
| J1 | 0—2 | 2—5  | 5—9   |
| J2 | 2—4 | 5—8  | 9—13  |
| J3 | 4—6 | 8—11 | 13—17 |

最终：

$$
\boxed{T_{\min}=17\text{ms}}
$$

不要简单计算：

$$
3(2+3+4)=27\text{ms}
$$

因为这个算法错误地假设所有任务完全串行执行。

真正的关键是：

不同设备允许并行；同一独占设备上的操作不能重叠。

2012 年相关题也考查 CPU 计算和 I/O 等待交错执行，给定条件下最短总历时为 260 ms。

### 十四、上下文切换与调度开销

#### 14.1 上下文切换保存什么？

典型内容包括：

- PC；
- 通用寄存器；
- 栈指针；
- 状态寄存器；
- 相关调度状态。

若切换到不同进程，还可能需要更换地址空间信息、页表基地址等。

#### 14.2 上下文切换、模式切换和调度的区别

| 概念      | 发生了什么            | 必须切换进程吗 |
| ------- | ---------------- | ------- |
| 模式切换    | CPU 在用户态、内核态间切换  | 否       |
| 调度决策    | 选择下一个执行实体        | 否       |
| 进程上下文切换 | 保存当前进程并恢复另一进程的现场 | 是       |

例如：

一个进程执行系统调用，进入内核读取系统时间，然后返回同一个进程。

这个过程发生了用户态与内核态的切换。

但不一定发生进程上下文切换。

#### 14.3 真题：2024 年进程切换

在分页存储管理系统中，切换进程时可能需要更新：

Ⅰ. 程序计数器

Ⅱ. 栈相关寄存器

Ⅲ. 页表基地址寄存器

答案：三者都需要。

原因是切换进程意味着恢复另一进程的执行现场，并通常切换地址空间。

## 第三部分：进程同步与互斥

### 十五、为什么需要同步与互斥？

这是本章综合大题的核心基础。

#### 15.1 什么是竞态条件？

假设两个线程共享：

```c
int count = 0;
```

线程 T1 和 T2 都执行：

```text
count++;
```

我们可能认为最终结果必然是：

$$
count=2
$$

但实际上不一定。

因为 `count++` 可能被分解成：

```text
读取 count
    ↓
加 1
    ↓
写回 count
```

如果出现如下交错：

| 步骤 | T1         | T2         |
| -- | ---------- | ---------- |
| 1  | 读取 count=0 |            |
| 2  |            | 读取 count=0 |
| 3  | 计算 0+1     |            |
| 4  |            | 计算 0+1     |
| 5  | 写回 1       |            |
| 6  |            | 写回 1       |

最终：

$$
\boxed{count=1}
$$

明明执行了两次加一，却只得到一。

这就是竞态条件（Race Condition）。

其本质是：

多个执行流访问共享状态，结果依赖不可预测的执行顺序。

#### 15.2 临界资源与临界区

临界资源：

同一时刻只允许一个执行流进行相关访问的资源。

临界区：

访问临界资源的代码段。

例如：

```text
P(mutex);

/* 临界区 */
count++;

V(mutex);
```

需要注意：

共享资源不一定必须禁止多个读者同时访问。

如果所有线程都只读某份不会变化的数据，通常可以并发读取。

### 十六、同步和互斥到底有什么区别？

这是整个 P/V 学习过程的第一道关。

<Tabs items={['互斥', '同步']} defaultIndex={0}>
  <Tab value="互斥">

例如：

两个进程使用同一台打印机。

```text
P1：打印文件A

P2：打印文件B
```

如果打印机不能同时为两个作业服务，就需要互斥。

使用：

```c
semaphore printer = 1;
```

P1：

```text
P(printer);
print_A();
V(printer);
```

P2：

```text
P(printer);
print_B();
V(printer);
```

<Callout type="info" title="互斥控制的是访问资格，而非执行顺序">

这里不规定谁先打印。

只要求：

</Callout>

$$
\boxed{\text{同一时刻最多一个}}
$$

  </Tab>
  <Tab value="同步">

例如：

```text
P1：读取文件
P2：处理读取结果
```

P2 必须等 P1 读取完成。

这是前驱关系：

$$
P_1\rightarrow P_2
$$

使用：

```c
semaphore done = 0;
```

P1：

```text
read_file();
V(done);
```

P2：

```text
P(done);
process_data();
```

这里的 `done` 不控制互斥，而是记录读取完成事件。

  </Tab>
</Tabs>

#### 16.3 三种最常见信号量

| 需求    | 信号量初值 | 作用     |
| ----- | ----- | ------ |
| 互斥访问  | 1     | 控制独占   |
| 前驱同步  | 0     | 等待前驱完成 |
| N 个资源 | N     | 控制资源数量 |

记住这一张表，就掌握了 P/V 设计的基本语言。

### 十七、临界区互斥的基本准则

教材通常总结为：

#### 1. 空闲让进

临界区空闲时，有资格进入的进程应能够进入。

#### 2. 忙则等待

临界区已经被使用时，其他竞争者不能同时进入。

#### 3. 有限等待

应避免某个进程无限期等待进入临界区。

#### 4. 让权等待

不能获得资源时，尽量放弃 CPU，而不是一直进行无意义的循环检查。

注意第四条反映的是理想的等待方式，不意味着自旋锁一定不正确。

自旋锁可以实现互斥，只是未必满足让权等待。

#### 17.1 忙等与阻塞等待

| 对比       | 忙等           | 阻塞等待         |
| -------- | ------------ | ------------ |
| 等待方式     | 循环检查         | 睡眠等待         |
| 是否占用 CPU | 通常占用         | 不占用等待期间的 CPU |
| 优点       | 短暂等待时可避免切换开销 | 长时间等待更节省 CPU |
| 缺点       | 可能浪费 CPU     | 阻塞和唤醒需要开销    |

忙等不等于死锁。

忙等也不等于饥饿。

### 十八、软件互斥算法

#### 18.1 单纯的锁变量为什么不可靠？

错误代码：

```text
bool lock = false;

while (lock);

lock = true;

/* 临界区 */

lock = false;
```

问题是：

```text
while (lock);
lock = true;
```

属于两个独立操作。

可能发生：

```text
T1发现 lock=false
         ↓
CPU切换
         ↓
T2发现 lock=false
         ↓
T2进入临界区
         ↓
T1恢复执行
         ↓
T1也进入临界区
```

结果违反互斥。

#### 18.2 单标志轮流法

通过共享变量 `turn` 控制两个线程轮流进入。

其问题在于：

即使轮到的线程不想进入临界区，另一个线程也可能无法进入。

因此可能违反空闲让进。

#### 18.3 Peterson 算法

Peterson 算法是经典的软件互斥算法，适用于两个执行流的教学模型。

主要变量：

```c
bool flag[2] = {false, false};
int turn;
```

其中：

- `flag[i]`：线程 i 是否希望进入临界区；
- `turn`：双方竞争时优先让谁进入。

线程 0：

```text
flag[0] = true;
turn = 1;

while (flag[1] && turn == 1) {
    ;
}

/* 临界区 */

flag[0] = false;
```

线程 1：

```text
flag[1] = true;
turn = 0;

while (flag[0] && turn == 0) {
    ;
}

/* 临界区 */

flag[1] = false;
```

#### 18.4 理解 Peterson 的关键

线程 0 想进入时：

```text
flag[0] = true;
```

表示自己希望进入。

接着：

```text
turn = 1;
```

表示如果双方同时竞争，优先让对方。

判断：

```text
while (flag[1] && turn == 1)
```

只有对方也想进入，而且自己已经让出了优先权时，线程 0 才等待。

如果线程 1 不想进入：

```text
flag[1] == false
```

线程 0 可以直接进入。

如果两者同时竞争，`turn` 最终只会取一个值，从而决定其中一方等待。

注意： 这是建立在相应内存访问顺序假设上的经典教材算法。真实现代多核程序还需要考虑内存模型、编译器重排及同步原语，不能直接将普通共享变量代码当成通用工程实现。

### 十九、硬件互斥：TAS、CAS、Swap

#### 19.1 Test-and-Set

硬件保证检查旧值和设置新值具有原子语义。

逻辑上：

```text
bool test_and_set(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
```

注意：这里展示的是抽象逻辑，真实实现必须使用硬件原子操作。

使用方式：

```text
while (test_and_set(&lock)) {
    ;
}

/* 临界区 */

lock = false;
```

#### 19.2 CAS

CAS（Compare-and-Swap）：

比较内存中的值是否等于期望值。

如果相等，则原子地修改。

例如：

```text
while (!CAS(&lock, 0, 1)) {
    ;
}

/* 临界区 */

lock = 0;
```

TAS、CAS 和 Swap 的共同核心：

$$
\boxed{\text{检查与修改必须具有原子语义}}
$$

#### 19.3 真题：2023 年第 45 题

题目给出：

```text
bool lock = FALSE;
bool key = TRUE;

if (key == TRUE)
    swap(key, lock);

/* 临界区 */

lock = TRUE;
```

要求找到错误。

第一处错误：`if` 应改为 `while`。

正确写法：

```text
while (key == TRUE)
    swap(key, lock);
```

原因：

如果一次交换之后没有成功获得锁，就必须继续等待。

仅判断一次不能保证成功。

第二处错误：退出临界区应设置 `lock=FALSE`。

因为：

```text
lock = TRUE;
```

表示锁被占用。

退出时应该将锁设为未占用。

完整结构：

```c
bool lock = FALSE;

void worker() {
    bool key = TRUE;

    while (key == TRUE) {
        atomic_swap(&key, &lock);
    }

    /* 临界区 */

    lock = FALSE;
}
```

这里将 `atomic_swap` 视为具备适当内存同步语义的原子操作。

#### 19.4 为什么不能用普通交换函数替代原子 Swap？

例如：

```c
void newSwap(bool *a, bool *b) {
    bool temp = *a;
    *a = *b;
    *b = temp;
}
```

因为这个函数由多条普通指令组成。

两个线程可以在其执行过程中交错。

所以：

单线程执行结果等价，不代表并发执行语义等价。

这是 2023 年真题真正想考查的内容。

### 二十、开关中断实现互斥

#### 20.1 为什么关中断能帮助实现互斥？

在单处理器系统中，关中断可以阻止普通可屏蔽中断触发的抢占。

因此内核可以在适当的短暂关键区间中使用这一机制保护共享数据。

但是：

关中断不是所有情形下都适用的万能互斥方法。

#### 20.2 真题：2021 年第 45 题

题目提供两种实现。

方法一：

```text
wait(S) {
    关中断;

    while (S <= 0);

    S--;

    开中断;
}
```

这种方法有严重问题。

当：

$$
S=0
$$

当前进程会一直执行：

```text
while (S <= 0);
```

并且始终关中断。

在题目默认的单处理机环境中，如果其他进程需要获得 CPU 才能执行：

```text
signal(S);
```

那么系统可能无法让那个进程运行。

最终形成永久等待。

#### 20.3 正确思路

等待条件不满足时，必须给其他执行流运行和释放资源的机会。

例如题目方法二：

```text
wait(S) {
    关中断;

    while (S <= 0) {
        开中断;
        关中断;
    }

    S--;

    开中断;
}
```

这种方式在题目规定的单 CPU、内核态条件下可以维持相应互斥。

但是在多核系统中：

只关闭当前 CPU 的中断，不能阻止另一个 CPU 核心同时访问共享变量。

此外，普通用户程序不能直接执行任意开关中断指令，因为它们属于特权操作。

## 第四部分：信号量和 P/V 操作

### 二十一、信号量的基本原理

信号量可以用来表示：

1. 某种资源还剩多少；
2. 某个事件是否已经发生；
3. 某个共享对象是否可以访问。

#### 21.1 P 操作

P 操作又叫 `wait()`。

主要作用：

申请一个许可。

如果许可充足，则继续执行。

否则可能进入等待状态。

#### 21.2 V 操作

V 操作又叫 `signal()`。

主要作用：

释放一个许可，或者发出一次事件通知。

若存在等待者，可能唤醒其中一个。

#### 21.3 经典记录型信号量

教材中常见定义：

```text
P(S) {
    S.value--;

    if (S.value < 0) {
        block();
    }
}

V(S) {
    S.value++;

    if (S.value <= 0) {
        wakeup();
    }
}
```

这里的修改计数、判断、维护等待队列等关键操作必须具有原子性。

#### 21.4 负数信号量的含义

在上述经典定义下：

$$
S.value=-k
$$

表示：

$$
\boxed{\text{有 }k\text{ 个进程等待该信号量}}
$$

例如：

```text
初值 S=2

P(S) → S=1
P(S) → S=0
P(S) → S=-1，有1个进程等待
P(S) → S=-2，有2个进程等待
```

此时执行一次 V：

```text
S=-2

V(S) → S=-1
```

会唤醒一个等待进程。

仍有一个进程等待。

注意不同教材可能采用不同的信号量内部表示方式，做题时必须以题目定义为准。

### 二十二、最重要的 P/V 解题方法

看到题目时，不要急着写代码。

应首先把自然语言转换成三类约束。

| 约束类型 | 典型描述       | 处理方法         |
| ---- | ---------- | ------------ |
| 互斥   | 同时只能一个     | `mutex=1`    |
| 前驱   | A 做完，B 才能做 | `sync=0`     |
| 容量   | 最多允许 N 个   | `resource=N` |

#### 22.1 最关键的原则：先申请资源，再进入临界区

错误代码：

```text
P(mutex);
P(full);

get_item();

V(mutex);
```

假设缓冲区为空：

$$
full=0
$$

消费者先取得互斥锁。

然后执行：

```text
P(full);
```

发生阻塞。

但生产者需要取得同一把锁才能放入产品。

因此：

```text
消费者持有 mutex
      ↓
等待生产者产生产品
      ↓
生产者等待 mutex
      ↓
无法继续
```

这就是典型死锁。

正确方式：

```text
P(full);
P(mutex);

get_item();

V(mutex);
V(empty);
```

考场最重要的 P/V 顺序原则：

> 先等待业务条件满足，再取得共享结构的互斥锁。

当然，这条原则适用于此类标准有界缓冲区模型；复杂题目仍应分析具体的锁依赖关系。

### 二十三、前驱图与最少信号量设计

#### 23.1 真题：2020 年第 45 题

有五个操作：

A、B、C、D、E。

要求：

- C 必须等待 A 和 B 完成；
- E 必须等待 C 和 D 完成。

依赖关系：

```text
A ──┐
    ├──► C ──┐
B ──┘        ├──► E
D ───────────┘
```

一种直接设计是为四条前驱边分别设置信号量。

```c
semaphore ac = 0;
semaphore bc = 0;
semaphore ce = 0;
semaphore de = 0;
```

各进程：

```text
PA() {
    A();
    V(ac);
}

PB() {
    B();
    V(bc);
}

PC() {
    P(ac);
    P(bc);

    C();

    V(ce);
}

PD() {
    D();
    V(de);
}

PE() {
    P(ce);
    P(de);

    E();
}
```

理解重点：

C 有两个前驱，因此必须等待两个完成通知。

不能只执行一次 P 操作就默认两个前驱都已完成。

#### 23.2 真题：2022 年第 46 题

两个线程：

```text
T1：A → E → F
T2：B → C → D
```

额外要求：

- C 必须在 A、B 后执行；
- D、E 必须在 C 后执行；
- F 必须在 E 后执行。

本题特别要求尽量减少信号量数量。

关键技巧：

同一线程内原本存在的顺序，不需要再用信号量保证。

因此：

- B 在 C 前，天然满足；
- C 在 D 前，天然满足；
- E 在 F 前，天然满足。

真正需要跨线程建立的关系只有：

$$
A\rightarrow C
$$

$$
C\rightarrow E
$$

使用两个信号量：

```c
semaphore AC = 0;
semaphore CE = 0;
```

T1：

```text
T1() {
    A();
    V(AC);

    P(CE);
    E();
    F();
}
```

T2：

```text
T2() {
    B();
    P(AC);

    C();
    V(CE);

    D();
}
```

这就是标准答案的核心。

答题技巧：先删去线程内部已经保证的前驱边，再为跨线程约束设计同步。

## 第五部分：经典同步问题

这是本章最需要反复练习的部分。

### 二十四、生产者—消费者问题

#### 24.1 基本模型

一个容量为 $N$ 的缓冲区。

生产者放入产品。

消费者取出产品。

约束：

- 满了不能再放；
- 空了不能再取；
- 对共享缓冲区数据结构的修改必须互斥。

使用：

```c
semaphore empty = N;
semaphore full  = 0;
semaphore mutex = 1;
```

#### 24.2 生产者

```text
producer() {
    while (true) {
        item x = produce();

        P(empty);
        P(mutex);

        put(x);

        V(mutex);
        V(full);
    }
}
```

#### 24.3 消费者

```text
consumer() {
    while (true) {
        P(full);
        P(mutex);

        item x = get();

        V(mutex);
        V(empty);

        consume(x);
    }
}
```

#### 24.4 三个信号量分工

| 信号量     | 解决什么           |
| ------- | -------------- |
| `empty` | 缓冲区不能写满        |
| `full`  | 缓冲区不能读空        |
| `mutex` | 共享结构不能发生并发修改冲突 |

#### 24.5 资源守恒

在稳定状态下，如果没有尚未完成的预订和发布动作：

$$
\boxed{empty+full=N}
$$

更严格地说，并发过程中可能存在已执行 `P(empty)` 但尚未 `V(full)` 的在途产品，因此不能在任意指令交错瞬间都机械使用这个等式。

正确的不变量应该同时考虑已预订但尚未转换为成品许可的容量。

### 二十五、真题：2009 年奇偶数生产者—消费者

这是经典模型的重要变形。

#### 25.1 题目

有三个进程：

- P1 生产正整数；
- P2 只消费奇数；
- P3 只消费偶数。

共享容量为 $N$ 的缓冲区。

要求：

- 缓冲区不能溢出；
- 不能重复消费；
- P2 只能取奇数；
- P3 只能取偶数；
- 共享缓冲区操作需要互斥。

#### 25.2 为什么普通 `full` 不够？

普通生产者—消费者使用：

```text
full = 0;
```

只能表示：

有多少产品可以消费。

但不能表示产品属于哪一类。

如果 P2 获得一个 `full` 许可，缓冲区中可能只有偶数。

所以必须把同步条件进一步细分。

#### 25.3 设计四个信号量

```c
semaphore mutex = 1;
semaphore empty = N;
semaphore odd   = 0;
semaphore even  = 0;
```

含义：

- `mutex`：缓冲区互斥；
- `empty`：剩余空槽；
- `odd`：可消费奇数数量；
- `even`：可消费偶数数量。

#### 25.4 生产者

```c
P1() {
    while (true) {
        int x = produce();

        P(empty);
        P(mutex);

        put(x);

        V(mutex);

        if (x % 2 == 1)
            V(odd);
        else
            V(even);
    }
}
```

#### 25.5 奇数消费者

```c
P2() {
    while (true) {
        P(odd);
        P(mutex);

        int x = getodd();

        V(mutex);
        V(empty);

        countodd(x);
    }
}
```

#### 25.6 偶数消费者

```c
P3() {
    while (true) {
        P(even);
        P(mutex);

        int x = geteven();

        V(mutex);
        V(empty);

        counteven(x);
    }
}
```

#### 25.7 为什么是四个信号量？

这道题包含四种约束：

| 约束           | 信号量     |
| ------------ | ------- |
| 有空位才能生产      | `empty` |
| 有奇数才能由 P2 消费 | `odd`   |
| 有偶数才能由 P3 消费 | `even`  |
| 修改共享缓冲区必须互斥  | `mutex` |

这类题的通用方法：

当不同消费者具有不同消费条件时，通常需要分别记录对应条件的可用许可。

以后遇到：

- 红球与蓝球；
- 奇数与偶数；
- A 类型与 B 类型产品；
- 优先级不同的任务；

都可以考虑这种分类计数模式。

### 二十六、真题：2014 年连续消费 10 件产品

题目：

多个生产者和多个消费者共享容量为 1000 的环形缓冲区。

额外要求：

一个消费者必须连续取出 10 件产品后，其他消费者才能开始取产品。

#### 26.1 与普通模型有什么区别？

普通模型只要求一次缓冲区访问互斥。

这道题还要求：

一个消费者在连续 10 次取出操作期间，不能被其他消费者插入。

因此增加：

```c
semaphore consumerGroup = 1;
```

信号量：

```c
semaphore empty = 1000;
semaphore full = 0;
semaphore mutex = 1;
semaphore consumerGroup = 1;
```

#### 26.2 消费者

```c
consumer() {
    while (true) {
        P(consumerGroup);

        for (int i = 0; i < 10; i++) {
            P(full);
            P(mutex);

            item x = get();

            V(mutex);
            V(empty);

            save_to_local_batch(x);
        }

        V(consumerGroup);

        process_batch();
    }
}
```

#### 26.3 为什么不能让 `mutex` 一直保持 10 次操作？

例如错误写法：

```c
P(mutex);

for (int i = 0; i < 10; i++) {
    P(full);
    get();
}

V(mutex);
```

如果缓冲区暂时只有 5 件产品：

消费者取完 5 件后等待第 6 件。

但它仍然持有 `mutex`。

生产者无法进入缓冲区放入第 6 件产品。

因此可能死锁。

正确思想：

- `consumerGroup` 只排斥其他消费者；
- `mutex` 只保护一次缓冲区操作；
- `full` 用来等待产品。

这说明：

不同层次的互斥要求，不能简单用同一把锁全部代替。

### 二十七、真题：2024 年单缓冲区同步与互斥

题目中的缓冲区 B 只能放一个数据分组。

三种操作：

- C1：写入数据；
- C2：读出数据；
- C3：修改数据。

#### 27.1 两个进程都执行 C1

两者都写共享缓冲区。

因此 C1 属于需要互斥保护的临界区操作。

#### 27.2 B 初始为空，P1 写一次，P2 读一次

只需要：

```c
semaphore full = 0;
```

P1：

```text
C1();
V(full);
```

P2：

```text
P(full);
C2();
```

为什么不需要 mutex？

因为题设只有：

- 一个写者；
- 一个读者；
- 每人只执行一次。

同步关系已经保证：

$$
C1\rightarrow C2
$$

两次访问不可能重叠。

这道题的意义非常重要：

不能看到共享缓冲区就无条件添加三个信号量。

必须根据具体并发关系判断最少需要几个。

#### 27.3 B 初始非空，两者都执行 C3

此时两个进程都修改相同数据。

只需要：

```c
semaphore mutex = 1;
```

每个进程执行：

```text
P(mutex);
C3();
V(mutex);
```

这就是：

同步和互斥要分别判断，不能机械套模板。

### 二十八、读者—写者问题

#### 28.1 基本要求

多个读者可以同时读取。

但是：

- 写者之间互斥；
- 写者和读者互斥；
- 读者之间不需要互斥读取。

| 当前访问情况 | 新读者 | 新写者 |
| ------ | --- | --- |
| 无人访问   | 可进入 | 可进入 |
| 已有读者   | 可进入 | 等待  |
| 已有写者   | 等待  | 等待  |

#### 28.2 读者优先算法

设置：

```c
int read_count = 0;

semaphore mutex = 1;
semaphore wrt = 1;
```

读者：

```text
reader() {
    while (true) {
        P(mutex);

        read_count++;

        if (read_count == 1)
            P(wrt);

        V(mutex);

        read_data();

        P(mutex);

        read_count--;

        if (read_count == 0)
            V(wrt);

        V(mutex);
    }
}
```

写者：

```text
writer() {
    while (true) {
        P(wrt);

        write_data();

        V(wrt);
    }
}
```

#### 28.3 为什么第一个读者要申请 `wrt`？

因为只要有读者正在读取，写者就不能进入。

第一个读者负责锁住写者。

之后第二、第三个读者可以直接加入读取。

#### 28.4 为什么最后一个读者才释放 `wrt`？

只要还有读者，写者就不能修改数据。

所以：

$$
read\\_count=0
$$

时，最后一个读者才释放写者锁。

因此这道题的核心口诀：

第一个读者锁写者，最后一个读者释放写者。

#### 28.5 读者优先的缺陷

如果读者不断到来：

```text
读者1进入
读者2进入
读者3进入
读者4进入
……
```

`read_count` 可能长期不为 0。

写者一直无法得到 `wrt`。

这就是写者饥饿。

#### 28.6 写者优先

写者优先的关键是：

一旦写者开始等待，后来的读者不能无限制插队。

通常增加控制新读者进入的闸门信号量，以及等待写者计数。

第一个等待写者关闭新读者入口。

最后一个写者完成后重新开放入口。

#### 28.7 公平读写

公平方案通常使用统一入口队列或顺序控制机制。

目标：

- 不让后来读者不断越过等待写者；
- 不让后来写者不断越过等待读者。

但严格公平性还依赖锁或信号量的等待队列规则。

如果底层唤醒策略不公平，仅凭普通二元信号量未必能保证严格的先来先服务。

### 二十九、哲学家就餐问题

#### 29.1 基本模型

$n$ 位哲学家围成圆圈。

每两个人之间有一根筷子。

每个人必须同时获得左右两根筷子才能吃饭。

若所有人都执行：

```text
P(left);
P(right);

eat();

V(right);
V(left);
```

可能发生：

```text
每个人都拿到了左边筷子
              ↓
每个人等待右边筷子
              ↓
没有人能够继续
```

形成死锁。

#### 29.2 为什么会发生死锁？

因为满足了四个必要条件：

- 筷子必须互斥使用；
- 每个人拿着一根继续等待另一根；
- 筷子不能被强制收回；
- 形成循环等待。

#### 29.3 解决方案一：最多允许 n-1 人尝试取筷子

```c
semaphore room = n - 1;
semaphore chop[n] = {1, 1, ..., 1};
```

哲学家：

```c
philosopher(int i) {
    while (true) {
        think();

        P(room);

        P(chop[i]);
        P(chop[(i + 1) % n]);

        eat();

        V(chop[(i + 1) % n]);
        V(chop[i]);

        V(room);
    }
}
```

由于至少有一个人不能同时参与取筷子，经典的所有人各持一根筷子的闭合等待局面被破坏。

#### 29.4 解决方案二：统一资源顺序

给所有筷子编号。

规定每个人先申请编号较小的筷子，再申请编号较大的筷子。

这样所有人按照统一顺序申请资源。

不会形成循环等待链。

这是死锁预防中最重要、最容易迁移的方法之一。

### 三十、真题：2019 年哲学家、筷子和碗

该题在原有哲学家模型中增加：

- $n$ 位哲学家；
- $m$ 个碗；
- 每人还必须获得一个碗。

要求：

尽可能多的人同时就餐，且避免死锁。

可以设置：

```c
semaphore chop[n] = {1, 1, ..., 1};

semaphore bowl = min(m, n - 1);
```

哲学家：

```c
philosopher(int i) {
    while (true) {
        think();

        P(bowl);

        P(chop[i]);
        P(chop[(i + 1) % n]);

        eat();

        V(chop[(i + 1) % n]);
        V(chop[i]);

        V(bowl);
    }
}
```

#### 为什么碗的信号量不是直接设置为 m？

当：

$$
m\ge n
$$

时，如果所有哲学家都能同时获得碗，那么所有人可能再次形成拿一根筷子等待另一根的闭环。

因此最多允许：

$$
n-1
$$

人进入取筷子阶段。

综合碗数量限制，设置：

$$
\boxed{bowl=\min(m,n-1)}
$$

#### 最大能够同时就餐多少人？

还必须考虑：

相邻哲学家不能同时就餐，因为它们共享筷子。

因此最大同时就餐人数：

$$
\boxed{ N_{\max}= \min\left(m,\left\lfloor\frac n2\right\rfloor\right) }
$$

这是本题非常重要的两个不同数量：

$$
\min(m,n-1)
$$

是允许进入资源申请阶段的人数限制。

而：

$$
\min\left(m,\left\lfloor\frac n2\right\rfloor\right)
$$

才是实际最大同时就餐人数。

### 三十一、真题：2025 年植树流水线

这道题是生产者—消费者与前驱同步的综合模型。

#### 31.1 题目

甲：挖坑。

乙：放树苗并填土。

丙：浇水。

顺序为：

```text
甲挖坑 → 乙种树 → 丙浇水
```

条件：

- 甲、乙共用一把铁锹；
- 尚未被乙处理的树坑数量最多为 3；
- 初始没有树坑；
- 水桶只有丙使用。

#### 31.2 分析四种约束

| 约束        | 信号量      | 初值 |
| --------- | -------- | -- |
| 最多三个待处理树坑 | `slots`  | 3  |
| 乙必须等甲挖好坑  | `pits`   | 0  |
| 丙必须等乙种好树  | `water`  | 0  |
| 甲乙共用铁锹    | `shovel` | 1  |

#### 31.3 完整代码

```c
semaphore slots = 3;
semaphore pits = 0;
semaphore water = 0;
semaphore shovel = 1;
```

甲：

```text
Jia() {
    while (true) {
        P(slots);

        P(shovel);
        dig();
        V(shovel);

        V(pits);
    }
}
```

乙：

```text
Yi() {
    while (true) {
        P(pits);

        P(shovel);
        plant();
        V(shovel);

        V(slots);
        V(water);
    }
}
```

丙：

```text
Bing() {
    while (true) {
        P(water);

        water_plant();
    }
}
```

#### 31.4 为什么不需要再给水桶加锁？

因为只有丙一个执行主体使用水桶。

不存在与其他进程争用水桶的情况。

所以没有必要额外引入水桶互斥信号量。

#### 31.5 为什么甲必须先 P(slots)，再 P(shovel)？

如果先拿铁锹，再等待空位：

```text
P(shovel);
P(slots);
```

当待处理树坑达到上限时，甲会等待 `slots`。

但乙需要铁锹才能填土并释放 `slots`。

于是可能发生死锁。

正确顺序：

```text
P(slots);
P(shovel);
```

这就是前面“先申请资源数量许可，再进入互斥临界区”原则的直接应用。

### 三十二、模拟题：猴子过绳与读者—写者模型

这是 2027 王道八套卷第 3 套综合题。

题意：

- 北行猴子之间可以同时通过；
- 南行猴子之间可以同时通过；
- 北行和南行不能同时通过同一根绳子。

本质是：

同方向共享，反方向互斥。

它与读者—写者问题高度相似。

#### 32.1 信号量设计

```c
semaphore rope = 1;
semaphore mutexN = 1;
semaphore mutexS = 1;

int north = 0;
int south = 0;
```

北行：

```text
GoNorth() {
    P(mutexN);

    north++;

    if (north == 1)
        P(rope);

    V(mutexN);

    crossNorth();

    P(mutexN);

    north--;

    if (north == 0)
        V(rope);

    V(mutexN);
}
```

南行对称实现。

#### 32.2 为什么允许同向并行？

因为只有第一只北行猴子需要占有 `rope`。

后来的北行猴子只增加计数，不需要再次申请 `rope`。

因此同方向可以同时通行。

最后一只北行猴子离开后，才释放方向占有权。

#### 32.3 这套方案有什么问题？

如果北行猴子连续到来：

```text
北行1进入
北行2进入
北行3进入
北行4进入
……
```

`north` 可能长期不归零。

南行猴子可能饥饿。

因此模拟题进一步要求考虑公平性。

典型方法是增加统一入口闸门 `turnstile`，让一个已经开始等待绳索的方向能够阻止新来的反方向或同方向猴子不断插队。

严格的有界等待则需要结合公平队列或 FIFO 机制。

### 三十三、模拟题：多接收者广播

2027 八套卷第 5 套综合题给出：

- 多个发送者；
- 多个接收者；
- $m$ 个缓冲区；
- 每条消息必须被所有接收者分别读取一次；
- 所有人读完后，缓冲区才允许重用。

#### 33.1 与普通消费者模型最大的区别

普通消费者模型：

```text
生产一个产品
       ↓
一个消费者取走
       ↓
缓冲区释放
```

本题是：

```text
生产一条消息
       ↓
接收者1读取
接收者2读取
……
接收者n读取
       ↓
缓冲区释放
```

因此不能让任何一个接收者在读完后立即释放空位。

#### 33.2 设计思路

需要建立：

- `empty=m`：剩余可用缓冲区；
- 每个接收者自己的消息就绪许可；
- 每条消息的剩余未读人数；
- 对共享计数和缓冲区状态的互斥保护；
- 各接收者自己的读取位置。

对每条消息建立计数：

$$
remain=n_2
$$

每个接收者成功读取一次后：

$$
remain\leftarrow remain-1
$$

只有当：

$$
\boxed{remain=0}
$$

才能：

```text
V(empty);
```

#### 33.3 本题的考点迁移

这种模型可以直接迁移到：

- 多订阅者消息广播；
- 一份数据必须被全部线程读取；
- 所有子任务完成后才能回收缓冲区；
- 引用计数式资源管理。

核心是“最后一个完成者释放资源”。

这与读者—写者问题中的“最后一个读者释放写者锁”有相似思想。

## 第六部分：死锁

### 三十四、什么是死锁？

死锁是指多个进程因争夺资源形成相互等待，导致相关进程都无法继续推进。

例如：

```text
P1持有R1，等待R2

P2持有R2，等待R1
```

等待关系：

```text
P1 ──等待──► P2
▲            │
│            │
└──等待──────┘
```

如果没有外部机制打破这种等待关系，就会产生死锁。

### 三十五、死锁的四个必要条件

这是绝对必须掌握的基础。

#### 35.1 互斥条件

某些资源只能被一个进程独占。

例如：

一台打印机不能同时执行两个相互冲突的打印操作。

#### 35.2 占有并等待条件

进程已经占有一部分资源，同时继续申请其他资源。

例如：

```text
P1已拿到R1
仍然等待R2
```

#### 35.3 非抢占条件

已分配资源不能被系统随意强制收回。

注意：

CPU 可以抢占，不代表打印机、锁等资源也能够安全抢占。

#### 35.4 循环等待条件

进程之间形成封闭等待链：

$$
P_1\rightarrow P_2 \rightarrow\cdots\rightarrow P_n \rightarrow P_1
$$

四个必要条件必须同时具备，才可能形成经典资源死锁。

但仅仅观察到部分必要条件成立，不能直接判断系统已经死锁。

### 三十六、死锁、饥饿和忙等

| 概念 | 本质              | 举例              |
| -- | --------------- | --------------- |
| 死锁 | 多个执行主体相互等待，无法继续 | P1 等 P2，P2 等 P1 |
| 饥饿 | 某个执行主体长期得不到机会   | 低优先级进程一直被延后     |
| 忙等 | 不断检查某个条件        | `while(lock);`  |
| 阻塞 | 暂时放弃执行，等待事件     | 等待 I/O 完成       |

尤其注意：

饥饿不需要形成循环等待。

如果高优先级任务不断到来，使低优先级任务一直无法运行，这是饥饿，不一定是死锁。

### 三十七、处理死锁的三类主要策略

| 策略      | 思想          | 特征   |
| ------- | ----------- | ---- |
| 死锁预防    | 破坏必要条件      | 事先限制 |
| 死锁避免    | 保证资源分配后仍安全  | 动态检查 |
| 死锁检测与解除 | 允许发生，之后检测恢复 | 事后处理 |

#### 37.1 死锁预防

方法一：

破坏占有并等待，例如要求一次性申请所有资源。

方法二：

破坏非抢占，例如允许回收某些能够安全抢占的资源。

方法三：

破坏循环等待，例如给资源统一编号。

假设：

$$
R_1<R_2<R_3
$$

所有进程都必须按照编号递增顺序申请。

这样可以避免资源申请关系形成闭合环。

#### 37.2 死锁避免

主要代表：

银行家算法。

特点：

不是直接禁止四个必要条件。

而是每次准备分配资源时，判断分配后是否仍处于安全状态。

#### 37.3 检测与解除

允许资源按正常请求分配。

如果发现死锁，再采取：

- 撤销部分进程；
- 资源抢占；
- 回滚到检查点。

## 第七部分：银行家算法彻底讲解

### 三十八、银行家算法为什么重要？

它是本章最有代表性的资源矩阵计算题。

其核心思想是：

不能只看当前资源够不够，还要保证资源分配后，所有进程仍有可能顺利完成。

#### 38.1 四个核心数据结构

| 名称         | 含义       |
| ---------- | -------- |
| Available  | 当前可用资源   |
| Max        | 进程最大资源需求 |
| Allocation | 已分配资源    |
| Need       | 尚需资源     |

最重要的公式：

$$
\boxed{Need=Max-Allocation}
$$

#### 38.2 安全性算法

<Steps>
  <Step>

    ### 初始化资源与完成标志

    令 `Work = Available`，所有进程的 `Finish` 初始为 `false`。

  </Step>
  <Step>

    ### 寻找可满足的进程

    选择尚未完成且各类资源需求均满足 `Need[i] ≤ Work` 的进程。

  </Step>
  <Step>

    ### 假设执行完成并释放占有资源

    更新 `Work = Work + Allocation[i]`，并将该进程标为完成；继续寻找下一进程。

  </Step>
  <Step>

    ### 判定安全性

    若所有进程均能依次完成，则存在安全序列；否则当前状态不安全。

  </Step>
</Steps>

初始化：

$$
Work=Available
$$

然后寻找某个未完成进程 $P_i$，满足：

$$
Need_i\le Work
$$

这里的向量比较是：

每一种资源的需求都不能超过对应的可用数量。

找到后，假设它获得所需资源、执行完成并释放资源。

更新：

$$
\boxed{Work=Work+Allocation_i}
$$

反复执行。

如果所有进程都能依次完成，则系统安全。

#### 38.3 为什么加 Allocation，而不是 Need？

假设进程已经占有：

$$
Allocation_i
$$

还需要：

$$
Need_i
$$

才能完成。

先分配给它：

$$
Work-Need_i
$$

完成后释放：

$$
Allocation_i+Need_i
$$

最终：

$$
\begin{aligned} Work' &=Work-Need_i\\ &\quad+Allocation_i+Need_i\\ &=Work+Allocation_i \end{aligned}
$$

所以：

$$
\boxed{Work'=Work+Allocation_i}
$$

这是银行家算法最容易算错的地方之一。

### 三十九、真题：2020 年银行家算法

题目：

系统拥有两类资源 A、B，各 6 个。

当前情况：

| 进程 | 已分配 A | 已分配 B | 最大需求 A | 最大需求 B |
| -- | ----- | ----- | ------ | ------ |
| P1 | 2     | 3     | 4      | 4      |
| P2 | 2     | 1     | 3      | 1      |
| P3 | 1     | 2     | 3      | 4      |

求安全状态及安全序列。

#### 第一步：计算 Available

A 类已分配：

$$
2+2+1=5
$$

剩余：

$$
6-5=1
$$

B 类已分配：

$$
3+1+2=6
$$

剩余：

$$
6-6=0
$$

所以：

$$
\boxed{Available=(1,0)}
$$

#### 第二步：计算 Need

P1：

$$
Need_1=(4,4)-(2,3)=(2,1)
$$

P2：

$$
Need_2=(3,1)-(2,1)=(1,0)
$$

P3：

$$
Need_3=(3,4)-(1,2)=(2,2)
$$

#### 第三步：寻找第一个可以完成的进程

初始：

$$
Work=(1,0)
$$

比较：

P1：

$$
(2,1)\nleq(1,0)
$$

不能完成。

P2：

$$
(1,0)\le(1,0)
$$

可以完成。

P3：

$$
(2,2)\nleq(1,0)
$$

不能完成。

因此首先选择 P2。

#### 第四步：释放 P2 的资源

$$
Work=(1,0)+(2,1)
$$

得到：

$$
\boxed{Work=(3,1)}
$$

此时：

$$
Need_1=(2,1)\le(3,1)
$$

所以 P1 可以完成。

#### 第五步：释放 P1 的资源

$$
Work=(3,1)+(2,3)
$$

得到：

$$
\boxed{Work=(5,4)}
$$

P3 需要：

$$
Need_3=(2,2)
$$

满足：

$$
(2,2)\le(5,4)
$$

所以 P3 可以完成。

最终得到：

$$
\boxed{ P2\rightarrow P1\rightarrow P3 }
$$

系统安全。

#### 考场标准表格

| 步骤 | 进程 | 执行前 Work | Need  | Allocation | 执行后 Work |
| -- | -- | -------- | ----- | ---------- | -------- |
| 1  | P2 | (1,0)    | (1,0) | (2,1)      | (3,1)    |
| 2  | P1 | (3,1)    | (2,1) | (2,3)      | (5,4)    |
| 3  | P3 | (5,4)    | (2,2) | (1,2)      | (6,6)    |

建议以后所有银行家算法题都画这种表格。

### 四十、银行家算法中的资源请求

假设进程 $P_i$ 请求：

$$
Request_i
$$

必须依次执行以下检查。

#### 40.1 第一关：是否超过最大剩余需求？

$$
\boxed{Request_i\le Need_i}
$$

超过则请求不合法。

#### 40.2 第二关：当前资源是否足够？

$$
\boxed{Request_i\le Available}
$$

如果不满足，则不能立即分配。

#### 40.3 第三关：试分配

$$
Available'=Available-Request_i
$$

$$
Allocation_i'=Allocation_i+Request_i
$$

$$
Need_i'=Need_i-Request_i
$$

#### 40.4 第四关：安全性检查

在试分配后的状态下，运行安全性算法。

如果安全，则正式分配。

如果不安全，则撤销试分配。

#### 40.5 最重要的陷阱

$$
Request_i\le Available
$$

只能说明：

当前能够拿出这些资源。

不能说明：

拿出去以后系统仍然安全。

因此：

$$
\boxed{\text{资源足够}\neq\text{分配安全}}
$$

### 四十一、真题：2022 年安全序列计数

这类题比普通银行家算法更容易出错。

题目给出：

$$
Available=(1,3,2)
$$

| 进程 | Allocation | Need    |
| -- | ---------- | ------- |
| P0 | (2,0,1)    | (0,2,1) |
| P1 | (0,2,0)    | (1,2,3) |
| P2 | (1,0,1)    | (0,1,3) |

求安全序列个数。

#### 第一步：判断谁能第一个执行

P0：

$$
(0,2,1)\le(1,3,2)
$$

可以。

P1：

$$
(1,2,3)\nleq(1,3,2)
$$

不可以。

P2：

$$
(0,1,3)\nleq(1,3,2)
$$

不可以。

因此第一位只能是 P0。

#### 第二步：P0 完成

$$
Work=(1,3,2)+(2,0,1)
$$

得到：

$$
Work=(3,3,3)
$$

此时 P1 和 P2 都可以完成。

形成两个分支：

```text
       P0
      /  \
     P1   P2
     |     |
     P2    P1
```

所以安全序列共有：

$$
\boxed{2\text{ 条}}
$$

分别为：

$$
P0\rightarrow P1\rightarrow P2
$$

$$
P0\rightarrow P2\rightarrow P1
$$

#### 安全序列数量题的技巧

不能仅找到一条安全序列就结束。

必须在每一步检查：

当前是否有多个可完成进程。

只要出现多个选择，就需要考虑对应的分支。

### 四十二、安全状态、不安全状态和死锁

三者的关系必须彻底弄清楚。

#### 42.1 安全状态

至少存在一条安全序列。

说明系统可以通过某种资源满足顺序，让所有进程完成。

#### 42.2 不安全状态

不存在安全序列。

表示系统已经无法保证所有进程都能完成。

但不表示当前一定发生死锁。

#### 42.3 死锁状态

某些进程已经形成无法自行解除的等待关系。

在经典资源模型下：

$$
\boxed{\text{死锁状态}\Rightarrow\text{不安全状态}}
$$

但反过来不成立：

$$
\boxed{\text{不安全状态}\nRightarrow\text{已经死锁}}
$$

此外：

安全状态可以有多条安全序列。

不要求只有一条。

#### 42.4 真题：2018 年安全性判断

系统共有 4 个同类资源。

| 进程 | 最大需求 | 已分配 |
| -- | ---- | --- |
| P1 | 4    | 2   |
| P2 | 3    | 1   |
| P3 | 1    | 0   |

当前可用：

$$
Available=4-(2+1)=1
$$

尚需：

$$
Need=(2,2,1)
$$

首先只有 P3 能完成。

但是 P3 当前占有资源为 0。

所以它完成之后：

$$
Work'=1+0=1
$$

仍然不能满足 P1、P2。

因此系统处于：

$$
\boxed{\text{不安全状态}}
$$

这道题最重要的陷阱：

<Callout type="warn" title="银行家算法：释放的是 Allocation">

某个进程能够完成，不代表它一定能够释放足够的新资源。

</Callout>

## 第八部分：死锁资源数量计算

### 四十三、保证不发生死锁的最小资源数

假设：

- 有 $n$ 个进程；
- 每个进程最多需要 $w$ 个同类独占资源；
- 资源可以逐个申请；
- 进程最终能够完成并归还资源。

最坏情况下，每个进程已经占有：

$$
w-1
$$

个资源。

但每个进程都还差一个资源才能完成。

此时所有进程总共占有：

$$
n(w-1)
$$

个资源。

如果额外还有一个资源，就可以满足至少一个进程的最后需求，使它完成并释放资源。

因此经典充分保证条件为：

$$
\boxed{ m_{\min}=n(w-1)+1 }
$$

这里 $m_{\min}$ 表示在该经典模型下，为保证不因这类同类资源竞争而死锁所需的最小资源数。

### 四十四、真题：2009 年打印机问题

题目：

系统有 8 台打印机。

每个进程最多需要 3 台。

问至少多少个进程竞争时，可能发生死锁？

#### 44.1 分析最坏情况

每个进程先占有 2 台。

然后每个进程都继续请求第 3 台。

如果有 4 个进程：

$$
4\times2=8
$$

8 台打印机全部被占用。

每个进程还需要 1 台。

因此可能发生：

```text
P1：占有2台，等待1台
P2：占有2台，等待1台
P3：占有2台，等待1台
P4：占有2台，等待1台
```

没有任何空闲资源。

所以：

$$
\boxed{K_{\min}=4}
$$

#### 44.2 为什么 3 个进程不行？

三个进程各占 2 台：

$$
3\times2=6
$$

还剩：

$$
8-6=2
$$

可以给某个进程再分配一台，使它完成。

完成后释放资源，其他进程便有机会继续。

因此 3 个进程不足以构造这类死锁。

### 四十五、真题：2014 年设备数量

三个进程对某类设备的最大需求分别为：

$$
3,\quad4,\quad5
$$

问保证不发生死锁，设备数量至少为多少？

最大需求不同时使用推广公式：

$$
\boxed{ m_{\min}=\sum_{i=1}^{n}(r_i-1)+1 }
$$

代入：

$$
m_{\min} =(3-1)+(4-1)+(5-1)+1
$$

$$
=2+3+4+1
$$

得到：

$$
\boxed{m_{\min}=10}
$$

为什么不是 12？

因为不需要让三个进程同时取得最大需求资源。

只需要保证系统能让至少一个进程完成并释放资源，使其他进程继续推进。

### 四十六、真题：2021 年资源数量

有 $n$ 个进程。

每个进程需要 2 个同类资源。

问至少需要多少个资源，才能保证不发生死锁？

直接代入：

$$
m_{\min}=n(2-1)+1
$$

所以：

$$
\boxed{m_{\min}=n+1}
$$

这类题通常计算很短，但必须理解公式适用条件。

## 第九部分：死锁检测与资源分配图

### 四十七、资源分配图

资源分配图主要包含：

- 进程节点；
- 资源节点；
- 请求边；
- 分配边。

请求边：

$$
P_i\rightarrow R_j
$$

表示进程正在请求资源。

分配边：

$$
R_j\rightarrow P_i
$$

表示资源已经分配给进程。

#### 47.1 单实例资源

如果每类资源只有一个实例，在经典资源分配图模型中：

$$
\boxed{\text{有环}\Longleftrightarrow\text{死锁}}
$$

#### 47.2 多实例资源

如果一类资源有多个实例：

资源分配图存在环，不一定已经死锁。

因为可能仍有其他空闲资源实例，使某个进程完成并释放资源，从而打破等待关系。

因此需要进一步执行死锁检测算法。

### 四十八、死锁检测算法与银行家算法的区别

这两种算法非常相似。

但输入数据的语义不同。

| 项目                | 银行家算法             | 死锁检测              |
| ----------------- | ----------------- | ----------------- |
| 目标                | 避免进入不安全状态         | 判断是否已经死锁          |
| 主要需求量             | Need              | Request           |
| Need / Request 含义 | 最大剩余需求            | 当前实际请求            |
| 是否需要最大需求信息        | 通常需要              | 通常不需要             |
| 资源更新              | Work + Allocation | Work + Allocation |

银行家算法：

$$
Need=Max-Allocation
$$

寻找：

$$
Need_i\le Work
$$

死锁检测算法：

寻找当前尚未完成、且满足：

$$
Request_i\le Work
$$

的进程。

最容易出现的错误：

把“当前请求量”和“未来最大剩余需求”混为一谈。

### 五十一、进程与线程

| 错误理解             | 正确理解            |
| ---------------- | --------------- |
| 程序就是进程           | 程序静态，进程动态       |
| PCB 只保存状态        | PCB 还保存资源和运行现场  |
| 线程是资源分配基本单位      | 进程是资源分配基本单位     |
| 同一进程的线程共享寄存器     | 每个线程独立保存寄存器现场   |
| 同一进程线程完全隔离       | 它们共享虚拟地址空间      |
| fork 之后一定复制所有物理页 | 现代系统通常采用写时复制    |
| exec 创建新进程       | exec 替换当前进程程序映像 |
| 阻塞等于挂起           | 两者描述不同方面        |

### 五十二、进程状态和调度

| 错误理解          | 正确理解          |
| ------------- | ------------- |
| I/O 完成直接进入运行态 | 通常先进入就绪态      |
| 时间片耗尽进入阻塞态    | 进入就绪态         |
| 被抢占进入阻塞态      | 进入就绪态         |
| P 操作一定阻塞      | 许可不足时才可能阻塞    |
| 新进程创建后立即运行    | 通常先进入就绪态      |
| SJF 一定抢占      | 经典 SJF 非抢占    |
| SRTF 比较原始运行时间 | 比较剩余时间        |
| RR 时间片越小越好    | 太小会增加切换开销     |
| 时钟中断必然切换进程    | 不一定           |
| 响应时间就是等待时间    | 响应只统计首次运行前的等待 |

### 五十三、同步与互斥

| 错误理解                | 正确理解          |
| ------------------- | ------------- |
| 共享变量一定禁止所有并发读取      | 多个只读访问通常可以并发  |
| 同步和互斥完全相同           | 两者表达不同约束      |
| P/V 代码顺序随便写         | 顺序可能决定是否死锁    |
| V 操作一定唤醒进程          | 无等待者时可以只是增加许可 |
| P 操作一定阻塞            | 许可充足时可以直接通过   |
| 普通交换函数等价于原子 Swap    | 并发原子性不同       |
| 条件变量 signal 会永久保存通知 | 通常不会积累通知      |
| CAS 一定保证公平          | CAS 不保证公平调度   |

### 五十四、死锁

| 错误理解              | 正确理解           |
| ----------------- | -------------- |
| 有等待环就一定死锁         | 多实例资源需进一步判断    |
| 不安全状态就是死锁         | 不安全不一定已经死锁     |
| 银行家算法用于死锁预防       | 属于死锁避免         |
| Available 足够就可以分配 | 还需检查分配后是否安全    |
| Work 更新加 Need     | 更新加 Allocation |
| 安全序列只有一条          | 可以有多条          |
| Need 就是当前 Request | 二者语义不同         |
| 抢占 CPU 能解决资源死锁    | CPU 抢占不等于资源抢占  |

#### 第四轮：银行家算法和死锁计算

要求看到资源矩阵就能立即执行：

$$
Need=Max-Allocation
$$

$$
Work=Available
$$

寻找：

$$
Need_i\le Work
$$

然后：

$$
Work'=Work+Allocation_i
$$

$$
\boxed{m_{\min}=n(w-1)+1}
$$

以及不同最大需求时：

$$
\boxed{ m_{\min}=\sum_{i=1}^{n}(r_i-1)+1 }
$$

### 本章最终结论

操作系统第 2 章的知识虽然多，但可以统一成三种分析工具。

第一种：时间轴。

用于解决进程调度、CPU 与 I/O 并行、时钟中断、上下文切换和周转时间计算。

第二种：P/V 依赖关系。

用于解决同步互斥、资源容量、生产者—消费者、读者—写者以及各种复杂流水线。

第三种：资源向量。

用于解决安全序列、银行家算法、死锁避免和资源数量计算。

真正掌握这三种分析工具之后，题目无论把背景改成银行、博物馆、工厂、餐厅、植树、广播还是猴子过绳，都能够还原为熟悉的操作系统模型。

本章最值得优先投入时间的四个专题是：P/V 综合设计、进程调度计算、银行家算法、死锁条件与资源计算。 进程和线程的概念是这些题目的基础，不能跳过；但综合题能力的提升，关键在于能够自己画出时间轴、写出信号量约束、推演资源分配，而不是只记最终答案。
