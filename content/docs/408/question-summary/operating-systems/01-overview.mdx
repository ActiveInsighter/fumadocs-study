## 二、操作系统的基本概念与功能

### 2.1 什么是操作系统？

标准定义：

操作系统（Operating System，OS）是控制和管理计算机软硬件资源、合理组织计算机工作，并为用户及其他软件提供接口和运行环境的系统软件。

可以从三个角度理解。

#### 第一：操作系统是资源管理者

假设一台计算机有一个 CPU，运行三个程序：

```text
浏览器 ────┐
           │
播放器 ────┼── 操作系统 ── CPU
           │
编辑器 ────┘
```

三个程序都需要 CPU，但 CPU 在经典单核模型下，同一时刻只能执行一个指令流。

操作系统需要决定：

- 谁先运行？
- 每个程序运行多久？
- 谁需要等待？
- 哪些资源可以共享？
- 如何阻止程序相互破坏？

这就是资源管理。

#### 第二：操作系统是硬件抽象层

应用程序读取文件时，可能只需要：

```text
read(fd, buf, 100);
```

但真实硬件操作涉及：

```text
查找文件
   ↓
检查权限
   ↓
定位文件数据
   ↓
操作设备驱动
   ↓
发出I/O请求
   ↓
等待设备完成
   ↓
通过内核缓冲区传递数据
```

操作系统将复杂的设备操作抽象为简单的文件读写接口。

类似地：

| 真实硬件资源    | 操作系统提供的抽象    |
| --------- | ------------ |
| CPU       | 进程、线程        |
| 物理内存      | 虚拟地址空间       |
| 磁盘扇区      | 文件、目录        |
| 物理 I/O 设备 | 逻辑设备         |
| 网络硬件      | Socket 等网络接口 |

#### 第三：操作系统是服务提供者

应用程序需要创建进程、访问文件、使用设备。

但这些行为涉及受保护资源。

所以操作系统提供统一的服务入口：

系统调用。

这里的“统一”是指某一操作系统向应用提供规定的受控接口，并不是所有不同操作系统拥有完全相同的系统调用集合。

### 2.2 操作系统的四大管理功能

| 功能    | 管理对象   | 主要工作            |
| ----- | ------ | --------------- |
| 处理机管理 | CPU    | 进程管理、调度、同步互斥    |
| 存储器管理 | 内存     | 分配回收、地址转换、保护    |
| 文件管理  | 外存文件   | 文件读写、目录、共享与保护   |
| 设备管理  | I/O 设备 | 驱动、分配、缓冲、I/O 控制 |

要记住：

<Callout type="warn" title="管理功能与基本特征是两组不同概念">

四大管理功能不等于四大基本特征。

</Callout>

四大管理功能回答“管理什么”。

四大基本特征回答“操作系统表现出什么性质”。

### 2.3 操作系统提供哪些接口？

主要分为两类。

| 接口   | 面向对象 | 例子              |
| ---- | ---- | --------------- |
| 命令接口 | 用户   | Shell、命令行、批处理命令 |
| 程序接口 | 应用程序 | 系统调用            |

命令接口又可以区分为联机命令接口和脱机命令接口。

联机命令接口强调用户交互，例如在终端中输入 `ls`、`cd`。

脱机命令接口强调事先提交作业命令，之后由系统批量执行。

GUI 通常属于交互式用户接口，而不是脱机接口。

## 三、操作系统的四大基本特征

必须背熟：

并发、共享、虚拟、异步。

其中，传统教材特别强调并发和共享是两个最基本的特征。

### 3.1 并发与并行

这是第一章最经典的考点之一。

#### 并发 Concurrency

多个事件在同一时间间隔内发生或推进。

例如单核 CPU：

```text
时间 ─────────────────────────→

CPU：
│  A  │  B  │  C  │  A  │  B  │

A、B、C交替执行
```

虽然 CPU 同一时刻只执行一个进程，但在较长时间范围内，多个进程都取得了进展。

这就是并发。

#### 并行 Parallelism

多个事件在同一时刻真正同时发生。

例如：

```text
时间 ─────────────────────→

CPU核心1：AAAAAAAAAAAAAAAA
CPU核心2：BBBBBBBBBBBBBBBB
```

两个核心同时执行不同任务。

这就是并行。

#### 必考对比

| 比较     | 并发     | 并行            |
| ------ | ------ | ------------- |
| 时间含义   | 同一时间间隔 | 同一时刻          |
| 单核 CPU | 可以     | 通常不能执行两个独立指令流 |
| 多核 CPU | 可以     | 可以            |
| 核心机制   | 时间复用   | 硬件同时执行        |

特别注意：单处理机系统也可以发生真正的硬件并行。

为什么？

因为 CPU 不一定需要亲自完成所有 I/O 工作。

例如：

```text
CPU：     执行进程A的计算

磁盘：    进行数据读取

网卡：    接收网络数据
```

这些硬件部件可以同时工作。

#### 真题精讲：2009 年

题目问：单处理机系统中，哪些能够并行？

I. 进程与进程\
II. 处理机与设备\
III. 处理机与通道\
IV. 设备与设备

答案：D，II、III、IV。

分析：

- I 错误。经典单处理机模型中，同一时刻只能运行一个进程的 CPU 指令流。
- II 正确。CPU 与具有独立控制能力的设备可以并行。
- III 正确。I/O 通道可以独立执行有关操作，与 CPU 并行。
- IV 正确。不同设备可以并行工作。

这道题有一个重要的判断方法：

先确定题目讨论的是 CPU 指令流，还是多个相互独立的硬件部件。

不要看到“单处理机”就认为整个计算机内部完全不能并行工作。

#### 真题精讲：2018 年

多任务操作系统具有以下特点：

I. 具有并发和并行的特点\
II. 需要保护共享资源\
III. 必须运行在多 CPU 系统上

答案：C，I、II。

这里的 I 要理解为：多任务操作系统支持并发，在具备相应硬件时也能支持并行，而不是说每台单核机器上的多任务都必然并行。

II 正确，因为共享资源存在竞争。

III 错误，因为单核 CPU 也可以通过时间片实现多任务并发。

### 3.2 共享

共享是指系统资源可以由多个并发进程共同使用。

主要有两种形式。

#### 互斥共享

某一时刻只能允许一个进程使用某种资源。

例如独占式打印机：

```text
进程A ── 正在使用打印机
进程B ── 等待
进程C ── 等待
```

同一时刻只允许一个进程占有。

#### 同时共享

允许多个进程在同一时间段共同使用资源。

例如多个进程读取同一个只读文件。

注意：

这里的“同时”可以是宏观意义上的同时，不要求每个瞬间都发生真正并行访问。

#### 并发与共享是什么关系？

传统教材说：

并发与共享互为存在条件。

可以从系统设计角度理解：

```text
多个程序并发
      ↓
需要共同使用资源
      ↓
产生资源共享和竞争
      ↓
操作系统需要同步、互斥
      ↓
保证并发运行的正确性
```

这是一种教材层面的相互联系，不是说任何两个独立计算任务必须共享同一资源才能并发。

### 3.3 虚拟

虚拟的核心是：

将一个物理实体映射或抽象为多个逻辑上的对应物。

例如：

一台计算机只有一个 CPU，却能运行多个进程。

每个进程似乎都有自己的处理器。

实际上，操作系统通过 CPU 调度和时间片轮转，使多个进程轮流占用物理 CPU。

#### 时分复用与空分复用

| 方式   | 含义              | 例子        |
| ---- | --------------- | --------- |
| 时分复用 | 不同任务在不同时间使用资源   | CPU 时间片轮转 |
| 空分复用 | 不同任务使用资源的不同空间部分 | 内存分区、磁盘分区 |

注意：

内存分区可以体现空间复用，但不等于现代虚拟内存的全部机制。

典型虚拟化技术包括：

- CPU 虚拟化：时间片轮转。
- 存储器虚拟化：虚拟地址空间。
- 设备虚拟化：SPOOLing。
- 计算机虚拟化：虚拟机。

#### 模拟题

下列说法正确的是：

I. 时间片轮转体现 CPU 资源虚拟化。\
II. 内存分区体现空间复用。\
III. SPOOLing 是一种设备虚拟技术。\
IV. 虚拟机管理程序一定始终运行在内核态。

答案：I、II、III。

IV 错误，因为 Hypervisor 存在不同实现方式，宿主型虚拟化软件可以包含用户态组件。

### 3.4 异步

异步是指：

多道程序环境中的各个进程以不可预知的速度向前推进。

例如：

```text
进程A：运行 → 等待I/O → 就绪 → 运行

进程B：运行 → 时间片到 → 就绪

进程C：等待网络 → 被唤醒 → 运行
```

调度顺序、I/O 完成时间、资源竞争情况都会影响进程推进速度。

但是：

<Callout type="warn" title="异步不代表结果随机">

异步不等于程序执行结果必然随机。

</Callout>

例如两个进程分别计算：

$$
a=1+2
$$

$$
b=3+4
$$

即使执行次序不同，只要没有影响结果的竞态问题，最终仍可以得到：

$$
a=3,\qquad b=7
$$

真正可能出现结果不确定的情况，通常与共享状态、竞态和错误的同步机制有关。

#### 四大特征速记

| 特征 | 关键问题          | 记忆词   |
| -- | ------------- | ----- |
| 并发 | 多个任务如何共同推进    | 同一时间段 |
| 共享 | 如何共同使用资源      | 互斥、同时 |
| 虚拟 | 如何抽象硬件资源      | 逻辑对应物 |
| 异步 | 进程为何不能按固定速度推进 | 不可预知  |

## 四、操作系统的发展历程

这一节的考点不是单纯记时间线，而是理解：

为什么会出现下一种操作系统？它解决了上一种系统的什么问题？

### 4.1 发展主线

```text
手工操作
   ↓
脱机输入输出
   ↓
单道批处理
   ↓
多道批处理
   ├────────→ 分时系统
   │
   └────────→ 实时系统
```

其中，分时与实时更适合理解为不同需求推动的系统发展方向，不是所有系统都必须按这条顺序逐代演进。

### 4.2 手工操作阶段

早期没有成熟的操作系统。

用户需要手动完成程序装入、输入、执行和输出。

最大问题：

人机速度矛盾。

人的操作速度远慢于处理器，CPU 经常处于空闲状态。

### 4.3 脱机输入输出

通过外围机预先准备输入数据、处理输出结果。

这样可以减少主机直接等待慢速人工输入输出的时间。

注意：

脱机 I/O 与后来的 SPOOLing 在思想上有联系，但不能完全等同。

### 4.4 单道批处理系统

多个作业组成一个批次，自动依次执行。

主要优点是减少人工干预。

主要缺点是：

一个作业等待 I/O 时，CPU 往往只能空闲。

#### 计算例题

假设某作业执行顺序为：

```text
CPU计算2ms
    ↓
I/O等待6ms
    ↓
CPU计算2ms
```

总时间：

$$
T=2+6+2=10\text{ ms}
$$

CPU 工作时间：

$$
T_{\mathrm{CPU}}=2+2=4\text{ ms}
$$

CPU 利用率：

$$
\begin{aligned}
U_{\mathrm{CPU}} &=\frac{4}{10}\times100% \\ &=40%
\end{aligned}
$$

说明 CPU 有 60% 的时间没有执行有效计算。

### 4.5 多道批处理系统

多道程序技术允许多个程序同时驻留内存。

当一个程序等待 I/O 时，CPU 可以执行另一个就绪程序。

假设刚才的程序 A 在等待 6 ms I/O 时，程序 B 正好需要进行 6 ms CPU 计算：

```text
时间        0       2       8      10

进程A       CPU ─── I/O ────── CPU

进程B               CPU ──────

CPU执行     A       B           A
```

在忽略调度开销、程序 B 可以立即运行等理想条件下：

$$
U_{\mathrm{CPU}}=\frac{10}{10}=100%
$$

CPU 利用率由原来的 40% 提升到 100%。

真正原因不是单核 CPU 同时执行两个程序。

而是：

用程序 B 的计算时间覆盖程序 A 的 I/O 等待时间。

#### 多道程序的主要特点

| 优点           | 缺点      |
| ------------ | ------- |
| 提高 CPU 利用率   | 调度管理复杂  |
| 提高 I/O 设备利用率 | 系统开销增加  |
| 增加系统吞吐量      | 资源竞争更明显 |
| 支持多个程序并发     | 交互性通常较弱 |

#### 真题：2017 年

与单道程序系统相比，多道程序系统的优点是：

I. CPU 利用率高\
II. 系统开销小\
III. 系统吞吐量大\
IV. I/O 设备利用率高

答案：D，I、III、IV。

II 错误，因为多道程序需要额外的调度、资源管理和保护机制。

### 4.6 多道程序数量是不是越多越好？

不是。

#### 真题：2022 年

题目要求选择关于多道程序系统的错误表述。

其中 D 选项为：

“进程数越多，CPU 利用率越高。”

答案：D。

原因是进程数量增加具有收益，也具有成本。

适度增加进程：

- 减少 CPU 空闲。
- 增加 I/O 与计算重叠。
- 提高资源利用率。

进程数量过大：

- 上下文切换频繁。
- 内存不足。
- 资源争用增加。
- 可能出现频繁缺页和抖动。

因此，真实系统的 CPU 有效利用率不保证始终随进程数增加而增加。

#### 理想化计算模型

假设每个进程独立地以概率 (p) 等待 I/O，系统中有 (n) 个进程。

所有进程都等待 I/O 的概率：

$$
P_{\mathrm{idle}}=p^n
$$

因此，在忽略调度和资源竞争开销的模型中：

$$
\boxed{U_{\mathrm{CPU}}\approx1-p^n}
$$

例如：

$$
p=0.8,\qquad n=3
$$

则：

$$
\begin{aligned}
U_{\mathrm{CPU}}\approx1-0.8^3 &=0.488=48.8%
\end{aligned}
$$

这个公式用于理解多道程序的潜在收益。

不能拿它证明真实系统中“进程越多越好”。

### 4.7 分时操作系统

分时系统把 CPU 时间划分为时间片，使多个用户或任务轮流使用 CPU。

```text
时间 ──────────────────→

P1 → P2 → P3 → P1 → P2 → P3
```

四个典型特征：

1. 多路性。
2. 独立性。
3. 及时性。
4. 交互性。

核心目标：

改善人机交互，缩短响应时间。

分时强调及时响应，不意味着每个任务都必须满足严格截止时间。

### 4.8 实时操作系统

实时系统最关心的不是平均执行速度，而是：

能否在规定时间约束内完成任务。

#### 硬实时系统

必须满足关键截止时间。

例如：

- 飞行控制。
- 工业安全控制。
- 某些医疗设备控制。

#### 软实时系统

偶尔未满足截止时间，通常造成服务质量下降，而不一定导致整个系统失效。

例如部分多媒体和实时通信业务。

#### 三种系统对比

| 系统    | 首要目标      | 关键词  |
| ----- | --------- | ---- |
| 多道批处理 | 提高吞吐量和利用率 | 资源效率 |
| 分时系统  | 改善交互响应    | 时间片  |
| 实时系统  | 满足时间约束    | 截止时间 |

#### 真题：2016 年

关于批处理系统：

I. 允许多个用户直接交互。\
II. 分为单道和多道批处理。\
III. 中断技术可以支持 CPU 和 I/O 设备并行工作。

答案：A，II、III。

I 错误，因为典型批处理系统不强调作业执行期间的直接人机交互。

II 正确。

III 正确，因为 I/O 设备能够独立工作，中断机制可以在设备完成操作后通知 CPU。

注意：“中断支持 CPU 与 I/O 并行”是经典教材语境中的描述；并行工作的硬件基础还包括设备控制器等独立硬件，并不能把中断说成一切硬件并行的唯一必要条件。

## 五、CPU 的用户态、内核态与特权指令

这一节是操作系统第一章最重要的部分之一。

### 5.1 为什么需要两种运行模式？

假设普通程序可以直接执行：

```text
disable_interrupts();
```

关闭所有可屏蔽中断后一直占用 CPU。

操作系统可能无法通过时钟中断正常重新取得 CPU 控制权。

再假设普通程序可以随意修改页表。

它就可能访问其他进程甚至内核的受保护内存。

所以：

操作系统必须防止普通程序直接控制关键系统资源。

CPU 硬件为此提供不同的特权级。

### 5.2 用户态与内核态

| 属性      | 用户态        | 内核态          |
| ------- | ---------- | ------------ |
| 权限      | 较低         | 较高           |
| 普通指令    | 可以执行       | 可以执行         |
| 特权指令    | 不允许合法执行    | 可以执行         |
| 内核受保护资源 | 不可任意访问     | 按内核权限访问      |
| 典型代码    | 应用程序、Shell | 中断处理、调度、核心管理 |

在经典 x86 特权环模型中：

- Ring 0：通常运行内核。
- Ring 3：通常运行普通应用程序。

CPU 通过特权级相关硬件状态区分执行权限。传统教材常将这类状态归入 PSW 或等价处理器控制状态。

必须记住：

用户态只能合法执行非特权指令；内核态既可以执行特权指令，也可以执行非特权指令。

#### 真题：2022 年

题目问哪一项 CPU 模式描述正确。

A. 用户态只能执行特权指令\
B. 内核态只能执行特权指令\
C. 用户态只能执行非特权指令\
D. 内核态只能执行非特权指令

答案：C。

关键在于：

内核态具有更高权限，不代表只能执行高权限指令。

### 5.3 什么是特权指令？

特权指令是只能在满足规定特权级条件时正常执行的指令。

经典例子：

| 操作              | 是否通常需要内核权限 |
| --------------- | ---------- |
| 普通加法            | 否          |
| 普通跳转            | 否          |
| 修改通用寄存器         | 否          |
| 访问自身合法内存        | 否          |
| 关闭中断            | 是          |
| 修改页表基址          | 是          |
| 设置系统级定时器        | 是          |
| 修改系统控制寄存器       | 是          |
| 执行受保护的设备 I/O 指令 | 是          |
| 修改内存保护状态        | 是          |

一个实用判断方法是：

该操作是否能够直接修改影响系统整体安全、保护或硬件控制的关键状态？

如果可以，通常需要高权限。

但是一定要区分：

- 用户程序请求操作系统修改系统状态。
- 用户程序亲自执行修改系统状态的特权指令。

两者不同。

### 5.4 高频陷阱：Trap 是特权指令吗？

这是非常容易做错的一点。

408 常规语境下，用户程序发起系统调用使用的 Trap/访管指令，不属于只能在内核态执行的特权指令。

为什么？

因为用户程序需要合法请求操作系统服务。

假设执行：

```text
read(fd, buf, 100);
```

用户程序必须有办法请求内核完成文件读取。

典型过程：

```text
用户态运行
    ↓
执行Trap/系统调用入口指令
    ↓
CPU通过受控入口进行权限转换
    ↓
内核态执行服务
    ↓
返回用户态
```

因此：

Trap 指令本身必须允许用户态执行，但它引发的服务处理发生在内核态。

不同体系结构会使用不同的入口机制，例如：

- x86：`syscall` 等。
- ARM：`svc`。
- RISC-V：`ecall`。

这些是具有特殊受控陷入语义的入口指令，不能因此把它们归为“只能在内核态执行”。

#### 真题：2014 年

下列指令不能在用户态执行的是：

A. trap 指令\
B. 跳转指令\
C. 压栈指令\
D. 关中断指令

答案：D。

A 是用户态可发起的受控陷入。

B、C 是普通非特权指令。

D 会影响 CPU 的中断控制，属于特权操作。

#### 真题：2021 年

下列指令只能在内核态执行的是：

A. trap\
B. I/O 指令\
C. 数据传送指令\
D. 设置断点指令

答案：B。

这里的 I/O 指令指直接控制受保护外设的机器指令。

不要与应用程序通过 `read()`、`write()` 请求 I/O 服务混淆。

### 5.5 操作系统提供的程序一定运行在内核态吗？

不一定。

例如：

- 命令解释程序。
- Shell。
- 图形界面中的应用组件。
- 一些用户态系统服务。

它们都可能运行在用户态。

#### 真题：2011 年

下列程序在用户态执行的是：

A. 命令解释程序\
B. 缺页处理程序\
C. 进程调度程序\
D. 时钟中断处理程序

答案：A。

B、C、D 都涉及操作系统内核核心机制。

A 虽然用于操作系统的人机交互，但通常只是一个普通用户进程。

考试判断的依据是权限要求，而不是程序名称。

### 5.6 非特权指令一定不会导致陷入吗？

不是。

这是理解 2015 年真题的关键。

假设用户程序执行：

```text
MOV R0, [addr]
```

这是普通访存指令。

但如果目标地址发生以下情况：

- 不在当前进程合法地址范围内。
- 页面不在内存中。
- 访问权限不允许。

那么 CPU 仍可能产生异常，转入内核处理。

所以要区分：

某条指令是否为特权指令与执行它时是否可能发生异常。

#### 真题：2015 年

以下哪条指令执行时，不可能因该指令自身的执行语义导致用户态进入内核态？

A. `DIV R0, R1`\
B. `INT n`\
C. `NOT R0`\
D. `MOV R0, addr`

答案：C。

逐项分析：

| 指令  | 可能引起的事件            |
| --- | ------------------ |
| DIV | 除数为零时产生异常          |
| INT | 主动产生软件中断或陷入        |
| NOT | 只对寄存器取反，正常情况下无陷入条件 |
| MOV | 访存可能引起缺页或保护异常      |

这道题讨论的是指令本身可能触发的事件，不考虑恰好在指令执行边界到达的无关外部中断。

最终结论：非特权不等于永远不会异常。

## 六、中断、异常与系统调用：全章最核心的考点

这一部分必须真正理解，因为它不仅是第一章的高频考点，而且会贯穿后面的进程调度、虚拟内存、文件管理和 I/O 管理。

### 6.1 为什么操作系统需要中断？

假设有一个程序：

```text
while (1) {
    compute();
}
```

如果这个程序始终执行普通计算、不主动请求操作系统服务，那么操作系统如何重新取得 CPU 控制权？

现代抢占式操作系统的重要手段之一，就是时钟中断。

CPU 可以在满足中断响应条件时暂停当前执行流，转去执行操作系统的中断处理代码。

中断的重要作用包括：

1. 响应外部设备事件。
2. 支持抢占式调度。
3. 处理 I/O 完成通知。
4. 支持多个程序并发。
5. 减少 CPU 对设备状态的无意义轮询。

### 6.2 中断、异常、系统调用到底有什么区别？

先看最重要的对比表。

| 比较           | 外部中断       | 异常         | 系统调用          |
| ------------ | ---------- | ---------- | ------------- |
| 来源           | CPU 外部事件   | 当前指令执行条件   | 程序主动发起        |
| 典型同步性        | 异步         | 同步         | 同步            |
| 是否主动请求 OS 服务 | 否          | 否          | 是             |
| 典型事件         | 时钟、键盘、磁盘完成 | 除零、缺页、保护错误 | `read`、`fork` |
| 是否可能进入内核态    | 是          | 是          | 是             |
| 是否必然切换进程     | 否          | 否          | 否             |

注意：在一些教材的分类中，系统调用产生的 Trap 也归入广义“异常”或“内中断”。上表为了讲清触发原因，将主动系统调用单独列出。

#### 外部中断：和当前指令通常没有直接关系

例如：

```text
CPU正在执行ADD指令
         ↓
磁盘完成读取
         ↓
磁盘控制器产生中断请求
         ↓
CPU在满足条件时响应
         ↓
执行磁盘中断处理程序
```

磁盘完成读取，与 CPU 正在执行的 `ADD` 指令没有直接因果关系。

所以属于异步事件。

#### 异常：由当前指令引起

例如：

```text
DIV R1, R2
```

如果：

$$
R_2=0
$$

就可能触发除零异常。

这和当前指令直接相关，因此属于同步异常。

#### 系统调用：程序主动请求操作系统服务

例如：

```text
read(fd, buf, 100);
```

程序主动执行相应系统调用入口，请求内核完成服务。

这与被动发生的除零、非法访存不同。

#### 最实用的分类方法

```text
发生了一个事件
       │
       ▼
事件是否由当前程序主动请求内核服务？
       │
       ├── 是 → 系统调用
       │
       └── 否
            │
            ▼
       是否与当前指令执行条件直接有关？
            │
            ├── 是 → 同步异常
            │
            └── 否 → 通常是外部中断
```

### 6.3 中断从产生到处理，究竟发生了什么？

典型过程：

```text
① 用户程序正在执行
          ↓
② 外部设备产生中断请求
          ↓
③ CPU检查能否响应
          ↓
④ 硬件保存关键返回状态
          ↓
⑤ CPU转入中断处理入口
          ↓
⑥ OS保存必要的软件现场
          ↓
⑦ 执行中断服务程序
          ↓
⑧ 根据需要唤醒进程或进行调度
          ↓
⑨ 恢复相应的执行现场
          ↓
⑩ 中断返回，继续执行程序
```

这里要注意几个容易被题目利用的细节。

第一，中断请求产生不等于 CPU 立即响应。

因为 CPU 可能正在执行指令，或者中断被屏蔽，或者存在优先级条件。

第二，中断处理不一定导致进程切换。

例如处理完键盘输入后，CPU 可以继续运行原来的程序。

第三，中断发生时，不一定已经处于内核态。

这正是 2024 年真题的重点。

### 6.4 真题：2024 年——中断发生时 CPU 在什么模式？

题目要求选择错误的说法。

A. 中断或异常发生时，CPU 处于内核态。\
B. 每个系统调用都有对应的内核服务例程。\
C. 中断处理程序开始执行时，CPU 处于内核态。\
D. 添加采用中断驱动的新设备时，需要注册相应的中断处理例程。

答案：A。

关键是区分两个时间点。

#### 时间点一：中断发生时

```text
用户程序正在用户态运行
            ↓
       中断请求到来
```

此时 CPU 完全可能仍处于用户态。

#### 时间点二：中断处理程序开始执行

```text
中断请求
    ↓
CPU响应并进行受控模式转换
    ↓
内核态执行中断处理程序
```

按照 408 的典型操作系统模型，中断处理程序在内核态执行。

因此：

中断发生时的模式，不等于中断处理程序执行时的模式。

这一点特别容易出“必然、一定、立即”类干扰选项。

### 6.5 中断处理中，哪些步骤由硬件完成？

这是必须背熟的高频考点。

| 操作          | 典型执行者        |
| ----------- | ------------ |
| 检测并响应中断     | CPU 硬件       |
| 保存必要断点 PC   | 硬件机制         |
| 保存关键处理器状态   | 硬件机制         |
| 切换 CPU 特权级  | 硬件机制         |
| 按中断向量确定处理入口 | 硬件机制配合预先设置的表 |
| 保存额外通用寄存器   | 操作系统软件       |
| 执行中断服务程序    | 操作系统软件       |
| 更新内核数据结构    | 操作系统软件       |
| 唤醒等待进程      | 操作系统软件       |
| 判断是否进行调度    | 操作系统软件       |
| 恢复现场并中断返回   | 软件与硬件共同完成    |

不同 CPU 架构保存现场的具体细节可能不同，但 408 的常规判断是：

硬件负责保存关键返回信息和受控进入；软件负责额外现场保护和实际事件处理。

#### 真题：2015 年

处理外部中断时，应当由操作系统保存的是：

A. PC\
B. 通用寄存器\
C. TLB 内容\
D. Cache 内容

答案：B。

为什么？

因为 CPU 响应中断时，需要先由硬件可靠保存必要的返回位置和关键状态。

操作系统的中断入口代码还需要保存可能被处理程序破坏的通用寄存器值。

而普通中断处理不要求整体保存 TLB 或 Cache 的所有内容。

#### 真题：2022 年

系统调用过程包括：

I. 保存断点和 PSW。\
II. 保存通用寄存器。\
III. 执行系统调用服务例程。\
IV. 将 CPU 模式改为内核态。

问：哪些由操作系统软件完成？

答案：B，II、III。

因为 I、IV 属于硬件受控入口机制的职责。

II、III 属于内核软件职责。

#### 考试口诀

> 硬件保断点、切模式；软件保现场、做服务。

### 6.6 为什么中断必须保存 PSW？

PSW 是程序状态字，或教材中对处理器关键状态的一种概括。

它可能包含：

- 条件码。
- 中断相关状态。
- 运行模式相关信息。
- 其他处理器控制状态。

假设中断之前，CPU 正在用户态运行。

处理完中断后，如果不恢复原来的关键处理器状态，就无法正确回到之前的执行环境。

因此中断返回不仅需要知道：

返回哪条指令？

还需要知道：

以什么处理器状态返回？

#### 真题：2012 年

中断处理和普通子程序调用都会保护现场。

中断处理一定需要保存，而普通子程序调用通常不需要保存的是：

A. PC\
B. PSW\
C. 通用数据寄存器\
D. 通用地址寄存器

答案：B。

普通函数调用同样需要保存返回地址，因此不能选 PC。

而中断返回需要恢复处理器的关键状态，通常必须保存 PSW 或等价状态。

### 6.7 中断向量表为什么适合使用数组？

#### 真题：2023 年

中断向量表最适合采用：

A. 数组\
B. 队列\
C. 单向链表\
D. 双向链表

答案：A。

中断向量表的作用是根据中断类型号，快速定位对应的处理程序入口。

例如：

```text
中断类型号
    ↓
vector[编号]
    ↓
中断处理程序入口
```

数组支持基于下标的直接访问。

在常规模型中：

$$
T(n)=O(1)
$$

而链表通常需要逐个结点查找。

这道题是数据结构 + 操作系统 + 计算机组成原理的交叉考点。

## 七、异常的分类与缺页异常

### 7.1 Fault、Trap、Abort

| 类型    | 含义               | 典型例子     | 处理后          |
| ----- | ---------------- | -------- | ------------ |
| Fault | 当前指令执行中检测到故障     | 缺页       | 可恢复时重新执行故障指令 |
| Trap  | 有意触发或在规定执行点报告的陷入 | 系统调用     | 通常从规定后继位置继续  |
| Abort | 严重、难以恢复的异常       | 某些严重硬件错误 | 通常无法正常恢复     |

这套分类是经典教材模型。不同体系结构可能存在具体语义差异。

最重要的是掌握缺页 Fault 与系统调用 Trap 的恢复位置区别。

### 7.2 为什么缺页属于异常？

假设程序执行：

```text
LOAD R1, [0x8000]
```

CPU 需要访问虚拟地址：

```text
0x8000
```

地址转换硬件发现：

- 地址合法。
- 访问权限合法。
- 但是页面尚未驻留内存。

于是产生缺页异常。

```text
执行LOAD
    ↓
MMU地址转换
    ↓
发现页面不在主存
    ↓
缺页异常
    ↓
进入内核态
    ↓
操作系统调入页面
    ↓
更新页表
    ↓
重新执行LOAD
```

因为缺页是由当前 `LOAD` 指令触发的，所以属于同步异常。

它不是来自外部设备完成操作的中断。

### 7.3 缺页、地址越界、权限错误的区别

| 情况            | 可能的处理             |
| ------------- | ----------------- |
| 地址合法，但页面未驻留   | 缺页处理，必要时调页        |
| 地址不属于合法虚拟地址范围 | 地址或保护异常           |
| 页面存在，但访问权限不允许 | 保护异常              |
| 写入写时复制页面      | 特殊保护故障，内核可能建立私有副本 |

最后一项非常重要。

不是所有写入只读映射导致的异常都意味着程序必须终止。

例如写时复制（Copy-on-Write）机制，会利用写保护异常完成页面复制。

因此：

是否能够恢复，要结合异常类型和操作系统的内存管理策略判断。

### 7.4 TLB Miss 等于缺页吗？

不等于。

TLB 是地址转换缓存。

TLB 未命中只是说明：

当前需要的地址转换信息不在 TLB 中。

可能发生：

```text
TLB Miss
    ↓
查找页表
    ↓
发现页表项有效
    ↓
获得物理页框号
    ↓
更新TLB
    ↓
继续访存
```

在具有硬件页表遍历机制的系统中，这一过程不一定需要陷入操作系统。

而缺页意味着目标页面没有按当前映射要求驻留，需要进行相应异常处理。

所以：

TLB 未命中不一定产生缺页异常，更不意味着一定从磁盘读取数据。

### 7.5 三种事件的返回位置

这是综合题中非常容易考的细节。

假设：

```text
地址100：ADD
地址104：LOAD
地址108：SUB
```

#### 情况一：外部中断

如果 CPU 已经执行完 `LOAD`，在下一条指令前响应外部中断。

处理后通常继续执行：

```text
108：SUB
```

#### 情况二：LOAD 发生缺页

假设执行 `LOAD` 时发现页面未驻留。

处理缺页后，应当重新执行：

```text
104：LOAD
```

不能直接跳到 `SUB`。

因为 `LOAD` 原本没有成功完成。

#### 情况三：系统调用

假设：

```text
100：准备参数
104：SYSCALL
108：继续执行
```

系统调用成功完成后，一般从规定的后继位置：

```text
108
```

继续运行。

#### 对比表

| 事件           | 典型恢复位置     |
| ------------ | ---------- |
| 外部中断         | 下一条尚未执行的指令 |
| 可恢复的缺页 Fault | 原故障指令      |
| 系统调用 Trap    | 规定的后继位置    |
| 严重 Abort     | 通常无法正常恢复   |

## 八、系统调用与进程上下文切换

### 8.1 系统调用的完整执行过程

以：

```text
read(fd, buf, 100);
```

为例。

典型流程：

<Steps>

<Step>

    ### 发起请求

    用户程序准备系统调用号与参数，执行系统调用入口指令。

</Step>

<Step>

    ### 进入内核并分派

    处理器保存关键执行状态、切换到内核执行环境；内核按系统调用号分派服务，并检查参数与权限。

</Step>

<Step>

    ### 执行服务并返回

    内核完成请求、设置返回值，恢复相关上下文并返回用户态；若服务阻塞，可能先调度其他进程。

</Step>

</Steps>

#### 真题：2017 年

题目给出四个操作：

I. 返回用户态。\
II. 执行 Trap 指令。\
III. 传递系统调用参数。\
IV. 执行系统调用服务程序。

正确顺序是：

$$
\boxed{\text{III}\rightarrow\text{II}\rightarrow\text{IV}\rightarrow\text{I}}
$$

答案：C。

记忆方式：

传参 → 陷入 → 服务 → 返回。

### 8.2 系统调用与普通函数调用

| 比较项      | 普通函数调用 | 用户态发起系统调用 |
| -------- | ------ | --------- |
| 是否需要进入内核 | 通常不需要  | 需要        |
| 是否改变特权级  | 通常不改变  | 发生受控权限转换  |
| 是否执行内核服务 | 不一定    | 是         |
| 是否可能阻塞   | 可能     | 可能        |
| 是否必然切换进程 | 否      | 否         |

例如：

```c
int a = abs(-10);
```

一般只涉及用户态计算。

而：

```c
int fd = open("data.txt", O_RDONLY);
```

通常需要请求操作系统完成文件打开。

#### 真题：2013 年

哪些操作会导致用户进程从用户态转入内核态？

I. 整数除以零。\
II. 调用 `sin()`。\
III. 执行 `read` 系统调用。

答案：B，I、III。

原因：

- I：触发异常。
- II：普通数学库函数通常可以在用户态计算。
- III：系统调用请求内核服务。

### 8.3 哪些操作需要通过系统调用完成？

典型系统调用包括：

| 功能   | 例子          |
| ---- | ----------- |
| 进程管理 | 创建、终止进程     |
| 文件管理 | 打开、读取、写入文件  |
| 内存管理 | 请求映射内存      |
| 通信   | 建立通信端点、发送接收 |
| 设备服务 | 请求设备读写      |

但是，有些工作虽然由内核执行，却不一定由用户程序通过系统调用直接请求。

#### 真题：2021 年

下列哪项操作通过系统调用完成？

A. 页置换\
B. 进程调度\
C. 创建新进程\
D. 生成随机整数

答案：C。

关键区别：

- 页置换：内存管理内部机制。
- 进程调度：操作系统内部机制。
- 创建新进程：需要向操作系统请求资源与进程管理服务。
- 生成随机整数：可以通过普通用户态算法完成。

必须记住：内核执行的操作，不全都是系统调用。

### 8.4 系统调用、模式切换、进程切换，是一回事吗？

不是。

这是整个第一章最值得彻底理解的问题。

#### 概念一：模式切换

改变 CPU 执行权限。

例如：

```text
用户态
   ↓
系统调用
   ↓
内核态
   ↓
返回
   ↓
用户态
```

整个过程中可以一直是同一个进程。

#### 概念二：进程状态转换

例如：

```text
运行态
   ↓
等待I/O
   ↓
阻塞态
```

状态转换描述进程是否具有继续执行的条件。

#### 概念三：进程上下文切换

例如：

```text
进程A正在运行
      ↓
保存A的上下文
      ↓
选择进程B
      ↓
恢复B的上下文
      ↓
执行B
```

这才是真正的进程切换。

#### 三者对比

| 概念      | 改变了什么？      | 是否必然切换进程？ |
| ------- | ----------- | --------- |
| 模式切换    | CPU 权限模式    | 否         |
| 进程状态转换  | 进程运行条件与状态   | 否         |
| 进程上下文切换 | CPU 当前执行的进程 | 是         |

例如：

```text
getpid();
```

在典型系统调用实现中，程序可能进入内核、获取结果、返回原进程。

发生了模式切换。

但不一定发生进程切换。

### 8.5 真题：2012 年——哪种事件不可能在用户态发生？

A. 系统调用\
B. 外部中断\
C. 进程切换\
D. 缺页

答案：C。

注意题目的语义：

- 用户态可以发起系统调用。
- 用户程序执行期间可能收到外部中断。
- 用户态执行访存指令可能触发缺页。
- 真正的进程上下文切换需要内核参与。

因此选 C。

这个题型的关键是区分：

事件在用户态被触发与事件处理工作在用户态完成。

### 8.6 真题：2023 年——系统调用什么时候返回用户态？

题目问：哪项操作完成时，会使 CPU 从内核态转为用户态？

A. 阻塞进程\
B. 执行 CPU 调度\
C. 唤醒进程\
D. 执行系统调用

答案：D。

原因是系统调用正常完成并返回用户程序时，CPU 会恢复相应的用户态执行环境。

注意：

如果题目问系统调用刚开始时：

```text
用户态 → 内核态
```

如果问系统调用正常完成并返回时：

```text
内核态 → 用户态
```

一定要看清题干中的时间条件。

### 8.7 真题：2019 年——系统调用的本质

题目给出：

I. 系统调用服务程序在内核态执行。\
II. 系统调用避免用户程序直接控制受保护外设。\
III. 不同操作系统提供统一的系统调用接口。\
IV. 系统调用是 OS 内核提供服务的接口。

答案：C，I、II、IV。

III 错误，因为不同操作系统的系统调用集合、编号和 ABI 可以不同。

还要区分两个层次：

系统调用机器指令由处理器指令集体系结构决定。

系统调用接口与调用约定由操作系统及平台 ABI 共同规定。

例如同样使用 x86 架构的 Linux 和 Windows，并不意味着二者拥有完全相同的系统调用 ABI。

## 九、程序的链接、装入、重定位和内存映像

这一部分虽然不像中断机制考查得那么集中，但程序运行链路仍需完整掌握。

### 9.1 一个程序是怎样运行起来的？

典型流程：

```text
源程序
   ↓
编译、汇编
   ↓
目标文件
   ↓
链接
   ↓
可执行文件
   ↓
装入并建立地址空间
   ↓
创建执行环境
   ↓
运行中的进程
```

这里有三个不同概念：

程序： 静态代码与数据。

进程： 程序的一次执行活动。

进程内存映像： 程序运行时建立的代码、数据、堆、栈等地址空间内容。

同一个可执行文件可以对应多个正在运行的进程。

### 9.2 静态链接与动态链接

<Tabs items={['静态链接', '动态链接']} defaultIndex={0}>

<Tab value="静态链接">

链接阶段将需要的静态库代码组合进可执行文件。

```text
main.o + libmath.a
        ↓
      链接器
        ↓
     可执行文件
```

特点：

- 可执行文件通常较大。
- 运行时对对应共享库的依赖较少。
- 不同程序可能重复包含相同库代码。
- 库更新后可能需要重新链接。

</Tab>

<Tab value="动态链接">

动态库独立保存，装入或运行期间完成必要的符号绑定。

例如：

```text
main程序
   ↓
动态链接
   ↓
libc.so
```

特点：

- 可执行文件通常较小。
- 多个进程可以共享只读库代码页。
- 动态库便于统一维护。
- 可能出现库缺失或 ABI 不兼容问题。

</Tab>

</Tabs>

#### 对比

| 比较       | 静态链接      | 动态链接       |
| -------- | --------- | ---------- |
| 库代码      | 链接时组合     | 独立保存       |
| 文件大小     | 通常较大      | 通常较小       |
| 运行时动态库依赖 | 较少        | 较多         |
| 多进程共享库代码 | 相对困难      | 更方便        |
| 兼容性风险    | 更多在构建阶段处理 | 运行环境也需满足要求 |

重点：动态链接不等于动态装入。

链接解决模块和符号的组织问题。

装入解决程序进入内存和建立可执行地址环境的问题。

### 9.3 程序的三种装入与重定位方式

| 方式    | 地址绑定时间 | 核心特点    |
| ----- | ------ | ------- |
| 绝对装入  | 编译或链接时 | 最终位置已知  |
| 静态重定位 | 装入时    | 一次性修正   |
| 动态重定位 | 运行时    | 执行时地址转换 |

#### 绝对装入

程序编译或链接时已经知道实际装入位置。

特点是简单，但位置灵活性差。

#### 静态重定位

装入时根据实际装入基址修正地址。

例如：

程序中的相对地址：

$$
A=120
$$

实际装入基址：

$$
B=5000
$$

则修正后的地址：

$$
\boxed{P=B+A=5120}
$$

装入时完成修正。

运行期间通常不能随意整体移动程序而不重新处理地址。

#### 动态重定位

执行指令时，通过硬件地址转换得到实际物理地址。

在简单的基址—界限模型中：

$$
\boxed{P=B+A}
$$

但这个加法是在访问时通过地址转换机制完成，而不是装入时永久修改指令中的地址。

在分页系统中，地址转换更一般地通过页表完成，不能把所有现代动态重定位都理解为简单的基址相加。

#### 必考辨析

静态重定位：装入时修改地址。

动态重定位：运行时转换地址。

这里的“静态”和“动态”指地址绑定时机，不是指链接库的方式。

### 9.4 进程内存映像

典型布局：

```text
             高地址
┌────────────────────────┐
│         Stack          │
│       栈，通常向下增长 │
├────────────────────────┤
│                        │
│   共享库 / mmap区域    │
│                        │
├────────────────────────┤
│         Heap           │
│       堆，通常向上增长 │
├────────────────────────┤
│          BSS           │
├────────────────────────┤
│          Data          │
├────────────────────────┤
│          Text          │
└────────────────────────┘
             低地址
```

具体布局会受到操作系统、体系结构和 ASLR 等机制影响。

主要记住各区域存储什么。

| 区域      | 典型内容                |
| ------- | ------------------- |
| Text    | 机器指令                |
| Data    | 已初始化的全局、静态变量        |
| BSS     | 未显式初始化或零初始化的全局、静态变量 |
| Heap    | 动态分配的内存对象           |
| Stack   | 函数调用信息、局部变量等        |
| mmap 区域 | 动态库、映射文件、匿名映射       |

#### 综合例题：变量存储位置

```c
#include <stdlib.h>

int a = 10;
int b;

static int c = 20;
static int d;

int main(void)
{
    int x = 5;

    static int y = 30;

    int *p = malloc(100);

    free(p);
    return 0;
}
```

典型分类：

| 对象           | 存储区域       |
| ------------ | ---------- |
| 程序指令         | Text       |
| a            | Data       |
| b            | BSS        |
| c            | Data       |
| d            | BSS        |
| x            | Stack 或寄存器 |
| y            | Data       |
| p 这个指针变量     | Stack 或寄存器 |
| malloc 分配的对象 | Heap       |

两个特别重要的陷阱：

第一，局部 static 变量不因为写在函数内部就位于栈。

`y` 具有静态存储期。

第二，指针变量的位置与其指向的数据位置不同。

`p` 是局部指针变量，而 `malloc()` 分配的对象来自堆管理区域。

编译器可能优化局部变量，因此不要把表中的典型位置理解为所有情况下的绝对保证。

### 9.5 虚拟地址连续，物理内存一定连续吗？

不一定。

假设：

```text
虚拟页0 → 物理页框7

虚拟页1 → 物理页框3

虚拟页2 → 物理页框9
```

进程看到的虚拟地址可以连续，但物理页框可能分散。

另外：

两个进程都可以访问虚拟地址：

```text
0x1000
```

但进程 A 的 `0x1000` 和进程 B 的 `0x1000` 可能映射到不同物理页框。

同一个虚拟地址值，不代表同一个物理地址。

这是后续内存管理章节的重要基础。

## 十、操作系统内核结构

### 10.1 分层结构

分层结构把操作系统划分为多个层次。

```text
用户程序
    ↓
高级系统服务
    ↓
进程与内存管理
    ↓
底层硬件控制
    ↓
硬件
```

优点：

- 层次清晰。
- 易于理解和调试。
- 接口关系明确。

缺点：

- 层次划分不容易。
- 某些请求可能需要经过多层。
- 严格分层可能增加开销。

### 10.2 模块化结构

操作系统按功能划分模块：

```text
进程管理模块
内存管理模块
文件管理模块
设备管理模块
网络模块
```

模块化强调功能划分和接口。

分层强调上下级关系。

模块化不等于微内核。

例如 Linux 通常属于宏内核体系，但支持可装卸内核模块。

### 10.3 宏内核

宏内核将大量操作系统核心服务放在内核地址空间中。

```text
用户程序
   ↓
系统调用
   ↓
┌──────────────────────┐
│        宏内核        │
│                      │
│  进程管理            │
│  内存管理            │
│  文件系统            │
│  网络协议栈          │
│  设备驱动            │
└──────────────────────┘
   ↓
硬件
```

典型代表包括传统 UNIX 与 Linux 内核。

优点：

- 内核内部服务调用直接。
- IPC 等跨保护域通信开销相对较少。
- 通常具有较高执行效率。

缺点：

- 内核规模较大。
- 内核组件之间可能存在较强耦合。
- 严重内核故障容易影响整个系统。

### 10.4 微内核

微内核尽量只保留最基本的内核机制。

例如：

- 基本调度。
- IPC。
- 基础地址空间管理。
- 必要的中断和陷入机制。

文件系统、部分设备驱动等服务可以放在用户态。

```text
       用户程序
           ↓
┌──────────────────────┐
│ 用户态文件服务器     │
│ 用户态设备服务器     │
│ 用户态网络服务器     │
└──────────────────────┘
           ↓ IPC
┌──────────────────────┐
│        微内核        │
│                      │
│ 基本调度             │
│ IPC                  │
│ 基础内存管理         │
└──────────────────────┘
           ↓
          硬件
```

#### 微内核的优点

因为更多服务运行于独立的用户态保护域，所以通常具有：

- 更好的故障隔离潜力。
- 较高的可靠性潜力。
- 较高的安全性潜力。
- 较强的可扩展性。

#### 微内核的缺点

服务之间可能需要更多：

- IPC。
- 模式切换。
- 调度操作。
- 数据传递。

因此可能产生额外的性能开销。

但是不能说：

“任何微内核都一定比任何宏内核慢。”

具体性能仍取决于实现。

### 10.5 真题：2023 年——微内核优缺点

与宏内核相比，微内核通常具有：

I. 较好的性能。\
II. 较高的可靠性。\
III. 较高的安全性。\
IV. 较强的可扩展性。

答案：D，II、III、IV。

逐项分析：

| 选项  | 判断 | 原因                 |
| --- | -- | ------------------ |
| I   | 错误 | 更多 IPC 等操作可能增加性能开销 |
| II  | 正确 | 用户态服务隔离有利于可靠性      |
| III | 正确 | 更小的内核可信计算基有利于安全性   |
| IV  | 正确 | 独立服务更容易扩展与维护       |

#### 宏内核与微内核对比

| 特征     | 宏内核    | 微内核      |
| ------ | ------ | -------- |
| 内核规模   | 较大     | 较小       |
| 文件服务   | 通常在内核态 | 可在用户态    |
| 内核内部调用 | 较多     | 相对较少     |
| IPC    | 通常相对较少 | 通常较多     |
| 性能     | 通常较有优势 | 可能存在额外开销 |
| 故障隔离   | 相对较弱   | 相对较强     |
| 可扩展性   | 依赖具体设计 | 通常较强     |

<Accordions>

<Accordion title="拓展：外核（Exokernel）与微内核的区别">

外核是另一种内核设计思路。

它强调：

内核主要负责保护和安全复用硬件资源，尽量把高层资源管理策略交给用户态。

```text
应用程序
   ↓
Library OS
   ↓
Exokernel
   ↓
硬件
```

与微内核相比：

微内核重在将系统服务移出内核。

外核更强调减少强制性的高层资源抽象，让应用通过库操作系统管理已授权资源。

但外核并不意味着用户程序可以任意破坏硬件或其他进程。

内核仍需要负责安全与保护。

## 十一、操作系统引导

### 11.1 为什么需要引导？

操作系统内核通常保存在外存。

但 CPU 加电后，必须先从体系结构规定的入口执行初始代码。

这时操作系统内核尚未完成装入。

因此需要引导机制逐步加载操作系统。

### 11.2 典型引导过程

```text
加电
  ↓
CPU执行固件代码
  ↓
BIOS / UEFI
  ↓
硬件初始化
  ↓
寻找启动设备和启动程序
  ↓
Bootloader
  ↓
将OS内核装入内存
  ↓
转入内核入口
  ↓
初始化内存、中断、调度、驱动等
  ↓
启动系统服务
  ↓
正常运行
```

### 11.3 传统 BIOS + MBR

经典过程：

```text
加电
  ↓
BIOS固件
  ↓
POST硬件自检
  ↓
选择启动设备
  ↓
读取MBR
  ↓
执行引导代码
  ↓
加载后续引导程序
  ↓
加载OS内核
```

传统 512 字节 MBR 的经典布局：

| 内容     | 大小     |
| ------ | ------ |
| 引导代码区域 | 446 字节 |
| 分区表    | 64 字节  |
| 结束标志   | 2 字节   |
| 总计     | 512 字节 |

结束标志通常为 `0x55AA`。

这是经典 BIOS/MBR 模型，不应直接套用到所有现代机器。

### 11.4 UEFI 引导

现代系统常采用 UEFI。

```text
加电
  ↓
UEFI固件
  ↓
查找EFI启动程序
  ↓
执行.efi文件
  ↓
加载内核
```

需要区分三个概念：

| 概念         | 作用          |
| ---------- | ----------- |
| UEFI       | 固件和启动接口体系   |
| GPT        | 磁盘分区表格式     |
| Bootloader | 负责加载操作系统的程序 |

GPT 不是 Bootloader。

UEFI 常与 GPT 配合，但二者不是同一种机制。

### 11.5 真题：2013 年

计算机开机后，操作系统最终装入：

A. BIOS\
B. ROM\
C. EPROM\
D. RAM

答案：D。

原因是操作系统内核运行时通常需要驻留在主存的相应区域。

BIOS、ROM、EPROM 主要与固件有关。

#### 模拟题：BIOS 引导顺序

传统 BIOS 引导过程中，下面哪项最先发生？

A. 硬件自检\
B. 加载 MBR\
C. 加载分区引导记录\
D. 加载 OS 内核

答案：A。

在题目所列的四项中，POST 硬件自检最早。

但如果题目问 CPU 通电后执行的第一条指令，就要回答从处理器规定的复位入口开始执行固件代码，而不是把 POST 当成第一条机器指令。

## 十二、虚拟机与 Hypervisor

### 12.1 什么是虚拟机？

虚拟机是通过虚拟化技术构建的逻辑计算机。

例如：

```text
         物理服务器
              ↓
         Hypervisor
          /   |    \
         /    |     \
      VM1    VM2    VM3
      Linux  Windows Linux
```

每台虚拟机可以拥有：

- vCPU。
- 虚拟内存。
- 虚拟磁盘。
- 虚拟网络设备。
- Guest OS。

### 12.2 Hypervisor 的作用

Hypervisor 又叫 VMM。

主要负责：

- 创建虚拟机。
- 分配虚拟 CPU。
- 管理客户机内存。
- 虚拟化设备。
- 隔离不同虚拟机。
- 协助处理客户机敏感操作。

客户机操作系统不能任意控制物理机器上的全部资源。

真正的物理资源管理仍受到 Hypervisor 和硬件虚拟化机制约束。

### 12.3 两类 Hypervisor

| 比较   | Type 1   | Type 2     |
| ---- | -------- | ---------- |
| 名称   | 裸机型      | 宿主型        |
| 运行方式 | 直接位于硬件之上 | 依托 Host OS |
| 应用场景 | 服务器虚拟化   | 桌面虚拟化等     |

Type 1：

```text
Guest OS
    ↓
Hypervisor
    ↓
硬件
```

Type 2：

```text
Guest OS
    ↓
虚拟机软件
    ↓
Host OS
    ↓
硬件
```

### 12.4 虚拟机与容器

| 特点          | 虚拟机              | 容器       |
| ----------- | ---------------- | -------- |
| 独立 Guest 内核 | 通常有              | 通常没有     |
| 虚拟化对象       | 机器级环境            | OS 级运行环境 |
| 开销          | 通常较大             | 通常较小     |
| 典型隔离基础      | Hypervisor、硬件虚拟化 | OS 内核机制  |

不要认为 Docker 容器就是传统硬件虚拟机。

容器通常共享宿主机内核。

## 十四、结合模拟题深入训练

下面选取典型题型进行分析。对较长题干采用题意概括，保留关键条件与解题逻辑。

### 模拟题一：哪个操作必须受到保护？

题目问多用户系统中，哪项操作必须受到操作系统保护。

选项涉及：

A. 从内核态转为用户态。\
B. 读取内核空间数据。\
C. 读取内核空间指令。\
D. 打开或控制系统级定时器。

正确答案：D。

按传统教材题目的意图，D 会直接影响 CPU 定时控制、时间片等关键机制，因此必须限制。

但是这里需要注意一个现代系统中的重要区别：

普通用户程序通常也无权任意读取受保护的内核地址空间。

这道题采用较简化的经典保护模型，不能把它推广为现代操作系统允许用户任意读取内核内存。

做题时要分别考虑题目采用的教材模型与现代内存保护机制。

### 模拟题二：进入内核态是否一定切换进程？

假设：

```text
进程A正在用户态运行
        ↓
发生时钟中断
        ↓
进入内核态
        ↓
中断服务完成
```

问题：是否一定切换到进程 B？

答案：不一定。

可能发生：

```text
A用户态 → A内核态 → A用户态
```

也可能发生：

```text
A用户态
   ↓
A内核态
   ↓
调度器决定运行B
   ↓
B恢复执行
```

判断发生进程切换的依据，不是是否进入内核态，而是调度器是否真正更换了执行主体。

### 模拟题三：系统调用指令由什么决定？

典型比较题：

在同一硬件平台上运行不同操作系统，其系统调用所用的处理器入口指令一般属于相同指令集机制。

同一个 Linux 系统运行在不同硬件架构上，其系统调用入口指令则可能不同。

正确答案：B，相同、不同。

原因：

```text
CPU架构
   ↓
决定可用机器指令和陷入机制
```

```text
操作系统及平台ABI
   ↓
决定系统调用号、参数约定等
```

例如：

- x86 可能使用 `syscall`。
- ARM 使用 `svc`。
- RISC-V 使用 `ecall`。

不要混淆硬件指令与操作系统 API。

### 模拟题四：微内核中的用户程序如何访问文件服务器？

传统微内核中，文件系统可以作为用户态服务器运行。

因此：

```text
用户程序
   ↓ IPC
文件服务器
   ↓
微内核提供必要通信与保护机制
```

不要认为：

“文件服务器运行在用户态，因此用户程序可以直接执行文件服务器内部函数并绕开保护机制。”

用户程序与文件服务器可以通过受控 IPC 通信。

跨保护域通信通常是微内核的核心机制之一。

### 模拟题五：系统调用时，所有寄存器都必须直接写入 PCB 吗？

不一定。

不同系统的现场保存可能涉及：

- 内核栈。
- 陷入帧。
- 每线程保存区。
- 进程或线程控制结构。

不能认为：

```text
进入内核态
    ↓
必须把所有寄存器直接复制进PCB
```

PCB 负责管理进程状态和上下文信息，但具体保存位置和机制依赖实现。

更不能认为阻塞时需要把整个用户栈复制进 PCB。

### 模拟题六：地址变换可能引起哪些异常？

典型题给出：

I. 地址越界。\
II. 缺页。\
III. 访问权限错误。\
IV. 内存溢出。

正确答案：D，I、II、III。

原因：

I 是合法地址范围检查。

II 是页面驻留检查。

III 是访问权限检查。

IV 的“内存溢出”是较宽泛的程序或资源问题，并不是这里定义的独立地址转换异常类型。

## 十五、综合应用题：把整章机制连起来

以下为根据本章知识点设计的综合训练题，不作为历年统考原题。

这些题特别适合衔接后续章节。

### 综合题一：系统调用 + I/O + 中断 + 进程调度

#### 题目

单核 CPU 上有两个进程：

- P1 正在用户态运行。
- P2 处于就绪态。

P1 执行：

```text
read(fd, buf, 100);
```

已知：

1. 数据不在缓存中。
2. 需要磁盘 I/O。
3. 采用阻塞式同步 I/O。
4. 磁盘最终正常完成读取。

回答：

（1）P1 是否进入内核态？\
（2）P1 是否阻塞？\
（3）P2 能否运行？\
（4）磁盘完成时属于什么事件？\
（5）P1 被唤醒后是否立即运行？\
（6）read 正常返回后，P1 从哪里继续执行？

#### 详细解析

第一步：发起系统调用

```text
P1用户态
   ↓
执行read对应系统调用
   ↓
P1内核态
```

因此（1）需要进入内核态。

第二步：检查数据是否就绪

数据不在缓存中，需要磁盘读取。

在题目给定的阻塞式 I/O 条件下，P1 需要等待。

因此（2）P1 阻塞。

第三步：调度其他进程

P1 已经不能继续运行，而 P2 处于就绪态。

所以调度器可以让 P2 运行。

因此（3）可以。

第四步：磁盘完成读取

磁盘控制器产生 I/O 完成中断请求。

这属于外部中断。

因此（4）外部中断。

第五步：唤醒 P1

操作系统完成必要 I/O 处理，将 P1 从阻塞态转为就绪态。

但就绪不代表立即运行。

P1 仍然需要等待调度。

因此（5）不一定。

第六步：P1 恢复运行

以后调度器重新选择 P1。

P1 恢复原来的执行上下文，系统调用完成并返回后，继续执行 `read` 后面的程序代码。

#### 完整时序

```text
P1用户态运行
      ↓
调用read
      ↓
进入内核态
      ↓
发现需要等待磁盘
      ↓
P1阻塞
      ↓
调度P2
      ↓
P2运行
      ↓
磁盘完成I/O
      ↓
产生外部中断
      ↓
中断处理程序运行
      ↓
P1阻塞态 → 就绪态
      ↓
合适时机重新调度P1
      ↓
P1恢复执行
      ↓
read返回
```

这一道题同时检验：

系统调用、用户态内核态、进程状态、调度、设备中断和执行恢复。

建议能够不看答案，自己把这个时序完整画出来。

### 综合题二：缺页异常 + 指令恢复

#### 题目

某程序执行：

```text
1000：ADD R1, R2

1004：LOAD R3, [0x8000]

1008：SUB R4, R5
```

假设：

- 虚拟地址 `0x8000` 合法。
- 对应页面没有驻留主存。
- 采用请求分页。
- 缺页能够成功处理。

回答：

（1）在哪条指令发生异常？\
（2）是什么异常？\
（3）是否进入内核态？\
（4）处理完成后执行哪条指令？\
（5）是否必然切换进程？

#### 解析

（1）`LOAD`。

因为它需要访存，才会触发相应地址转换。

（2）同步缺页异常。

因为由当前访存指令直接触发。

（3）需要进入内核态。

因为 OS 需要完成缺页处理和页表更新等工作。

（4）重新执行地址 1004 的 `LOAD`。

因为故障指令尚未成功完成。

（5）不一定切换进程。

例如某种可快速修复的页面映射故障可能无需切换进程；如果需要等待磁盘，则可能阻塞并调度其他进程。

核心结论：缺页 Fault 可恢复时通常重启故障指令，而不是直接跳过。

### 综合题三：CPU 利用率计算

#### 题目

某单道程序系统中，作业 A 执行：

- CPU 计算 3 ms。
- I/O 6 ms。
- CPU 计算 3 ms。

问：

（1）单道系统的 CPU 利用率是多少？

（2）若有另一个完全 CPU 密集型作业 B，并且能在 A 的 I/O 阶段执行 6 ms，忽略切换开销，则这 12 ms 内的 CPU 利用率是多少？

#### 解答

单道系统：

$$
T=3+6+3=12\text{ ms}
$$

CPU 工作时间：

$$
T_{\mathrm{CPU}}=3+3=6\text{ ms}
$$

因此：

$$
U_1=\frac{6}{12}=50%
$$

多道系统中：

```text
0—3ms：执行A

3—9ms：A进行I/O，CPU执行B

9—12ms：执行A
```

CPU 工作时间：

$$
3+6+3=12\text{ ms}
$$

因此：

$$
\boxed{U_2=100%}
$$

但这是给定条件下的理想化结果。

多道程序提高 CPU 利用率的原因，是允许 CPU 计算与设备 I/O 重叠。

### 综合题四：宏内核与微内核的开销比较

#### 题目

某文件服务在宏内核中的额外处理开销为：

- 进入内核及返回：0.6 μs。
- 内核服务处理：0.4 μs。

微内核完成同样服务，假设具有相同基础开销，但额外发生 4 次 IPC，每次 IPC 开销为 0.3 μs。

求两种实现的开销。

#### 解答

宏内核：

$$
T_{\mathrm{mono}}=0.6+0.4=1.0\,\mu\mathrm{s}
$$

微内核：

$$
\begin{aligned}
T_{\mathrm{micro}} &=0.6+0.4+4\times0.3 \\ &=2.2\,\mu\mathrm{s}
\end{aligned}
$$

时间差：

$$
\Delta T=2.2-1.0=1.2\,\mu\mathrm{s}
$$

比值：

$$
\frac{T_{\mathrm{micro}}}{T_{\mathrm{mono}}}=2.2
$$

在这个假设模型中，微内核路径的处理开销是宏内核的 2.2 倍。

但不能据此推断真实微内核系统固定慢 2.2 倍。

实际性能依赖 IPC、缓存、内存映射、硬件支持和具体实现。

此题主要用来说明：

微内核用更多受保护的服务协作，换取较好的隔离和模块化。

## 十七、第一章考试解题方法总结

真正考试时，建议按下面的流程判断。

### 方法一：判断指令能否在用户态执行

看操作是否直接控制受保护硬件或修改关键系统状态。

```text
普通计算、普通函数、合法访存
              ↓
          通常用户态

关中断、修改页表、直接设备控制
              ↓
          通常内核态
```

特殊情况：

Trap 等系统调用入口指令允许用户态执行，但它会触发受控进入内核。

### 方法二：判断事件属于哪一类

```text
时钟、键盘、磁盘完成
          ↓
       外部中断

除零、缺页、非法访存
          ↓
       同步异常

程序主动请求文件、进程等服务
          ↓
       系统调用
```

### 方法三：判断是否发生进程切换

重点检查：

- 原进程是否需要阻塞？
- 时间片是否耗尽？
- 是否有更高优先级进程需要运行？
- 调度器是否真正选择了另一个进程？

不能仅因为发生了中断、异常或系统调用，就判定一定切换进程。

### 方法四：判断中断处理由谁完成

```text
硬件：
响应事件
保存必要返回状态
受控权限转换
提供处理入口机制

软件：
保存额外现场
执行服务程序
更新系统状态
唤醒和调度进程
```

### 方法五：判断恢复位置

```text
外部中断
    ↓
下一条尚未执行的指令

可恢复缺页
    ↓
重新执行故障指令

系统调用
    ↓
规定的后继位置
```

### 方法六：判断操作系统结构

```text
宏内核
    ↓
更多服务位于内核态
内部调用较直接
性能通常较好

微内核
    ↓
更多服务位于用户态
IPC较多
故障隔离潜力较好

外核
    ↓
保护和安全复用硬件
高层资源管理策略更多交给用户态
```

### 复习优先顺序

结合本章典型题，建议按三个层次复习。

第一层：必须熟练掌握

操作系统四大特征、发展历程、用户态与内核态、特权指令、外部中断与异常、系统调用、宏内核与微内核。

这些概念应该能够迅速判断，不需要临时推理。

第二层：必须能够解释机制

为什么 Trap 可以在用户态执行？为什么缺页属于异常？为什么硬件必须保存关键断点？为什么进入内核态不一定发生进程切换？为什么微内核可能有更多 IPC 开销？

这些问题决定你能否做对较难的选择题。

第三层：必须能独立分析完整执行过程

重点掌握两条链路。

第一条：

```text
用户程序
   ↓
系统调用
   ↓
内核服务
   ↓
等待I/O
   ↓
进程阻塞
   ↓
运行其他进程
   ↓
I/O完成中断
   ↓
唤醒等待进程
   ↓
重新调度
   ↓
恢复执行
```

第二条：

```text
用户程序访存
   ↓
MMU地址转换
   ↓
缺页异常
   ↓
进入内核
   ↓
建立或恢复页面映射
   ↓
更新页表
   ↓
重新执行故障指令
```

这两条链路既是第一章综合理解的关键，也直接联系后续进程管理、内存管理与 I/O 管理。

### 本章最终结论

操作系统第一章最核心的思想，可以浓缩为一句话：

操作系统通过资源管理、硬件抽象、特权级保护、中断异常机制和系统调用，使多个程序能够安全、有序地使用计算机硬件。

学完这一章，面对任何有关用户态、内核态、中断、异常或系统调用的题目，都应该能够回答四个问题：

1. 是谁触发的？ 是外部设备、当前指令，还是程序主动请求？
2. 为什么需要内核？ 是否涉及受保护资源或异常处理？
3. 硬件和操作系统分别做什么？ 谁保存状态，谁执行服务？
4. 处理结束后如何继续？ 返回原指令、下一条指令，还是调度另一个进程？

如果这四个问题都能独立回答，并且能够正确分析上面的两道执行时序综合题，那么操作系统第一章最重要、最容易混淆的机制就基本掌握了。
