## 第一部分 本章知识体系与考情分析

### 一、本章究竟考什么？

操作系统第 1 章是整个操作系统课程的基础。

这一章虽然不像进程同步、内存管理那样包含大量计算题，但其重要性不能低估。

原因在于：

- 后续进程调度依赖中断和 CPU 工作模式。
- 进程创建、终止、通信依赖系统调用。
- 虚拟内存管理依赖异常处理和硬件地址转换。
- 文件读写依赖用户态、内核态之间的转换。
- 设备管理依赖中断、异常和 I/O 机制。
- 程序的装入与链接决定程序如何真正进入运行状态。

因此，本章的核心不是孤立记忆概念，而是理解：

**一个普通应用程序究竟如何在操作系统的管理下运行。**

## 第二部分 操作系统的基本概念、功能与特征

### 二、操作系统的基本概念

#### 2.1 什么是操作系统？

操作系统（Operating System，OS）是：

**控制和管理整个计算机系统的硬件与软件资源，合理组织计算机工作，并为用户及其他软件提供方便接口和运行环境的系统软件。**

可以从三个角度理解。

##### 角度一：资源管理者

计算机中存在大量有限资源：

- CPU。
- 主存。
- 磁盘。
- 打印机。
- 网络设备。
- 文件。
- 外设。

多个程序可能同时申请同一种资源。

例如：

```text
进程 A ──申请 CPU──┐
                  │
进程 B ──申请 CPU──┼──操作系统──CPU
                  │
进程 C ──申请 CPU──┘
```

操作系统必须决定：

- CPU 应该先分配给谁？
- 每个进程可以运行多久？
- 哪些进程需要等待？
- 资源何时回收？
- 如何防止一个进程破坏其他进程？

这就是资源管理。

##### 角度二：硬件抽象层

考虑读取磁盘文件。

普通应用程序只需要：

    open()
    read()
    close()

但磁盘实际工作涉及：

- 文件目录查找。
- 文件块定位。
- 设备驱动。
- 控制器操作。
- 数据传输。
- 缓冲区管理。
- 中断处理。

操作系统将复杂硬件操作包装为文件接口。

所以：

**文件是一种重要的操作系统抽象。**

类似的抽象还有：

| 物理资源 | 操作系统抽象 |
|---|---|
| CPU | 进程、线程、虚拟处理器 |
| 物理内存 | 虚拟地址空间 |
| 磁盘扇区 | 文件 |
| 物理设备 | 逻辑设备 |
| 网络硬件 | Socket 等接口 |

##### 角度三：服务提供者

操作系统需要向用户和应用程序提供服务。

例如：

- 创建进程。
- 读取文件。
- 分配内存。
- 网络通信。
- 获取时间。
- 管理设备。

这些服务主要通过系统调用提供。


#### 2.2 操作系统的四大管理功能

##### ① 处理机管理

主要包括：

- 进程创建与撤销。
- 进程状态管理。
- CPU 调度。
- 进程同步与互斥。
- 进程通信。
- 死锁处理。

核心问题：

**多个进程如何合理共享 CPU？**

##### ② 存储器管理

主要包括：

- 内存分配。
- 内存回收。
- 地址转换。
- 内存保护。
- 内存扩充。
- 虚拟内存。

核心问题：

**多个进程如何安全、有效地使用有限的主存？**

##### ③ 文件管理

主要包括：

- 文件创建与删除。
- 文件读写。
- 目录管理。
- 文件存储空间管理。
- 文件共享与保护。

核心问题：

**如何把外存空间组织成用户容易使用的文件？**

##### ④ 设备管理

主要包括：

- 设备分配。
- 设备驱动。
- I/O 控制。
- 缓冲管理。
- 设备独立性。
- 设备共享。

核心问题：

**如何协调 CPU、内存和外部设备之间的工作？**


#### 2.3 操作系统的接口

这是历年真题的重要考点。

操作系统向用户和程序提供的接口，可以分为两类。

##### ① 命令接口

面向用户。

又分为：

**联机命令接口：**

用户输入命令，系统立即或交互式处理。

例如：

    ls
    cd
    mkdir
    dir

Linux Shell 和 Windows 命令行属于典型例子。

**脱机命令接口：**

用户预先准备作业控制命令，由系统按规定执行。

例如批处理脚本。

##### ② 程序接口

面向应用程序。

核心形式：

**系统调用（System Call）。**

例如：

    read()
    write()
    open()
    fork()
    execve()

注意：

系统调用接口与库函数接口不是同一个概念。

##### 真题：2010 年

题目：

操作系统提供给应用程序的接口是（）。

A. 系统调用

B. 中断

C. 库函数

D. 原语

**答案：A**

解析：

A 正确。

系统调用是操作系统为应用程序提供内核服务的接口。

B 错误。

中断是处理事件的机制，而不是一般的应用程序服务接口。

C 错误。

库函数属于程序库提供的接口。

部分库函数内部可能执行系统调用，但并非所有库函数都是系统调用。

D 错误。

原语强调操作的原子性，是内核实现同步、状态转换等机制时可能使用的基本操作，不属于面向应用程序的通用服务接口。

**本题推广：**

题目出现：

- 操作系统向应用程序提供的接口。
- 请求操作系统服务。
- 用户程序进入内核。
- 内核为应用程序提供服务。

通常应联想到：

**系统调用。**


### 三、操作系统的四个基本特征

必须记住：

**并发、共享、虚拟、异步。**

其中：

**并发和共享是两个最基本的特征。**

#### 3.1 并发与并行

##### ① 并发

并发（Concurrency）：

多个事件在同一时间间隔内发生或推进。

例如单核 CPU：

```text
时间 ─────────────────────────►

CPU：

AAA │ BBB │ CCC │ AAA │ BBB
```

其中：

- A、B、C 都在向前推进。
- 但是任意时刻只能有一个进程占用这个单核 CPU 执行指令。

因此是并发。

##### ② 并行

并行（Parallelism）：

多个事件在同一时刻真正同时发生。

例如：

```text
时间 ─────────────────────────►

CPU 0：AAAAAAAAAAAA

CPU 1：BBBBBBBBBBBB
```

两个 CPU 核心同时运行不同程序。

属于并行。

##### ③ 对比总结

| 比较 | 并发 | 并行 |
|---|---|---|
| 时间范围 | 同一时间间隔 | 同一时刻 |
| 单核 CPU | 可以 | 单核上通常不能执行两个独立指令流 |
| 多核 CPU | 可以 | 可以 |
| 实现方式 | 时间复用 | 硬件同时执行 |
| 核心含义 | 多个任务交替推进 | 多个任务真正同时执行 |

##### 高频陷阱

**单处理机系统中，进程不能并行，不代表 CPU 与设备不能并行。**

这是一个特别容易混淆的考点。

##### 真题：2009 年

单处理机系统中，可并行的是（）。

Ⅰ. 进程与进程

Ⅱ. 处理机与设备

Ⅲ. 处理机与通道

Ⅳ. 设备与设备

A. 仅Ⅰ、Ⅱ、Ⅲ

B. 仅Ⅰ、Ⅱ、Ⅳ

C. 仅Ⅰ、Ⅲ、Ⅳ

D. Ⅱ、Ⅲ、Ⅳ

**答案：D**

逐项判断：

**Ⅰ：错误。**

在题目的单处理机模型下，同一时刻只有一个进程能在 CPU 上执行。

因此进程之间不能真正并行执行。

**Ⅱ：正确。**

CPU 可以执行计算任务，而磁盘控制器同时进行 I/O。

**Ⅲ：正确。**

通道具有独立执行 I/O 控制任务的能力，可以与 CPU 并行工作。

**Ⅳ：正确。**

多个独立 I/O 设备可以同时工作。

因此：

正确的是Ⅱ、Ⅲ、Ⅳ。

##### 解题方法

遇到“能否并行”：

第一步：看是否争用同一个执行部件。

第二步：看是否存在独立工作的硬件单元。

第三步：区分进程的 CPU 指令执行与设备自身的工作。

**单核不能并行执行两个普通进程的指令流，但整个计算机可以存在多个并行工作的硬件部件。**


#### 3.2 共享

共享：

系统中的资源可供多个并发执行的进程共同使用。

分为两类。

##### ① 互斥共享

同一时刻只允许一个进程访问资源。

例如：

- 独占式打印机。
- 临界区。
- 需要独占保护的共享数据。

示意：

```text
进程 A ──占用打印机
进程 B ──等待
进程 C ──等待
```

A 释放资源以后，其他进程才能进入。

##### ② 同时共享

多个进程可以在同一时间段内共同使用资源。

例如：

- 多个进程读取同一个只读文件。
- 多个进程共享只读代码。
- 多个进程使用支持并发服务的设备。

需要注意：

“同时共享”不要求任意物理时刻都发生真正并行访问。

##### ③ 并发与共享的关系

二者互为存在条件。

并发带来了共享资源的需求。

共享资源又使多个程序的并发运行具有实际意义，并要求操作系统协调资源使用。

可以理解为：

```text
多个进程并发执行
        ↓
共同使用有限资源
        ↓
产生共享
        ↓
可能出现资源竞争
        ↓
需要同步、互斥与资源管理
```


#### 3.3 虚拟

虚拟：

把一个物理实体转换为若干逻辑上的对应物。

核心目标：

**让用户感觉自己拥有某种独立资源。**

例如：

一台计算机只有一个 CPU，但可以同时运行大量进程。

每个进程似乎都拥有一个处理器。

实际上：

操作系统通过时间片轮转实现 CPU 复用。

##### 两类经典复用方式

**① 时分复用**

不同程序在不同时间使用同一资源。

例如：

- CPU 时间片轮转。
- 部分设备的分时共享。

**② 空分复用**

不同程序使用资源的不同空间部分。

例如：

- 内存分区。
- 磁盘分区。

需要注意：

空间复用不必然等同于完整的虚拟内存机制。

现代虚拟内存还要求地址映射、保护以及可能的按需调入等能力。

##### 典型虚拟化技术

| 技术 | 虚拟效果 |
|---|---|
| 时间片轮转 | 一颗 CPU 表现为多个逻辑处理器 |
| 虚拟存储器 | 每个进程拥有独立虚拟地址空间 |
| SPOOLing | 将独占式设备包装成可共享的逻辑设备 |
| 虚拟机 | 一台物理主机运行多个虚拟计算机 |

##### 模拟题

下列关于虚拟化的说法：

Ⅰ. 时间片轮转是一种 CPU 资源虚拟化。

Ⅱ. 内存分区体现空间复用。

Ⅲ. SPOOLing 是设备虚拟化技术。

Ⅳ. 虚拟机管理程序一定始终运行在内核态。

判断正确项。

**答案：Ⅰ、Ⅱ、Ⅲ。**

分析：

Ⅰ正确。

时间片轮转让多个进程共享 CPU。

Ⅱ正确。

内存分区体现空间复用，但不能直接等同于现代虚拟内存。

Ⅲ正确。

SPOOLing 是典型的设备虚拟化技术。

Ⅳ错误。

虚拟机管理程序具有不同实现形态，宿主型虚拟化软件的一部分可以运行于用户态。

因此不能用“一定”概括。


#### 3.4 异步

异步是指：

多个程序以不可预知的速度向前推进。

例如：

```text
进程 A：运行 → 等待磁盘 → 就绪 → 运行

进程 B：运行 → 时间片结束 → 就绪

进程 C：等待网络 → 就绪 → 运行
```

由于：

- 调度时间不确定。
- I/O 完成时间不确定。
- 资源竞争具有不确定性。
- 中断可能在不同时间到来。

所以进程执行的推进速度并不固定。

##### 注意：异步不等于结果随机

例如：

两个进程分别计算自己的独立数据。

即使执行顺序不同，也可能得到相同结果。

只有当共享状态受到未正确同步的并发访问影响时，才可能产生竞态条件。

##### 四大特征总结

| 特征 | 核心问题 |
|---|---|
| 并发 | 多个程序如何共同推进？ |
| 共享 | 多个程序如何共同使用资源？ |
| 虚拟 | 如何把物理资源抽象为逻辑资源？ |
| 异步 | 为什么进程推进速度不可预知？ |


## 第三部分 操作系统的发展历程

### 四、操作系统的发展

#### 4.1 发展主线

```text
手工操作
   ↓
脱机输入输出
   ↓
单道批处理
   ↓
多道批处理
   ↓
分时系统 / 实时系统
```

理解历史发展的关键：

**每一代操作系统都在解决前一代系统存在的主要问题。**

#### 4.2 手工操作阶段

早期计算机没有成熟的操作系统。

用户需要手动完成：

- 程序装入。
- 程序启动。
- 数据输入。
- 结果输出。

最大问题：

**人机速度矛盾。**

人的操作速度远远慢于 CPU。

CPU 经常处于等待状态。


#### 4.3 脱机输入输出

使用外围机预先完成输入输出准备。

例如：

```text
输入设备
   ↓
外围机
   ↓
磁带
   ↓
主机
   ↓
磁带
   ↓
外围机
   ↓
输出设备
```

核心目的：

减少主机等待慢速人工输入输出的时间。

注意：

脱机 I/O 与后来的 SPOOLing 有思想联系，但不是完全相同的技术。


#### 4.4 单道批处理

多个作业组成一个批次，自动依次运行。

同一时刻内存中通常只有一个正在处理的用户作业。

优点：

减少人工干预。

缺点：

**CPU 等待 I/O 时无法转去执行其他用户作业。**

##### 计算示例

某作业执行过程：

1. CPU 计算 2 ms。
2. I/O 等待 6 ms。
3. CPU 计算 2 ms。

则总时间：

$$
T=2+6+2=10\text{ ms}
$$

CPU 实际工作时间：

$$
T_{\mathrm{CPU}}=4\text{ ms}
$$

CPU 利用率：

$$
U=\frac{4}{10}\times100\%=40\%
$$

CPU 有 60% 的时间处于空闲状态。


#### 4.5 多道批处理

允许多个作业同时进入内存。

当某个作业等待 I/O 时：

CPU 可以执行其他就绪作业。

例如：

```text
时间：0       2               8      10

进程 A：
      CPU 2ms | I/O等待6ms      | CPU 2ms

进程 B：
              | CPU计算6ms      |

CPU：
      AAAAAA  BBBBBBBBBBBBBBBB  AAAAAA
```

以上示意中：

- 0～2 ms：执行 A。
- 2～8 ms：A 进行 I/O，执行 B。
- 8～10 ms：执行 A。

忽略切换开销时：

$$
U_{\mathrm{CPU}}=\frac{10}{10}=100\%
$$

相比单道批处理的 40%，CPU 利用率显著提高。

核心原理：

**用其他程序的 CPU 计算时间覆盖当前程序的 I/O 等待时间。**

##### 多道程序技术的主要优点

1. CPU 利用率提高。
2. 设备利用率提高。
3. 系统吞吐量提高。

##### 缺点

1. 调度管理复杂。
2. 系统开销增加。
3. 资源竞争更加明显。
4. 用户交互能力通常较弱。

##### 真题：2017 年

与单道程序系统相比，多道程序系统的优点是：

Ⅰ. CPU 利用率高

Ⅱ. 系统开销小

Ⅲ. 系统吞吐量大

Ⅳ. I/O 设备利用率高

**答案：Ⅰ、Ⅲ、Ⅳ。**

分析：

Ⅰ正确。

某进程等待 I/O 时，可以执行其他进程。

Ⅱ错误。

系统需要增加调度、进程管理和资源保护机制，开销通常增加。

Ⅲ正确。

单位时间能够完成更多作业。

Ⅳ正确。

多个作业能够使设备获得更充分的利用。

##### 真题：2022 年

判断：

“多道程序系统中，进程数越多，CPU 利用率越高。”

**答案：错误。**

原因：

当进程数量较少时，增加进程通常能够减少 CPU 空闲时间。

但是进程数量过多时：

- 内存压力增大。
- 资源竞争加剧。
- 上下文切换增加。
- 缺页次数可能增加。
- 可能产生抖动。

CPU 有效利用率不一定继续提高。

##### 补充公式

对于一个非常理想化的模型：

假设每个进程在某一时刻独立地以概率 $p$ 等待 I/O，并且系统中有 $n$ 个进程。

全部进程同时等待的概率：

$$
P_{\mathrm{idle}}=p^n
$$

因此：

$$
U_{\mathrm{CPU}}\approx1-p^n
$$

例如：

$$
p=0.8,\qquad n=3
$$

则：

$$
U_{\mathrm{CPU}}\approx1-0.8^3
$$

$$
U_{\mathrm{CPU}}\approx48.8\%
$$

但要特别注意：

该公式只是忽略调度开销、资源争用等因素的理想化概率模型。

不能根据它得出：

“进程越多，实际 CPU 利用率一定越高。”


#### 4.6 分时操作系统

分时操作系统：

把 CPU 时间划分为较短的时间片，让多个用户或进程轮流执行。

例如：

```text
CPU 时间：

P1 → P2 → P3 → P1 → P2 → P3
```

核心特征：

- 多路性。
- 独立性。
- 及时性。
- 交互性。

主要目标：

**提高用户交互体验，缩短响应时间。**

##### 特别注意

分时系统强调：

用户请求能够获得较及时的响应。

但不要求所有任务都在严格截止时间之前完成。


#### 4.7 实时操作系统

实时操作系统：

要求系统在规定时间约束内完成任务。

##### 硬实时

错过截止时间可能造成严重后果。

例如：

- 飞行控制。
- 部分工业安全控制。
- 高安全要求的嵌入式控制。

##### 软实时

偶尔错过截止时间通常造成服务质量下降，但不一定使系统整体失败。

例如：

- 一些多媒体业务。
- 部分实时通信业务。

##### 三类系统对比

| 类型 | 核心目标 |
|---|---|
| 多道批处理 | 提高吞吐量与资源利用率 |
| 分时系统 | 提高响应速度与交互性 |
| 实时系统 | 满足时间约束 |

##### 真题：2016 年

关于批处理系统：

Ⅰ. 允许多个用户与计算机直接交互。

Ⅱ. 分为单道批处理和多道批处理。

Ⅲ. 中断技术支持 CPU 与 I/O 设备并行工作。

**答案：Ⅱ、Ⅲ。**

原因：

Ⅰ错误。

批处理系统通常缺乏作业运行期间的直接交互。

Ⅱ正确。

批处理包括单道批处理和多道批处理。

Ⅲ正确。

设备可以独立工作，中断机制可以在设备完成工作后通知 CPU，使两者协调并行工作。


## 第四部分 CPU 运行模式与特权指令

### 五、用户态与内核态

<Callout type="warn" title="用户态触发与内核态处理不能混淆">

普通指令在用户态执行时可能发生异常；系统调用可由用户态发起，但受保护的内核服务在内核态执行。

</Callout>


这是本章最核心的内容之一。

#### 5.1 为什么需要用户态与内核态？

考虑一个问题：

如果任何程序都能关闭中断，会发生什么？

某个普通程序可以执行：

    disable_interrupts()

然后一直占用 CPU。

操作系统可能无法通过时钟中断及时重新取得控制权。

再比如：

用户程序能够随意修改页表。

它就可能访问其他进程甚至内核的内存。

因此：

**操作系统必须限制普通程序能够执行的操作。**

CPU 硬件通过特权级机制实现这种限制。


#### 5.2 两种运行模式

##### 用户态（User Mode）

低特权级。

普通应用程序通常运行在用户态。

例如：

- 浏览器。
- 编辑器。
- 普通命令解释程序。
- 大部分用户程序代码。

用户态可以：

- 执行算术运算。
- 执行逻辑运算。
- 执行普通跳转。
- 修改通用寄存器。
- 访问合法的用户内存。
- 调用普通函数。
- 执行系统调用入口指令。

但不能直接执行高权限操作。

##### 内核态（Kernel Mode）

高特权级。

操作系统内核的受保护代码在内核态运行。

例如：

- 进程调度。
- 内存管理。
- 中断处理。
- 页表管理。
- 核心设备控制。
- 系统调用服务例程。

##### 对比

| 属性 | 用户态 | 内核态 |
|---|---|---|
| 特权级 | 低 | 高 |
| 普通指令 | 可以执行 | 可以执行 |
| 特权指令 | 不允许直接执行 | 可以执行 |
| 内核受保护资源 | 无法任意访问 | 可以按内核权限访问 |
| 典型程序 | Shell、应用程序 | 调度器、中断处理程序 |

注意：

**内核态既可以执行特权指令，也可以执行非特权指令。**

这是高频考点。


#### 5.3 什么是特权指令？

特权指令：

只能在具有足够权限的处理器运行模式下正常执行的指令。

典型包括：

- 关闭或配置中断。
- 修改系统控制寄存器。
- 修改页表基址寄存器。
- 控制内存保护机制。
- 执行受保护的设备 I/O 操作。
- 设置系统级定时器。

特权指令的共同点：

**能够修改系统关键状态或控制受保护的硬件资源。**

##### 非特权指令

例如：

    ADD
    SUB
    CMP
    JMP
    MOV

这些普通指令通常可以在用户态执行。

但注意：

非特权指令不意味着绝对不会引发异常。

例如：

    MOV R0, [addr]

如果 addr 对应的地址没有访问权限，就可能触发保护异常。


#### 5.4 Trap 指令为什么不是普通意义上的特权指令？

这是极其重要的易错点。

普通程序需要请求操作系统服务。

例如：

    read(fd, buffer, 100)

但读文件涉及内核资源管理。

那么用户程序如何进入内核？

答案：

**执行系统调用入口指令。**

不同架构可能采用：

    trap
    syscall
    svc
    ecall

等机制。

核心流程：

```text
用户程序
    │
    │ 执行系统调用入口指令
    ▼
CPU 执行受控权限转换
    │
    ▼
内核态
    │
    │ 执行内核服务
    ▼
返回用户态
```

这里的关键：

**用户程序必须能够执行系统调用入口指令。**

否则用户程序根本无法合法请求内核服务。

因此：

在 408 的常规分类中，用于发起系统调用的 Trap 指令不是只能在内核态执行的特权指令。

但它会触发进入内核态的受控过程。

##### 真题：2014 年

下列指令中，不能在用户态执行的是：

A. trap 指令

B. 跳转指令

C. 压栈指令

D. 关中断指令

**答案：D**

解析：

A：

Trap 用于请求内核服务，必须允许用户态执行。

B：

普通跳转指令属于非特权指令。

C：

普通压栈指令属于非特权指令。

D：

关中断会影响操作系统重新取得 CPU 控制权，因此属于特权操作。


#### 5.5 如何判断操作是否需要内核态？

建议掌握一个通用判断方法：

**看该操作是否需要修改受保护的系统状态。**

例如：

| 操作 | 是否通常需要内核权限 |
|---|---|
| 普通加法 | 否 |
| 普通比较 | 否 |
| 修改通用寄存器 | 否 |
| 普通函数调用 | 否 |
| 修改自己合法的用户变量 | 否 |
| 修改页表 | 是 |
| 直接配置硬件定时器 | 是 |
| 关闭中断 | 是 |
| 执行进程调度核心操作 | 是 |
| 控制受保护的 I/O 设备 | 是 |
| 发起系统调用入口指令 | 否，入口指令可在用户态执行 |
| 执行系统调用服务例程 | 是 |

##### 高频陷阱：修改 PC

普通跳转指令也会修改 PC。

例如：

    JMP target

所以不能认为：

“凡是修改 PC 的操作，都是特权操作。”

真正需要区分：

- 普通控制流跳转。
- 非法修改系统控制状态。
- 跨越特权级保护边界的操作。


#### 5.6 真题：2011 年

下列选项中，在用户态执行的是：

A. 命令解释程序

B. 缺页处理程序

C. 进程调度程序

D. 时钟中断处理程序

**答案：A**

解析：

命令解释程序虽然是操作系统提供的用户工具，但通常作为普通用户进程运行。

例如：

    bash
    zsh
    cmd.exe

它们不需要始终运行在内核态。

B：

缺页处理需要更新受保护的内存管理状态。

C：

进程调度属于内核功能。

D：

时钟中断处理程序属于内核中断处理机制。

因此只有 A。

##### 重要结论

**操作系统提供的程序，不一定全部运行在内核态。**

例如：

- Shell 通常运行于用户态。
- GUI 的大量组件运行于用户态。
- 某些系统服务也可以运行于用户态。

决定执行模式的是权限要求和操作系统结构，而不是程序名字里是否带有“系统”。


## 第五部分 中断、异常与系统调用

### 六、中断机制

#### 6.1 为什么操作系统需要中断？

假设一个程序正在执行：


```c
while (true) {
    compute();
}

```

它一直不主动请求操作系统服务。

如果没有外部可抢占机制：

操作系统可能无法按预期时间重新取得 CPU。

因此需要某种机制：

**使 CPU 能够暂停当前执行流，转去处理更重要的事件。**

中断正是重要机制之一。

##### 中断的主要作用

1. 让 CPU 处理外部设备事件。
2. 支持时钟驱动的抢占式调度。
3. 支持 I/O 完成通知。
4. 改善 CPU 与设备的并行工作。
5. 使操作系统及时处理异步事件。


#### 6.2 中断与异常的本质区别

在 408 中，可以首先按来源区分。

##### 外部中断

来自当前 CPU 指令执行流之外的事件。

例如：

- 时钟中断。
- 键盘中断。
- 磁盘 I/O 完成。
- 网络设备中断。

一般属于异步事件。

##### 异常

通常由当前指令及其执行条件引起。

例如：

- 整数除零。
- 非法指令。
- 缺页。
- 地址访问越界。
- 访问权限错误。

一般属于同步事件。

##### 系统调用

由程序主动执行规定的入口指令发起。

例如：

- read。
- write。
- fork。
- open。

它是程序主动请求操作系统服务的机制。

在部分教材中，系统调用引发的陷入也被归入广义异常或内中断。

##### 核心对比

| 类型 | 触发来源 | 同步性 | 是否主动请求内核服务 |
|---|---|---|---|
| 外部中断 | CPU 外部事件 | 通常异步 | 否 |
| 普通异常 | 当前指令或执行条件 | 同步 | 否 |
| 系统调用 | 程序主动执行入口指令 | 同步 | 是 |


#### 6.3 什么是同步与异步？

这是区分中断和异常的关键。

##### 同步

事件与当前指令的执行直接相关。

例如：

    DIV R1, R2

如果：

$$
R_2=0
$$

那么执行这条除法指令就会触发除零异常。

在相同处理器状态和执行条件下，异常可以在确定的位置被触发。

##### 异步

事件与当前正在执行的指令通常没有直接关系。

例如：

CPU 正在执行加法：

    ADD R1, R2

突然磁盘完成一次读取。

磁盘向 CPU 发出中断请求。

这与当前 ADD 指令本身无关。

因此属于异步事件。


#### 6.4 外部中断的分类

##### ① 可屏蔽中断

Maskable Interrupt。

在允许的情况下，可以通过中断屏蔽机制暂时禁止响应。

例如部分普通设备中断。

##### ② 不可屏蔽中断

Non-Maskable Interrupt。

通常用于较严重、需要及时响应的硬件事件。

其响应不受普通可屏蔽中断允许位的控制。

但具体行为仍依赖处理器体系结构。

##### 注意

**中断请求出现，不等于 CPU 立即响应。**

例如：

设备完成 I/O 后发出 IRQ。

CPU 可能需要：

- 完成当前指令。
- 检查中断允许状态。
- 判断中断优先级。
- 判断是否已经存在更高优先级事件。

满足响应条件以后才进入中断处理。


#### 6.5 中断处理的完整过程

```text
用户程序正在执行
       │
       ▼
外部设备产生中断请求
       │
       ▼
CPU 检查中断响应条件
       │
       ▼
硬件保存必要的断点和处理器状态
       │
       ▼
CPU 转入内核处理入口
       │
       ▼
根据中断向量确定处理程序
       │
       ▼
操作系统保存必要的软件现场
       │
       ▼
执行中断服务程序 ISR
       │
       ▼
必要时唤醒进程或触发调度
       │
       ▼
恢复相应执行上下文
       │
       ▼
中断返回
```

这一过程有两个非常重要的考点：

**第一：哪些操作由硬件完成？**

**第二：哪些操作由操作系统软件完成？**


#### 6.6 硬件与操作系统的分工

| 操作 | 典型完成者 |
|---|---|
| 检测和响应中断 | CPU 硬件 |
| 保存必要的 PC / PSW 状态 | CPU 硬件机制 |
| 进入受控中断入口 | CPU 硬件机制 |
| 根据向量机制定位处理入口 | 硬件机制及预先配置的表 |
| 保存额外通用寄存器 | 操作系统软件 |
| 执行中断服务程序 | 操作系统软件 |
| 更新设备和内核状态 | 操作系统软件 |
| 唤醒等待进程 | 操作系统软件 |
| 判断是否调度其他进程 | 操作系统软件 |
| 执行规定的中断返回机制 | 软件发起、硬件恢复关键状态 |

必须理解：

不同处理器保存的具体状态可能不同。

但是 408 常规判断是：

**关键断点和处理器状态由硬件保存。**

**额外通用寄存器和软件上下文通常由操作系统保存。**


#### 6.7 为什么 PC 必须由硬件保存？

PC（程序计数器）记录程序执行位置。

中断发生时，CPU 即将进入中断处理程序。

如果不保存原来的执行位置：

就无法正确恢复原程序。

例如：

```text
100：ADD
104：SUB
108：MUL
112：DIV
```

假设：

CPU 执行完地址 104 的指令后响应外部中断。

那么中断结束后：

通常应从地址 108 的指令继续执行。

硬件必须可靠记录这个返回位置。


#### 6.8 PSW 为什么必须保存？

PSW（Program Status Word，程序状态字）或处理器中的等价状态包含：

- 条件标志。
- 中断相关状态。
- 处理器工作模式等控制信息。

普通函数调用通常需要保存返回地址。

但中断返回还需要恢复中断前的处理器状态。

所以：

**中断处理与普通函数调用都需要保存返回位置，但中断通常还必须保存、恢复关键处理器状态。**

##### 真题：2012 年

中断处理和子程序调用都需要保护现场。

中断处理一定要保存，而普通子程序调用通常不需要保存的是：

A. PC

B. PSW

C. 通用数据寄存器

D. 通用地址寄存器

**答案：B**

解析：

PC：

普通函数调用也需要记录返回位置。

PSW：

中断返回必须正确恢复处理器模式等关键状态。

普通函数调用通常不要求保存完整的处理器状态字。

因此选 B。


#### 6.9 真题：2015 年

处理外部中断时，应该由操作系统保存的是：

A. PC 的内容

B. 通用寄存器的内容

C. TLB 中的内容

D. Cache 中的内容

**答案：B**

分析：

A：

中断入口的必要返回位置由硬件负责保存。

B：

通用寄存器的额外现场保护通常由操作系统完成。

C：

中断不意味着必须清空并保存全部 TLB。

D：

中断也不需要保存整个 Cache 的内容。

因此选 B。

##### 解题口诀

**硬件保关键断点，软件保额外现场。**


### 七、异常机制

#### 7.1 异常的三种典型类型

经典分类：

1. Fault。
2. Trap。
3. Abort。

<Tabs items={["Fault 故障", "Trap 陷阱", "Abort 终止"]} defaultIndex={0}>
  <Tab value="Fault 故障">

##### ① Fault：故障

典型特点：

由当前指令执行时检测到的条件引起。

如果故障可以修复，通常可以重新执行引发故障的指令。

典型例子：

**缺页异常。**

  </Tab>
  <Tab value="Trap 陷阱">

##### ② Trap：陷阱

通常是在规定的执行点触发的异常。

系统调用入口是常见例子。

在经典分类中，Trap 处理后通常从后继执行位置继续。

但具体返回地址语义由体系结构规定。

  </Tab>
  <Tab value="Abort 终止">

##### ③ Abort：终止性异常

通常表示严重错误，难以精确恢复当前指令执行。

例如某些严重硬件错误。

  </Tab>
</Tabs>

##### 对比

| 类型 | 典型情况 | 处理后的位置 |
|---|---|---|
| Fault | 缺页 | 可修复时通常重新执行故障指令 |
| Trap | 系统调用 | 通常从规定的后继位置继续 |
| Abort | 严重错误 | 通常无法按普通方式恢复 |


#### 7.2 为什么缺页属于异常？

假设某个程序执行：

    MOV R0, [0x12345000]

CPU 尝试读取虚拟地址：

    0x12345000

MMU 检查页表。

发现：

该虚拟页属于合法地址空间，但是当前没有驻留在物理内存中。

于是：

触发缺页异常。

过程：

```text
执行访存指令
      │
      ▼
MMU 地址转换
      │
      ▼
发现页面不在主存
      │
      ▼
触发缺页异常
      │
      ▼
进入内核态
      │
      ▼
操作系统定位目标页面
      │
      ▼
必要时从外存调入页面
      │
      ▼
更新页表
      │
      ▼
重新执行产生缺页的指令
```

为什么不是外部中断？

因为缺页由当前执行的访存指令直接触发。

因此是同步异常。

##### 必须区分三种情况

**情况一：合法地址，但目标页不在内存。**

产生缺页异常。

内核可能调入页面后恢复运行。

**情况二：地址不属于进程允许访问的范围。**

可能产生地址或保护异常。

通常不能简单地通过调页恢复。

**情况三：页面存在，但访问权限不允许。**

例如向只读页面写入数据。

可能产生保护异常。

某些特殊情况如写时复制可以由内核处理后恢复，但普通非法写入通常导致错误处理。


#### 7.3 TLB Miss 不一定等于缺页异常

这是结合计算机组成原理的一个重要交叉考点。

TLB 用来缓存地址转换信息。

TLB 未命中只表示：

所需地址转换信息没有在 TLB 中找到。

接下来可能：

1. 查询页表。
2. 找到有效页表项。
3. 将地址转换信息加入 TLB。
4. 继续执行。

只有目标页面未驻留，或者出现其他地址异常条件时，才需要对应的异常处理。

注意：

不同体系结构可能使用硬件或软件方式处理 TLB 未命中。

所以：

**TLB Miss 不必然导致操作系统进行磁盘换页。**


#### 7.4 外部中断与缺页异常的返回位置

##### 外部中断

假设：

```text
100：ADD
104：SUB
108：MUL
```

执行完 SUB 后响应外部中断。

一般返回：

地址 108。

因为：

ADD、SUB 已经完成。

##### 缺页异常

假设：

```text
100：ADD
104：LOAD R1, [addr]
108：MUL
```

执行 LOAD 时发生缺页。

内核调入页面后：

需要重新执行 LOAD。

因此通常返回地址 104。

##### 系统调用

假设：

```text
100：准备参数
104：SYSCALL
108：继续执行
```

系统调用完成后：

通常从规定的后继位置继续执行。

这里一般是地址 108。

##### 总结

| 事件 | 典型返回位置 |
|---|---|
| 外部中断 | 下一条尚未执行的指令 |
| 可恢复的缺页 Fault | 重新执行故障指令 |
| 系统调用 Trap | 系统调用之后的执行位置 |
| 严重 Abort | 通常无法正常恢复 |


### 八、中断发生时 CPU 一定处于内核态吗？

这是 2024 年真题的核心。

需要严格区分：

**中断发生的时刻。**

与：

**中断处理程序开始执行的时刻。**

##### 情况一：中断发生时

CPU 可能正在：

- 用户态执行应用程序。
- 内核态执行内核代码。

所以：

中断发生时，CPU 不一定处于内核态。

##### 情况二：中断处理程序执行时

在 408 通常讨论的操作系统模型中：

中断处理程序在内核态执行。

##### 真题：2024 年

下面关于中断、异常和系统调用的叙述，错误的是：

A. 中断或异常发生时，CPU 处于内核态。

B. 每个系统调用都有对应的内核服务例程。

C. 中断处理程序开始执行时，CPU 处于内核态。

D. 系统添加需要中断驱动的新类型设备时，需注册相应的中断服务例程。

**答案：A**

原因：

中断或者异常可能在用户态执行期间发生。

例如：

用户程序正在执行普通计算。

此时时钟中断请求到来。

因此不能说：

“中断发生时 CPU 一定处于内核态。”

但是 CPU 进入中断服务程序执行后，需要具备内核处理权限。

##### 最容易犯的错误

错误：

中断发生 = 已经进入内核态。

正确：

```text
CPU 可能处于用户态
        ↓
中断请求到来
        ↓
CPU 响应中断
        ↓
执行受控状态保存与模式切换
        ↓
内核态执行中断处理程序
```


## 第六部分 系统调用与进程上下文切换

### 九、系统调用

#### 9.1 为什么需要系统调用？

用户态不能直接控制受保护的系统资源。

但应用程序又需要：

- 文件读写。
- 进程创建。
- 网络通信。
- 内存管理。
- 设备服务。

因此：

操作系统提供系统调用接口。

系统调用是一种：

**用户程序受控请求内核服务的机制。**


#### 9.2 系统调用完整过程

以文件读取为例：

    read(fd, buffer, 100)

典型流程：

```text
用户程序
    │
    ▼
准备系统调用号和参数
    │
    ▼
执行系统调用入口指令
    │
    ▼
CPU 保存必要状态并进入内核态
    │
    ▼
根据系统调用号分派服务
    │
    ▼
检查参数和访问权限
    │
    ▼
执行对应内核服务
    │
    ▼
设置返回结果
    │
    ▼
恢复用户执行状态
    │
    ▼
返回用户态
```

注意：

系统调用的具体参数传递方式取决于体系结构和 ABI。

常见方式：

- 寄存器。
- 栈。
- 参数块及其地址。


#### 9.3 真题：2017 年

系统调用过程包括：

Ⅰ. 返回用户态。

Ⅱ. 执行 Trap 指令。

Ⅲ. 传递系统调用参数。

Ⅳ. 执行内核服务程序。

正确顺序是什么？

**答案：Ⅲ → Ⅱ → Ⅳ → Ⅰ。**

原因：

第一步：

必须先准备参数。

第二步：

执行系统调用入口指令。

第三步：

内核根据系统调用号执行服务。

第四步：

完成服务后返回用户态。

##### 解题口诀

**传参 → 陷入 → 服务 → 返回。**


#### 9.4 系统调用与普通函数调用的区别

| 比较 | 普通函数调用 | 系统调用 |
|---|---|---|
| 是否一定进入内核 | 否 | 正常执行内核服务时需要 |
| 是否涉及权限转换 | 通常否 | 用户态发起时需要 |
| 是否由 OS 提供服务 | 不一定 | 是 |
| 是否可能阻塞 | 可能 | 可能 |
| 是否必然切换进程 | 否 | 否 |

##### 例子一：sin()

    double y = sin(1.0);

通常在用户态执行。

不需要请求操作系统提供内核服务。

##### 例子二：read()

    read(fd, buf, 100);

通常通过相应系统调用进入内核。

因为读取文件需要操作系统协调文件系统和设备资源。

##### 注意

程序员调用的 `read()` 通常是库函数封装入口。

它内部再通过系统调用机制请求内核。

因此：

**库函数调用与系统调用并非严格一一对应。**


#### 9.5 真题：2013 年

会导致用户进程由用户态进入内核态的操作：

Ⅰ. 整数除以零。

Ⅱ. 调用 sin()。

Ⅲ. read 系统调用。

**答案：Ⅰ、Ⅲ。**

分析：

Ⅰ：

除零会导致同步异常。

需要进入异常处理机制。

Ⅱ：

普通数学函数通常在用户态完成。

Ⅲ：

read 请求内核服务。

需要进入内核态。

##### 统一判断方法

看到一个操作：

先问：

**它是普通用户态计算，还是需要内核介入的异常或系统服务？**


#### 9.6 哪些操作属于系统调用？

##### 典型系统调用服务

- 创建进程。
- 终止进程。
- 打开文件。
- 读取文件。
- 写入文件。
- 请求内存映射。
- 创建通信端点。
- 请求设备服务。

##### 不要直接等同于系统调用的操作

- 进程调度。
- 页置换。
- 中断处理。
- 普通算术运算。
- 普通随机数算法。

例如：

进程调度是内核内部机制。

它不意味着应用程序必须主动发起某个“调度系统调用”。

页置换通常是内存管理机制在需要时执行的操作。

也不需要用户程序主动请求。


#### 9.7 真题：2021 年

下列操作通过系统调用完成的是：

A. 页置换。

B. 进程调度。

C. 创建新进程。

D. 生成随机整数。

**答案：C**

原因：

创建进程涉及：

- 建立进程控制结构。
- 分配必要资源。
- 初始化执行上下文。
- 建立地址空间等。

用户程序需要请求操作系统完成相关服务。

而：

页置换属于内核内存管理机制。

进程调度属于内核调度机制。

随机整数可以通过普通算法生成。


### 十、用户态切换与进程切换

<Callout type="idea" title="三种变化不能画等号">

模式切换、进程状态转换和进程上下文切换是不同概念；发生系统调用或外部中断不必然发生进程切换。

</Callout>


#### 10.1 三个概念必须严格区分

① 用户态与内核态的模式切换。

② 进程状态转换。

③ 进程上下文切换。

它们不是同一个概念。

##### ① 模式切换

改变 CPU 当前执行权限。

例如：

```text
用户态
  ↓
系统调用
  ↓
内核态
  ↓
系统调用返回
  ↓
用户态
```

期间：

可能始终属于同一个进程。

##### ② 进程状态转换

例如：

```text
运行态
  ↓
等待 I/O
  ↓
阻塞态
```

状态转换描述进程是否能够继续占用 CPU。

##### ③ 进程上下文切换

CPU 从一个进程转去执行另一个进程。

例如：

```text
进程 A 正在运行
        ↓
保存 A 的必要执行上下文
        ↓
选择进程 B
        ↓
恢复 B 的必要执行上下文
        ↓
运行 B
```


#### 10.2 系统调用一定导致进程切换吗？

**不一定。**

例如：

程序请求获取当前进程标识。

内核可以快速完成服务。

然后返回原进程。

```text
进程 A 用户态
      ↓
进程 A 内核态
      ↓
进程 A 用户态
```

没有发生进程切换。

但如果：

进程 A 调用阻塞式 read()，需要等待尚未到达的数据。

可能发生：

```text
进程 A 用户态
      ↓
进程 A 内核态
      ↓
进程 A 阻塞
      ↓
调度器选择 B
      ↓
进程 B 运行
```

此时才真正发生进程切换。

##### 核心结论

**系统调用一定要通过受控机制进入内核服务，但不一定导致进程切换。**


#### 10.3 中断一定导致进程切换吗？

**不一定。**

例如：

进程 A 正在运行。

键盘产生中断。

中断处理程序处理完成。

如果没有必要重新调度：

CPU 仍然可以返回进程 A。

因此：

中断可以产生权限模式变化，却不一定产生进程切换。


#### 10.4 进程切换一定需要内核参与吗？

在 408 通常讨论的操作系统模型下：

**需要。**

原因：

进程切换涉及：

- 保存进程上下文。
- 更新进程状态。
- 切换必要的地址空间状态。
- 执行调度决策。
- 恢复新进程上下文。

这些工作需要操作系统受保护地完成。

但要注意：

并不是每次进入内核态都必然发生进程切换。


#### 10.5 真题：2012 年

下列事件不可能在用户态完成的是：

A. 系统调用。

B. 外部中断。

C. 进程切换。

D. 缺页。

**答案：C**

理解：

A：

用户态可以发起系统调用。

B：

用户程序执行时可以发生外部中断。

C：

真正的进程上下文切换需要内核参与。

D：

用户程序访存时可以触发缺页异常。

需要区分：

**事件在用户态发生，与事件由用户态代码完成处理，不是同一个概念。**


#### 10.6 真题：2023 年

下列操作完成时，导致 CPU 从内核态转为用户态的是：

A. 阻塞进程。

B. 执行 CPU 调度。

C. 唤醒进程。

D. 执行系统调用。

**答案：D**

解析：

阻塞进程、进程调度、唤醒进程都是内核操作。

但它们本身不必立即返回用户态。

系统调用正常完成后：

通常通过系统调用返回机制恢复用户程序执行。

因此 D 正确。

注意题目中的：

**“操作完成时”。**

如果题目问：

“系统调用开始时发生什么？”

答案应是：

用户态进入内核态。

如果题目问：

“系统调用完成并返回时发生什么？”

答案是：

内核态返回用户态。


## 第七部分 程序的链接、装入与内存映像

### 十一、程序如何从源代码变成运行中的进程？

这是本章容易被忽视，但应掌握的知识。

#### 11.1 程序运行流程

```text
源程序
   │
   ▼
编译
   │
   ▼
目标文件
   │
   ▼
链接
   │
   ▼
可执行文件
   │
   ▼
装入
   │
   ▼
建立进程内存映像
   │
   ▼
开始执行
```

例如：

    main.c
      ↓
    main.o
      ↓
    a.out
      ↓
    装入内存
      ↓
    运行进程

需要特别区分：

**程序是静态的。**

**进程是程序的一次执行。**

同一个可执行文件可以产生多个进程。


### 十二、静态链接与动态链接

#### 12.1 链接的本质

链接主要解决：

- 多个目标模块的组合。
- 符号引用解析。
- 必要的地址重定位。
- 库代码的组织。

例如：

    main.o
    math.o
    utils.o

链接器将它们组合成可执行程序。


#### 12.2 静态链接

静态链接：

在链接阶段，把所需静态库代码组合进可执行文件。

例如：

```text
main.o
   +
libmath.a
   ↓
静态链接
   ↓
可执行文件
```

优点：

- 对相应共享库的运行时依赖较少。
- 部署时不必再寻找对应动态库。
- 库代码随程序一起分发。

缺点：

- 可执行文件通常较大。
- 不同程序可能重复保存相同库代码。
- 静态链接的库更新后，通常需要重新链接程序。

注意：

静态链接不意味着生成的程序可以跨任意 CPU 架构和操作系统运行。


#### 12.3 动态链接

动态链接：

共享库代码独立存在。

在程序装入或执行过程中完成需要的符号绑定。

例如：

    libc.so
    kernel32.dll

优点：

- 可执行文件通常较小。
- 多个进程可共享只读库代码页。
- 有利于库的统一维护。

缺点：

- 运行环境需要提供兼容的动态库。
- 可能出现库缺失。
- 可能出现版本不兼容。

##### 对比

| 项目 | 静态链接 | 动态链接 |
|---|---|---|
| 库代码 | 链接时组合进程序 | 独立保存 |
| 可执行文件 | 通常较大 | 通常较小 |
| 运行时库依赖 | 较少 | 较多 |
| 共享库代码 | 相对不方便 | 相对方便 |
| 库更新 | 通常需重新链接 | 通常更方便 |

##### 高频易错点

**动态链接不等于动态装入。**

链接主要解决：

程序模块和符号如何组合。

装入主要解决：

程序如何进入内存并建立可执行的地址环境。


### 十三、程序装入与地址重定位

#### 13.1 为什么需要重定位？

假设：

程序中的一条指令需要访问逻辑地址 100。

但是程序最终被装入物理地址 4000 开始的内存区域。

那么：

该数据对应的物理位置可能是：

$$
4000+100=4100
$$

这就需要地址重定位。


#### 13.2 绝对装入

程序编译或链接时已经确定装入位置。

生成的地址直接对应预期的内存位置。

特点：

- 简单。
- 地址位置固定。
- 灵活性差。

适合早期简单系统或地址固定的特殊环境。


#### 13.3 静态重定位

静态重定位：

**装入时一次性完成地址修正。**

例如：

程序的相对地址：

$$
A=120
$$

装入起始地址：

$$
B=5000
$$

修正后：

$$
A_{\mathrm{physical}}=B+A
$$

$$
A_{\mathrm{physical}}=5120
$$

装入程序对需要重定位的地址进行修正。

之后：

运行期间通常不再通过这种方式整体修改程序内部地址。

缺点：

程序装入后整体移动不够灵活。


#### 13.4 动态重定位

动态重定位：

**在程序执行时，通过地址转换机制获得实际物理地址。**

例如：

```text
逻辑地址 120
      │
      ▼
地址转换硬件
      │
      ▼
物理地址 5120
```

早期可以使用：

重定位寄存器。

现代系统主要依靠：

MMU、页表等硬件机制。

##### 动态重定位的优点

- 地址绑定灵活。
- 有利于进程地址空间隔离。
- 支持更复杂的内存管理。
- 可以结合分页、分段和虚拟存储机制。

##### 三种方式比较

| 方式 | 地址绑定时间 | 灵活性 |
|---|---|---|
| 绝对装入 | 编译/链接时 | 低 |
| 静态重定位 | 装入时 | 较低 |
| 动态重定位 | 运行时 | 高 |

##### 高频判断

静态重定位：

**装入时修改地址。**

动态重定位：

**运行时进行地址转换。**

不要因为名字里都有“动态”就把动态链接和动态重定位混为一谈。


### 十四、进程的内存映像

#### 14.1 典型进程地址空间

```text
高地址
┌──────────────────────┐
│                      │
│        Stack         │
│          ↓           │
│                      │
├──────────────────────┤
│                      │
│      mmap 区域       │
│       共享库等       │
│                      │
├──────────────────────┤
│                      │
│          ↑           │
│         Heap         │
│                      │
├──────────────────────┤
│         BSS          │
├──────────────────────┤
│         Data         │
├──────────────────────┤
│         Text         │
└──────────────────────┘
低地址
```

这是用于理解的典型示意图。

不同操作系统及体系结构的具体内存布局可能不同。


#### 14.2 Text 段

通常保存：

程序机器指令。

典型特点：

- 通常可执行。
- 常为只读。
- 可允许多个进程共享。


#### 14.3 Data 段

通常保存：

已经初始化的全局变量和静态变量。

例如：


```c
int a = 10;

static int b = 20;

```

典型情况下：

a、b 属于已初始化数据区域。


#### 14.4 BSS 段

通常保存：

未显式初始化或零初始化的全局变量、静态变量。

例如：


```c
int a;

static int b;

```

在典型 C 程序模型中：

这些对象属于 BSS。

BSS 在运行时建立并按规定初始化。


#### 14.5 Heap：堆

保存动态分配的对象。

例如：

    int *p = malloc(100 * sizeof(int));

这里需要区分：

- `p` 是一个局部指针变量时，通常位于栈或被优化到寄存器。
- `malloc()` 申请的动态对象通常位于堆管理区域。

因此：

**指针变量存放的位置，不等于它指向的数据存放位置。**


#### 14.6 Stack：栈

通常保存：

- 函数调用相关信息。
- 返回地址。
- 局部自动变量。
- 某些寄存器保存值。

但编译器可能把部分局部变量放入寄存器或优化掉。

所以：

“所有局部变量一定实际存放在栈中”并不严格。


#### 14.7 综合例题：变量存储位置

```c
int g1 = 100;
int g2;

static int s1 = 20;
static int s2;

int main(void)
{
    int x = 10;

    static int y = 30;

    int *p = malloc(100);

    return 0;
}
```

逐项分析：

| 对象 | 典型位置 |
|---|---|
| 程序机器代码 | Text |
| g1 | Data |
| g2 | BSS |
| s1 | Data |
| s2 | BSS |
| x | Stack 或寄存器 |
| y | Data |
| p 指针变量 | Stack 或寄存器 |
| malloc 申请的内存 | Heap |

特别注意：

函数内部的 static 变量不因为写在函数里面就位于栈。

static 局部变量具有静态存储期。


#### 14.8 虚拟地址与物理地址

进程看到的通常是自己的虚拟地址空间。

假设：

进程 A 访问虚拟地址：

    0x1000

进程 B 也访问：

    0x1000

这两个地址在数值上相同。

但可能映射到不同的物理页框。

例如：

```text
进程 A：

虚拟地址 0x1000
       ↓
物理地址 0xA000


进程 B：

虚拟地址 0x1000
       ↓
物理地址 0xF000
```

因此：

**不同进程使用相同虚拟地址，不意味着访问同一个物理地址。**

同时：

连续虚拟地址不要求对应连续的物理内存。

这一点是后续分页存储管理的基础。


## 第八部分 操作系统结构

### 十五、分层结构与模块化结构

#### 15.1 分层结构

把操作系统划分成多个层次。

上层利用下层提供的接口。

例如：

```text
用户应用
   ↓
文件系统
   ↓
进程与内存管理
   ↓
设备控制
   ↓
硬件
```

优点：

- 结构清晰。
- 易于调试。
- 易于验证。
- 层次接口明确。

缺点：

- 层次划分不容易。
- 有些操作跨层调用较复杂。
- 严格层次结构可能产生额外开销。


#### 15.2 模块化结构

把操作系统划分成相对独立的功能模块。

例如：

- 内存管理模块。
- 进程管理模块。
- 文件系统模块。
- 网络模块。
- 设备驱动模块。

优点：

- 模块职责清晰。
- 便于维护。
- 便于扩展。
- 某些实现支持动态加载模块。

注意：

模块化结构不等于微内核。

宏内核也可以采用模块化设计。

Linux 就是典型例子。


### 十六、宏内核与微内核

#### 16.1 宏内核

Monolithic Kernel。

将大量操作系统核心功能放在内核空间。

包括：

- 进程管理。
- 内存管理。
- 文件系统。
- 设备驱动。
- 网络协议栈。
- 其他内核服务。

典型代表：

Linux 和传统 UNIX 内核。

##### 结构

```text
用户程序
    │
    ▼
系统调用入口
    │
    ▼
┌────────────────────────┐
│        宏内核          │
│                        │
│  进程管理  内存管理     │
│  文件系统  网络协议栈   │
│  设备驱动  IPC         │
└────────────────────────┘
    │
    ▼
硬件
```

##### 优点

- 内核服务之间可以高效调用。
- 内核内部通信开销通常较小。
- 系统调用路径相对直接。
- 通常具有较好的性能。

##### 缺点

- 内核规模较大。
- 故障影响范围可能较大。
- 内核代码复杂。
- 保护边界较少。

例如：

一个存在严重缺陷的内核驱动可能导致整个操作系统崩溃。


#### 16.2 微内核

Microkernel。

只在内核态保留最基本的机制。

例如：

- 基本线程调度。
- 低层地址空间管理。
- IPC。
- 必要的中断与陷入机制。

把更多服务移到用户态。

例如：

- 文件服务。
- 部分设备驱动。
- 网络服务。

##### 结构

```text
用户程序
    │
    ▼
用户态系统服务
    │
    ├── 文件服务器
    ├── 设备服务器
    └── 网络服务器
    │
    ▼
┌──────────────────────┐
│       微内核         │
│                      │
│ 基本调度             │
│ IPC                  │
│ 基础内存管理         │
│ 必要中断机制         │
└──────────────────────┘
    │
    ▼
硬件
```

##### 微内核为什么可靠性通常更好？

因为：

文件系统或设备驱动等部分服务运行在独立用户态进程中。

一个服务出现问题时：

故障更可能被限制在该服务的保护域内。

不会必然直接破坏整个内核。

因此：

- 故障隔离潜力较好。
- 安全性潜力较高。
- 可靠性潜力较高。
- 服务扩展和维护较方便。


#### 16.3 微内核为什么可能性能较低？

考虑一个文件读取操作。

##### 宏内核

```text
用户进程
   ↓
系统调用
   ↓
内核文件系统
   ↓
设备驱动
   ↓
返回
```

大量服务可以在内核空间内部调用。

##### 微内核

```text
用户进程
   ↓
IPC
   ↓
文件服务器
   ↓
IPC
   ↓
设备服务
   ↓
返回
```

可能涉及：

- 更多 IPC。
- 更多权限模式转换。
- 更多调度操作。
- 更多数据传递。

因此可能产生额外开销。

但不能绝对断言：

所有微内核系统都一定比所有宏内核系统慢。

具体性能依赖实现和工作负载。


#### 16.4 宏内核与微内核对比

| 属性 | 宏内核 | 微内核 |
|---|---|---|
| 内核规模 | 较大 | 较小 |
| 内核服务数量 | 多 | 少 |
| 文件系统 | 常在内核态 | 可放在用户态 |
| 驱动程序 | 常在内核态 | 部分可放在用户态 |
| 服务通信 | 内核内部调用较多 | IPC 较多 |
| 性能 | 通常较高 | 可能存在额外通信开销 |
| 可靠性潜力 | 相对较弱 | 较高 |
| 安全隔离潜力 | 相对较弱 | 较高 |
| 扩展性潜力 | 依赖模块设计 | 通常较好 |


#### 16.5 真题：2023 年

与宏内核相比，微内核具有：

Ⅰ. 较好的性能。

Ⅱ. 较高的可靠性。

Ⅲ. 较高的安全性。

Ⅳ. 较强的可扩展性。

**答案：Ⅱ、Ⅲ、Ⅳ。**

分析：

Ⅰ：

错误。

微内核的 IPC 等机制可能带来额外开销。

Ⅱ：

正确。

用户态服务隔离有助于提高可靠性。

Ⅲ：

正确。

更小的可信计算基及服务隔离有助于提高安全性。

Ⅳ：

正确。

用户态服务更便于维护和替换。

##### 解题方法

看到微内核：

优先联想：

**内核小、服务隔离、IPC 多、可靠性高、安全性潜力高、可扩展性强。**

看到宏内核：

优先联想：

**内核功能多、内部调用直接、通常性能较好，但故障隔离相对较弱。**


### 十七、外核

外核（Exokernel）是一种更强调底层资源保护和安全复用的内核结构。

核心思想：

**内核尽量不强制提供复杂的高层抽象。**

主要保留：

- 底层资源保护。
- 安全资源复用。
- 必要资源授权机制。

更多资源管理策略和抽象由用户态 Library OS 实现。

##### 结构

```text
应用程序
    ↓
Library OS
    ↓
Exokernel
    ↓
硬件
```

##### 与微内核的区别

微内核：

主要通过把系统服务移到用户态来减少内核功能。

外核：

进一步强调减少强制性的高层资源抽象，让应用或库操作系统根据需求管理已授权的资源。

##### 高频判断

“外核是一种不同于宏内核和微内核的操作系统内核架构。”

按通常教材分类：

正确。


## 第九部分 操作系统的引导过程

### 十八、为什么计算机开机需要引导程序？

操作系统内核通常保存在外存中。

但计算机加电以后：

CPU 必须先执行某个位置上的指令。

此时：

操作系统内核尚未装入主存。

因此必须通过启动固件和引导加载程序逐步完成操作系统装入。


#### 18.1 典型启动流程

```text
计算机加电
    ↓
CPU 从规定复位入口开始执行
    ↓
BIOS / UEFI 固件
    ↓
必要硬件初始化
    ↓
选择启动设备
    ↓
加载启动程序
    ↓
Bootloader 装入 OS 内核
    ↓
CPU 转移到内核入口
    ↓
内核初始化
    ↓
启动系统服务与用户环境
```


#### 18.2 传统 BIOS + MBR 引导

经典流程：

```text
加电
  ↓
BIOS
  ↓
POST 硬件自检
  ↓
选择启动设备
  ↓
读取 MBR
  ↓
执行相应引导代码
  ↓
加载后续启动程序
  ↓
加载 OS 内核
```

##### MBR 的典型结构

传统 MBR 位于磁盘起始扇区。

经典 512 字节 MBR 布局：

| 内容 | 字节数 |
|---|---:|
| 引导代码区域 | 446 |
| 分区表 | 64 |
| 结束标志 | 2 |
| 合计 | 512 |

其中：

结束标志通常是：

    0x55AA

注意：

这是经典 MBR 扇区布局。

实际引导方案还可能使用后续扇区等其他空间。


#### 18.3 UEFI 引导

现代计算机通常使用 UEFI 固件。

典型流程：

```text
加电
  ↓
UEFI 固件
  ↓
硬件初始化
  ↓
定位 EFI 启动程序
  ↓
执行 .efi 程序
  ↓
加载操作系统内核
```

UEFI 系统常见：

- GPT 分区表。
- EFI System Partition（ESP）。
- `.efi` 启动程序。

##### 特别注意

GPT 是分区表格式。

UEFI 是固件及启动接口体系。

Bootloader 是引导加载程序。

这三个概念不能混淆。

UEFI 经常与 GPT 配合使用，但不能认为 GPT 本身就是引导程序。


#### 18.4 真题：2013 年

计算机开机后，操作系统最终被加载到：

A. BIOS。

B. ROM。

C. EPROM。

D. RAM。

**答案：D**

原因：

操作系统内核通常需要装入主存后执行。

BIOS、ROM、EPROM 主要与固件存储有关。

它们不是运行中的完整操作系统内核通常所在的位置。


#### 18.5 模拟题

计算机开机后，传统 BIOS 引导过程首先完成的是：

A. 硬件自检。

B. 加载 MBR。

C. 加载分区引导记录。

D. 加载操作系统内核。

**答案：A**

因为：

在该经典 BIOS 模型中：

POST 硬件自检先于 MBR 和内核装入。

##### 注意

如果题目问：

“计算机加电后 CPU 最先执行什么？”

则更准确的答案是：

从体系结构规定的复位入口执行固件代码。

不能把 POST 误认为 CPU 执行的第一条机器指令。


## 第十部分 虚拟机与 Hypervisor

### 十九、虚拟机的基本概念

虚拟机（Virtual Machine）通过虚拟化技术构造逻辑计算机。

一个物理主机可以运行多个虚拟机。

例如：

```text
物理服务器
     │
     ▼
Hypervisor
     │
     ├── VM 1：Linux
     │
     ├── VM 2：Windows
     │
     └── VM 3：Linux
```

每个虚拟机可以拥有：

- vCPU。
- 虚拟内存。
- 虚拟磁盘。
- 虚拟网络设备。
- Guest OS。
- 应用程序。


#### 19.1 什么是 Hypervisor？

Hypervisor 又称 VMM：

Virtual Machine Monitor。

它负责：

- 创建虚拟机。
- 分配虚拟资源。
- 管理 vCPU。
- 管理客户机内存。
- 虚拟化设备。
- 隔离不同虚拟机。
- 管理敏感操作。


#### 19.2 Type 1：裸机型

直接运行在物理硬件之上。

```text
应用程序
   ↓
Guest OS
   ↓
Hypervisor
   ↓
硬件
```

特点：

通常适用于服务器和数据中心虚拟化。


#### 19.3 Type 2：宿主型

虚拟化软件运行在宿主操作系统之上。

```text
应用程序
   ↓
Guest OS
   ↓
虚拟机软件
   ↓
Host OS
   ↓
硬件
```

特点：

部署和使用方便。

但虚拟化实现需要依赖宿主操作系统的相应机制。


#### 19.4 Guest OS 可以直接控制全部物理硬件吗？

不能。

Guest OS 虽然认为自己正在管理一台计算机，但它所看到的资源受到 Hypervisor 控制。

例如：

Guest OS 修改客户机页表或执行敏感操作时：

可能需要硬件虚拟化机制或 Hypervisor 参与。

现代处理器提供了专门的硬件虚拟化支持。

例如：

- Intel VT-x。
- AMD-V。
- ARM 的相应虚拟化扩展。


#### 19.5 虚拟机与容器的区别

| 比较 | 虚拟机 | 容器 |
|---|---|---|
| 是否通常拥有独立 Guest OS 内核 | 是 | 否 |
| 主要虚拟化对象 | 机器级环境 | 操作系统级环境 |
| 隔离基础 | Hypervisor 与硬件支持等 | 命名空间、控制组等 OS 机制 |
| 典型开销 | 相对较大 | 通常较小 |
| 典型用途 | 多操作系统隔离 | 应用隔离与部署 |

##### 高频判断

Docker 容器不能简单等同于传统硬件虚拟机。

容器通常共享宿主机内核。


## 第十一部分 历年真题系统归纳

以下按第 1 章的历年真题考点整理。

重点是理解原题为什么这样考，以及如何应对变式。

### 二十、历年真题考点汇总

| 年份 | 核心考点 | 关键结论 |
|---|---|---|
| 2009 | 并发与并行 | CPU 与设备可以并行 |
| 2010 | 操作系统接口 | 应用程序接口是系统调用 |
| 2011 | 用户态程序 | 命令解释程序通常在用户态 |
| 2012 | 进程切换 | 真正切换需要内核参与 |
| 2012 | 中断现场 | PSW 是中断返回的关键状态 |
| 2013 | 模式转换 | 除零、系统调用导致陷入 |
| 2013 | 系统引导 | OS 内核最终装入 RAM |
| 2014 | 特权指令 | 关中断是特权操作 |
| 2015 | 中断现场保护 | 通用寄存器通常由软件保存 |
| 2015 | 异常判断 | 普通访存也可能引发异常 |
| 2016 | 批处理系统 | 多道批处理与中断机制 |
| 2017 | 多道程序 | 提高吞吐量和资源利用率 |
| 2017 | 系统调用顺序 | 传参→Trap→服务→返回 |
| 2018 | 多任务系统 | 单 CPU 也能实现多任务 |
| 2019 | 系统调用 | 内核服务接口不完全统一 |
| 2021 | 特权指令 | 直接 I/O 控制通常为特权 |
| 2021 | 创建进程 | 通过系统调用请求 |
| 2022 | 多道程序 | 进程越多不一定越好 |
| 2022 | CPU 工作模式 | 用户态不能执行特权指令 |
| 2022 | 系统调用分工 | 硬件保存关键状态，OS 执行服务 |
| 2023 | 模式转换 | 系统调用返回可进入用户态 |
| 2023 | 微内核 | 安全、可靠、扩展性 |
| 2023 | 中断向量表 | 适合使用数组 |
| 2024 | 中断与异常 | 发生时不一定已处于内核态 |
| 2024 | 键盘中断 | 数据通常先放入内核缓冲区 |

接下来重点分析容易出变式的题型。


#### 20.1 真题：2015 年——普通指令是否可能进入内核态？

题目：

以下指令执行时，不可能导致 CPU 从用户态变为内核态的是：

A. DIV R0, R1。

B. INT n。

C. NOT R0。

D. MOV R0, addr。

**答案：C**

逐项解析：

##### A：DIV

如果除数为零：

会触发除零异常。

因此可能进入内核态。

##### B：INT

用于产生软件中断或陷入。

能够进入相应的受控处理入口。

##### C：NOT

只对通用寄存器中的位进行取反。

不涉及：

- 内存访问。
- 特权操作。
- 显式陷入。
- 可能的算术故障条件。

在题目给定的指令语义下，不会因执行本身产生上述陷入。

因此选 C。

##### D：MOV

访问内存。

如果目标地址：

- 不存在有效映射。
- 页面未驻留。
- 访问权限不满足。

就可能触发异常。

##### 核心方法

**普通指令也可能引起异常。**

不要把：

“非特权指令”

误认为：

“绝对不会使 CPU 进入内核态的指令”。


#### 20.2 真题：2019 年——系统调用判断

判断：

Ⅰ. 系统调用服务程序在内核态执行。

Ⅱ. 系统调用可以避免用户程序直接操作受保护的外设。

Ⅲ. 不同操作系统提供完全统一的系统调用接口。

Ⅳ. 系统调用是操作系统为应用程序提供的服务接口。

**答案：Ⅰ、Ⅱ、Ⅳ。**

原因：

Ⅰ正确。

系统调用服务需要内核权限。

Ⅱ正确。

程序通过受控接口申请设备服务。

Ⅲ错误。

Windows、Linux 等操作系统的系统调用接口并不完全相同。

Ⅳ正确。

这是系统调用的核心定义。


#### 20.3 真题：2022 年——用户态能执行什么？

题目：

A. CPU 在用户态只能执行特权指令。

B. CPU 在内核态只能执行特权指令。

C. CPU 在用户态只能执行非特权指令。

D. CPU 在内核态只能执行非特权指令。

**答案：C**

原因：

用户态只能合法执行非特权指令。

内核态则可以执行：

- 特权指令。
- 非特权指令。

特别注意：

系统调用入口指令需要允许用户态执行，不能误当成只能在内核态执行的特权指令。


#### 20.4 真题：2022 年——系统调用由谁完成？

题目：

系统调用涉及：

Ⅰ. 保存断点和 PSW。

Ⅱ. 保存通用寄存器。

Ⅲ. 执行系统调用服务例程。

Ⅳ. 将 CPU 切换为内核态。

其中由操作系统软件完成的是：

**答案：Ⅱ、Ⅲ。**

解析：

Ⅰ：

必要的返回位置和处理器状态由硬件机制保存。

Ⅱ：

额外通用寄存器由内核入口代码保存。

Ⅲ：

内核执行系统调用服务例程。

Ⅳ：

权限切换由处理器硬件机制完成。

##### 高频口诀

**硬件负责受控进入，软件负责实际服务。**


#### 20.5 真题：2023 年——中断向量表的数据结构

题目：

中断向量表适合采用：

A. 数组。

B. 队列。

C. 单向链表。

D. 双向链表。

**答案：A**

原因：

中断类型号可以用于快速定位对应表项。

数组支持基于下标的高效随机访问。

例如：

    vector[interrupt_number]

访问时间通常为：

$$
O(1)
$$

而链表需要通过节点进行查找。

##### 交叉考点

这道题同时涉及：

- 计算机组成原理。
- 操作系统。
- 数据结构。

其本质是：

**中断向量表的索引访问需求与数组的随机访问特点相匹配。**


#### 20.6 真题：2024 年——键盘中断的数据存放位置

题目：

键盘中断服务例程执行结束时，输入数据通常存放在：

A. 用户缓冲区。

B. CPU 通用寄存器。

C. 内核缓冲区。

D. 键盘控制器寄存器。

**答案：C**

典型过程：

```text
用户按下按键
      ↓
键盘控制器产生数据和中断
      ↓
CPU 响应中断
      ↓
执行键盘中断处理程序
      ↓
内核获取输入数据
      ↓
放入内核管理的输入缓冲区
      ↓
后续通过读操作交付给应用程序
```

为什么不是用户缓冲区？

因为中断处理程序不能假定：

某个特定用户程序已经准备好接收数据。

操作系统需要先进行缓冲、排队与输入管理。


## 第十二部分 模拟题中的关键陷阱

模拟题不只是考概念，还会通过绝对化表述或跨章节内容设置干扰项。

### 二十一、模拟题高频易错情况

#### 21.1 陷阱一：设备中断是否立即导致权限切换？

模拟题中出现类似说法：

“外部设备 I/O 完成时，会发出中断请求，CPU 立即切换到内核态。”

该说法的严格性存在问题。

正确机制是：

设备产生中断请求。

CPU 在满足相应中断响应条件后才响应。

因此：

**设备发出中断请求，不等于 CPU 在同一个瞬间完成模式切换。**

遇到：

- 立即。
- 一定。
- 必然。
- 所有。

需要检查是否存在例外条件。


#### 21.2 陷阱二：中断是否必然引起进程切换？

答案：

**不必然。**

例如：

进程 A 执行时发生时钟中断。

内核处理后可能：

1. 继续运行 A。
2. 选择其他进程 B。

只有第二种情况才发生进程切换。


#### 21.3 陷阱三：系统调用时寄存器一定保存到 PCB 吗？

不一定。

不同操作系统可能把寄存器现场保存在：

- 内核栈。
- 陷入帧。
- 任务相关数据结构。
- 其他体系结构规定的位置。

PCB 负责保存和管理进程信息。

但不能理解为：

CPU 进入内核后，所有寄存器都必须直接写入 PCB 的固定字段。


#### 21.4 陷阱四：进入内核态时一定切换到共享内核栈吗？

不一定。

现代操作系统可能具有：

- 每线程内核栈。
- 专用中断栈。
- 每 CPU 特殊栈。
- 其他专门的异常处理栈。

因此：

“所有内核代码都使用同一个共享内核栈”

是过于绝对的表述。


#### 21.5 陷阱五：用户态是否可以读取内核地址空间？

模拟题中部分经典题的安全模型较为简化。

但现代操作系统通常必须保护内核地址空间。

不能认为：

只要不修改内核内存，用户程序就可以随意读取内核数据。

因为：

读取受保护的内核内存本身也可能导致信息泄漏。

因此一般应掌握：

**普通用户程序无权任意读取或写入受保护的内核地址空间。**


#### 21.6 陷阱六：打开文件后，任何操作都只需文件描述符吗？

不严格。

对于已经打开的文件：

    read(fd)
    write(fd)
    lseek(fd)

通常可以使用文件描述符。

但是：

    rename()
    unlink()

等操作可能仍然需要路径名或其他文件标识。

因此：

“任何文件操作都不再需要路径名”

不是严格成立的普遍结论。


#### 21.7 陷阱七：关闭文件一定立即写回所有数据吗？

不一定。

close 的主要工作包括：

- 撤销文件描述符引用。
- 更新内核打开文件状态。
- 释放相关资源。

但并不保证：

所有数据都在 close 返回之前持久化到物理存储介质。

需要区分：

- 文件关闭。
- 缓冲区刷新。
- 数据持久化。

保证持久化通常还需要考虑相应同步操作。


#### 21.8 陷阱八：分页与虚拟存储器是不是同一概念？

不是。

分页是一种内存组织与地址转换方式。

虚拟存储器通常还依赖：

- 请求调页。
- 缺页处理。
- 页面置换。
- 外存后备存储等机制。

所以：

**基本分页不一定意味着具有完整虚拟存储功能。**


#### 21.9 陷阱九：虚拟地址空间大小等于 RAM 加硬盘吗？

错误。

虚拟地址空间的大小受：

- 虚拟地址位数。
- 操作系统地址布局。
- 体系结构限制。
- 资源管理策略。

等因素影响。

不能简单认为：

$$
V=RAM+Disk
$$

这不是虚拟地址空间容量的通用公式。

### 二十二、综合题一：系统调用、中断和进程切换

单处理机系统中有两个进程：

P1 和 P2。

某时刻 P1 执行：

    read(fd, buf, 100);

假设：

1. 该操作需要从磁盘读取尚未缓存的数据。
2. 系统采用阻塞式 I/O。
3. P2 已经处于就绪态。
4. 读取操作最终正常完成。

回答：

（1）P1 执行 read 时是否需要进入内核态？

（2）P1 是否会从运行态转为阻塞态？

（3）CPU 是否可能执行 P2？

（4）磁盘完成 I/O 后属于中断还是异常？

（5）P1 被唤醒后是否立即运行？

（6）P1 最终如何继续执行？

---

<Accordions>
  <Accordion title="查看完整答案与解析">

##### 第一步：P1 发起系统调用

P1 执行 read。

系统调用入口触发：

```text
   ↓

   ↓
```

（1）需要进入内核态。

需要从磁盘读取数据，并采用阻塞式 I/O。

因此：

P1 不能立即取得结果。

（2）会阻塞。

注意：

阻塞态转为就绪态，不等于立即运行。

（5）不一定立即运行。

调度器以后重新选择 P1。

P1 恢复此前的执行上下文。

read 完成后，程序继续执行后续代码。

因此：

（6）P1 在获得 CPU 后，从规定的恢复位置继续执行。

```text
      ↓
P1 阻塞态 → 就绪态
      ↓
调度器在合适时机选择 P1
      ↓
P1 恢复运行
```

- 用户态与内核态。
- 阻塞态。
- 外部中断。
- 进程调度。

### 二十三、综合题二：缺页异常与指令恢复

#### 题目

某用户进程执行以下指令：

```text
1000：ADD R1, R2

1004：LOAD R3, [0x8000]

1008：SUB R4, R5
```

假设：

1. 地址 0x8000 属于进程合法虚拟地址空间。
2. 目标页面尚未驻留主存。
3. 系统采用请求分页。
4. 缺页能够正常处理。

回答：

（1）执行哪条指令时发生异常？

（2）属于外部中断还是内部异常？

（3）CPU 是否需要进入内核态？

（4）处理后重新执行哪条指令？

（5）一定发生进程切换吗？

---

<Accordions>
  <Accordion title="查看完整答案与解析">

##### （1）LOAD 指令

LOAD 需要读取内存。

地址转换时发现目标页未驻留。

因此触发缺页。

##### （2）同步异常

缺页由当前 LOAD 指令直接触发。

因此是同步异常。

##### （3）需要进入内核态

操作系统需要：

- 处理缺页。
- 必要时选择页框。
- 调入页面。
- 更新页表。

因此需要内核参与。

##### （4）重新执行 LOAD

缺页是可恢复 Fault。

修复后通常重新执行引起故障的访存指令。

因此返回：

    1004

不是直接跳到：

    1008

##### （5）不一定发生进程切换

如果页面已经可通过内核机制快速建立映射，且没有调度其他进程的必要：

可能仍继续运行原进程。

如果需要磁盘 I/O：

该进程可能阻塞，调度器运行其他进程。

因此不能说缺页一定发生进程切换。

##### 结论

| 问题 | 答案 |
|---|---|
| 故障指令 | LOAD |
| 事件类型 | 同步异常 |
| 是否进入内核 | 是 |
| 恢复位置 | 重新执行 LOAD |
| 是否必然切换进程 | 否 |

### 二十四、综合题三：宏内核与微内核的性能分析

#### 题目

某操作系统需要完成文件读取服务。

假设：

宏内核实现中：

- 用户态到内核态及返回的额外开销合计为 0.6 μs。
- 内核内部服务调用及管理开销为 0.4 μs。

微内核实现中：

- 服务处理本身的开销与宏内核相同，均为 0.4 μs。
- 完成相同操作额外需要 4 次 IPC。
- 每次 IPC 的平均额外开销为 0.3 μs。

忽略其他差异。

求两种实现的额外处理时间，并分析微内核的优缺点。

---

<Accordions>
  <Accordion title="查看完整答案与解析">

##### 宏内核

$$
T_{\mathrm{mono}}=0.6+0.4
$$

$$
T_{\mathrm{mono}}=1.0\ \mu s
$$

##### 微内核

在该简化模型中，假定它保留题目给出的基础开销，并额外产生 IPC 开销。

$$
T_{\mathrm{micro}}=0.6+0.4+4\times0.3
$$

$$
T_{\mathrm{micro}}=2.2\ \mu s
$$

##### 时间差

$$
\Delta T=2.2-1.0
$$

$$
\Delta T=1.2\ \mu s
$$

##### 相对倍数

$$
\frac{T_{\mathrm{micro}}}{T_{\mathrm{mono}}}=2.2
$$

在这个特定的简化模型中：

微内核路径额外处理时间是宏内核的 2.2 倍。

##### 为什么微内核仍然有价值？

因为性能不是唯一目标。

微内核可能具有：

- 更好的故障隔离。
- 更小的内核可信计算基。
- 更好的服务模块化。
- 更方便的独立维护。
- 较高的可靠性和安全性潜力。

##### 重要提醒

这只是用于理解 IPC 开销的构造模型。

不能把 2.2 倍作为实际系统中宏内核与微内核的固定性能比例。

实际 IPC 优化、缓存、硬件支持和服务设计都会影响结果。

### 二十五、综合题四：启动、装入和地址转换

#### 题目

某计算机启动后，需要执行程序 P。

假设：

1. 程序 P 存放在磁盘中。
2. 程序采用静态链接。
3. 操作系统采用分页虚拟内存。
4. 程序的虚拟地址为 0x1000。
5. 对应页最终映射到某个物理页框。

回答：

（1）程序执行前是否必须经过操作系统的装入过程？

（2）静态链接是否意味着程序不需要地址转换？

（3）虚拟地址 0x1000 是否必须对应物理地址 0x1000？

（4）进程地址空间是否必须物理连续？

（5）其他进程能否也使用虚拟地址 0x1000？

<Accordions>
  <Accordion title="查看完整答案与解析">

##### （1）需要建立运行环境

操作系统需要建立进程执行所需的地址空间、映射和初始执行状态。

但现代系统不一定一次性把所有程序页面读入 RAM。

可能采用按需装入。

静态链接解决库和目标模块的组合问题。

两者不能混淆。

虚拟地址与物理地址通过页表映射。

数值不必相同。

##### （4）不必须

分页可以把连续虚拟地址映射到离散物理页框。

##### （5）可以

不同进程拥有独立地址空间。

可以使用相同的虚拟地址值，却映射到不同物理位置。

## 第十五部分 本章通用做题方法

### 二十七、遇到操作系统概述题如何判断？

建议形成固定的判断流程。

<Steps>
  <Step>

### 第一步：识别题目考查对象

题目是关于：

- 资源管理？
- CPU 权限？
- 中断？
- 异常？
- 系统调用？
- 进程切换？
- 程序装入？
- 内核结构？

先确定所属知识点。


  </Step>
  <Step>

### 第二步：判断是否涉及受保护资源

如果涉及：

- 中断控制。
- 页表修改。
- 设备直接控制。
- 进程调度。
- 系统级资源分配。

通常需要内核权限。

如果只是：

- 普通运算。
- 通用寄存器操作。
- 合法访存。
- 普通函数调用。

通常可以在用户态完成。


  </Step>
  <Step>

### 第三步：判断事件来源

```text
当前指令本身引起？
        │
        ├── 是
        │    ├── 主动请求服务 → 系统调用
        │    └── 执行条件出错 → 异常
        │
        └── 否
             └── 外部设备等事件 → 外部中断
```


  </Step>
  <Step>

### 第四步：判断是否需要进程切换

不要直接认为：

“进入内核态 = 进程切换”。

应检查：

- 原进程是否阻塞？
- 时间片是否耗尽？
- 是否有更高优先级进程需要运行？
- 调度器是否决定更换运行主体？

只有真正从一个进程切换到另一个进程，才发生相应的进程上下文切换。


  </Step>
  <Step>

### 第五步：判断返回位置

如果是：

外部中断：

通常从下一条尚未执行的指令继续。

可恢复 Fault：

通常重新执行引发故障的指令。

系统调用 Trap：

通常从规定的后继执行位置继续。

Abort：

通常无法按普通方式恢复。


  </Step>
  <Step>

### 第六步：判断硬件与软件职责

硬件：

- 检测和响应受控事件。
- 保存必要返回状态。
- 执行特权模式转换。
- 提供中断向量和地址转换等硬件机制。

操作系统：

- 执行服务程序。
- 保存额外软件现场。
- 更新内核数据结构。
- 管理资源。
- 决定是否调度其他进程。


  </Step>
</Steps>

## 第十六部分 本章知识总结

### 二十八、必须真正理解的八个核心结论

#### 结论一：操作系统本质上是资源管理者

它负责：

- 统一管理资源。
- 实现资源共享。
- 提供安全保护。
- 向应用程序提供服务。


#### 结论二：并发不等于并行

单核可以并发执行多个程序。

但在单核处理器上：

普通进程之间通常不能真正同时执行 CPU 指令流。

CPU 与设备却可以并行工作。


#### 结论三：用户态与内核态是权限机制

用户态：

能够执行普通指令。

内核态：

能够执行特权操作。

用户程序不能随意修改关键硬件状态。


#### 结论四：中断、异常和系统调用必须分开

外部中断：

通常异步，来源于 CPU 外部。

异常：

通常同步，来源于当前指令执行条件。

系统调用：

程序主动请求内核服务。


#### 结论五：模式切换不是进程切换

模式切换：

改变 CPU 的执行权限。

进程切换：

改变 CPU 当前运行的进程。

系统调用、中断和异常均不必然导致进程切换。


#### 结论六：中断处理由硬件和软件共同完成

硬件：

保证受控响应、状态保存和处理入口。

软件：

完成实际事件处理、资源管理和必要调度。

必须掌握二者分工。


#### 结论七：程序运行需要链接、装入和地址转换

程序从静态可执行文件变成运行中的进程。

涉及：

- 链接。
- 装入。
- 地址空间建立。
- 必要的重定位。
- 运行时地址转换。

这些过程不能互相混淆。


#### 结论八：内核结构体现性能与隔离的权衡

宏内核：

更多系统服务处于内核态。

通常有利于高效内部调用。

微内核：

更多服务移到用户态。

通常有利于故障隔离与扩展。

外核：

更强调底层资源保护和用户态资源管理策略。

### 三十、复习建议

#### 第二层：必须理解执行机制

- 为什么系统调用需要进入内核。
- 为什么 Trap 指令允许用户态执行。
- 为什么普通访存指令可能触发异常。
- 为什么中断不一定发生进程切换。
- 为什么缺页可能重新执行原指令。
- 为什么硬件必须保存关键返回状态。
- 为什么微内核可能产生更多 IPC 开销。

这些内容决定你能否解决变式题。

#### 第三层：必须会综合分析

重点掌握：

**系统调用 + 进程阻塞 + I/O 中断 + 进程调度。**

以及：

**访存指令 + 地址转换 + 缺页异常 + 内核处理 + 恢复执行。**

这两条执行链路，是本章与后续章节联系最紧密的部分。

- 进程状态转换。

- 虚拟内存。
- 缺页处理。
- I/O 管理。

就会容易很多。


### 最终总结

操作系统第 1 章最核心的问题只有一个：

**操作系统如何在保证安全和资源共享的前提下，让多个程序受控地使用计算机硬件？**

完整答案是：

1. 操作系统通过进程、文件、虚拟内存等机制管理和抽象资源。
2. 通过用户态与内核态实现权限隔离。
3. 通过特权指令防止普通程序直接控制关键硬件状态。
4. 通过系统调用向用户程序提供受控内核服务。
5. 通过中断处理外部事件，通过异常处理当前指令引发的问题。
6. 通过调度与上下文切换协调多个进程的执行。
7. 通过链接、装入和地址转换建立程序的运行环境。
8. 通过适当的内核结构和虚拟化机制组织系统服务、保护资源并扩展计算环境。

**真正掌握这一整套运行机制，比孤立背诵几十条概念更重要。**

学完本章，应能够在看到任何一道涉及中断、系统调用、用户态、内核态和进程切换的题目时，准确回答四个问题：

- 事件是谁触发的？
- CPU 为什么需要进入内核？
- 硬件和操作系统分别做什么？
- 处理结束后，哪个进程从哪里继续执行？

能够独立回答这四个问题，就基本掌握了本章最有价值的核心内容。
