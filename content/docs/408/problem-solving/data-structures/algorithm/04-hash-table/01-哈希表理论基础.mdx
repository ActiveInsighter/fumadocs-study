# 哈希表理论基础

哈希表（Hash Table，也常译作**散列表**）是算法题中最常见的“**用空间换时间**”的数据结构之一。

它最核心的价值不是“存数据”，而是把原本需要顺序查找的问题，转化为**根据键直接定位位置**的问题。  
在哈希函数分布合理、负载因子受控的情况下，插入、删除、查询的平均时间复杂度都可以达到 $O(1)$。

<Callout type="info" title="什么时候应该想到哈希表？">
如果题目中出现“是否出现过”“出现了几次”“某个值对应什么信息”“快速查找另一半”“去重”等关键词，通常都应该优先考虑哈希法。
</Callout>

---

## 1. 什么是哈希表

哈希表是一种根据**键（key）**快速访问数据的数据结构。

最简单的理解，可以从数组开始。

数组之所以能够在 $O(1)$ 时间内访问元素，是因为我们知道它的下标：

```text
下标：  0   1   2   3   4
元素：  A   B   C   D   E
```

只要知道下标 $3$，就能直接找到 `D`，而不需要从头扫描。

哈希表做的事情，本质上就是：

> **把任意形式的 key 转换成一个可以用于定位存储位置的索引。**

原始示意图：

![哈希表通过索引直接访问元素](https://file1.kamacoder.com/i/algo/20210104234805168.png)

假设学校中有 $n$ 名学生，现在要判断“张三是否在学校里”。

如果直接遍历全部学生，最坏需要检查 $n$ 次：

$$
T(n)=O(n)
$$

如果提前把所有姓名存入哈希集合，那么平均情况下只需要一次哈希计算和一次查找：

$$
T(n)=O(1)
$$

这就是哈希表最重要的使用场景之一：**快速判断某个元素是否存在**。

---

## 2. 哈希函数：如何从 key 找到位置

真实问题中的 key 往往并不是整数下标，例如：

- 姓名：`"Alice"`
- 字符串：`"abc"`
- 学号：`20260001`
- 坐标：`(3, 5)`

因此，需要一个函数把 key 映射成整数，这个函数就是**哈希函数（Hash Function）**。

可以写成：

$$
h(key)=index
$$

其中：

- $key$ 是原始键；
- $h$ 是哈希函数；
- $index$ 是哈希表中的位置。

原始示意图：

![哈希函数把姓名映射到哈希表索引](https://file1.kamacoder.com/i/algo/2021010423484818.png)

### 2.1 为什么经常需要取模

哈希函数计算出的原始哈希值可能非常大，而哈希表只有有限个槽位。

若哈希表容量为 $m$，通常会进一步计算：

$$
index = hash(key) \bmod m
$$

这样一定有：

$$
0 \le index < m
$$

于是所有 key 都可以落到哈希表合法范围内。

<Callout type="warning" title="取模并不能避免冲突">
即使两个 key 的原始哈希值不同，它们经过取模后仍然可能得到同一个下标。因此，哈希表必须设计“哈希冲突”的处理机制。
</Callout>

---

## 3. 哈希冲突：不同 key 映射到了同一位置

如果：

$$
key_1 \ne key_2
$$

但：

$$
h(key_1)=h(key_2)
$$

就发生了**哈希冲突（Hash Collision）**。

例如“小李”和“小王”都映射到下标 `1`：

![两个不同 key 发生哈希冲突](https://file1.kamacoder.com/i/algo/2021010423494884.png)

哈希冲突不是异常，而是哈希表设计中必须面对的正常现象。

即使哈希函数设计得很好，只要 key 的数量足够多，而桶数量有限，就不可能保证永不冲突。

---

## 4. 解决哈希冲突的两种经典方法

### 4.1 拉链法

拉链法（Separate Chaining）的思路是：

> 每个哈希槽位不只存一个元素，而是存放一个“桶”；发生冲突的元素全部放进同一个桶中。

经典实现中，这个桶可以是一条链表：

![拉链法解决哈希冲突](https://file1.kamacoder.com/i/algo/20210104235015226.png)

假设：

- 元素数量为 $n$；
- 桶数量为 $m$。

定义负载因子：

$$
\alpha = \frac{n}{m}
$$

当哈希分布比较均匀时，一个桶中平均大约有 $\alpha$ 个元素。

因此，合理控制负载因子非常重要：

- $m$ 太大：浪费空间；
- $m$ 太小：链过长，查询性能下降。

理想情况下，哈希表会在负载因子过高时自动**扩容并重新哈希（rehash）**。

#### 拉链法的优点

- 对装载率要求相对宽松；
- 删除操作比较自然；
- 实现思想清晰；
- 即使元素数量超过桶数量，也仍然可以继续存储。

#### 潜在问题

极端情况下，如果大量元素落到同一个桶中，那么查询会退化为：

$$
O(n)
$$

所以哈希表的 $O(1)$ 通常指的是**平均复杂度**，而不是绝对的最坏复杂度。

---

### 4.2 开放寻址法：以线性探测为例

开放寻址法（Open Addressing）不额外维护链表，而是把所有元素都直接存放在哈希数组中。

如果目标位置被占用，就继续寻找其他空位置。

最简单的策略是**线性探测（Linear Probing）**：

$$
index,\quad index+1,\quad index+2,\quad \dots
$$

并对表长取模。

原始示意图：

![线性探测法解决哈希冲突](https://file1.kamacoder.com/i/algo/20210104235109950.png)

例如：

1. 小李映射到位置 `1`，位置为空，直接存入；
2. 小王也映射到位置 `1`，发现已被占用；
3. 继续检查位置 `2`；
4. 若位置 `2` 为空，则将小王存入位置 `2`。

因为开放寻址依赖空槽位解决冲突，所以必须保证表中存在空位。

<Callout type="info" title="线性探测并不是唯一的开放寻址策略">
开放寻址还包括二次探测、双重哈希等方法。算法题中通常不要求手写工业级哈希表，但理解这些思想有助于理解哈希容器为什么需要控制负载因子。
</Callout>

## 5. 为什么哈希表是“空间换时间”

假设我们只用数组顺序扫描，通常不需要额外结构，但查找代价为：

$$
O(n)
$$

如果建立哈希表，则需要额外存储：

$$
O(n)
$$

但平均查询可以降低为：

$$
O(1)
$$

因此哈希法是一种典型的：

> **使用额外空间，换取更快查询速度。**

算法题中看到“空间复杂度增加，但时间复杂度显著下降”时，不要本能认为不好。  
很多题目的关键恰恰就是主动建立辅助映射。

## 6. 算法题里常见的三类哈希结构

在刷题时，通常不会自己从零实现哈希表，而是根据 key 的范围和需要选择合适的数据结构。

### 6.1 数组：范围已知时最快、最直接

如果 key 是范围很小的整数，例如：

- 小写字母 `a-z`
- ASCII 字符
- 数字 $0 \sim 1000$
- 固定范围的频次统计

可以直接使用数组。

例如统计小写字母频次：

```cpp
int count[26] = {0};

for (char c : s) {
    ++count[c - 'a'];
}
```

这里：

$$
hash(c)=c-'a'
$$

其实数组本身就承担了哈希表的角色。

<Callout type="tip" title="刷题优先级">
如果 key 的范围固定且不大，优先考虑数组，而不是 `unordered_map`。数组通常常数更小、内存局部性更好，也更容易写对。
</Callout>

---

### 6.2 Set：只关心“这个 key 是否存在”

如果只需要判断：

> 某个元素有没有出现过？

那么集合最自然。

典型场景：

- 判重；
- 两个数组求交集；
- 检测循环；
- 判断某个状态是否访问过。

C++ 中常用的集合容器：

| 容器 | 常见底层结构 | 是否有序 | 是否允许重复 | 平均/典型查询复杂度 |
| --- | --- | --- | --- | --- |
| `std::set` | 红黑树 | 是 | 否 | $O(\log n)$ |
| `std::multiset` | 红黑树 | 是 | 是 | $O(\log n)$ |
| `std::unordered_set` | 哈希表 | 否 | 否 | 平均 $O(1)$ |

如果题目不要求有序，通常优先考虑 `unordered_set`。

如果题目需要：

- 自动排序；
- 查找前驱、后继；
- `lower_bound` / `upper_bound`；

那么应考虑 `set`，而不是 `unordered_set`。

---

### 6.3 Map：不仅要知道“有没有”，还要保存对应信息

Map 保存的是：

$$
key \rightarrow value
$$

典型问题：

- 数字 $\rightarrow$ 出现次数；
- 数字 $\rightarrow$ 下标；
- 字符串 $\rightarrow$ 编号；
- 节点 $\rightarrow$ 状态；
- 前缀和 $\rightarrow$ 出现次数。

C++ 常见映射容器：

| 容器 | 常见底层结构 | key 是否有序 | key 是否可重复 | 查询复杂度 |
| --- | --- | --- | --- | --- |
| `std::map` | 红黑树 | 是 | 否 | $O(\log n)$ |
| `std::multimap` | 红黑树 | 是 | 是 | $O(\log n)$ |
| `std::unordered_map` | 哈希表 | 否 | 否 | 平均 $O(1)$ |

如果只需要快速映射，通常优先：

```cpp
unordered_map<Key, Value>
```

如果需要根据 key 的有序性做进一步操作，则使用：

```cpp
map<Key, Value>
```

---

## 7. 三种结构怎么选

可以用下面的决策顺序。

### 情况一：key 范围很小、连续、确定

使用**数组**。

例如：

```text
'a' ~ 'z'
0 ~ 100
ASCII 字符
```

### 情况二：只关心是否存在

使用 **Set**。

例如：

```text
这个数出现过吗？
这个状态访问过吗？
两个集合有哪些公共元素？
```

### 情况三：需要记录 key 对应的信息

使用 **Map**。

例如：

```text
这个数出现了几次？
这个数第一次出现在哪里？
某个前缀和出现过多少次？
```

可以把它记成：

| 需求 | 首选结构 |
| --- | --- |
| 固定小范围计数 | 数组 |
| 判断存在性 | `set` / `unordered_set` |
| 记录映射关系 | `map` / `unordered_map` |

## 8. 有序容器和哈希容器不要混为一谈

原资料中容易让初学者产生一个误区：

> 只要通过 key 查找 value，就都是“哈希表”。

严格来说并不是。

例如：

- `std::unordered_map` 的底层通常是哈希表；
- `std::map` 的底层通常是平衡搜索树；
- `std::unordered_set` 的底层通常是哈希表；
- `std::set` 的底层通常是平衡搜索树。

它们都能完成“按 key 查找”，但底层原理和复杂度不同。

因此，算法分析时应区分：

### 哈希结构

平均：

$$
O(1)
$$

但：

- 无序；
- 存在哈希冲突；
- 最坏情况可能退化。

### 平衡搜索树

稳定：

$$
O(\log n)
$$

并且：

- key 有序；
- 可以进行范围查询；
- 可以做前驱、后继等顺序相关操作。

## 9. 高频算法题型中的哈希思维

真正重要的不是记住容器名称，而是识别“映射关系”。

### 9.1 频次统计

例如判断两个字符串是否为字母异位词：

$$
count[c]++
$$

核心是：

```text
字符 -> 出现次数
```

---

### 9.2 补数查找

“两数之和”的核心是：

$$
a+b=target
$$

当遍历到 $a$ 时，立即去查：

$$
target-a
$$

是否已经出现。

映射关系是：

```text
数字 -> 下标
```

这样把暴力枚举的：

$$
O(n^2)
$$

优化为平均：

$$
O(n)
$$

---

### 9.3 去重

如果问题只要求唯一元素，可以把值加入集合：

```text
元素 -> 是否存在
```

---

### 9.4 状态判重

很多“循环检测”问题都可以保存已经见过的状态。

例如某个状态不断变换：

$$
x_0 \rightarrow x_1 \rightarrow x_2 \rightarrow \cdots
$$

如果某个状态第二次出现，就说明进入了环。

映射关系：

```text
状态 -> 是否访问过
```

---

## 10. 常见误区

### 误区一：看到查找就无脑用 `unordered_map`

如果 key 只是 `'a' ~ 'z'`，使用长度为 `26` 的数组通常更好。

### 误区二：认为哈希表查询永远是 $O(1)$

更准确地说：

> 在合理哈希函数和负载因子下，哈希表的查询、插入、删除通常是**平均 $O(1)$**。

不能把平均复杂度与最坏复杂度混为一谈。

### 误区三：题目要求顺序，却仍然使用无序哈希表

如果需要：

- 最小 key；
- 最大 key；
- 排序遍历；
- 范围查询；

哈希表通常不是最自然的选择。

### 误区四：Map 和 Set 的选择不明确

可以直接记住：

- `Set`：回答“有没有”；
- `Map`：回答“它对应什么”。

## 11. 一套通用做题模板

遇到可能使用哈希法的题，可以按下面四步分析。

### 第一步：明确我要快速查询什么

问自己：

> 遍历到当前位置时，我希望能 $O(1)$ 得到什么信息？

### 第二步：确定 key

例如：

- 一个数字；
- 一个字符；
- 一个字符串；
- 一个前缀和；
- 一个状态。

### 第三步：确定 value 是否需要存在

如果只需要“有没有”，用 Set。

如果需要额外信息：

```text
key -> 次数
key -> 下标
key -> 状态
```

用 Map。

### 第四步：判断能否用数组替代

若 key 范围足够小，优先用数组。

## 12. 复杂度总结

设一共有 $n$ 个元素。

| 操作/结构 | 数组直接索引 | `unordered_set/map` | `set/map` |
| --- | ---: | ---: | ---: |
| 查询 | $O(1)$ | 平均 $O(1)$ | $O(\log n)$ |
| 插入 | 视场景而定 | 平均 $O(1)$ | $O(\log n)$ |
| 删除 | 视场景而定 | 平均 $O(1)$ | $O(\log n)$ |
| 是否有序 | 下标天然有序 | 否 | 是 |
| 额外空间 | 通常 $O(U)$ | $O(n)$ | $O(n)$ |

其中 $U$ 表示值域大小。

## 13. 多语言常用写法


  
### C++


```cpp
#include <unordered_map>
#include <unordered_set>
using namespace std;

unordered_set<int> seen;
seen.insert(10);

if (seen.count(10)) {
    // 10 出现过
}

unordered_map<int, int> freq;
++freq[10];
```

  

  
### Java


```java
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

Set<Integer> seen = new HashSet<>();
seen.add(10);

if (seen.contains(10)) {
    // 10 出现过
}

Map<Integer, Integer> freq = new HashMap<>();
freq.put(10, freq.getOrDefault(10, 0) + 1);
```

  

  
### Python


```python
seen = set()
seen.add(10)

if 10 in seen:
    # 10 出现过
    pass

freq = {}
freq[10] = freq.get(10, 0) + 1
```

## 14. 本节小结

哈希表需要掌握的不是“背 API”，而是建立下面这条思维链：

```text
需要快速查找
    ↓
能否建立 key -> 信息 的映射
    ↓
key 范围小？
 ┌──是──→ 数组
 │
 否
 │
 ↓
只关心存在性？
 ┌──是──→ Set
 │
 否
 │
 ↓
Map
```

最终记住三个核心判断：

1. **判断某元素是否出现过**：优先想到哈希。
2. **值域小而固定**：优先数组。
3. **需要保存 key 对应的信息**：使用 Map；只关心存在性则使用 Set。

<Callout type="tip" title="下一步">
掌握理论后，最适合继续练习的是“有效的字母异位词”“两个数组的交集”“快乐数”“两数之和”。这些题分别对应频次统计、集合判重、状态判重和补数查找，是哈希表最典型的四种模式。
</Callout>
