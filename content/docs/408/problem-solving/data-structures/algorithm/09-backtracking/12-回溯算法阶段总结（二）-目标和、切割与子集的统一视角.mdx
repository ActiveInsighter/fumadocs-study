# 回溯算法阶段总结（二）：目标和、切割与子集的统一视角

这一阶段的几道题表面差异很大：

- `39. 组合总和`：同一个候选值可以重复选择；
- `40. 组合总和 II`：候选值可能重复，但每个下标只能使用一次；
- `131. 分割回文串`：不是“选数”，而是在字符串中选择切割位置；
- `93. 复原 IP 地址`：切割问题再叠加段数和合法性约束；
- `78. 子集`：不再只收集终点，而是收集整棵搜索树的所有节点。

但如果统一站在搜索树角度观察，它们仍然只是在改变几个核心问题：

$$
\boxed{\text{本层候选是什么}}
\quad
\boxed{\text{下一层从哪里开始}}
\quad
\boxed{\text{什么节点需要收集}}
\quad
\boxed{\text{哪些子树可以提前舍弃}}
$$

<Callout title="这一阶段最重要的能力">

不要根据题名判断模板，而要先画出搜索树，并回答：

1. 一个节点表示什么状态？
2. 一条边表示什么选择？
3. 同一层允许选择哪些候选？
4. 相同元素出现在同一树层和同一树枝时，含义是否相同？
5. 当前节点本身是不是答案，还是必须走到某种终止状态才是答案？

这五个问题比记忆任何一段代码都更重要。

</Callout>

## 1. `startIndex` 的本质：定义“当前层的候选区间”

这一阶段反复出现 `startIndex`，但它不是一个机械模板变量。

它真正表达的是：

> 当前递归节点下，下一步允许从原序列的哪个位置开始枚举。

例如同一集合中做组合时：

```text
nums = [1, 2, 3, 4]
```

若当前已经选择下标 `i`，后续通常只允许考虑右边的元素，从而保证选择顺序单调向右。

这样做同时解决两个问题：

- 不重复使用已经越过的下标；
- 不把 `[1,2]` 与 `[2,1]` 当成两个组合。

因此，大多数“同一集合的组合 / 子集 / 切割”问题都会出现某种形式的 `startIndex`。

## 2. 为什么 39. 组合总和仍然需要 `startIndex`？

`39. 组合总和` 的特殊之处是：

> 当前候选可以在同一条路径中重复使用。

这并不意味着应该删掉 `startIndex`。

如果完全从 `0` 开始搜索，会同时产生：

```text
[2, 3, 3]
[3, 2, 3]
[3, 3, 2]
```

它们只是同一组合的不同排列。

所以仍然要限制搜索方向，只不过选择 `candidates[i]` 后，下一层从 `i` 而不是 `i + 1` 开始：

```cpp
backtracking(candidates, target, i);
```

其语义是：

```text
允许继续选择当前元素
但不允许回头选择更早的元素
```

对应搜索树如下：

![39.组合总和](https://file1.kamacoder.com/i/algo/20201223170730367.png)

### `i` 与 `i + 1` 的统一理解

| 下一层起点 | 含义 | 典型题目 |
| --- | --- | --- |
| `i` | 当前下标还能再次使用 | 39. 组合总和 |
| `i + 1` | 当前下标不能再次使用 | 40. 组合总和 II、78. 子集 |

所以不要死记“组合传 `i + 1`”。真正应该先问：

> **当前元素在同一条路径中还能不能再次被选择？**

## 3. 求和问题中的通用剪枝：排序 + 单调性

如果所有候选都是正数，随着不断选择元素，路径和只会增大。

令剩余目标为：

$$
remain=target-\sum path
$$

如果数组已经升序排列，当某个候选满足：

$$
candidates[i]>remain
$$

则后面的候选只会更大，所以整个当前层都可以结束：

```cpp
if (candidates[i] > remain) break;
```

也可以直接把条件写进循环：

```cpp
for (int i = startIndex;
     i < candidates.size() && candidates[i] <= remain;
     ++i) {
    // ...
}
```

<Callout type="info" title="为什么排序后才能这样剪枝">

这里使用的是单调性：数组升序后，若当前值已经太大，右侧所有值都至少和它一样大。

如果数组没有排序，只能说明“当前这个元素不能选”，不能推出“后面所有元素都不能选”。

</Callout>

## 4. 40. 组合总和 II：真正理解“树层去重”

`40. 组合总和 II` 把回溯中的去重问题推到了核心位置。

它同时要求：

- 数组中可以存在相同数值；
- 每个数组下标只能使用一次；
- 结果组合不能重复。

排序后，以重复值为例：

```text
[1, 1, 2, ...]
```

搜索树中“两个 `1`”可能出现在两种位置。

![40.组合总和II树层去重](https://file1.kamacoder.com/i/algo/20201123202817973.png)

### 同一树枝上的重复值

例如：

```text
第一个 1 → 第二个 1
```

它们来自两个不同下标，可以共同组成：

```text
[1, 1, ...]
```

所以这种重复**不能删**。

### 同一树层上的重复值

若根节点先用“第一个 `1`”展开过整棵子树，再用“第二个 `1`”作为同层起点，就会产生完全相同的一批组合。

所以这种重复必须跳过。

因此经典条件是：

```cpp
if (i > startIndex && candidates[i] == candidates[i - 1]) {
    continue;
}
```

它表达的不是“相同值永远不能再用”，而是：

> **当前层已经以这个值作为分支起点搜索过一次，不要再启动一个等价分支。**

## 5. 去重为什么一定要区分“树层”和“树枝”？

很多回溯去重错误都来自一句模糊的话：

> “遇到重复元素就跳过。”

这句话是不完整的。

同一个数值：

- 在**同一树枝**中，可能代表合法地选取多个不同下标；
- 在**同一树层**中，可能代表重复启动同一种决策。

因此判断重复之前，一定要明确当前是在比较：

```text
纵向路径上的重复
```

还是：

```text
横向候选中的重复
```

后续的 `90. 子集 II`、`47. 全排列 II` 都会再次用到这个思想。

## 6. 切割问题为什么也是组合问题？

`131. 分割回文串` 看起来和“组合”没有关系，但把字符串中的切割位置当成选择后，结构就完全一致了。

假设字符串：

```text
"aab"
```

在某个递归节点，从 `startIndex` 开始，可以尝试把结束位置放在：

```text
startIndex
startIndex + 1
startIndex + 2
...
```

也就是枚举：

```text
s[startIndex ... i]
```

如果这一段是回文串，就把它加入路径并继续切剩余部分。

![131.分割回文串](https://file1.kamacoder.com/i/algo/20201123203228309.png)

这与组合问题一一对应：

| 组合问题 | 字符串切割 |
| --- | --- |
| 选择一个元素 | 选择一个子串 |
| `i` 表示候选元素位置 | `i` 表示当前切割终点 |
| `startIndex` 表示候选起点 | `startIndex` 表示未切割部分起点 |
| 下一层 `i + 1` | 下一段从 `i + 1` 开始 |

因此切割问题可以理解为：

$$
\boxed{\text{在所有可能的切割线组合中搜索合法方案}}
$$

## 7. 分割回文串最关键的递归不变量

假设递归函数为：

```cpp
backtracking(s, startIndex)
```

可以给它一个非常清晰的不变量：

> `s[0 ... startIndex - 1]` 已经被合法分割，并且这些分段已经记录在 `path` 中。

当前层只负责决定：

```text
从 startIndex 开始的下一段在哪里结束？
```

当：

```cpp
startIndex == s.size()
```

说明所有字符恰好被切完，当前 `path` 才是一个完整答案。

这个不变量非常重要，因为它能自然推出：

- 为什么循环从 `startIndex` 开始；
- 为什么截取 `[startIndex, i]`；
- 为什么下一层传 `i + 1`；
- 为什么 `startIndex == s.size()` 才收集答案。

## 8. 93. 复原 IP 地址：在切割模板上增加约束

`93. 复原 IP 地址` 与分割回文串本质相同，只是每一段的合法性更严格。

合法 IPv4 地址必须满足：

1. 恰好有四段；
2. 每段非空；
3. 每段只能包含数字；
4. 每段数值属于 $[0,255]$；
5. 多位数字不能以 `0` 开头。

搜索树如下：

![93.复原IP地址](https://file1.kamacoder.com/i/algo/20201123203735933-20230310133532452.png)

### 段数约束带来的剪枝

如果已经生成 `segmentCount` 段，则还需要：

$$
4-segmentCount
$$

段。

假设还剩 `remainingChars` 个字符，因为每段长度只能是 $1\sim3$，必须满足：

$$
4-segmentCount
\le
remainingChars
\le
3(4-segmentCount)
$$

否则当前状态一定无法组成合法 IP，可以直接返回。

这比简单判断：

```cpp
if (s.size() > 12) return;
```

更精确，因为它会在递归的每个节点动态利用“剩余字符数”和“剩余段数”。

<Callout title="剪枝的一般形式">

很多看似不同的剪枝，本质都是在比较：

$$
\text{剩余资源}
$$

与：

$$
\text{完成答案所需资源的最小值 / 最大值}
$$

一旦区间不可能相交，就可以舍弃整个子树。

</Callout>

## 9. 78. 子集：答案从“终点”变成“所有节点”

子集问题是这一阶段最重要的一次视角转换。

前面的题目通常只有满足某个目标时才收集结果，例如：

```text
选够 k 个元素
```

```text
剩余目标变成 0
```

```text
字符串全部切完
```

而子集问题不同。

对于：

```text
nums = [1, 2, 3]
```

搜索树中的：

```text
[]
[1]
[1,2]
[1,2,3]
[1,3]
[2]
...
```

每一个节点都已经是合法子集。

![78.子集](https://file1.kamacoder.com/i/algo/202011232041348.png)

因此收集代码必须放在递归入口：

```cpp
result.push_back(path);
```

而不是只在叶子节点执行。

这直接揭示了一个通用判断方法：

> **先问搜索树中的哪些节点代表答案，再决定 `result.push_back(path)` 应该写在哪里。**

## 10. 为什么子集题甚至可以不写显式终止条件？

子集代码通常是：

```cpp
void backtracking(const vector<int>& nums, int startIndex) {
    result.push_back(path);

    for (int i = startIndex; i < nums.size(); ++i) {
        path.push_back(nums[i]);
        backtracking(nums, i + 1);
        path.pop_back();
    }
}
```

当：

```text
startIndex == nums.size()
```

循环自然不会执行，函数随后直接返回。

所以这里即使没有显式写：

```cpp
if (startIndex >= nums.size()) return;
```

递归也会自然终止。

这说明：

> 终止条件不一定总要写成一个 `if`；有时它已经隐含在候选集合为空这件事里。

## 12. “结果在哪里收集”比模板更值得记忆

回溯题可以按照答案节点在搜索树中的位置进一步分类。

### 只收集固定深度节点

例如 `77. 组合`：

$$
|path|=k
$$

### 收集满足目标状态的节点

例如 `39 / 40. 组合总和`：

$$
remain=0
$$

### 收集完整覆盖输入后的节点

例如字符串切割：

$$
startIndex=n
$$

### 收集所有节点

例如 `78. 子集`：

```cpp
result.push_back(path);
```

一进入递归就执行。

<Callout type="info" title="一个非常实用的画树技巧">

画搜索树时，直接给“会被加入答案的节点”画圈。

如果只有叶子被圈起来，答案收集通常写在终止条件中；如果所有节点都被圈起来，答案收集通常写在递归入口。

</Callout>

## 13. 回溯中的三种“重复”不要混淆

### 13.1 同一下标被重复使用

由下一层起点控制：

```text
传 i      → 可以重复使用当前下标
传 i + 1  → 不能重复使用当前下标
```

### 13.2 同值元素造成重复答案

常通过：

```text
排序 + 同一树层跳过相同值
```

解决。

### 13.3 同一批元素的不同顺序

组合问题通过单调向右的 `startIndex` 避免：

```text
[1,2] 有
[2,1] 不再生成
```

排列问题则恰恰要保留不同顺序，因此后续会使用另一套搜索方式。

这三种“重复”分别属于不同问题，不能看到“重复”二字就统一用 `set` 处理。

## 14. 一个更稳定的回溯分析流程

<Steps>
<Step>

### ① 明确答案是什么

先确定答案是：

- 固定长度组合；
- 满足目标和的路径；
- 一组切割结果；
- 任意子集；
- 或者后续会遇到的排列、棋盘布局。

</Step>
<Step>

### ② 定义递归状态

问自己：

> 为了完整描述“现在走到哪里”，最少需要哪些变量？

常见状态包括：

```text
startIndex
remain / sum
path
段数
当前字符串位置
```

</Step>
<Step>

### ③ 定义当前层候选

把 `for` 循环说成人话：

> 当前节点下一步究竟有哪些选择？

如果说不清，代码通常也写不对。

</Step>
<Step>

### ④ 判断下一层从哪里开始

根据元素是否允许重复使用、是否需要保持组合顺序，决定传：

```text
i
i + 1
index + 1
```

</Step>
<Step>

### ⑤ 确定答案收集位置

问：

> 当前节点本身是不是一个答案？

这一步决定 `result.push_back(path)` 是写在入口、条件分支还是叶子处。

</Step>
<Step>

### ⑥ 最后再做剪枝和去重

先保证搜索空间定义正确，再利用：

- 单调性；
- 剩余数量上下界；
- 排序；
- 树层去重；
- 合法性检查；

减少无意义搜索。

</Step>
</Steps>

## 15. 常见错误速查

### 错误一：看到“可以重复选”就删除 `startIndex`

后果是把组合搜索变成排列搜索，产生大量顺序重复。

正确做法通常是：

```cpp
backtracking(..., i);
```

而不是从 `0` 重新开始。

### 错误二：遇到相同值就一律跳过

这会把树枝上合法的重复元素一起删除。

真正需要处理的是：

```text
同一树层是否已经用相同值启动过等价分支
```

### 错误三：子集只在叶子收集

这样会漏掉大量中间节点对应的子集。

### 错误四：切割题只盯着字符串操作

真正应该先建立的是：

```text
当前未处理起点 + 当前切割终点
```

对应的搜索树。

### 错误五：为了去重直接把最终结果丢进 `set`

这通常能“救正确性”，但没有解决搜索阶段的重复分支，既浪费时间，也掩盖了真正的树层去重逻辑。

## 16. 复杂度应该怎么看？

回溯不是“复杂度都一样的暴搜”。不同问题的搜索空间规模不同，剪枝也会显著改变实际访问节点数。

例如 `78. 子集` 必须输出 $2^n$ 个答案，而复制每个答案还需要与其长度成正比，因此常写为：

$$
O(n2^n)
$$

而组合问题的节点数量与：

$$
\sum_{j=0}^{k}\binom{n}{j}
$$

有关。

目标和问题还与候选值、目标值以及允许重复次数有关。

所以更可靠的分析方式是：

1. 先估计搜索树最多有多少节点；
2. 再估计每个节点需要多少额外工作；
3. 最后考虑输出结果本身的复制成本。

## 17. 本阶段知识地图

```text
回溯
├─ 同一集合的组合
│  ├─ 元素可重复使用 → 下一层传 i
│  └─ 元素不可重复使用 → 下一层传 i + 1
│
├─ 候选值有重复
│  └─ 排序 + 树层去重
│
├─ 切割问题
│  ├─ startIndex = 当前未切部分起点
│  ├─ i = 当前段终点
│  └─ 下一层从 i + 1 开始
│
├─ 子集问题
│  └─ 搜索树所有节点都收集
│
└─ 剪枝
   ├─ 排序后的单调性
   ├─ 剩余数量上下界
   └─ 当前选择的合法性
```

## 18. 下一阶段要解决什么？

接下来最重要的变化是：

1. `90. 子集 II`：把“子集收集所有节点”与“树层去重”结合起来；
2. `491. 非递减子序列`：无法通过排序后再搜索，去重逻辑会发生变化；
3. `46 / 47. 全排列`：不再使用 `startIndex` 单向向右，而是每层从整个集合中挑选尚未使用的元素；
4. 棋盘类问题：路径从一维数组变成二维决策空间。

如果这一阶段已经真正理解：

$$
\boxed{\text{候选区间}}
+
\boxed{\text{收集位置}}
