# 数据规模与算法复杂度估算

知道一个算法是 $O(n)$、$O(n\log n)$ 或 $O(n^2)$ 还不够。真正做题时，更关键的问题是：

> **题目给出的数据范围，允许我们使用什么数量级的算法？**

很多超时并不是代码写得“慢”，而是一开始选择的复杂度就不可能通过。

<Callout title="本篇核心能力" type="info">
看到 $n$ 的范围后，先估算可接受复杂度，再决定用暴力、排序、二分、哈希、动态规划还是更高级的数据结构。
</Callout>

---

## 1. OJ 为什么会判定超时

在线评测系统通常会给程序设置一个时间限制，例如 1 秒、2 秒或 5 秒。如果程序在规定时间内没有完成全部测试数据，就会得到 **Time Limit Exceeded，TLE**。

![程序超时](https://file1.kamacoder.com/i/algo/20200729112716117-20230310124308704.png)

但要注意：

- “1 秒”不是一个固定的操作次数；
- C++、Java、Python 的常数差异很大；
- CPU、编译器优化、内存访问模式、缓存命中率都会影响耗时；
- 同样是一次循环，里面做整数加法、字符串拼接、哈希查询的成本完全不同；
- OJ 机器与本地电脑的性能也可能不同。

所以不能把“$10^8$ 次操作约等于 1 秒”当成严格定律，它只能作为**数量级经验**。

<Callout title="不要机械套公式" type="warning">
复杂度用于判断增长趋势；“每秒能跑多少次”只用于做粗略预算。二者都不能替代实际题目中的常数、语言和实现细节。
</Callout>

---

## 2. CPU 频率不等于“每秒执行多少行代码”

例如一颗 3 GHz 左右的 CPU，每秒包含大约 $3\times10^9$ 个时钟周期，但这并不意味着程序每秒就能执行 $3\times10^9$ 次高级语言语句。

原因包括：

- 一条高级语言语句可能被编译成多条机器指令；
- 一条机器指令也可能需要多个阶段完成；
- 现代 CPU 会进行流水线、乱序执行、分支预测和向量化；
- 内存访问可能比寄存器运算慢几个数量级；
- CPU 同时还要运行操作系统和其他进程。

因此，**CPU 主频只能说明硬件时钟节奏，不能直接换算成算法操作次数**。

## 4. 做题时怎样由数据范围反推复杂度

一种常见经验是：如果是 C++ 中较简单的整数运算，可以先把每秒大约 $10^7\sim10^8$ 次“轻量级操作”作为粗略预算，再保守一些判断。

这不是公式，而是竞赛和刷题中的工程经验。

下面给出一张更实用的估算表。

| 最大规模 $n$ | 常见可考虑的复杂度 | 典型算法 |
| ---: | --- | --- |
| $n\le 20$ | $O(2^n)$、$O(n2^n)$ | 状态压缩、枚举子集 |
| $n\le 10$ | $O(n!)$ | 全排列、暴力搜索 |
| $n\le 100$ | $O(n^3)$ | Floyd、区间 DP 的部分写法 |
| $n\le 10^3$ | $O(n^2)$ | 双重循环、二维 DP |
| $n\le 10^5$ | $O(n\log n)$ | 排序、堆、平衡树、分治 |
| $n\le 10^6$ | $O(n)$ 或接近线性 | 双指针、滑动窗口、前缀和 |
| $n\ge 10^7$ | 往往需要极小常数的 $O(n)$ 或 $O(\log n)$ | 数学推导、二分、位运算 |

<Callout title="这张表是经验，不是定理" type="warning">
真正的上限还取决于时间限制、语言、常数、内存访问模式以及测试数据。Python 往往需要比 C++ 更保守。
</Callout>

---

## 5. 三个典型规模的判断

### 情况一：$n=10^3$

若写一个完整双重循环：

$$
n^2=10^6
$$

通常很轻松。

三重循环则为：

$$
n^3=10^9
$$

一般就非常危险。

所以此时 $O(n^2)$ 往往合理，而 $O(n^3)$ 往往需要重新考虑。

### 情况二：$n=10^5$

如果算法是：

$$
O(n\log_2 n)
$$

那么：

$$
10^5\log_2 10^5\approx 1.66\times10^6
$$

通常十分可控。

但如果是：

$$
O(n^2)=10^{10}
$$

几乎一定无法通过普通时间限制。

### 情况三：$n=10^9$

哪怕只遍历一次：

$$
O(n)=10^9
$$

也可能无法接受。

此时应该优先寻找：

- $O(\log n)$ 的二分或快速幂；
- $O(\sqrt n)$ 的数论方法；
- $O(1)$ 的数学公式；
- 不依赖于逐元素枚举的规律。

---

## 6. 为什么 $O(n)$ 也可能超时

很多初学者会觉得“线性复杂度已经很好了”，但线性并不等于永远足够快。

例如：

$$
n=5\times10^8
$$

一个 $O(n)$ 算法依然要执行数亿次循环。

而且如果循环中包含：

- 字符串复制；
- 哈希计算；
- 动态内存分配；
- 随机内存访问；
- 大量 I/O；

实际代价会进一步上升。

因此，判断是否会超时至少要同时考虑：

$$
\text{总工作量}\approx \text{执行次数}\times\text{单次操作成本}
$$

---

## 7. 从复杂度反推最大可处理规模

假设我们粗略允许约 $10^8$ 次简单操作，可以反向估算。

### $O(n)$

$$
n\lesssim10^8
$$

### $O(n^2)$

要求：

$$
n^2\lesssim10^8
$$

所以：

$$
n\lesssim10^4
$$

实际刷题中通常还会进一步保守到 $10^3\sim10^4$。

### $O(n^3)$

$$
n^3\lesssim10^8
$$

于是：

$$
n\lesssim\sqrt[3]{10^8}\approx464
$$

但由于三层循环常数较大，常见安全范围通常更小。

### $O(2^n)$

要求：

$$
2^n\lesssim10^8
$$

因为：

$$
2^{26}\approx6.7\times10^7,\qquad 2^{27}\approx1.34\times10^8
$$

所以纯指数枚举通常只能处理二十几的规模。

<Callout title="快速估算技巧" type="tip">
记住 $2^{10}\approx10^3$，于是 $2^{20}\approx10^6$，$2^{30}\approx10^9$。分析指数复杂度时非常方便。
</Callout>

---

## 8. $O(n\log n)$ 的规模怎样估算

如果 $n=10^7$：

$$
\log_2 10^7\approx23.25
$$

于是：

$$
n\log_2 n\approx2.3\times10^8
$$

这已经可能比较吃紧。

如果 $n=10^5$：

$$
n\log_2n\approx1.7\times10^6
$$

一般非常安全。

所以常见排序和树结构能够处理 $10^5$ 甚至 $10^6$ 量级的数据，但到了千万级，就需要认真考虑常数和时间限制。

---

## 9. 常数因子为什么仍然重要

渐近复杂度只保留增长最快的部分。例如：

$$
T_1(n)=1000n
$$

与：

$$
T_2(n)=n\log_2n
$$

从渐近意义看，$T_1(n)$ 是 $O(n)$，理论增长更慢。

但在某些实际范围内，$1000n$ 仍可能比 $n\log n$ 大。

所以实际优化分为两个层次：

### 第一层：先降低复杂度阶数

从 $O(n^2)$ 降到 $O(n\log n)$，通常是决定性的优化。

### 第二层：再优化常数

复杂度阶数相同时，再考虑：

- 避免不必要复制；
- 减少动态分配；
- 改善缓存局部性；
- 使用更合适的数据结构；
- 优化输入输出。

---

## 10. I/O 也可能成为瓶颈

如果输入包含数百万个整数，那么即使核心算法只有 $O(n)$，读取数据本身也需要时间。

C++ 中常见写法：

```cpp
std::ios::sync_with_stdio(false);
std::cin.tie(nullptr);
```

它可以减少 `iostream` 与 C 标准 I/O 的同步开销。

Java 常常使用 `BufferedReader`、`BufferedInputStream` 或自行实现快速读入；Python 则通常使用 `sys.stdin.buffer`。

因此：

> **复杂度正确不等于一定通过，工程实现同样重要。**

---

## 11. 一个实战判断流程

拿到题目后，可以按以下顺序判断。

### 看最大数据范围

例如 $n\le10^5$。

### 枚举候选复杂度

$O(n^2)$ 对应 $10^{10}$，明显太大；$O(n\log n)$ 约为 $10^6$ 量级，比较合理。

### 根据题目结构选择算法

可能考虑：

- 排序；
- 二分；
- 双指针；
- 哈希；
- 单调栈；
- 堆；
- 树状数组或线段树。

### 最后检查常数和内存

确认容器、递归深度、I/O 和空间占用不会成为新的瓶颈。

## 12. 测试不同复杂度的程序

下面给出与原始材料一致的三个测试模型：

```cpp
// O(n)
void linear(long long n) {
    volatile long long k = 0;
    for (long long i = 0; i < n; ++i) {
        ++k;
    }
}

// O(n^2)
void quadratic(long long n) {
    volatile long long k = 0;
    for (long long i = 0; i < n; ++i) {
        for (long long j = 0; j < n; ++j) {
            ++k;
        }
    }
}

// O(n log n)
void nLogN(long long n) {
    volatile long long k = 0;
    for (long long i = 0; i < n; ++i) {
        for (long long j = 1; j < n; j *= 2) {
            ++k;
        }
    }
}
```

这里使用 `volatile` 只是为了降低编译器把“无实际用途循环”直接优化掉的可能性。真正做严谨 benchmark 时，还应使用专门的基准测试框架，并进行多次预热与重复测量。

## 13. 常见误区

### 误区一：$O(n)$ 一定不会超时

错误。要看 $n$ 到底有多大。

### 误区二：1 GHz 就等于每秒执行 $10^9$ 行代码

错误。时钟周期和高级语言操作没有一一对应关系。

### 误区三：只看复杂度，不看常数

复杂度是第一优先级，但在同阶算法之间，常数非常重要。

### 误区四：本地 0.3 秒，OJ 就一定能过

不一定。评测机性能、编译参数和测试数据都可能不同。

### 误区五：一看到 $10^5$ 就机械套 $O(n\log n)$

数据范围只是约束之一，还必须结合题目结构。很多题可以做到 $O(n)$，有些则必须使用 $O(n\log n)$。

---

## 14. 一页速记

| 数据规模 | 第一反应 |
| ---: | --- |
| $n\le10$ | 可以考虑全排列 |
| $n\le20\sim25$ | 可以考虑子集枚举、状态压缩 |
| $n\le10^2$ | $O(n^3)$ 可能可行 |
| $n\le10^3$ | 常见目标 $O(n^2)$ |
| $n\le10^5$ | 常见目标 $O(n\log n)$ 或 $O(n)$ |
| $n\le10^6$ | 优先接近线性 |
| $n\ge10^8$ | 通常不能逐项遍历 |

<Callout title="真正应该形成的条件反射" type="tip">
先看数据范围，再算数量级，再选算法。不要先写完暴力解法，提交 TLE 后才开始思考复杂度。
</Callout>

```cpp
    }

void nLogN(long long n) {
    volatile long long k = 0;
    for (long long i = 0; i < n; ++i) {
        for (long long j = 1; j < n; j *= 2) {
            ++k;
        }
    }
}

int main() {
    long long n;
    while (cin >> n) {
        auto start = steady_clock::now();

        linear(n);
        // quadratic(n);
        // nLogN(n);

             << " ms\n";
    }
}
```

### Java

```java
import java.util.Scanner;

public class TimeComplexityDemo {
    static long sink;

    static void linear(long n) {
        long k = 0;
        for (long i = 0; i < n; ++i) {
            ++k;
        }
        sink = k;
    }

    static void quadratic(long n) {
        long k = 0;
        for (long i = 0; i < n; ++i) {
            for (long j = 0; j < n; ++j) {
                ++k;
            }
        }
        sink = k;
    }

    static void nLogN(long n) {
        long k = 0;
        for (long i = 0; i < n; ++i) {
            for (long j = 1; j < n; j *= 2) {
                ++k;
            }
        }
        sink = k;
    }

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        while (scanner.hasNextLong()) {
            long n = scanner.nextLong();
            long start = System.nanoTime();

            linear(n);
            // quadratic(n);
            // nLogN(n);

            long end = System.nanoTime();
            System.out.printf("%.3f ms%n", (end - start) / 1_000_000.0);
        }
    }
}
```

## 总结

判断算法是否会超时，本质上是在做一份“计算预算”：

$$
\text{输入规模}
\longrightarrow
\text{操作次数数量级}
\longrightarrow
\text{可接受复杂度}
\longrightarrow
\text{算法选择}
$$

最重要的不是记住某台电脑“1 秒能跑多少次”，而是形成对 $10^5$、$10^8$、$n^2$、$2^n$ 等数量级的直觉。

一旦这种直觉建立起来，很多题目甚至在读完数据范围时，就已经排除了大部分错误解法。
