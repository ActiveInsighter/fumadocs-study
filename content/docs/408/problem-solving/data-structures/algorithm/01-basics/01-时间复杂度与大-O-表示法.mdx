# 时间复杂度与大 O 表示法

时间复杂度并不是“程序实际运行了多少秒”，而是用一个数学函数描述：**当输入规模增长时，算法执行工作量如何增长**。

这一区别非常重要。实际运行时间会受到 CPU、编译器、缓存、语言、操作系统负载等因素影响；而时间复杂度关注的是更稳定、更具有普适性的 **增长趋势**。

<Callout title="先记住一句话" type="info">
时间复杂度研究的核心不是“现在快不快”，而是“当输入规模扩大以后，执行代价增长得有多快”。
</Callout>

本文将依次解决这些问题：

- 什么是时间复杂度与操作次数；
- 大 $O$、大 $\Omega$、大 $\Theta$ 分别表示什么；
- 为什么常数、低阶项可以忽略；
- $O(\log n)$ 的底数为什么通常不写；
- 如何分析循环、嵌套循环和多变量问题；
- 为什么“快速排序是 $O(n\log n)$”这句话需要上下文；
- 如何从代码快速判断复杂度。

---

## 1. 从“运行时间”到“操作次数”

假设一个算法处理规模为 $n$ 的输入，需要执行 $f(n)$ 次基本操作。如果每个基本操作的耗时近似看作常数，那么总运行时间可以写成：

$$
T(n) = c \cdot f(n)
$$

其中 $c$ 表示单次操作的平均耗时。

实际分析时，我们往往不关心 $c$ 的具体值，而关心 $f(n)$ 随 $n$ 增大时的增长速度。

例如：

```text
算法 A：T(n) = 20n + 100
算法 B：T(n) = 3n² + 10n + 5
```

当 $n$ 很小时，常数项和常数系数可能非常重要；但当 $n$ 足够大时，$n^2$ 的增长速度会压倒 $n$。

因此我们通常将二者分别记作：

$$
T_A(n) = O(n)
$$

$$
T_B(n) = O(n^2)
$$

![不同时间复杂度在不同数据规模下的差异](https://file1.kamacoder.com/i/algo/20200728191447384-20230310124015324.png)

<Callout title="复杂度不等于实际耗时" type="warning">
$O(n)$ 算法不一定在所有输入规模下都比 $O(n^2)$ 算法快。复杂度描述的是渐近增长趋势，而不是某台机器上的绝对耗时。
</Callout>

## 2. 大 O 到底是什么意思

### 2.1 严格数学定义

如果存在正常数 $c$ 和 $n_0$，使得当 $n \ge n_0$ 时：

$$
0 \le T(n) \le c \cdot f(n)
$$

那么记作：

$$
T(n) = O(f(n))
$$

也就是说，大 $O$ 给出了一个**渐近上界**。

例如：

$$
T(n) = 3n^2 + 10n + 100
$$

当 $n$ 足够大时，一定可以找到某个常数 $c$，使得：

$$
3n^2 + 10n + 100 \le c n^2
$$

因此：

$$
T(n) = O(n^2)
$$

### 2.2 大 $\Theta$ 与大 $\Omega$

完整的渐近记号通常有三种：

| 记号 | 含义 | 直观理解 |
| --- | --- | --- |
| $O(f(n))$ | 渐近上界 | 最多增长到这个量级 |
| $\Omega(f(n))$ | 渐近下界 | 至少增长到这个量级 |
| $\Theta(f(n))$ | 紧确界 | 与这个量级同阶增长 |

如果一个算法满足：

$$
T(n) = 3n^2 + 10n + 100
$$

那么更准确地说：

$$
T(n) = \Theta(n^2)
$$

因为它既有 $O(n^2)$ 的上界，也有 $\Omega(n^2)$ 的下界。

<Callout title="算法题中的常见口语习惯" type="info">
刷题和面试里，人们经常用“时间复杂度是 $O(n)$”表达“这个算法的主导增长量级是线性的”。严格数学意义上，很多时候写 $\Theta(n)$ 更精确。
</Callout>

## 3. 最好、平均与最坏情况

同一个算法在不同输入下，执行次数可能不同。

以插入排序为例：

- 输入已经有序：接近 $O(n)$；
- 输入逆序：需要大量移动，达到 $O(n^2)$；
- 一般随机输入：平均也是平方量级。

快速排序也是典型例子：

- 平均情况：$O(n\log n)$；
- 最坏情况：$O(n^2)$；
- 使用随机化或更合理的枢轴选择，可以显著降低频繁出现最坏情况的概率。

![一般情况下的时间复杂度示意](https://file1.kamacoder.com/i/algo/20200728185745611-20230310123844306.png)

因此，当看到一句：

> 快速排序的时间复杂度是 $O(n\log n)$。

最好进一步确认它指的是**平均复杂度、期望复杂度，还是最坏复杂度**。

## 4. 常见复杂度的增长速度

从增长速度看，常见时间复杂度通常满足：

$$
O(1)
< O(\log n)
< O(n)
< O(n\log n)
< O(n^2)
< O(n^3)
< O(2^n)
< O(n!)
$$

可以从“输入规模翻倍后，工作量如何变化”来理解：

| 复杂度 | $n$ 翻倍后的典型变化 | 常见场景 |
| --- | ---: | --- |
| $O(1)$ | 基本不变 | 数组随机访问、哈希表平均查询 |
| $O(\log n)$ | 增加一个常数量级 | 二分查找、平衡树查找 |
| $O(n)$ | 约变为 2 倍 | 单次遍历 |
| $O(n\log n)$ | 略大于 2 倍 | 高效比较排序 |
| $O(n^2)$ | 约变为 4 倍 | 两层完整嵌套循环 |
| $O(n^3)$ | 约变为 8 倍 | 三层完整嵌套循环 |
| $O(2^n)$ | 指数爆炸 | 枚举所有子集 |
| $O(n!)$ | 极快爆炸 | 枚举所有排列 |

<Callout title="算法设计中的关键判断" type="tip">
看到数据范围时，第一反应应该是：这个 $n$ 允许什么数量级的复杂度，而不是立刻开始写代码。
</Callout>

## 5. 为什么可以忽略常数和低阶项

假设：

$$
T(n)=2n^2+10n+1000
$$

化简复杂度时可以分三步。

### 去掉加法常数项

$$
2n^2+10n+1000 \longrightarrow 2n^2+10n
$$

常数 $1000$ 不会随着 $n$ 增长。

### 忽略常数系数

$$
2n^2+10n \longrightarrow n^2+n
$$

常数倍不会改变增长阶。

### 保留最高阶项

$$
n^2+n \longrightarrow n^2
$$

因为：

$$
\lim_{n\to\infty}\frac{n}{n^2}
=
\lim_{n\to\infty}\frac{1}{n}
=0
$$

所以当 $n$ 足够大时，$n$ 相比 $n^2$ 可以忽略。

最终得到：

$$
T(n)=O(n^2)
$$

### 但“大常数”真的永远不用管吗？

不是。

如果两个算法分别是：

$$
T_1(n)=10^8n
$$

和

$$
T_2(n)=n^2
$$

那么在实际可见的数据范围内，线性算法 $T_1$ 可能反而更慢。

因此：

- **复杂度**用于判断规模增长趋势；
- **常数、缓存、语言、实现细节**用于判断真实工程性能。

二者不能互相替代。

## 6. 为什么 $O(\log n)$ 不写底数

设一个算法复杂度为：

$$
O(\log_2 n)
$$

另一个是：

$$
O(\log_{10} n)
$$

根据换底公式：

$$
\log_a n
=
\frac{\log_b n}{\log_b a}
$$

其中：

$$
\frac{1}{\log_b a}
$$

是一个与 $n$ 无关的常数。

因此：

$$
\log_a n = \Theta(\log_b n)
$$

在渐近复杂度中可以统一写成：

$$
O(\log n)
$$

![不同底数的对数复杂度示意](https://file1.kamacoder.com/i/algo/20200728191447349-20230310124032001.png)

<Callout title="什么时候底数仍然值得关注？" type="info">
在理论复杂度里底数通常可以忽略；但在具体算法实现中，二叉、四叉或更高分支结构会影响常数、缓存命中率和真实运行时间。
</Callout>

## 7. 从代码判断时间复杂度

### 7.1 单层循环：$O(n)$

```cpp
for (int i = 0; i < n; ++i) {
    work();
}
```

循环执行约 $n$ 次，因此：

$$
T(n)=O(n)
$$

### 7.2 完整双层嵌套：$O(n^2)$

```cpp
for (int i = 0; i < n; ++i) {
    for (int j = 0; j < n; ++j) {
        work();
    }
}
```

总执行次数约为：

$$
n\times n=n^2
$$

因此：

$$
T(n)=O(n^2)
$$

### 7.3 每次翻倍：$O(\log n)$

```cpp
for (int i = 1; i < n; i *= 2) {
    work();
}
```

若循环执行 $k$ 次，则：

$$
2^k < n
$$

所以：

$$
k < \log_2 n
$$

因此：

$$
T(n)=O(\log n)
$$

### 7.4 外层线性、内层对数：$O(n\log n)$

```cpp
for (int i = 0; i < n; ++i) {
    for (int j = 1; j < n; j *= 2) {
        work();
    }
}
```

外层 $n$ 次，内层 $\log n$ 次：

$$
T(n)=O(n\log n)
$$

## 8. 嵌套循环不一定就是 $O(n^2)$

这是复杂度分析中非常常见的误区。

例如：

```cpp
for (int i = 0; i < n; ++i) {
    for (int j = i; j < n; ++j) {
        work();
    }
}
```

执行次数为：

$$
n+(n-1)+(n-2)+\cdots+1
$$

根据等差数列求和：

$$
\frac{n(n+1)}{2}
$$

所以仍然是：

$$
O(n^2)
$$

但下面这段代码不同：

```cpp
for (int i = 0; i < n; ++i) {
    for (int j = 1; j <= i; j *= 2) {
        work();
    }
}
```

内层第 $i$ 次执行约 $\log i$ 次，总工作量为：

$$
\sum_{i=1}^{n}\log i
=
\log(n!)
$$

由斯特林公式可知：

$$
\log(n!)=\Theta(n\log n)
$$

所以整体复杂度是：

$$
O(n\log n)
$$

<Callout title="判断原则" type="warning">
不要通过“看见几层 for 循环”机械判断复杂度。真正应该计算的是每层循环的执行次数以及它们之间的依赖关系。
</Callout>

## 9. 多变量复杂度：不要强行只写一个 $n$

考虑这样一个问题：有 $n$ 个字符串，每个字符串平均长度为 $m$，需要找出其中重复的字符串。

### 方法一：两两比较

最多比较约 $n^2$ 对字符串，每次字符串比较最坏需要扫描 $m$ 个字符，因此：

$$
T(n,m)=O(mn^2)
$$

注意不能直接写成 $O(n^2)$，因为字符串比较本身不是 $O(1)$。

### 方法二：排序后扫描

假设采用比较排序：

- 排序需要 $O(n\log n)$ 次字符串比较；
- 每次比较最坏为 $O(m)$；
- 排序结束后再扫描相邻字符串，需要 $O(mn)$。

因此：

$$
T(n,m)
=
O(mn\log n+mn)
$$

提取公共因子：

$$
T(n,m)
=
O\bigl(mn(\log n+1)\bigr)
$$

最终：

$$
T(n,m)=O(mn\log n)
$$

这比：

$$
O(mn^2)
$$

增长得更慢。

### 为什么多变量很重要

很多题目天然包含多个独立规模：

- 图：顶点数 $V$、边数 $E$；
- 矩阵：行数 $m$、列数 $n$；
- 字符串集合：字符串数量 $n$、平均长度 $m$；
- 两个数组：长度分别为 $m$ 和 $n$。

如果变量彼此独立，就不应该无依据地把它们都写成同一个 $n$。

## 10. 均摊复杂度：一次很贵，不代表每次都贵

以动态数组 `vector` 为例，尾部插入通常是 $O(1)$，但容量不足时需要扩容并搬移已有元素，一次扩容可能需要 $O(n)$。

为什么仍然常说 `push_back` 的复杂度是**均摊 $O(1)$**？

假设容量每次翻倍：

$$
1,2,4,8,\ldots,n
$$

所有扩容搬移元素的总次数大约是：

$$
1+2+4+\cdots+\frac{n}{2}
< n
$$

再加上 $n$ 次正常插入，总操作量仍然是：

$$
O(n)
$$

因此平均到每一次插入：

$$
\frac{O(n)}{n}=O(1)
$$

这就是均摊分析。

## 11. 常见误区

### 误区一：$O(1)$ 就一定只执行一次

不是。下面代码无论 $n$ 多大，始终执行 1000 次：

```cpp
for (int i = 0; i < 1000; ++i) {
    work();
}
```

它仍然是：

$$
O(1)
$$

因为执行次数与输入规模 $n$ 无关。

### 误区二：$O(n)$ 一定比 $O(n\log n)$ 快

只在渐近意义上成立。对于很小的 $n$，常数项、缓存、函数调用等因素可能改变实际结果。

### 误区三：递归就一定很慢

递归只是代码结构。二分查找的递归实现仍然是：

$$
O(\log n)
$$

真正决定复杂度的是递归树中一共生成多少调用、每层做多少工作。

### 误区四：只分析最深的循环层数

循环边界可能依赖其他变量，也可能呈倍增、递减或摊还特征。必须分析**总执行次数**。

## 12. 一套稳定的复杂度分析流程

以后拿到一段代码，可以按下面的顺序分析。

### 确定输入规模

先明确 $n$ 到底代表什么。若有多个独立规模，用 $m,n,V,E$ 等分别表示。

### 找基本操作

通常是循环体、比较、赋值、哈希查询、字符串比较等真正重复发生的操作。

### 计算执行次数

重点处理：

- 循环次数；
- 嵌套循环；
- 每次乘 2 / 除 2；
- 递归树；
- 数据结构操作本身的复杂度。

### 合并多个阶段

若程序先排序再遍历：

$$
O(n\log n)+O(n)
=
O(n\log n)
$$

若两个独立循环分别扫描长度 $m$、$n$ 的数组：

$$
O(m)+O(n)
=
O(m+n)
$$

### 最后再做渐近化简

去掉常数系数、常数项和低阶项，保留主导增长项。

## 13. 复杂度速查表

| 代码或结构特征 | 典型复杂度 |
| --- | --- |
| 固定次数操作 | $O(1)$ |
| `i++` 扫描整个输入 | $O(n)$ |
| `i *= 2`、`i /= 2` | $O(\log n)$ |
| 两层完整 $n$ 次循环 | $O(n^2)$ |
| 一层 $n$，一层 $\log n$ | $O(n\log n)$ |
| 二分查找 | $O(\log n)$ |
| 归并排序 | $O(n\log n)$ |
| 枚举所有子集 | $O(2^n)$ |
| 枚举所有排列 | $O(n!)$ |
| 图的邻接表 DFS / BFS | $O(V+E)$ |

## 14. 小结

时间复杂度最值得掌握的不是“背表”，而是下面四个思维：

1. **复杂度研究增长趋势，而不是秒数。**
2. **真正分析的是操作总次数，而不是代码有几行。**
3. **遇到多个独立输入规模时，要保留多个变量。**
4. **算法题中的 $O(f(n))$ 经常是主导量级的习惯表达，严格分析时要区分最好、平均、最坏和均摊复杂度。**

如果能熟练完成“确定规模 → 计算次数 → 合并阶段 → 渐近化简”这条链路，绝大多数基础复杂度题都可以稳定判断。

## 15. 多语言示例：识别 $O(n\log n)$

下面三段程序做的是同一件事：外层执行 $n$ 次，内层变量每次翻倍，因此总复杂度均为：

$$
O(n\log n)
$$

### C++

```cpp
void solve(int n) {
    long long count = 0;

    for (int i = 0; i < n; ++i) {
        for (int j = 1; j < n; j *= 2) {
            ++count;
        }
    }
}
```

### Java

```java
static void solve(int n) {
    long count = 0;

    for (int i = 0; i < n; ++i) {
        for (int j = 1; j < n; j *= 2) {
            ++count;
        }
    }
}
```

### Python

```python
def solve(n: int) -> None:
    count = 0

    for _ in range(n):
        j = 1
        while j < n:
            count += 1
            j *= 2
```
