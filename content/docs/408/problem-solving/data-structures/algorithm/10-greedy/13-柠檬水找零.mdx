# 860. 柠檬水找零

[LeetCode 860. 柠檬水找零](https://leetcode.cn/problems/lemonade-change/)

一杯柠檬水售价 $5$ 美元，顾客按照数组 `bills` 的顺序依次付款，每张钞票只可能是：

```text
5, 10, 20
```

你一开始没有任何零钱，并且必须当场为每位顾客正确找零。

如果所有顾客都能完成交易，返回 `true`；否则返回 `false`。

例如：

```text
bills = [5, 5, 5, 10, 20]
```

可以依次完成：

```text
收到 5  -> 无需找零
收到 5  -> 无需找零
收到 5  -> 无需找零
收到 10 -> 找 5
收到 20 -> 找 10 + 5
```

因此答案为 `true`。

## 1. 先不要把它想成“组合搜索”

初看这道题，容易担心：

> 我现在应该怎么找零，才能保证后面的顾客也一定能找开？

如果从“所有未来可能”出发思考，问题看起来像是搜索或动态规划。

但仔细观察钞票面额后会发现，实际状态非常少。

售价恒为 $5$ 美元，所以三种付款分别需要：

| 顾客付款 | 需要找零 | 可行方式 |
| --- | ---: | --- |
| $5$ | $0$ | 无需找零 |
| $10$ | $5$ | 只能找一张 $5$ |
| $20$ | $15$ | $10+5$ 或 $5+5+5$ |

只有收到 $20$ 美元时，才真正存在两种选择。

所以本题可以概括为：

$$
\boxed{\text{固定模拟} + \text{一个局部贪心决策}}
$$

## 2. 只需要维护 5 美元和 10 美元的数量

定义：

```cpp
int five = 0;
int ten = 0;
```

分别记录当前手里的 $5$ 美元和 $10$ 美元钞票数量。

不需要记录 $20$ 美元。

原因很简单：后续顾客最多需要找 $15$ 美元，而 $20$ 美元钞票无法参与任何找零组合。

也就是说，一张 $20$ 美元收到以后只增加收入，但对后续“能否找零”没有帮助。

<Callout type="info" title="状态压缩">
做模拟题时，不要机械记录所有输入类型。真正需要维护的状态，只应该包含“会影响未来决策”的信息。本题中 20 美元数量不会影响任何未来找零，所以完全可以删除这个状态。
</Callout>

## 3. 三种付款分别怎么处理

<Steps>
<Step>

### 收到 5 美元

不需要找零，直接增加一张 $5$：

```cpp
++five;
```

这是唯一处理方式。

</Step>
<Step>

### 收到 10 美元

必须找回 $5$ 美元，因此只能消耗一张 $5$：

```cpp
if (five == 0) {
    return false;
}
--five;
++ten;
```

如果手里没有 $5$ 美元，当前交易立刻失败，而且之后也不可能补救。

</Step>
<Step>

### 收到 20 美元

需要找回：

$$
20-5=15
$$

有两种可能：

```text
10 + 5
5 + 5 + 5
```

这里才出现真正的贪心选择。

</Step>
</Steps>

## 4. 核心贪心：优先用 `10 + 5`

收到 $20$ 美元时，如果两种方案都能使用：

```text
方案 A：10 + 5
方案 B：5 + 5 + 5
```

应该优先选择：

$$
\boxed{10+5}
$$

代码：

```cpp
if (ten > 0 && five > 0) {
    --ten;
    --five;
} else if (five >= 3) {
    five -= 3;
} else {
    return false;
}
```

原因不是“看起来省钞票”，而是：

> $5$ 美元比 $10$ 美元更有用，更应该保留。

## 5. 为什么 5 美元比 10 美元更“宝贵”

看两种钞票的用途：

### 5 美元

可以参与：

- 给 $10$ 美元找零；
- 给 $20$ 美元找零。

### 10 美元

只能参与：

- 给 $20$ 美元找零。

因此 $5$ 美元的适用场景更多。

可以把它理解成一种“资源通用性”：

$$
\text{flexibility}(5)>\text{flexibility}(10)
$$

所以当收到 $20$ 美元、两种方案都可行时，应该尽量消耗用途较窄的 $10$ 美元，而保留用途更广的 $5$ 美元。

<Callout type="success" title="本题的贪心本质">
优先消耗“未来用途更少”的资源，保留“未来用途更多”的资源。这类思想在资源调度、找零、区间安排等题目中都很常见。
</Callout>

## 6. 为什么不能优先用三张 5 美元

假设当前手里有：

```text
five = 4
ten  = 1
```

此时收到一张 $20$。

### 如果使用 `10 + 5`

交易后：

```text
five = 3
ten  = 0
```

接下来即使来一位付 $10$ 的顾客，也可以继续找零。

### 如果使用 `5 + 5 + 5`

交易后：

```text
five = 1
ten  = 1
```

虽然当前交易也完成了，但手里只剩一张 $5$。

再连续来两位支付 $10$ 的顾客时，第二位就会失败。

所以三张 $5$ 的方案会更快消耗最关键的通用零钱。

## 7. 用交换论证证明贪心正确

仅凭“$5$ 更有用”还可以进一步形式化。

假设某个可行方案在收到 $20$ 美元时，同时拥有：

```text
至少 1 张 10
至少 3 张 5
```

但它选择使用：

```text
5 + 5 + 5
```

我们把这一步替换为：

```text
10 + 5
```

比较两种选择后的零钱：

### 原方案

消耗：

$$
3\times5
$$

### 贪心方案

消耗：

$$
10+5
$$

与原方案相比，贪心方案：

- 多保留了两张 $5$；
- 少保留了一张 $10$。

而一张 $10$ 只能用于未来的 $20$ 找零；两张 $5$ 不但也能参与 $20$ 找零，还能分别为两位支付 $10$ 的顾客找零。

因此把“三张 $5$”替换成“$10+5$”不会让未来的可行性变差，只可能让可行性更强。

于是任何使用三张 $5$ 的最优策略，都可以交换成优先使用 `10 + 5` 的策略而不变坏。

所以贪心选择是安全的。

## 8. 为什么当前失败就可以立刻返回 `false`

这道题的顾客顺序是固定的。

如果在处理某个顾客时已经无法找零，那么：

- 不能跳过当前顾客；
- 不能从未来顾客那里提前拿钱；
- 不能改变之前顾客的付款方式；

因此当前状态一旦失败，就不存在任何补救空间。

这也是为什么算法可以在线扫描：

```text
读取一个顾客 -> 更新零钱 -> 必要时立刻失败
```

而不需要回溯。

## 9. 完整过程演示

考虑：

```text
bills = [5, 5, 10, 5, 20, 10, 20]
```

记录状态 `(five, ten)`。

| 顾客付款 | 操作 | 交易后状态 |
| ---: | --- | --- |
| 5 | 收下 5 | `(1, 0)` |
| 5 | 收下 5 | `(2, 0)` |
| 10 | 找 5 | `(1, 1)` |
| 5 | 收下 5 | `(2, 1)` |
| 20 | 优先找 `10 + 5` | `(1, 0)` |
| 10 | 找 5 | `(0, 1)` |
| 20 | 没有 5，无法找 15 | 失败 |

最后一个顾客到来时，虽然我们有一张 $10$，但找 $15$ 仍然至少需要一张 $5$。

因此返回：

```text
false
```

## 10. C++ 标准实现

```cpp
class Solution {
public:
    bool lemonadeChange(vector<int>& bills) {
        int five = 0;
        int ten = 0;

        for (int bill : bills) {
            if (bill == 5) {
                ++five;
            } else if (bill == 10) {
                if (five == 0) {
                    return false;
                }

                --five;
                ++ten;
            } else {  // bill == 20
                // 优先消耗用途更少的 10 美元，保留更通用的 5 美元。
                if (ten > 0 && five > 0) {
                    --ten;
                    --five;
                } else if (five >= 3) {
                    five -= 3;
                } else {
                    return false;
                }
            }
        }

        return true;
    }
};
```

### 复杂度

每位顾客只处理一次：

$$
T(n)=O(n)
$$

只维护两个计数器：

$$
S(n)=O(1)
$$

## 11. 为什么它既像模拟，又是贪心

本题绝大部分逻辑都是确定的：

- 收到 $5$：只能收下；
- 收到 $10$：只能用一张 $5$ 找零；
- 收到 $20$：才出现两种方案。

所以从代码结构看，它很像一道简单模拟题。

但只要存在：

```text
10 + 5
```

和：

```text
5 + 5 + 5
```

两个都合法的方案，就必须做策略选择。

这个策略会影响未来，所以这里就是贪心算法真正发挥作用的地方。

可以把整道题理解成：

$$
\text{状态模拟}+\text{资源保留型贪心}
$$

## 12. 常见错误

### 错误一：收到 20 时优先用三张 5

这样会过度消耗最通用的零钱，使后续支付 $10$ 的顾客更容易失败。

正确优先级是：

```text
10 + 5  >  5 + 5 + 5
```

这里的 `>` 表示“更优先使用”。

### 错误二：记录 20 美元数量并尝试拿它找零

后续最多只需要找 $15$，一张 $20$ 无法参与找零，所以其数量与未来决策无关。

### 错误三：只检查总金额，不检查面额

即使手里零钱总金额足够，也不代表一定能组合出需要的找零。

例如：

```text
five = 0
ten = 2
```

总零钱有 $20$ 美元，但收到 $20$ 美元时需要找 $15$，仍然无法完成。

这说明找零问题不能只看：

$$
\text{零钱总额}
$$

还要看：

$$
\text{面额结构}
$$

### 错误四：等失败以后再尝试回溯

本题不需要回溯。优先 `10 + 5` 已经是不会降低未来可行性的贪心选择，因此可以一路在线处理。

## 13. 如何识别“保留更通用资源”的贪心

如果一个问题中存在多种资源，并且：

- 多种资源都可以完成当前任务；
- 某种资源在未来能应对更多类型的需求；
- 另一种资源用途更窄；

那么一个很重要的思考方向是：

$$
\boxed{\text{优先消耗用途窄的资源，保留用途广的资源}}
$$

本题：

```text
10 美元：只能处理 20 美元付款
5 美元：既能处理 10，也能处理 20
```

所以优先消耗 $10$。

类似思想还会出现在：

- 用有限规格资源匹配任务；
- 区间调度时保留更多未来空间；
- 用特殊能力与通用能力完成任务；
- 多种硬币或票券的在线分配。

## 14. 本题记忆模板

<Callout type="info" title="四句话记住整道题">
收到 5，直接收；收到 10，必须消耗一个 5；收到 20，优先消耗 10+5，其次才是三个 5；任何一步无法找零就立刻返回 false。
</Callout>

伪代码：

```text
five = 0
ten = 0

for bill in bills:
    if bill == 5:
        five += 1

    else if bill == 10:
        if five == 0:
            return false
        five -= 1
        ten += 1

    else:
        if ten > 0 and five > 0:
            ten -= 1
            five -= 1
        else if five >= 3:
            five -= 3
        else:
            return false

return true
```
