## 8. 控制器与三级时序概念

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-001.svg" alt="控制器基本组成" />
<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-002.svg" alt="指令控制器工作过程" />
<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-003.svg" alt="指令周期、机器周期与时钟周期" />

> **真题考查**
>
> - 控制器选择题：2025 年第 19 题
> - 控制器解答题：2022 年第 43 题、2026 年第 44 题

控制器的核心职责是：

- **指令控制**：取指、译码、形成下一条指令地址；
- **操作控制**：产生完成各微操作所需的控制信号；
- **时间控制**：保证微操作在正确时刻、按正确顺序发生；
- **异常/中断控制**：特殊事件出现时改变正常控制流。

### 8.1 时钟周期、机器周期、指令周期

| 概念 | 含义 |
| --- | --- |
| 时钟周期 | CPU 最基本的时序节拍 |
| 机器周期 / CPU 周期 | 完成某个较完整基本操作的一段时间，通常含若干时钟周期 |
| 指令周期 | 取出并执行一条完整机器指令所需的总时间 |

常见层次关系：

```text
指令周期
  └─ 一个或多个机器周期
       └─ 一个或多个时钟周期
```

不同机器、不同教材对“机器周期”的具体划分可能不同，综合题应以题设数据通路及时序图为准。

### 8.2 控制信号

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-004.svg" alt="控制信号发生器" />
<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-005.svg" alt="典型 CPU 内部数据通路与控制信号" />

典型信号包括：

- `MemR`、`MemW`：主存读/写；
- `Rout`：某寄存器驱动数据通路；
- `Rin`：把当前输入锁存到寄存器；
- `ALUop`：选择 ALU 运算；
- `MUXop`：选择 MUX 输入。

<Callout type="warning" title="Rout 与 Rin 不要写反">
`Rout` 是“从寄存器读出并驱动总线”，`Rin` 是“把数据写入寄存器”。
</Callout>

## 9. 寄存器传送语言 RTL

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-006.svg" alt="寄存器传送语言 RTL" />
<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-007.svg" alt="RTL 基本语法" />
<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-008.svg" alt="取指与译码阶段数据通路" />

RTL（Register Transfer Language）用来描述 CPU 内部的数据传送和基本微操作。

| 写法 | 含义 |
| --- | --- |
| `R1 ← R2` | `R2` 内容送入 `R1` |
| `R1 ← R2 + R3` | ALU 加法后结果写入 `R1` |
| `M[x]` | 地址 `x` 对应的存储单元 |
| 逗号 `,` | 资源允许时可在同一时钟周期并行完成 |

### 9.1 并行与顺序微操作

资源允许时：

```text
MAR ← PC, PC ← PC + 4
```

可以在同一时钟周期并行完成。

而：

```text
MAR ← PC
MDR ← M[MAR]
IR  ← MDR
```

通常跨越多个时钟节拍，因为后一步依赖前一步产生的结果。

### 9.2 主存读写的 RTL

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-009.svg" alt="ADD R0 (R1) 执行阶段数据通路" />

读：

```text
MAR ← 地址
MDR ← M[MAR]
```

写：

```text
MAR ← 地址
MDR ← 待写数据
M[MAR] ← MDR
```

<Callout type="info" title="能否同拍执行要看数据通路">
RTL 中用逗号写在同一拍，只说明“逻辑上希望并行”。是否真的能同拍完成，还必须检查总线数量、端口数量、ALU 输入来源以及是否存在数据依赖。
</Callout>

## 10. 从 RTL 推导控制信号

以抽象指令：

```text
ADD R0, (R1)
```

为例，其语义是：

```text
R0 ← R0 + M[R1]
```

一种可能的执行序列是：

```text
MAR ← PC
MDR ← M[MAR]
IR  ← MDR
PC  ← PC + 指令长度

MAR ← R1
MDR ← M[MAR]
T   ← R0
R0  ← T + MDR
```

由某一步 RTL 推控制信号时，只需逐项问：

1. **谁提供源数据？** → 对应 `Rout` 或 MUX 选择；
2. **数据送到哪里？** → 对应 `Rin`；
3. **是否经过 ALU？** → 对应 `ALUop`；
4. **是否访问主存？** → 对应 `MemR/MemW`；
5. **是否存在共享总线冲突？** → 判断是否必须拆成多个时钟周期。

例如：

```text
MAR ← R1
```

通常需要：

```text
R1out, MARin
```

而：

```text
R0 ← T + MDR
```

需要让 `T`、`MDR` 成为 ALU 的两个输入，并选择加法，最后使 `R0` 锁存结果。

> **数据通路大题通用方法**
>
> **先写 RTL，再推控制信号；不要反过来死背某张控制表。**

## 11. 硬布线控制器

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-010.svg" alt="硬布线控制器结构" />

> **真题考查**
>
> - 硬布线/微程序控制：2009 年第 17、19 题，2012 年第 18 题，2014 年第 18 题，2024 年第 13 题等

硬布线控制器根据：

- 指令译码结果；
- 当前时序状态；
- 条件标志；
- 外部状态信号；

由固定逻辑直接产生控制信号。

某个控制信号可抽象写成：

$$
C_i=f(\text{Opcode},\text{Timing},\text{Flags},\text{State})
$$

从行为上看，它可以建模为有限状态机。

| 特点 | 说明 |
| --- | --- |
| 速度快 | 无需读取控制存储器 |
| 延迟低 | 组合逻辑直接形成控制信号 |
| 修改困难 | 改指令控制逻辑往往意味着修改硬件 |
| 复杂度上升快 | 指令和状态复杂时，逻辑设计容易膨胀 |

## 12. 微程序控制器

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-011.svg" alt="微程序控制器基本结构" />
<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-012.svg" alt="控制存储器中的微指令" />

微程序控制器仍然是**硬件控制器的一种实现方式**，并不是让普通软件去控制 CPU。

它将控制信号编码成**微指令**，存放于专门的**控制存储器**中。

常见部件：

- 控制存储器 `CM`；
- 微地址寄存器 / 微程序计数器 `µPC`；
- 微指令寄存器 `µIR`；
- 微地址形成部件；
- 微命令译码/输出逻辑。

基本流程：

```text
机器指令进入 IR
      ↓
根据操作码形成微程序入口地址
      ↓
µPC 指向控制存储器
      ↓
取微指令到 µIR
      ↓
发出一组微命令
      ↓
形成下一微地址
      ↓
继续取下一条微指令
```

### 12.1 下一微地址从哪里来

“下一条微指令地址”不是永远简单地执行 $\mu PC+1$。常见来源有：

1. **顺序地址**：当前微地址加 $1$；
2. **微指令给出的转移地址**：无条件转到指定微地址；
3. **条件转移**：结合条件码、外部状态或测试字段选择下一地址；
4. **机器指令操作码映射**：一条新机器指令开始时，由 `IR` 中的操作码形成其微程序入口。

因此微指令常可抽象成：

```text
┌──────── 微命令字段 ────────┬── 判别/转移字段 ──┬── 下地址字段 ──┐
│ 本拍让数据通路做什么       │ 下一地址怎么选     │ 候选微地址      │
└────────────────────────────┴───────────────────┴────────────────┘
```

<Callout type="info" title="微程序控制器的两条链">
一条是**数据通路控制链**：微命令 → 微操作；另一条是**微地址控制链**：当前微指令 + 条件 → 下一微地址。大题把这两条链分开写，通常更清楚。
</Callout>

<Callout type="warning" title="微程序 ≠ 普通程序">
微程序位于控制器内部，服务于机器指令的实现；普通程序运行在 ISA 层面，由机器指令组成。二者处在不同抽象层级。
</Callout>

## 13. 微操作、微命令、微指令与微程序

四个概念必须按“控制关系”区分：

### 13.1 微操作

CPU 内部最基本的数据处理或传送动作，例如：

```text
MAR ← PC
```

### 13.2 微命令

控制器发出的、促使某个微操作发生的控制信号，例如：

```text
PCout
MARin
```

### 13.3 微指令

一条微指令通常包含：

- 本拍需要发出的若干微命令；
- 下一条微指令地址的形成信息。

一条微指令可以同时包含多个互不冲突的微命令。

### 13.4 微程序

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-016.svg" alt="指令、微程序、微指令与微命令关系" />

为实现**一条机器指令**而按顺序执行的一组微指令。

关系可记为：

```text
机器指令
   ↓
微程序
   ↓
多条微指令
   ↓
每条微指令含若干微命令
   ↓
微命令驱动微操作
```

## 14. 微指令编码方式

### 14.1 直接编码

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-013.svg" alt="微指令直接编码" />

每一位直接对应一条微命令。

```text
D7 D6 D5 D4 ...
│  │  │
│  │  └─ ALU_ADD
│  └──── RB_load
└─────── RA_load
```

优点：

- 无需额外译码；
- 控制速度快；
- 并行性强。

缺点：

- 微指令字较长；
- 控制存储器容量增大。

通常具有**水平型微指令**的特征。

### 14.2 字段编码

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-014.svg" alt="微指令字段编码" />

把互斥微命令放入同一字段，再译码得到具体控制信号。例如：

```text
F1：寄存器操作
00 → 无操作
01 → RA_load
10 → RB_load

F2：ALU 操作
00 → 无操作
01 → ADD
10 → SUB
```

不同字段之间仍可并行，而同一字段内通常只能选一种微命令。

优点是微指令较短；代价是需要译码，且并行能力通常低于直接编码。

### 14.3 混合编码

<InlineSvg src="/images/computer-organization/computer-organization-cpu-controller-015.svg" alt="微指令混合编码" />

重要、高频控制信号可直接编码，其余信号采用字段编码，以折中：

- 微指令长度；
- 控制速度；
- 并行能力；
- 控制存储器容量。

### 14.4 微命令字段位数怎样算

这是微程序计算题最常见的入口。

#### 直接编码

若共有 $m$ 个独立控制信号，且每一位直接对应一个微命令，则微命令字段通常至少需要：

$$
m\ \text{bit}
$$

#### 字段编码

若某一字段中有 $n$ 个**互斥**微命令，并且还需要表示“本字段不发命令”，则该字段至少需要：

$$
\left\lceil \log_2(n+1) \right\rceil\ \text{bit}
$$

若题目明确“不需要空操作编码”，才按 $\lceil\log_2 n\rceil$ 计算。

例如某字段含 5 个互斥微命令并需保留“无操作”：

$$
\left\lceil\log_2(5+1)\right\rceil=3\ \text{bit}
$$

<Callout type="warning" title="先分组，再取对数">
字段编码不是把所有微命令总数直接取对数。应先依据“哪些微命令绝不可能同拍出现”划分互斥组，每组分别计算位数，再把各字段位数相加。
</Callout>

### 14.5 控制存储器容量与微地址位数

若控制存储器共有 $N$ 个微指令字，则寻址全部微地址至少需要：

$$
k=\left\lceil\log_2 N\right\rceil\ \text{bit}
$$

若每条微指令字长为 $W$ bit，则控制存储器容量为：

$$
N\times W\ \text{bit}
$$

反过来，若微地址字段有 $k$ bit，最多可直接区分：

$$
2^k
$$

个微地址。

> **综合题计算顺序**
>
> `互斥组 → 各控制字段位数 → 判别字段 → 下地址字段 → 微指令总字长 → CM 总容量`

### 14.6 水平型与垂直型：不要和某一种编码法机械绑定

- **水平型微指令**：一条微指令可并行发出较多微命令，字长通常较长、并行性较强；
- **垂直型微指令**：更像“操作码 + 操作数”式编码，字长较短，但需要较多译码，单条微指令并行能力通常较弱。

直接编码是水平型的典型形式。字段编码的具体归类要看题设格式，不要只看到“有字段”就机械判为垂直型。

### 14.7 硬布线与微程序控制对比

| 比较项 | 硬布线控制 | 微程序控制 |
| --- | --- | --- |
| 控制信号来源 | 固定逻辑网络 | 控制存储器中的微指令 |
| 速度 | 通常更快 | 通常相对较慢 |
| 修改 | 困难 | 相对容易 |
| 复杂指令实现 | 逻辑复杂 | 更灵活 |
| 设计思想 | “算出”控制信号 | “读出”控制信号 |
