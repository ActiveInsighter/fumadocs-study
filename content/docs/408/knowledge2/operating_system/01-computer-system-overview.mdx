遇到“某操作能否在用户态完成”“是否必须由操作系统完成”一类题目，优先判断该操作是否会：

* 直接控制关键硬件；
* 修改中断、页表、地址转换等系统关键状态；
* 影响其他进程或破坏资源保护；
* 需要操作系统统一管理全局资源。

若答案是肯定的，通常必须由**内核态代码**完成。但“用户程序可以发起请求”与“用户程序可以亲自完成该操作”是两回事。

</Callout>

## 1. 操作系统的基本概念、功能与接口

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-001.svg" alt={"用户 系统程序 应用程序 用户程序 依赖库 系统调用 操作系统 计算机硬件 更加抽象 更偏底层 用户模式 内核模式"} />

**操作系统（Operating System，OS）**&#x2060;是控制和管理整个计算机系统软硬件资源、合理组织计算机工作与资源分配，并为用户和其他软件提供方便接口与运行环境的系统软件。

从 408 角度，可以用三个视角理解操作系统：

| 视角 | 核心含义 | 典型体现 |
| --- | --- | --- |
| 资源管理者 | 对共享软硬件资源进行统一管理 | 处理机、内存、文件、设备 |
| 资源抽象层 | 把复杂硬件抽象成更容易使用的对象 | 进程、文件、虚拟地址空间 |
| 服务与接口提供者 | 向用户和程序提供受控使用系统的入口 | 命令接口、系统调用 |

典型管理对象包括：

* **处理机管理**：进程/线程调度、CPU 分配；
* **存储器管理**：内存分配、回收、地址转换、虚拟内存；
* **文件管理**：文件、目录、外存空间；
* **设备管理**：I/O 设备分配、驱动与控制；
* 进程通信、网络等其他共享资源。

### 1.1 用户接口与程序接口

操作系统提供的接口可分为两大类：

| 接口 | 面向对象 | 典型形式 |
| --- | --- | --- |
| 命令接口 | 普通用户 | Shell 命令、批处理脚本、图形界面等 |
| 程序接口 | 应用程序 | **系统调用（System Call）** |

命令解释程序（如 Shell）本身通常是普通用户进程，并不意味着“只要属于操作系统配套程序就必须运行在内核态”。

<Callout type="warn" title="程序接口 = 系统调用接口">

系统调用是应用程序请求内核服务的接口。不同操作系统的系统调用集合、编号、参数约定和 ABI 可以不同，因此不能说“所有操作系统都为应用程序提供完全统一的系统调用接口”。

</Callout>

> **真题考察**
>
> * 2019 年真题考查过“系统调用是否为统一接口”以及“系统调用是否属于内核提供的服务接口”。

## 2. 操作系统的四个基本特征

操作系统的四个基本特征是：

> **并发、共享、虚拟、异步。**

其中，**并发与共享互为存在条件**，也是理解多道程序系统的基础。

### 2.1 并发与并行

**并发（Concurrency）**：多个事件在**同一时间间隔内**发生或推进。

**并行（Parallelism）**：多个事件在**同一时刻**真正同时发生。

| 对比项 | 并发 | 并行 |
| --- | --- | --- |
| 时间含义 | 同一时间段 | 同一时刻 |
| 单核 CPU | 可以实现 | 同一时刻通常只能执行一个指令流 |
| 多核/多处理器 | 可以实现 | 可以真正并行执行多个任务 |

单核处理器中，多进程往往通过快速切换形成“宏观同时”的效果：

```text
时间 →
A: ███       ███
B:    ███       ███
C:       ███
```

<Callout type="warn" title="“同时运行”不等于“同一时刻并行执行”">

操作系统题目中的“多个程序同时运行”经常只是指**并发推进**。除非题目明确给出多核、多处理器或多个执行单元，否则不要直接推断为真正并行。

</Callout>

### 2.2 共享

**共享（Sharing）**&#x2060;是指系统资源可供多个并发执行的进程共同使用。

主要有两种共享方式：

1. **互斥共享**：某一时刻只允许一个进程访问，例如打印机、临界资源；
2. **同时共享**：允许多个进程在同一时间段共同访问，例如多个进程读取同一个只读文件。

“同时共享”中的“同时”通常是宏观意义，不要求每个物理时刻都真正并行访问。

并发与共享的关系：

* 若多个程序不能并发运行，就很难形成典型的共享资源竞争；
* 若资源完全不能共享，多道程序并发运行的意义和效率会大幅降低。

### 2.3 虚拟

**虚拟（Virtualization）**&#x2060;是把一个物理实体转换成若干逻辑上的对应物，使使用者感觉自己拥有较独立的资源。

| 物理资源 | 虚拟后的逻辑效果 | 典型技术 |
| --- | --- | --- |
| 一颗 CPU | 多个进程仿佛分别拥有处理器 | 时分复用、调度 |
| 有限主存 | 每个进程拥有独立虚拟地址空间 | 虚拟内存、地址转换 |
| I/O 设备 | 多个作业仿佛分别使用逻辑设备 | SPOOLing 等 |
| 一台物理主机 | 多台相互隔离的虚拟机 | Hypervisor |

常见复用思想：

* **时分复用**：多个任务轮流使用同一资源；
* **空分复用**：多个任务占用同一资源的不同空间部分。

### 2.4 异步

**异步（Asynchronism）**&#x2060;是指在多道程序环境中，各进程以不可预知的速度向前推进。

```text
运行 → 发起 I/O → 阻塞 → 被唤醒 → 就绪 → 再次运行
```

异步性的来源包括调度时机、I/O 完成时间、资源竞争等。

<Callout type="warn" title="异步不等于结果随机">

异步描述的是**推进速度和执行时机具有不确定性**，并不意味着程序的逻辑结果可以任意变化。正确的同步互斥机制仍应保证预期结果。

</Callout>

## 3. 操作系统的发展历程

<InlineSvg src="/images/operating-system/operating-system-concepts-concept-001.svg" alt={"手工操作 阶段 联机批处理 脱机批处理 执行系统 批处理（单道） 多道程序系统 多道批处理 系统 分时系统 实时系统 操作系统形成 个人计算机操作系统 网络操作系统 分布式操作系统"} />

操作系统的发展主线可以记为：

```text
手工操作
   ↓
单道批处理
   ↓
多道批处理
   ↓
分时系统 / 实时系统
```

每一次演进，本质上都是在解决前一阶段的主要矛盾。

### 3.1 手工操作阶段

早期没有操作系统，程序员需要直接操作机器完成装入、启动和结果处理。

主要矛盾是：

> **人机速度矛盾。**

CPU 很快，而人工装入和操作很慢，因此处理器大量时间处于空闲状态。

### 3.2 单道批处理系统

多个作业预先形成批次，系统自动按顺序逐个执行。

优点：

* 减少人工干预；
* 作业之间可自动衔接。

核心缺点：

> 当前作业等待 I/O 时，CPU 仍可能空闲。

因此资源利用率依旧不高。

### 3.3 多道批处理系统

**多道程序技术**允许多个程序同时进入内存。当一个程序因为 I/O 等待而不能继续时，CPU 转而执行另一个程序。

```text
进程 A：计算 → I/O 等待 ─────→ 计算
CPU   ：执行 A → 执行 B → 执行 C → 执行 A
```

本质不是“单核 CPU 在同一时刻执行多个程序”，而是：

> **把一个程序的 I/O 等待时间与其他程序的 CPU 计算时间重叠。**

主要优点：

* 提高 CPU 利用率；
* 提高设备利用率；
* 提高系统吞吐量。

主要缺点：

* 用户交互性较弱；
* 作业周转时间可能较长；
* 系统管理复杂度显著提高。

### 3.4 分时系统

分时系统把 CPU 时间划分为较短的**时间片**，让多个用户或任务轮流获得 CPU。

典型特征：

* 多用户；
* 交互性强；
* 响应较及时；
* 依赖时间片与调度机制。

分时系统追求的核心目标是：

> **较快的人机交互响应。**

### 3.5 实时系统

实时系统要求：

> **在规定的时间约束内对外部事件作出响应并完成相应任务。**

| 类型 | 截止时间要求 | 典型场景 |
| --- | --- | --- |
| 硬实时 | 截止时间必须满足，错过可能造成严重后果 | 飞行控制、工业安全控制 |
| 软实时 | 偶尔错过截止时间通常只降低服务质量 | 多媒体、部分通信业务 |

三类典型系统的目标对比：

| 系统 | 首要目标 |
| --- | --- |
| 多道批处理 | 提高资源利用率和吞吐量 |
| 分时系统 | 缩短响应时间、增强交互性 |
| 实时系统 | 满足时间约束和可预测性 |

## 4. 操作系统的引导过程

<InlineSvg src="/images/operating-system/operating-system-concepts-concept-002.svg" alt={"OSBootProcess"} />

操作系统主体通常存放在外存，而 CPU 上电后必须先从规定位置取得最初的指令，因此需要通过**逐级加载**完成启动。

典型流程：

```text
加电 / 复位
    ↓
固件 BIOS / UEFI
    ↓
硬件初始化并选择启动设备
    ↓
引导加载程序 Bootloader
    ↓
把操作系统内核装入内存
    ↓
内核初始化
    ↓
启动系统进程 / 服务
    ↓
进入正常运行状态
```

### 4.1 BIOS、UEFI 与初始引导

上电后，CPU 从体系结构规定的复位入口开始执行固件代码。

固件典型职责：

* 基本硬件检测与初始化；
* 确定启动设备；
* 找到下一阶段的引导程序并把控制权交给它。

传统系统常使用 BIOS；现代系统更多使用 UEFI。UEFI 可从 EFI System Partition（ESP）加载 `.efi` 程序。

<Callout type="warn" title="GPT 不是启动程序">

**GPT 是磁盘分区表格式。**&#x2060;现代系统常见“UEFI + GPT”组合，但 GPT 本身不是 Bootloader，也不能简单理解为“UEFI 从 GPT 首扇区执行启动程序”。

</Callout>

### 4.2 Bootloader

**引导加载程序（Bootloader）**&#x2060;的核心任务是：

> 找到操作系统内核，将其装入内存，并把控制权转交给内核入口。

典型例子有 GRUB、Windows Boot Manager。

### 4.3 内核初始化

内核获得 CPU 控制权后，需要建立操作系统运行所需的关键环境，例如：

* 初始化内存管理；
* 建立中断、异常处理机制；
* 初始化调度与时钟；
* 初始化设备及驱动；
* 建立内核数据结构；
* 挂载必要文件系统；
* 启动首批系统进程和系统服务。

<Callout type="info" title="引导过程中的层层接力">

前一阶段只需要具备足够能力去加载“下一阶段”，不必一开始就具备完整操作系统功能。理解这种逐级接力，比死记不同平台上的具体文件名更重要。

</Callout>

## 5. 用户态与内核态

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-002.svg" alt={"CPU 特权级边界：Ring 0 (内核态) ↔ Ring 3 (用户态) Ring 3 用户态 Ring 2 Ring 1 Ring 0 内核态 最高权限 权限：内 高 → 外 低 Linux/Windows 仅使用 Ring 0 与 Ring 3 用户态 (Ring 3) — 受限 ✓ 执行普通指令 (ALU, MOV, JMP) ✓ 访问自己的用户空间 (代码/数据/堆栈) ✓ 调用库函数 (printf, malloc) ✗ 执行特权指令"} />

用户态和内核态的本质是：

> **处理器硬件提供的不同运行权限级别。**

处理器通常在程序状态字（PSW）或等价的控制状态中保存当前运行模式。操作系统利用这种硬件机制把普通应用与内核隔离。

以 x86 的经典特权环表示为例：

| 特权级 | 常见用途 |
| --- | --- |
| Ring 0 | 操作系统内核 |
| Ring 3 | 普通用户程序 |

现代桌面和服务器操作系统通常主要使用这两个级别。

### 5.1 内核态

在内核态下，处理器具有高权限，可以执行涉及系统核心资源的操作，例如：

* 进程调度；
* 内存和页表管理；
* 中断处理；
* 文件系统核心操作；
* 设备与 I/O 控制；
* 时钟管理。

### 5.2 用户态

普通应用程序通常运行在用户态，例如浏览器、编辑器、游戏和 Shell。

用户程序可以：

* 进行普通算术、逻辑和控制转移；
* 调用普通函数与大多数库函数；
* 访问自己被允许访问的虚拟地址空间；
* **执行系统调用入口指令，请求进入内核。**

但用户程序不能在用户态直接完成修改页表、关闭中断、直接控制关键 I/O 设备等高权限操作。

> **真题考察**
>
> * 2011 年真题考查过“哪些程序/操作在用户态执行”。
> * 2024 年真题强调：中断“发生的瞬间”未必已经处于内核态，但**中断处理程序开始执行时必须处于内核态**。

## 6. 特权指令、非特权指令与访管指令

### 6.1 特权指令

**特权指令（Privileged Instruction）**&#x2060;只能在高特权级状态下正常执行，典型操作包括：

* 设置中断屏蔽或开/关中断；
* 修改页表基址或地址转换关键寄存器；
* 修改内存保护机制；
* 设置某些系统控制寄存器；
* 直接控制某些 I/O 设备；
* 设置定时器等系统级硬件状态。

让这些指令只能由内核执行，是操作系统实现保护的硬件基础之一。

### 6.2 非特权指令

普通算术、逻辑、比较、跳转和一般数据传送指令通常属于非特权指令，例如概念上的：

```text
ADD
SUB
MOV
CMP
JMP
```

但“非特权”只说明该指令**允许在用户态执行**，不代表它一定执行成功。例如普通访存指令访问非法地址，仍可能触发保护异常或缺页异常。

### 6.3 访管 / Trap / 系统调用入口指令

这是高频易错点：

> 用于发起系统调用的 Trap、`syscall`、`svc` 等入口指令，必须允许用户程序执行，因此**它本身通常不是“只能在内核态执行的特权指令”**。

其作用是让处理器通过硬件规定的受控入口：

```text
用户态
  ↓ 执行系统调用入口指令
硬件检查并切换到高特权级
  ↓
内核入口 / 系统调用处理程序
```

如果系统调用入口指令本身只能在内核态执行，用户程序反而无法合法请求内核服务。

> **真题考察**
>
> * 2026 年真题明确考查：系统调用指令可在用户态执行，因此不属于“只能在内核态执行”的特权指令。

### 6.4 用户态操作判断法

通常可以直接在用户态完成：

* 普通计算；
* 普通函数调用；
* 修改自己的普通变量；
* 访问自身合法地址空间；
* 执行系统调用入口指令以**请求**内核服务。

通常必须由内核态代码完成：

* 控制关键 I/O 设备；
* 修改页表和内存保护；
* 修改中断状态；
* 进行全局进程调度；
* 分配和回收全局系统资源；
* 真正执行需要高权限的系统服务。

## 7. 中断、异常与系统调用的统一框架

CPU 执行程序时，控制流可能因为外部事件、当前指令执行条件或用户程序主动请求而进入内核。

| 类型 | 典型来源 | 与当前指令关系 | 同步性 | 对当前程序而言 |
| --- | --- | --- | --- | --- |
| 外部中断 | 时钟、磁盘、网卡 | 通常无直接关系 | 异步 | 被动 |
| 异常 | 除零、缺页、非法指令、保护错误 | 直接相关 | 同步 | 被动 |
| 系统调用 | 用户程序执行访管/系统调用指令 | 直接相关 | 同步 | **主动请求** |

三者都可能导致：

```text
用户态 → 内核态
```

但触发来源、是否主动以及处理语义不同。

<Callout type="warn" title="教材术语可能存在口径差异">

一些教材把“异常”统称为**内中断**，并把系统调用通过 Trap/访管指令产生的陷入也放在广义异常/内中断框架下。做题时应抓住本质：**外部中断来自 CPU 外部；普通异常由当前指令执行条件触发；系统调用是程序主动请求 OS 服务。**

</Callout>

---

## 8. 中断

**中断（Interrupt）**&#x2060;通常指由处理器外部事件引起的中断请求，例如：

* 时钟中断；
* 磁盘 I/O 完成；
* 网卡收到数据；
* 外部设备状态变化。

典型过程：

```text
当前程序执行
    ↓
外部设备产生中断请求
    ↓
CPU 完成本次指令后检查并响应中断
    ↓
硬件保存关键返回信息并进入内核入口
    ↓
OS 保存必要软件现场、执行中断服务程序
    ↓
恢复现场并返回
```

外部中断最重要的特点是**异步性**：它通常不是“当前执行的那条指令本身”导致的。

### 8.1 中断响应中的硬件与软件分工

408 很喜欢考“哪一步必须由硬件完成”。可以按下面的思路理解：

| 工作 | 典型承担者 | 原因 |
| --- | --- | --- |
| 响应中断、切换处理器模式 | 硬件 | 必须先建立可信入口 |
| 保存断点（PC）与关键状态（如 PSW） | 硬件 | 不保存就无法可靠返回 |
| 根据中断向量找到入口 | 硬件机制配合系统设置 | 保证进入预设处理程序 |
| 保存通用寄存器 | OS 中断入口代码 | 属于软件现场保护 |
| 执行具体中断服务 | OS / 驱动 | 处理实际事件 |
| 恢复现场并执行中断返回 | OS + 特殊硬件返回机制 | 恢复原执行流 |

具体体系结构保存哪些寄存器可能不同，但考试中的稳定判断是：**断点必须由硬件及时保存；通用寄存器通常由软件保存。**

### 8.2 时钟中断的作用

时钟中断使操作系统可以周期性重新获得 CPU 控制权，从而支持：

* 时间片管理；
* 抢占式调度；
* CPU 时间统计；
* 定时事件处理。

<Callout type="info" title="为什么抢占式系统离不开时钟中断">

如果用户程序一直运行且不主动进入内核，而硬件又没有周期性时钟中断，操作系统就很难按预定时间重新获得 CPU 控制权。时钟中断为调度器提供了重要的受控入口。

</Callout>

> **真题考察**
>
> * 2024 年真题考查中断发生时与中断处理程序执行时的 CPU 模式。
> * 2026 年真题考查中断响应中“保存断点”必须由硬件完成，而保存通用寄存器等工作可由软件完成。

## 9. 异常

**异常（Exception）**&#x2060;通常由当前正在执行的指令及其执行条件引起，因此具有明显的**同步性**。

常见异常：

* 除零；
* 非法指令；
* 地址越界或保护错误；
* 缺页；
* 其他由当前指令触发的处理器异常。

“同步”的含义是：在相同机器状态和执行路径下，执行到相应指令时会在可确定的位置触发异常。

### 9.1 Fault、Trap 与 Abort 的理解

不同体系结构命名存在差异，可以只抓住以下典型语义：

| 类型 | 典型含义 | 是否可能恢复并继续 |
| --- | --- | --- |
| Fault | 执行当前指令时发现可处理问题 | 处理后可能重新执行当前指令，如缺页 |
| Trap | 有意触发或在指令执行后报告的陷入 | 常用于调试或受控进入系统 |
| Abort | 严重错误 | 通常难以恢复 |

408 不应死扣不同体系结构的具体命名，而应优先判断**异常是否由当前指令同步触发、是否能恢复**。

### 9.2 缺页为什么属于异常

缺页通常发生在 CPU 执行某条访存指令时：虚拟地址合法，但目标页当前不在主存。它与当前指令直接相关，因此属于同步异常，而不是外部中断。

若缺页可以处理：

```text
访存指令触发缺页
      ↓
进入缺页异常处理程序
      ↓
把所需页面调入内存
      ↓
更新页表
      ↓
重新执行导致缺页的访存指令
```

## 10. 系统调用

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-003.svg" alt={"用户程序执行 发起系统调用 执行系统调用 从系统调用返回 用户态 内核态 ① ② ③ ④"} />

**系统调用（System Call）**&#x2060;是用户程序请求操作系统内核服务的受控程序接口。

常见请求包括：

* 创建、终止和管理进程；
* 打开、读写文件；
* 使用网络；
* 申请系统级资源；
* 请求设备相关服务。

### 10.1 系统调用的基本执行过程

更完整的过程可以拆成“用户软件准备 + 硬件陷入 + 内核处理 + 硬件返回”四段：

```text
用户程序 / 库函数封装
        ↓
准备系统调用号和参数
        ↓
执行 syscall / trap / svc 等入口指令
        ↓
[硬件] 保存必要返回信息、切换到内核态、转入内核入口
        ↓
[OS] 保存通用寄存器，检查参数和系统调用号
        ↓
[OS] 执行对应系统调用服务例程
        ↓
[OS] 准备返回值并恢复软件现场
        ↓
[硬件返回机制] 恢复用户态继续执行
```

<Callout type="info" title="不要把“进入内核态”全部算成 OS 软件做的">

执行系统调用入口指令后，处理器的**模式切换、关键返回状态保存、跳转到受控入口**通常依赖硬件自动机制；进入内核后，保存通用寄存器、参数检查、执行服务例程等才是操作系统软件的工作。

</Callout>

### 10.2 系统调用与普通函数调用

| 对比项 | 普通函数调用 | 系统调用 |
| --- | --- | --- |
| 调用目标 | 当前程序或用户态库函数 | 内核服务 |
| 是否必然进入内核 | 否 | 是 |
| 是否发生特权级转换 | 通常否 | 是 |
| 是否涉及受控陷入机制 | 否 | 是 |
| 开销 | 通常较小 | 通常较大 |
| 典型用途 | 算法、字符串处理 | 文件、进程、设备、网络 |

**库函数不等于系统调用。**

例如：

```c
strlen(s);
```

通常完全在用户态执行，不需要进入内核。

而文件读取类库函数最终往往会封装一个或多个系统调用。还有些库函数会先使用用户态缓冲，只有必要时才真正系统调用，因此不能简单用“函数名”判断进入内核的次数。

> **真题考察**
>
> * 2019 年真题考查系统调用是内核向应用提供服务的接口，且不同 OS 的系统调用接口并非完全统一。
> * 2022 年真题考查系统调用过程中“硬件完成模式切换/保存断点”与“OS 保存通用寄存器/执行服务程序”的分工。
> * 2024、2026 年真题继续考查系统调用入口、内核服务程序与 CPU 运行模式的关系。

---

## 11. 模式切换与进程上下文切换

这是本章最重要的易错点之一。

系统调用一定会发生：

> **用户态 → 内核态的模式/特权级转换。**

但不一定发生：

> **进程 A → 进程 B 的上下文切换。**

例如：

```text
进程 A（用户态）
      ↓ system call
进程 A（内核态）
      ↓ return
进程 A（用户态）
```

整个过程仍可能始终是进程 A 在执行。

只有当：

* A 因系统调用而阻塞；
* A 的时间片用完；
* 出现更高优先级任务；
* 调度器因为其他原因选择了 B；

才会进一步发生真正的进程/线程上下文切换。

| 事件 | 权限级可能变化 | 执行主体一定变化吗 |
| --- | --- | --- |
| 系统调用 | 用户态 → 内核态 | **不一定** |
| 异常处理 | 用户态可进入内核态 | **不一定** |
| 中断处理 | 可进入内核态 | **不一定** |
| 进程上下文切换 | 可能发生 | **一定换执行主体** |

<Callout type="warn" title="模式切换 ≠ 进程切换">

模式切换描述**CPU 权限状态**变化；上下文切换描述**CPU 当前执行的进程/线程**发生变化。二者是两个维度，不能画等号。

</Callout>

### 11.1 x86 系统调用入口示意

早期 32 位 x86 Linux 中常见：

```asm
int 0x80
```

现代 x86-64 常使用专门的快速系统调用机制，例如：

```text
syscall
sysret
```

不同体系结构的具体指令不同，但共同目标都是：

> **让用户程序只能通过预设、可检查的受控入口进入内核，而不能任意跳转到内核代码。**

## 12. 程序的链接

源程序经过编译/汇编后常形成多个目标模块。生成最终可执行程序前，需要由**链接器（Linker）**&#x2060;把目标模块及所需库组合起来，并解决符号引用和地址关系。

链接主要分为：

* 静态链接；
* 动态链接。

### 12.1 静态链接

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-004.svg" alt={"printf.o strlen.o rand.o libc.a foo.o bar.o baz.o libstrange.a Static Linker main.o main.o printf.o baz.o main.o printf.o baz.o prog.exe prog.exe 拷贝到另一台机器 Static Linking"} />

静态链接时，程序所需的库代码在链接阶段被复制到最终可执行文件中。

```text
main.o + libxxx.a
        ↓
      Linker
        ↓
   可执行文件
```

主要特点：

* 可执行文件通常较大；
* 运行时对相应共享库依赖较少；
* 多个程序可能各自保存重复库代码；
* 库更新后通常需要重新链接程序。

静态链接不意味着程序“到任何机器都能直接运行”。程序仍受 CPU 指令集、ABI、可执行文件格式、系统调用 ABI 和操作系统环境等约束。

### 12.2 动态链接

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-005.svg" alt={"printf.o strlen.o rand.o libc.so foo.o bar.o baz.o libstrange.so Dynamic Linker main.o prog.exe prog.exe 拷贝到另一台机器 Dynamic Linking main.o libc.so libstrange.so main.o libc.so libstrange.so printf.o strlen.o rand.o libc.so libstrange.so ? ? ?"} />

动态链接时，库代码独立保存在共享库中，可执行文件主要记录对库的依赖和符号引用，在装入或运行阶段完成必要的解析与地址绑定。

常见共享库：

* Linux：`.so`；
* Windows：`.dll`。

主要特点：

* 可执行文件通常较小；
* 多个进程可共享只读库代码页；
* 更新共享库通常更方便；
* 运行时依赖外部动态库；
* 可能出现库缺失、版本或 ABI 不兼容。

### 12.3 静态链接与动态链接对比

| 对比项 | 静态链接 | 动态链接 |
| --- | --- | --- |
| 库代码 | 链接时进入可执行文件 | 共享库独立存在 |
| 可执行文件 | 通常较大 | 通常较小 |
| 运行时外部库依赖 | 较少 | 较多 |
| 多进程共享库代码 | 相对困难 | 更容易 |
| 库更新 | 常需重新链接 | 通常更方便 |
| 兼容风险 | 更多集中在构建阶段 | 运行环境还需满足版本/ABI |

<Callout type="warn" title="动态链接与动态装入不是同一个概念">

**链接**解决“模块/符号如何组合和引用”；**装入**解决“程序如何进入内存并获得可执行地址”。两者可能在时间上交织，但概念上必须区分。

</Callout>

---

## 13. 程序的装入、重定位与地址绑定

**装入（Loading）**&#x2060;是把程序代码和数据从外存装入内存，使其能够执行的过程。负责装入的程序称为 **Loader**。

按照地址在什么时候最终绑定，可以分为三种典型方式：

```text
编译/链接时确定 → 绝对装入
装入时确定       → 可重定位装入（静态重定位）
运行时转换       → 动态运行时装入（动态重定位）
```

### 13.1 绝对装入

如果编译/链接阶段已经知道程序最终在内存中的实际位置，就可以直接生成绝对地址。

特点：

* 地址很早就确定；
* 装入时通常无需再整体修改地址；
* 灵活性差；
* 适合早期简单系统或位置固定场景。

### 13.2 可重定位装入：静态重定位

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-006.svg" alt={"LOAD 1, 6 Add 1,8 Store 1,10 A B LOAD 1,106 Add 1,108 Store 1,110 A B 0 2 4 6 8 100 102 104 106 108 10 110 地址空间 存储空间"} />

编译时不知道程序最终放到哪个物理位置时，可先生成相对地址。装入时根据实际起始位置统一修正。

若某地址字段为 `6`，程序实际装入基址为 `100`，则装入时修正为：

$$
100+6=106
$$

这种修正在**装入时一次性完成**，因此称为**静态重定位**。

特点：

* 装入时修改地址；
* 装入后地址基本固定；
* 运行过程中不便整体移动程序。

### 13.3 动态运行时装入：动态重定位

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-007.svg" alt={"LOAD 500 12345 500 1000 + LOAD 1.500 12345 0 100 500 1000 1500 地址空间 存储空间"} />

动态重定位把地址转换推迟到**指令实际执行时**。

```text
逻辑 / 虚拟地址
      ↓
运行时地址转换机构
      ↓
物理地址
```

这需要硬件地址转换机制支持，例如早期的重定位寄存器，或现代 MMU、页表等。

主要优势：

* 地址绑定更灵活；
* 有利于程序运行期间移动；
* 便于实现分页、分段和虚拟存储；
* 每个进程可以使用相对独立的虚拟地址空间。

<Callout type="warn" title="动态重定位不等于非连续分配">

动态重定位的核心是**运行时才完成地址转换**。是否采用非连续物理分配，还取决于分页、分段等具体内存管理方案，不能把两者直接画等号。

</Callout>

### 13.4 三种装入方式总表

| 方式 | 地址确定/转换时间 | 运行时移动灵活性 | 典型环境 |
| --- | --- | --- | --- |
| 绝对装入 | 编译/链接时 | 很低 | 早期简单环境 |
| 静态重定位 | 装入时 | 较低 | 早期多道程序环境 |
| 动态重定位 | 运行时 | 较高 | 现代虚拟存储系统 |

## 14. 程序内存映像与地址空间

这是当前考纲“程序运行环境”中很容易被忽略的一项。

### 14.1 从可执行文件到进程内存映像

可执行文件是外存中的静态文件；当程序被装入并开始执行后，操作系统为它建立进程及相应的**内存映像（Memory Image）**。

典型进程虚拟地址空间可以抽象为：

```text
高地址
┌────────────────────┐
│        栈 Stack     │  ← 函数调用、局部变量
│         ↓           │
│                    │
│         ↑           │
│        堆 Heap      │  ← 动态分配
├────────────────────┤
│ 共享库 / mmap 区域 │
├────────────────────┤
│ BSS：未初始化全局量│
├────────────────────┤
│ Data：已初始化数据 │
├────────────────────┤
│ Text：机器代码     │
└────────────────────┘
低地址
```

具体排列顺序和地址因体系结构、操作系统、ASLR 等机制而异，408 更应掌握各区域的**语义**而不是死记某个绝对地址。

### 14.2 常见区域

| 区域 | 典型内容 | 典型属性 |
| --- | --- | --- |
| Text / Code | 程序机器指令、只读常量的一部分 | 通常可执行、可共享、只读 |
| Data | 已初始化的全局/静态变量 | 可读写 |
| BSS | 未显式初始化或零初始化的全局/静态变量 | 运行时建立并清零 |
| Heap | `malloc/new` 等动态分配区域 | 按需扩展/映射 |
| Stack | 调用栈、返回地址、局部变量等 | 随函数调用动态变化 |
| Shared Library / mmap | 动态库、文件映射、匿名映射 | 由映射关系决定 |

### 14.3 地址空间不等于物理内存连续区域

进程看到的是自己的**逻辑/虚拟地址空间**。在分页系统中：

```text
连续的虚拟地址页
      ↓ 页表映射
可以对应离散的物理页框
```

因此：

* 进程的虚拟地址空间可以看起来连续；
* 实际物理内存不要求连续；
* 某些虚拟页甚至暂时不在主存；
* 不同进程可以使用相同的虚拟地址值，却映射到不同物理页。

<Callout type="info" title="程序、进程与地址空间的关系">

**程序**是静态代码和数据的集合；**进程**是程序的一次执行过程；**进程内存映像/虚拟地址空间**是程序运行时被组织成的代码、数据、堆、栈及各种映射区域。

</Callout>

## 15. 分层与模块化结构

随着操作系统规模扩大，内核自身也需要结构化设计。

### 15.1 分层结构

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-001.svg" alt={"LayeredOS"} />

分层结构把系统划分为若干层，上层原则上通过下层提供的接口获得服务。

```text
高层应用 / 系统服务
──────────────
文件等高级抽象
──────────────
进程、内存管理
──────────────
底层硬件控制
──────────────
硬件
```

优点：

* 结构清晰；
* 易于设计、调试和验证；
* 层间接口明确。

局限：

* 层次边界不一定容易合理划分；
* 某些操作可能被迫跨越多层；
* 严格分层可能带来额外调用开销。

### 15.2 模块化结构

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-002.svg" alt={"操作系统 进程管理 磁盘管理 文件管理 进程控制 进程调度 内存分配 内存回收 磁盘管理 目录管理 操作系统模块"} />

模块化把系统按功能拆成相对独立的模块，例如：

* 进程管理；
* 文件系统；
* 内存管理；
* 设备管理；
* 网络模块。

模块化强调：

> **功能拆分 + 清晰接口 + 相对独立。**

分层强调：

> **上下级调用关系。**

二者并不互斥，现实系统常同时使用。

## 16. 宏内核、微内核与外核

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-003.svg" alt={"宏内核 vs 微内核架构对比 宏内核 (Monolithic Kernel) 用户空间 (User Space) 应用程序 系统调用接口 内核空间 (Kernel Space) 进程管理 内存管理 文件系统 设备驱动 网络协议 IPC 其他系统服务 硬件层 (Hardware) 微内核 (Microkernel) 用户空间 (User Space) 应用程序 文件系统 设备驱动 网络服务 其他服务 消息传递 系统调用接口 微内核 (Microkernel) 进程管理 内存管理"} />

### 16.1 宏内核

**宏内核（Monolithic Kernel）**&#x2060;把大量核心服务放在内核地址空间运行，常包括：

* 进程管理；
* 内存管理；
* 文件系统；
* 网络协议栈；
* 设备驱动；
* IPC 等。

优点：

* 内核内部组件可高效直接调用；
* 系统调用路径相对短；
* 通常具有较高性能。

缺点：

* 内核规模较大；
* 组件耦合可能较强；
* 某个内核组件严重故障可能影响整个系统。

Linux 通常作为宏内核/单体内核体系的代表理解，同时支持可装卸内核模块，因此“宏内核”不等于“完全不可模块化”。

### 16.2 微内核

**微内核（Microkernel）**&#x2060;尽量只把最基础的机制保留在内核态，例如：

* 基本线程/进程调度；
* 地址空间基础管理；
* IPC；
* 少量底层机制。

文件系统、部分驱动、网络服务等尽量移到用户态服务器，通过**消息传递**协作。

优点：

* 内核体积较小；
* 服务隔离较好；
* 故障影响范围更容易控制；
* 安全性、可靠性和可扩展性潜力更好；
* 便于单独维护或替换用户态服务。

缺点：

* 服务之间 IPC 更频繁；
* 可能增加用户态/内核态转换；
* 可能增加调度、数据复制和上下文切换开销。

> **真题考察**
>
> * 2023 年真题集中考查微内核的可靠性、安全性、可扩展性以及 IPC 带来的性能代价。

### 16.3 宏内核与微内核对比

| 特征 | 宏内核 | 微内核 |
| --- | --- | --- |
| 内核中服务数量 | 多 | 少 |
| 内核规模 | 较大 | 较小 |
| 服务通信 | 内核内部调用较多 | IPC/消息传递较多 |
| 性能 | 通常较高 | IPC 路径可能增加开销 |
| 故障隔离 | 相对较弱 | 相对较强 |
| 安全/可靠性潜力 | 内核攻击面较大 | 更容易缩小可信计算基 |
| 可维护与扩展 | 大型内核复杂度较高 | 用户态服务边界更清晰 |

<Callout type="warn" title="微内核的性能代价不是一句“必然很慢”">

正确表述是：把更多服务移到用户态后，服务协作往往需要更多 **IPC、权限级切换、调度和数据复制**，因此**可能**产生额外开销。现代实现可通过优化显著降低这些成本。

</Callout>

### 16.4 外核 Exokernel

**外核（Exokernel）**&#x2060;的设计思想是把内核进一步缩小：内核主要负责**安全地复用和保护底层硬件资源**，尽量不强制提供高层资源抽象；更丰富的抽象交给用户态的库操作系统（Library OS）实现。

可以概括为：

```text
应用程序
   ↓
Library OS：文件、虚拟内存等高层抽象
   ↓
Exokernel：保护 + 安全资源复用
   ↓
硬件
```

核心思想：

* **保护（Protection）**&#x2060;仍由内核保证；
* **管理策略与高层抽象**尽量上移到用户态；
* 应用可根据自身需求选择更合适的资源管理方式。

与微内核相比，外核不只是“把服务移到用户态”，而是更强调**尽量少规定高层抽象，让应用/库 OS 更直接地管理已授权资源**。

### 16.5 现实系统并非总是纯类型

现实操作系统常综合使用宏内核、微内核、模块化等思想。考试更重要的是掌握**结构特征、服务放在哪里、组件如何通信、优缺点来自哪里**，而不是强行把每个现实系统归入纯理论模型。

## 17. 虚拟机与 Hypervisor

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-004.svg" alt={"虚拟机架构图 物理硬件 (Physical Hardware) CPU • 内存 (RAM) • 存储设备 • 网络设备 Hypervisor (虚拟机监视器) 资源管理 • 隔离 • 虚拟化 虚拟机 1 Linux OS App1 App2 Web 虚拟硬件 vCPU: 2核 vRAM: 4GB 虚拟机 2 Windows OS SQL IIS Office 虚拟硬件 vCPU: 4核 vRAM: 8GB 虚拟机 3 Ubuntu OS Docker K8s DB 虚拟硬件"} />

**虚拟机（Virtual Machine，VM）**&#x2060;是通过虚拟化技术在物理计算机上构造出的逻辑计算机。

一台虚拟机可以拥有自己的：

* vCPU；
* 虚拟内存；
* 虚拟磁盘；
* 虚拟网络设备；
* Guest OS；
* 应用程序。

负责创建、管理和隔离虚拟机的软件层称为：

> **Hypervisor**，也称 **Virtual Machine Monitor（VMM）**。

### 17.1 Hypervisor 的主要职责

**资源虚拟化**：把物理 CPU、内存、设备等抽象成可分配的虚拟资源。

```text
8 核物理 CPU
      ↓
 Hypervisor
   ↙      ↘
2 vCPU   4 vCPU
 VM1      VM2
```

**资源管理**：为不同虚拟机分配 vCPU、内存、虚拟磁盘、网络等。

**隔离与保护**：原则上一个虚拟机不能任意访问另一个虚拟机或 Hypervisor 的受保护状态。

**截获与虚拟化敏感操作**：Guest OS 认为自己在管理“硬件”，但真正对物理资源具有最终控制权的是 Hypervisor。

### 17.2 Type 1 与 Type 2 Hypervisor

<Tabs items={["Type 1（裸机型）", "Type 2（宿主型）"]}>
<Tab value="Type 1（裸机型）">

Hypervisor 直接运行在物理硬件之上，再承载多个 Guest OS：

```text
应用
Guest OS
Hypervisor
硬件
```

通常用于服务器和数据中心虚拟化。

</Tab>
<Tab value="Type 2（宿主型）">

Hypervisor 作为宿主操作系统上的软件运行：

```text
应用 / Guest OS
虚拟机软件
Host OS
硬件
```

实现和使用方便，但还要经过宿主 OS 这一层。

</Tab>
</Tabs>

### 17.3 Hypervisor 与特权级

硬件虚拟化扩展会提供专门支持 VMM 的执行模式，例如：

* x86：VMX root / non-root mode；
* ARM：EL2 等。

有时把 Hypervisor 所在层非正式称为“Ring -1”，但应注意：

> **Ring -1 不是传统 x86 Ring 0～Ring 3 中真正新增的一个 Ring 编号。**

它只是强调 Hypervisor 对 Guest OS 具有更高控制权的一种通俗说法。

典型控制层次：

```text
Hypervisor
    ↓
Guest OS 内核
    ↓
Guest 用户程序
```

### 17.4 虚拟机与容器不要混淆

| 对比 | 虚拟机 | 容器 |
| --- | --- | --- |
| 是否有独立 Guest OS 内核 | 通常有 | 通常共享宿主机内核 |
| 虚拟化对象 | 机器/硬件接口 | 操作系统级运行环境 |
| 隔离开销 | 相对更大 | 通常更轻量 |

408 的“虚拟机”重点是 Hypervisor/VMM 与 Guest OS，不要把容器直接当成同一种虚拟机机制。

## 18. 本章高频辨析

### 18.1 并发 vs 并行

```text
并发：同一时间段内多个任务都在推进
并行：同一时刻多个任务真正同时执行
```

### 18.2 用户态 vs 内核态

```text
用户态：权限低，可执行普通指令并发起系统调用
内核态：权限高，执行 OS 核心功能和特权操作
```

### 18.3 特权指令 vs 系统调用入口指令

```text
特权指令：只能在高特权级执行
系统调用入口指令：必须允许用户态执行，用于受控陷入内核
```

### 18.4 中断 vs 异常 vs 系统调用

| 类型 | 来源 | 是否主动请求 OS | 典型例子 |
| --- | --- | --- | --- |
| 中断 | CPU 外部 | 否 | 时钟、I/O 完成 |
| 异常 | 当前指令 | 否 | 缺页、除零、保护错误 |
| 系统调用 | 当前程序 | 是 | `read`、`write` 等 |

### 18.5 系统调用 vs 上下文切换

```text
系统调用：必然产生特权级转换
进程切换：只有调度器真正更换执行主体时才发生
```

### 18.6 静态链接 vs 动态链接

```text
静态链接：库代码在链接阶段进入可执行文件
动态链接：共享库独立存在，装入/运行时完成必要绑定
```

### 18.7 静态重定位 vs 动态重定位

```text
静态重定位：装入时完成地址修正
动态重定位：运行时进行地址转换
```

### 18.8 可执行文件 vs 进程内存映像

```text
可执行文件：外存中的静态程序文件
内存映像：程序运行后建立的代码、数据、堆、栈及映射区域
```

### 18.9 宏内核 vs 微内核 vs 外核

```text
宏内核：更多服务在内核态，内核内直接调用多
微内核：只留基本机制，其他服务更多通过 IPC 协作
外核：内核重点做保护和资源复用，高层抽象尽量交给用户态 Library OS
```

## 19. 408 高频判断

> **判断 1：** 用户态和内核态完全是操作系统用软件“模拟”出来的两种状态。  
> **错误。**&#x2060;它们依赖处理器提供的硬件特权级机制，操作系统负责使用这些机制。

> **判断 2：** 用户程序发生系统调用后一定会切换到另一个进程。  
> **错误。**&#x2060;一定会受控进入内核态，但可能仍由原进程继续在内核中执行。

> **判断 3：** 系统调用入口指令属于只能在内核态执行的特权指令。  
> **错误。**&#x2060;用户程序必须能够执行该受控入口指令来请求内核服务。

> **判断 4：** 中断一定由当前正在执行的指令产生。  
> **错误。**&#x2060;外部中断通常来自时钟或 I/O 设备等 CPU 外部事件。

> **判断 5：** 异常通常与当前正在执行的指令有关。  
> **正确。**&#x2060;例如除零、缺页、保护错误等。

> **判断 6：** CPU 响应中断时，保存断点可以完全等到中断服务程序用普通指令完成。  
> **错误。**&#x2060;关键返回位置必须由硬件及时可靠保存，否则无法安全转入处理程序再返回。

> **判断 7：** 多道批处理提高 CPU 利用率的原因是单核 CPU 可以同一时刻真正执行多个程序。  
> **错误。**&#x2060;核心是某个程序等待 I/O 时让 CPU 转去执行其他程序。

> **判断 8：** 所有库函数都会触发系统调用。  
> **错误。**&#x2060;许多库函数完全在用户态执行，另一些才会封装系统调用。

> **判断 9：** 静态重定位是在程序运行过程中不断计算最终物理地址。  
> **错误。**&#x2060;静态重定位在装入时一次性完成主要地址修正。

> **判断 10：** 进程虚拟地址连续意味着对应的物理内存也必须连续。  
> **错误。**&#x2060;分页系统可把连续虚拟页映射到离散物理页框。

> **判断 11：** 微内核通常具有更好的故障隔离潜力。  
> **正确。**&#x2060;更多非核心服务可运行在彼此隔离的用户态进程中。

> **判断 12：** 微内核一定比宏内核慢。  
> **错误。**&#x2060;更准确的说法是微内核设计可能因 IPC、模式切换和调度产生额外开销，具体性能取决于实现。

> **判断 13：** 外核意味着取消内核保护，让应用直接任意访问硬件。  
> **错误。**&#x2060;外核仍负责保护和安全资源复用，只是尽量把高层抽象策略上移到用户态。

> **判断 14：** GPT 是 UEFI 的启动程序。  
> **错误。**&#x2060;GPT 是分区表格式，UEFI 启动程序通常位于 ESP 中的 `.efi` 文件。

> **判断 15：** 非特权指令在用户态执行时一定不会产生异常。  
> **错误。**&#x2060;例如普通访存指令访问非法地址仍可触发保护异常或缺页异常。

> **判断 16：** 发生中断或异常后一定进行进程调度。  
> **错误。**&#x2060;进入内核处理事件并不意味着调度器一定切换到其他进程。
