### 1. 操作系统的基本概念

#### 1.1 什么是操作系统

**操作系统（Operating System，OS）** 是计算机系统中最核心的系统软件之一，位于应用程序与硬件之间。

从不同角度看，操作系统具有三种重要身份：

1. **用户与计算机硬件之间的接口**
2. **计算机系统资源的管理者**
3. **对硬件资源进行抽象的软件层**

操作系统负责管理的典型资源包括：

* CPU
* 主存
* 外存
* 文件
* I/O 设备
* 进程与线程
* 网络资源

应用程序通常不直接操作硬件，而是通过操作系统提供的接口使用这些资源。

---

### 2. 操作系统的基本特征

操作系统具有四个基本特征：

> **并发、共享、虚拟、异步**

其中，**并发与共享互为存在条件**，是理解现代操作系统的核心。

#### 2.1 并发

**并发（Concurrency）** 是指两个或多个事件在**同一时间间隔内发生**。

在单核 CPU 中，多个程序并不是真的在同一时刻同时执行，而是 CPU 在多个程序之间高速切换，使它们在宏观上表现为同时运行。

需要区分：

| 概念 | 含义             |
| -- | -------------- |
| 并发 | 多个事件在同一时间间隔内发生 |
| 并行 | 多个事件在同一时刻同时发生  |

因此：

* 单核 CPU 可以实现**并发**
* 多核 CPU 才可能真正实现多个任务的**并行**

> **易错点**
>
> “多个程序同时运行”在操作系统语境中通常指宏观上的并发，并不一定意味着它们在同一个时钟周期真正并行执行。

---

#### 2.2 共享

**共享（Sharing）** 是指系统中的资源可以由多个并发执行的进程共同使用。

资源共享主要有两种方式：

##### 互斥共享

某些资源在一个时间段内只允许一个进程访问。

例如：

* 打印机
* 某些临界资源

##### 同时共享

允许多个进程在同一时间段内共同访问。

这里的“同时”通常是宏观意义上的同时，不一定意味着每一时刻都真正并行访问。

例如：

* 多个进程读取同一个只读文件

#### 并发与共享的关系

并发和共享互为条件：

* 如果系统不允许多个程序并发执行，就没有复杂资源共享问题。
* 如果多个程序无法共享系统资源，也很难实现真正有意义的并发运行。

---

#### 2.3 虚拟

**虚拟（Virtualization）** 是指将一个物理实体转换为若干逻辑上的对应物，使用户感觉自己拥有独立的资源。

常见例子：

| 物理资源   | 虚拟后的逻辑资源       |
| ------ | -------------- |
| 一颗 CPU | 多个进程似乎分别拥有 CPU |
| 有限主存   | 每个进程拥有独立虚拟地址空间 |
| 一台物理主机 | 多台虚拟机          |

虚拟技术通常可从两个角度理解：

* **时分复用**：多个任务轮流使用同一个资源，如 CPU。
* **空分复用**：不同任务使用资源的不同空间区域，如内存。

---

#### 2.4 异步

**异步（Asynchronism）** 是指在多道程序环境中，各个程序以不可预知的速度向前推进。

例如，一个进程可能：

1. 获得 CPU
2. 执行一段时间
3. 发起 I/O
4. 被阻塞
5. 过一段时间重新被唤醒
6. 再次获得 CPU

因此，单个进程何时继续执行、何时完成通常具有一定的不确定性。

> **注意**
>
> 异步并不意味着程序执行结果可以随机变化。
>
> 操作系统必须通过进程同步等机制保证程序在正确同步条件下仍能得到预期结果。

---

### 3. 操作系统的发展历程

操作系统的发展大致经历：

**手工操作 → 批处理 → 分时系统 → 实时系统**

<InlineSvg src="/images/operating-system/operating-system-concepts-concept-001.svg" alt={"手工操作 阶段 联机批处理 脱机批处理 执行系统 批处理（单道） 多道程序系统 多道批处理 系统 分时系统 实时系统 操作系统形成 个人计算机操作系统 网络操作系统 分布式操作系统"} />

#### 3.1 手工操作阶段

早期计算机不存在操作系统，程序员需要直接操作硬件。

基本过程是：

1. 用户将程序装入计算机
2. 启动运行
3. 等待程序执行完成
4. 记录结果
5. 下一个用户继续使用

主要问题是：

> **人机速度矛盾**

CPU 运行速度远快于人工操作速度，因此大量时间被浪费在程序装入、调试和人工操作上。

CPU 利用率很低。

---

#### 3.2 单道批处理系统

用户将多个作业交给系统，系统依次自动执行。

一个作业运行结束后，再执行下一个作业。

优点：

* 减少人工干预
* 自动完成作业之间的切换

缺点：

> 当当前作业等待 I/O 时，CPU 仍然只能空闲等待。

因此 CPU 利用率仍然较低。

---

#### 3.3 多道批处理系统

多道程序技术的核心思想是：

> **让多个程序同时进入内存。**

当某个程序因为 I/O 暂时无法继续执行时，CPU 转而执行另一个程序。

例如：

```text
进程 A：计算 → I/O 等待 ─────────→ 计算
CPU   ：执行 A → 执行 B → 执行 C → 执行 A
```

这样可以让：

* CPU 运算
* I/O 操作

尽可能重叠进行。

##### 优点

* CPU 利用率高
* 系统吞吐量大
* 系统资源利用率提高

##### 缺点

* 用户交互能力较差
* 作业周转时间可能较长

> **核心原因**
>
> 多道程序技术提高效率的关键不是“让 CPU 同时执行多个程序”，而是：
>
> **某个程序等待 I/O 时，让 CPU 去执行其他程序。**

---

#### 3.4 分时操作系统

分时系统将 CPU 时间划分为很短的**时间片**，多个用户或任务轮流使用 CPU。

由于切换速度足够快，每个用户都感觉自己在独占计算机。

典型特点：

* 多用户
* 交互性强
* 响应及时
* CPU 时间片轮转

Unix 的早期系统就是典型的分时系统。

##### 分时系统的主要目标

> **快速响应用户。**

这与多道批处理系统主要追求高吞吐量不同。

---

#### 3.5 实时操作系统

实时系统要求：

> **必须在规定时间内对事件作出响应。**

按照时间约束严格程度，可分为：

##### 硬实时系统

必须严格满足截止时间。

一旦超过时间限制，可能造成严重后果。

例如：

* 飞行控制
* 工业安全控制
* 某些医疗设备

##### 软实时系统

偶尔错过截止时间会降低系统性能或用户体验，但通常不会造成灾难性后果。

例如：

* 多媒体播放
* 部分通信应用

| 系统      | 主要目标         |
| ------- | ------------ |
| 多道批处理系统 | 提高资源利用率和吞吐量  |
| 分时系统    | 提高交互性、缩短响应时间 |
| 实时系统    | 在规定时间内完成任务   |

---

### 4. 操作系统的引导

操作系统存储在外存中，而 CPU 开机后必须先执行内存中能够访问的程序，因此需要一个逐级加载操作系统的过程。

<InlineSvg src="/images/operating-system/operating-system-concepts-concept-002.svg" alt={"OSBootProcess"} />

整体流程可以概括为：

```text
开机
 ↓
固件 BIOS / UEFI
 ↓
寻找启动设备
 ↓
引导程序 Bootloader
 ↓
加载操作系统内核
 ↓
内核初始化
 ↓
启动系统服务
 ↓
进入正常运行状态
```

#### 4.1 加电与固件执行

按下电源后，处理器开始执行固件中的启动代码。

传统计算机主要使用：

* BIOS

现代计算机则更多使用：

* UEFI

固件通常会：

* 执行硬件初始化
* 进行基本硬件检测
* 寻找可启动设备

---

#### 4.2 BIOS 与 UEFI

##### 传统 BIOS

传统 BIOS 通常：

1. 按启动顺序寻找启动设备
2. 读取磁盘中的启动代码
3. 将控制权交给引导程序

传统 BIOS 与 MBR 启动方式联系较紧密。

##### UEFI

UEFI 可以识别文件系统，并从 **EFI System Partition（ESP）** 中读取 `.efi` 启动程序。

> **易错点**
>
> **GPT 是磁盘分区表格式，不是启动程序。**
>
> 不要简单把现代 UEFI 启动理解成“UEFI 从 GPT 首扇区执行启动程序”。

---

#### 4.3 引导加载程序

**Bootloader** 的主要任务是：

> 将操作系统内核从外存加载到内存，并将控制权交给内核。

典型 Bootloader：

* GRUB
* Windows Boot Manager

---

#### 4.4 加载内核

Bootloader 找到操作系统内核后：

1. 将内核装入主存
2. 准备必要参数
3. 跳转到内核入口
4. CPU 开始执行内核代码

---

#### 4.5 内核初始化

内核获得控制权后，会进行一系列初始化，例如：

* 初始化内存管理
* 初始化中断系统
* 初始化调度系统
* 初始化设备驱动
* 检测硬件
* 建立系统数据结构

随后系统会启动各种系统进程或服务，最终进入正常运行状态。

## 5. 程序运行环境

程序并不是直接运行在裸硬件上的。

用户程序通常运行在权限受限的环境中，需要通过操作系统使用关键系统资源。

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-001.svg" alt={"用户 系统程序 应用程序 用户程序 依赖库 系统调用 操作系统 计算机硬件 更加抽象 更偏底层 用户模式 内核模式"} />

核心概念包括：

* 用户态与内核态
* 特权指令
* 中断与异常
* 系统调用
* 程序链接
* 程序装入

---

### 6. 用户态与内核态

#### 6.1 本质是什么

用户态和内核态本质上是：

> **处理器硬件提供的不同运行权限级别。**

操作系统利用 CPU 提供的权限机制，将普通应用程序与操作系统内核隔离。

以 x86 为例，处理器提供 Ring 0～Ring 3 等特权级。

通常：

| 特权级    | 用途     |
| ------ | ------ |
| Ring 0 | 操作系统内核 |
| Ring 3 | 用户应用程序 |

现代 Windows 和 Linux 通常主要使用 Ring 0 与 Ring 3。

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-002.svg" alt={"CPU 特权级边界：Ring 0 (内核态) ↔ Ring 3 (用户态) Ring 3 用户态 Ring 2 Ring 1 Ring 0 内核态 最高权限 权限：内 高 → 外 低 Linux/Windows 仅使用 Ring 0 与 Ring 3 用户态 (Ring 3) — 受限 ✓ 执行普通指令 (ALU, MOV, JMP) ✓ 访问自己的用户空间 (代码/数据/堆栈) ✓ 调用库函数 (printf, malloc) ✗ 执行特权指令"} />

因此：

> **用户态/内核态是 CPU 的运行状态，而操作系统负责利用和管理这种硬件机制。**

---

### 7. 内核态

**内核态（Kernel Mode）** 又称：

* 核心态
* 管态
* 特权态

在内核态下，处理器拥有较高权限，可以执行特权操作。

内核态主要用于执行：

* 进程管理
* 内存管理
* 中断处理
* 文件系统
* 设备管理
* I/O 控制
* 时钟管理

#### 7.1 为什么不能让普通程序一直运行在内核态

如果用户程序能够直接：

* 修改页表
* 关闭中断
* 操作磁盘控制器
* 修改其他进程地址空间
* 修改系统关键寄存器

那么任何程序错误都可能破坏整个系统。

因此必须通过权限隔离保证操作系统的安全性和稳定性。

---

### 8. 用户态

**用户态（User Mode）** 是普通应用程序运行的受限环境。

例如：

* 浏览器
* 文本编辑器
* 游戏
* 普通命令行程序

一般都运行在用户态。

用户程序可以：

* 执行普通计算指令
* 访问自身允许访问的地址空间
* 调用普通函数
* 调用库函数

但不能直接执行影响整个系统的特权操作。

需要使用受保护资源时，必须请求操作系统。

---

### 9. 特权指令与非特权指令

#### 9.1 特权指令

**特权指令（Privileged Instruction）** 是只能在内核态执行的指令。

它们通常涉及：

* 修改处理器关键状态
* 修改中断控制状态
* 修改内存管理相关寄存器
* 修改地址转换机制
* 直接控制某些 I/O 设备

例如，从概念上看：

```text
关闭中断
修改页表基址
设置内存保护
直接控制设备
修改某些系统控制寄存器
```

通常都必须由内核完成。

#### 9.2 非特权指令

普通算术、逻辑、跳转等指令一般属于非特权指令，可以由用户程序执行。

例如：

```text
ADD
SUB
MOV
CMP
JMP
```

当然，某条指令能否成功执行还可能受到地址访问权限等限制。

---

### 10. 如何判断操作能否在用户态完成

考试中可以使用一个非常实用的判断原则：

#### 用户程序可以自己完成

* 普通运算
* 普通函数调用
* 修改自己的普通变量
* 访问自己合法地址空间中的数据

#### 通常需要进入内核态

* I/O 设备控制
* 修改页表
* 修改中断状态
* 进程调度
* 内存资源分配的核心管理
* 创建或终止系统级进程资源
* 文件读写涉及的内核服务
* 网络设备操作

> **口诀**
>
> **涉及硬件、全局状态、系统资源保护的操作，优先考虑内核态。**

---

## 11. 中断与异常

用户程序运行过程中，CPU 并不会永远顺序执行程序指令。

系统可能由于：

* 外部设备事件
* 当前指令发生错误
* 用户程序主动请求操作系统

而转入操作系统内核。

通常可以将这些事件分为：

| 类型   | 典型来源           | 是否与当前指令直接相关 |
| ---- | -------------- | ----------- |
| 外部中断 | 时钟、I/O 设备      | 通常无关        |
| 异常   | 除零、缺页、非法指令     | 通常有关        |
| 系统调用 | 用户程序主动执行系统调用指令 | 有关          |

---

### 12. 中断

**中断（Interrupt）** 通常由 CPU 外部事件产生。

例如：

* 时钟中断
* 磁盘 I/O 完成
* 网卡收到数据

中断具有明显的**异步性**：

```text
程序正在执行
      ↓
外部设备发出中断请求
      ↓
CPU 暂停当前程序
      ↓
进入内核执行中断处理程序
      ↓
处理完成
      ↓
恢复原程序
```

时钟中断尤其重要，因为操作系统可以借助周期性的时钟中断重新获得 CPU 控制权，实现：

* 时间片轮转
* 进程调度
* 时间管理

---

### 13. 异常

**异常（Exception）** 通常由当前正在执行的指令内部引起。

典型情况包括：

* 除零
* 非法指令
* 地址越界
* 缺页
* 访问权限错误

异常通常具有**同步性**：

> 执行到特定指令时才会产生。

---

### 14. 用户态进入内核态的典型原因

用户程序运行时，CPU 从用户态切换到内核态通常有三类原因：

1. **系统调用**
2. **异常**
3. **中断**

因此可以记为：

```text
用户态
  │
  ├── 系统调用
  ├── 异常
  └── 中断
  ↓
内核态
```

处理完成后，操作系统可恢复原程序并返回用户态。

---

## 15. 系统调用

**系统调用（System Call）** 是应用程序请求操作系统内核服务的接口。

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-003.svg" alt={"用户程序执行 发起系统调用 执行系统调用 从系统调用返回 用户态 内核态 ① ② ③ ④"} />

例如，应用程序需要：

* 创建进程
* 打开文件
* 读取文件
* 写入文件
* 分配某些系统资源
* 进行网络通信
* 控制设备

这些操作通常无法直接在用户态完成，因此需要通过系统调用进入内核。

---

### 16. 系统调用的基本过程

可以概括为：

```text
用户程序
   ↓
准备系统调用参数
   ↓
执行系统调用指令
   ↓
CPU 由用户态进入内核态
   ↓
进入对应的系统调用处理程序
   ↓
内核执行请求
   ↓
返回结果
   ↓
恢复用户态程序
```

CPU 在这个过程中通常会保存必要的执行现场，以便之后继续执行用户程序。

---

### 17. 系统调用与普通函数调用

这是非常容易混淆的一组概念。

| 项目      | 普通函数调用       | 系统调用          |
| ------- | ------------ | ------------- |
| 是否进入内核  | 通常不会         | 会             |
| 是否改变特权级 | 通常不会         | 会             |
| 调用对象    | 当前程序中的函数或库函数 | 操作系统内核        |
| 开销      | 较小           | 通常更大          |
| 典型用途    | 算法、字符串处理等    | 文件、进程、设备等系统服务 |

#### 库函数不一定是系统调用

例如：

```c
strlen()
```

通常完全可以在用户态完成，不需要系统调用。

而：

```c
read()
write()
```

最终通常需要请求操作系统内核。

有些高级库函数内部可能封装多个系统调用。

因此：

> **库函数 ≠ 系统调用。**

---

### 18. 系统调用是否一定发生进程上下文切换

这是一个重要易错点。

系统调用一定会涉及：

> **用户态 → 内核态的特权级转换。**

但：

> **不一定发生进程之间的上下文切换。**

例如：

```text
进程 A（用户态）
   ↓ system call
进程 A（内核态）
   ↓
进程 A（用户态）
```

整个过程中仍然可能始终是进程 A 在执行。

只有当系统调用导致：

* 当前进程阻塞
* 调度器选择其他进程
* 当前进程被抢占

才可能进一步发生真正的进程上下文切换。

因此：

```text
状态切换 ≠ 进程切换
```

这一点必须严格区分。

---

### 19. x86 系统调用示意

早期 32 位 x86 Linux 中常见：

```asm
int 0x80
```

CPU 会进入内核的系统调用入口。

处理结束后，再通过相应返回机制恢复用户程序。

现代处理器通常还提供更高效的系统调用指令，例如：

```text
syscall
sysret
```

不同体系结构的具体指令不同，但基本思想一致：

> 用户程序通过受控入口进入操作系统内核，而不能任意跳转到内核代码。

---

## 20. 程序的链接

源代码经过编译后，通常会形成一个或多个目标模块。

最终生成可执行程序之前，需要由**链接器（Linker）** 将：

* 多个目标文件
* 所需库代码或库引用

组合起来。

根据库代码如何参与最终程序，可以分为：

* 静态链接
* 动态链接

---

### 21. 静态链接

在**静态链接**中，程序需要使用的库代码会在链接阶段被复制进入最终可执行文件。

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-004.svg" alt={"printf.o strlen.o rand.o libc.a foo.o bar.o baz.o libstrange.a Static Linker main.o main.o printf.o baz.o main.o printf.o baz.o prog.exe prog.exe 拷贝到另一台机器 Static Linking"} />

例如：

```text
main.o
   +
libxxx.a
   ↓
链接器
   ↓
可执行文件
```

#### 优点

* 对对应动态库依赖较少
* 部署相对方便
* 运行时无需再解析相应共享库

#### 缺点

* 可执行文件通常更大
* 多个程序可能重复保存相同库代码
* 更新库时需要重新链接程序

> **注意**
>
> 静态链接并不意味着生成的程序可以在任何计算机上直接运行。
>
> 程序仍然受到：
>
> * CPU 指令集
> * ABI
> * 可执行文件格式
> * 操作系统环境
>
> 等因素影响。

---

### 22. 动态链接

动态链接时，所依赖的库不会全部复制进入可执行文件。

程序中保存对动态库的引用，在程序装入或运行期间由系统完成链接。

常见动态库：

* Linux：`.so`
* Windows：`.dll`

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-005.svg" alt={"printf.o strlen.o rand.o libc.so foo.o bar.o baz.o libstrange.so Dynamic Linker main.o prog.exe prog.exe 拷贝到另一台机器 Dynamic Linking main.o libc.so libstrange.so main.o libc.so libstrange.so printf.o strlen.o rand.o libc.so libstrange.so ? ? ?"} />

#### 优点

* 可执行文件较小
* 多个程序可以共享动态库
* 节省存储空间
* 库更新通常更加方便

#### 缺点

* 运行时依赖外部动态库
* 可能出现库缺失
* 可能出现版本或 ABI 不兼容

---

### 23. 静态链接与动态链接对比

| 特征       | 静态链接     | 动态链接       |
| -------- | -------- | ---------- |
| 库代码      | 链接进可执行文件 | 独立保存       |
| 文件体积     | 通常较大     | 通常较小       |
| 运行时外部库依赖 | 较少       | 较多         |
| 多程序共享库代码 | 较困难      | 容易         |
| 更新库      | 通常需要重新链接 | 通常更方便      |
| 部署       | 相对独立     | 需要保证动态库存在  |
| 兼容问题     | 相对少      | 可能存在版本兼容问题 |

---

## 24. 程序的装入

**装入（Loading）** 是将程序的代码和数据从外存装入主存，使其可以被 CPU 执行的过程。

装入器称为：

> **Loader**

按照地址转换发生的时间，可以分为：

1. 绝对装入
2. 可重定位装入
3. 动态运行时装入

---

### 25. 绝对装入

绝对装入通常适用于早期的**单道程序环境**。

如果在编译时已经确定程序将位于主存中的具体位置，那么编译器可以直接产生绝对地址。

例如：

```text
程序从物理地址 1000 开始运行
```

那么指令中的地址可直接按照最终实际地址生成。

#### 特点

* 编译时确定实际地址
* 逻辑地址与实际地址一致
* 装入时通常无需地址修改
* 灵活性很差

---

### 26. 可重定位装入

在多道程序环境中，编译时通常无法预先知道程序最终会被装入内存的哪个位置。

因此目标程序通常从相对地址：

```text
0
```

开始编址。

装入时，系统根据程序实际装入位置统一修改相关地址。

这个过程称为：

> **重定位**

由于地址转换在装入时一次性完成，因此也称为：

> **静态重定位**

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-006.svg" alt={"LOAD 1, 6 Add 1,8 Store 1,10 A B LOAD 1,106 Add 1,108 Store 1,110 A B 0 2 4 6 8 100 102 104 106 108 10 110 地址空间 存储空间"} />

例如程序逻辑地址为：

```text
6
```

若程序被装入：

```text
100
```

开始的位置，则最终地址可能变为：

```text
106
```

#### 静态重定位的特点

* 装入时完成地址修改
* 之后程序中的地址已经成为实际地址
* 程序运行期间一般不能随意移动

传统静态重定位还要求装入时能够获得满足程序要求的内存区域。

---

### 27. 动态运行时装入

动态运行时装入又称：

> **动态重定位**

程序装入后，并不立即将全部逻辑地址修改成最终物理地址。

地址转换推迟到：

> **指令真正执行时**

完成。

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-007.svg" alt={"LOAD 500 12345 500 1000 + LOAD 1.500 12345 0 100 500 1000 1500 地址空间 存储空间"} />

其基本思想可以理解为：

```text
逻辑地址
   +
重定位信息
   ↓
运行时地址转换
   ↓
物理地址
```

需要硬件地址转换机制的支持，例如重定位寄存器或更复杂的 MMU 地址转换机制。

#### 优点

* 程序运行期间可以进行更灵活的地址调整
* 有利于程序在内存中移动
* 可以配合虚拟存储、分页、分段等机制实现更灵活的内存管理
* 程序不必在运行前完成所有地址的最终确定

> **易错点**
>
> “动态重定位”本身的核心是：
>
> **运行时才进行地址转换。**
>
> 非连续物理分配通常还依赖分页、分段等内存管理机制，不能简单把“非连续分配”完全归因于动态重定位。

---

### 28. 三种装入方式对比

| 装入方式    | 地址确定时间 | 是否可灵活移动   | 典型环境     |
| ------- | ------ | --------- | -------- |
| 绝对装入    | 编译时    | 否         | 早期单道系统   |
| 可重定位装入  | 装入时    | 装入后通常不能移动 | 多道程序早期方案 |
| 动态运行时装入 | 运行时    | 可以更加灵活地移动 | 现代系统     |

可以记忆为：

```text
编译时 → 绝对装入

装入时 → 静态重定位

运行时 → 动态重定位
```

---

## 29. 操作系统结构

随着操作系统规模不断扩大，如何组织内核本身也成为一个重要问题。

常见设计思想包括：

* 分层
* 模块化
* 宏内核
* 微内核

---

### 30. 分层结构

分层操作系统将整个系统划分成多个层次。

通常：

```text
高层
应用与系统服务
────────────
文件等高级抽象
────────────
进程、内存等管理
────────────
底层硬件控制
────────────
硬件
低层
```

上层使用下层提供的功能。

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-001.svg" alt={"LayeredOS"} />

#### 优点

* 系统结构清晰
* 容易设计与调试
* 易于验证正确性
* 层次之间边界清晰

#### 局限

严格分层有时会：

* 难以合理划分层次
* 某些操作需要跨越多层
* 带来额外调用开销

---

## 31. 模块化结构

模块化结构将操作系统划分为多个相对独立的功能模块。

例如：

* 进程管理
* 文件系统
* 内存管理
* 设备管理
* 网络模块

模块之间通过清晰的接口协作。

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-002.svg" alt={"操作系统 进程管理 磁盘管理 文件管理 进程控制 进程调度 内存分配 内存回收 磁盘管理 目录管理 操作系统模块"} />

#### 优点

* 易维护
* 易扩展
* 模块可独立开发
* 接口明确
* 新功能更容易添加

分层强调：

> **上下级层次关系**

模块化更强调：

> **功能拆分与接口**

二者并不互斥。

---

## 32. 宏内核

**宏内核（Monolithic Kernel）** 将操作系统的大部分核心服务都放在内核空间运行。

通常包括：

* 进程管理
* 内存管理
* 文件系统
* 网络协议栈
* 设备驱动
* IPC

这些组件在内核中能够较直接地互相调用。

#### 优点

* 服务之间通信效率高
* 系统调用路径通常较短
* 性能较好

#### 缺点

* 内核规模大
* 各部分之间耦合度可能较高
* 某个内核组件发生严重错误可能导致整个系统崩溃

典型例子：

* 传统 UNIX
* Linux

---

## 33. 微内核

**微内核（Microkernel）** 尽量只在内核态保留最基础的机制。

常见核心功能包括：

* 基本进程/线程管理
* 地址空间管理的基础机制
* IPC
* 基本调度机制

而：

* 文件系统
* 部分设备驱动
* 网络服务

等尽可能作为用户态服务运行。

不同组件主要通过：

> **消息传递**

进行通信。

#### 优点

* 内核体积较小
* 模块隔离性较好
* 服务崩溃不一定导致整个内核崩溃
* 易于维护和扩展
* 安全性、可靠性更容易加强

#### 缺点

不同服务之间可能频繁发生：

* IPC
* 用户态与内核态转换
* 调度与上下文切换

因此可能产生额外性能开销。

---

### 34. 宏内核与微内核对比

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-003.svg" alt={"宏内核 vs 微内核架构对比 宏内核 (Monolithic Kernel) 用户空间 (User Space) 应用程序 系统调用接口 内核空间 (Kernel Space) 进程管理 内存管理 文件系统 设备驱动 网络协议 IPC 其他系统服务 硬件层 (Hardware) 微内核 (Microkernel) 用户空间 (User Space) 应用程序 文件系统 设备驱动 网络服务 其他服务 消息传递 系统调用接口 微内核 (Microkernel) 进程管理 内存管理"} />

| 特征   | 宏内核        | 微内核        |
| ---- | ---------- | ---------- |
| 内核规模 | 较大         | 较小         |
| 文件系统 | 通常在内核态     | 可放用户态      |
| 驱动   | 通常在内核态     | 可放用户态      |
| 服务通信 | 内核内部直接调用较多 | IPC/消息传递较多 |
| 性能   | 通常较高       | IPC 开销可能较大 |
| 故障隔离 | 相对较弱       | 相对较强       |
| 可维护性 | 大型内核较复杂    | 服务边界通常更清晰  |

> **408 判断重点**
>
> 微内核最典型的代价是：
>
> **服务之间消息传递以及用户态/内核态切换增加，可能带来性能损失。**

---

### 35. 关于现实操作系统的分类

现实中的操作系统经常不会严格属于某一种纯理论结构。

例如某些系统会同时吸收：

* 宏内核
* 微内核
* 模块化

等设计思想。

因此 408 考试更重要的是理解：

> **结构特点与优缺点，而不是死记所有现实操作系统的分类。**

例如 Apple 的 XNU 内核吸收了 Mach 微内核思想，但通常被视为混合式内核，并非教材意义上的纯微内核。

---

## 36. 虚拟机

**虚拟机（Virtual Machine，VM）** 是通过软件和硬件虚拟化技术，在一台物理计算机上建立出来的逻辑计算机。

每个虚拟机可以拥有自己的：

* 虚拟 CPU
* 虚拟内存
* 虚拟磁盘
* 虚拟网络设备
* 操作系统
* 应用程序

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-004.svg" alt={"虚拟机架构图 物理硬件 (Physical Hardware) CPU • 内存 (RAM) • 存储设备 • 网络设备 Hypervisor (虚拟机监视器) 资源管理 • 隔离 • 虚拟化 虚拟机 1 Linux OS App1 App2 Web 虚拟硬件 vCPU: 2核 vRAM: 4GB 虚拟机 2 Windows OS SQL IIS Office 虚拟硬件 vCPU: 4核 vRAM: 8GB 虚拟机 3 Ubuntu OS Docker K8s DB 虚拟硬件"} />

从虚拟机内部看，它好像运行在一台独立的真实计算机上。

---

### 37. Hypervisor

负责创建和管理虚拟机的软件层称为：

> **Hypervisor**

又称：

> **Virtual Machine Monitor，VMM**

Hypervisor 位于虚拟机与物理硬件之间，主要负责：

#### 37.1 虚拟机管理

为虚拟机创建并分配：

* vCPU
* 虚拟内存
* 虚拟磁盘
* 虚拟网络设备

---

#### 37.2 资源抽象

Hypervisor 将真实硬件资源抽象成虚拟资源。

例如：

```text
8 核物理 CPU
        ↓
Hypervisor
   ↓      ↓
2 vCPU   4 vCPU
 VM1      VM2
```

---

#### 37.3 隔离

不同虚拟机之间应当保持相对独立：

```text
VM A
 │
 ├─ 无权直接访问 VM B 内存
 │
VM B
```

这可以提高：

* 安全性
* 资源隔离性
* 系统可靠性

---

## 38. Hypervisor 与特权级

普通操作系统内核通常运行在 CPU 的高权限状态。

硬件虚拟化出现后，处理器又提供了专门支持虚拟机监视器的运行模式。

例如：

* x86：VMX root mode
* ARM：EL2

有时会非正式地将 Hypervisor 所处级别称为：

> **Ring -1**

但需要注意：

> **Ring -1 并不是传统 x86 Ring 体系真正增加出来的一个 Ring。**

它只是描述 Hypervisor 比虚拟机内部操作系统具有更高控制权的一种通俗说法。

例如：

```text
Hypervisor
    ↓
Guest OS 内核
    ↓
Guest 用户程序
```

Hypervisor 必须能够截获和管理 Guest OS 对底层硬件的敏感操作。

## 39. 本章核心辨析

### 39.1 并发 vs 并行

| 并发           | 并行            |
| ------------ | ------------- |
| 同一时间段内多个任务推进 | 同一时刻真正执行多个任务  |
| 单核也可以实现      | 通常需要多核或多个处理单元 |

---

### 39.2 用户态 vs 内核态

| 用户态        | 内核态         |
| ---------- | ----------- |
| 权限低        | 权限高         |
| 普通程序运行     | OS 内核运行     |
| 不能执行特权指令   | 可以执行特权指令    |
| 不能直接控制关键硬件 | 可以管理硬件和系统资源 |

---

### 39.3 中断 vs 异常 vs 系统调用

| 类型   | 来源     | 主动性 | 典型例子       |
| ---- | ------ | --- | ---------- |
| 中断   | CPU 外部 | 被动  | 时钟、I/O     |
| 异常   | 当前指令   | 被动  | 除零、缺页      |
| 系统调用 | 当前程序   | 主动  | read、write |

三者都可能导致：

```text
用户态 → 内核态
```

---

### 39.4 系统调用 vs 上下文切换

```text
系统调用
   ↓
必然发生特权级转换

系统调用
   ↓
不一定发生进程切换
```

只有调度器实际切换正在运行的进程时，才发生进程上下文切换。

---

### 39.5 静态链接 vs 动态链接

```text
静态链接：
库代码 → 可执行文件内部

动态链接：
可执行文件 → 引用外部共享库
```

---

### 39.6 静态重定位 vs 动态重定位

```text
静态重定位：
装入时确定最终地址

动态重定位：
运行时进行地址转换
```

---

### 39.7 宏内核 vs 微内核

```text
宏内核：
更多服务放在内核态
→ 调用快
→ 故障影响范围可能更大

微内核：
尽量只保留最核心机制
→ 隔离好
→ IPC 与状态切换开销可能增加
```

## 40. 408 高频判断总结

> **判断 1**
>
> 用户态和内核态是操作系统自己创造的两种软件状态。
>
> **错误。**
>
> 它们依赖 CPU 硬件提供的特权级机制，操作系统负责使用这种机制。

> **判断 2**
>
> 用户程序发生系统调用后一定切换到另一个进程。
>
> **错误。**
>
> 一定会进入内核态，但不一定发生进程切换。

> **判断 3**
>
> 中断一定由当前正在执行的指令引起。
>
> **错误。**
>
> 外部中断通常来自 CPU 外部事件。

> **判断 4**
>
> 异常通常与当前正在执行的指令有关。
>
> **正确。**

> **判断 5**
>
> 多道批处理系统提高 CPU 利用率的关键是多个程序在单核 CPU 上真正并行执行。
>
> **错误。**
>
> 关键是一个程序等待 I/O 时让 CPU 执行其他程序。

> **判断 6**
>
> 所有库函数都会引发系统调用。
>
> **错误。**
>
> 很多库函数完全在用户态运行。

> **判断 7**
>
> 静态重定位在程序运行过程中动态计算实际物理地址。
>
> **错误。**
>
> 静态重定位在装入时完成地址修改。

> **判断 8**
>
> 微内核通常比宏内核具有更强的故障隔离能力。
>
> **正确。**

> **判断 9**
>
> 微内核的服务通信可能产生额外 IPC 和状态切换开销。
>
> **正确。**

> **判断 10**
>
> GPT 本身就是 UEFI 启动程序。
>
> **错误。**
>
> GPT 是分区表格式；UEFI 通常从 ESP 中加载 `.efi` 程序。

## 41. 一页速记

```text
操作系统四特征
并发 + 共享 + 虚拟 + 异步

发展历程
手工 → 单道批处理 → 多道批处理 → 分时/实时

多道批处理
核心：I/O 等待时让 CPU 执行其他程序

分时
核心：时间片 + 快速响应

实时
核心：截止时间

OS 引导
固件 → Bootloader → 内核 → 初始化 → 系统服务

用户态进入内核态
系统调用 / 异常 / 中断

系统调用
一定：用户态 → 内核态
不一定：进程切换

链接
静态：库代码进入可执行文件
动态：运行时依赖共享库

装入
绝对装入：编译时
静态重定位：装入时
动态重定位：运行时

宏内核
服务多在内核态 → 快

微内核
核心机制留内核态 → 隔离强，但 IPC 开销大

虚拟机
Hypervisor 管理多个 Guest OS
```
