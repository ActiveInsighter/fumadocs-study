## 1. 操作系统的基本概念

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-001.svg" alt={"用户 系统程序 应用程序 用户程序 依赖库 系统调用 操作系统 计算机硬件 更加抽象 更偏底层 用户模式 内核模式"} />

**操作系统（Operating System，OS）** 是位于应用程序与硬件之间的系统软件。它既要让硬件“可用”，又要让多程序环境中的资源使用“安全、有序、高效”。

从 408 角度，可以从三个视角理解操作系统。

| 视角 | 含义 | 典型体现 |
| --- | --- | --- |
| 用户接口 | 向用户和应用提供使用计算机的接口 | 命令接口、程序接口 |
| 资源管理者 | 统一管理软硬件资源 | CPU、内存、文件、设备 |
| 资源抽象层 | 将复杂硬件包装成更易使用的逻辑对象 | 进程、文件、虚拟地址空间 |

典型管理对象包括：

* CPU 与处理器时间；
* 主存和虚拟内存；
* 文件与外存空间；
* I/O 设备；
* 进程与线程；
* 网络等共享资源。

因此，应用程序通常不是直接“碰硬件”，而是通过操作系统提供的受控接口使用系统资源。

## 2. 操作系统的四个基本特征

操作系统的四个基本特征是：

> **并发、共享、虚拟、异步。**

其中，**并发与共享互为存在条件**，是理解多道程序系统的基础。

### 2.1 并发与并行

**并发（Concurrency）**：多个事件在**同一时间间隔内**发生。

**并行（Parallelism）**：多个事件在**同一时刻**真正同时发生。

| 对比项 | 并发 | 并行 |
| --- | --- | --- |
| 时间含义 | 同一时间段 | 同一时刻 |
| 单核 CPU | 可以实现 | 同一时刻通常只能执行一个指令流 |
| 多核 CPU | 可以实现 | 可以真正并行执行多个任务 |

单核处理器中，多进程通常通过高速切换形成“宏观同时”的效果：

```text
时间 →
A: ███       ███
B:    ███       ███
C:       ███
```

<Callout type="warn" title="“同时运行”不等于“同一时刻并行执行”">

操作系统题目中的“多个程序同时运行”经常只是指**并发推进**。除非题目明确说明多核、多处理器或多个执行单元，否则不要自动理解为真正并行。

</Callout>

### 2.2 共享

**共享（Sharing）** 是指系统资源可供多个并发执行的进程共同使用。

主要有两种方式：

1. **互斥共享**：一段时间内只允许一个进程访问，例如某些独占设备、临界资源。
2. **同时共享**：多个进程可在同一时间段共同访问，例如多个进程读取同一个只读文件。

“同时共享”中的“同时”通常仍是宏观意义，不要求每个物理时刻都真正并行访问。

并发与共享的关系可以概括为：

* 没有并发执行，就不会形成复杂的资源共享问题；
* 没有资源共享，多程序并发运行的意义也会大幅降低。

### 2.3 虚拟

**虚拟（Virtualization）** 是把一个物理实体转换为若干逻辑上的对应物，使每个使用者感觉自己获得了较独立的资源。

| 物理资源 | 逻辑上的虚拟效果 |
| --- | --- |
| 一颗 CPU | 多个进程仿佛分别拥有处理器 |
| 有限主存 | 每个进程拥有独立虚拟地址空间 |
| 一台物理主机 | 多台相互隔离的虚拟机 |

常见思想：

* **时分复用**：多个任务轮流使用同一资源，如 CPU；
* **空分复用**：多个任务使用同一资源的不同空间区域，如内存。

### 2.4 异步

**异步（Asynchronism）** 是指多道程序环境下，各进程以不可预知的速度向前推进。

一个进程可能经历：

```text
运行 → 发起 I/O → 阻塞 → 被唤醒 → 就绪 → 再次运行
```

因此，很难仅从程序本身预先确定它“具体哪一时刻”再次获得 CPU 或完成执行。

<Callout type="warn" title="异步不等于结果随机">

异步描述的是**推进速度和调度时机具有不确定性**，不意味着程序的逻辑结果可以任意变化。正确的同步机制仍应保证程序得到预期结果。

</Callout>

## 3. 操作系统的发展历程

<InlineSvg src="/images/operating-system/operating-system-concepts-concept-001.svg" alt={"手工操作 阶段 联机批处理 脱机批处理 执行系统 批处理（单道） 多道程序系统 多道批处理 系统 分时系统 实时系统 操作系统形成 个人计算机操作系统 网络操作系统 分布式操作系统"} />

操作系统的发展主线可以记为：

```text
手工操作
   ↓
单道批处理
   ↓
多道批处理
   ↓
分时系统 / 实时系统
```

### 3.1 手工操作阶段

早期没有操作系统，程序员需要直接操作机器完成装入、启动和结果处理。

主要矛盾是：

> **人机速度矛盾。**

CPU 很快，而人工装入和操作很慢，因此处理器大量时间处于空闲状态。

### 3.2 单道批处理系统

多个作业预先形成批次，系统自动按顺序逐个执行。

优点：

* 减少人工干预；
* 作业之间可以自动衔接。

核心缺点：

> 当前作业等待 I/O 时，CPU 仍可能空闲。

因此资源利用率依旧不高。

### 3.3 多道批处理系统

**多道程序技术**允许多个程序同时进入内存。当一个程序因 I/O 等待而不能继续时，CPU 转而执行另一个程序。

```text
进程 A：计算 → I/O 等待 ─────→ 计算
CPU   ：执行 A → 执行 B → 执行 C → 执行 A
```

其本质不是“单核 CPU 同时执行多个程序”，而是：

> **把一个程序的 I/O 等待时间与其他程序的 CPU 计算时间重叠起来。**

主要优点：

* 提高 CPU 利用率；
* 提高设备利用率；
* 提高系统吞吐量。

主要缺点：

* 用户交互性较弱；
* 作业周转时间可能较长；
* 系统管理复杂度明显增加。

### 3.4 分时系统

分时系统将 CPU 时间划分成较短的**时间片**，让多个用户或任务轮流获得 CPU。

典型特征：

* 多用户；
* 交互性强；
* 响应较及时；
* 依赖时间片与调度机制。

分时系统追求的核心目标是：

> **较快的交互响应。**

这与多道批处理系统主要追求高资源利用率、高吞吐量不同。

### 3.5 实时系统

实时系统的核心要求是：

> **在规定时间约束内对外部事件作出响应并完成相应任务。**

| 类型 | 时间要求 | 典型场景 |
| --- | --- | --- |
| 硬实时 | 截止时间必须满足 | 飞行控制、工业安全控制 |
| 软实时 | 偶尔超时通常只降低服务质量 | 多媒体、部分通信业务 |

三类典型系统的主要目标可直接对比：

| 系统 | 主要目标 |
| --- | --- |
| 多道批处理 | 提高资源利用率和吞吐量 |
| 分时系统 | 缩短响应时间、增强交互性 |
| 实时系统 | 满足时间约束 |

## 4. 操作系统的引导过程

<InlineSvg src="/images/operating-system/operating-system-concepts-concept-002.svg" alt={"OSBootProcess"} />

操作系统主体存放在外存，而 CPU 上电后不能凭空执行外存中的内核，因此必须通过**逐级加载**完成启动。

典型流程：

```text
加电
 ↓
固件 BIOS / UEFI
 ↓
硬件初始化并寻找启动设备
 ↓
Bootloader
 ↓
加载操作系统内核
 ↓
内核初始化
 ↓
启动系统服务
 ↓
进入正常运行状态
```

### 4.1 BIOS 与 UEFI

上电后，CPU 首先从规定位置开始执行固件代码。

传统系统常使用 **BIOS**；现代系统更多使用 **UEFI**。

固件的典型职责包括：

* 进行基本硬件初始化和检测；
* 确定启动设备；
* 找到并启动下一阶段的引导程序。

传统 BIOS 与 MBR 启动方式联系较紧密。UEFI 则可以识别文件系统，并从 **EFI System Partition（ESP）** 中加载 `.efi` 程序。

<Callout type="warn" title="GPT 不是启动程序">

**GPT 是磁盘分区表格式。**&#x2060;现代系统常见“UEFI + GPT”组合，但不能把 GPT 本身理解为 Bootloader，也不能说“UEFI 从 GPT 首扇区执行启动程序”。

</Callout>

### 4.2 Bootloader

**引导加载程序（Bootloader）** 的核心任务是：

> 找到操作系统内核，将其装入内存，并把控制权转交给内核入口。

典型例子有 GRUB、Windows Boot Manager。

### 4.3 内核初始化

内核获得 CPU 控制权后，会建立操作系统运行所需的关键环境，例如：

* 初始化内存管理；
* 初始化中断和异常处理；
* 初始化调度机制；
* 初始化设备和驱动；
* 建立内核数据结构；
* 启动系统进程与系统服务。

## 5. 用户态与内核态

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-002.svg" alt={"CPU 特权级边界：Ring 0 (内核态) ↔ Ring 3 (用户态) Ring 3 用户态 Ring 2 Ring 1 Ring 0 内核态 最高权限 权限：内 高 → 外 低 Linux/Windows 仅使用 Ring 0 与 Ring 3 用户态 (Ring 3) — 受限 ✓ 执行普通指令 (ALU, MOV, JMP) ✓ 访问自己的用户空间 (代码/数据/堆栈) ✓ 调用库函数 (printf, malloc) ✗ 执行特权指令"} />

用户态和内核态的本质是：

> **处理器硬件提供的不同运行权限级别。**

操作系统利用 CPU 的特权级机制，将普通应用程序与内核隔离。

以 x86 的经典表示为例：

| 特权级 | 常见用途 |
| --- | --- |
| Ring 0 | 操作系统内核 |
| Ring 3 | 普通用户程序 |

现代桌面和服务器操作系统通常主要使用这两个级别。

因此应严格表述为：

> 用户态/内核态是 CPU 的运行模式或特权状态，操作系统负责利用这种硬件机制实施保护。

### 5.1 内核态

在内核态下，处理器具有较高权限，可以执行涉及系统核心资源的操作，例如：

* 进程调度；
* 内存管理；
* 中断处理；
* 文件系统；
* 设备管理；
* I/O 控制；
* 时钟管理。

### 5.2 用户态

普通应用程序通常运行在用户态，例如浏览器、编辑器、游戏和普通命令行程序。

用户程序可以：

* 进行普通算术和逻辑运算；
* 调用普通函数和大量库函数；
* 访问自己被允许访问的虚拟地址空间。

但不能直接执行会破坏全局系统状态或系统保护机制的操作。

## 6. 特权指令与非特权指令

### 6.1 特权指令

**特权指令（Privileged Instruction）** 只能在高特权级状态下执行，典型操作涉及：

* 修改中断控制状态；
* 修改页表基址等地址转换关键寄存器；
* 修改内存保护机制；
* 访问某些系统控制寄存器；
* 直接控制某些 I/O 设备。

普通用户程序不能随意执行这些指令，否则一个应用的错误就可能破坏整个系统。

### 6.2 非特权指令

普通算术、逻辑、比较、跳转和一般数据传送等指令通常属于非特权指令，例如概念上的：

```text
ADD
SUB
MOV
CMP
JMP
```

但“非特权指令”并不意味着它可以访问任意地址。例如普通 `MOV` 虽然不是特权指令，如果访问了没有权限的地址，仍可能触发异常。

### 6.3 用户态操作判断法

通常可在用户态完成：

* 普通计算；
* 普通函数调用；
* 修改自己的普通变量；
* 访问自身合法地址空间。

通常必须借助内核：

* 控制 I/O 设备；
* 修改页表和内存保护；
* 修改中断状态；
* 进行进程调度；
* 进行全局资源分配与回收；
* 访问文件系统和网络设备等受保护系统资源。

## 7. 中断、异常与系统调用的统一框架

CPU 执行用户程序时，控制流可能因为外部事件、当前指令问题或用户程序主动请求而进入内核。

| 类型 | 典型来源 | 与当前指令关系 | 主动性 |
| --- | --- | --- | --- |
| 外部中断 | 时钟、磁盘、网卡等设备 | 通常无直接关系 | 对当前程序而言被动 |
| 异常 | 除零、缺页、非法指令、保护错误 | 通常直接相关 | 被动 |
| 系统调用 | 用户程序主动请求 OS 服务 | 与系统调用指令直接相关 | 主动 |

三者都可能导致：

```text
用户态 → 内核态
```

但它们的**触发来源和语义不同**。

## 8. 中断

**中断（Interrupt）** 通常由处理器外部事件引起，例如：

* 时钟中断；
* 磁盘 I/O 完成；
* 网卡收到数据。

典型过程：

```text
用户程序执行
    ↓
外部设备产生中断请求
    ↓
CPU 响应中断并保存必要现场
    ↓
进入内核执行中断处理程序
    ↓
处理完成
    ↓
恢复后续执行
```

外部中断最重要的特点是**异步性**：它通常不是“当前执行的那条指令本身”产生的。

### 8.1 时钟中断的作用

时钟中断使操作系统可以周期性重新获得 CPU 控制权，从而支持：

* 时间片管理；
* 抢占式调度；
* 时间统计；
* 定时事件处理。

<Callout type="info" title="为什么抢占式系统离不开时钟中断">

如果用户程序一直运行且不主动进入内核，而硬件又没有周期性时钟中断，那么操作系统就很难在预定时间重新夺回 CPU。时钟中断为调度器提供了重要的受控入口。

</Callout>

---

## 9. 异常

**异常（Exception）** 通常由当前正在执行的指令及其执行条件引起，因此具有明显的**同步性**。

常见异常：

* 除零；
* 非法指令；
* 地址访问越界或保护错误；
* 缺页；
* 其他由当前指令触发的处理器异常。

“同步”的含义是：在同样的机器状态和执行路径下，执行到相应指令时会在可确定的位置触发异常。

### 9.1 缺页为什么属于异常

缺页通常发生在 CPU 执行某条访存指令时：虚拟地址合法，但目标页当前不在主存。它与当前指令直接相关，因此通常归入异常，而不是外部中断。

## 10. 系统调用

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-003.svg" alt={"用户程序执行 发起系统调用 执行系统调用 从系统调用返回 用户态 内核态 ① ② ③ ④"} />

**系统调用（System Call）** 是用户程序请求操作系统内核服务的受控接口。

常见请求包括：

* 创建或管理进程；
* 打开、读写文件；
* 使用网络；
* 申请某些系统级资源；
* 请求设备相关服务。

### 10.1 基本执行过程

可以概括为：

```text
用户程序
   ↓
准备系统调用号和参数
   ↓
执行系统调用入口指令
   ↓
CPU 切换到内核态并进入指定入口
   ↓
内核检查参数并执行服务
   ↓
返回结果
   ↓
恢复用户态继续执行
```

CPU 和操作系统需要保存必要的执行现场，确保系统调用完成后能够恢复原程序。

### 10.2 系统调用与普通函数调用

| 对比项 | 普通函数调用 | 系统调用 |
| --- | --- | --- |
| 调用目标 | 当前程序或库中的函数 | 内核服务 |
| 是否必然进入内核 | 否 | 是 |
| 是否发生特权级转换 | 通常否 | 是 |
| 开销 | 通常较小 | 通常较大 |
| 典型用途 | 算法、字符串处理 | 文件、进程、设备、网络 |

**库函数不等于系统调用。**

例如：

```c
strlen(s);
```

通常完全可以在用户态计算，不需要系统调用。

而文件读取类接口最终通常需要进入内核。某些高级库函数还可能在内部封装一个或多个系统调用。

---

## 11. 状态切换与进程上下文切换

这是本章最重要的易错点之一。

系统调用一定会发生：

> **用户态 → 内核态的特权级转换。**

但不一定发生：

> **进程 A → 进程 B 的上下文切换。**

例如：

```text
进程 A（用户态）
      ↓ system call
进程 A（内核态）
      ↓ return
进程 A（用户态）
```

整个过程仍然可能始终是进程 A 在执行。

只有当：

* A 因系统调用而阻塞；
* A 的时间片用完；
* 出现更高优先级任务；
* 调度器因为其他原因选择 B；

才会进一步发生真正的进程上下文切换。

<Callout type="warn" title="状态切换 ≠ 进程切换">

进入内核态只说明**处理器权限级别发生变化**；进程上下文切换则说明**CPU 的执行主体换成了另一个进程或线程**。二者是不同维度的事件。

</Callout>

### 11.1 x86 系统调用入口示意

早期 32 位 x86 Linux 中常见：

```asm
int 0x80
```

现代 x86-64 常使用专门的快速系统调用机制，例如：

```text
syscall
sysret
```

不同体系结构的具体指令不同，但共同目标都是：

> **让用户程序只能通过预设、可检查的受控入口进入内核，而不能任意跳转到内核代码。**

## 12. 程序的链接

源程序编译后常形成多个目标模块。生成最终可执行文件前，需要由**链接器（Linker）** 把目标模块及所需库组合起来。

链接主要分为：

* 静态链接；
* 动态链接。

### 12.1 静态链接

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-004.svg" alt={"printf.o strlen.o rand.o libc.a foo.o bar.o baz.o libstrange.a Static Linker main.o main.o printf.o baz.o main.o printf.o baz.o prog.exe prog.exe 拷贝到另一台机器 Static Linking"} />

静态链接时，所需库代码在链接阶段被复制到最终可执行文件中。

```text
main.o + libxxx.a
        ↓
      Linker
        ↓
   可执行文件
```

主要特点：

* 可执行文件通常较大；
* 运行时对相应共享库依赖较少；
* 多个程序可能各自保存重复库代码；
* 库更新后通常需要重新链接程序。

静态链接并不意味着程序“到任何机器都能直接运行”。程序仍受 CPU 指令集、ABI、可执行文件格式和操作系统环境等约束。

### 12.2 动态链接

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-005.svg" alt={"printf.o strlen.o rand.o libc.so foo.o bar.o baz.o libstrange.so Dynamic Linker main.o prog.exe prog.exe 拷贝到另一台机器 Dynamic Linking main.o libc.so libstrange.so main.o libc.so libstrange.so printf.o strlen.o rand.o libc.so libstrange.so ? ? ?"} />

动态链接时，库代码通常独立保存在共享库中，可执行文件主要记录对库的依赖与引用，装入或运行阶段再完成必要的符号解析和地址绑定。

常见共享库：

* Linux：`.so`；
* Windows：`.dll`。

主要特点：

* 可执行文件通常较小；
* 多个进程可共享只读库代码页；
* 更新库更方便；
* 运行时依赖外部动态库；
* 可能出现库缺失、版本或 ABI 不兼容。

### 12.3 静态链接与动态链接对比

| 对比项 | 静态链接 | 动态链接 |
| --- | --- | --- |
| 库代码 | 进入可执行文件 | 独立保存 |
| 可执行文件 | 通常较大 | 通常较小 |
| 运行时外部库依赖 | 较少 | 较多 |
| 多进程共享库代码 | 相对困难 | 更容易 |
| 库更新 | 常需重新链接 | 通常更方便 |
| 兼容风险 | 相对集中在构建阶段 | 运行环境还需满足库版本/ABI |

## 13. 程序的装入与重定位

**装入（Loading）** 是把程序代码和数据从外存装入主存，使其能够执行的过程。负责装入的程序称为 **Loader**。

按照地址何时确定，可以分为三种典型方式：

```text
编译时确定 → 绝对装入
装入时确定 → 可重定位装入（静态重定位）
运行时转换 → 动态运行时装入（动态重定位）
```

### 13.1 绝对装入

如果编译时已经知道程序最终在主存中的实际位置，编译器可直接生成绝对地址。

特点：

* 编译时确定实际地址；
* 装入时通常不需要修改地址；
* 灵活性差；
* 适合早期简单环境。

### 13.2 可重定位装入：静态重定位

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-006.svg" alt={"LOAD 1, 6 Add 1,8 Store 1,10 A B LOAD 1,106 Add 1,108 Store 1,110 A B 0 2 4 6 8 100 102 104 106 108 10 110 地址空间 存储空间"} />

多道程序环境下，编译时往往不知道程序最终会被放到哪个物理位置，因此程序通常生成相对地址。

设程序逻辑地址为 `6`，实际装入基址为 `100`，则重定位后可得到：

```text
100 + 6 = 106
```

这种地址修正在**装入时一次性完成**，因此又称**静态重定位**。

特点：

* 装入时修改地址；
* 装入后地址基本固定；
* 程序运行期间通常不能轻易整体移动。

### 13.3 动态运行时装入：动态重定位

<InlineSvg src="/images/operating-system/operating-system-concepts-environment-007.svg" alt={"LOAD 500 12345 500 1000 + LOAD 1.500 12345 0 100 500 1000 1500 地址空间 存储空间"} />

动态重定位把地址转换推迟到**指令实际执行时**。

```text
逻辑地址
   ↓
运行时地址转换机构
   ↓
物理地址
```

这需要硬件地址转换机制的支持，例如早期的重定位寄存器，或现代 MMU、页表等机制。

主要优势：

* 地址绑定更灵活；
* 有利于程序运行期间移动；
* 便于配合分页、分段和虚拟存储机制。

<Callout type="warn" title="动态重定位不等于非连续分配">

动态重定位的核心是**运行时才完成地址转换**。是否采用非连续物理分配还取决于分页、分段等具体内存管理方案，不能把两者直接画等号。

</Callout>

### 13.4 三种装入方式总表

| 方式 | 地址确定/转换时间 | 运行时移动灵活性 | 典型环境 |
| --- | --- | --- | --- |
| 绝对装入 | 编译时 | 很低 | 早期简单系统 |
| 静态重定位 | 装入时 | 较低 | 早期多道程序系统 |
| 动态重定位 | 运行时 | 较高 | 现代系统 |

## 14. 分层与模块化结构

随着操作系统规模扩大，内核自身也需要结构化设计。

### 14.1 分层结构

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-001.svg" alt={"LayeredOS"} />

分层结构把系统划分为若干层，上层原则上通过下层提供的接口获得服务。

```text
高层应用/系统服务
──────────────
文件等高级抽象
──────────────
进程、内存管理
──────────────
底层硬件控制
──────────────
硬件
```

优点：

* 结构清晰；
* 易于设计、调试和验证；
* 层间接口明确。

局限：

* 层次边界不一定容易合理划分；
* 某些操作可能被迫跨过多层；
* 严格分层可能带来额外调用开销。

### 14.2 模块化结构

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-002.svg" alt={"操作系统 进程管理 磁盘管理 文件管理 进程控制 进程调度 内存分配 内存回收 磁盘管理 目录管理 操作系统模块"} />

模块化把系统按功能拆成相对独立的模块，例如：

* 进程管理；
* 文件系统；
* 内存管理；
* 设备管理；
* 网络模块。

模块化强调：

> **功能拆分与接口。**

分层强调：

> **上下级层次关系。**

二者并不互斥，现实系统常同时使用。

## 15. 宏内核与微内核

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-003.svg" alt={"宏内核 vs 微内核架构对比 宏内核 (Monolithic Kernel) 用户空间 (User Space) 应用程序 系统调用接口 内核空间 (Kernel Space) 进程管理 内存管理 文件系统 设备驱动 网络协议 IPC 其他系统服务 硬件层 (Hardware) 微内核 (Microkernel) 用户空间 (User Space) 应用程序 文件系统 设备驱动 网络服务 其他服务 消息传递 系统调用接口 微内核 (Microkernel) 进程管理 内存管理"} />

### 15.1 宏内核

**宏内核（Monolithic Kernel）** 把大量操作系统核心服务放在内核地址空间中运行，常包括：

* 进程管理；
* 内存管理；
* 文件系统；
* 网络协议栈；
* 设备驱动；
* IPC 等。

优点：

* 内核内部组件可高效直接调用；
* 系统调用路径较短；
* 通常具有较高性能。

缺点：

* 内核规模较大；
* 组件之间可能耦合较强；
* 某个内核组件严重故障可能影响整个系统。

Linux 通常作为宏内核/单体内核体系的代表进行理解，同时它也支持高度模块化。

### 15.2 微内核

**微内核（Microkernel）** 尽量只把最基础的机制保留在内核态，例如：

* 基本线程/进程调度；
* 地址空间基础管理；
* IPC；
* 少量底层机制。

文件系统、部分驱动、网络服务等可尽量移到用户态服务器中，通过**消息传递**协作。

优点：

* 内核体积较小；
* 服务隔离较好；
* 故障影响范围更容易控制；
* 便于维护和扩展。

缺点：

* 服务之间 IPC 更频繁；
* 可能增加用户态/内核态转换；
* 可能增加调度和上下文切换开销。

### 15.3 对比

| 特征 | 宏内核 | 微内核 |
| --- | --- | --- |
| 内核中服务数量 | 多 | 少 |
| 内核规模 | 较大 | 较小 |
| 服务通信 | 内核内部调用较多 | IPC/消息传递较多 |
| 性能 | 通常较高 | IPC 路径可能带来额外开销 |
| 故障隔离 | 相对较弱 | 相对较强 |
| 可维护性 | 大型内核复杂度较高 | 服务边界更清晰 |

<Callout type="warn" title="微内核的典型性能代价">

408 最常考的不是“微内核一定慢”，而是：**微内核把更多服务移到用户态后，服务之间的通信往往需要更多 IPC、权限级切换和调度，因此可能产生额外性能开销。**

</Callout>

### 15.4 现实系统并非总是纯类型

现实操作系统常综合使用宏内核、微内核、模块化等思想，因此考试更重要的是掌握**结构特征与优缺点**，而不是把所有现实系统强行归入一种纯理论模型。

例如 Apple 的 XNU 吸收了 Mach 等设计思想，通常被视为混合式内核，而不是教材意义上的纯微内核。

## 16. 虚拟机与 Hypervisor

<InlineSvg src="/images/operating-system/operating-system-concepts-structure-004.svg" alt={"虚拟机架构图 物理硬件 (Physical Hardware) CPU • 内存 (RAM) • 存储设备 • 网络设备 Hypervisor (虚拟机监视器) 资源管理 • 隔离 • 虚拟化 虚拟机 1 Linux OS App1 App2 Web 虚拟硬件 vCPU: 2核 vRAM: 4GB 虚拟机 2 Windows OS SQL IIS Office 虚拟硬件 vCPU: 4核 vRAM: 8GB 虚拟机 3 Ubuntu OS Docker K8s DB 虚拟硬件"} />

**虚拟机（Virtual Machine，VM）** 是通过虚拟化技术在物理计算机上构造出的逻辑计算机。

一台虚拟机可以拥有自己的：

* vCPU；
* 虚拟内存；
* 虚拟磁盘；
* 虚拟网络设备；
* Guest OS；
* 应用程序。

负责创建、管理和隔离虚拟机的软件层称为：

> **Hypervisor**，也称 **Virtual Machine Monitor（VMM）**。

### 16.1 Hypervisor 的主要职责

**资源虚拟化**：把物理 CPU、内存、设备等抽象成可分配的虚拟资源。

```text
8 核物理 CPU
      ↓
 Hypervisor
   ↙      ↘
2 vCPU   4 vCPU
 VM1      VM2
```

**资源管理**：为不同虚拟机分配 vCPU、内存、虚拟磁盘、网络等。

**隔离**：原则上一个虚拟机不能任意访问另一个虚拟机的内存和内部状态。

### 16.2 Hypervisor 与特权级

硬件虚拟化扩展会提供专门支持 VMM 的执行模式，例如：

* x86：VMX root / non-root mode；
* ARM：EL2 等。

有时会把 Hypervisor 所在层非正式称为“Ring -1”，但应注意：

> **Ring -1 不是传统 x86 Ring 0～Ring 3 中真正新增的一个 Ring 编号。**

它只是强调 Hypervisor 对 Guest OS 具有更高控制权的一种通俗说法。

典型控制层次：

```text
Hypervisor
    ↓
Guest OS 内核
    ↓
Guest 用户程序
```

## 17. 本章高频辨析

### 17.1 并发 vs 并行

```text
并发：同一时间段内多个任务都在推进
并行：同一时刻多个任务真正同时执行
```

### 17.2 用户态 vs 内核态

```text
用户态：权限低，运行普通应用
内核态：权限高，执行 OS 核心功能和特权操作
```

### 17.3 中断 vs 异常 vs 系统调用

| 类型 | 来源 | 是否主动请求 OS | 典型例子 |
| --- | --- | --- | --- |
| 中断 | CPU 外部 | 否 | 时钟、I/O 完成 |
| 异常 | 当前指令 | 否 | 缺页、除零、保护错误 |
| 系统调用 | 当前程序 | 是 | `read`、`write` 等 |

### 17.4 系统调用 vs 上下文切换

```text
系统调用：必然产生特权级转换
进程切换：只有调度器真正更换执行主体时才发生
```

### 17.5 静态链接 vs 动态链接

```text
静态链接：库代码在链接阶段进入可执行文件
动态链接：程序保留共享库依赖，装入/运行时完成必要绑定
```

### 17.6 静态重定位 vs 动态重定位

```text
静态重定位：装入时完成地址修正
动态重定位：运行时进行地址转换
```

### 17.7 宏内核 vs 微内核

```text
宏内核：更多服务在内核态 → 直接调用多、通常性能高
微内核：更少服务留在内核态 → 隔离强、IPC 可能更多
```

---

## 18. 408 高频判断

> **判断 1：** 用户态和内核态完全是操作系统用软件“模拟”出来的两种状态。  
> **错误。**&#x2060;它们依赖处理器提供的硬件特权级机制，操作系统负责使用这些机制。

> **判断 2：** 用户程序发生系统调用后一定会切换到另一个进程。  
> **错误。**&#x2060;一定会受控进入内核态，但可能仍由原进程继续在内核中执行。

> **判断 3：** 中断一定由当前正在执行的指令产生。  
> **错误。**&#x2060;外部中断通常来自时钟或 I/O 设备等 CPU 外部事件。

> **判断 4：** 异常通常与当前正在执行的指令有关。  
> **正确。**&#x2060;例如除零、缺页、保护错误等。

> **判断 5：** 多道批处理提高 CPU 利用率的原因是单核 CPU 可以同一时刻真正执行多个程序。  
> **错误。**&#x2060;核心是某个程序等待 I/O 时让 CPU 转去执行其他程序。

> **判断 6：** 所有库函数都会触发系统调用。  
> **错误。**&#x2060;许多库函数完全在用户态执行。

> **判断 7：** 静态重定位是在程序运行过程中不断计算最终物理地址。  
> **错误。**&#x2060;静态重定位在装入时一次性完成主要地址修正。

> **判断 8：** 微内核通常具有更好的故障隔离潜力。  
> **正确。**&#x2060;更多服务运行在相互隔离的用户态进程中。

> **判断 9：** 微内核可能因为频繁 IPC 和权限级切换产生额外开销。  
> **正确。**&#x2060;这是其典型性能代价之一。

> **判断 10：** GPT 是 UEFI 的启动程序。  
> **错误。**&#x2060;GPT 是分区表格式，UEFI 启动程序通常位于 ESP 中的 `.efi` 文件。

> **判断 11：** 非特权指令在用户态执行时一定不会产生异常。  
> **错误。**&#x2060;例如普通访存指令访问非法地址仍可触发保护异常或缺页异常。

> **判断 12：** 发生中断或异常后一定进行进程调度。  
> **错误。**&#x2060;进入内核处理事件并不意味着调度器一定切换到其他进程。
