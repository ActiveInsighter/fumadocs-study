并发程序最容易犯的错误是：

> **把一段看起来像“一步”的高级语言操作，误认为在硬件上真的不可分割。**

例如 `count++` 往往至少包含“读—改—写”多个步骤。两个线程的步骤交错，就可能得到错误结果。

> **真题标签**
>
> 软件互斥、Peterson 和硬件原子指令多次出现在选择题；2023 年综合题也曾涉及软件互斥分析。

## 2.4.1 临界资源、临界区与竞态

**临界资源**：同一时刻只允许一个执行流访问的共享资源。

**临界区（Critical Section）**：程序中访问临界资源的代码段。

**竞态条件（Race Condition）**：程序结果依赖多个并发执行流的不可控执行先后。

例如两个线程都执行：

```c
count++;
```

可被拆为：

```text
A: read count = 5
B: read count = 5
A: write 6
B: write 6
```

结果只增加 1，而不是 2。

<Callout type="info" title="互斥不等于关中断到临界区结束">
线程 A 进入临界区后仍可能被抢占；互斥要求的是其他竞争同一临界资源的线程不能在此期间也进入临界区。
</Callout>

## 2.4.2 临界区的基本要求

经典教材常用四条原则：

1. **空闲让进**：临界区无人使用时，应允许需要者进入；
2. **忙则等待**：已有执行流在临界区时，其他竞争者不能进入；
3. **有限等待**：申请者不应无限期等待；
4. **让权等待**：不能进入时应尽量放弃 CPU，而不是无意义长期忙等。

其中前三条更接近正确性/活性要求；“让权等待”强调效率，现实中的短临界区也可能故意采用自旋。

## 2.4.3 为什么普通锁变量不够

错误写法：

```c
bool lock = false;

while (lock) {
    ;
}
lock = true;
// critical section
lock = false;
```

问题是“检查 `lock`”与“写 `lock=true`”不是一个原子动作：

```text
A: 看到 lock=false
B: 看到 lock=false
A: lock=true
B: lock=true
A/B 都进入临界区
```

因此：

> **互斥算法必须把关键的“检查 + 修改”做成不可被并发破坏的协议。**

## 2.4.4 严格轮流为什么也不理想

两个线程按 `turn` 严格交替：

```c
while (turn != 0) ;
// P0 critical section
turn = 1;
```

虽然能互斥，但可能违反**空闲让进**：

- 临界区明明空闲；
- `turn` 指向的线程却根本不想进入；
- 另一线程仍被迫等待。

这说明：

> **“保证不同时进入”只是互斥算法的最低要求，不代表实现就合理。**

## 2.4.5 Peterson 算法

Peterson 算法用于两个执行流，使用：

- `flag[i]`：线程 $i$ 是否想进入；
- `turn`：双方同时竞争时让谁优先。

```c
bool flag[2] = {false, false};
int turn = 0;

void P0() {
    flag[0] = true;
    turn = 1;
    while (flag[1] && turn == 1) {
        ;
    }

    // critical section

    flag[0] = false;
}
```

对称地实现 P1。

408 中主要掌握：

- 它属于**软件互斥**；
- 直接适用于两个参与者；
- 需要忙等；
- `flag` 表示意愿，`turn` 解决双方同时竞争。

现实多核还要考虑内存模型与编译器重排序，考试通常不展开到这一层。

## 2.4.6 原子操作是什么

**原子操作（Atomic Operation）**&#x2060;强调：

> 对并发观察者而言，操作表现为不可分割的整体，中间状态不会以破坏原子语义的方式暴露。

它**不等于“一定只需要一个时钟周期”**。

## 2.4.7 TAS：Test-and-Set

逻辑效果：

```c
bool test_and_set(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
```

硬件保证“读旧值 + 写新值”作为一个原子动作。

自旋锁：

```c
while (test_and_set(&lock)) {
    ;
}
// critical section
lock = false;
```

锁忙时线程反复执行检查，因此称为**自旋（Spin）**。

## 2.4.8 CAS：Compare-and-Swap

CAS 的抽象语义：

> **只有当前值仍等于期望值，才原子地把它改成新值。**

伪代码：

```c
bool CAS(int *addr, int expected, int new_value) {
    if (*addr == expected) {
        *addr = new_value;
        return true;
    }
    return false;
}
```

现实硬件保证比较与写回整体原子。

TAS/CAS 都在解决同一个核心问题：

> **普通的“先看一下，再改一下”之间存在竞态窗口。**

## 2.4.9 自旋锁与阻塞锁

### 自旋等待

锁不可用时：

```text
一直在 CPU 上循环检查
```

适合：

- 临界区很短；
- 预期等待时间很短；
- 阻塞/唤醒成本反而更高的场景。

代价：等待期间仍消耗 CPU。

### 阻塞等待

锁不可用时：

1. 当前线程进入等待队列；
2. 放弃 CPU；
3. 锁释放后被唤醒；
4. 进入就绪态；
5. 以后重新获得 CPU 并竞争锁。

适合预期等待较长的场景，但会增加睡眠/唤醒与调度开销。

| 对比 | 自旋 | 阻塞 |
| --- | --- | --- |
| 等待时占 CPU | 是 | 否 |
| 切换开销 | 小/无阻塞切换 | 有阻塞与唤醒开销 |
| 适合 | 短等待 | 长等待 |

## 2.4.10 互斥与同步不要混淆

**互斥**解决：

> 同一时刻谁可以进入共享临界区？

**同步**解决：

> 多个执行流应该按照什么先后或条件关系协作？

例如：

```text
A 写完数据后 B 才能读取
```

重点是顺序关系；

```text
A、B 都可能修改同一链表，但不能同时修改
```

重点是互斥。

一个问题经常同时包含二者，例如生产者—消费者既需要缓冲区互斥，又需要“非空/非满”同步。
