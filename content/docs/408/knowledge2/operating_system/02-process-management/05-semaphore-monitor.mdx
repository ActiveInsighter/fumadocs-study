锁只能回答“谁能进临界区”，但很多并发问题还要表达：

> **条件还没满足时先睡；条件满足后再继续。**

条件变量、信号量和管程就是表达这类同步关系的核心工具。

> **真题标签**
>
> 信号量是 408 综合题最重要的同步工具之一；2017、2024 等年份综合题以及多年份选择题均有考查。条件变量和管程也曾在 2016、2018 年出现。

## 2.5.1 条件变量：等“状态”而不是抢“数量”

条件变量通常与互斥锁一起使用：

```c
lock(mutex);
while (!condition) {
    wait(cond, mutex);
}
// condition 成立，且已经重新持有 mutex
...
unlock(mutex);
```

### `wait(cond, mutex)` 的关键语义

它必须把下面两件事协调成不可丢失的等待协议：

1. **释放关联锁**；
2. **把当前线程放入条件等待**。

被唤醒后，线程还要重新竞争并获得锁，`wait` 才返回。

为什么要写 `while` 而不是 `if`？

- 被唤醒只代表“可能有变化”；
- 其他线程可能先一步抢到锁并改变条件；
- 某些实现允许伪唤醒。

所以正确习惯是：

> **醒来以后重新检查条件。**

### `signal` 与 `broadcast`

- `signal/notify_one`：唤醒一个等待者；
- `broadcast/notify_all`：唤醒所有等待者。

唤醒并不等于立即执行，被唤醒线程通常先进入可竞争/就绪状态。

## 2.5.2 信号量的抽象模型

**信号量（Semaphore）**&#x2060;可以同时表达：

- 互斥；
- 前驱关系；
- 可用资源数量；
- 更复杂的同步约束。

两个原子操作：

- **P / wait**：申请资源或等待条件；
- **V / signal**：归还资源或发出一次同步通知。

### P 操作

抽象语义：

```text
如果资源/许可可得：消耗一个，继续
否则：阻塞到信号量等待队列
```

### V 操作

抽象语义：

```text
释放一个资源/许可
若有人等待，按实现规则唤醒等待者
```

<Callout type="info" title="数值表示服从题目定义">
有的教材让信号量始终用非负资源计数，并另设等待队列；有的经典实现允许信号量为负，用负值反映等待者数量。考试若要求计算信号量值，应以题目给出的 P/V 定义为准。
</Callout>

## 2.5.3 二元信号量：实现互斥

初始化：

```c
semaphore mutex = 1;
```

临界区：

```c
P(mutex);
// critical section
V(mutex);
```

含义：

- 初始有 1 个“进入许可”；
- 第一个执行流拿走许可后，其他人等待；
- 离开时归还许可。

## 2.5.4 初值为 0：实现前驱关系

若要求：

> **A 完成后 B 才能执行。**

则可使用：

```c
semaphore s = 0;

A() {
    do_A();
    V(s);
}

B() {
    P(s);
    do_B();
}
```

牢记方向：

> **前驱完成者 V，后继等待者 P。**

对于 DAG 型前驱图，可为每条必须满足的依赖边设计相应同步信号量。

## 2.5.5 计数信号量：表达资源数量

若系统初始有 $N$ 个同类可用资源：

```c
semaphore resource = N;
```

每申请一个：`P(resource)`；释放一个：`V(resource)`。

因此信号量的初值往往直接对应：

> **系统一开始能同时允许多少次该类操作。**

典型例子：容量为 $N$ 的有界缓冲区：

```c
semaphore empty = N;
semaphore full  = 0;
semaphore mutex = 1;
```

- `empty`：剩余空槽数量；
- `full`：已有产品数量；
- `mutex`：缓冲区临界区互斥。

## 2.5.6 为什么 P 的顺序可能导致死锁

生产者常写：

```text
P(empty)
P(mutex)
放入产品
V(mutex)
V(full)
```

而不是：

```text
P(mutex)
P(empty)
...
```

原因：若缓冲区已经满，生产者先拿着 `mutex` 再等待 `empty`，消费者却必须拿到同一个 `mutex` 才能消费并释放 `empty`，就可能形成相互等待。

因此对典型“资源数量 + 临界区”的题目，一个实用原则是：

> **先申请决定“能不能做”的资源型信号量，再申请保护“怎么安全做”的互斮信号量。**

但这不是机械万能规则；复杂题仍要根据依赖关系检查是否形成循环等待。

## 2.5.7 管程：把共享状态和同步规则封装起来

**管程（Monitor）**&#x2060;通常把以下内容封装到同一个抽象中：

- 共享数据；
- 操作共享数据的方法；
- 互斥进入规则；
- 条件变量。

核心思想：

> **任一时刻通常最多一个执行流在管程内部执行受保护操作；条件不满足时可通过条件变量等待。**

与直接散落 P/V 相比，管程的优势是：

- 共享状态与操作集中；
- 同步不变量更容易维护；
- 更不容易遗漏 P/V 或写错顺序；
- 条件同步表达更接近高级语言程序结构。

## 2.5.8 锁、条件变量、信号量、管程怎么选概念

| 工具 | 最适合表达 | 典型关键词 |
| --- | --- | --- |
| 互斥锁 | 一次只能一个 | 临界区 |
| 条件变量 | 等某个共享状态成立 | `while (!condition) wait` |
| 二元信号量 | 互斥或单个同步许可 | 初值 0/1 |
| 计数信号量 | 多个同类资源 | 初值为资源数 |
| 管程 | 高层封装互斥 + 条件同步 | 共享数据 + 方法 + 条件变量 |

<Callout type="warn" title="信号量不是“永远比锁高级”">
这些工具抽象层次和语义侧重点不同。考试重点不是评判谁更高级，而是根据题目约束选择能清楚表达正确关系的机制。
</Callout>
