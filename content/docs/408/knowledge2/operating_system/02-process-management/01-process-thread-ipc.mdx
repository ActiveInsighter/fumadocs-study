### 1.1 进程与程序

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-001.svg" alt={"Disk program CPU Memory process stack code static data heap Loading: 读取磁盘中的程序并将其加载到进程的地址空间中 code static data"} />

**程序（Program）** 是静态的指令和数据集合；**进程（Process）** 是程序的一次执行过程。

| 对比 | 程序 | 进程 |
| --- | --- | --- |
| 性质 | 静态 | 动态 |
| 典型位置 | 磁盘等持久化介质 | 内存与内核管理结构中 |
| 生命周期 | 文件存在即可 | 创建、就绪、运行、阻塞、终止 |
| 一对多关系 | 同一程序可多次运行 | 每次运行通常形成独立进程 |

因此不能写成“进程就是程序”。进程除了代码和数据，还包含地址空间、打开文件、调度状态、CPU 现场等运行时信息。

### 1.2 资源单位与调度单位

408 中最重要的两个结论：

> **进程是资源分配和保护的基本单位。**
>
> **线程是处理机调度和执行的基本单位。**

可以用一句话区分：

> **进程解决“资源归谁”，线程解决“谁在 CPU 上执行”。**

### 1.3 PCB：操作系统眼中的进程

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-002.svg" alt={"进程控制块 PCB PCB（进程控制块） 进程标识信息 PID（进程标识符）· UID（用户标识符） 进程控制信息 进程状态 · 进程优先级 处理机状态信息 PC · 通用寄存器 · PSW（程序状态字） 资源信息 打开的文件 · 内存指针 · 其他资源 常驻内存，随进程生命周期存在 ① 进程创建与终止 • 创建时，OS 为进程新建 PCB • PCB 常驻内存，可随时存取 • 进程结束时，PCB 被删除 PCB 是进程存在的唯一标志 ② 进程调度 • OS 读取 PCB 中"} />

操作系统通过 **PCB（Process Control Block，进程控制块）** 描述和管理进程。按 408 教材口径，**PCB 是进程存在的唯一标志**：创建进程时建立 PCB，撤销进程时回收 PCB。

| 信息类别 | 典型内容 | 作用 |
| --- | --- | --- |
| 标识信息 | PID、UID | 区分进程 |
| 调度与控制信息 | 状态、优先级、队列指针 | 调度与控制 |
| CPU 现场 | PC、通用寄存器、PSW、栈指针 | 恢复执行 |
| 资源信息 | 地址空间、页表、打开文件等 | 资源管理 |

当进程暂停运行时，操作系统要保存足够的处理机现场，使它以后能从原位置继续。

<Callout type="warn" title="易错点">
PCB 在内核中管理；用户程序通常不能任意直接修改 PCB。PCB 记录的也不只是“进程状态”，而是一整套进程管理信息。
</Callout>

### 1.4 进程控制原语：创建、终止、阻塞与唤醒

操作系统对进程状态的关键改变通常通过**原语（primitive）**完成。原语要求相关操作在逻辑上不可被中途破坏，以避免只改了一半管理数据。

| 控制动作 | 典型内核工作 | 常见状态变化 |
| --- | --- | --- |
| 创建 | 分配 PID、建立 PCB、建立地址空间与初始资源 | 创建态 → 就绪态 |
| 终止 | 回收资源、保存退出信息，最终撤销 PCB/进程描述项 | 运行态 → 终止态 |
| 阻塞 | 保存现场、移出运行队列、挂入相应等待队列 | 运行态 → 阻塞态 |
| 唤醒 | 从等待队列移出，放入就绪队列 | 阻塞态 → 就绪态 |

<Callout type="info" title="阻塞和唤醒通常成对理解">
进程往往因为“等待某事件”而阻塞；该事件发生后，由内核或其他执行流触发唤醒。**被唤醒只意味着重新具备运行条件，不意味着立即得到 CPU。**
</Callout>

## 2. `fork`、`exec`、`wait` 与父子进程

UNIX/Linux 中常见进程关系来自 `fork()`。

```c
pid_t fork(void);
```

`fork()` 成功后：

- 父进程得到子进程 PID，返回值大于 `0`；
- 子进程返回 `0`；
- 创建失败时父进程返回 `-1`，且没有新子进程。

父子进程都从 `fork()` 返回处继续，因此常利用返回值分流执行路径。父子进程拥有**不同的 PID 和独立的虚拟地址空间语义**，但会继承许多打开文件、环境变量等运行环境；这些继承关系的具体共享细节由对象类型和系统实现决定。

### 2.1 写时复制 COW

从抽象语义看，子进程获得父进程地址空间的一份逻辑副本。现代系统通常使用 **Copy On Write（COW）**：

1. `fork()` 后父子进程暂时共享相同物理页；
2. 页表权限配合内核机制防止直接同时写；
3. 某一方第一次写某页时，触发复制；
4. 复制后双方各自修改自己的物理页。

因此：

> **父子进程的虚拟地址空间彼此独立，但物理页可以暂时共享。**

### 2.2 `fork`、`exec`、`wait` 的角色

| 调用 | 核心作用 | 是否创建新进程 |
| --- | --- | --- |
| `fork()` | 复制当前执行环境，创建子进程 | 是 |
| `exec()` | 用新程序映像替换当前进程映像 | 否 |
| `wait()` / `waitpid()` | 等待并回收已结束子进程 | 否 |

成功执行 `exec()` 后，当前进程 PID 等身份通常保留，但原来的代码、数据、堆栈等程序映像被新程序替换；因此正常情况下不会从成功的 `exec()` 返回到原程序继续执行。

### 2.3 僵尸进程与孤儿进程

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-003.svg" alt={"图示"} />
<InlineSvg src="/images/operating-system/operating-system-process-process-thread-004.svg" alt={"图示"} />

**僵尸进程（Zombie）**：子进程已经终止，但父进程尚未读取退出状态。

- 不再执行，也不占用 CPU；
- 用户地址空间等大部分资源已释放；
- 内核仍保存 PID、退出状态等少量信息；
- 父进程通过 `wait()` / `waitpid()` 完成回收。

**孤儿进程（Orphan）**：父进程先终止，而子进程仍存在。

- 子进程通常可以继续运行；
- 会被 `init`、`systemd` 或其他子进程收割者接管。

| 项目 | 僵尸进程 | 孤儿进程 |
| --- | --- | --- |
| 子进程是否已终止 | 是 | 通常否 |
| 原父进程 | 尚未回收子进程 | 已终止 |
| 是否可能继续执行 | 否 | 是 |
| 核心问题 | 退出状态尚未回收 | 父子关系被重新接管 |

### 3.1 为什么引入线程

一个进程可以包含多个执行流。线程之间共享进程级资源，因此创建、通信和同进程切换通常比独立进程更轻量。

同一进程中的线程通常共享：

- 虚拟地址空间；
- 代码段、全局变量、静态变量；
- 堆；
- 打开的文件等进程级资源。

每个线程必须独有：

- 线程标识；
- 程序计数器；
- 寄存器现场；
- 栈；
- 线程状态和调度信息。

### 3.2 PCB 与 TCB

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-008.svg" alt={"PCB与TCB的关系"} />

多线程系统中，可以用下面的抽象理解：

> **PCB 管进程级资源和保护边界，TCB 管某条执行流的现场与调度信息。**

一个进程通常只有一个进程级资源环境，却可关联多个 **TCB（Thread Control Block）**。

<Callout type="warn" title="线程栈仍在同一地址空间">
“每个线程有自己的栈”不等于线程之间具有进程级地址隔离。线程栈仍位于同一进程虚拟地址空间，错误指针完全可能破坏其他线程的数据。
</Callout>

### 3.3 进程与线程对比

| 对比 | 进程 | 线程 |
| --- | --- | --- |
| 核心角色 | 资源拥有与保护边界 | CPU 调度与执行实体 |
| 地址空间 | 不同进程通常独立 | 同进程线程共享 |
| PC、寄存器、栈 | 与其执行流相关 | 每个线程独有 |
| 通信 | 常借助 IPC | 可直接访问共享地址空间 |
| 切换代价 | 通常较大 | 同进程线程切换通常较小 |
| 隔离性 | 较强 | 较弱 |
| 多核并行 | 取决于是否有多个可运行执行流 | 多线程可并行运行 |

一句话：

> **进程是资源容器，线程是执行实体。**

## 4. 进程状态与状态转换

> **真题考察：**
> 选择题：2012 年第 30 题、2014 年第 26 题、2015 年第 25 题、2018 年第 27 题、2019 年第 24 题、2021 年第 24、27 题、2022 年第 28 题、2023 年第 27 题等。

### 4.1 五种基本状态

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-009.svg" alt={"新建 就绪 运行 终止 阻塞 创建 调度 时间到 事件等待 事件发生 退出"} />

| 状态 | 含义 | 最关键特征 |
| --- | --- | --- |
| 创建态 New | 正在创建和初始化 | 尚未进入正常调度 |
| 就绪态 Ready | 已具备继续执行条件 | **只缺 CPU** |
| 运行态 Running | 正在 CPU 上执行 | 占有 CPU |
| 阻塞态 Blocked | 正等待事件或资源 | **给 CPU 也不能继续** |
| 终止态 Terminated | 已结束 | 等待清理回收 |

### 4.2 高频状态转换

**就绪 → 运行**：被调度器选中并获得 CPU。

**运行 → 就绪**：

- 时间片耗尽；
- 被更高优先级任务抢占；
- 主动让出 CPU。

此时任务仍具备运行条件，只是暂时失去 CPU。

**运行 → 阻塞**：

- 发出需要等待的 I/O；
- 请求暂不可得的锁、信号量或资源；
- `sleep()`；
- `wait()` / `waitpid()`；
- 等待消息、条件；
- 缺页后等待页面调入等。

**阻塞 → 就绪**：等待事件发生，例如 I/O 完成、锁可用、消息到达、定时器到期。

<Callout type="warn" title="408 高频陷阱">
阻塞事件完成后，进程通常先进入**就绪态**，而不是自动直接进入运行态；能否运行还要经过处理机调度。
</Callout>

### 4.3 挂起状态：和“阻塞”不是一回事

引入换入/换出后，教材常把状态进一步细分为**就绪挂起**和**阻塞挂起**。关键区别是：

- **阻塞**描述“逻辑上是否还在等事件”；
- **挂起**描述“进程映像是否被暂时移出内存/暂停调度”。

因此一个进程可以“阻塞但未挂起”，也可以“阻塞且挂起”。阻塞事件发生后，若进程仍在外存，它可由“阻塞挂起”转为“就绪挂起”，之后还要换入内存才能成为普通就绪态。

<Callout type="warn" title="挂起 ≠ 阻塞">
“给 CPU 能不能立刻继续”判断的是就绪/阻塞；“当前是否被换出、暂停参与短程调度”判断的是挂起。两组概念不要混成同一个维度。
</Callout>

### 4.4 一眼判断“就绪”还是“阻塞”

问自己：

> **现在立即把 CPU 给它，它能继续执行吗？**

- 能，但当前没 CPU → **就绪**；
- 不能，还在等事件/资源 → **阻塞**。

## 5. 进程虚拟地址空间与线程栈

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-010.svg" alt={"Process-specific data structures (e.g. page tables, tasks and kernel stack) Physical Memory Kernel code and data User stack Memory-mapped region for shared libraries Run-time heap Uninitialized data (.bss) Initialized data (.data) Code (.te"} />

> **真题考察：**

典型用户进程虚拟地址空间包括：

| 区域 | 典型内容 |
| --- | --- |
| Text | 可执行指令，通常只读 |
| Data | 已初始化全局/静态变量 |
| BSS | 未显式初始化的全局/静态变量，装入时通常置零 |
| Heap | `malloc` / `new` 等动态分配 |
| mmap 区 | 动态库、文件映射、匿名映射、共享内存等 |
| Stack | 栈帧、局部变量、返回信息等 |
| Kernel Space | 用户态不能直接访问的内核地址区域 |

“堆向高地址增长、栈向低地址增长”是很多教材示意图中的典型布局，**不是所有体系结构/系统都必须如此**；做题以题图或题设为准。

### 5.1 函数栈帧

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-011.svg" alt={"上一个栈帧 上一个 栈帧 的 EBP 局部变量 callee 的参数列表 n ~ 1 caller 返回地址 caller 栈帧 的 EBP 局部变量 下一个函数的参数列表 n ~ 1 返回地址 下一个栈帧 调用函数（caller）的栈帧 被调用函数（callee）的栈帧 高地址，栈底 低地址，栈顶 caller 的 EBP callee 的 EBP"} />
<InlineSvg src="/images/operating-system/operating-system-process-process-thread-012.svg" alt={"main main f1 main f1 f2 main f1 main 高地址 低地址 main(f1(f2())) 时间 函数的栈帧在内存中的结构变化"} />

以传统 x86 栈帧为例，栈帧可能保存：

- 返回地址；
- 上一栈帧基址；
- 局部变量；
- 保存的寄存器；
- 部分参数等。

调用者称为 **caller**，被调用函数称为 **callee**。`call` 建立调用关系并保存返回位置，`ret` 根据保存的返回信息回到 caller。

<Callout type="info" title="与组成原理联动">
函数调用、程序计数器、寄存器保存、`call`/`ret` 与上下文切换都涉及“保存现场—恢复现场”，但**函数调用不等于进程/线程上下文切换**。
</Callout>

## 6. 进程间通信 IPC

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-013.svg" alt={"Process  A Shared Memory Process B Kernel M M M Kernel 1 2 1 2 Process  A Pipe Process B Kernel 消息传递 管道 共享内存 Process A Process B"} />
<InlineSvg src="/images/operating-system/operating-system-process-process-thread-014.svg" alt={"图示"} />

> **复习优先级：低到中**
>
> **真题考察：**
> 选择题：2014 年第 31 题。

独立进程通常不能直接访问彼此普通虚拟地址空间，因此需要 **IPC（Inter-Process Communication）**。

常见机制：管道、共享内存、消息队列、信号、套接字、信号量等。按通信组织方式还可概括为：

- **共享存储**：通信双方访问一块共同可见的数据区；
- **消息传递**：通过 `send/receive` 一类原语交换消息，可分直接通信和借助邮箱/端口的间接通信；
- **管道通信**：把内核缓冲区抽象成顺序字节流通道。

<Callout type="warn" title="Signal 与 Semaphore 不是一回事">
Unix/Linux 的 **signal（信号）** 是异步事件通知机制；**semaphore（信号量）** 是同步/互斥工具。中文里都带“信号”二字，但语义完全不同。
</Callout>

### 6.1 管道 Pipe

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-015.svg" alt={"管道（Pipe）机制示意图"} />

经典管道由内核维护缓冲区，数据路径可以抽象为：

> 写进程 → 内核管道缓冲区 → 读进程

特征：

- 通常按 FIFO 次序读取；
- 普通匿名管道典型为字节流；
- 容量有限；
- 管道空时读可能阻塞，管道满时写可能阻塞；
- 经典匿名管道通常单向，双向通信可建立两个管道。

**匿名管道**常用于有亲缘关系的进程；**有名管道 FIFO** 在文件系统中有名字，通信双方不要求亲缘关系。

### 6.2 共享内存

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-016.svg" alt={"栈 共享区 堆 未初始化数据 初始化数据 代码段 内核区 用户空间 页表 进程 A 虚拟地址空间 栈 共享区 堆 未初始化数据 初始化数据 代码段 内核区 用户空间 进程 B 虚拟地址空间 页表 物理地址空间 共享内存区域 进程 A 进程 B"} />

共享内存把同一组物理页映射到多个进程的虚拟地址空间。例如：

$$VPN_A \rightarrow PPN_{200}$$

$$VPN_B \rightarrow PPN_{200}$$

虚拟地址可以不同，但最终访问同一物理页。

优势：建立映射后，双方可直接读写共享页，因此大块数据通信时通常可减少反复在进程与内核之间复制数据的开销。**建立映射、缺页和同步本身仍有成本**，所以“共享内存最快”是针对大量数据持续交换时的典型结论，而不是零开销。

代价：

> **共享内存只解决“共享”，不自动解决“同步”。**

多个进程并发读写时仍常需要互斥锁、信号量等同步机制。

### 6.3 消息队列

消息队列由内核维护，以“消息”为逻辑单位。典型特点：

- 可传递结构化消息；
- 可以同步或异步；
- 某些实现支持消息类型/优先级；
- 通常比直接共享内存多内核参与和数据复制开销。

<Callout type="info" title="IPC 选择题抓手">
看到“最快的大块共享数据”优先想到共享内存；看到“天然按消息边界传递”想到消息队列；看到“亲缘进程、字节流、内核缓冲”常想到匿名管道。
</Callout>

## 7. 用户级线程、内核级线程与映射模型

> **真题考察：**
> 选择题：2019 年第 23 题、2026 年第 25 题。

### 7.1 用户级线程 ULT

用户级线程由用户空间线程库管理。若内核只看见一个对应的内核调度实体，则：

- 用户线程切换可在用户态完成，开销较低；
- 一个用户线程发生阻塞系统调用时，可能使这个内核调度实体整体阻塞；
- 多个用户线程无法同时占用多个 CPU 核心。

### 7.2 内核级线程 KLT

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-017.svg" alt={"用户级线程 (ULT) 用户空间 内核空间 用户 / 内核边界 进程 线程库 创建 / 调度 / 切换 (用户态完成) 线程 T1 线程 T2 线程 T3 • 线程实体位于用户空间 • 切换不陷入内核，开销小、速度快 • 一个线程阻塞会导致整个进程阻塞 • 无法被内核调度到多核并行执行 • 可跨 OS 移植（依赖线程库） PCB（进程） 内核只看到 1 个执行实体 对线程完全无感知 内核调度以进程为单位 同一时刻只有 1 个线程能运行 内核级线程 (KLT) 用户空间 内核空"} />

内核级线程由操作系统直接管理：

- 内核可以分别调度；
- 一个线程阻塞不必导致同进程其他内核线程一起阻塞；
- 多个内核线程可被调度到不同核心并行执行。

### 7.3 三类映射模型

<InlineSvg src="/images/operating-system/operating-system-process-process-thread-018.svg" alt={"Thread Library P User Space Kernel Space P User Space Kernel Space P User Space Kernel Space P Thread Library a) Pure user-level b) Pure kernel-level c) combined user-level thread kernel-level thread P Process"} />

| 模型 | 映射关系 | 多核并行 | 典型影响 |
| --- | --- | --- | --- |
| 多对一 | 多个 ULT → 1 个 KLT | 不能真正并行 | 某个阻塞调用可能拖住整个映射实体 |
| 一对一 | 1 个 ULT → 1 个 KLT | 可以 | 内核管理成本更高 |
| 多对多 | 多个 ULT → 多个 KLT | 可以 | 灵活但实现复杂 |

还可把“一对一”和“多对一”记成两个极端：前者把每条用户线程直接暴露给内核调度，后者则把全部用户线程压缩到一个内核可调度实体中。

<Callout type="warn" title="不要机械记“用户线程不能多核”">
能否利用多核，关键不是“线程是不是用户级”，而是**最终有多少个内核可调度实体**。多对多模型中的用户线程同样可以借助多个内核线程并行执行。
</Callout>
