## 15. 临界资源、竞态条件与互斥原则

> **复习优先级：高**

**共享资源**不一定是临界资源；只有需要互斥访问的共享资源才称 **临界资源**。访问临界资源的代码段称 **临界区（Critical Section）**。

例如：

```c
count++;
```

可能被编译为“读出 → 加一 → 写回”多步指令。若两个线程交叉执行，结果依赖时序，便产生 **竞态条件（Race Condition）**。

### 15.1 互斥与同步

- **互斥**：同一时刻谁能进入临界区？
- **同步**：多个执行流应该按什么先后关系协作？

互斥可以视为并发同步关系中的一种特殊约束。

### 15.2 临界区经典要求

<InlineSvg src="/images/operating-system/operating-system-process-sync-001.svg" alt={"图 1"} />

常见教材总结：

1. **空闲让进**：临界区空闲时，应允许有资格者进入；
2. **忙则等待**：已有执行流在临界区时，其他竞争者不能进入；
3. **有限等待**：不能让某个执行流无限期等待；
4. **让权等待**：不能继续时应尽量让出 CPU，而不是长期无意义忙等。

<Callout type="warn" title="进入临界区 ≠ 禁止调度">
线程在临界区内仍可能被中断或抢占。互斥只要求其他竞争同一临界资源的执行流不能同时进入，并不等于“临界区内 CPU 永远不切换”。
</Callout>

## 16. 软件互斥与 Peterson 算法

> **真题考察：**
> 2010 年第 27 题、2023 年第 45 题。

### 16.1 普通锁变量为什么错误

```c
bool lock = false;

while (lock) {
    ;
}
lock = true;
// critical section
lock = false;
```

“检查 `lock`”和“设置 `lock`”不是一个原子操作，两个线程都可能先观察到 `false`，随后一起进入临界区。

因此核心问题是：

> **检查 + 修改必须不可分割。**

### 16.2 严格轮流为什么不理想

<InlineSvg src="/images/operating-system/operating-system-process-sync-002.svg" alt={"图 2"} />

只用 `turn` 强制两个线程轮流进入，虽然可保持互斥，却可能违反**空闲让进**：轮到某线程但它根本不想进入时，另一个线程也会被无意义挡住。

### 16.3 Peterson 算法

Peterson 算法针对两个执行流：

- `flag[i]`：线程 $i$ 是否想进入；
- `turn`：双方同时竞争时把优先机会让给谁。

```c
bool flag[2] = {false, false};
int turn = 0;

void thread0() {
    flag[0] = true;
    turn = 1;
    while (flag[1] && turn == 1) {
        ;
    }

    // critical section

    flag[0] = false;
}
```

另一个线程对称实现。

408 主要考其**软件互斥思想**。真实现代多核系统还需要考虑编译器优化、CPU 内存模型与内存屏障等，不能把教材伪代码直接当成通用工程实现。

## 17. 原子指令、自旋锁与阻塞锁

> **真题考察：**
> 2016 年第 27 题、2018 年第 32 题。

### 17.1 原子性

**原子操作**表示对并发观察者具有不可分割语义，不意味着“必然只耗一个时钟周期”。

### 17.2 TAS：Test-and-Set

逻辑可写成：

```c
bool test_and_set(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
```

硬件保证“读旧值 + 写新值”整体原子。

```c
while (test_and_set(&mutex)) {
    ;
}
// critical section
mutex = false;
```

这形成 **自旋锁（Spin Lock）**：获取不到锁时继续占 CPU 反复检查。

### 17.3 CAS：Compare-and-Swap

CAS 的抽象逻辑是：仅当内存值等于期望值时，原子地把它替换为新值。

```c
while (!compare_and_swap(&mutex, 0, 1)) {
    ;
}
// critical section
mutex = 0;
```

TAS/CAS 都解决普通“检查—修改”不是原子操作的问题。

### 17.4 自旋等待还是阻塞等待

| 方式 | 获取不到资源时 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 自旋 | 持续运行检查 | 避免睡眠/唤醒切换 | 浪费 CPU |
| 阻塞 | 进入等待态 | 不空耗 CPU | 阻塞/唤醒有调度开销 |

一般而言，预计等待极短且多核可并行释放锁时，自旋可能划算；预计等待较长时阻塞更合理。

<Callout type="warn" title="不要混淆“忙等”和“饥饿”">
忙等是**等待方式**；饥饿是**长期得不到所需资源/调度机会的结果**。一个执行流可以阻塞着饥饿，也可以自旋但很快成功。
</Callout>

## 18. 互斥锁与条件变量

<InlineSvg src="/images/operating-system/operating-system-process-sync-003.svg" alt={"图 3"} />
<InlineSvg src="/images/operating-system/operating-system-process-sync-004.svg" alt={"图 4"} />

> **真题考察：**
> 条件变量：2018 年第 28 题。

### 18.1 Mutex

互斥锁保证任意时刻最多一个持有者进入受保护临界区。

```c
lock(&mtx);
// critical section
unlock(&mtx);
```

阻塞式互斥锁在竞争失败时，典型过程是：

> 加入等待队列 → 阻塞让出 CPU → 锁释放后被唤醒 → 进入就绪态 → 重新竞争锁。

注意：被唤醒不等于立即运行，也不等于一定立刻获得锁。

### 18.2 条件变量 Condition Variable

<InlineSvg src="/images/operating-system/operating-system-process-sync-005.svg" alt={"图 5"} />

条件变量表达：

> **“某个共享状态不满足时先睡眠，状态变化后再回来检查。”**

经典写法：

```c
lock(mutex);

while (!condition) {
    wait(cond, mutex);
}

// condition 成立，且当前持有 mutex

unlock(mutex);
```

`wait(cond, mutex)` 的关键语义通常是：

1. **原子地释放 mutex 并进入等待**；
2. 被 `signal` / `broadcast` 唤醒后重新竞争 mutex；
3. 重新获得 mutex 后 `wait` 才返回。

为什么用 `while` 而不是 `if`：

- 被唤醒不保证条件此刻仍成立；
- 其他线程可能先获得锁并改变状态；
- 某些实现允许伪唤醒。

因此：

> **signal 表示“状态可能改变了”，不是把条件永久变成真。**

## 19. 信号量：P/V 的统一语义

<InlineSvg src="/images/operating-system/operating-system-process-sync-006.svg" alt={"图 6"} />
<InlineSvg src="/images/operating-system/operating-system-process-sync-007.svg" alt={"图 7"} />

> **真题考察：**
> 选择题：2010 年第 25 题、2018 年第 32 题、2026 年第 26 题。
> 解答题：2017 年第 46 题、2024 年第 46 题。

**Semaphore（信号量）** 可以同时表达：

- 互斥；
- 前驱关系；
- 可用资源数量；
- 更复杂的同步条件。

两个基本操作必须按**原子语义**实现：

- `P(S)` / `wait(S)`：申请资源或等待事件；
- `V(S)` / `signal(S)`：释放资源或发出一次同步通知。

教材中的一种经典“可为负”定义可写成：

```text
P(S):
    S.value--
    if S.value < 0:
        将本进程加入 S 的等待队列并阻塞

V(S):
    S.value++
    if S.value <= 0:
        从 S 的等待队列唤醒一个进程
```

这里“修改计数值 + 判断 + 阻塞/唤醒”整体必须由内核保证原子性；否则信号量本身也会产生竞态。

### 19.1 P 操作

若资源/许可可用，则占用一个；若不可用，则当前执行流按定义等待或阻塞。

### 19.2 V 操作

<InlineSvg src="/images/operating-system/operating-system-process-sync-008.svg" alt={"图 8"} />
<InlineSvg src="/images/operating-system/operating-system-process-sync-009.svg" alt={"图 9"} />

释放一个资源/许可，或唤醒等待者中的某一个（具体队列策略由实现决定）。

<Callout type="info" title="信号量数值看题设定义">
有的教材让信号量保持非负，并另设等待队列；经典定义也可能允许负值。若采用上面的经典定义，则 $S.value=-k$ 可理解为有 $k$ 个进程因该信号量而等待。考试时不要机械套“负数含义”，先看题目给出的 P/V 伪代码。
</Callout>

<Callout type="warn" title="信号量的 V 与条件变量的 signal 不等价">
计数信号量的 V 会“积累许可”：即使当前无人等待，计数也会增加；条件变量的 `signal` 通常只唤醒当时已经在等待的线程，**不会把通知永久存起来**。这是两者最重要的语义差异之一。
</Callout>

## 20. 信号量三种基本建模模式

### 20.1 互斥：初值通常为 1

```c
semaphore mutex = 1;

P(mutex);
// critical section
V(mutex);
```

看到“同一时刻只能一个”时，优先考虑二元互斮信号量。

### 20.2 前驱关系：初值通常为 0

若必须满足“A 完成之后 B 才能开始”：

```c
semaphore s = 0;

A() {
    ...
    V(s);
}

B() {
    P(s);
    ...
}
```

口诀：

> **前驱完成后 V，后继开始前 P。**

若一个后继必须等待多个前驱，就必须分别收到这些前驱对应的“完成通知”，不能只等其中一个。

### 20.3 资源数量：初值等于可用实例数

若系统有 $N$ 个同类可复用资源：

```c
semaphore resource = N;

P(resource);
// use one resource
V(resource);
```

对资源信号量，P 表示“占用一个名额”，V 表示“归还一个名额”。

## 21. 一般前驱图与 P/V 翻译

<InlineSvg src="/images/operating-system/operating-system-process-sync-010.svg" alt={"图 10"} />

对于 DAG 中每条前驱边 $A\rightarrow B$，可设置一个初值为 `0` 的同步信号量：

```text
A 完成：V(s_AB)
B 开始：P(s_AB)
```

若：

- $S_2,S_3$ 在 $S_1$ 之后；
- $S_4,S_5$ 在 $S_2$ 之后；
- $S_6$ 等待 $S_3,S_4,S_5$；

则 $S_6$ 需要等待三条独立前驱通知。

<Callout type="warn" title="一份 V 不能凭空满足多个独立后继">
如果一个同步信号量执行一次 `V`，通常只增加一个许可/唤醒机会。一个前驱要同时放行多个独立后继时，必须根据模型提供足够的通知，不能把“一次 V”误当成广播。
</Callout>

## 22. 管程 Monitor

<InlineSvg src="/images/operating-system/operating-system-process-sync-011.svg" alt={"图 11"} />

> **真题考察：**
> 2016 年第 32 题、2018 年第 28 题。

**管程（Monitor）** 是更高层的同步抽象，通常封装：

- 共享数据；
- 操作共享数据的过程/方法；
- 互斥进入规则；
- 条件变量。

基本思想：

> **任意时刻通常只允许一个执行流在管程内部执行受保护操作；条件不满足者通过条件变量等待。**

相比裸写 P/V，管程更容易把共享数据、互斥规则和条件等待组织在一起，减少把同步顺序写乱的风险。

## 23. P/V 综合题通用解题法

<InlineSvg src="/images/operating-system/operating-system-process-problem-001.svg" alt={"同步问题解题模板（信号量法） ① 找进程与循环结构 把题中角色 → 进程 反复行为套 while(1) ② 找互斥关系 共享同一资源 + 同时仅一个 → 互斥信号量（初值 1） ③ 找同步关系 动作 A 必须先于 B → 同步信号量（初值 0） ④ 找资源数量约束 缓冲区 / 座位 / 设备 → 资源信号量（初值=容量） ⑤ 写 P/V 伪代码 先资源信号量，后互斥信号量 V 顺序通常对称即可 ⑥ 自检 P/V 成对、方向一致 无死锁、覆盖全部角色 三类信号量怎么选？ 按 “"} />

> **复习优先级：高**
>
> **真题综合题高频：**
> 2009、2011、2013、2014、2015、2019、2020、2021、2022、2025 等年份均出现过同步设计相关问题。

不要背整段模板，要做“自然语言约束 → 同步模型”的翻译。

### 23.1 第一步：列并发角色

谁在并发执行？生产者、消费者、读者、写者、顾客、服务员等分别建模为进程/线程。

### 23.2 第二步：圈出临界资源

看到“同一时刻只能一个访问” → 互斥信号量，初值通常为 `1`。

### 23.3 第三步：画前驱关系

看到“A 后才能 B” → 同步信号量，初值通常为 `0`，A 后 `V`，B 前 `P`。

### 23.4 第四步：写资源容量

看到“最多 N 个”“缓冲区 N 个槽” → 计数信号量初值通常为资源数量。

### 23.5 第五步：缩小临界区并检查 P/V 顺序

先检查所有 **P 操作的先后顺序**。若某进程先拿互斥锁，再去 P 一个可能长期为 $0$ 的资源信号量，它可能“拿着锁睡觉”，从而阻止其他进程进入临界区改变该资源条件，形成死锁。

V 操作的先后在很多经典模板里不影响正确性，但会影响被唤醒者何时竞争 CPU/锁；因此答题时仍建议采用结构清晰、与资源获得顺序对应的释放方式。

重点检查：

1. 互斥 P/V 是否成对；
2. 等待者是否在正确位置执行 P；
3. 前驱动作完成后是否执行 V；
4. 资源数量是否守恒；
5. 是否“拿着 mutex 再等另一个可能长期不可用资源”，从而增加死锁风险；
6. 是否覆盖全部并发角色和循环次数。

| 约束语言 | 常见信号量 | 典型初值 |
| --- | --- | ---: |
| “只能一个” | `mutex` | 1 |
| “A 后才能 B” | `sync` | 0 |
| “共有 N 个资源” | `resource` | N |
| “共享计数器需要保护” | `count_mutex` | 1 |

<Callout type="info" title="P/V 题真正要守的是不变量">
例如生产者—消费者中始终应满足“空槽数 + 产品数 = 缓冲区容量”。信号量只是维护这些系统不变量的工具。
</Callout>
