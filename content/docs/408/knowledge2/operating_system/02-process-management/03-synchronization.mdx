## 十五、同步与互斥

> **复习优先级：高**

这是 408 操作系统中最重要的综合题来源之一。

---

### 1. 临界资源与临界区

#### 临界资源

**临界资源**：

> 一次只允许一个进程或线程访问的共享资源。

例如：

* 多个线程共同修改的共享变量；
* 打印机；
* 某些需要独占修改的数据结构。

注意：

> **共享资源不一定是临界资源，需要互斥访问的共享资源才是临界资源。**

#### 临界区

**临界区（Critical Section）** 是访问临界资源的那段程序代码。

<InlineSvg src="/images/operating-system/operating-system-process-sync-001.svg" alt={"图 1"} />

---

### 2. 为什么需要互斥

高级语言的一条语句经常会被编译成多条机器指令。

例如：

```c
count++;
```

可能包含：

1. 读取；
2. 加一；
3. 写回。

线程可能在这些步骤之间被中断。

<InlineSvg src="/images/operating-system/operating-system-process-sync-002.svg" alt={"图 2"} />

如果两个线程同时执行这种“读—改—写”操作，就可能产生 **竞态条件（Race Condition）**。

因此对临界资源的访问必须互斥。

<Callout type="info" title="重要区分">
互斥并不意味着一个线程进入临界区后 CPU 绝对不会中断它。线程 A 可以在临界区内被抢占，但只要互斥机制仍有效，其他竞争同一临界资源的线程就不能趁机进入临界区。
</Callout>

---

## 十六、实现互斥的方法

| 方法   | 核心思想        |
| ---- | ----------- |
| 软件互斥 | 使用共享变量与算法控制 |
| 硬件互斥 | 使用硬件原子指令    |
| 互斥锁  | 使用锁同步原语     |
| 信号量  | 使用二元或计数信号量  |

---

### 1. 互斥锁 Mutex

互斥锁保证：

> 任意时刻最多一个线程持有锁。

<InlineSvg src="/images/operating-system/operating-system-process-sync-003.svg" alt={"图 3"} />

典型接口：

* `lock()` / `acquire()`
* `unlock()` / `release()`

```c
mutex mtx;

void thread() {
    // remainder section

    lock(&mtx);

    // critical section

    unlock(&mtx);

    // remainder section
}
```

如果锁已经被其他线程持有，获取失败的线程可能：

* 阻塞；
* 或采用短暂自旋；

具体取决于实现。

---

### 2. 阻塞式互斥锁的逻辑

当锁不可用时：

1. 当前线程进入等待状态；
2. 被加入锁对应的等待队列；
3. 不再占用 CPU 执行临界区竞争；
4. 锁释放后，等待线程之一被唤醒；
5. 被唤醒线程进入就绪态；
6. 之后重新获得 CPU。

<InlineSvg src="/images/operating-system/operating-system-process-sync-004.svg" alt={"图 4"} />

## 十七、软件互斥

> **真题考察：**
> 2010 年第 27 题；2023 年第 45 题。

### 1. 错误方案：普通锁变量

```c
bool lock = false;

void thread() {
    while (lock);

    lock = true;

    // critical section

    lock = false;
}
```

问题：

“检查锁是否为空”和“设置锁”为两个独立操作。

可能发生：

```text
线程 A                    线程 B
读取 lock = false
                         读取 lock = false
lock = true
                         lock = true
进入临界区
                         进入临界区
```

所以：

> **检查 + 修改必须具有原子性。**

---

### 2. 错误方案：严格轮流

```c
int turn = 0;

void thread0() {
    while (turn != 0);

    // critical section

    turn = 1;
}

void thread1() {
    while (turn != 1);

    // critical section

    turn = 0;
}
```

这种方式可以实现互斥，却可能违反 **空闲让进**。

如果临界区空闲，而当前 `turn` 指向的线程根本不想进入，那么另一个线程也会被迫等待。

---

### 3. Peterson 算法

Peterson 算法适用于两个执行流。

使用：

* `flag[i]` 表示线程 i 是否想进入临界区；
* `turn` 表示双方同时竞争时优先让谁进入。

```c
bool flag[2] = {false, false};
int turn = 0;

void thread0() {
    flag[0] = true;
    turn = 1;

    while (flag[1] && turn == 1) {
        ;
    }

    // critical section

    flag[0] = false;
}

void thread1() {
    flag[1] = true;
    turn = 0;

    while (flag[0] && turn == 0) {
        ;
    }

    // critical section

    flag[1] = false;
}
```

理论上它可以满足两个执行流的互斥要求，但：

* 只直接适用于两个参与者；
* 需要忙等；
* 现代多核系统的实际实现还涉及内存模型等问题。

408 中主要用于理解软件互斥思想。

## 十八、硬件互斥与原子指令

> **真题考察：**
> 2016 年第 27 题、2018 年第 32 题。

### 1. 原子性

**原子操作（Atomic Operation）**：

> 对并发观察者表现为不可分割的整体操作。

它不是说：

> “这条指令一定只需要一个时钟周期。”

而是说：

> 对并发执行者而言，中间状态不会以破坏原子语义的方式暴露。

普通高级语言语句通常不天然具有原子性保证。

---

### 2. TAS：Test-and-Set

逻辑上可以理解为：

```c
int test_and_set(bool *lock) {
    bool old = *lock;
    *lock = true;
    return old;
}
```

关键是：

> 上述“读旧值 + 写新值”由硬件保证为一个原子操作。

实现自旋锁：

```c
bool mutex = false;

void thread() {
    while (test_and_set(&mutex)) {
        ;
    }

    // critical section

    mutex = false;
}
```

如果锁已经为 `true`，线程不断尝试，因此称为 **自旋锁（Spin Lock）**。

---

### 3. CAS：Compare-and-Swap

逻辑：

```c
bool compare_and_swap(
    bool *lock,
    bool expected,
    bool new_value
) {
    if (*lock == expected) {
        *lock = new_value;
        return true;
    }

    return false;
}
```

硬件实际上保证整个比较和交换过程具有原子性。

实现自旋锁：

```c
int mutex = 0;

void thread() {
    while (!compare_and_swap(&mutex, 0, 1)) {
        ;
    }

    // critical section

    mutex = 0;
}
```

TAS 和 CAS 的核心作用都是解决：

> **普通“检查—修改”操作不是原子的。**

## 十九、同步

**互斥**主要解决：

> 同一时刻谁能访问共享资源？

**同步**主要解决：

> 多个执行流应该按照什么先后顺序协作？

因此：

> **互斥可以看作同步控制中的一种特殊关系。**

---

### 1. 临界区同步原则

经典原则：

1. **空闲让进**
2. **忙则等待**
3. **有限等待**
4. **让权等待**

其中：

* **忙等**：不断占用 CPU 检查条件；
* **长期得不到执行机会**：可能形成饥饿；
* **让权等待**：不能继续时主动阻塞，不持续浪费 CPU。

---

## 二十、条件变量

> **真题考察：**
> 2018 年第 28 题。

条件变量适用于：

> “必须等待某个共享状态条件成立后才能继续执行。”

核心操作：

#### wait

`wait()` 通常需要与互斥锁配合。

执行时：

1. 原子地释放关联锁；
2. 当前线程进入等待；
3. 被唤醒后重新竞争锁；
4. 获得锁后 `wait()` 才返回。

因此常写为：

```c
lock(mutex);

while (!condition) {
    wait(cond, mutex);
}

...  // condition 成立

unlock(mutex);
```

使用 `while` 而不是单纯 `if`，是因为：

* 被唤醒不等于条件一定仍成立；
* 其他线程可能先一步改变状态；
* 某些系统允许伪唤醒。

#### signal

唤醒一个等待该条件变量的线程。

#### broadcast / notify_all

唤醒所有等待该条件变量的线程。

## 二十一、信号量

> **真题考察：**
> 选择题：2010 年第 25 题、2018 年第 32 题、2026 年第 26 题。
> 解答题：2017 年第 46 题、2024 年第 46 题。

**信号量（Semaphore）** 是一种通用同步原语。

<InlineSvg src="/images/operating-system/operating-system-process-sync-006.svg" alt={"图 6"} />

它可以用于：

* 互斥；
* 前驱关系；
* 资源数量管理；
* 复杂进程同步。

两个基本原子操作：

* **P / wait**
* **V / signal**

<InlineSvg src="/images/operating-system/operating-system-process-sync-007.svg" alt={"图 7"} />

---

### 1. P 操作

抽象语义：

> 尝试申请一个资源。

若资源可用：

* 信号量减一；
* 继续执行。

若资源不可用：

* 当前进程或线程阻塞；
* 进入信号量的等待队列。

---

### 2. V 操作

抽象语义：

> 释放一个资源或发送一次同步通知。

可能执行：

* 增加资源计数；
* 唤醒等待该信号量的执行流。

<Callout type="info" title="关于信号量数值">
不同教材对信号量内部表示方法不同。有些伪代码使用非负计数并另设等待队列；经典实现也可能让信号量出现负值，并用负值表示等待进程数量。408 做题应优先按照题目给出的 P/V 定义计算，核心语义始终是“P 申请，V 释放/通知”。
</Callout>

## 二十二、信号量典型应用

### 1. 实现互斥

初值：

```c
semaphore mutex = 1;
```

```c
P1() {
    P(mutex);

    // critical section

    V(mutex);
}

P2() {
    P(mutex);

    // critical section

    V(mutex);
}
```

核心：

> **互斮信号量初值通常为 1。**

---

### 2. 实现简单前驱关系

若要求：

> A 完成后 B 才能执行。

则同步信号量初值通常设为 `0`。

```c
semaphore S = 0;

P1() {
    code1;

    V(S);
}

P2() {
    P(S);

    code2;
}
```

因此可以记成：

> **前驱执行者 V，后继执行者 P。**

---

### 3. 实现一般前驱图

若有如下依赖：

* S2、S3 必须在 S1 之后；
* S4、S5 必须在 S2 之后；
* S6 必须等待 S3、S4、S5。

<InlineSvg src="/images/operating-system/operating-system-process-sync-010.svg" alt={"图 10"} />

对 DAG 的每条依赖边都可设置一个初值为 `0` 的同步信号量。

```c
semaphore a1 = 0;
semaphore a2 = 0;
semaphore b1 = 0;
semaphore b2 = 0;
semaphore c  = 0;
semaphore d  = 0;
semaphore e  = 0;

S1() {
    ...
    V(a1);
    V(a2);
}

S2() {
    P(a1);
    ...
    V(b1);
    V(b2);
}

S3() {
    P(a2);
    ...
    V(e);
}

S4() {
    P(b1);
    ...
    V(c);
}

S5() {
    P(b2);
    ...
    V(d);
}

S6() {
    P(c);
    P(d);
    P(e);
    ...
}
```

## 二十三、管程

> **真题考察：**
> 2016 年第 32 题、2018 年第 28 题。

**管程（Monitor）** 是一种更高层次的同步抽象。

它通常把：

* 共享数据；
* 操作共享数据的方法；
* 互斥控制；
* 条件变量；

封装到一个结构中。

基本思想：

> 任意时刻通常只有一个执行流可以在管程内部执行受保护的操作。

其他执行流若不能进入，则等待。

管程中常通过条件变量进一步表达：

* 条件等待；
* 唤醒；
* 复杂同步。

<InlineSvg src="/images/operating-system/operating-system-process-sync-011.svg" alt={"图 11"} />

相比直接裸用 P/V：

* 结构更清晰；
* 封装性更好；
* 更容易维护同步不变量；
* 更不容易把 P/V 顺序写错。

## 二十四、经典同步问题：通用解题法

> **复习优先级：高**
>
> **真题综合题高频：**
> 2009、2011、2013、2014、2015、2019、2020、2021、2022、2025 等年份均出现过同步设计相关问题。

不要死背某一段代码，而应建立：

> **自然语言约束 → 同步关系 → 信号量 → P/V 位置**

的翻译能力。

---

### 1. 第一步：找进程

把题目中的并发参与者抽象成进程或线程，例如：

* 生产者；
* 消费者；
* 读者；
* 写者；
* 服务员；
* 顾客。

重复行为通常写：

```c
process_i() {
    while (1) {
        ...
    }
}
```

---

### 2. 第二步：找互斥关系

若多个进程访问同一资源，并且同一时刻只允许一个访问：

```c
semaphore mutex = 1;
```

```c
P(mutex);

// critical section

V(mutex);
```

<Callout type="warn" title="易错点">
互斥范围不要随意扩大。只保护真正的临界区，否则会降低并发度，甚至增加死锁风险。
</Callout>

---

### 3. 第三步：找同步关系

若：

> A 必须先发生，B 才允许发生。

则：

```c
semaphore s = 0;

A() {
    ...
    V(s);
}

B() {
    P(s);
    ...
}
```

---

### 4. 第四步：找资源数量约束

有限资源通常用计数信号量。

例如大小为 `n` 的缓冲区：

```c
semaphore empty = n;
semaphore full  = 0;
semaphore mutex = 1;
```

常见经验：

> **先 P 资源型信号量，再 P 互斮信号量。**

否则可能出现：

* 已持有互斥锁；
* 却等待某种资源；
* 其他进程又必须获得该互斥锁才能释放资源；

最终形成死锁。

---

### 5. 第五步：检查 P/V

完成代码后检查：

1. 互斥的 P/V 是否成对；
2. 谁等待，谁执行 P；
3. 谁完成前驱动作，谁执行 V；
4. 资源数量是否守恒；
5. 是否可能循环等待；
6. 所有并发角色是否都覆盖。

---

### 6. 常见信号量类型

| 类型      | 常见初值 | 用途        |
| ------- | ---: | --------- |
| 互斮信号量   |    1 | 保护临界区     |
| 同步信号量   |    0 | 表示前驱事件未发生 |
| 资源信号量   | 资源数量 | 表示剩余资源数   |
| 计数保护信号量 |    1 | 保护共享计数器   |
