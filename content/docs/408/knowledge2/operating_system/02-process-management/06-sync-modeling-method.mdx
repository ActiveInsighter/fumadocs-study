同步综合题真正考的是“翻译能力”：

> **自然语言约束 → 并发角色 → 共享资源 → 先后关系 → 信号量含义 → P/V 位置。**

不要死背某一题代码，因为题目换一个业务背景后，死背模板很容易套错。

> **真题标签**
>
> 同步问题设计是操作系统综合题的核心题型之一。2009、2011、2013、2014、2015、2019、2020、2021、2022、2025 等年份均出现过相关考查。

## 2.6.1 第一步：列出并发角色

把题目中的主动参与者写成进程/线程：

- 生产者、消费者；
- 读者、写者；
- 顾客、服务员；
- 奇数消费者、偶数消费者；
- 多类工序等。

若行为重复发生：

```c
process_i() {
    while (1) {
        ...
    }
}
```

若只是一次性流程，不必机械套 `while(1)`。

## 2.6.2 第二步：找所有“只能一个”的共享对象

看到：

- “一次只能一个进程访问”；
- “对共享计数器的修改不能并发”；
- “插入/删除必须原子保护”；

就考虑互斥：

```c
semaphore mutex = 1;
```

但要只包住真正临界区：

```c
produce_item();     // 通常可放外面
P(mutex);
put_item();         // 操作共享缓冲区
V(mutex);
```

<Callout type="warn" title="临界区越大不一定越安全">
把与共享资源无关的耗时操作也锁住，会降低并发度；若锁内再等待其他条件，还可能引入新的死锁风险。
</Callout>

## 2.6.3 第三步：把“必须先发生”画成箭头

若 A 必须先于 B：

```text
A ──s──▶ B
```

设：

```c
semaphore s = 0;
```

然后：

```text
A 完成关键动作：V(s)
B 执行前：P(s)
```

若 B 必须等 A、C 都完成，就需要表达两个前驱条件，而不是“随便等其中一个”。

## 2.6.4 第四步：把数量上限变成计数信号量

自然语言常见模式：

- “最多允许 $N$ 个”；
- “共有 $N$ 个空位”；
- “共有 $K$ 台设备”；
- “缓冲区容量为 $N$”。

可以直接把初始可用数量设为信号量初值。

例如：

```c
semaphore slots = N;
```

进入前 `P(slots)`，离开/释放后 `V(slots)`。

## 2.6.5 第五步：为每个信号量写一句中文含义

这是综合题最有效的自检技巧之一。

例如：

```text
mutex：当前是否允许进入缓冲区临界区（初值 1）
empty：空槽数量（初值 N）
odd：缓冲区内可供奇数消费者取得的奇数数量（初值 0）
even：缓冲区内可供偶数消费者取得的偶数数量（初值 0）
```

如果你无法用一句清楚中文解释一个信号量，它往往就设计得过于混乱或多余。

## 2.6.6 第六步：确定 P/V 离事件有多近

同步信号量要围绕“事件发生点”放置：

- **P** 放在“没有这个许可就不能继续”的动作之前；
- **V** 放在“我刚刚创造了这个许可/资源”的动作之后。

例如：

```text
生产产品入缓冲区之后，才 V(full)
消费者真正取走产品之后，才 V(empty)
```

不要把 V 提前到资源状态还没有真正改变之前。

## 2.6.7 第七步：做四类安全检查

### 互斥检查

每个临界资源是否始终被互斥保护？

### 同步方向检查

是否“等待者 P，通知者 V”？是否存在漏掉的前驱？

### 数量守恒检查

如果一个产品从“空槽”转化为“满槽”：

```text
empty - 1
full  + 1
```

消费时反向转换。资源计数不能凭空产生。

### 死锁检查

把“持有什么、还在等什么”列出来：

```text
进程 A：持有 mutex，等待 empty
进程 B：需要 mutex 才能释放 empty
```

若形成闭环，就有问题。

## 2.6.8 复杂题先画约束图，再写代码

若题目有多个工序：

```text
A 完成后 B、C 才能开始
B、C 都完成后 D 才能开始
```

先画：

```text
      ┌──▶ B ──┐
A ────┤         ├──▶ D
      └──▶ C ──┘
```

再为依赖边或汇合条件设计信号量。

这样比直接在伪代码中“边想边 P/V”更不容易漏关系。

## 2.6.9 常见信号量模式速查

| 自然语言 | 常见初值 | 典型解释 |
| --- | ---: | --- |
| “一次只能一个” | 1 | 互斥许可 |
| “A 后 B” | 0 | 前驱事件尚未发生 |
| “最多 N 个” | N | N 个可用名额/资源 |
| “当前有多少产品” | 0 或题给数量 | 已存在资源计数 |
| “保护共享计数器” | 1 | 计数变量自身也要互斥 |

## 2.6.10 综合题最后一遍检查清单

写完代码后逐条问：

1. 每个信号量的含义和初值是否一致？
2. 每个 `P` 对应的资源/事件究竟是谁提供的？
3. 每个 `V` 是不是在状态真正改变后发生？
4. 互斥锁是否只包临界区？
5. 是否存在“拿着 mutex 再等一个只能由别人进 mutex 才能创造的条件”？
6. 资源数量是否守恒？
7. 是否可能长期偏袒某一类进程而产生饥饿？
8. 所有并发角色是否都写了伪代码？

> **真题建模口诀**
>
> **先列角色，再找共享；先画顺序，再数资源；最后落 P/V，并查死锁。**
