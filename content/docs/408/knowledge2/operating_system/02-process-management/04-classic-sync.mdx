## 24. 生产者—消费者问题

<InlineSvg src="/images/operating-system/operating-system-process-problem-002.svg" alt={"Producer Producer Consumer Consumer Text is not SVG - cannot display"} />
<InlineSvg src="/images/operating-system/operating-system-process-problem-003.svg" alt={"ProducerConsumer"} />

生产者与消费者共享容量为 $N$ 的有限缓冲区，要同时满足：

1. 缓冲区数据结构需要互斥访问；
2. 缓冲区满时生产者不能继续放入；
3. 缓冲区空时消费者不能继续取出。

因此最经典的三个信号量：

```c
semaphore mutex = 1;
semaphore empty = N;
semaphore full  = 0;
```

其系统不变量是：

$$empty + full = N$$

生产者：

```c
producer() {
    while (1) {
        produce_item();

        P(empty);
        P(mutex);

        put_item();

        V(mutex);
        V(full);
    }
}
```

消费者：

```c
consumer() {
    while (1) {
        P(full);
        P(mutex);

        get_item();

        V(mutex);
        V(empty);

        consume_item();
    }
}
```

三者含义：

- `empty`：剩余空槽数；
- `full`：已有产品数；
- `mutex`：保护缓冲区内部读写。

除 $empty+full=N$ 外，还应始终满足：

$$0\le empty\le N,\qquad 0\le full\le N$$

这三个量分工不同：`empty/full` 解决**同步与容量约束**，`mutex` 解决**临界区互斥**，不能相互替代。

### 24.1 为什么通常先 P 资源，再 P 互斥锁

生产者先 `P(empty)`，消费者先 `P(full)`，确认“业务条件”满足后再进入缓冲区临界区。

如果反过来先持有 `mutex`，再等待 `empty/full`，可能出现：

> 当前进程拿着缓冲区互斥锁睡眠，而另一类进程必须拿到同一把锁才能改变 `empty/full`，于是形成死锁。

因此经典有界缓冲区中，**P 的顺序是关键**：先检查容量资源，再进入互斥区。`V(mutex)` 与 `V(full/empty)` 在这一标准模型中通常都能维持正确性，但先释放互斥锁能让临界区尽快开放，结构也更清楚。

<Callout type="warn" title="不要把 produce/consume 全包进 mutex">
`produce_item()` 和 `consume_item()` 若不访问共享缓冲区，就应放在临界区外。临界区越小，并发度越高。
</Callout>

## 25. 读者—写者问题

<InlineSvg src="/images/operating-system/operating-system-process-problem-004.svg" alt={"reader reader reader reader writer writer x reader writer writer x x writer 可以多个读者一起读， 但是此时写者不能写 系统一个时刻最多允许一个写者在写， 并且此时其他读者和写者都不允许操作"} />

基本要求：

- 多个读者可同时读；
- 写者与写者互斥；
- 写者与任意读者互斥；
- 写者访问时独占资源。

| 当前状态 | 新读者 | 新写者 |
| --- | --- | --- |
| 无人访问 | 可进入 | 可进入 |
| 有读者 | 可并发读 | 等待 |
| 有写者 | 等待 | 等待 |

### 25.1 读者优先

使用：

- `read_count`：当前读者数；
- `mutex`：保护 `read_count`；
- `wrt`：控制共享资源访问。

```c
int read_count = 0;
semaphore wrt   = 1;
semaphore mutex = 1;

reader() {
    while (1) {
        P(mutex);
        read_count++;
        if (read_count == 1) {
            P(wrt);
        }
        V(mutex);

        read();

        P(mutex);
        read_count--;
        if (read_count == 0) {
            V(wrt);
        }
        V(mutex);
    }
}

writer() {
    while (1) {
        P(wrt);
        write();
        V(wrt);
    }
}
```

核心机制：

> **第一个读者替读者群体锁住写者，最后一个读者替群体释放写者。**

但若读者持续到达，写者可能长期得不到机会，即**写者饥饿**。

### 25.2 写者优先

目标：一旦已有写者等待，后来的新读者不再不断插队。

一种经典实现增加：

- `write_count`：等待/活跃写者计数；
- `write_mutex`：保护该计数；
- `readTry`：写者到来后临时关闭新读者入口。

```c
int read_count  = 0;
int write_count = 0;

semaphore wrt         = 1;
semaphore mutex       = 1;
semaphore write_mutex = 1;
semaphore readTry     = 1;
```

第一个写者执行 `P(readTry)`，阻止后来的新读者继续进入；最后一个写者离开后再 `V(readTry)`。

这种策略可缓解写者饥饿，但若设计成过强的写者偏好，也可能让读者长期等待。

### 25.3 公平方案

<InlineSvg src="/images/operating-system/operating-system-process-problem-005.svg" alt={"ReaderWriterProblem"} />

可再引入统一“入口闸门/排队信号量”，使新到达的读者和写者都按某种顺序竞争进入资格，从而避免后一类持续插队。若该闸门本身按 FIFO 排队，就能近似实现“先到先服务”的公平读写策略；但**公平性是否严格成立仍取决于信号量/锁的唤醒队列规则**。

关键不是背某段唯一代码，而是识别三层资源：

1. 共享数据本身的读/写权限；
2. 读者计数 `read_count` 的互斥保护；
3. 是否需要额外的公平入口策略。

<Callout type="warn" title="read_count 本身也是共享变量">
多个读者可以并发“读数据”，但对 `read_count++/--` 的修改必须互斥，否则计数本身会产生竞态。
</Callout>

## 26. 哲学家就餐问题

<InlineSvg src="/images/operating-system/operating-system-process-problem-006.svg" alt={"SVG figure 6"} />
<InlineSvg src="/images/operating-system/operating-system-process-problem-007.svg" alt={"图示"} />

假设有 $N$ 位哲学家围成一圈，每两位相邻哲学家之间有一把叉子，哲学家进餐必须同时获得左右两把叉子。

若所有哲学家都执行：

> 先拿左叉，再拿右叉

就可能形成：

```text
P0：持有左叉，等待右叉
P1：持有左叉，等待右叉
...
PN-1：持有左叉，等待右叉
```

每个人都持有一个资源并等待下一个人的资源，形成环形等待，因此可能死锁。

### 26.1 破坏循环等待

最直接方法之一：让最后一位哲学家按相反顺序取叉。

```c
semaphore fork[N] = {1, 1, ..., 1};

void philosopher(int i) {
    int first, second;

    if (i != N - 1) {
        first  = i;
        second = (i + 1) % N;
    } else {
        first  = (i + 1) % N;
        second = i;
    }

    while (1) {
        think();

        P(fork[first]);
        P(fork[second]);

        eat();

        V(fork[second]);
        V(fork[first]);
    }
}
```

其他常见思路：

- 最多允许 $N-1$ 位哲学家同时尝试取叉；
- 通过管程/服务员一次性检查两把叉是否都可用；
- 给所有叉统一编号，并要求所有哲学家都按编号从小到大申请。

最后一种“资源全序”方法最值得迁移：只要所有进程都严格按同一全局顺序申请多类独占资源，就能破坏**循环等待**条件。

这些方案本质都在破坏死锁形成条件中的某一项，尤其常针对**循环等待**或**占有并等待**。

<Callout type="info" title="哲学家题的核心不是叉子">
它是“多个进程需要同时获得多个独占资源”的抽象模型。做题时应直接检查：是否可能每个进程各占一部分资源，然后形成等待环。
</Callout>
