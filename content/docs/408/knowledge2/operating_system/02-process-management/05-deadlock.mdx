## 27. 死锁、饥饿与四个必要条件

<InlineSvg src="/images/operating-system/operating-system-process-deadlock-001.svg" alt={"P1 P2 P3 P4 A B C D 占有 想要"} />

> **真题考察：**
> 2014 年第 24 题、2019 年第 30 题、2021 年第 31 题。

**死锁（Deadlock）**：一组进程中的每个进程都在等待只能由该组其他进程释放的资源或事件，导致相关进程都无法继续。

### 27.1 四个必要条件

死锁发生需要四个条件同时成立：

1. **互斥**：某些资源一次只能被一个进程占用；
2. **占有并等待**：进程占有一部分资源的同时继续等待其他资源；
3. **非抢占**：已分配资源不能被系统任意强制夺走；
4. **循环等待**：存在闭合等待链。

循环等待可写为：

$$P_1\rightarrow P_2\rightarrow\cdots\rightarrow P_n\rightarrow P_1$$

<Callout type="warn" title="必要条件不是充分条件的逐项判断">
四个条件缺一则不会发生经典资源死锁；但仅知道某一个或某几个条件成立，不能推出已经死锁。判断死锁最终还要看系统当前资源关系。
</Callout>

### 27.2 死锁与饥饿

| 现象 | 含义 | 是否一定存在等待环 |
| --- | --- | --- |
| 死锁 | 一组进程彼此等待，整体无法推进 | 经典资源死锁常有 |
| 饥饿 | 某个进程长期得不到 CPU/资源 | 不一定 |

饥饿可能来自不公平调度或优先级策略，即使其他进程一直在正常推进，也可能发生。

## 28. 死锁处理：预防、避免、检测与解除

<InlineSvg src="/images/operating-system/operating-system-process-deadlock-002.svg" alt={"死锁预防 (Deadlock Prevention) 1. 破坏互斥条件 • 资源复制或虚拟化技术 • 减少资源的互斥使用 • 某些硬件资源难以避免互斥 共享 2. 破坏占有并等待 • 一次性申请所有所需资源 • 申请失败则释放已分配资源 一次性 3. 破坏非抢占 • 允许进程抢占其他进程的资源 • 需要时可强制回收资源 抢占 4. 破坏循环等待 • 对资源申请顺序进行限制 • 按固定顺序申请资源 1 2 3 顺序 ! 核心思想 通过破坏死锁产生的四个必要条件中的至少一个，从"} />

> **真题考察：**
> 2015 年第 26 题、2016 年第 25 题。

| 策略 | 核心思想 | 代价/特点 |
| --- | --- | --- |
| 预防 Prevention | 制度上破坏至少一个必要条件 | 限制较强，资源利用率可能低 |
| 避免 Avoidance | 每次分配前保证系统仍处于安全状态 | 需要知道最大需求等信息 |
| 检测与解除 Detection & Recovery | 允许死锁发生，之后检测并恢复 | 需承担检测与恢复成本 |

### 28.1 死锁预防的四类方法

**破坏互斥**：把资源改造成可共享。对天然独占资源通常不可行。

**破坏占有并等待**：

- 一次性申请全部资源；或
- 申请新资源失败时先释放已占有资源。

**破坏非抢占**：允许系统在适当条件下收回资源。适用于可以保存/恢复状态的资源。

**破坏循环等待**：给资源建立全局顺序，例如：

$$R_1<R_2<R_3<R_4$$

所有进程只按规定顺序申请资源，就不能形成反向闭环等待。

## 29. 银行家算法：数据结构与资源请求

<InlineSvg src="/images/operating-system/operating-system-process-deadlock-003.svg" alt={"MAX A B C Allocation Need Available A B C A B C A B C P0 P1 P2 P3 P4 7 5 3 3 2 2 9 0 2 2 2 2 4 3 3 0 1 0 2 0 0 3 0 2 2 1 1 0 0 2 7 4 3 1 2 2 6 0 0 0 1 1 4 3 1 3 3 2"} />
<InlineSvg src="/images/operating-system/operating-system-process-deadlock-004.svg" alt={"进程提出资源请求 Y N 资源数是否 ≤ 进程可拥有的最大值 分配失败 N 资源数是否 ≤ 系统可分配量 系统预分配 系统执行安全性检查算法 在系统试分配的基础上，统计 系统剩余资源量 Y Y 能否找到一个可执行 进程，执行并回收 其 占用的资源 N Y 能否找到一条 安全序列 分配成功 银行家算法 安全性检查算法"} />

> **真题考察：**
> 2011 年第 27 题、2012 年第 27 题、2013 年第 32 题、2018 年第 26 题、2020 年第 27 题、2022 年第 26 题。

银行家算法属于 **死锁避免**：不要求破坏四个必要条件，而是在每次分配前确保系统不会进入不安全状态。

### 29.1 四个核心量

对每类资源建立向量/矩阵：

- `Available`：系统当前剩余资源；
- `Max`：每个进程声明的最大需求；
- `Allocation`：当前已分配资源；
- `Need`：未来最多还需要的资源。

$$Need = Max - Allocation$$

### 29.2 处理进程请求 `Request_i`

对进程 $P_i$：

第一关：请求不能超过它声明的剩余最大需求。

$$Request_i\le Need_i$$

第二关：系统当前必须有足够资源可供试分配。

$$Request_i\le Available$$

若都满足，执行**试分配**：

$$Available' = Available - Request_i$$

$$Allocation_i' = Allocation_i + Request_i$$

$$Need_i' = Need_i - Request_i$$

随后对试分配后的状态运行安全性算法：

- 安全 → 正式批准；
- 不安全 → 撤销试分配，恢复原状态。

<Callout type="warn" title="Request ≤ Available 还不够">
“当前拿得出来”只说明资源够发，不说明发完以后所有进程还能最终完成。因此银行家算法必须继续做安全性检查。
</Callout>

## 30. 安全状态、安全序列与安全性算法

<InlineSvg src="/images/operating-system/operating-system-process-deadlock-005.svg" alt={"A B C 安全分配序列 资源 3 3 2 P1 5 3 2 P3 7 4 3 P0 7 5 3 P2 10 5 5 P4 10 5 7"} />

如果存在某个进程序列：

$$P_{i_1},P_{i_2},\cdots,P_{i_n}$$

使每个进程轮到自己时都能获得剩余所需资源并完成，然后释放其占有资源，则该序列是**安全序列**。

- 存在至少一个安全序列 → **安全状态**；
- 不存在安全序列 → **不安全状态**。

<Callout type="warn" title="不安全状态 ≠ 已经死锁">
正确关系是：**死锁状态一定不安全；不安全状态当前未必已经死锁。** 不安全表示系统已经失去“保证所有进程都能完成”的能力，未来可能进入死锁。
</Callout>

### 30.1 安全性算法

<InlineSvg src="/images/operating-system/operating-system-process-deadlock-006.svg" alt={"BankersAlgorithm"} />

使用临时向量：

$$Work = Available$$

并初始化：

```text
Finish[i] = false
```

反复寻找尚未完成且满足：

$$Need_i\le Work$$

的进程。若找到，就假设它得到所需资源并运行完成，随后释放其**原已分配资源**：

$$Work = Work + Allocation_i$$

并令：

```text
Finish[i] = true
```

重复直到：

- 所有 `Finish[i] = true` → 安全；
- 再也找不到可完成进程但仍有 `false` → 不安全。

### 30.2 为什么只加 `Allocation_i`

在安全性算法中，$Work$ 表示当前可用于满足“剩余需求”的资源。假设 $P_i$ 获得 `Need_i` 后完成，它会归还 `Allocation_i + Need_i`，但 `Need_i` 是刚从 `Work` 临时给出去的，给出再归还彼此抵消，因此净增加量正好是：

$$Allocation_i$$

这也是银行家算法综合题非常容易算错的一步。

## 31. 死锁检测与资源分配图

<InlineSvg src="/images/operating-system/operating-system-process-deadlock-007.svg" alt={"死锁的检测与解除 · Deadlock Detection & Recovery ① 死锁检测 (Detection) 资源分配图 · DFS 找环 将进程与资源建模为有向图，环 = 死锁 资源分配图示例 P1 P2 R1 R2 请求 请求 存在环路 进程 资源 边 检测步骤 1 为请求/分配关系建立有向边 2 对资源分配图执行 DFS / 简化 3 若存在环 → 系统已死锁 4 环中进程即为死锁进程 📌 小贴士 • 单实例资源：图中有环 ⇔ 死锁 • 多实例资源：有环只是必"} />

资源分配图中：

- 进程节点表示进程；
- 资源节点表示资源；
- 请求边：进程 $\rightarrow$ 资源；
- 分配边：资源 $\rightarrow$ 进程。

### 31.1 每类资源只有一个实例

若每一种资源都只有一个实例，则：

> **资源分配图存在环 ⇔ 存在死锁。**

### 31.2 多实例资源

当某类资源有多个实例时：

> **存在环只能说明存在潜在循环关系，不能仅凭“有环”就充分断定死锁。**

通常需要基于当前：

- `Available`；
- `Allocation`；
- `Request`；

运行类似“能否不断找到可完成进程”的检测算法。

<Callout type="info" title="避免算法和检测算法看起来很像，但输入语义不同">
银行家安全性检查关注未来最大剩余需求 `Need`；死锁检测通常关注进程当前实际尚未满足的请求 `Request`。不要把两张表混用。
</Callout>

## 32. 死锁解除

检测到死锁后，常见恢复办法有三类。

### 32.1 终止进程

- 一次终止全部死锁进程；或
- 逐个终止，直到等待环被打破。

选择牺牲者可考虑优先级、已执行时间、剩余工作量、已占资源和回滚成本等。

### 32.2 抢占资源

从某些进程手中收回资源，再分配给其他进程。需要解决：

- 牺牲者选择；
- 状态回滚；
- 避免同一进程反复成为牺牲者而饥饿。

### 32.3 回滚

若系统支持检查点，可恢复到较早安全状态，再重新执行部分工作。

## 34. 408 综合题解题框架

### 34.1 调度题

先画时间轴，再算：

$$TAT=CT-AT$$

$$RT=ST-AT$$

若没有单独 I/O 阻塞：

$$WT=TAT-BT$$

HRRN：

$$R=\frac{WT+BT}{BT}$$

RR：维护**就绪队列**，不要只凭“轮流”直觉写编号。

### 34.2 状态转换题

记住：

> **阻塞事件完成：阻塞 → 就绪。**
>
> **等待事件：运行 → 阻塞。**
>
> **CPU 被剥夺但仍可继续：运行 → 就绪。**

### 34.3 P/V 题

看到“只能一个” → `mutex = 1`。

看到“A 后才能 B” → `s = 0`，A 后 `V(s)`，B 前 `P(s)`。

看到“共有 N 个资源” → 计数信号量初值为 $N$。

### 34.4 生产者—消费者

固定资源框架：

```c
semaphore empty = N;
semaphore full  = 0;
semaphore mutex = 1;
```

生产：

```text
P(empty)
P(mutex)
放入产品
V(mutex)
V(full)
```

消费：

```text
P(full)
P(mutex)
取出产品
V(mutex)
V(empty)
```

### 34.5 读者—写者

读者优先经典结构：

> **第一个读者锁住写者，最后一个读者释放写者；修改 `read_count` 本身也必须互斥。**

### 34.6 银行家算法

固定顺序：

1. 计算 `Need`；
2. 检查 `Request ≤ Need`；
3. 检查 `Request ≤ Available`；
4. 试分配；
5. 执行安全性算法；
6. 安全则批准，否则回滚。

其中：

$$Need=Max-Allocation$$

安全性算法持续寻找：

$$Need_i\le Work$$

找到后：

$$Work=Work+Allocation_i$$

<Callout type="info" title="把整章压缩成一条链">
**程序运行形成进程 → 进程包含线程 → 调度器决定谁用 CPU → 并发产生竞态 → 互斥/同步约束执行顺序 → 信号量描述资源和前驱关系 → 复杂资源竞争可能死锁 → 通过预防、避免、检测与解除处理。**
</Callout>
