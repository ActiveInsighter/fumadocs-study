中断和异常机制是操作系统取得处理机控制权的基础。最核心的学习方式不是死背名词，而是回答三个问题：

1. **事件从哪里来？**
2. **由硬件自动完成哪些动作？**
3. **内核软件接管后完成哪些动作？**

> **真题标签｜系统调用**
>
> 参考真题索引：选择题 2012#28、2013#28、2017#24、2019#25、2021#32、2022#31、2024#29。

## 1.3.1 三类进入内核的典型事件

| 类型 | 典型来源 | 与当前指令的关系 | 典型例子 |
| --- | --- | --- | --- |
| 外部中断 | CPU 外部设备或时钟 | 通常异步 | 时钟到期、I/O 完成、网卡到包 |
| 异常 | 当前指令执行或内部状态 | 通常同步 | 除零、非法指令、缺页、保护错误 |
| 系统调用/陷入 | 用户程序主动执行受控指令 | 同步且主动 | `read`、`write`、创建进程 |

教材术语有时把“中断”用作广义总称，也可能把内部异常称“内中断”。做题时要以题目上下文为准；若题目明确比较“中断与异常”，通常可按“外部异步 vs 指令相关同步”区分。

## 1.3.2 外部中断

外部中断由处理器外部事件提出，例如：

- 时钟中断；
- 磁盘、键盘、网卡等设备完成 I/O；
- 其他外部中断源。

典型流程：

```text
当前程序运行
   ↓
外部设备提出中断请求
   ↓
CPU 在合适的指令边界响应
   ↓
硬件保存必要返回信息并进入内核态
   ↓
转到中断处理入口
   ↓
内核保存更完整现场并处理中断
   ↓
恢复现场并返回
```

### 为什么时钟中断特别重要

若用户程序一直运行且不主动进入内核，操作系统也必须有办法周期性重新取得 CPU 控制权。

时钟中断使内核能够：

- 更新计时；
- 检查时间片；
- 触发调度；
- 维护超时事件。

因此抢占式多任务系统离不开时钟和中断机制。

## 1.3.3 异常

异常通常由**当前指令执行过程中**检测到的内部事件引发，例如：

- 整数除零；
- 非法指令；
- 地址保护错误；
- 缺页；
- 调试断点；
- 某些主动陷入指令。

异常是同步的：执行到相关指令才会出现。

不同异常处理后，返回位置并不一定相同：

- 有的处理完可重新执行原指令，如可恢复的缺页；
- 有的从下一条指令继续；
- 有的属于严重故障，直接终止当前进程。

因此不要机械记忆“异常返回一定执行下一条”或“一定重执行当前指令”。

## 1.3.4 硬件响应和软件处理要分开

这是 408 高频考法。

事件被 CPU 接受后，**必须先由硬件完成最低限度的控制转移**，典型包括：

- 保存必要断点/返回地址；
- 保存或更新必要的处理器状态；
- 切换到规定的高特权模式；
- 根据向量/入口机制取得处理程序入口并开始执行。

之后内核软件再完成：

- 保存通用寄存器等更完整现场；
- 判断中断/异常原因；
- 执行服务程序；
- 必要时进行调度；
- 恢复现场并返回。

> **真题易错点**
>
> “把 CPU 模式从用户态改为内核态”是硬件响应受控事件时自动完成的关键动作，不是先在用户态运行一段内核代码，再由软件自己把权限改高。

## 1.3.5 什么是系统调用

**系统调用（System Call）**&#x2060;是应用程序请求操作系统内核服务的程序接口。

典型服务：

- 进程/线程创建、终止、等待；
- 文件打开、读取、写入、关闭；
- 网络通信；
- 设备控制；
- 某些内存管理服务。

它建立了一个安全边界：

> **用户程序只能通过内核预先设计好的受控入口提出请求，不能任意跳入内核代码执行。**

## 1.3.6 系统调用的完整路径

抽象过程：

```text
用户程序准备参数和调用号
        ↓
执行系统调用/陷入指令
        ↓
CPU 硬件保存必要返回信息
并切换到内核态、进入统一入口
        ↓
内核保存需要保护的现场
        ↓
根据调用号找到对应服务例程
        ↓
执行内核服务
        ↓
形成返回值
        ↓
恢复现场并通过受控返回机制回用户态
```

不同 ISA 和操作系统的寄存器约定、调用号位置、入口指令不同，但上述逻辑相同。

早期 32 位 x86 Linux 常举例 `int 0x80`；现代 x86-64 更常使用 `syscall/sysret`。考试重点是机制，而不是把某个平台的具体指令当成通用规则。

## 1.3.7 系统调用、库函数、普通函数调用

三者不能混为一谈。

| 对比 | 普通函数调用 | 库函数 | 系统调用 |
| --- | --- | --- | --- |
| 调用对象 | 当前程序/链接代码中的函数 | 用户态库提供的 API | 内核服务 |
| 是否必进内核 | 否 | 不一定 | 是 |
| 是否发生特权级转换 | 否 | 取决于内部实现 | 是 |
| 例子 | 自定义排序函数 | `strlen`、`printf` 等 | `read`、`write`、`fork` 等 |

注意：

- `strlen()` 这类函数可完全在用户态计算；
- `printf()` 通常先做用户态格式化/缓冲，真正输出时可能调用 `write()`；
- 某些库 API 内部可能组合多个系统调用。

因此：

> **库函数 ≠ 系统调用。**

## 1.3.8 系统调用一定导致进程切换吗

不一定。

系统调用**一定导致受控的用户态 → 内核态转换**，但当前执行实体可能仍是同一个进程：

```text
A(用户态) → A(内核态) → A(用户态)
```

只有当：

- 系统调用使 A 阻塞；
- 时间片到期；
- 出现更高优先级可运行任务；
- 调度器决定换人；

才可能进一步发生：

```text
A → B
```

> **严谨口径**
>
> 模式切换（mode switch）和进程上下文切换（process context switch）不是同一个概念。后者通常还要切换地址空间、调度实体及更多进程级状态，开销更大。

## 1.3.9 一张表完成高频辨析

| 问题 | 中断 | 异常 | 系统调用 |
| --- | --- | --- | --- |
| 来源 | 外部事件 | 当前指令/内部条件 | 当前程序主动请求 |
| 同步性 | 通常异步 | 同步 | 同步 |
| 是否主动 | 被动 | 被动或内部触发 | 主动 |
| 处理程序模式 | 内核态 | 内核态 | 内核态 |
| 典型例子 | 时钟、I/O 完成 | 缺页、除零 | 文件读写 |

> **做题技巧**
>
> 看到“发生”先判断事件到来时 CPU 可能在哪个模式；看到“处理程序执行”则判断处理代码必须具备的权限。二者不要混淆。
