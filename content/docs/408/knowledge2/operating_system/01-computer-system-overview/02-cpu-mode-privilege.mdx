现代操作系统必须同时满足两个目标：

- 让普通应用高效执行；
- 又不能允许应用任意修改全局系统状态或直接控制关键硬件。

解决办法不是靠“程序自觉”，而是利用处理器硬件提供的**特权级机制**建立保护边界。

> **真题标签｜CPU 运行模式**

> 参考真题索引：选择题 2011#24、2012#23、2013#28、2014#25、2015#24、2019#25、2021#23、2022#27、2023#26、2026#21、2026#23；解答题 2023#46。

## 1.2.1 用户态与内核态本质上是谁的状态

**用户态（User Mode）与内核态（Kernel Mode）首先是 CPU 提供的运行权限状态。**

操作系统利用这种硬件机制实现隔离和保护。

以 x86 的经典描述为例，处理器提供 Ring 0～Ring 3 等权限级，桌面操作系统通常主要使用：

- Ring 0：内核；
- Ring 3：普通用户程序。

ARM 等体系结构也有不同异常级/特权级设计，但考试核心不在具体编号，而在：

> **不同模式具有不同指令权限和资源访问权限。**

因此，下列说法不严谨：

> “用户态、内核态是操作系统纯软件虚构出来的两种状态。”

更准确的表述是：

> **CPU 提供硬件特权级，操作系统使用它们建立用户空间与内核空间的保护边界。**

## 1.2.2 用户态能做什么

普通应用程序通常运行在用户态，可以：

- 执行普通算术、逻辑、比较和转移指令；
- 访问其有权限访问的用户地址空间；
- 调用普通函数和多数纯计算库函数；
- 执行用于发起系统调用的受控陷入指令。

最后一点非常容易考错：

> **系统调用指令本身必须能从用户态发起，否则用户程序就无法请求内核服务。**
>
> 因此，`syscall`、特定陷入/访管指令不应简单归类为“用户态绝不能执行的特权指令”；真正的特权服务在陷入后由内核完成。

## 1.2.3 内核态为什么权限更高

内核态用于执行需要全局控制能力的操作，例如：

- 进程和线程管理；
- CPU 调度；
- 地址空间与页表管理；
- 中断、异常处理；
- 文件系统核心操作；
- 设备驱动和 I/O 控制；
- 时钟与系统级资源管理。

如果普通程序可直接执行这些操作，就可能：

- 关闭中断并长期霸占 CPU；
- 修改页表后读取其他进程数据；
- 绕过文件和设备权限；
- 覆盖内核数据结构；
- 破坏全系统稳定性。

## 1.2.4 特权指令与非特权指令

### 特权指令

**特权指令（Privileged Instruction）**&#x2060;只能在高特权模式正确执行，典型作用包括：

- 修改中断使能/屏蔽等关键状态；
- 修改控制寄存器和地址转换相关状态；
- 设置内存保护机制；
- 对某些体系结构的设备控制资源执行直接操作；
- 执行仅允许内核使用的系统管理操作。

若用户态非法执行真正的特权指令，CPU 通常会产生异常，而不是“悄悄帮它执行”。

### 非特权指令

普通数据运算、逻辑和一般控制转移通常属于非特权指令，例如加减、比较、普通加载/存储等。

但要注意：

> **“指令本身非特权”不等于“任何地址都能访问”。**

例如普通 load/store 指令本身可以在用户态执行，但若访问无权限页面，仍会触发保护异常或缺页异常。

## 1.2.5 判断某操作能否由用户态直接完成

可用“四问法”：

1. 是否直接控制关键硬件？
2. 是否修改全局系统状态？
3. 是否改变地址转换或保护机制？
4. 是否可能直接影响其他进程的安全与资源？

若其中任一项明显为“是”，通常需要内核执行。

### 通常可在用户态完成

- 纯算术/逻辑计算；
- 普通函数调用；
- 修改自己地址空间中的合法变量；
- 字符串处理等纯用户态库函数；
- 发起系统调用请求。

### 通常必须由内核态完成

- 真正执行进程切换；
- 修改页表或地址空间保护状态；
- 处理中断服务；
- 直接管理设备和 DMA 等系统资源；
- 核心内存资源分配和回收；
- 文件系统和网络协议栈中需要内核权限的部分。

## 1.2.6 “发生在用户态”与“在用户态执行”不是一回事

408 很喜欢利用措辞差异设题。

例如：

- 用户程序在用户态**发起**系统调用；
- 缺页可以在用户程序执行时**发生**；
- 外部中断也可能在 CPU 正执行用户程序时**到来**；
- 但对应的系统调用服务、缺页处理和中断处理程序要在内核态执行。

因此必须区分：

```text
事件发生前 CPU 处于什么模式
              ≠
事件处理程序在什么模式执行
```

> **典型辨析**
>
> “进程切换可能发生在用户态吗？”
>
> 进程切换需要保存/恢复受保护的进程执行状态并由调度机制决定下一运行实体，因此真正的切换动作必须在内核态完成。

## 1.2.7 状态切换不等于进程切换

CPU 从用户态进入内核态只是**特权级/运行模式切换**。

例如：

```text
进程 A：用户态
   ↓ 系统调用
进程 A：内核态
   ↓ 服务完成
进程 A：用户态
```

整个过程仍可能一直属于进程 A，并没有换到进程 B。

所以：

> **用户态 ↔ 内核态切换 ≠ 必然发生进程上下文切换。**

只有调度器真正把 CPU 从一个进程切换给另一个进程时，才发生进程级上下文切换。
