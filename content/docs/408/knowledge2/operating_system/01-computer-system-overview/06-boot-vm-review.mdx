## 1.6.1 为什么操作系统需要“引导”

操作系统内核长期存放在外存，而 CPU 复位后不能凭空知道“应该去磁盘哪里找内核”。因此开机必须经过一个**逐级建立运行环境、逐级加载更复杂软件**的过程。

抽象流程：

```text
上电 / 复位
   ↓
CPU 从规定复位入口开始执行固件
   ↓
BIOS / UEFI 初始化基本硬件
   ↓
选择启动设备、找到引导程序
   ↓
Bootloader 加载 OS 内核
   ↓
跳转到内核入口
   ↓
内核初始化内存、中断、调度、设备等
   ↓
启动系统服务 / 第一个用户空间进程
   ↓
进入正常运行
```

## 1.6.2 BIOS、UEFI 与 Bootloader

### BIOS

传统 BIOS 启动流程通常与 MBR 方式紧密相关：固件初始化硬件后，根据启动顺序读取启动介质上的启动代码，并把控制权交给后续引导程序。

### UEFI

现代 UEFI 能理解更丰富的启动环境，通常从 **EFI System Partition（ESP）** 中找到并加载 `.efi` 启动程序。

> **高频易错点**
>
> **GPT 是磁盘分区表格式，不是引导程序。**
>
> UEFI 常与 GPT/ESP 组合使用，但不能把“GPT 首扇区”说成 UEFI 直接执行的操作系统启动程序。

### Bootloader

Bootloader 的主要任务是：

- 定位操作系统内核；
- 把内核及必要附加数据装入主存；
- 准备启动参数；
- 把处理器控制权交给内核入口。

典型引导器包括 GRUB、Windows Boot Manager 等。

## 1.6.3 内核初始化做什么

内核得到控制权后，通常需要逐步建立完整系统环境：

- 初始化物理内存与虚拟内存管理；
- 建立中断/异常处理机制；
- 初始化调度器；
- 初始化内核数据结构；
- 发现并初始化设备/驱动；
- 挂载必要文件系统；
- 启动系统级进程和服务。

不同操作系统细节不同，408 主要掌握“固件 → 引导器 → 内核 → 初始化”的层次，不要求记某个具体发行版的每一步命令。

## 1.6.4 虚拟机是什么

**虚拟机（Virtual Machine，VM）**&#x2060;是在物理计算机之上构造出的逻辑计算机环境。

每台虚拟机可拥有自己的：

- 虚拟 CPU（vCPU）；
- 虚拟内存；
- 虚拟磁盘；
- 虚拟网络/设备；
- Guest OS；
- 应用程序。

从 Guest OS 视角看，它好像拥有一套独立硬件。

## 1.6.5 Hypervisor/VMM 的职责

负责创建和管理虚拟机的软件层称为：

- **Hypervisor**；
- 或 **Virtual Machine Monitor（VMM）**。

它负责：

1. **资源复用**：把物理 CPU、内存和设备分给多个 VM；
2. **虚拟硬件抽象**：给 Guest 呈现 vCPU、虚拟设备等接口；
3. **隔离与保护**：阻止一个 VM 任意访问另一个 VM 的内存与状态；
4. **截获敏感操作**：Guest OS 认为自己在管理“机器”，但关键硬件控制仍必须受 Hypervisor 管理。

## 1.6.6 两类常见 Hypervisor

### Type 1：裸机型

Hypervisor 直接运行在硬件之上，再承载多个 Guest OS。

```text
应用    应用
Guest   Guest
   \    /
 Hypervisor
     ↓
   Hardware
```

特点：隔离和控制路径直接，常见于服务器虚拟化。

### Type 2：宿主型

Hypervisor 作为宿主操作系统上的应用/服务运行：

```text
Guest OS
   ↓
VMM/虚拟化软件
   ↓
Host OS
   ↓
Hardware
```

两者都是虚拟化方案，只是 Hypervisor 与物理硬件之间是否还有一个完整 Host OS 的位置关系不同。

## 1.6.7 “Ring -1”怎么理解

硬件虚拟化引入了比 Guest OS 更高控制权的执行环境，例如：

- x86 的 VMX root/non-root 模式；
- ARM 的 EL2 等虚拟化支持。

人们有时把 Hypervisor 所处位置非正式称为 **Ring -1**。

但要明确：

> **“Ring -1”不是传统 x86 Ring 0～Ring 3 体系真的多出一个编号为 -1 的普通 Ring。**

它只是强调 Hypervisor 对 Guest OS 具有更高控制层级的一种通俗说法。

## 1.6.8 本章最重要的十组判断

> **判断 1｜并发 = 并行？**
>
> 错。并发是同一时间段内交替推进，并行才是同一时刻真正同时执行。

> **判断 2｜多道程序提高效率，是因为单核同时执行多条程序？**
>
> 错。关键是某程序等待 I/O 时，CPU 转去运行其他程序。

> **判断 3｜用户态/内核态只是 OS 自己定义的软件变量？**
>
> 错。它们依赖 CPU 的硬件特权级支持。

> **判断 4｜系统调用指令本身一定是只能在内核态执行的特权指令？**
>
> 错。用户程序必须能执行受控陷入/系统调用指令来请求内核服务；真正的服务例程在内核态运行。

> **判断 5｜用户程序执行系统调用后一定切换到另一个进程？**
>
> 错。一定发生受控模式切换，但不一定发生进程切换。

> **判断 6｜外部中断一定由当前指令引起？**
>
> 错。外部中断通常来自设备、时钟等外部事件。

> **判断 7｜异常一般与当前指令执行有关？**
>
> 对。除零、缺页、保护错误等属于典型同步异常。

> **判断 8｜所有库函数都会产生系统调用？**
>
> 错。许多纯计算库函数完全在用户态执行。

> **判断 9｜静态重定位是在运行过程中逐次转换地址？**
>
> 错。静态重定位在装入时完成；运行时转换属于动态重定位范畴。

> **判断 10｜微内核隔离性较强，但可能增加 IPC 和状态切换开销？**
>
> 对。

## 1.6.9 一页速记

```text
OS 三种角色
资源管理者 / 程序与硬件接口 / 硬件抽象层

四特征
并发 + 共享 + 虚拟 + 异步

发展主线
手工 → 单道批处理 → 多道批处理 → 分时 / 实时

用户态进入内核的典型原因
系统调用 / 异常 / 中断

系统调用
必然：发生受控特权级切换
不必然：发生进程切换

链接
静态：库代码更多进入可执行文件
动态：运行/装入时依赖共享库

装入与重定位
编译时确定 → 绝对装入
装入时修改 → 静态重定位
运行时转换 → 动态重定位

地址空间
Text / Data / BSS / Heap / Stack
虚拟地址空间 ≠ 物理内存

OS 结构
分层 / 模块化 / 宏内核 / 微内核 / 外核

启动
固件 → Bootloader → 内核 → 内核初始化 → 系统服务

虚拟机
Hypervisor 复用硬件 + 提供虚拟硬件 + 隔离 Guest
```
