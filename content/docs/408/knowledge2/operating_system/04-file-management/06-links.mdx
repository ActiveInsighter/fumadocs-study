文件名本质上是目录项中的名字，而目录项再关联 inode。因此同一个 inode 可以拥有多个名字。

> **真题标签**
>
> 文件链接：2009 年第 31 题、2017 年第 31 题、2021 年第 30 题。

## 4.6.1 硬链接：再增加一个目录项

执行类似：

```bash
ln A D
```

逻辑结构：

```text
A ─┐
   ├→ inode 123 → 同一份文件数据
D ─┘
```

其本质是：**新增一个目录项，让它指向同一个 inode。**

因此：

- inode 号相同；
- 共享同一份数据；
- inode 硬链接计数增加；
- 删除某一个名字只删除一个目录项；
- 仍有其他硬链接时，文件仍可正常访问。

## 4.6.2 为什么硬链接通常不能跨文件系统

inode 号只在所属文件系统内部解释。另一个文件系统拥有自己的 inode 命名空间，因此普通硬链接无法跨文件系统直接引用对方 inode。

## 4.6.3 为什么普通用户通常不能给目录建硬链接

若目录可任意建立硬链接，目录图可能出现环：

```text
A → B → C
↑       ↓
└───────┘
```

这样会破坏简单树形结构，导致遍历、回收和一致性维护复杂化。

## 4.6.4 软链接：新建一个保存路径的特殊文件

执行：

```bash
ln -s A L
```

结构：

```text
L 的目录项
   ↓
L 自己的 inode
   ↓
内容："A"（路径字符串）
   ↓ 再次路径解析
A 的 inode
   ↓
A 的数据
```

因此软链接：

- 自己有独立 inode；
- 内容主要是目标路径字符串；
- 可以跨文件系统；
- 可以指向目录；
- 访问时需要额外路径解析。

## 4.6.5 删除目标后的差异

### 删除一个硬链接名

如果还有其他目录项指向该 inode：

- inode 仍存在；
- 数据块仍存在；
- 其他硬链接继续工作。

### 删除软链接的目标

软链接文件本身还在，但其中保存的路径可能找不到目标，成为**悬挂链接（dangling link）**。

## 4.6.6 链接计数如何理解

inode 中的硬链接计数表示有多少目录项直接指向该 inode。

建立软链接时：

- 不会给目标 inode 新增硬链接目录项；
- 软链接自己作为一个独立文件有自己的 inode 和链接计数。

> **高频陷阱**
>
> “创建符号链接会使目标文件硬链接计数 +1”——错误。

## 4.6.7 硬链接与已打开文件

即使最后一个硬链接目录项被删除，如果某进程仍持有该文件的打开引用，内核仍可能保留 inode 和数据块，直到相关打开引用释放。

因此回收条件不能简单写成“链接计数变 0 就立即物理删除”，应结合题目是否存在打开引用。

## 4.6.8 对比表

| 特征 | 硬链接 | 软链接 |
| --- | --- | --- |
| 本质 | 新目录项指向同一 inode | 新建一个保存路径的特殊文件 |
| inode | 与目标相同 | 自己有独立 inode |
| 数据 | 直接共享目标数据 | 先解析路径再访问目标 |
| 删除原名字后 | 其他硬链接仍可用 | 可能悬挂 |
| 跨文件系统 | 一般不能 | 可以 |
| 链接目录 | 通常受严格限制 | 可以 |
| 是否增加目标硬链接计数 | 是 | 否 |

## 4.6.9 一眼判断法

> **硬链接看 inode；软链接看路径。**

> **硬链接是“同一个文件多个名字”；软链接是“一个独立文件保存另一个路径”。**
