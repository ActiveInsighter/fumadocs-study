文件管理解决的核心问题是：**如何把外存上的盘块组织成用户可理解的文件与目录，并完成文件的命名、访问、共享、保护、分配与回收。**

从 408 的角度，本章可以始终沿着一条主线理解：

```text
文件名 / 路径
    ↓
目录项
    ↓
inode / FCB
    ↓
文件逻辑块
    ↓
文件物理块
    ↓
磁盘 / SSD
```

文件被打开之后，还会多出一条运行时链路：

```text
fd → 进程文件描述符表 → 系统打开文件表 → inode → 文件数据
```

<Callout type="info" title="复习重点">
本章综合题最常考：**多级索引容量与访盘次数、目录与 inode、打开文件表、硬链接与软链接、位图、文件系统整体结构**。做题时要先判断题目问的是“名字”“打开实例”“文件元数据”还是“数据块”。
</Callout>

## 1. 文件的基本概念

文件是操作系统提供的**持久化数据抽象**。用户看到的是文件名、路径和文件内容；操作系统还必须管理文件的属性和其在外存上的位置。

一个文件通常涉及以下信息：

- 文件名与类型；
- 所有者、权限；
- 文件大小；
- 创建、修改、访问时间；
- 文件数据所在的盘块；
- 文件与目录的组织关系；
- 文件被打开后的运行时状态。

理解文件管理时，应严格区分三个层次：

| 层次 | 研究对象 | 典型问题 |
| --- | --- | --- |
| 逻辑结构 | 用户如何理解文件内容 | 字节流还是记录？如何按记录访问？ |
| 物理结构 | 文件块如何放到外存 | 连续、链式、索引还是混合索引？ |
| 文件系统结构 | 文件、目录、元数据与空闲空间如何统一管理 | 超级块、inode、位图、VFS、挂载如何配合？ |

<Callout type="warning" title="不要混淆">
**逻辑结构与物理结构是两个维度。**“顺序文件”并不等价于“连续分配”；一个逻辑上顺序访问的文件完全可以采用索引分配。
</Callout>

## 2. 文件元数据、FCB 与 inode

文件内容之外，操作系统还要保存描述文件的信息，这些信息统称为**元数据（metadata）**。

在一般操作系统教材中，保存文件管理信息的数据结构称为 **FCB（File Control Block，文件控制块）**。在 UNIX / 类 UNIX 文件系统中，其核心角色通常由 **inode（索引节点）**承担。

### 2.1 inode 保存什么

典型 inode 中包含：

- 文件类型；
- 访问权限；
- 用户 ID、组 ID；
- 文件大小；
- 时间信息；
- 硬链接计数；
- 定位文件数据块所需的直接地址、间接地址等信息。

但必须牢记：

> **inode 通常不保存文件名。文件名保存在目录项中。**

因此，在 UNIX 类文件系统中可以把一次名字解析理解为：

```text
文件名 → 目录项 → inode 号 → inode → 数据块
```

> 综合题：2026 年第 46 题。

### 2.2 inode 表

<InlineSvg src="/images/operating-system/operating-system-files-file-001.svg" alt={"inode 结构及其中保存的主要文件元数据"} />
<InlineSvg src="/images/operating-system/operating-system-files-file-002.svg" alt={"inode 表结构示意图"} />

一个文件系统中有大量 inode，因此需要专门区域统一保存。每个 inode 有自己的编号，目录项通常记录“文件名 + inode 号”。

例如：

| inode 号 | 类型 | 大小 | 链接计数 | 数据块定位信息 |
| ---: | --- | ---: | ---: | --- |
| 12 | 目录 | 4096 B | 2 | 100、101 |
| 35 | 普通文件 | 1024 B | 1 | 200 |
| 46 | 符号链接 | 14 B | 1 | 保存目标路径的数据 |

还要区分：

- **磁盘 inode**：持久保存文件元数据；
- **内存 inode / vnode 等对象**：文件被访问时，内核把相关信息装入内存，避免每次操作都重新访问外存。

<Callout type="warning" title="高频判断">
如果两个不同文件名最终对应**同一个 inode**，它们是同一文件的两个硬链接，而不是两份文件数据。
</Callout>

## 3. 打开文件的三层结构

<InlineSvg src="/images/operating-system/operating-system-files-file-003.svg" alt={"系统打开文件表及其与文件描述符和 inode 的关系"} />

文件一旦打开，内核不能在每次 `read()`、`write()` 时都重新从文件名开始查找。它需要建立运行时数据结构，保存**当前偏移量、打开方式、状态标志和对底层文件对象的引用**。

最重要的关系是：

```text
进程文件描述符表
        ↓
系统打开文件表（打开文件实例）
        ↓
inode / vnode（底层文件对象）
```

> **真题标记**
>
> 选择题：2020 年第 23 题、2024 年第 29 题、2025 年第 29 题。

### 3.1 文件描述符表

<InlineSvg src="/images/operating-system/operating-system-files-file-004.svg" alt={"进程文件描述符表与系统打开文件表的映射关系"} />
<InlineSvg src="/images/operating-system/operating-system-files-file-005.svg" alt={"进程文件描述符表、系统打开文件表和 inode 表的总体关系"} />

每个进程都有自己的**文件描述符表**。文件描述符 `fd` 是一个小的非负整数，本质上只是该表的索引。

UNIX 类系统中通常约定：

- `0`：标准输入；
- `1`：标准输出；
- `2`：标准错误。

例如：

| fd | 指向的打开文件表项 |
| ---: | ---: |
| 0 | 5 |
| 1 | 6 |
| 2 | 7 |
| 3 | 9 |

因此，**fd 不是 inode 号，也不是磁盘块号**。

### 3.2 系统打开文件表

系统打开文件表中的一个表项表示一次**打开文件实例**，典型包含：

- 当前文件偏移量；
- 打开模式与状态标志；
- 引用计数；
- 指向 inode / vnode 的指针。

```c
int fd = open("file.txt", O_RDWR);
write(fd, "Hello", 5);
```

若从文件开头写入 5 B，完成后该打开实例的当前偏移量通常移动 5 B。

### 3.3 两次 `open()` 与 `dup()`

这是 408 的高频辨析。

**两次独立 `open()` 同一个文件：**

```text
fdA → 打开文件表项 1 ─┐
                       ├→ 同一 inode
fdB → 打开文件表项 2 ─┘
```

通常意味着：

- 最终访问同一文件；
- 文件元数据和内容相同；
- 但两个打开实例可拥有**相互独立的文件偏移量**。

**`dup()` 复制文件描述符：**

```text
fdA ─┐
     ├→ 同一打开文件表项 → inode
fdB ─┘
```

此时两个 fd 通常：

- 共享当前文件偏移量；
- 共享该打开实例的状态；
- 使打开文件表项的引用计数增加。

`fork()` 后父子进程继承的相关文件描述符也可能引用同一打开文件实例，因此常见情形下同样共享偏移量。

<Callout type="info" title="一句话记忆">
**fd 属于进程；打开文件表项描述一次打开；inode 描述底层文件。**
</Callout>

## 4. 文件系统调用：`open`、`close`、`read`、`write`、`lseek`

<InlineSvg src="/images/operating-system/operating-system-files-file-006.svg" alt={"open、read、write、lseek、close 的文件操作流程"} />

### 4.1 `open`

`open()` 的本质不是“把整个文件读进内存”，而是建立后续访问文件所需的内核状态。

典型过程：

1. 逐级解析路径；
2. 检查文件是否存在及访问权限；
3. 找到对应 inode / vnode；
4. 建立或取得打开文件表项；
5. 在进程文件描述符表中建立引用；
6. 返回 fd。

### 4.2 `close`

`close(fd)` 表示**当前进程释放这个 fd 引用**。典型动作包括：

- 清除对应文件描述符表项；
- 减少打开文件表项的引用计数；
- 当引用计数归零时释放相应的打开实例结构。

它不等价于删除磁盘文件。

更进一步，UNIX 中即使一个文件名已经被 `unlink()` 删除，只要文件仍被某进程打开，其数据也可能继续存在；通常要等**硬链接计数为 0 且不再有打开引用**后，相关 inode 和数据块才真正具备回收条件。

### 4.3 `read`

```c
read(fd, buf, count);
```

表示从当前偏移量开始，最多读取 `count` 字节到用户缓冲区 `buf`。读取完成后，偏移量通常相应向后移动。

若数据已在页缓存中，可直接从内存获取；否则需要先把数据从外存读入。操作系统还可能对顺序访问执行**预读（read-ahead）**，提前加载后续块。

### 4.4 `write`

```c
write(fd, buf, count);
```

写操作常先修改内核缓存中的页面，再由系统择机回写外存，这称为**延迟写**。它可合并多次写入并减少实际 I/O，但意味着：

> `write()` 返回成功，不必然等价于数据已经持久落盘。

需要更强持久性保证时，可使用类似 `fsync()` 的机制请求同步相关脏数据。

### 4.5 `lseek`

`lseek()` 主要修改当前打开实例的文件偏移量，本身不负责读取或写入数据。

典型用途：

- 跳转到文件指定位置；
- 回到文件开头；
- 随机访问固定位置记录；
- 通过移动偏移量形成稀疏文件等操作模式。

<Callout type="warning" title="易错点">
文件偏移量属于**打开文件实例**，不是 inode 的固有属性。因此两次独立 `open()` 可以有两个不同偏移量，而 `dup()` 出来的 fd 通常共享同一个偏移量。
</Callout>

## 5. 文件逻辑结构

文件的逻辑结构回答：

> **用户眼中的文件内容怎样组织？**

它不回答数据具体落在哪些物理盘块上。

### 5.1 无结构文件（流式文件）

操作系统把文件视为字节序列：

```text
byte0 byte1 byte2 ... byteN
```

至于字节如何解释，由应用程序决定。现代 UNIX 类系统的普通文件通常采用这种抽象。

### 5.2 有结构文件（记录式文件）

文件由若干逻辑记录构成。记录可按不同方式组织和访问，例如：

- **顺序访问**：从前到后依次处理记录；
- **直接 / 随机访问**：根据记录号、键值或偏移量直接定位；
- 某些教材还会讨论索引顺序文件等组织方式。

<Callout type="warning" title="顺序 ≠ 连续">
“顺序访问”描述的是**访问方式**；“连续分配”描述的是**物理盘块布局**。两者不能直接画等号。
</Callout>

## 6. 文件访问的完整抽象链

把本节内容合起来，一次典型访问可表示为：

```text
用户路径
  ↓
逐级查目录项
  ↓
inode / vnode
  ↓
open() 建立打开文件实例
  ↓
返回 fd
  ↓
read / write / lseek
  ↓
文件逻辑块
  ↓
文件物理结构完成地址映射
  ↓
盘块 / 页缓存 / 设备
```

做综合题时，先问自己：题目现在处在哪一层？

- 问“文件名在哪里” → 目录项；
- 问“权限、大小、数据块指针” → inode / FCB；
- 问“当前偏移量” → 打开文件表项；
- 问“fd” → 进程文件描述符表；
- 问“逻辑块到物理块” → 文件物理结构。

## 7. 高频易错点

| 说法 | 判断 | 原因 |
| --- | :---: | --- |
| inode 中通常保存文件名 | ❌ | 文件名通常在目录项中 |
| fd 就是 inode 号 | ❌ | fd 是进程文件描述符表索引 |
| 两次独立 `open()` 同一文件一定共享偏移量 | ❌ | 通常得到不同打开文件表项 |
| `dup()` 得到的两个 fd 通常共享偏移量 | ✅ | 二者指向同一打开文件表项 |
| `close()` 会删除磁盘文件 | ❌ | 它只是释放一个打开引用 |
| `write()` 成功即表示数据已经持久化 | ❌ | 可能仍在缓存中等待回写 |
| `lseek()` 本身会读取目标位置的数据 | ❌ | 它主要修改文件偏移量 |
| 顺序访问文件必须采用连续分配 | ❌ | 逻辑访问方式与物理分配方式是两个维度 |
