文件管理解决的核心问题是：**如何把外存上的数据块组织成用户可理解的文件和目录，并完成命名、访问、共享、保护、分配与回收。**

从 408 的角度，可以始终抓住两条主线。

第一条是**按名访问链**：

```text
文件名 / 路径
    ↓
目录项
    ↓
inode / FCB
    ↓
文件逻辑块
    ↓
文件物理块
    ↓
磁盘 / SSD
```

第二条是**文件打开后的运行时访问链**：

```text
fd
 ↓
进程级打开文件信息
 ↓
系统级打开文件信息 / 打开实例
 ↓
inode / vnode
 ↓
文件数据
```

<Callout type="info" title="复习重点">
本章综合题最常围绕 6 类对象出题：**目录项、inode / FCB、文件描述符、打开文件表、文件数据块、空闲空间管理信息**。做题前先判断题目问的是“名字”“文件本身”“一次打开”“逻辑块”还是“物理块”。
</Callout>

## 1. 文件的基本概念

文件是操作系统提供的**持久化数据抽象**。用户看到的是文件名、路径和内容；操作系统还必须维护文件属性以及文件数据在外存上的位置。

一个文件通常涉及：

- 文件名与类型；
- 所有者、所属组与访问权限；
- 文件大小；
- 创建、修改、访问时间；
- 文件数据所在盘块；
- 文件与目录的组织关系；
- 文件被打开后的运行时状态。

理解文件管理时，应严格区分三个层次：

| 层次 | 研究对象 | 典型问题 |
| --- | --- | --- |
| 逻辑结构 | 用户如何理解文件内容 | 字节流还是记录？按什么方式访问？ |
| 物理结构 | 文件数据块如何放到外存 | 连续、链式、索引还是混合索引？ |
| 文件系统结构 | 文件、目录、元数据与空闲空间如何统一管理 | 超级块、inode、位图、VFS、挂载如何配合？ |

<Callout type="warning" title="不要混淆">
**逻辑结构、访问方式、物理结构是三个不同维度。**“顺序访问”不等于“连续分配”；一个按顺序读取的文件完全可以采用索引分配。
</Callout>

## 2. 文件元数据、FCB 与 inode

文件内容之外，操作系统还要保存描述文件的信息，这些信息统称为**元数据（metadata）**。

在一般教材中，用来描述和控制文件的数据结构称为 **FCB（File Control Block，文件控制块）**。在 UNIX / 类 UNIX 文件系统中，其核心角色通常由 **inode（索引节点）**&#x2060;承担。

### 2.1 inode 保存什么

典型 inode 中包含：

- 文件类型；
- 访问权限；
- 用户 ID、组 ID；
- 文件大小；
- 时间信息；
- 硬链接计数；
- 定位文件数据块所需的直接地址、间接地址等信息。

必须牢记：

> **inode 通常不保存文件名。文件名保存在目录项中。**

因此，在 UNIX 类文件系统中可以把一次名字解析理解为：

```text
文件名 → 目录项 → inode 号 → inode → 数据块
```

> **真题标记**
>
> 选择题：2009 年第 30 题、2013 年第 23/26 题、2014 年第 29 题、2017 年第 30/31 题、2020 年第 31 题、2025 年第 29 题。  
> 综合题：2026 年第 46 题。

### 2.2 inode 表

<InlineSvg src="/images/operating-system/operating-system-files-file-001.svg" alt={"inode 结构及其中保存的主要文件元数据"} />
<InlineSvg src="/images/operating-system/operating-system-files-file-002.svg" alt={"inode 表结构示意图"} />

一个文件系统中有大量 inode，因此通常设置专门的 inode 区统一保存。每个 inode 有自己的编号，目录项记录“文件名 + inode 号”。

| inode 号 | 类型 | 大小 | 链接计数 | 数据块定位信息 |
| ---: | --- | ---: | ---: | --- |
| 12 | 目录 | 4096 B | 2 | 100、101 |
| 35 | 普通文件 | 1024 B | 1 | 200 |
| 46 | 符号链接 | 14 B | 1 | 保存目标路径的数据 |

还要区分：

- **磁盘 inode**：持久保存文件元数据；
- **内存 inode / vnode 等对象**：文件被访问时，内核把相关信息装入内存，避免每次操作都重新访问外存。

<Callout type="warning" title="高频判断">
如果两个不同文件名最终对应**同一个 inode**，它们是同一文件的两个硬链接，而不是两份独立文件数据。
</Callout>

### 2.3 inode 定位公式

综合题常给出：

- inode 区起始盘块号；
- inode 从 0 开始编号；
- 每个 inode 的字节数；
- 盘块大小。

若盘块大小为 $B$，每个 inode 大小为 $I$，则每块可容纳：

$$
N_i=\left\lfloor\frac{B}{I}\right\rfloor
$$

个 inode。

编号为 $k$ 的 inode 所在盘块号为：

$$
\text{block}=\text{inodeStart}+\left\lfloor\frac{k}{N_i}\right\rfloor
$$

块内第几个 inode 为：

$$
k\bmod N_i
$$

> **真题标记**
>
> 2026 年第 46 题直接考查“inode 号 → inode 表所在盘块”的计算。

## 3. 文件保护与访问控制

文件保护解决的是：

> **谁能对哪个文件执行哪些操作？**

常见操作包括：读、写、执行、追加、删除、列目录等。

典型实现方式包括：

1. **访问控制矩阵**：行表示用户 / 主体，列表示文件 / 客体，表项表示权限；
2. **访问控制表（ACL）**：以文件为中心，记录哪些用户拥有哪些权限；
3. **能力表（Capability List）**：以用户 / 进程为中心，记录其可访问哪些对象以及权限；
4. UNIX 类系统常见的**所有者 / 同组用户 / 其他用户**权限位。

例如传统 UNIX 权限：

```text
rwx rw- r--
│   │   └─ other
│   └───── group
└───────── owner
```

其中每一类常用 3 bit 表示：

- `r`：读；
- `w`：写；
- `x`：执行。

<Callout type="warning" title="权限信息放在哪里">
访问权限属于**文件元数据**，因此通常保存在 FCB / inode 一类结构中，而不是作为普通字段直接放在目录项中。目录项主要负责“名字 → 文件控制信息”的映射。
</Callout>

> **真题标记**
>
> 2009 年第 30 题考查访问控制信息应存放在 FCB；2017 年第 30 题考查访问权限位；2025 年第 29 题再次强调访问权限通常在 inode 中，而不是目录项中。

## 4. 打开文件的运行时结构

<InlineSvg src="/images/operating-system/operating-system-files-file-003.svg" alt={"系统打开文件表及其与文件描述符和 inode 的关系"} />

文件一旦打开，内核不能在每次 `read()`、`write()` 时都重新从路径开始查找，因此需要建立运行时数据结构保存：

- 当前文件偏移量；
- 打开方式和状态标志；
- 引用关系；
- 指向底层文件对象的引用。

教材和具体 UNIX 实现对“用户打开文件表”“系统打开文件表”“打开文件描述”等名称和字段归属可能略有不同，但做 408 时应抓住下面三层语义：

```text
进程文件描述符 fd
        ↓
进程级表项 / 句柄
        ↓
一次打开所需的运行时状态
        ↓
inode / vnode 等底层文件对象
```

> **真题标记**
>
> 选择题：2017 年第 31 题、2020 年第 23 题、2024 年第 28/29 题。

### 4.1 文件描述符表

<InlineSvg src="/images/operating-system/operating-system-files-file-004.svg" alt={"进程文件描述符表与系统打开文件表的映射关系"} />
<InlineSvg src="/images/operating-system/operating-system-files-file-005.svg" alt={"进程文件描述符表、系统打开文件表和 inode 表的总体关系"} />

每个进程维护自己的**文件描述符表**。文件描述符 `fd` 是一个小的非负整数，本质上是该表的索引或句柄。

UNIX 类系统中通常约定：

- `0`：标准输入；
- `1`：标准输出；
- `2`：标准错误。

例如：

| fd | 指向的内核打开文件信息 |
| ---: | ---: |
| 0 | 5 |
| 1 | 6 |
| 2 | 7 |
| 3 | 9 |

因此：

- **fd 不是 inode 号**；
- **fd 不是磁盘块号**；
- 同一进程内的多个线程通常共享该进程的文件描述符集合。

> **真题标记**
>
> 2024 年第 28 题考查同一进程的线程共享文件描述符。

### 4.2 当前偏移量属于“打开状态”，不是 inode 固有属性

一次打开文件后，系统通常要记录当前读写位置。例如：

```c
int fd = open("file.txt", O_RDWR);
write(fd, "Hello", 5);
```

若从偏移 0 开始写入 5 B，完成后当前偏移通常变为 5。

关键结论：

> **文件当前读写位置不是 inode 的永久属性，而是运行时打开状态的一部分。**

至于具体教材把这个位置放在“用户打开文件表”还是“系统打开文件表 / open file description”，要按题目给出的结构作答。

### 4.3 两次独立 `open()`、`dup()` 与 `fork()`

这是高频辨析。

<Tabs items={["两次独立 open", "dup / 继承共享"]}>
<Tab value="两次独立 open">

```text
fdA → 打开状态 1 ─┐
                   ├→ 同一 inode
fdB → 打开状态 2 ─┘
```

通常可以理解为：

- 最终访问同一底层文件；
- inode 与文件数据相同；
- 两个独立打开的句柄可拥有**彼此独立的当前偏移量**。

这也是“两个进程分别打开同一硬链接文件名时，读写指针不必相同”的根本原因。

</Tab>
<Tab value="dup / 继承共享">

```text
fdA ─┐
     ├→ 同一打开状态 → inode
fdB ─┘
```

`dup()` 复制文件描述符后，两个 fd 通常引用同一打开状态，因此：

- 通常共享当前文件偏移量；
- 共享相应状态标志；
- 引用计数增加。

`fork()` 后父子进程继承的描述符也常引用同一打开状态，因此同样可能共享偏移量。

</Tab>
</Tabs>

<Callout type="info" title="一句话记忆">
**fd 属于进程；偏移量属于打开状态；inode 描述底层文件。**
</Callout>

## 5. 文件系统调用：`open`、`close`、`read`、`write`、`lseek`

<InlineSvg src="/images/operating-system/operating-system-files-file-006.svg" alt={"open、read、write、lseek、close 的文件操作流程"} />

### 5.1 `open`

`open()` 的本质不是“把整个文件读进内存”，而是完成**按名查找并建立后续访问所需的内核状态**。

典型过程：

1. 逐级解析路径；
2. 查找目录项；
3. 检查文件是否存在以及访问权限；
4. 找到并装入对应 FCB / inode；
5. 建立打开文件所需的运行时表项；
6. 在进程文件描述符表中建立引用；
7. 返回 fd。

<Callout type="warning" title="open 的考试口径">
首次打开文件时，通常需要把**文件控制信息**调入内存，而不是把整个文件内容读入内存。`open()` 也是 `open/read/write/close` 中唯一显式接收路径名、包含按名查找过程的典型调用。
</Callout>

> **真题标记**
>
> 2014 年第 29 题：首次打开文件需要把 FCB 调入内存；2024 年第 29 题：`open()` 包含文件按名查找功能。

### 5.2 `close`

`close(fd)` 表示当前进程释放这个 fd 对打开文件的引用。典型动作包括：

- 清除对应文件描述符表项；
- 减少相关打开状态的引用计数；
- 当引用计数满足释放条件时回收相应运行时结构。

它**不等价于删除磁盘文件**。

### 5.3 `read`

```c
read(fd, buf, count);
```

表示从当前偏移量开始，最多读取 `count` 字节到用户缓冲区 `buf`。成功读取后，偏移量通常向后移动。

若数据已在页缓存中，可直接从内存获取；否则需要触发外存 I/O。系统还可能对顺序访问进行预读。

### 5.4 `write`

```c
write(fd, buf, count);
```

写操作常先修改内核缓存中的页面，再由系统择机回写外存，即**延迟写**。

因此：

> `write()` 返回成功，不必然表示数据已经物理持久化到存储介质。

需要更强持久性保证时，可使用类似 `fsync()` 的同步机制。

### 5.5 `lseek`

`lseek()` 主要修改当前打开状态中的文件偏移量，本身不负责读取或写入数据。

典型用途：

- 跳转到指定偏移；
- 回到文件开头；
- 随机访问记录；
- 配合写入形成稀疏文件。

<Callout type="warning" title="易错点">
`read` / `write` 依赖 fd，不再需要从文件名重新查找；`lseek` 主要改偏移；`close` 只释放打开引用，不等于删除文件。
</Callout>

## 6. 删除文件：目录项、链接计数与打开引用

删除文件名时，不应简单理解为“立即擦除文件数据”。在 UNIX 类语义下，`unlink()` 更接近：

1. 从目录中删除对应目录项；
2. 使 inode 的硬链接计数减 1；
3. 若链接计数变为 0，还要继续判断是否仍存在打开引用；
4. 当文件不再有名字引用且也不再被打开时，inode 和数据块才具备最终回收条件。

这解释了为什么：

- 删除一个硬链接后，其他硬链接仍可访问文件；
- 文件即使路径名已被删除，已打开该文件的进程仍可能继续读写。

## 7. 文件逻辑结构与访问方式

文件的逻辑结构回答：

> **用户眼中的文件内容怎样组织？**

它不回答数据具体放在哪些物理盘块上。

### 7.1 无结构文件（流式文件）

操作系统把文件视为字节序列：

```text
byte0 byte1 byte2 ... byteN
```

字节的具体解释由应用程序决定。现代 UNIX 类系统普通文件通常采用这种抽象。

### 7.2 有结构文件（记录式文件）

文件由若干逻辑记录构成。常见记录可为固定长度或可变长度。

文件常见访问方式包括：

- **顺序访问**：从前到后依次访问；
- **直接 / 随机访问**：按记录号或字节偏移直接定位；
- **索引访问**：通过索引先找到目标记录或记录块。

<Callout type="warning" title="顺序访问 ≠ 连续分配">
“顺序访问”描述的是**访问方式**；“连续分配”描述的是**物理块布局**。这两个概念不能画等号。
</Callout>

## 8. 文件访问的完整抽象链

把本节内容合起来，一次典型文件访问可以表示为：

```text
用户路径
  ↓
逐级查目录项
  ↓
inode / vnode
  ↓
open() 建立运行时打开状态
  ↓
返回 fd
  ↓
read / write / lseek
  ↓
文件逻辑块
  ↓
文件物理结构完成地址映射
  ↓
盘块 / 页缓存 / 设备
```

做综合题时，先问自己题目现在处在哪一层：

| 题目问法 | 对应对象 |
| --- | --- |
| 文件名在哪里 | 目录项 |
| 权限、大小、数据块指针 | inode / FCB |
| 当前读写位置 | 打开状态 / 相应打开文件表项 |
| fd 是什么 | 进程文件描述符表中的索引 / 句柄 |
| 逻辑块怎样变成物理块 | 文件物理结构 |
| 哪些块尚未被占用 | 空闲空间管理结构 |

## 9. 高频易错点

| 说法 | 判断 | 原因 |
| --- | :---: | --- |
| inode 中通常保存文件名 | ❌ | 文件名通常在目录项中 |
| 文件权限通常保存在目录项中 | ❌ | 通常属于 FCB / inode 元数据 |
| fd 就是 inode 号 | ❌ | fd 是进程级句柄 / 表索引 |
| 同一进程多个线程可以共享 fd | ✅ | 文件描述符属于进程级资源 |
| 两次独立 `open()` 同一文件一定共享偏移量 | ❌ | 独立打开状态可有独立偏移量 |
| `dup()` 得到的两个 fd 通常共享偏移量 | ✅ | 通常指向同一打开状态 |
| `open()` 会把整个文件内容读入内存 | ❌ | 主要装入控制信息并建立打开关系 |
| `close()` 会删除磁盘文件 | ❌ | 它主要释放打开引用 |
| `write()` 成功即表示已经持久落盘 | ❌ | 可能仍在缓存中等待回写 |
| `lseek()` 本身会读取目标位置的数据 | ❌ | 它主要修改当前偏移量 |
| 顺序访问文件必须采用连续分配 | ❌ | 访问方式与物理分配方式是不同维度 |

<Callout type="info" title="本节速记">
**目录项管名字，inode 管文件；fd 管入口，打开状态管偏移；open 按名找，read/write 按 fd 走。**
</Callout>
