文件管理把底层外存块抽象成用户可理解的“文件”。408 中最重要的主线不是记命令，而是始终追踪：**文件名在哪里、元数据在哪里、数据块在哪里、访问权限由谁检查**。

> **真题标签**
>
> inode / FCB：2009 年第 30 题、2013 年第 23/26 题、2014 年第 29 题、2017 年第 30/31 题、2020 年第 31 题、2023 年第 31 题；综合题：2026 年第 46 题。

## 4.1.1 文件的三个观察层次

理解文件时要把三层问题分开：

| 层次 | 核心问题 | 典型考点 |
| --- | --- | --- |
| 逻辑结构 | 用户眼中的内容如何组织 | 流式文件、记录式文件、顺序/随机访问 |
| 物理结构 | 文件数据块怎样放到外存 | 连续、链接、FAT、索引、混合索引 |
| 文件系统结构 | 文件、目录、元数据、空闲块如何统一管理 | inode、目录项、超级块、位图、VFS |

<Callout type="info" title="一条总链路">
文件名 → 目录项 → inode / FCB → 数据块地址 → 文件数据块。
</Callout>

## 4.1.2 文件属性与元数据

文件的**元数据（metadata）**&#x2060;是“描述文件的信息”，常见包括：

- 文件类型；
- 文件大小；
- 所有者和所属组；
- 读/写/执行权限；
- 创建、修改、访问时间；
- 硬链接计数；
- 文件数据块定位信息。

一般教材把描述和控制一个文件所需的信息称为 **FCB（File Control Block，文件控制块）**。UNIX/类 UNIX 文件系统常用 **inode（索引节点）**&#x2060;承担其中的核心职责。

## 4.1.3 inode 最重要的边界

inode 通常保存：

- 文件类型、权限、所有者；
- 文件大小、时间戳；
- 链接计数；
- 直接/间接数据块指针。

但有一个高频结论：

> **inode 通常不保存文件名。文件名位于目录项中。**

因此：

```text
目录项：  "a.txt" → inode 123
                         ↓
inode 123：权限、大小、数据块位置……
                         ↓
                    文件数据块
```

多个目录项可以指向同一个 inode，这正是硬链接的基础。

## 4.1.4 inode 表、磁盘 inode 与内存 inode

一个文件系统包含大量 inode，因此会设置专门的 **inode 区 / inode 表**。每个 inode 具有 inode 编号，编号只在所在文件系统内部有意义。

应区分：

- **磁盘 inode**：持久保存文件元数据；
- **内存 inode / vnode 等结构**：文件被访问后，内核把相关元数据装入内存，以减少重复外存访问。

<Callout type="warn" title="不要混淆三个编号">
文件描述符 `fd` 是进程内的小整数；inode 号是文件系统内部标识；磁盘块号定位外存块。三者作用完全不同。
</Callout>

## 4.1.5 文件的逻辑结构

### 无结构文件（流式文件）

操作系统把内容看作字节序列：

```text
byte0 byte1 byte2 ... byteN
```

字节内部如何解释由应用程序决定。现代 UNIX 类普通文件通常采用这种抽象。

### 有结构文件（记录式文件）

文件由若干记录组成，可按记录进行组织和访问。常见访问方式：

- **顺序访问**：从前向后依次处理；
- **直接/随机访问**：依据记录号、键值或字节偏移直接定位。

> **易错点**
>
> “顺序访问/随机访问”描述访问方式；“连续分配/链接分配”描述外存物理布局，二者不是同一维度。

## 4.1.6 文件基本操作

文件管理常见操作可归为：

- 创建与删除；
- 打开与关闭；
- 读与写；
- 定位（seek）；
- 截断；
- 获取或修改属性；
- 建立/删除链接。

后续系统调用只是这些抽象操作的具体接口。

## 4.1.7 文件保护

新版 408 大纲明确要求文件保护。保护的目标是控制：**谁可以对哪个文件执行什么操作**。

典型权限包括：

- `r`：读取；
- `w`：修改；
- `x`：执行，或对目录进行搜索/进入。

常见实现思路：

1. **访问控制矩阵**：行是主体（用户/进程），列是客体（文件），单元格记录权限；
2. **ACL（Access Control List）**：以文件为中心，记录哪些主体拥有哪些权限；
3. **Capability（能力表）**：以主体为中心，记录它可以访问哪些对象及相应权限。

UNIX 传统权限可理解为一种紧凑的访问控制方案：

```text
owner | group | others
 rwx  |  r-x  |  r--
```

## 4.1.8 删除文件并不等于立即回收数据

删除文件名通常先删除目录项并改变链接计数。若仍存在：

- 其他硬链接；
- 已打开文件的有效内核引用；

则底层 inode 和数据块未必立即回收。

这说明“名字”“打开实例”“底层文件对象”是不同层次。

## 4.1.9 本节速查

| 对象 | 主要保存什么 |
| --- | --- |
| 文件名 | 位于目录项 |
| 目录项 | 文件名 + inode 号等目录信息 |
| inode / FCB | 文件元数据 + 数据块定位信息 |
| 数据块 | 文件实际内容 |
| ACL/权限位 | 谁能以何种方式访问文件 |
