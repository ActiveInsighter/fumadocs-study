DNS 解析题最关键的问题只有一个：

> **当前服务器不知道答案时，究竟是谁继续向下查询？**

这个责任边界决定了查询属于递归还是迭代。

## 6.3.1 递归查询

递归查询中，被查询服务器需要为查询者继续完成解析，并最终返回：

- 最终答案；或
- 明确的失败结果。

记忆：

```text
“我问你，你帮我查到底。”
```

典型场景是：

```text
主机 → 本地递归 DNS
```

## 6.3.2 迭代查询

迭代查询中，被查询服务器若没有最终答案，可以返回：

> 下一步应该询问哪个服务器。

查询者随后自己继续查询。

记忆：

```text
“你不知道最终答案，就告诉我下一站。”
```

典型场景是本地递归解析器依次询问：

```text
根 → TLD → 权威 DNS
```

## 6.3.3 典型实际解析流程

假设主机要解析：

```text
www.example.com
```

且各级缓存均未命中：

```text
主机
 │ 递归查询
 ↓
本地 DNS
 │
 ├─→ 根 DNS
 │    ←─ 返回 .com TLD 地址
 │
 ├─→ .com TLD
 │    ←─ 返回 example.com 权威 DNS 地址
 │
 └─→ 权威 DNS
      ←─ 返回 www.example.com 最终记录
 │
 ↓
主机收到 IP
```

也就是说，常见组合是：

```text
主机 → 本地 DNS：递归
本地 DNS → 根/TLD/权威：迭代
```

## 6.3.4 递归与迭代对比

| 对比项 | 递归查询 | 迭代查询 |
| --- | --- | --- |
| 谁负责继续查 | 被查询服务器 | 查询者 |
| 当前服务器不知道答案时 | 继续替对方查询 | 返回下一站信息 |
| 查询者工作量 | 小 | 大 |
| 被查询服务器负担 | 较大 | 较小 |
| 典型场景 | 主机 → 本地 DNS | 本地 DNS → 根/TLD/权威 |

<Callout type="warn" title="不要用“查询了几次”判断递归/迭代">
判断标准不是报文条数，而是**继续查询的责任属于谁**。
</Callout>

## 6.3.5 DNS 缓存与 TTL

可能出现 DNS 缓存的位置包括：

- 浏览器；
- 操作系统；
- 本地递归 DNS；
- 中间 DNS 服务器。

一条 DNS 记录中的 TTL（Time To Live）规定该记录允许被缓存多久。

若：

$$
TTL=3600\text{ s}
$$

则在记录仍有效时，后续查询可直接命中缓存；过期后需要重新查询。

缓存的价值是：

- 减少 DNS 查询时延；
- 降低根/TLD/权威服务器负载；
- 减少网络中的查询流量。

代价是：

- TTL 尚未到期时，缓存信息可能暂时落后于权威数据更新。

## 6.3.6 DNS 时延题的统一算法

如果忽略处理时间与报文传输时间，一个完整的查询往返通常贡献一个 RTT。

若解析需要依次发生 $k$ 次独立请求/响应，则 DNS 查询时延可抽象为：

$$
T_{DNS}=\sum_{i=1}^{k} RTT_i
$$

若题目把主机到本地 DNS 的往返也计入，则要把这一项同样加入；若本地有缓存命中，对应的外部查询 RTT 可以消失。

<Callout type="info" title="做 RTT 题先画事件链">
先写“主机→本地 DNS→根→TLD→权威”，再根据题目说明删掉缓存命中的步骤。不要直接背“DNS 一定需要 4 个 RTT”。
</Callout>

## 6.3.7 与 Web 综合题的顺序

首次通过域名访问 Web 服务器时，典型顺序是：

```text
DNS 解析
  ↓
得到服务器 IP
  ↓
TCP 三次握手
  ↓
HTTP 请求
  ↓
HTTP 响应
```

如果目标不在本地子网，还可能在发送 DNS/HTTP 数据前触发 ARP，以获得默认网关或本地 DNS 的 MAC 地址。

> **真题标签**
>
> Web 综合题常要求判断“HTTP 之前还运行了什么应用层协议”。若 URL 使用域名且缓存未提供 IP，答案通常是 **DNS**；随后再按 UDP/IP/帧逐层封装分析。

## 6.3.8 一眼判断

```text
服务器替查询方继续查到底 → 递归
服务器只告诉下一站       → 迭代

缓存命中 → 少走外部 DNS 查询
TTL 到期 → 重新解析
```
