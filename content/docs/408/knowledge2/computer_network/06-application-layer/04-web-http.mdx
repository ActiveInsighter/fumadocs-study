## 20. 万维网 WWW

WWW（World Wide Web，万维网）是通过网络访问相互关联的信息资源的系统。

用户通常使用：

> **浏览器**

访问 Web 资源。

Web 中需要重点掌握三个概念：

1. URL
2. HTTP / HTTPS
3. HTML

---

### 20.1 URL

URL（Uniform Resource Locator，统一资源定位符）用于描述：

> 网络资源在哪里，以及如何访问它。

例如：

```text
https://www.example.com/index.html
```

其中包含：

* 使用的协议；
* 主机名称；
* 资源路径等信息。

---

### 20.2 HTTP / HTTPS

HTTP：

> 浏览器与 Web 服务器之间传输 Web 数据的应用层协议。

HTTPS 可以理解为：

> 在 HTTP 通信基础上加入 TLS 安全保护。

HTTP 默认端口通常为：

```text
80
```

HTTPS 默认端口通常为：

```text
443
```

---

### 20.3 HTML

HTML（HyperText Markup Language，超文本标记语言）用于：

> 描述网页的结构和内容。

HTTP 负责：

```text
传输资源
```

HTML 负责：

```text
描述网页内容
```

两者不能混为一谈。

---

## 21. HTTP 基本工作方式

HTTP（HyperText Transfer Protocol，超文本传输协议）是一种应用层协议。

典型工作方式为：

```text
客户端发送 HTTP 请求
          ↓
Web 服务器处理请求
          ↓
服务器返回 HTTP 响应
```

<InlineSvg src="/images/computer-network/computer-network-application-www-001.svg" alt={"万维网 图 1"} />

HTTP/1.x 和 HTTP/2 通常基于 TCP 通信。

---

## 22. HTTP 是无状态协议

HTTP 的重要特点之一是：

> **无状态（Stateless）**

含义是：

HTTP 协议本身不会自动要求服务器记住：

```text
“这个客户端上一次请求了什么”
```

从协议本身看，两次请求可以相互独立。

例如：

```text
第一次：GET /login
第二次：GET /profile
```

HTTP 自身不会天然规定：

> 第二个请求属于第一个请求中的哪个用户。

如果 Web 应用需要维持用户登录状态，则通常需要额外机制，例如：

* Cookie；
* Session；
* Token。

> **易错**
>
> “HTTP 无状态”并不意味着 Web 网站不能保持登录状态。
> 它只是意味着这种状态不是由 HTTP 协议本身自动维护的。

---

## 23. HTTP 报文

HTTP 通信由：

* 请求报文；
* 响应报文

构成。

### 23.1 请求

客户端向服务器发送请求。

典型形式：

```text
请求行
请求首部
空行
消息体
```

---

### 23.2 响应

服务器向客户端返回响应。

典型形式：

```text
状态行
响应首部
空行
消息体
```

---

## 24. HTTP 请求方法

HTTP 定义了多种方法。

### GET

获取指定资源。

```text
GET /index.html
```

### POST

向服务器提交数据。

典型场景：

* 表单提交；
* API 请求。

### PUT

通常用于创建或更新指定资源。

### DELETE

用于删除指定资源。

### HEAD

与 GET 类似，但服务器只返回：

> 响应首部，不返回正常的实体主体。

#### 方法速记

| 方法     | 含义      |
| ------ | ------- |
| GET    | 获取资源    |
| POST   | 提交数据    |
| PUT    | 创建/更新资源 |
| DELETE | 删除资源    |
| HEAD   | 只获取首部   |

---

## 25. HTTP 状态码

HTTP 响应包含状态码，用于说明请求处理结果。

常见状态码：

| 状态码                         | 含义      |
| --------------------------- | ------- |
| `200 OK`                    | 请求成功    |
| `404 Not Found`             | 资源不存在   |
| `500 Internal Server Error` | 服务器内部错误 |

还可以按首位数字进行分类：

| 类别  | 含义    |
| --- | ----- |
| 1xx | 信息性响应 |
| 2xx | 成功    |
| 3xx | 重定向   |
| 4xx | 客户端错误 |
| 5xx | 服务器错误 |

---

## 26. HTTP 首部字段

HTTP 请求和响应中都包含首部字段。

常见字段包括：

#### Content-Type

说明消息体的数据类型。

例如：

```text
Content-Type: text/html
```

#### User-Agent

用于描述客户端软件。

#### Connection

用于控制当前连接的相关行为。

例如：

```text
Connection: close
```

#### Cookie / Set-Cookie

用于在客户端与服务器之间关联会话信息。

---

## 27. HTTP 持久连接与非持久连接

<InlineSvg src="/images/computer-network/computer-network-application-www-002.svg" alt={"万维网 图 2"} />

HTTP 的连接方式是 408 中的重要考点。

---

### 27.1 非持久连接

非持久连接（Non-Persistent Connection）中：

> 一条 TCP 连接通常只服务一个 HTTP 请求/响应。

例如页面需要：

```text
HTML
图片 1
图片 2
图片 3
```

则可能不断经历：

```text
建立 TCP
传输一个对象
关闭 TCP
```

然后针对其他对象重新建立连接。

缺点：

* 建立 TCP 连接存在额外开销；
* 多次握手增加时间；
* 服务器需要维护大量短连接。

---

### 27.2 持久连接

持久连接（Persistent Connection）中：

> 一条 TCP 连接可以连续传输多个 HTTP 请求和响应。

这样就可以减少：

* TCP 建连次数；
* 握手开销；
* 网络延迟。

---

### 27.3 HTTP/1.0 与 HTTP/1.1

#### HTTP/1.0

默认采用：

> **非持久连接**

若希望保持连接，可显式使用类似：

```text
Connection: keep-alive
```

的机制。

#### HTTP/1.1

默认采用：

> **持久连接**

若希望通信后关闭 TCP 连接，可以使用：

```text
Connection: close
```

#### 高频对比

| HTTP 版本  | 默认连接方式 |
| -------- | ------ |
| HTTP/1.0 | 非持久连接  |
| HTTP/1.1 | 持久连接   |

> **408 必记**
>
> `HTTP/1.1 → 默认持久连接`

---

## 28. HTTP 非流水线与流水线

<InlineSvg src="/images/computer-network/computer-network-application-www-003.svg" alt={"万维网 图 3"} />

持久连接建立后，还可以根据请求的发送方式进一步区分：

* 非流水线；
* 流水线。

---

### 28.1 非流水线

非流水线方式中：

```text
发送请求 1
↓
等待响应 1
↓
发送请求 2
↓
等待响应 2
↓
发送请求 3
```

也就是：

> 必须收到前一个请求的响应后，才能继续发送下一个请求。

---

### 28.2 流水线

HTTP 流水线（HTTP Pipelining）允许：

> 客户端在还没有收到前一个请求的响应时，继续发送后续请求。

例如：

```text
请求 1 ──→
请求 2 ──→
请求 3 ──→

       ←── 响应 1
       ←── 响应 2
       ←── 响应 3
```

它减少了逐个等待响应带来的时间开销。

---

### 28.3 不同版本

#### HTTP/1.0

通常不支持 HTTP 流水线。

#### HTTP/1.1

支持 HTTP 流水线机制，但实际应用并不广泛，其中一个重要问题是：

> **队头阻塞**

#### HTTP/2

HTTP/2 使用多路复用机制，使同一连接中的多个请求和响应可以交错传输，大幅改善 HTTP/1.1 请求按序处理带来的应用层队头阻塞问题。

需要注意的是，HTTP/2 仍然基于 TCP，因此底层 TCP 丢包时仍可能造成传输层级别的等待。

---

## 29. 队头阻塞

所谓队头阻塞，可以理解为：

> 排在最前面的任务没有完成，导致后面的任务即使已经准备好，也不能及时得到处理。

例如：

```text
请求 1 —— 响应很慢
请求 2 —— 等待
请求 3 —— 等待
请求 4 —— 等待
```

HTTP/1.1 的流水线要求响应保持与请求对应的顺序，因此前面的响应迟迟不能完成时，后面的响应可能被阻塞。

---

## 30. Cookie

HTTP 是无状态协议。

为了让应用能够识别：

> “这个请求是不是之前那个用户发来的？”

可以使用 Cookie。

<InlineSvg src="/images/computer-network/computer-network-application-www-004.svg" alt={"万维网 图 4"} />

---

### 30.1 服务器设置 Cookie

服务器可以在 HTTP 响应中加入：

```text
Set-Cookie
```

例如：

```text
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Expires=Wed, 21 Oct 2025 07:28:00 GMT; Path=/; Secure; HttpOnly
```

浏览器收到响应后，将 Cookie 保存起来。

---

### 30.2 浏览器发送 Cookie

随后访问符合条件的资源时，浏览器会在 HTTP 请求中加入：

```text
Cookie
```

例如：

```text
GET /dashboard HTTP/1.1
Cookie: sessionId=abc123
```

服务器收到后，就可以根据 Cookie 中的信息：

* 识别会话；
* 关联用户；
* 恢复登录状态；
* 保存一些应用状态。

---

### 30.3 Cookie 与 HTTP 无状态并不矛盾

这里是非常容易混淆的一点。

HTTP：

> **本身仍然是无状态协议。**

Cookie：

> 是应用为了在多个无状态 HTTP 请求之间建立关联而使用的额外机制。

因此：

```text
HTTP 无状态
        ↓
应用需要记住用户
        ↓
使用 Cookie / Session 等机制维护状态
```

## 31. 全章核心协议对比

| 协议    | 功能        | TCP / UDP |    默认端口 | 最关键特征       |
| ----- | --------- | --------- | ------: | ----------- |
| DNS   | 域名解析      | UDP/TCP   |      53 | 递归、迭代、缓存    |
| FTP   | 文件传输      | TCP       | 21 / 20 | 控制连接与数据连接分离 |
| SMTP  | 发送邮件      | TCP       |      25 | Push        |
| POP3  | 获取邮件      | TCP       |     110 | 下载邮件        |
| IMAP  | 管理邮件      | TCP       |     143 | 服务器同步       |
| HTTP  | Web 资源传输  | TCP       |      80 | 请求/响应、无状态   |
| HTTPS | 安全 Web 访问 | TCP       |     443 | HTTP + TLS  |

## 32. 高频易错点总结

### 32.1 DNS

> **错误：** 主机直接向根服务器逐级查询。
> **正确：** 主机通常把递归查询交给本地 DNS，本地 DNS 再负责后续查询。

> **错误：** 根服务器一定返回最终 IP。
> **正确：** 根服务器通常返回下一层 TLD 服务器的信息。

> **错误：** DNS 每次解析都要重新访问根服务器。
> **正确：** 首先检查缓存，缓存受 TTL 控制。

---

### 32.2 FTP

> **错误：** FTP 只需要一条 TCP 连接。
> **正确：** FTP 将控制连接和数据连接分开。

> **错误：** FTP 的 21 端口用于传文件。
> **正确：** 21 端口主要用于控制连接。

> **错误：** 主动模式指客户端主动建立数据连接。
> **正确：** 主动模式下是服务器主动连接客户端的数据端口。

> **错误：** 被动模式下所有连接都是服务器主动建立。
> **正确：** 被动模式的数据连接由客户端主动建立。

---

### 32.3 电子邮件

> **错误：** SMTP 用来收邮件。
> **正确：** SMTP 主要负责发送和转发邮件。

> **错误：** POP3 用来发送邮件。
> **正确：** POP3 用于用户从邮件服务器获取邮件。

> **错误：** MIME 是邮件发送协议。
> **正确：** MIME 是电子邮件内容格式的扩展机制。

快速记忆：

```text
SMTP：送
POP3：取
IMAP：同步管理
MIME：扩展内容格式
```

---

### 32.4 HTTP

> **错误：** HTTP 能保持登录状态，所以 HTTP 是有状态协议。
> **正确：** HTTP 本身无状态，登录状态由 Cookie、Session 等额外机制维护。

> **错误：** HTTP/1.0 默认使用持久连接。
> **正确：** HTTP/1.0 默认非持久连接。

> **错误：** HTTP/1.1 每个对象都必须新建一条 TCP 连接。
> **正确：** HTTP/1.1 默认使用持久连接，一条 TCP 连接可以处理多个请求。

> **错误：** 持久连接就一定是流水线。
> **正确：** “是否持久”和“是否流水线”是两个不同概念。

---

## 33. 408 做题判断框架

应用层题目可以按下面的顺序快速判断。

### 第一步：判断协议

先看题目场景：

```text
域名解析 → DNS
文件传输 → FTP
发邮件 → SMTP
取邮件 → POP3 / IMAP
访问网页 → HTTP
```

### 第二步：判断传输层

重点记：

```text
FTP   → TCP
SMTP  → TCP
POP3  → TCP
IMAP  → TCP
HTTP  → TCP
DNS   → 常见查询 UDP，必要时也可 TCP
```

### 第三步：判断连接

例如：

```text
FTP
→ 控制连接 + 数据连接

HTTP/1.0
→ 默认非持久

HTTP/1.1
→ 默认持久
```

### 第四步：判断通信方向

例如：

```text
SMTP
→ Push

POP3
→ Pull

DNS 递归
→ 被查询服务器负责继续查询

DNS 迭代
→ 查询者自己继续查询

FTP 主动模式
→ 服务器主动建立数据连接

FTP 被动模式
→ 客户端主动建立数据连接
```
