## 20. WWW、URL、HTTP 与 HTML

> **真题考察**
>
> - 2014、2015、2022、2024、2026 年第 40 题
> - 2011 年第 47 题

WWW（World Wide Web）通过浏览器访问由超链接组织的 Web 资源。408 中必须分清以下概念：

| 概念 | 作用 |
| --- | --- |
| URL | 标识资源的位置与访问方式 |
| HTTP / HTTPS | 浏览器与 Web 服务器交换资源的应用层协议 |
| HTML | 描述网页内容与结构 |
| 浏览器 | Web 客户端 |
| Web 服务器 | 保存/生成 Web 资源并响应请求 |

### 20.1 URL

例如：

```text
https://www.example.com/index.html
```

可抽象为：

```text
方案://主机名[:端口]/路径
```

若 URL 使用域名，浏览器在真正访问服务器前通常需要先通过 DNS 获得 IP 地址。

### 20.2 HTTP / HTTPS

HTTP 默认服务器端口通常为 **80**；HTTPS 默认服务器端口通常为 **443**。在传统 408 模型中，HTTPS 可理解为 HTTP 通过 TLS 获得机密性、完整性和服务器身份认证等安全能力。

### 20.3 HTML

HTML（HyperText Markup Language）描述网页的内容与结构；HTTP 负责把 HTML、图片、脚本等 Web 对象传输到客户端。

```text
HTTP：怎么传
HTML：页面内容如何组织
```

<Callout type="info" title="一个网页通常不是一个 HTTP 对象">

基础 HTML 中可能引用多个图片、样式表、脚本等对象。浏览器通常需要对**每个独立资源发出 HTTP 请求**。因此“一个网页”不等于“只发送一个 HTTP 请求”。

</Callout>

## 21. HTTP 基本工作方式与版本

<InlineSvg src="/images/computer-network/computer-network-application-www-001.svg" alt={"万维网 图 1"} />

HTTP（HyperText Transfer Protocol）采用请求/响应模式：

```text
客户端发送 HTTP 请求
          ↓
Web 服务器处理
          ↓
服务器返回 HTTP 响应
```

经典 408 题中：

- HTTP/1.0、HTTP/1.1：基于 TCP；
- HTTP/2：通常也基于 TCP，并支持多路复用；
- HTTP/3：基于 QUIC/UDP，题目明确出现时再按其特性分析。

<Callout type="warning" title="HTTP 与 TCP 的职责要分层判断">

HTTP 定义方法、URL、首部、状态码和请求/响应等**应用语义**；可靠传输、按序交付、流量控制、拥塞控制等由 TCP（HTTP/1.x、HTTP/2 场景）负责。

</Callout>

---

## 22. HTTP 的无状态性

HTTP 是**无状态（Stateless）**&#x2060;协议：协议本身不要求服务器自动保留某个客户端上一次请求的应用状态。

例如：

```text
GET /login
GET /profile
```

仅靠 HTTP 本身，服务器不会天然知道第二个请求必然属于第一个请求中登录成功的用户。

Web 应用若需要登录态、购物车等跨请求状态，通常借助：

- Cookie；
- Session；
- Token 等机制。

<Callout type="warning" title="无状态 ≠ 网站不能保持状态">

“HTTP 无状态”描述协议本身；“网站能记住用户”是应用利用 Cookie、Session 等额外机制建立跨请求关联。二者并不矛盾。

</Callout>

## 23. HTTP 报文结构

HTTP 通信由**请求报文**和**响应报文**组成。

### 23.1 请求报文

典型结构：

```text
请求行
请求首部
空行
可选消息体
```

请求行典型形式：

```text
GET /index.html HTTP/1.1
```

其中包含方法、请求目标和 HTTP 版本。

### 23.2 响应报文

典型结构：

```text
状态行
响应首部
空行
可选消息体
```

状态行包含 HTTP 版本、状态码和原因短语等。

## 24. HTTP 请求方法

| 方法 | 典型语义 |
| --- | --- |
| GET | 获取资源 |
| POST | 提交数据，让服务器处理 |
| PUT | 创建或替换指定资源 |
| DELETE | 删除指定资源 |
| HEAD | 获取与 GET 类似的响应首部，但通常不返回正常响应主体 |

408 主要考查方法的基础语义，不需要把某个 Web 框架或 REST 设计习惯绝对化。

## 25. HTTP 状态码

HTTP 状态码第一位表示响应类别：

| 类别 | 含义 |
| --- | --- |
| 1xx | 信息性响应 |
| 2xx | 成功 |
| 3xx | 重定向 |
| 4xx | 客户端侧请求错误 |
| 5xx | 服务器侧错误 |

典型状态码：

| 状态码 | 含义 |
| --- | --- |
| `200 OK` | 请求成功 |
| `301/302` | 重定向 |
| `404 Not Found` | 资源不存在 |
| `500 Internal Server Error` | 服务器内部错误 |

常见首部及作用：

| 字段 | 作用示例 |
| --- | --- |
| `Host` | 指明目标主机/虚拟主机 |
| `Content-Type` | 描述消息体媒体类型 |

## 27. HTTP 持久连接与非持久连接

<InlineSvg src="/images/computer-network/computer-network-application-www-002.svg" alt={"万维网 图 2"} />

“持久/非持久”回答的是：**一条 TCP 连接可以承载多少个 HTTP 请求/响应？**

### 27.1 非持久连接

一条 TCP 连接通常只服务一个 HTTP 请求/响应对象：

```text
建立 TCP
→ 请求一个对象
→ 返回一个对象
→ 连接结束
```

页面包含基础 HTML 和多个嵌入对象时，可能需要反复建立 TCP 连接。

### 27.2 持久连接

一条 TCP 连接可以连续承载多个 HTTP 请求与响应，从而减少反复握手的 RTT 和资源开销。

### 27.3 HTTP/1.0 与 HTTP/1.1 的 408 默认口径

| HTTP 版本 | 典型默认判断 |
| --- | --- |
| HTTP/1.0 | 默认非持久 |
| HTTP/1.1 | 默认持久 |

HTTP/1.0 存在扩展的保持连接机制；HTTP/1.1 若显式关闭可以使用：

```text
Connection: close
```

<Callout type="warning" title="对象数、HTTP 请求数、TCP 连接数不是同一概念">

假设页面由 1 个 HTML + 7 张图片组成：通常至少涉及 8 次对象请求，但 TCP 连接数取决于是否使用持久连接、是否并行等条件。**8 个对象不必等于 8 条 TCP 连接。**

</Callout>

## 28. HTTP 非流水线、流水线与并行连接

<InlineSvg src="/images/computer-network/computer-network-application-www-003.svg" alt={"万维网 图 3"} />

这三个概念经常混在一起，必须分别判断。

### 28.1 持久非流水线

同一 TCP 连接可以复用，但必须等前一个响应回来后才发送下一个请求：

```text
请求 1 → 等响应 1
请求 2 → 等响应 2
请求 3 → 等响应 3
```

### 28.2 持久流水线

同一条 TCP 连接上可以在前一个响应返回前继续发后续请求：

```text
请求 1 ──→
请求 2 ──→
请求 3 ──→

       ←── 响应 1
       ←── 响应 2
       ←── 响应 3
```

HTTP/1.1 规范支持流水线，但现实部署较少。

### 28.3 并行连接

并行连接表示浏览器**同时建立多条 TCP 连接**请求不同对象。它与“流水线”不是一回事：

```text
流水线：同一条 TCP 连接上连续发多个请求
并行：  同时用多条 TCP 连接
```

HTTP 时延题只要题目说“允许最多 $m$ 条并行 TCP 连接”，就必须按批次计算，而不能直接套串行公式。

## 29. HTTP 队头阻塞

队头阻塞（Head-of-Line Blocking）指前面的任务迟迟不能完成，导致后面的任务被迫等待。

HTTP/1.1 流水线要求响应按请求顺序对应返回。若第一个响应很慢，后续响应即使准备好也不能随意越过：

```text
请求 1 —— 响应很慢
请求 2 —— 等待
请求 3 —— 等待
```

HTTP/2 通过应用层多路复用缓解了 HTTP/1.1 流水线的应用层队头阻塞；但 HTTP/2 仍建立在单条 TCP 字节流之上，TCP 丢包可能让同一连接上的多个流共同等待缺失字节恢复。

## 30. Cookie、Session 与 Web 缓存

<InlineSvg src="/images/computer-network/computer-network-application-www-004.svg" alt={"万维网 图 4"} />

### 30.1 Cookie

服务器可以在响应中发送：

```text
Set-Cookie: sessionId=abc123
```

浏览器保存后，在满足域、路径等条件的后续请求中携带：

```text
Cookie: sessionId=abc123
```

服务器即可把多个独立 HTTP 请求关联到同一用户或会话。

```text
HTTP 本身无状态
      ↓
应用需要跨请求识别用户
      ↓
服务器设置 Cookie
      ↓
浏览器后续请求携带 Cookie
      ↓
服务器据此关联 Session / 用户状态
```

<Callout type="warning" title="Cookie 不是可执行代码">

Cookie 本质上是浏览器保存并按规则随 HTTP 请求携带的数据（常见为键值信息），并不是“服务器下发的一段程序代码”。

</Callout>

### 30.2 Session

Session 常指服务器侧保存的会话状态。常见做法是：Cookie 中携带会话标识，服务器根据该标识找到对应 Session。

因此：

```text
Cookie：客户端保存/携带
Session：常由服务器保存应用会话状态
```

### 30.3 Web 缓存 / 代理缓存

Web 缓存保存近期获取的 Web 对象。如果再次请求的对象仍有效，可直接由附近缓存返回，从而：

- 减少访问源服务器的流量；
- 降低跨网络传输时延；
- 减轻源服务器负载。

<Callout type="info" title="缓存与 DNS 缓存不是一回事">

DNS 缓存保存的是名称解析结果；Web 缓存保存的是 HTTP/Web 对象。两者都能减少时延，但作用对象和所在协议过程不同。

</Callout>

## 31. HTTP RTT 与页面访问时延计算

HTTP 综合题常把 DNS、TCP 建连、HTTP 请求和对象发送组合在一起。计算前必须先列题设：

- DNS 是否已解析/是否缓存；
- TCP 是否已经建立；
- HTTP 是持久还是非持久；
- 是否允许流水线；
- 是否允许并行 TCP；
- 是否忽略对象传输时间和服务器处理时间。

### 31.1 获取一个对象：经典非持久模型

若从“开始建立 TCP”计时，对象传输时延为 $T_{tx}$：

$$
T \approx 2RTT + T_{tx}
$$

其中：

- 第 1 个 RTT：TCP 三次握手；
- 第 2 个 RTT：HTTP 请求发出到响应首部/数据开始返回；
- $T_{tx}$：对象真正发完所需时间。

这里不需要再额外给 TCP 四次挥手加一个固定 RTT，除非题目明确要求把关闭过程计入终止时刻。

### 31.2 基础 HTML + $n$ 个嵌入对象

若对象都来自同一服务器、RTT 相同、忽略对象传输时间：

**非持久，完全串行**：共 $n+1$ 个对象，每个对象 2 RTT：

$$
T \approx 2(n+1)RTT
$$

**持久，非流水线**：

- 1 RTT：建立 TCP；
- 1 RTT：获取基础 HTML；
- 之后每个嵌入对象各 1 RTT。

因此：

$$
T \approx (n+2)RTT
$$

**持久，流水线**：

- 1 RTT：建 TCP；
- 1 RTT：获取基础 HTML；
- 1 RTT：流水化请求并开始收到所有嵌入对象。

因此经典简化结果：

$$
T \approx 3RTT
$$

<Callout type="warning" title="这些公式只适用于对应简化模型">

若题目给出不同 RTT、并行连接上限、对象大小、链路速率、服务器处理时间或连接已预先建立，都必须画时间线重新计算，不能机械套公式。

</Callout>

### 31.3 并行非持久连接

若基础 HTML 收到后，浏览器一次最多并行建立 $m$ 条非持久 TCP 连接，而有 $n$ 个嵌入对象，则对象请求需分：

$$
\left\lceil \frac{n}{m} \right\rceil
$$

批完成。若每批仍按“1 RTT 建连 + 1 RTT 请求/响应”简化，则每批约 2 RTT。

### 31.4 DNS + HTTP 总时间

若访问前还需 DNS 解析：

$$
T_{DNS}=\sum RTT_{DNS}
$$

再加 TCP/HTTP 与对象传输时间：

$$
T_{total}=T_{DNS}+T_{TCP/HTTP}+T_{tx}
$$

最安全的做法不是先找公式，而是先画：

```text
DNS
→ 建立 TCP
→ 请求基础 HTML
→ 收到并解析 HTML
→ 请求嵌入对象
→ 收完对象
```

然后把只能串行发生的阶段相加。

## 32. 全章核心协议对比

| 协议 | 功能 | 传输层 | 默认/常见服务器端口 | 关键特征 |
| --- | --- | --- | ---: | --- |
| DNS | 域名解析 | UDP / TCP | 53 | 递归、迭代、缓存 |
| FTP | 文件传输 | TCP | 控制 21；主动数据传统 20 | 控制/数据连接分离 |
| SMTP | 发送、转发邮件 | TCP | 25 | Push |
| POP3 | 下载邮件 | TCP | 110 | Pull |
| IMAP | 邮箱同步管理 | TCP | 143 | 服务器端状态同步 |
| HTTP | Web 资源传输 | TCP（HTTP/1.x、HTTP/2） | 80 | 请求/响应、无状态 |
| HTTPS | 加密 Web 访问 | 典型 408 场景为 TLS/TCP | 443 | HTTP + TLS |

### 32.1 协议与“主动方”不要混淆

| 场景 | 典型主动方 |
| --- | --- |
| DNS 主机查询本地 DNS | 主机 |
| HTTP 请求 | 浏览器/客户端 |
| FTP 控制连接 | FTP 客户端 |
| FTP 主动模式数据连接 | FTP 服务器 |
| SMTP 邮件发送 | SMTP 客户端 |
| POP3 / IMAP 取信 | 邮件客户端 |

## 33. 高频易错点与做题判断框架

### 33.1 DNS

- 主机通常先问**本地递归解析器**，不是直接问根服务器；
- 根服务器通常返回下一层委派信息；
- 查询前先看缓存；
- 递归/迭代看“谁负责继续查”；
- 普通查询常用 UDP，但 DNS 不是“绝对只用 UDP”。

### 33.2 FTP

- 控制连接与数据连接分离；
- TCP 21 是控制连接服务器端口；
- 主动/被动模式只看**数据连接发起方**；
- 连接总数要按实际数据传输次数计算。

### 33.3 电子邮件

```text
SMTP：发送 / 转发
POP3：下载
IMAP：服务器端同步管理
MIME：内容表示扩展
HTTP：浏览器访问 Webmail
```

### 33.4 HTTP

- 一个网页可包含多个独立 HTTP 对象；
- HTTP 无状态不等于网站不能维持登录态；
- HTTP/1.0 典型默认非持久，HTTP/1.1 典型默认持久；
- 持久连接、流水线、并行 TCP 是三个不同概念；
- Cookie 是数据，不是可执行代码；
- 算时延前先判断 DNS、TCP、对象数、连接复用、并行/流水线和传输时间。

### 33.5 应用层综合题六步法

1. **场景 → 协议**；
2. **协议 → TCP/UDP + 服务器端口**；
3. **判断通信两端与主动方**；
4. **判断连接结构**：一条还是多条、是否复用；
5. **判断缓存/并行/流水线等条件**；
6. **画时间线**，累加真正串行发生的 RTT 和传输时延。

## 34. 一页速记

```text
【网络应用模型】
C/S：客户端主动请求，服务器通常长期运行
P2P：节点既可请求也可提供资源

【DNS】
服务器端口：53
普通查询常用 UDP；特定情形可用 TCP
主机 → 本地 DNS：常见递归
本地 DNS → 根/TLD/权威：常见迭代
根：返回 TLD 委派
TLD：返回权威 DNS 委派
权威 DNS：返回权威资源记录
先看缓存，TTL 决定缓存有效期

【FTP】
TCP
控制连接：客户端 → 服务器:21，通常持续整个会话
数据连接：按需建立
主动模式：服务器主动连接客户端，服务器传统使用 20
被动模式：客户端主动连接服务器协商出的数据端口

【电子邮件】
SMTP：TCP 25，发送/转发，Push
POP3：TCP 110，下载邮件
IMAP：TCP 143，服务器端同步管理
MIME：正文/附件的类型与编码表示
Webmail：浏览器侧使用 HTTP/HTTPS

【HTTP】
HTTP：80
HTTPS：443
HTTP 本身无状态
HTTP/1.0：典型默认非持久
HTTP/1.1：典型默认持久
持久 ≠ 流水线 ≠ 并行 TCP
Cookie：客户端保存并随请求携带数据

【经典时延】
DNS：串行查询 RTT 求和
非持久 HTTP 单对象：约 2RTT + 对象传输时间
总时间：DNS + TCP/HTTP + 实际数据传输时间
```
