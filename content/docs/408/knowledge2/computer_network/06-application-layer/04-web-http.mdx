## 20. WWW、URL、HTTP 与 HTML

> **真题考察**
>
> - 2014、2015、2022、2024、2026 年第 40 题
> - 2011 年第 47 题

WWW（World Wide Web）通过浏览器访问相互关联的 Web 资源。需要区分三个概念：

| 概念 | 作用 |
| --- | --- |
| URL | 标识资源的位置和访问方式 |
| HTTP / HTTPS | 浏览器与 Web 服务器之间传输资源的应用层协议 |
| HTML | 描述网页的结构与内容 |

### 20.1 URL

例如：

```text
https://www.example.com/index.html
```

可分解为协议方案、主机名和资源路径等部分。

### 20.2 HTTP / HTTPS

HTTP 默认端口通常为 **80**；HTTPS 默认端口通常为 **443**。408 传统模型中，HTTPS 可理解为“HTTP 通过 TLS 提供机密性、完整性和身份认证”。

### 20.3 HTML

HTML（HyperText Markup Language）负责描述网页内容和结构；HTTP 负责在网络上传输 HTML、图片等资源。

```text
HTTP：怎么传
HTML：网页写了什么、如何组织
```

## 21. HTTP 基本工作方式与版本

<InlineSvg src="/images/computer-network/computer-network-application-www-001.svg" alt={"万维网 图 1"} />

HTTP（HyperText Transfer Protocol）采用请求/响应模式：

```text
客户端发送 HTTP 请求
          ↓
Web 服务器处理
          ↓
服务器返回 HTTP 响应
```

经典 408 题中：

- HTTP/1.0、HTTP/1.1：基于 TCP；
- HTTP/2：也通常基于 TCP，并引入多路复用；
- HTTP/3：建立在 QUIC/UDP 之上，若题目未涉及一般无需展开。

<Callout type="info" title="不要把 HTTP 与 TCP 的职责混在一起">

HTTP 定义的是请求、响应、首部、方法、状态码等应用层语义；可靠字节传输、重传、流量控制等由下层 TCP（HTTP/1.x、HTTP/2 场景）负责。

</Callout>

## 22. HTTP 的无状态性

HTTP 是**无状态（Stateless）**&#x2060;协议：协议本身不要求服务器自动记住某个客户端上一次请求的应用状态。

例如两次请求：

```text
GET /login
GET /profile
```

仅靠 HTTP 协议本身，并不会自动建立“第二个请求属于第一个请求中登录用户”的长期身份关系。

Web 应用若需要登录态、购物车等跨请求状态，通常通过：

- Cookie；
- Session；
- Token 等机制

建立关联。

<Callout type="warning" title="无状态 ≠ 网站不能保持状态">

“HTTP 无状态”描述协议本身；“网站能记住用户”通常依赖额外的应用状态机制。二者不矛盾。

</Callout>

## 23. HTTP 报文结构

HTTP 通信由**请求报文**和**响应报文**组成。

### 23.1 请求报文

典型结构：

```text
请求行
请求首部
空行
可选消息体
```

请求行包含方法、目标资源以及 HTTP 版本等信息。

### 23.2 响应报文

典型结构：

```text
状态行
响应首部
空行
可选消息体
```

状态行包含 HTTP 版本、状态码及原因短语等信息。

## 24. HTTP 请求方法

| 方法 | 典型含义 |
| --- | --- |
| GET | 获取资源 |
| POST | 向服务器提交数据 |
| PUT | 创建或替换/更新指定资源 |
| DELETE | 删除指定资源 |
| HEAD | 获取与 GET 类似的响应首部，但不返回正常响应主体 |

示例：

```text
GET /index.html HTTP/1.1
```

408 通常考查方法的基本语义，不必把 REST 风格的具体业务规则绝对化。

---

## 25. HTTP 状态码

HTTP 响应状态码首位数字反映大类：

| 类别 | 含义 |
| --- | --- |
| 1xx | 信息性响应 |
| 2xx | 成功 |
| 3xx | 重定向 |
| 4xx | 客户端侧请求错误 |
| 5xx | 服务器侧错误 |

典型状态码：

| 状态码 | 含义 |
| --- | --- |
| `200 OK` | 请求成功 |
| `404 Not Found` | 资源不存在 |
| `500 Internal Server Error` | 服务器内部错误 |

---

## 26. HTTP 首部字段

常见首部包括：

| 字段 | 作用示例 |
| --- | --- |
| `Content-Type` | 描述消息体媒体类型，如 `text/html` |
| `User-Agent` | 描述客户端软件 |
| `Connection` | 控制连接相关行为，如 `close` |
| `Cookie` | 客户端向服务器携带 Cookie |
| `Set-Cookie` | 服务器要求浏览器保存 Cookie |

HTTP 首部用于传递控制与元数据，不要把首部本身误认为应用数据主体。

## 27. HTTP 持久连接与非持久连接

<InlineSvg src="/images/computer-network/computer-network-application-www-002.svg" alt={"万维网 图 2"} />

“持久/非持久”回答的是：**一条 TCP 连接服务多少个 HTTP 请求/响应？**

### 27.1 非持久连接

一条 TCP 连接通常只服务一个 HTTP 请求/响应对象：

```text
建立 TCP
→ 请求一个对象
→ 返回一个对象
→ 关闭 TCP
```

页面中若包含 HTML 和多个图片等对象，就可能反复建立新 TCP 连接。

### 27.2 持久连接

一条 TCP 连接可以连续承载多个 HTTP 请求和响应，从而减少反复建立 TCP 的 RTT 和资源开销。

### 27.3 HTTP/1.0 与 HTTP/1.1

| HTTP 版本 | 408 常用默认判断 |
| --- | --- |
| HTTP/1.0 | 默认非持久连接 |
| HTTP/1.1 | 默认持久连接 |

HTTP/1.0 可以通过扩展机制尝试保持连接；HTTP/1.1 若要关闭连接可使用：

```text
Connection: close
```

<Callout type="warning" title="持久连接不等于流水线">

“持久”只说明一条 TCP 连接能否复用；“流水线”说明是否可以在前一个响应回来前继续发送后续请求。两个概念必须分开判断。

</Callout>

## 28. HTTP 非流水线与流水线

<InlineSvg src="/images/computer-network/computer-network-application-www-003.svg" alt={"万维网 图 3"} />

在持久连接已经存在的前提下，请求发送方式还可以分为非流水线和流水线。

### 28.1 非流水线

```text
请求 1 → 等响应 1
请求 2 → 等响应 2
请求 3 → 等响应 3
```

客户端收到前一个请求的响应后，才发送下一个请求。

### 28.2 流水线

客户端可以连续发出多个请求，不必等待前一个响应返回：

```text
请求 1 ──→
请求 2 ──→
请求 3 ──→

       ←── 响应 1
       ←── 响应 2
       ←── 响应 3
```

HTTP/1.1 规范支持流水线，但实际部署较少；HTTP/2 使用多路复用，让多个请求/响应帧可以交错传输。

## 29. HTTP 队头阻塞

队头阻塞（Head-of-Line Blocking）可以理解为：最前面的任务迟迟不能完成，使后续已准备好的任务也被迫等待。

HTTP/1.1 流水线中，响应需要按请求顺序对应返回。如果第一个响应很慢，后续响应即使已经计算完成也不能任意越过它：

```text
请求 1 —— 响应很慢
请求 2 —— 等待
请求 3 —— 等待
请求 4 —— 等待
```

HTTP/2 的应用层多路复用显著改善了 HTTP/1.1 流水线的应用层队头阻塞，但由于 HTTP/2 仍基于单条 TCP 字节流，TCP 丢包仍可能让同一连接上的多个流等待丢失字节恢复。

## 30. Cookie 与会话状态

<InlineSvg src="/images/computer-network/computer-network-application-www-004.svg" alt={"万维网 图 4"} />

服务器可以在响应中发送：

```text
Set-Cookie: sessionId=abc123
```

浏览器保存后，在符合域、路径等条件的后续请求中携带：

```text
Cookie: sessionId=abc123
```

服务器即可把多个原本相互独立的 HTTP 请求关联到同一用户或会话。

典型流程：

```text
HTTP 无状态
    ↓
应用需要跨请求识别用户
    ↓
服务器设置 Cookie
    ↓
浏览器后续请求携带 Cookie
    ↓
服务器据此关联 Session / 用户状态
```

<Callout type="warning" title="Cookie、Session 与 HTTP 无状态">

Cookie 是客户端保存并随请求发送的数据机制；Session 常指服务器侧保存的会话状态。它们帮助应用建立跨请求关联，但不会改变“HTTP 协议本身无状态”的性质。

</Callout>

## 31. HTTP RTT 与页面访问时延计算

HTTP 综合题经常把 DNS、TCP 建连、HTTP 请求和对象传输组合在一起。计算前先写清题目假设：**是否忽略对象发送时延、是否已建立 TCP、是否并行、是否流水线**。

### 31.1 获取一个对象的经典模型

若使用非持久 HTTP，且对象传输时延记为 $T_{tx}$，从开始建立 TCP 到完整收到对象，典型简化模型为：

$$
T\approx 2RTT+T_{tx}
$$

其中：

- 第 1 个 RTT：TCP 三次握手；
- 第 2 个 RTT：发送 HTTP 请求并收到响应首部/开始返回对象；
- $T_{tx}$：对象实际发送时间。

### 31.2 基础 HTML + $n$ 个嵌入对象

若忽略对象传输时间，并假设 RTT 相同：

**非持久、完全串行**：

$$
T\approx 2(n+1)RTT
$$

**持久、非流水线**：先 1 RTT 建 TCP，1 RTT 获取基础 HTML，之后每个对象各需约 1 RTT：

$$
T\approx (n+2)RTT
$$

**持久、流水线**：先建立 TCP，再获取基础 HTML，随后一次连续发出所有嵌入对象请求：

$$
T\approx 3RTT
$$

<Callout type="warning" title="这些公式只有在题目假设一致时才能直接用">

若题目给出不同 RTT、并行 TCP 连接数量、对象大小、链路速率或服务器处理时间，应画时间线重新计算，不能机械套公式。特别是“并行非持久连接”会改变多个嵌入对象的等待关系。

</Callout>

### 31.3 DNS + HTTP 的总时间

若访问前还要解析域名，通常先计算 DNS：

$$
T_{DNS}=\sum RTT_{DNS}
$$

再加后续 TCP/HTTP 时间：

$$
T_{total}=T_{DNS}+T_{TCP/HTTP}+T_{tx}
$$

做题时顺序应是：

```text
DNS 得到服务器 IP
→ 建立 TCP（若需要）
→ 发送 HTTP 请求
→ 接收基础 HTML
→ 解析出嵌入对象 URL
→ 再请求嵌入对象
```

## 32. 全章核心协议对比

| 协议 | 功能 | 传输层 | 默认/常见服务器端口 | 最关键特征 |
| --- | --- | --- | ---: | --- |
| DNS | 域名解析 | UDP / TCP | 53 | 递归、迭代、缓存 |
| FTP | 文件传输 | TCP | 控制 21；主动数据传统 20 | 控制/数据连接分离 |
| SMTP | 发送、转发邮件 | TCP | 25 | Push |
| POP3 | 下载邮件 | TCP | 110 | Pull |
| IMAP | 邮箱同步管理 | TCP | 143 | 服务器端状态同步 |
| HTTP | Web 资源传输 | TCP（HTTP/1.x、HTTP/2） | 80 | 请求/响应、无状态 |
| HTTPS | 加密 Web 访问 | 典型 408 场景为 TLS/TCP | 443 | HTTP + TLS |

## 33. 高频易错点与做题判断框架

### 33.1 DNS

- 主机通常先问本地递归解析器，而不是自己逐级访问根/TLD/权威服务器；
- 根服务器通常返回下一层委派信息，不是普通主机最终 IP；
- 先看缓存，缓存命中会省掉后续查询；
- 递归与迭代的根本区别是“谁负责继续查”。

### 33.2 FTP

- FTP 不只一条 TCP 连接；
- 21 是控制连接服务器端口，不是普通文件数据传输端口；
- 主动/被动模式只看**数据连接的主动发起方**；
- 两种模式的控制连接都由客户端主动建立。

### 33.3 电子邮件

```text
SMTP：送 / 转发
POP3：下载
IMAP：服务器端同步管理
MIME：内容表示扩展
```

### 33.4 HTTP

- HTTP 无状态不等于网站不能登录；
- HTTP/1.0 默认非持久，HTTP/1.1 默认持久；
- 持久连接不等于流水线；
- 算页面时间前先判断 DNS、TCP、连接复用、并行/流水线和对象传输时间。

### 33.5 四步判断法

遇到应用层综合题，可按以下顺序：

1. **场景 → 协议**：域名解析/DNS，文件传输/FTP，发邮件/SMTP，取邮件/POP3 或 IMAP，网页/HTTP；
2. **协议 → TCP/UDP 与端口**；
3. **判断连接结构和主动方**：FTP 双连接、HTTP 是否持久、DNS 递归/迭代；
4. **画时间线**：把所有串行 RTT 与真正的数据传输时延加起来。

## 34. 一页速记

```text
【网络应用模型】
C/S：客户端主动，服务器通常长期运行并被动等待
P2P：节点既可请求也可提供资源

【DNS】
端口：53
主机 → 本地 DNS：常见递归
本地 DNS → 根/TLD/权威：常见迭代
根：给 TLD 委派
TLD：给权威 DNS 委派
权威 DNS：给权威资源记录
TTL：控制缓存有效期

【FTP】
TCP
控制连接：客户端 → 服务器 21，通常持续整个会话
数据连接：按需建立，传文件/目录
主动模式：服务器主动连客户端，传统服务器数据端口 20
被动模式：客户端主动连服务器协商出的数据端口

【电子邮件】
SMTP：TCP 25，发送/转发，Push
POP3：TCP 110，下载邮件
IMAP：TCP 143，服务器端同步管理
MIME：扩展正文/附件内容表示

【HTTP】
HTTP：80
HTTPS：443
HTTP 本身无状态
HTTP/1.0：默认非持久
HTTP/1.1：默认持久
持久 ≠ 流水线
Cookie：Set-Cookie / Cookie，用于跨请求关联状态

【时延】
DNS：串行查询 RTT 求和
非持久 HTTP 单对象：约 2RTT + 对象传输时间
总时间：DNS + TCP/HTTP + 数据传输
```
