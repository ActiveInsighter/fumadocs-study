## 6. TCP 滑动窗口

> **真题考察**
>
> * 选择题：2009 年第 38 题
> * 选择题：2011 年第 40 题
> * 选择题：2013 年第 39 题
> * 选择题：2021 年第 40 题
> * 选择题：2025 年第 38 题
> * 解答题：2016 年第 41 题
> * 解答题：2023 年第 47 题

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-004.svg" alt={"TCP 图 4"} />

如果 TCP 每发送一个报文段都必须等到 ACK 返回后才能发送下一个报文段，那么链路的大量时间都会浪费在等待中。

因此 TCP 使用**滑动窗口**，允许发送方在没有立即收到确认的情况下连续发送多个字节或多个报文段。

---

### 6.1 字节序列号

TCP 是**面向字节流**的。

可以把应用数据想象成一条连续字节流，每一个字节都对应一个序列号。

TCP 首部的 Sequence Number 为 32 位，因此序列号空间大小为：

$$
2^{32}
$$

到达最大值后会重新回绕。

---

### 6.2 逻辑绝对下标与 TCP 序列号

为了理解序列号回绕，可以人为引入一个不会回绕的“逻辑绝对下标”。

这只是教学中的抽象，不是 TCP 首部真实字段。

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-005.svg" alt={"TCP 图 5"} />

若某方向的初始序列号为 `ISN`，并令：

```text
absolute index = 0
```

表示第一个应用层数据字节，则：

$$
\text{seq}
=
(\text{ISN}+1+\text{absolute index})
\bmod 2^{32}
$$

例如：

```text
absolute index = 0 → seq = ISN + 1
absolute index = 1 → seq = ISN + 2
```

---

### 6.3 序列号回绕

由于 Sequence Number 只有 32 位，因此同一个序列号值理论上可以对应不同轮次的数据。

例如序列号 `100` 可能对应逻辑位置：

$$
100
$$

也可能对应：

$$
2^{32}+100
$$

甚至：

$$
2\times2^{32}+100
$$

接收方需要结合：

* 当前连接状态；
* 当前接收窗口的位置；
* 已经接收的数据范围；

判断一个序列号属于当前字节流中的哪一个位置。

可抽象理解为：

$$
\text{absolute index}
=
(\text{seq}-\text{ISN}-1)\bmod2^{32}
+k\cdot2^{32}
$$

其中选择适当的 `k`，使对应数据落在当前合理窗口附近。

> **理解即可：**
>
> 408 计算题通常直接围绕给定的序号、数据长度和 ACK 计算，不需要实现实际 TCP 的序列号展开算法。

## 7. 发送窗口与接收窗口

### 7.1 TCP 发送窗口

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-006.svg" alt={"TCP 图 6"} />

发送方字节流可抽象为四个区域：

| 区域 | 状态            |
| -- | ------------- |
| 1  | 已发送且已确认       |
| 2  | 已发送但未确认       |
| 3  | 当前允许发送但还未发送   |
| 4  | 当前窗口之外，暂时不能发送 |

其中：

> **第 2 部分 + 第 3 部分构成发送窗口。**

当收到新的累计 ACK 后：

1. 窗口左边界向右移动；
2. 已确认数据离开窗口；
3. 窗口右侧出现新的可发送空间；
4. 发送方继续发送后续数据。

---

### 7.2 TCP 接收窗口

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-007.svg" alt={"TCP 图 7"} />

接收方可以把数据范围理解为：

| 区域 | 状态              |
| -- | --------------- |
| 1  | 已经被应用程序读取       |
| 2  | TCP 已接收，但应用还未读取 |
| 3  | 当前允许接收但尚未到达     |
| 4  | 超出当前接收窗口        |

接收方会根据：

* 接收缓冲区大小；
* 已缓存的数据量；
* 应用程序读取速度；

动态调整 `rwnd`。

---

## 8. `swnd`、`rwnd` 与 `cwnd`

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-008.svg" alt={"TCP 图 8"} />

这是本章最容易混淆的一组概念。

### 8.1 接收窗口 `rwnd`

`rwnd`：

* 由**接收方**维护；
* 反映接收缓冲区还能容纳多少数据；
* 通过 TCP 首部 Window 字段通知发送方；
* 用于**流量控制**。

它主要回答：

> **接收方还能吃下多少数据？**

---

### 8.2 拥塞窗口 `cwnd`

`cwnd`：

* 由**发送方**维护；
* 不直接出现在 TCP 首部；
* 根据 ACK、重复 ACK、超时等网络反馈动态变化；
* 用于**拥塞控制**。

它主要回答：

> **当前网络大概还能承受多少未确认数据？**

---

### 8.3 实际发送窗口 `swnd`

在经典教材模型中，发送方能够实际使用的发送窗口受 `rwnd` 和 `cwnd` 共同限制：

$$
\text{swnd}
=
\min(\text{rwnd},\text{cwnd})
$$

因此：

* `rwnd` 小：受接收方处理能力限制；
* `cwnd` 小：受网络拥塞限制。

> **高频题一句话：**
>
> **流量控制看 `rwnd`，拥塞控制看 `cwnd`，实际发送看二者较小值。**

## 9. TCP 窗口滑动过程

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-009.svg" alt={"TCP 图 9"} />

假设发送窗口为：

```text
[左边界, 右边界)
```

发送方可以连续发送窗口中的数据。

当接收方成功收到连续字节后，会返回累计 ACK。

例如收到：

```text
ACK = 5000
```

表示：

> 序列号 5000 之前的连续字节都已经正确收到，下一步希望收到字节 5000。

发送方收到该 ACK 后：

1. 把已经确认的数据移出发送窗口；
2. 把窗口左边界移动到新的确认位置；
3. 若窗口大小允许，则右边界相应向前移动；
4. 新进入窗口的数据可以继续发送。

因此滑动窗口本质上是：

> **ACK 推动发送窗口向前移动。**

## 10. TCP 流量控制

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-010.svg" alt={"TCP 图 10"} />

流量控制解决的问题是：

> **防止发送方发送得太快，使接收方缓冲区溢出。**

假设发送方网络速度很快，而接收应用读取数据很慢。

如果没有流量控制：

1. TCP 数据不断到达；
2. 接收缓冲区逐渐填满；
3. 最终没有空间存放新数据。

因此接收方需要通过 `rwnd` 告诉发送方：

> “我现在还能接收多少字节。”

---

### 10.1 接收方通告窗口

接收方根据剩余缓冲空间确定 `rwnd`，并通过 ACK 中的 Window 字段告知发送方。

发送方必须使未确认数据受到该窗口限制。

---

### 10.2 窗口动态变化

当应用程序不断从接收缓冲区读取数据时，缓冲区空闲空间重新增大。

接收方可以在后续报文段中通告更大的 `rwnd`。

发送方于是能够继续增加发送的数据。

---

### 10.3 零窗口

如果接收缓冲区完全没有可用空间，接收方可以通告：

$$
rwnd=0
$$

发送方此时应停止发送普通新数据。

但这里存在一个问题：

如果接收方后来缓冲区恢复，并发送新的非零窗口通告，而这个通告恰好丢失，则：

* 接收方等待发送方发送；
* 发送方仍认为窗口为 0；

双方可能永久等待。

TCP 因此使用**持续计时器（persist timer）**&#x2060;以及**零窗口探测**机制，周期性探测接收方窗口是否已经重新打开。

---

## 11. TCP 可靠传输机制

TCP 运行在 IP 提供的尽力而为服务之上，而 IP 网络可能出现：

* 数据丢失；
* ACK 丢失；
* 报文乱序；
* 报文重复；
* 比特错误；
* RTT 大幅波动。

TCP 需要在此基础上为应用提供可靠字节流。

核心手段可以概括为：

> **序号 + 确认 + 校验 + 重传 + 窗口。**

---

## 12. TCP 序列号与确认号

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-011.svg" alt={"TCP 图 11"} />

### 12.1 序列号

如果 TCP 报文段：

```text
seq = S
```

并携带 `L` 字节数据，则其字节范围为：

$$
S\sim S+L-1
$$

若这些数据全部连续收到，则接收方下一步期望：

$$
S+L
$$

因此 ACK 通常为：

$$
ACK=S+L
$$

---

### 12.2 累计确认

TCP 的确认号表示：

> **下一个期望收到的字节序号。**

所以：

```text
ACK = N
```

意味着：

> 所有序号小于 `N` 的连续字节都已经成功收到。

不是只确认序号为 `N-1` 的一个报文段。

---

### 12.3 数据段丢失

假设：

```text
1 → 到达
2 → 丢失
3 → 到达
4 → 到达
```

接收端发现 2 没到，即使后面的 3、4 已经到达，其累计 ACK 仍然无法越过缺口。

因此会不断返回相同确认号。

---

### 12.4 数据乱序

后续数据提前到达时，接收端可以缓存乱序数据，但累计 ACK 仍然指向第一个缺失字节。

因此重复 ACK 可以向发送方传递一个重要信息：

> **后面的数据能到，前面某一段可能丢了。**

---

### 12.5 数据按序到达

如果缺口被补上，而且后续缓存数据也已经连续，则累计 ACK 可以一次向前推进较大距离。

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-012.svg" alt={"TCP 图 12"} />

可以总结成：

| 接收情况        | ACK 行为   | 发送方可能采取的动作 |
| ----------- | -------- | ---------- |
| 数据完全没到      | ACK 无法前进 | 最终可能超时重传   |
| 后续数据到了，前面缺失 | 重复相同 ACK | 可能触发快速重传   |
| 数据连续到达      | ACK 向前推进 | 正常继续发送     |

---

## 13. TCP 超时重传

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-013.svg" alt={"TCP 图 13"} />

发送方发送数据后，会为尚未确认的数据维护重传相关计时。

如果在 RTO（Retransmission Timeout，重传超时时间）内没有获得需要的确认，则认为相应数据可能已经丢失，并进行重传。

超时可能由多种情况造成：

* 数据报文段丢失；
* ACK 丢失；
* 网络时延突然显著增加。

---

### 13.1 TCP 与 GBN、SR 的关系

从思想上看，TCP 与数据链路层的滑动窗口协议存在相似之处。

TCP 使用：

* 滑动窗口；
* 累计确认；

与 GBN 有一定相似性。

另一方面，实际 TCP 又可以：

* 缓存乱序数据；
* 快速重传缺失报文；
* 使用 SACK 精确描述已经接收的区间；

因此又具有一定的选择性重传思想。

不能简单认为：

> TCP 就等于 GBN 或 TCP 就等于 SR。

TCP 有自己独立的可靠传输机制。

可结合：

* [回退 N 帧](/docs/408/knowledge2/computer_network/03-data-link-layer/01-framing-error-arq/)
* [选择性重传](/docs/408/knowledge2/computer_network/03-data-link-layer/01-framing-error-arq/)

进行对比。

## 14. RTO 的确定

> **了解为主。**

RTO 不能设置得太短，否则正常但稍有延迟的数据可能被误判为丢失。

也不能设置得太长，否则真正丢包后需要等待很久才能重传。

TCP 因此根据测得的 RTT 动态估计 RTO。

常见计算模型为：

$$
\text{EstimatedRTT}
=
(1-\alpha)\text{EstimatedRTT}
+
\alpha\text{SampleRTT}
$$

$$
\text{DevRTT}
=
(1-\beta)\text{DevRTT}
+
\beta
\left|
\text{SampleRTT}-\text{EstimatedRTT}
\right|
$$

$$
\text{RTO}
=
\text{EstimatedRTT}
+
4\text{DevRTT}
$$

典型参数为：

$$
\alpha=0.125
$$

$$
\beta=0.25
$$

其中：

* `SampleRTT`：某次实际测得的 RTT；
* `EstimatedRTT`：RTT 的平滑估计值；
* `DevRTT`：RTT 波动程度。

可以直观理解为：

> **RTO = 平均 RTT + 对网络抖动预留的安全余量。**

## 15. TCP 校验和

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-015.svg" alt={"TCP 图 15"} />

TCP 也使用 16 位反码校验和。

其计算范围包括：

* TCP 伪首部；
* TCP 首部；
* TCP 数据。

这一点与 IPv4 首部校验和不同。

IPv4 首部校验和只保护：

> **IPv4 首部本身。**

而 TCP 校验和还要保护运输层数据。

可结合 [IP 首部校验和](/docs/408/knowledge2/computer_network/04-network-layer/01-ipv4-cidr-fragmentation/) 复习。

> **易错点：**
>
> 接收端发现 TCP 校验和错误时，会丢弃该报文段。
> 接收端不是发送一个专门的“请重传”TCP 命令；发送端随后可能由于 ACK 没有推进、重复 ACK 或超时等机制完成重传。
