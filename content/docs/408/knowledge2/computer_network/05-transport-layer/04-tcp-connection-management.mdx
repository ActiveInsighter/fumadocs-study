TCP 是面向连接的协议。连接管理题的核心不是背“3 次、4 次”，而是同时追踪：

```text
控制位 + seq + ack + 状态
```

> **真题标签**
>
> 三次握手：2011 年第 39 题、2019 年第 39 题、2020 年第 39 题、2024 年第 38 题、2016 年第 41 题、2026 年第 47 题。
>
> 四次挥手：2020 年第 39 题、2021 年第 38 题、2022 年第 39 题、2024 年第 38 题、2023 年第 47 题、2026 年第 47 题。

## 5.4.1 三次握手

设客户端初始序列号为 `x`，服务端初始序列号为 `y`。

### 第 1 次：客户端发 SYN

```text
SYN = 1
seq = x
```

状态：

```text
CLOSED → SYN-SENT
```

### 第 2 次：服务端发 SYN + ACK

```text
SYN = 1
ACK = 1
seq = y
ack = x + 1
```

状态：

```text
LISTEN → SYN-RECEIVED
```

### 第 3 次：客户端发 ACK

```text
ACK = 1
seq = x + 1
ack = y + 1
```

客户端进入 `ESTABLISHED`；服务端收到后也进入 `ESTABLISHED`。

用图压缩：

```text
Client                           Server
  | --- SYN, seq=x ------------> |
  | <--- SYN+ACK, seq=y, ack=x+1 |
  | --- ACK, ack=y+1 ----------> |
```

## 5.4.2 为什么 SYN 占一个序列号

SYN 虽通常不携带普通应用数据，但在 TCP 序列空间中消耗 1 个序号。

因此客户端第一个普通数据字节从：

$$
x+1
$$

开始；服务端同理从 `y+1` 开始。

FIN 也消耗 1 个序号，而不携带数据、SYN、FIN 的纯 ACK 通常不额外消耗序号。

## 5.4.3 ISN：双方各自选择初始序列号

ISN（Initial Sequence Number）由连接两端分别选择：客户端的 `x` 与服务端的 `y` 彼此独立。实际 TCP 会让 ISN 随时间变化且不容易被简单预测，以降低旧连接残留报文与新连接混淆、以及序列号猜测的风险。

408 题目通常直接给出 ISN，只需按“`SYN` 消耗 1 个序号”继续计算。

## 5.4.4 为什么需要三次而不是两次

三次握手最终让双方确认：

1. 双向通信能力可用；
2. 对端已经收到本方的连接请求/响应；
3. 双方初始序列号已经同步。

若只进行两次，历史延迟到达的旧 SYN 可能导致服务端错误建立“半开”的新连接。第三次握手使服务端确认客户端确实收到了**本次** SYN+ACK。

## 5.4.5 第三次握手可以携带数据吗

可以。若第三次报文携带数据，客户端第一个数据字节仍从：

$$
x+1
$$

开始。

考试若明确给第三次握手的数据长度，应把这些数据计入后续序号；若题目没有说明，一般按纯 ACK 处理。

## 5.4.6 四次挥手

TCP 是全双工，两方向需要分别关闭。设主动关闭方为 A，被动关闭方为 B。

### 第 1 次：A 发 FIN

```text
FIN = 1
seq = u
```

```text
ESTABLISHED → FIN-WAIT-1
```

### 第 2 次：B 确认 A 的 FIN

```text
ACK = 1
ack = u + 1
```

```text
B: ESTABLISHED → CLOSE-WAIT
A: FIN-WAIT-1 → FIN-WAIT-2
```

此时只是 **A → B** 的数据方向关闭，B 仍可继续发送数据。

### 第 3 次：B 发 FIN

当 B 也发送完数据：

```text
FIN = 1
ACK = 1
seq = w
ack = u + 1
```

```text
CLOSE-WAIT → LAST-ACK
```

### 第 4 次：A 确认 B 的 FIN

```text
ACK = 1
ack = w + 1
```

A 进入 `TIME-WAIT`，B 收到后进入 `CLOSED`。

```text
A                                B
| --- FIN ---------------------> |
| <--- ACK --------------------- |
| <--- FIN --------------------- |
| --- ACK ---------------------> |
|      TIME-WAIT                 |
```

## 5.4.7 为什么通常是四次挥手

收到对方 FIN 只说明：

> 对方已经没有数据再发给我。

但本方应用可能还有数据未发送完，所以对 FIN 的 ACK 往往必须先发，自己的 FIN 要等应用完成后再发。

因此常见为：

```text
FIN → ACK → FIN → ACK
```

而建连时服务端可把自己的 SYN 与对客户端 SYN 的 ACK 合并，所以是三次。

## 5.4.8 TIME-WAIT 与 2MSL

主动关闭方发送最后 ACK 后一般等待：

$$
2MSL
$$

再进入 `CLOSED`。

其中 MSL 是 Maximum Segment Lifetime。

等待的两大目的：

1. **可靠处理最后 ACK 丢失**：若对端重传 FIN，主动关闭方还能再次发送 ACK；
2. **让旧连接报文消失**：避免同一四元组的新连接被旧报文干扰。

<Callout type="warn" title="主动关闭方不一定是客户端">
连接可以由任意一方主动释放。考试图中不要把 `TIME-WAIT` 永远固定画在“客户端”。
</Callout>

## 5.4.9 连接管理计算模板

按这三条几乎可以完成所有序号题：

$$
\text{数据 }L\text{ B}\Rightarrow\text{消耗 }L\text{ 个序号}
$$

$$
SYN\Rightarrow+1
$$

$$
FIN\Rightarrow+1
$$

纯 ACK 通常 `+0`。

例如最后数据字节序号为 `3000`，紧接着发送 FIN，则 FIN 的序号通常是 `3001`，对端确认号为：

$$
3002
$$

## 5.4.10 高频状态速记

```text
主动建连：CLOSED → SYN-SENT → ESTABLISHED
被动建连：LISTEN → SYN-RECEIVED → ESTABLISHED

主动关闭：ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2
         → TIME-WAIT → CLOSED

被动关闭：ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED
```
