运输层位于应用层和网络层之间，运行在**通信的端系统**中。网络层解决的是**主机到主机**的通信，而运输层进一步把通信对象细化到主机中的**应用进程**，因此运输层提供的是**进程到进程的逻辑通信**。

本章是计算机网络中综合性最强、408 考查频率最高的章节之一。复习时应建立如下主线：

> **端口定位进程 → UDP/TCP 提供不同运输服务 → TCP 建立连接 → 序号与确认号实现可靠传输 → 滑动窗口实现流水线传输和流量控制 → 拥塞窗口控制注入网络的数据量。**

| 内容       | 408 复习重点                        |
| -------- | ------------------------------- |
| 运输层基本功能  | 进程到进程通信、端口、复用与分用                |
| UDP      | 首部、校验和、特点、适用场景                  |
| TCP 首部   | 序列号、确认号、窗口、控制位                  |
| TCP 连接管理 | 三次握手、四次挥手、状态变化、序号变化             |
| TCP 可靠传输 | 累计确认、超时重传、快速重传、校验和              |
| TCP 流量控制 | `rwnd`、滑动窗口、零窗口                 |
| TCP 拥塞控制 | `cwnd`、`ssthresh`、慢开始、拥塞避免、快速恢复 |

> **高频易混：**
>
> * `rwnd`：解决**接收方来不及接收**的问题，属于流量控制。
> * `cwnd`：解决**网络来不及转发**的问题，属于拥塞控制。
> * 实际发送窗口通常受二者共同限制。

### 1. 运输层基本功能

#### 1.1 主机到主机与进程到进程

IP 协议能够把数据报从一台主机送到另一台主机，但一台主机中可能同时运行浏览器、邮件客户端、DNS 程序等多个应用。

因此，仅知道目的 IP 地址还不够，还必须知道：

> **数据究竟应该交给目的主机中的哪个应用进程？**

运输层通过**端口号**解决这个问题。

可以把网络通信理解为：

$$
\text{源进程}
\rightarrow
\text{源端口}
\rightarrow
\text{IP 网络}
\rightarrow
\text{目的端口}
\rightarrow
\text{目的进程}
$$

因此：

* **IP 地址**标识主机或网络接口；
* **端口号**标识主机中的通信端点；
* IP 地址与端口号共同确定网络通信的一端。

#### 1.2 端口号

TCP 和 UDP 的端口号均为 **16 位**，因此端口号范围为：

$$
0\sim 2^{16}-1=65535
$$

发送方运输层首部中通常同时包含：

* **源端口号**：标识发送进程；
* **目的端口号**：标识接收进程。

> **易错点：**
>
> 端口不是一个物理接口，也不是应用进程本身，而是运输层用来识别通信进程的逻辑标识。

#### 1.3 复用与分用

**复用（multiplexing）**发生在发送端。

多个应用进程的数据都可以交给运输层，由 TCP 或 UDP 添加运输层首部后，再统一交给网络层。

**分用（demultiplexing）**发生在接收端。

运输层收到 IP 数据报中的 TCP 报文段或 UDP 用户数据报后，根据运输层首部中的端口等信息，把数据交给正确的应用进程。

可以记为：

> **发送端：多进程 → 一个网络层，叫复用。**
> **接收端：一个网络层 → 多进程，叫分用。**

### 2.1 UDP 数据报

UDP（User Datagram Protocol，用户数据报协议）提供一种**无连接、面向报文**的运输层服务。

<InlineSvg src="/images/computer-network/computer-network-transport-udp-001.svg" alt={"UDP 图 1"} />

UDP 首部长度固定为 **8 字节**，包含 4 个字段，每个字段均为 16 位。

| 字段   |     长度 | 含义               |
| ---- | -----: | ---------------- |
| 源端口  | 16 bit | 标识发送方应用进程        |
| 目的端口 | 16 bit | 标识接收方应用进程        |
| 长度   | 16 bit | UDP 首部与数据的总长度    |
| 校验和  | 16 bit | 检测 UDP 数据报是否出现差错 |

由于 UDP 首部固定为 8 字节，因此 UDP 长度字段至少为：

$$
8\text{ B}
$$

#### 目的端口与分用

当目的主机的 IP 层把 UDP 用户数据报交给运输层后，UDP 根据**目的端口号**找到对应的应用进程。

<InlineSvg src="/images/computer-network/computer-network-transport-udp-002.svg" alt={"UDP 图 2"} />

如果目的端口对应的应用进程不存在：

1. 接收端丢弃该 UDP 数据报；
2. 通常由 ICMP 向发送方返回**端口不可达**差错报文。

> **易错点：**
>
> “端口不可达”不是 UDP 自己返回的 UDP 报文，而是由网络层的 **ICMP** 报告。

---

### 2.2 UDP 校验和

UDP 校验和用于检测数据在传输过程中是否发生比特错误。

UDP 校验的范围不仅包括：

* UDP 首部；
* UDP 数据；

还包含一个只参与校验计算、**并不会实际作为 UDP 数据报的一部分发送**的**伪首部**。

#### 2.2.1 UDP 伪首部

<InlineSvg src="/images/computer-network/computer-network-transport-udp-003.svg" alt={"UDP 图 3"} />

IPv4 UDP 伪首部主要包含：

| 字段       |     长度 |
| -------- | -----: |
| 源 IP 地址  | 32 bit |
| 目的 IP 地址 | 32 bit |
| 全 0 字段   |  8 bit |
| 协议号      |  8 bit |
| UDP 长度   | 16 bit |

其中 UDP 的 IP 协议号为：

$$
17
$$

伪首部的作用是让 UDP 校验和同时检查关键的 IP 层信息，降低数据被错误交付给错误主机或错误协议的风险。

> **注意：**
>
> 伪首部只参与校验和计算，并不会作为 UDP 数据报首部真正发送。

---

### 2.3 UDP 校验和的发送端计算

发送端计算 UDP 校验和时，可按以下顺序理解。

#### 第一步：校验和字段暂时置 0

计算前，将 UDP 首部中的 Checksum 字段置为 0。

#### 第二步：拼接校验内容

参与计算的数据依次包括：

1. 伪首部；
2. UDP 首部；
3. UDP 数据。

如果总字节数为奇数，需要在最后补一个全 0 字节，使其能够按 16 位分组。

这个补 0：

> **仅用于计算校验和，不属于实际传输的数据。**

#### 第三步：按 16 位分组求反码和

把全部数据按 16 位划分。

所有 16 位字相加时，如果最高位产生进位，要把进位重新加到低 16 位，这称为**回卷进位**。

例如：

$$
1\,0000\,0000\,0000\,0001
$$

低 16 位为：

$$
0000\,0000\,0000\,0001
$$

再把最高位进位 `1` 加回来，得到：

$$
0000\,0000\,0000\,0010
$$

#### 第四步：按位取反

对最终得到的 16 位结果逐位取反，即得到 UDP 校验和。

若计算得到的校验和值恰好为全 0，在 IPv4 UDP 中实际发送时使用全 1，以避免和“未使用 UDP 校验和”的全 0 字段混淆。

---

### 2.4 UDP 校验和的接收端验证

接收方收到 UDP 数据报后：

1. 根据收到的 IP 首部重新构造伪首部；
2. 将伪首部、UDP 首部、UDP 数据以及收到的校验和共同按 16 位分组；
3. 进行反码加法并处理回卷进位。

如果传输无误，最终结果应为：

$$
1111\,1111\,1111\,1111
$$

即全 1。

如果结果不是全 1，则说明数据报检测到差错，应当丢弃。

UDP 本身：

> **只负责检错，不负责差错恢复和重传。**

#### IPv4 与 IPv6 的区别

在 IPv4 中，UDP 校验和字段可以为全 0，表示发送端没有启用 UDP 校验和。

IPv6 中通常要求 UDP 校验和必须使用，因此不能简单按 IPv4 的规则把校验和置 0。

---

### 2.5 UDP 校验和实例

假设：

* 源 IP：192.168.1.1；
* 目的 IP：192.168.1.2；
* 源端口：1024；
* 目的端口：2048；
* 数据：`0x48 0x65 0x6C`，即 3 字节的 `"Hel"`。

UDP 长度为：

$$
8+3=11\text{ B}
$$

由于数据部分为奇数字节，需要在校验计算时在末尾补一个 `0x00`。

<InlineSvg src="/images/computer-network/computer-network-transport-udp-004.svg" alt={"UDP 图 4"} />

对应的 16 位字为：

$$
\begin{aligned}
&\texttt{C0A8},\ \texttt{0101},\ \texttt{C0A8},\ \texttt{0102},\\
&\texttt{0011},\ \texttt{000B},\\
&\texttt{0400},\ \texttt{0800},\ \texttt{000B},\ \texttt{0000},\\
&\texttt{4865},\ \texttt{6C00}
\end{aligned}
$$

进行 16 位反码求和并最终取反后，得到校验和：

$$
\boxed{\texttt{0xBC1E}}
$$

接收方把所有字段连同 `0xBC1E` 一起进行反码加法，若数据未损坏，最终结果应为：

$$
\texttt{0xFFFF}
$$

> **计算题易错：**
>
> 1. 忘记伪首部；
> 2. 奇数字节忘记末尾补 0；
> 3. UDP 长度包含首部；
> 4. 加法溢出后忘记回卷；
> 5. 最后忘记逐位取反。

---

### 2.6 UDP 的特点

#### 无连接

UDP 在发送数据之前不需要建立运输层连接，也没有 TCP 的三次握手和四次挥手。

因此通信开销较小。

#### 面向报文

应用层交给 UDP 一个报文，UDP 原则上就把这个报文作为一个完整的数据单位处理。

UDP 不像 TCP 那样把应用数据抽象成连续字节流。

#### 不保证可靠交付

UDP 本身不保证：

* 数据一定到达；
* 数据只到达一次；
* 数据按发送顺序到达；
* 丢失的数据能够自动重传。

校验错误的数据报通常被直接丢弃。

#### 首部开销小

UDP 首部只有：

$$
8\text{ B}
$$

而普通 TCP 首部至少为：

$$
20\text{ B}
$$

因此 UDP 的协议控制开销较低。

#### 支持一对多通信

UDP 可以方便地用于广播和多播场景，而 TCP 本质上是点到点连接。

---

### 2.7 UDP 的典型应用

UDP 常用于一次交互数据量较少、希望减少连接建立开销的协议，例如：

* DNS；
* SNMP。

UDP 也常作为低时延协议或应用自定义运输机制的基础，例如：

* 实时音视频；
* 在线游戏；
* QUIC。

采用 UDP 并不意味着应用一定“不可靠”。

应用层完全可以在 UDP 之上自行设计：

* 确认；
* 重传；
* 排序；
* 拥塞控制；
* 前向纠错。

例如 HTTP/3 所使用的 QUIC，就是建立在 UDP 之上、但自行实现可靠传输和拥塞控制等机制的协议。

> **核心理解：**
>
> UDP 提供的是“简单的运输服务”，而不是强迫应用“不可靠”。

## 3. TCP

> **复习优先级：高。**
>
> TCP 是本章核心。必须把**首部 → 建连 → 序号与 ACK → 滑动窗口 → 可靠传输 → 流量控制 → 拥塞控制 → 释放连接**串成一个完整过程。

### 3.1 TCP 的基本特点

TCP（Transmission Control Protocol）主要具有以下特点。

#### 面向连接

发送数据前必须建立 TCP 连接。

正常结束通信时，还要释放连接。

#### 可靠传输

TCP 综合使用：

* 校验和；
* 序列号；
* 确认；
* 重传；
* 滑动窗口；
* 接收端缓存和重排；

为应用程序提供可靠、有序、无重复的字节流。

#### 面向字节流

TCP 不保留应用层报文之间天然的消息边界。

应用层连续交给 TCP 的数据，在 TCP 看来是一串连续字节。

#### 全双工

TCP 连接建立后，双方都可以同时发送和接收数据。

因此一个 TCP 连接实际上包含两个相反方向的数据流。

#### 点到点

一条 TCP 连接只有两个端点，不用于广播和多播。

---

### 3.2 TCP 首部

> **真题考察**
>
> * 选择题：2021 年第 39 题
> * 解答题：2012 年第 47 题

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-001.svg" alt={"TCP 图 1"} />

普通 TCP 首部最小长度为：

$$
20\text{ B}
$$

若带有选项，首部最长可以达到：

$$
60\text{ B}
$$

#### 源端口与目的端口

源端口和目的端口均为 16 位，用于实现运输层的复用与分用。

#### 序列号 Sequence Number

长度为 32 位。

如果 TCP 报文段携带数据，则序列号表示：

> **该报文段数据部分第一个字节的序列号。**

如果某 TCP 报文段：

* `seq = 1000`；
* 数据长度为 500 B；

那么该报文段携带的字节序号范围为：

$$
1000\sim1499
$$

下一个连续数据段的序列号应为：

$$
1500
$$

#### 确认号 Acknowledgment Number

长度为 32 位。

ACK 有效时，确认号表示：

> **下一次希望收到的数据字节序号。**

因此：

$$
ACK=N
$$

表示：

$$
N
$$

之前的所有连续字节都已经正确收到，下一步期待序号为 `N` 的字节。

这就是 TCP 的**累计确认**。

#### 首部长度

首部长度字段为 4 位，单位是 **32 位字**。

若其值为 5，则 TCP 首部长度为：

$$
5\times4=20\text{ B}
$$

#### 控制位

408 中重点掌握以下 6 个控制位。

| 控制位 | 含义           |
| --- | ------------ |
| URG | 紧急指针有效       |
| ACK | 确认号字段有效      |
| PSH | 尽快向应用层交付数据   |
| RST | 复位连接         |
| SYN | 建立连接、同步初始序列号 |
| FIN | 释放一个方向上的连接   |

其中最重要的是：

> **SYN 建连接，FIN 释放连接，ACK 表示确认号有效。**

#### 窗口字段

窗口字段为 16 位。

报文段发送方利用该字段向对方通告自己的：

> **接收窗口 `rwnd`。**

因此 TCP 首部的 Window 字段是**流量控制信息**，不是 `cwnd`。

> **高频陷阱：**
>
> TCP 报文首部中没有一个直接叫“拥塞窗口”的字段。
> `cwnd` 是发送方 TCP 内部根据网络情况维护的状态变量。

#### 校验和

TCP 校验和用于校验：

* TCP 首部；
* TCP 数据；
* IP 伪首部。

#### 紧急指针

仅当 `URG=1` 时有意义，用于配合紧急数据机制。

#### 选项

常见 TCP 选项包括：

* MSS；
  -窗口扩大因子；
  -时间戳；
  -SACK 相关选项。

TCP 选项最长可占 40 B。

## 4. TCP 连接建立：三次握手

> **真题考察**
>
> * 选择题：2011 年第 39 题
> * 选择题：2019 年第 39 题
> * 选择题：2020 年第 39 题
> * 选择题：2024 年第 38 题
> * 解答题：2016 年第 41 题
> * 解答题：2026 年第 47 题

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-002.svg" alt={"TCP 图 2"} />

假设：

* 客户端初始序列号为 `x`；
* 服务端初始序列号为 `y`。

### 4.1 第一次握手

客户端发送：

```text
SYN = 1
seq = x
```

客户端状态：

```text
CLOSED → SYN-SENT
```

服务端此时通常处于：

```text
LISTEN
```

客户端的意思是：

> “我要建立连接，我的初始序列号是 x。”

---

### 4.2 第二次握手

服务端收到 SYN 后发送：

```text
SYN = 1
ACK = 1
seq = y
ack = x + 1
```

服务端状态：

```text
LISTEN → SYN-RECEIVED
```

其中：

```text
ack = x + 1
```

表示客户端发来的 SYN 已被接收。

同时服务端利用自己的 SYN 告诉客户端：

> “我的初始序列号是 y。”

---

### 4.3 第三次握手

客户端收到服务端的 SYN + ACK 后发送：

```text
ACK = 1
seq = x + 1
ack = y + 1
```

客户端进入：

```text
ESTABLISHED
```

服务端收到第三次握手后，也进入：

```text
ESTABLISHED
```

TCP 连接建立完成。

---

### 4.4 为什么 SYN 要占用一个序列号

SYN 本身虽然通常不携带普通应用数据，但在 TCP 序列空间中会消耗一个序列号。

因此若客户端的初始 SYN：

```text
seq = x
```

那么客户端第一个应用层数据字节的序列号就是：

$$
(x+1)\bmod 2^{32}
$$

服务端同理：

$$
(y+1)\bmod 2^{32}
$$

FIN 同样会占用一个序列号。

而一个**不携带数据的普通 ACK**通常不会额外消耗序列号。

---

### 4.5 ISN：初始序列号

ISN（Initial Sequence Number）表示建立连接时某一方选择的初始序列号。

客户端和服务端：

> **各自独立选择自己的 ISN。**

实际 TCP 实现不会简单地每次从固定序列号开始，而会产生随时间变化、较难预测的 ISN，以：

* 降低旧连接残留报文与新连接混淆的风险；
* 提高对序列号猜测攻击的抵抗能力。

---

### 4.6 三次握手解决了什么问题

三次握手的核心不是单纯“多发一次确认”，而是使双方确认：

1. 对方能够收到自己的报文；
2. 自己能够收到对方的报文；
3. 双方的初始序列号已经同步。

最终双方都掌握：

```text
客户端 ISN = x
服务端 ISN = y
```

从而可以建立后续的可靠字节流。

---

### 4.7 为什么不能只握手两次

如果只有两次握手，服务端在收到一个过期的旧 SYN 后，就可能误认为客户端正在建立新连接并分配资源。

第三次握手允许服务端确认：

> 客户端确实收到了服务端针对**当前这次连接请求**发送的 SYN + ACK。

因此可以进一步避免历史重复连接请求导致的异常连接建立。

---

### 4.8 第三次握手能否携带数据

可以。

第三次握手本质上是 ACK 报文段，TCP 协议允许它携带数据。

如果客户端 SYN 的序列号为 `x`，则第三次握手中第一个数据字节的序列号从：

$$
x+1
$$

开始。

不过常见实现中：

* 第三次握手通常是纯 ACK；
* 应用数据紧接着在后续 TCP 报文段中发送。

---

## 5. TCP 连接释放：四次挥手

> **真题考察**
>
> * 选择题：2020 年第 39 题
> * 选择题：2021 年第 38 题
> * 选择题：2022 年第 39 题
> * 选择题：2024 年第 38 题
> * 解答题：2023 年第 47 题
> * 解答题：2026 年第 47 题

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-003.svg" alt={"TCP 图 3"} />

TCP 是全双工连接，因此：

> **两个方向的数据流需要分别关闭。**

以下把主动关闭的一方称为 A，被动关闭的一方称为 B。

---

### 5.1 第一次挥手

A 发送：

```text
FIN = 1
seq = u
```

A 状态：

```text
ESTABLISHED → FIN-WAIT-1
```

含义是：

> A 已经没有数据需要发送给 B。

但 A 此时仍然可以继续接收 B 发来的数据。

---

### 5.2 第二次挥手

B 收到 FIN 后立即确认：

```text
ACK = 1
ack = u + 1
```

B 状态：

```text
ESTABLISHED → CLOSE-WAIT
```

A 收到 ACK 后：

```text
FIN-WAIT-1 → FIN-WAIT-2
```

此时：

> A → B 的方向已经关闭，但 B → A 的方向仍然可以继续传输数据。

---

### 5.3 第三次挥手

当 B 的应用进程也已经没有数据需要发送时，B 发送 FIN。

例如：

```text
FIN = 1
ACK = 1
seq = w
ack = u + 1
```

B 状态：

```text
CLOSE-WAIT → LAST-ACK
```

---

### 5.4 第四次挥手

A 收到 B 的 FIN 后发送确认：

```text
ACK = 1
ack = w + 1
```

随后 A 进入：

```text
TIME-WAIT
```

B 收到最后的 ACK 后：

```text
LAST-ACK → CLOSED
```

A 需要等待：

$$
2\times MSL
$$

后才能进入：

```text
CLOSED
```

---

### 5.5 MSL 与 TIME-WAIT

MSL（Maximum Segment Lifetime）表示：

> **一个 TCP 报文段在网络中可能存在的最长时间。**

主动关闭方在最后一个 ACK 发出后继续等待：

$$
2MSL
$$

主要有两个原因。

#### 原因一：保证最后一个 ACK 可以重新发送

如果第四次挥手的 ACK 丢失：

1. B 没有收到 ACK；
2. B 会重新发送 FIN；
3. A 若仍处于 TIME-WAIT，就可以再次发送 ACK。

如果 A 立即 CLOSED，则无法可靠处理这个重传 FIN。

#### 原因二：让旧连接的残留报文全部消失

等待足够长时间，可以让旧连接中可能滞留在网络中的报文全部失效，降低其干扰后续同一四元组新连接的风险。

---

### 5.6 第一次挥手一定由客户端发起吗

不是。

建立连接时通常由客户端主动发起，因此经常习惯性地画成“客户端主动关闭”。

实际上：

> **任何一方都可以主动关闭 TCP 连接。**

所以考试中更准确的称呼是：

* 主动关闭方；
* 被动关闭方。

而不是把它们固定理解为客户端和服务器。

---

### 5.7 为什么握手三次而挥手通常四次

#### 建立连接时

服务端收到客户端 SYN 后，可以把：

* 对客户端 SYN 的 ACK；
* 自己的 SYN；

合并在同一个报文段中。

于是：

```text
SYN
SYN + ACK
ACK
```

共三次。

#### 释放连接时

收到对方 FIN，只代表：

> 对方已经没有数据要发送。

但自己可能仍然有尚未发送完成的数据。

因此接收 FIN 后通常先立即发送 ACK，等本方数据发送完成后再独立发送 FIN。

于是：

```text
FIN
ACK
FIN
ACK
```

通常需要四次。

> **核心记忆：**
>
> 建连时 **SYN 与 ACK 可以合并**；
> 释放连接时 **ACK 与 FIN 不一定能立即合并**。
