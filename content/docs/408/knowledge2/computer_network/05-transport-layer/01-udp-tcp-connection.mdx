运输层位于应用层与网络层之间，运行在**端系统**中。网络层负责把分组送到目的主机，运输层进一步把数据交给目的主机中的正确应用进程，因此其核心任务是提供**进程到进程的逻辑通信**。

整章可以沿着一条主线复习：

```text
端口定位应用进程
→ UDP/TCP 提供不同运输服务
→ TCP 建立连接并同步初始序列号
→ 序号 + ACK + 窗口 + 重传实现可靠字节流
→ rwnd 完成流量控制
→ cwnd 完成拥塞控制
→ FIN/ACK 释放两个方向的连接
```

<Callout type="info" title="先分清三个控制对象">

- **端口 / Socket**：解决“数据交给哪个应用进程”。
- **`rwnd`**：解决“接收方是否来得及接收”。
- **`cwnd`**：解决“网络是否承受得住继续注入的数据”。

</Callout>

## 1. 运输层的功能、端口与 Socket

IP 地址只能把数据送到某个主机或网络接口，而一台主机可能同时运行浏览器、DNS 客户端、邮件客户端等多个进程，因此运输层还必须识别具体的通信端点。

### 1.1 端口号

TCP 与 UDP 的端口号均为 16 bit，范围为：

$$
0\sim 2^{16}-1=65535
$$

运输层首部通常包含：

- **源端口号**：发送端应用通信端点；
- **目的端口号**：接收端应用通信端点。

<Callout type="warning" title="端口不是物理接口">

端口号是运输层的逻辑标识。它既不是网卡接口，也不能简单等同于“某个进程本身”；一个进程可以使用多个 Socket，一个端口也可能在不同 IP 地址、不同协议或不同连接上下文中出现。

</Callout>

### 1.2 Socket 与 TCP 连接

复习时可以把一个通信端点抽象为：

$$
\text{Socket}=\text{IP 地址}+\text{端口号}
$$

一条典型 TCP 连接由四元组唯一标识：

$$
(\text{源 IP},\text{源端口},\text{目的 IP},\text{目的端口})
$$

因此同一个服务器监听端口（如 80 或 443）可以同时服务多个客户端连接，因为这些连接的四元组不同。

## 2. 复用与分用

**复用（multiplexing）**&#x2060;发生在发送端：多个应用进程的数据交给运输层，再交给网络层发送。

**分用（demultiplexing）**&#x2060;发生在接收端：运输层根据首部信息把收到的数据交给正确的 Socket / 应用进程。

```text
发送端：多个应用进程 → 运输层 → 网络层
接收端：网络层 → 运输层 → 多个应用进程
```

### 2.1 UDP 与 TCP 分用的判断口径

- UDP 分用时，408 基础题通常重点看**目的端口号**；
- TCP 已建立连接后的分用，应结合连接四元组理解，而不是只看目的端口。

因此多个客户端可以同时访问同一服务器的同一 TCP 端口，而不会把各自字节流混在一起。

## 3. UDP：首部、特点与适用场景

> **真题考察**
>
> * 选择题：2014 年第 39 题
> * 选择题：2018 年第 39 题
> * 选择题：2021 年第 39 题
> * 选择题：2024 年第 39 题

UDP（User Datagram Protocol）提供**无连接、面向报文**的运输服务。

### 3.1 UDP 首部

<InlineSvg src="/images/computer-network/computer-network-transport-udp-001.svg" alt={"UDP 图 1"} />
<InlineSvg src="/images/computer-network/computer-network-transport-udp-002.svg" alt={"UDP 图 2"} />
<InlineSvg src="/images/computer-network/computer-network-transport-udp-003.svg" alt={"UDP 图 3"} />

UDP 首部固定为 8 Byte，由 4 个 16 bit 字段组成：

| 字段 | 长度 | 含义 |
| --- | ---: | --- |
| Source Port | 16 bit | 源端口 |
| Destination Port | 16 bit | 目的端口 |
| Length | 16 bit | UDP 首部 + UDP 数据总长度 |
| Checksum | 16 bit | UDP 校验和 |

因此 UDP Length 的最小值为：

$$
8\text{ Byte}
$$

若目的端口没有对应的应用程序，接收主机通常丢弃该 UDP 数据报，并可由 ICMP 返回**端口不可达**差错报文。

### 3.2 UDP 的核心特点

| 特点 | 含义 |
| --- | --- |
| 无连接 | 发送前不建立运输层连接 |
| 面向报文 | 基本保留应用交付给 UDP 的报文边界 |
| 尽力而为 | UDP 本身不保证到达、按序、不重复 |
| 首部小 | 固定 8 Byte |
| 无内建流量/拥塞控制 | 若应用需要，应自行设计 |
| 支持广播/多播 | 适合一对多数据报通信 |

<Callout type="info" title="UDP 不等于应用一定不可靠">

应用完全可以在 UDP 之上自行实现确认、重传、排序、拥塞控制或前向纠错。QUIC 就建立在 UDP 之上，同时提供可靠传输等更复杂机制。

</Callout>

典型应用包括 DNS、SNMP、实时音视频、在线游戏等。是否采用 UDP，关键看应用对消息边界、时延、控制开销和可靠机制的需求，而不是简单记成“UDP 快、TCP 慢”。

## 4. UDP 校验和

<InlineSvg src="/images/computer-network/computer-network-transport-udp-004.svg" alt={"UDP 图 4"} />

UDP 校验和覆盖：

```text
伪首部 + UDP 首部 + UDP 数据
```

### 4.1 IPv4 UDP 伪首部

IPv4 中常见 UDP 伪首部包含：

| 字段 | 长度 |
| --- | ---: |
| 源 IPv4 地址 | 32 bit |
| 目的 IPv4 地址 | 32 bit |
| 全 0 | 8 bit |
| Protocol | 8 bit |
| UDP Length | 16 bit |

UDP 的 IP Protocol 值为：

$$
17
$$

伪首部**只参与校验和计算，不会作为 UDP 首部实际发送**。

### 4.2 发送端算法

1. 计算时先把 UDP Checksum 字段置 0；
2. 拼接伪首部、UDP 首部和 UDP 数据；
3. 若总字节数为奇数，仅为校验计算在末尾补 1 Byte 的 0；
4. 按 16 bit 分组做**反码加法**；
5. 最高位产生的进位要回卷加到低 16 位；
6. 对最终 16 bit 和逐位取反，得到校验和。

若反码加法的中间结果为：

$$
1\,0000\,0000\,0000\,0001
$$

则先取低 16 位，再把最高位进位 `1` 加回来。

### 4.3 接收端验证

接收端重新构造伪首部，把收到的校验和也参与反码求和。若未检测到差错，最终结果应为：

$$
\texttt{0xFFFF}
$$

UDP 只负责**检错**，不会因为校验错误而自行恢复丢失的数据。

<Callout type="warning" title="IPv4 与 IPv6 的 UDP 校验和">

在 IPv4 中，UDP 校验和字段为全 0 可表示未使用校验和；在标准 IPv6 UDP 使用中，校验和通常是必需的。408 题目若未给特殊背景，按这一常规结论判断即可。

</Callout>

### 4.4 UDP 校验和计算易错点

- 忘记伪首部；
- 把 UDP Length 误写成只含数据；
- 奇数字节补 0 后误认为补的 0 会实际发送；
- 普通二进制加法后忘记**回卷进位**；
- 最后忘记逐位取反。

## 5. TCP 的服务特性

TCP（Transmission Control Protocol）提供**面向连接、可靠、有序、全双工、面向字节流**的运输服务。

### 5.1 面向字节流

TCP 不保留应用层消息的天然边界。应用连续写入的数据，在 TCP 看来是一串字节：

```text
应用写入：A | B | C
TCP 视角：连续字节流 ……
```

一次应用写操作不保证恰好对应一个 TCP 报文段；一次应用读操作也不保证恰好读出一个原写入块。

### 5.2 可靠传输来自哪些机制

TCP 的可靠性不是由单一机制实现，而是由以下机制共同完成：

```text
校验和
+ 字节序列号
+ 累计确认
+ 超时重传 / 快速重传
+ 滑动窗口
+ 接收缓存与乱序重排
```

TCP 是点到点协议，一条连接只有两个端点，不直接用于广播和多播。

## 6. TCP 首部

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-001.svg" alt={"TCP 图 1"} />

> **真题考察**
>
> * 选择题：2021 年第 39 题
> * 解答题：2012 年第 47 题

无选项时 TCP 首部最小为：

$$
20\text{ Byte}
$$

Data Offset 字段为 4 bit，单位为 32 bit（4 Byte）。最大取值 15，因此首部最大为：

$$
15\times4=60\text{ Byte}
$$

### 6.1 重点字段

| 字段 | 重点含义 |
| --- | --- |
| Source / Destination Port | 复用与分用 |
| Sequence Number | 本报文段数据第一个字节的序列号 |
| Acknowledgment Number | 下一个期望收到的字节序号 |
| Data Offset | TCP 首部长度，单位 4 Byte |
| Flags | 连接管理、确认等控制 |
| Window | 报文发送方通告给对端的接收窗口 `rwnd` |
| Checksum | 伪首部 + TCP 首部 + TCP 数据 |
| Urgent Pointer | `URG=1` 时配合紧急数据机制 |
| Options | MSS、窗口扩大、时间戳、SACK 等 |

### 6.2 六个经典控制位

| 标志 | 含义 |
| --- | --- |
| `URG` | Urgent Pointer 有效 |
| `ACK` | Acknowledgment Number 有效 |
| `PSH` | 希望尽快向应用交付 |
| `RST` | 复位连接 |
| `SYN` | 建立连接、同步初始序列号 |
| `FIN` | 关闭本方向的数据发送 |

<Callout type="warning" title="Window 字段不是 cwnd">

TCP 首部中的 Window 是发送该报文段的一方通告给对端的**接收窗口 `rwnd`**。`cwnd` 是发送方本地维护的拥塞控制状态变量，不直接写入 TCP 首部。

</Callout>

## 7. TCP 序列号与确认号的基本规则

TCP 的 Sequence Number 与 Acknowledgment Number 都是 32 bit，因此序号空间大小为：

$$
2^{32}
$$

达到最大值后按模 $2^{32}$ 回绕。

### 7.1 数据消耗序列号

若某段：

```text
seq = S
数据长度 = L Byte
```

则它覆盖的字节序号为：

$$
S\sim S+L-1
$$

若连续收到这些数据，则接收方下一步期望：

$$
ACK=S+L
$$

### 7.2 ACK 是“下一字节”

`ACK=N` 表示：

> 序号小于 $N$ 的连续字节已经收到，下一步期望序号 $N$。

这就是**累计确认**，不是“只确认第 $N-1$ 个字节”。

### 7.3 SYN、FIN 与纯 ACK

- `SYN`：即使不携带普通应用数据，也消耗 1 个序列号；
- `FIN`：同样消耗 1 个序列号；
- 不携带数据、SYN、FIN 的纯 ACK：通常不额外消耗序列号。

因此做题时可以统一写成：

$$
\text{下一 seq}=\text{当前 seq}+\text{数据长度}+I_{SYN}+I_{FIN}
$$

其中 $I_{SYN},I_{FIN}\in\{0,1\}$。

## 8. TCP 三次握手

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-002.svg" alt={"TCP 图 2"} />

> **真题考察**
>
> * 选择题：2011 年第 39 题
> * 选择题：2019 年第 39 题
> * 选择题：2020 年第 39 题
> * 选择题：2024 年第 38 题
> * 解答题：2016 年第 41 题
> * 解答题：2026 年第 47 题

设客户端 ISN 为 $x$，服务器 ISN 为 $y$。

### 8.1 第一次握手

客户端：

```text
SYN = 1
seq = x
```

状态：

```text
CLOSED → SYN-SENT
```

### 8.2 第二次握手

服务器：

```text
SYN = 1
ACK = 1
seq = y
ack = x + 1
```

状态：

```text
LISTEN → SYN-RECEIVED
```

### 8.3 第三次握手

客户端：

```text
ACK = 1
seq = x + 1
ack = y + 1
```

若该 ACK 不携带数据，它本身不再额外消耗序列号。客户端发送后进入 `ESTABLISHED`，服务器收到后也进入 `ESTABLISHED`。

### 8.4 为什么需要三次

三次握手至少完成两件关键工作：

1. 双方确认彼此的发送、接收路径可用；
2. 双方交换并确认彼此的初始序列号。

第三次握手还能避免服务器仅凭一个可能滞留在网络中的旧 SYN 就误认为新连接已经成立。

### 8.5 第三次握手能否带数据

协议上可以。因为客户端 SYN 已消耗序列号 $x$，第三次握手若携带应用数据，其第一个数据字节序号从：

$$
x+1
$$

开始。

## 9. TCP 四次挥手

<InlineSvg src="/images/computer-network/computer-network-transport-tcp-003.svg" alt={"TCP 图 3"} />

> **真题考察**
>
> * 选择题：2020 年第 39 题
> * 选择题：2021 年第 38 题
> * 选择题：2022 年第 39 题
> * 选择题：2024 年第 38 题
> * 解答题：2023 年第 47 题
> * 解答题：2026 年第 47 题

TCP 是全双工连接，两个方向的数据流需要分别关闭。设主动关闭方为 A，被动关闭方为 B。

### 9.1 典型四步

1. A 发送 `FIN=1, seq=u`，进入 `FIN-WAIT-1`；
2. B 回复 `ACK=u+1`，进入 `CLOSE-WAIT`；A 收到后进入 `FIN-WAIT-2`；
3. B 发送完剩余数据后再发 `FIN=1, seq=w`，进入 `LAST-ACK`；
4. A 回复 `ACK=w+1`，进入 `TIME-WAIT`；B 收到后进入 `CLOSED`。

A 等待：

$$
2MSL
$$

后再进入 `CLOSED`。

### 9.2 为什么通常是四次

建连时，服务器可以把“确认客户端 SYN”和“发送自己的 SYN”合并成一个 `SYN+ACK`。

释放连接时，收到对方 FIN 只说明：

> **对方已经不再发送数据。**

本方可能仍有数据没发完，因此通常先 ACK，对本方向数据发送完毕后再单独 FIN，于是形成 `FIN → ACK → FIN → ACK`。

若被动关闭方收到 FIN 时恰好也没有数据要发送，ACK 与 FIN 可以合并，所以“四次挥手”是经典常见流程，不是“永远必须恰好四个报文段”。

## 10. TIME-WAIT、MSL 与连接管理易错点

MSL（Maximum Segment Lifetime）表示一个 TCP 报文段在网络中可能存活的最长时间。主动关闭方在发出最后 ACK 后进入 `TIME-WAIT` 并等待 $2MSL$，主要有两个目的。

### 10.1 允许重发最后 ACK

若最后 ACK 丢失，被动关闭方会重传 FIN。主动关闭方仍处于 `TIME-WAIT` 时，可以再次回复 ACK。

### 10.2 让旧连接残留报文失效

等待足够长时间可以降低旧连接中的迟到报文干扰后续同一四元组新连接的风险。

<Callout type="warning" title="四个常见判断陷阱">

1. **主动关闭方不一定是客户端**，任何一方都可以先发 FIN。
2. 收到对端 FIN 后，本方仍可能继续发送数据，这叫**半关闭**状态的一种表现。
3. SYN 与 FIN 各消耗 1 个序列号，纯 ACK 通常不消耗。
4. `TIME-WAIT` 典型出现在**主动关闭方**，不是固定属于“客户端”。

</Callout>
